## 0. 核心裁定

這批對話暴露的問題，不只是個別答案品質不足，而是從「理解當前任務」到「調用既有工作、交付指定成果、驗收、吸收校正並避免重犯」的執行鏈不穩定。使用者多次要求回到原始核心、提供明確層級與細項、不要直接新增功能、先比對既有內容、避免無效驗證迴圈，以及真正交付指定文件；這些要求未能每次都轉化成執行前的硬性檢查。

本文件採用三份主要紀錄分工，不把所有內容塞進同一份長文：

1. **問題清單（第 16B 號）**：保存目前缺陷、嚴重度、對應責任、修正動作與狀態；每個問題只設一個主要 ID。
2. **修正開發紀錄（本文件第 49 號）**：保留事件順序、使用者校正、當時偏差、根因假說、修正與驗收結果，讓後續能追溯「為何改」。
3. **流程／通用規則參考（第 31 號）**：承載可遷移的候選方法；但未經實際觸發測試前，仍是參考候選，不代表已成為穩定運作的全域規則。

README 是導航與狀態入口，不再用它取代細節紀錄。此分工保留分類治理，同時避免事件歷程與問題狀態互相混雜。

### 2.1 這些事件共同指出什麼？

重複模式是：使用者提供了相當具體的方向，但執行過程仍可能產生「文字看似回應、實際交付不完整」的落差。這包括回到錯的問題、只交付概念而缺少細項、沒有產生指定文件、先提新增再查既有能力，以及把已寫出檢查規則當成流程已會自動執行。

這些表現不代表每一輪所有工作都無效。第 06、12、16B、28、31、47、48 號確實保存了部分問題、方法與驗收成果；缺陷是這些成果尚未成為穩定、可觀察、可重複執行的任務控制。建立文件是必要工作之一，但無法單獨證明流程已被接通。

## 4. 造成反覆偏差的根因分析

以下是依可觀察紀錄提出的根因模型。它用來設計可測的控制，不宣稱能直接觀察模型內部機制。

### RC-A｜缺少任務契約（對應 PROC-01、02、03、10）

任務進場時沒有始終把原始目的、不可偏移的主題、預期輸出、文件位置、必要細項及通過標準統一固定。於是可能產生語義上相關、但交付上不符合要求的內容；尤其「已討論」「已規劃」「已建立文件」「已驗收」容易被混同。

**修正方向：** 複雜任務開始前先形成任務契約；不需向使用者重複詢問已知資訊，直接從現有對話和檔案抽取並列明。遇到新的分支時，先判斷它是完成核心問題的必要工作還是旁支，不得自行以旁支替換原始目標。

### RC-B｜對話連續性與檔案真相未被強制核實（對應 PROC-04、11）

雖然案件資料夾已保存大量紀錄，仍可能發生既有成果未被及時找回、相似文件責任不清、再次規劃而未交付的情況。問題不只是資訊遺失，也包含沒有把「目前權威狀態」「歷史紀錄」「待辦」「實際已驗收」清楚分開。

**修正方向：** 以 Repository 中實際讀回的文件為依據，不以摘要或記憶取代檔案核實。每次新工作都先確認現有檔案、版本、唯一責任、相關待辦和上一輪結論；對近似文件明示主從關係。

### RC-C｜檢查既有框架多，從任務終點倒推少（對應 PROC-06、07、15）

既有框架的內部檢查擅長找重複、責任邊界和邏輯矛盾，卻無法保證找出整類尚未被建模的必要工作。第 47／48 號文件已記錄這種封閉集合審查問題。只增加逆向分析輪次、要求更深入思考或要求再次重讀，不會自動消除這個限制。

**修正方向：** 當任務屬高影響、核心架構宣稱完整、反覆發生漏項，或使用者指出偏移時，啟動任務終點倒推與外部需求比較；把缺口映射到既有責任，再決定修正，不因外部基準提到一個名稱就立即新增模組。

### RC-D｜校正停在當輪文字，沒有變成持續控制（對應 PROC-08、13）

問題被指出後，即使補寫解釋或新增紀錄，仍需要把它連到下一次遇到相同條件時會啟動的流程、實際測試和關閉門檻。沒有這條關聯，就會出現「文件說應該做，但下次依然要使用者提醒」的落差。

**修正方向：** 每項重大校正形成一筆可追溯鏈：
使用者原始要求 → 當時未達成之處 → 問題 ID → 根因假說 → 最小修正 → 觸發條件 → 回歸測試 → 執行證據 → 狀態。
缺少回歸測試時只能標記為 RULE_CANDIDATE 或 IMPLEMENTATION_PENDING。

### RC-E｜產物證據取代任務成效證據（對應 PROC-09、10）

文件數量、篇幅、架構細緻度或寫入成功，只能證明產物存在，不能證明工作流被實際執行或原始問題已解決。第 07、12、28、31、48 號已有類似原則，但本次仍需要把它落到對話交付的完成規則。

**修正方向：** 每次交付分別報告：文件／資料產物是否建立、是否從實際位置讀回、是否通過內容驗收、是否完成 Runtime 或外部行動、核心目標是否達成。不能以其中一項替代其他項。

### RC-F｜驗證沒有按風險及資訊價值控制（對應 PROC-12、14）

使用者提出的效率疑慮是合理的：如果每個小改動都執行完整審查，成本會過高；但如果對架構完整性只做一次自我檢查，又容易漏掉高影響缺口。

**修正方向：** 採風險分層而非一律全開。每個新檢查需回答：預計找出哪類錯誤、哪個決策會因此改變、成本是多少、何時停止。若連續兩輪沒有新增獨立證據、沒有改變問題排序，也沒有產生新行動，應停止該分支或改道，而不是只重寫結論。

## 5. 建議採用的文件治理方式

### 5.1 分類清單與歷程紀錄各自唯一負責

- **第 16B 號：現況問題清單。** 放入 SYS／PROC 問題 ID、嚴重度、狀態、控制點、驗收門檻及本文件連結；不把每次對話寫成長篇敘事。
- **第 49 號：修正開發紀錄。** 保存本次校正事件、原因分析、修正方式、測試要求和限制；每次新事件只新增有證據的條目，不覆寫舊的原因判斷。
- **第 31 號：通用方法參考。** 現階段保留候選性質，不因本次建檔就宣稱已整合為全域規則。
- **README：索引與摘要。** 只維護文件定位、關鍵狀態與相互連結；細節不重複貼入 README。

### 5.2 關於第 16A／16B 號

第 16A 與 16B 均有相關內容，不能直接刪除 16A，以免丟失歷史脈絡；但日後不應把兩者視為兩份同等權威、各自更新的問題清單。建議將第 16B 指定為擴展後的現行問題清單入口，第 16A 保留為早期診斷紀錄，並在索引上明確註記。這次只補清單與索引，不合併或刪除歷史文件。

### 5.3 每筆問題最小紀錄欄位

每個 SYS／PROC 問題至少維護：ID、描述、證據來源、影響、根因狀態（已證實／根因假說）、優先級、既有責任映射、控制措施、驗收測試、狀態、最後核驗日期、關聯文件。若欠缺事實，標 NOT_VERIFIED；若只形成方案，標 PLAN_ONLY；若已規格化但沒有實際測試，標 SPEC_ONLY／REGRESSION_PENDING。

## 6. 後續任務的最小有效工作流程

本流程不是每次都使用最高成本版本。依任務風險選擇輕量、標準或完整檢查；若發生核心偏移、交付缺失、反覆犯錯、宣稱完整、重大架構變更或新證據推翻前提，則提高審查等級。

1. **固定任務契約：** 記錄原始問題、不可偏移的核心、預期產物、範圍、寫入權限與成功條件。
2. **先查現有工作：** 讀回相關文件、問題清單、藍圖版本、索引與待辦；把已完成、未完成、阻塞與未驗收分開。
3. **確認任務層級：** 區分案件事實研究、流程根因診斷、系統架構設計、文件撰寫和 Runtime 驗收；不可用其中一種任務的成果冒充另一種。
4. **建立差距映射：** 將目標要求映射到現有文件與能力；逐項判定重用、修正、接入、合併、阻塞、不適用或確實缺失。
5. **先定義測試再實施：** 寫明通過條件、失敗條件與修正後要重跑的測試；不是產出完再依現有結果倒推標準。
6. **外部與反方檢查：** 高風險任務從外部要求倒推完整需求，檢查既有框架未包含的方向；由反方視角尋找漏項及最可能失敗的路徑。
7. **選最小有效變更：** 優先修正既有責任與流程，不為了填滿分類或對齊外部清單而擴建。
8. **執行並留下收據：** 記錄實際執行了什麼、結果是什麼、哪些沒有執行、阻塞在哪裡；把文件創建、讀回、內容驗收、Runtime 執行分開狀態化。
9. **讀回與索引驗收：** 核查實際儲存路徑、文件內容、版本、連結、索引和相依紀錄；若只成功寫入，不得聲稱內容已驗收。
10. **回寫問題與回歸測試：** 若使用者指出新錯誤，新增或更新 PROC/SYS 紀錄，連回開發紀錄及受影響文件，定義後續重犯測試。

### 6.1 防止無限驗證迴圈

完整性審查只在以下情況升級：核心目標改變；宣稱某層已完整；重大架構或責任變更；出現新的高影響缺口；盲測或 Runtime 測試失敗；同類錯誤重現；關鍵證據推翻前提。

停止條件為：本次範圍內的高風險要求已有明確責任和可執行路徑；未執行部分被清楚標為阻塞或待驗；代表性測試通過，或已明確記錄失敗及下一步。低風險、無新資訊的細節不應無限重複查驗。

## 9. 最終裁定

這次問題應採分類治理，而不是把所有問題、流程和歷史修正合成單一長檔。第 16B 號維持問題清單功能，第 49 號記錄事件歷程，第 31 號暫作通用候選參考，README 負責索引。每個問題以唯一 ID 連接狀態、根因、修正和測試，避免同一問題在多份文件中各自變更、彼此衝突。

最重要的修正不是要求使用者更精確地提醒，也不是反覆使用「深度研究」「逆向思考」等提示，而是讓系統在執行前固定核心與交付契約、查核已有成果、做外部需求／負向空間比較，在完成後以實際產物和執行收據驗收，並把每次校正轉為下一次可測試的防再犯控制。在這些回歸測試通過前，應將本次成果視為問題已登錄、修正流程已規格化，而非流程缺陷已全面解決。
