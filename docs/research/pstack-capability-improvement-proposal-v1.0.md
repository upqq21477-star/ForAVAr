## 摘要

本研究逆向拆解 pstack 的核心工作流程，並以 forAVAr 專案治理規則、P1 控制架構及 P2 目標系統為對照，找出可用於提升本系統能力的候選設計。

**核心判斷：pstack 最值得借鏡的是把工程方法寫成可重用、可分流、可驗證的工作流程；不應複製它來建立第二套中央控制系統。** 建議保留 P1／P2 的任務契約、Current 權威、執行證據、狀態提交、蒸餾與生命週期治理，再將經篩選的 pstack 類方法包裝成可替換的外部 Skill，由既有控制層調度。

優先研究的能力有五類：

1. **任務到流程的穩定路由：** 讓任務類型、風險、範圍與驗收條件決定所需流程，減少每次對話重述工作規則。
2. **多方案競賽與獨立評審：** 借鏡 arena，在高影響或高不確定性設計中比較候選、選擇基底、選擇性融合，再驗證合成成果。
3. **可追溯的平行工作：** 借鏡 swarm，先固定切分範圍與完成條件，要求每個工作者回傳結果、來源版本、驗證方法與缺口。
4. **問題重現到回歸證據的閉環：** 借鏡 TDD Bug Fix 流程，區分修正前失敗、修正後通過、局部驗收與整體驗收。
5. **Skill 本身的評估與治理：** 比較不同工作流程的真實效益，並對版本、宿主相容性、權限、資源預算、失敗降級與資料生命週期設置可檢查的契約。

**重要限制：** 本次已讀取 pstack 官方 README、部分核心 Skill、社群移植版說明，以及 P1／P2 README 和 Current。這是文件／原始碼層的逆向研究，不是 pstack 與本系統的實測效能比較。P2 Current 明確記錄整體 Runtime Truth 為 INCOMPLETE，部分局部案例仍為 NOT_RUN；不可將架構設計或檔案存在當成系統已驗收。

## 01. 研究目的與邊界

### 1.1 研究問題

本紀錄不以「安裝 pstack」為研究目標，而是回答：

- pstack 把哪些工程知識變成可執行流程？
- 這些流程解決了哪些 AI 工作中的常見失效模式？
- 哪些能力可補強本系統的任務分流、代理協作、驗收和長期維護？
- 哪些能力已與 P1／P2 的設計重疊，不應重建？
- 如何在不破壞既有權威、權限和證據規則下整合候選能力？
- 需要什麼實驗才能判定借鏡後確實提升系統，而不是增加流程與成本？

### 1.2 範圍及排除事項

- 研究對象：Cursor 官方 pstack、michael-denyer/pstack-claude、backnotprop/pstack、Agent Skills CLI，以及貼文提到的核心 Skill 與方法。
- 對照範圍：forAVAr 的紀錄／治理定位、P1 的控制層設計、P2 的目標架構與當前文件明列的執行證據。
- 本文件只提出研究和候選改進，不更新 P1／P2，不宣稱已修改正式藍圖。
- 本次沒有安裝或執行 pstack，也未在相同任務上完成基準測試。
- 不以模型數量、代理數量、程式碼行數或文件數量作為能力改善的充分證據。

## 02. 核心結論

### 2.1 pstack 的本質

pstack 是一套以 Agent Skills、playbook、工程原則、子代理協作及驗證步驟組成的工作流程集合。poteto-mode 是主要入口，負責依任務選擇流程並在需要時使用其他 Skill。

它不是新的基礎模型，也不等於一個獨立的全域狀態控制 Runtime。

### 2.2 與本系統的差異

| 面向 | pstack 的主要角色 | P1／P2 所定義的主要角色 |
|---|---|---|
| 任務分流 | 選擇適用的工程工作流程 | Brain 提案、任務分類及中央調度 |
| 分工 | 指定代理、切片、評審及聚合方法 | WorkSegment、TaskPacket、並行排程及結果收集 |
| 結果 | 候選成果、評審報告、測試／量測證據 | ResultPacket、ExecutionRecord、Evidence、Provenance |
| 狀態 | Skill 執行過程與工作報告 | Event Log、Reducer、Current State Projection |
| 長期維護 | 原則、Skill 與 playbook 的演進 | Current／History／Runtime 分離、蒸餾及生命週期治理 |
| 最終權威 | 由宿主流程及其能力決定 | 依既有權威、授權、驗收和狀態提交規則管理 |

此表比較的是文件明列的職責，不代表每一項均已在當前 P1／P2 Runtime 中完整接線或驗收。

### 2.3 建議採用原則

**採用可驗證的工作方法，不複製第二套系統控制核心。**

外部 Skill 可以提出流程、候選方案、程式差異及測試結果；正式任務範圍、權限、驗收、證據接納和全域狀態提交仍應由既有控制層負責。外部工作流程不得自行創造第二個 Current 權威。

## 04. pstack 工具逆向拆解

### 4.1 宿主與安裝工具

| 名稱 | 主要職責 | 對本系統的借鏡價值 |
|---|---|---|
| Cursor | pstack 的原生宿主之一，載入 Plugin／Skill 並提供代理環境 | 宿主能力必須和 Skill 規格分開 |
| Claude Code、Codex | 可透過移植版或 Plugin／Skill 形式使用相關工作流程 | 跨宿主需有相容性檢查及明確降級狀態 |
| npx skills add backnotprop/pstack | 安裝獨立鏡像中選定的 Agent Skills | 安裝工具不等於驗收工具；須記錄來源與版本 |
| michael-denyer/pstack-claude | 將 pstack 移植到其他 Agent Harness，並維護宿主適配內容 | 需要 adapter 邊界和相容性測試 |

**關鍵判斷：** 安裝成功只能證明 Skill 已被安裝或可供宿主讀取；不能證明自動路由、代理啟動、工具權限、測試執行或整體品質保證已正常工作。

### 4.2 setup-pstack

職責是配置任務角色與模型選擇，將模型配置從每次任務的臨時決策中抽離。

可借鏡項目：

- 角色與模型選擇應有明確規則，而非每次臨場猜選。
- 模型配置應可檢查、可版本化、可回退。
- 設定值、實際採用的模型和執行證據要分開。
- 路由不支援或模型不可用時，必須記錄實際降級方式。

不可直接推論：設定檔內容正確就表示模型真的依該設定執行；也不能由預設配置直接推斷品質或成本最優。

### 4.3 poteto-mode

職責是主要任務入口，依任務選用 playbook，並在需要時調用其他 Skill。

可借鏡項目：

- 將任務分類與流程選擇明確化。
- 固定各流程的適用條件、必要步驟和退出條件。
- 將可重用的工作規則保留在可維護的 Skill／流程目錄。
- 對被跳過、降級或無法執行的步驟留下明確狀態。

邊界：模型提出的任務分類或流程選擇是提案，不應自行改變全域權威狀態或跳過既有授權。

### 4.4 arena

核心流程：

1. 定義共同任務契約及 3–6 個具體評分條件。
2. 將同一任務交給多個候選者，隔離各自輸出。
3. 由獨立評審按條件比較候選。
4. 選擇可維護性和契約符合度較佳的基底。
5. 有選擇地整合其他候選的優點，不機械式貼上。
6. 驗證最終合成成果。

適用場合：架構選擇、重大介面設計、難以一次決定的高影響方案，以及有明確評分標準的競賽型任務。

不適用原則：不要對所有小修改無差別啟動多模型競賽。它會增加模型使用、評審和整合成本；共識也不等於真實性。

### 4.5 swarm

核心流程：

1. 先定義完成條件及交付物。
2. 選擇分切工作、相同任務競賽或混合方式。
3. 將工作範圍、驗證方法及輸出要求分配給不同代理。
4. 收集各代理的終止結果，檢查必要 SHA、方法和範圍證據。
5. 對缺少證據的結果保留缺口，不把缺口算成通過。
6. 形成一份統一報告，列出結果、問題、退出及未覆蓋範圍。

可補強之處：讓每個代理承接可識別的 WorkSegment，並把它的輸出映射到標準 ResultPacket 和 ExecutionRecord。分工數量本身不是完整性證據；每個必需切片都要有可核對結果。

### 4.6 tdd／Bug Fix 流程

核心流程：

問題理解 → 最小重現 → 修正前失敗證據 → 最小修正 → 修正後回歸證據 → 結果報告

官方流程並未要求在所有情境中都強行創造測試。如果測試路徑不明、成本不合理或依賴過重，允許採用最近似的可執行驗證方式。

可借鏡項目：

- 先把錯誤轉成可觀測行為，再修正。
- 修正前的失敗應是由目標問題造成，而非無關錯誤。
- 修正後重跑同一檢查，並保留測試與程式版本關係。
- 只有局部測試通過時，只能宣稱局部測試通過，不能替代整體驗收。

### 4.7 no-comments

目標是識別失效、重複或無實際約束力的註解，並評估可否轉換為型別、執行時檢查、測試或 lint。

可借鏡項目：

- 將機器可強制執行的限制轉成可檢查條件。
- 刪除註解前檢查它是否記錄不可由程式直接表達的必要理由。
- 限定審查範圍，拒絕沒有依據的廣泛修改。

不可採用的簡化規則：不得把「刪除註解數量」當作品質指標，也不得無條件刪除安全、相容性或外部契約的必要說明。

### 4.8 unslop

職責是清理 AI 常見的空泛用語、重複句型、冗詞、不明確歸因和不自然表達。

可借鏡項目：

- 讓紀錄更容易搜尋、比對和維護。
- 刪除空泛語句，要求明確來源或具體機制。
- 降低重複敘述，保留技術含義與不確定性。

限制：文字更精簡、語氣更自然，不代表資料正確或推理成立。此方法只應處理表達，不得以文風規則覆蓋來源、必要邊界和證據聲明。

### 4.9 Skill／流程本身的評估

pstack 還包含 eval 類工作流程，用以比較 Skill 或提示變更對代理行為的影響。這值得本系統借鏡：流程規則本身也應視為可版本化、可測試的系統資產，而非寫入文件後就假定有效。

候選驗證方式包括固定任務集、盲測比較、失敗案例分類、版本差異和回歸測試。具體樣本規模與統計門檻須在實驗設計階段先定義，不應事後根據結果調整。

## 05. 與 forAVAr／P1／P2 的能力映射

### 5.1 建議映射表

| pstack 方法 | 對應的系統責任 | 建議處理方式 |
|---|---|---|
| poteto-mode | Brain 提案、任務分類與流程路由 | 作為候選流程選擇器，由中央控制驗證與接納 |
| setup-pstack | Skill／模型角色配置 | 映射到可追溯的 Skill Manifest／執行配置，不自行取得狀態提交權 |
| arena | 候選方案生成、獨立評審、方案融合 | 只在高影響或高不確定性任務啟動；融合後重新驗收 |
| swarm | Scheduler、依賴 DAG、fan-out／join | 每個切片綁定範圍、輸入版本、輸出與完成證據 |
| tdd | Regression Selection／Execution | 綁定前後測試、程式版本、執行狀態及結果 |
| no-comments | 程式品質與約束編碼 | 作為受範圍限制的靜態審查，不替代正式驗收 |
| unslop | 文件整理、文字蒸餾與可搜尋性 | 只處理表達，保留語意、來源及不確定性 |
| eval | Skill／路由／流程的行為評估 | 將流程改動納入版本化評估與回歸選擇 |

### 5.2 已有設計重疊，不應重建的部分

P1／P2 文件已列出以下設計概念，整合時應確認既有實作及接線狀態，而不是另造一份相互競爭的系統：

- TaskPacket／ResultPacket 任務與結果契約。
- ExecutionRecord、Evidence、Provenance 及 DistillationRecord。
- Event Log、Reducer 和 Current State Projection。
- 並行調度、依賴管理與結果彙整。
- 變更影響掃描、回歸選擇、回歸執行和回滾。
- Skill Manifest 與外部 Skill Adapter。
- Current、History 與 Runtime 的資料分離。

這些能力在專案文件中有規格或實作聲明；本次未逐一重新執行驗收。因此，正式差距必須透過 Current、實作矩陣、程式接線及有效的執行收據確認。

## 06. 候選不足與待驗證差距

本節列的是**差距核實項目**，不等於已證實系統缺少該能力。

### GAP-CAP-01：任務分類到工作流程的實際接線

P1／P2 已有任務分類與路由相關設計／檔案聲明。待驗證問題是：每類任務是否真的能由有效的 Current 和正式規則選到合適流程，並保存實際採用、降級、略過及失敗原因。

建議證據：相同輸入的路由結果、配置版本、工作流程 ID、最終執行記錄及回歸案例。

### GAP-CAP-02：平行工作切片的完整性與隔離

需要驗證每個必需切片都有唯一範圍、輸入版本、執行者、輸出位置和完成狀態；代理退出、重複寫入、工作重疊、部分失敗及重試後，整體結果仍能正確判定。

建議證據：切片覆蓋矩陣、來源 SHA、失敗注入案例、聚合報告及未覆蓋範圍。

### GAP-CAP-03：候選方案評審的客觀性

需要驗證評分條件是否具體、候選是否真正遵守相同任務契約、評審是否獨立、融合後是否保留原始來源和重新驗收。

建議證據：候選版本、預先定義的評分表、評審理由、採用／拒絕紀錄、融合差異及驗收收據。

### GAP-CAP-04：流程／Skill 變更的有效性

需要驗證 Skill 修改是否改善可觀察結果，並確認改善不是因為更換模型、擴大成本、縮小測試範圍或事後修改成功標準所造成。

建議證據：固定任務集、版本綁定、盲測或獨立評審、失敗分類及成本量測。

### GAP-CAP-05：局部驗收與整體結案的邊界

需要確保單元測試、程式靜態檢查、模擬、端到端測試和真實 Runtime 各自保留正確的證據層級，不可互相代替。

建議證據：驗收政策、證據等級、執行版本／SHA 綁定，以及對無證據、過期證據和測試失敗的負例測試。

### GAP-CAP-06：外部 Skill 的版本、權限及相容性

需要驗證 Skill 來源、固定版本、宿主所提供的工具、實際模型配置、寫入範圍、成本上限和失敗降級規則。

建議證據：Skill Manifest、來源 commit、能力清單、權限政策、相容性測試、執行紀錄及移除／回退方式。

### GAP-CAP-07：結果蒸餾與紀錄精簡

需要驗證精簡程序是否只刪除重複或不再需要的內容，而不遺失必須保留的來源、衝突、未解決事項、失敗證據或引用關係。

建議證據：蒸餾前後差異、必要欄位完整率、反向查詢測試、重複資訊比對及歷史還原測試。

## 07. 能力提升提案與優先級

優先級表示研究與驗證順序，不代表已批准實作。

### P0：維持現有權威與驗收邊界

**CAP-PSTACK-P0-01：外部工作流程不得建立第二個 Current 或直接提交全域狀態。**

- 目的：避免不同工作流程對當前狀態、授權和完成狀態產生相互衝突的判斷。
- 借鏡來源：pstack 的 Skill 工作流程與代理操作方式。
- 系統依據：P1／P2 已定義的 Current 權威、中央控制和狀態提交責任。
- 驗收：負例測試證明外部 Skill 無權繞過中央提交；來源版本與結果可追溯。
- 狀態：PROPOSED；尚未整合驗收。

### P1：建立可重用的工作流程路由與契約

**CAP-PSTACK-P1-01：統一任務到工作流程的路由規格。**

- 任務類型、風險、範圍、成本預算、可用工具和驗收需求共同影響路由。
- 每個流程要聲明必要輸入、輸出、驗證方式、退出條件、失敗分支及降級方式。
- 同類情境要重用已接受規則，不應每次重新創造工作方法。
- 驗收：固定任務案例能穩定路由；未知或衝突情境會明確阻擋或進入指定處理路徑，而非默認成功。

**CAP-PSTACK-P1-02：為外部 Skill 增加標準輸入／輸出轉接。**

- 將可重用的 pstack 類 Skill 包裝成外部能力。
- 每次執行都要帶入必要的工作範圍、版本及權限限制。
- 結果返回標準 ResultPacket；執行證據由控制層記錄與驗證。
- 驗收：Skill 可被替換或停用，而不改變全域狀態權威或破壞呼叫契約。

**CAP-PSTACK-P1-03：標準化平行工作的切片與聚合規則。**

- 先確定全部必需範圍，再分配工作。
- 每一切片應有唯一標識、輸入版本、預期輸出、完成條件和驗證方法。
- 聚合時明確處理退出、缺失、重複、失敗和證據不合格情境。
- 驗收：任何必需切片缺失或證據過期，都不能被統計成整體通過。

**CAP-PSTACK-P1-04：建立 Skill／流程變更的評估閉環。**

- 將流程規則和 Skill 版本視為可以測試的系統資產。
- 在變更前固定任務集、衡量指標及接受標準。
- 比較變更前後的品質、證據完整性、人工介入、時間及資源成本。
- 驗收：只有達到預定標準且沒有違反必要邊界的變更，才可列為候選採用。

### P2：選擇性導入高成本工作流程

**CAP-PSTACK-P2-01：Arena 候選方案比較。**

適用於架構分歧、高影響設計或難以單次決策的任務。非重大任務不預設多模型競賽。

**CAP-PSTACK-P2-02：TDD 式問題重現及回歸證據。**

適用於有清楚、低成本可執行驗證路徑的 Bug。若無法重現，須記錄限制與替代驗證，不得虛構失敗測試。

**CAP-PSTACK-P2-03：以程式化條件取代可機械驗證的註解。**

先驗證註解是否過時、限制是否能被編碼、改動是否會破壞安全或契約資訊。不得以註解刪除數為驗收指標。

### P3：文字與知識整理

**CAP-PSTACK-P3-01：受控文字蒸餾與 AI 文風清理。**

將 unslop 類規則用在紀錄、交接、摘要和報告；必須保留來源、狀態、不確定性、反例及必要限制。

**CAP-PSTACK-P3-02：限制與設計理由的雙重表示。**

可以由程式驗證的限制應寫成 Schema、測試、lint 或 Runtime Gate；不能被機械驗證的設計理由，應以簡潔且可追溯的文字保留。

## 08. 建議的外部 Skill 契約

以下是提案所建議的最低契約欄位，不代表 P1／P2 目前已具備完全一致的實作。

| 欄位群組 | 最低要求 | 要解決的問題 |
|---|---|---|
| 身分與版本 | skill_id、版本、來源 URL、來源 commit／指紋、宿主相容範圍 | 避免來源不明及版本漂移 |
| 任務輸入 | task_id、工作範圍、Current／Work 引用、必要上下文引用、完成條件 | 避免任務理解不一致 |
| 能力與權限 | 所需工具、讀寫範圍、外部副作用、授權要求 | 避免越權與工具缺失 |
| 資源限制 | 成本／Token 預算、逾時、併發限制、停止條件 | 避免無界成本與代理擴張 |
| 執行識別 | run_id、attempt_id、輸入版本／SHA、實際模型／宿主配置 | 支援重試、去重與證據綁定 |
| 結果 | 狀態、輸出引用、修改差異、完成／未完成範圍、錯誤分類 | 避免空泛成功回報 |
| 驗證 | 驗證方法、實際輸出引用、測試狀態、驗證版本／SHA | 區分推理、靜態檢查和真實執行 |
| 來源與推導 | evidence refs、provenance refs、結論與來源關係 | 支援獨立稽核與逆向追溯 |
| 恢復方式 | retry／cancel／timeout 行為、idempotency、回退策略 | 避免重試造成重複副作用 |
| 結案與提交 | 誰可接受結果、誰可提交狀態、何種證據可解鎖下一步 | 保留唯一權威及驗收邊界 |

建議的控制流程：

REQUEST → ADMISSION → ROUTE → DISPATCH → EXECUTE → CAPTURE → VALIDATE → DISTILL → CENTRAL_COMMIT

這個流程是提案模型。正式採用前須與 P1／P2 既有 Schema、Command、Event、Reducer、Gate 及驗收契約做差異比對；不得另建一套平行狀態機而造成雙重真相。

## 09. 風險、反例與防護條件

| 風險 | 可能後果 | 必要防護條件 |
|---|---|---|
| 多模型共享錯誤前提 | 多數共識仍為錯誤結論 | 獨立測試、來源核實及反例檢查 |
| 代理漏做切片 | 報告看似完成但覆蓋不足 | 必需切片清單與逐項證據核對 |
| 同時寫入共享狀態 | 衝突、覆寫或無法復原 | 獨立工作區、中央提交、SHA 綁定 |
| 測試與需求不一致 | 測試通過但需求仍未滿足 | 預先固定任務契約及邊界案例 |
| 流程增加過多 | 成本上升、延遲增加、收益不明 | 依風險調度、成本預算、對照測量 |
| Skill 版本漂移 | 相同名稱產生不同執行行為 | 固定來源版本、相容性測試與回退 |
| 文風清理刪掉重要限制 | 文件變短但失去必要語意 | 保留來源、政策、例外及不確定性 |
| 把設定視為執行證據 | 虛報模型、測試或 Runtime 已完成 | 設定與觀測分離，要求執行收據 |
| 把局部 PASS 當成整體 PASS | 過早結案 | 明確劃分測試層級與全域接受條件 |
| 蒸餾遺失衝突或來源 | 長期紀錄不可逆地失真 | 蒸餾差異、必要欄位檢查與回溯測試 |

### 9.1 逆向壓力問題

在正式採用前，至少要能回答：

- 如果一個子代理完全沒有回報，系統會不會錯誤結案？
- 如果所有模型都同意一個錯誤方案，哪一個獨立機制能發現它？
- 如果修正後只通過一個單元測試，系統會不會誤判整體驗收完成？
- 如果外部 Skill 讀取的是舊版 Current 或舊程式碼 SHA，結果會不會被接納？
- 如果重試兩次產生重複副作用，系統是否可辨識及安全恢復？
- 如果 Skill 被移除、版本變更或宿主能力消失，中央路由能否明確降級？
- 如果蒸餾刪掉唯一的失敗原因或來源關係，是否能在結案前被發現？
- 如果多代理帶來的成本上升超過品質收益，系統是否有資料可停止使用此流程？

任何問題沒有可檢查的控制條件或測試案例，都應保留為待研究項目，不得只以提示詞宣稱已解決。

## 10. 驗證與對照實驗方案

### 10.1 實驗目的

驗證 pstack 類工作流程是否在相同任務條件下，改善系統的正確性、證據完整性、任務交接、失敗偵測與長期維護，同時控制時間、模型使用及人工介入成本。

### 10.2 對照組

| 組別 | 方法 | 驗證目的 |
|---|---|---|
| A：Baseline | 現有正式工作流程 | 量測現有基線 |
| B：Workflow | 使用選定的 pstack 類工作流程 | 衡量工作流程本身的差異 |
| C：Governed Workflow | 工作流程加上正式契約、證據綁定與中央驗收 | 衡量治理約束的額外效果 |

組別 B 不得繞過必要安全、授權與資料治理規則。所有組別都必須符合共同的最低安全條件。

### 10.3 任務集及公平性

任務集應至少涵蓋：

- 可以明確重現的 Bug 修復。
- 多個可比較的架構候選。
- 可自然切分的多工作者任務。
- 需要來源核實與不確定性保留的研究任務。
- 需要維護現有契約及歷史相容性的修改。
- 代理缺席、版本過期、工作重疊、測試失敗及預算耗盡等負例。

具體樣本數、重複次數、統計門檻及資源預算，須在正式實驗前定義。不能在看到結果後才修改成功標準。

### 10.4 指標

| 指標 | 定義方向 |
|---|---|
| 任務正確完成率 | 依預先定義且可獨立檢查的接受條件計算 |
| 缺陷／回歸率 | 包含原始缺陷未修正及修正引入的新問題 |
| 證據完整率 | 必要結果是否具備來源、版本、方法與執行證據 |
| 切片覆蓋率 | 必需工作範圍中，具有效結果的比例 |
| 誤結案率 | 缺證據、失敗或未完成卻被判完成的比例 |
| 路由準確度 | 選擇的流程是否符合事先標註的任務條件 |
| 成本與時間 | 模型／代理使用量、總耗時、重試和人工介入 |
| 狀態一致性 | Current、工作紀錄、結果和執行證據是否相互一致 |
| 可維護性 | 版本升級、流程更換及失敗恢復時的變更範圍與成本 |

### 10.5 驗收原則

- 每次實驗要記錄任務輸入、程式／配置版本、實際執行結果及退出狀態。
- 不可用文件檢查或模型自評替代要求的真實執行。
- 所有必要任務都要計入，包括失敗、阻塞及代理退出。
- 測試與實驗結果只能支持其實際涵蓋範圍。
- 未證明效益時，保留 NOT_ADOPTED；發現回歸時，依預先規定的回退流程處理。
- 正式採用之前，先確認實驗結果可重現，並由獨立檢查者核對證據。

## 11. 分階段研究及驗收門檻

### Phase A：現況差距盤點

產出：正式路由、Skill Manifest、TaskPacket／ResultPacket、證據記錄、驗收 Gate 的差異表。

驗收：每一候選差距都能指向現有來源、實作位置或有效的缺口證據。若現有能力已具備，不再重建。

### Phase B：規格對接

產出：外部 Skill 契約草案、任務路由條件、結果映射、權限／副作用政策及失敗狀態定義。

驗收：與既有 Schema、Current 權威及狀態提交規則無衝突，所有未知和缺欄情境都有明確處理方式。

### Phase C：最小原型

產出：一種低風險工作流程的受控原型。先選可客觀驗收的任務，不同時導入所有 Skill。

驗收：可以追蹤完整輸入、配置、實際執行、結果、驗證與退出狀態；失敗及取消也能留下正確記錄。

### Phase D：對照實驗

產出：Baseline、Workflow、Governed Workflow 的對照報告。

驗收：使用預先固定的任務集和門檻，報告效果量、成本、失敗案例及未解限制；不能只報最好的一次結果。

### Phase E：採用或拒絕

產出：正式決策紀錄，將候選分類為 ACCEPTED、REJECTED、DEFERRED 或 NEEDS_MORE_EVIDENCE。

驗收：被接受的能力有正式 owner、版本、引用、測試及退場方式；拒絕或延後的原因可追溯。任何提案都不能因文件已建立而自動升為正式架構。

- 候選不被採用時，標記 REJECTED 或 DEFERRED 及理由，不應讓過期提案繼續被誤判為現行規則。

## 13. 結論與尚未決策事項

### 13.1 結論

pstack 最值得本系統借鏡的不是增加一個新入口，而是把工程方法轉化成可重複執行、有明確完成條件、能追蹤缺口並要求證據的工作流程。

優先研究順序：

1. 路由與 Skill 契約的實際接線及負例驗證。
2. 多代理切片、證據收集和聚合完整性。
3. Bug 重現、前後測試及局部／整體驗收分界。
4. Skill 本身的版本化評估與對照實驗。
5. 在明確適用範圍下使用 arena 及文字／程式碼品質整理工具。

### 13.2 尚未決策

- 哪一個工作流程最適合作為第一個最小原型。
- 目前 P1／P2 哪些相關元件已完整接線、哪些仍只有設計或未驗證的程式碼。
- 外部 Skill 契約應沿用哪些既有 Schema，是否需要擴充欄位。
- 實驗的任務樣本、資源上限、統計門檻及正式採用條件。
- 哪些候選應列入正式問題清單，及其對應的正式 Issue／決策紀錄位置。

上述事項未完成差距盤點與證據核實之前，不應直接更新正式架構藍圖，也不應宣稱 pstack 已提升本系統能力。
