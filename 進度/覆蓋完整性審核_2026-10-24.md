# forAVAr 全量覆蓋基線審核

日期：2026-10-24
目的：確認現行正式清單是否足以追溯所有已登錄問題、功能與流程，作為後續 ZIP／HANDOFF 更新審核的基準。
範圍：只審閱目前 main 的權威 JSON 與其欄位／映射狀態；不宣稱已執行 Runtime。
基線：藍圖 v0.8（2026-10-24）。
結論：**NOT_PROVEN — 基礎 ID 清單可解析且唯一，但全量責任映射和驗收追溯尚未成立。**
本紀錄是基線缺口盤點，不代表每一項功能在程式中必然不存在；必須區分「未映射／未證明」與「已證明未實作」。

## 一、基線核對

權威來源：
- `docs/blueprint.json`：CORE、A1–A6、N01–N18、F0–F7。
- `docs/operating_contract.json`：INTAKE→AUTHORIZE→SELECT_SOP→PLAN→EXECUTE→VERIFY→PERSIST→REVIEW、L0–L3、PLANNING／REALIZATION／CLOSURE／FINAL_TEST。
- `docs/capability_registry.json`：功能／流程／問題修正／治理與架構需求登錄。
- `docs/problem_register.json`：問題描述與 PR ID。
- `docs/index.json`：導航、來源和歸檔追溯。

可確認的基本完整性：
- 能力登錄：175 項、175 個唯一 ID、0 個重複 ID、0 個 JSON 解析錯誤。
- 問題登錄：54 個 PR ID。
- 正式架構骨架：6 個主軸 A1–A6、18 個節點 N01–N18、8 個條件式框架 F0–F7。
- 正式運作契約有 8 個任務流程步驟與 L0–L3 分級；施工流程有四個正式階段。

上述只證明清單與架構定義存在且可解析，不證明每項能力已被實作、接線、驗證或在真實 Runtime 有效。

## 二、發現的核心覆蓋缺口

### COV-01｜S1｜175 項登錄沒有完成可驗收的責任映射

實際核對 `docs/capability_registry.json`：
- 175 項中有 132 項缺少 `mapping` 欄位。
- 缺少 mapping 的 132 項分成兩組：
  - 78 個 `BASELINE_CAPABILITY`：P1-F01–P1-F48 以及 P2-F01–P2-F30。
  - 54 個 `PROBLEM_REMEDIATION`：PR-001–PR-054。
- 其餘 43 項雖有 mapping 欄位，但欄位值仍可能是待決、候選、未審查或未驗證狀態；「有字串」不等於「已驗證映射」。

影響：
- 無法僅依本登錄逐項證明 78 個 P1/P2 基礎功能分別由哪些 forAVAr 的 A/N/F、既有能力、SOP、失敗出口和驗收案例承接。
- 無法僅依本登錄證明 54 個問題都具有明確的控制點與回歸檢查。
- 後續更新可能在不易察覺的情況下丟失功能語意、失效情境或舊問題對應。

重要限制：這是覆蓋可追溯性的缺口，不是證明 132 項都未被程式實作。要判定實作情況仍需檢查正式程式、測試及實際執行證據。

### COV-02｜S1｜54 個問題修正項缺少 mapping 與 decision

`problem_register.json` 對 54 個問題均有 ID、嚴重度與簡述；但能力登錄中相對應的 54 個 `PROBLEM_REMEDIATION` 項目全數缺少 `mapping`，也全數缺少 `decision`。

這代表問題「被列出」不等於問題「已被系統處理」。每個 PR 項目應可追溯到：
1. 觸發該問題的輸入／上下文／失敗情境。
2. 預防或限制控制點。
3. 偵測及分類方式。
4. 修復、恢復、阻斷或保留未知的處理路徑。
5. 對應的 A/N/F、能力 ID、流程／SOP。
6. 正常、反例、負向、回歸或復發驗收案例。
7. 真實成熟度與證據位置，以及仍存在的殘餘風險。

問題描述文件本身應維持只描述問題，不應把解決方案塞回問題登錄；完整映射可放在專門的覆蓋矩陣／工作紀錄中，並由權威登錄提供穩定 ID。

### COV-03｜S1｜正式登錄的必填欄位規定與實際資料不一致

能力登錄的 `source_manifest.required_fields` 將 `mapping`、`implementation/evidence`、`acceptance` 和 `decision` 等列為必要欄位，但實際資料存在：
- 132/175 項缺少 mapping。
- 70/175 項缺少 decision。
- 70 個缺少 decision 的項目由 54 個 PR 修正項，以及 16 個跨切面／架構／視圖項目構成。

這是登錄資料契約和實際資料之間的可檢查差異。不能只將缺欄當作不影響運作的格式問題，因為 mapping 與 decision 是判定覆蓋範圍及是否採納的重要資訊。

本輪不直接替這些項目臆造決策。應先釐清欄位適用規則，再由有權的正式更新流程填入真實且有依據的值；在此之前以 `NOT_ASSESSED`／`NOT_PROVEN` 呈現，不能當成通過。

### COV-04｜S1｜流程／功能到主架構尚無單一已稽核的完整矩陣

現行登錄已有明確缺口訊號：
- `VIEW-006`：P1/P2 功能到 forAVAr 四層的雙向映射，標記為缺少單一受稽核矩陣。
- `VIEW-008`：問題→控制點→回歸／復發檢查追溯，標記為仍待驗證。
- 10 個 `FIXED_PROCESS` 的 mapping 是 `SOP_TO_FRAMEWORK_MAPPING_NOT_VALIDATED`。
- 7 個 `DECISION_PENDING` 流程仍是 `NOT_DECIDED`。
- 另有 SOP 候選、正式 SOP 與治理／架構／視圖項目處於不同成熟度；不能將其全部視為已整合。

因此，尚不能由現行清單證明全部流程都能在正確條件下被觸發，並可完成輸入、執行、失敗分支、狀態回寫、交接及恢復。

## 三、對更新審核的強制要求

對每次新 ZIP／HANDOFF，審核者必須比較「更新前基線」與「候選更新」至少包含以下四組：

| 覆蓋域 | 全量範圍 | 必須證明的事 |
|---|---|---|
| 問題 | 54 個 PR ID | 每個問題都有處理路徑、控制點、反例／回歸驗收與殘餘風險狀態 |
| 功能 | 175 個登錄 ID，含 P1／P2 能力、問題修正、治理與架構／視圖項目 | 每項都保留語意、ID、責任映射、成熟度、驗收依據；共用機制可承接多項功能，但需有可追溯證明 |
| 流程 | 固定流程、正式 SOP、候選／待決 SOP、L0–L3 任務路由、四階段施工與交接流程 | 觸發條件、輸入、執行責任、輸出、失敗／未知／停止分支、回寫、恢復及驗收可追溯 |
| 架構 | CORE、A1–A6、N01–N18、F0–F7，以及權限／Runtime／狀態規則 | 新增／修改／移除是否偏離核心、形成重複責任、打斷依賴或破壞失敗出口 |

每個差異必須歸類為保留、修改、合併、替代、退場、待裁決或新增。合併或替代必須保留舊 ID 到新責任的追溯關係；任何不再獨立存在的功能，都要證明它的必要行為已由其他責任完整承接。

## 四、怎樣才算「系統能處理」

不得把以下幾種狀態混為一談：

- **有登錄**：清單中有該 ID。
- **有設計**：定義出處理路徑和契約。
- **有實作**：程式存在且有對應程式路徑。
- **已接線**：可透過實際系統路由呼叫，非只有孤立函式或 mock。
- **已測試**：有實際命令、環境、輸出與可回讀證據。
- **真實 Runtime 驗證**：在目標環境對應情境實測，有結果、失敗出口與副作用紀錄。
- **持續有效**：相關更新後有回歸證據，且復發／退場機制可追溯。

完整系統最終驗收，必須讓所有必要問題、功能與流程都有可執行或可路由的處理方式，並在其宣稱的成熟度上提供相符證據。若項目被授權合併、退場或由其他能力承接，仍須保留原 ID、決策依據與等價行為驗收。只留一條「通用推理」描述、只連到 CORE、或只有功能名稱都不算足夠映射。

中間增量允許只實作其中一部分，但交付狀態必須標明本批完成範圍、原有缺口、此次新增／修復／引入的差異，不可宣稱全系統完成。候選與待決項目必須保留其非正式狀態；需要使用者裁決的項目應明確列出，不能由審核者代做正式採納決定。

## 五、與 B8 審核的關係

B8 HANDOFF 提到新增 FINAL_TEST harness、87 項測試報告及合成比較，但沒有提供全數 175 個功能、54 個問題、所有流程／SOP 到架構責任與驗收案例的完整覆蓋矩陣。因此，本輪只能確認交接描述存在，不能確認 B8 有造成或修復哪些具體功能覆蓋差異。

B8 的程式碼級審核仍受 ZIP 無法解包限制。此限制不應被隱去；也不應把基線已存在的 mapping 缺口錯算成 B8 新引入的程式缺陷。後續拿到可解包的檔案內容後，應先逐檔差異，再做 ID／責任／驗收覆蓋對帳。

## 六、優先處理順序

1. 保全現有 175 個 ID 與 54 個問題 ID，不先刪除、重編或合併。
2. 補齊或建立唯一可稽核的追溯矩陣：問題↔能力／功能↔流程／SOP↔CORE/A/N/F↔測試／驗收↔成熟度／證據。
3. 對現有無 mapping、無 decision、未驗證 mapping 逐項分類；依據不足的保持未決，不臆造答案。
4. 對每次更新執行前後差異與覆蓋回歸；驗證原功能語意沒有遺失。
5. 在完整覆蓋有證據之前，總體完整性保持 `NOT_PROVEN`；不能由單一 harness 或測試總數替代。

本紀錄不直接修改正式藍圖、能力登錄表或問題登錄表；正式資料更新需走現有授權及變更流程。
