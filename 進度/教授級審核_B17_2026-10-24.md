### 2.2 A-001：交接宣稱的 ZIP SHA-256 與實際封包不一致（阻擋驗收）

HANDOFF 宣告 `sha256 前 16 碼 909f94267638d853`。本次從 GitHub 取得該 ZIP 的實際位元組，確認大小為 129,209 bytes，並重新計算完整 SHA-256：

- 實際 ZIP SHA-256：`3af5194f88bb3d3a8090b0171c6f53ad5b5a9a0faadda0f22bd1951a19bf1702`
- HANDOFF 宣告前 16 碼：`909f94267638d853`
- 比對結果：**不一致**。

ZIP 自身 CRC 全通過，因此目前證據指向「交接與封包不是同一個位元組版本／校驗值過期或抄錄錯誤」，而不是 ZIP 內部損壞。原因尚未證明，不直接推斷為惡意竄改。

**影響：** 無法證明 HANDOFF、COVERAGE_REPORT 與實際 B17 產物為同一版本。不得進入最終驗收，也不能只改文字後假定完成。

**修復驗收條件：**
1. 由實際要驗收的 ZIP 重新計算完整 SHA-256。
2. 將完整 SHA-256、檔案大小、檔名、基線完整 commit、分支、封包內是否含 `.git` 寫進同一份 HANDOFF。
3. 從該 ZIP 重新產生覆蓋清單，記錄產生工具版本／來源 commit／封包 SHA-256。
4. 提交後回讀三檔，逐項重比對；所有版本識別相符後才解除本項阻擋。

成熟做法參考：[SLSA — Verifying artifacts](https://github.com/slsa-framework/slsa/blob/main/spec/verifying-artifacts.md)。SLSA 強調驗證者要確認 provenance 確實對應被驗證的產物，而非只相信產物旁的文字宣告。此專案最低限度應先做完整 digest 綁定；日後若有建置簽章或 provenance，再驗證建置者與來源。

## 3. 教授總評

B17 的工程方向大體一致：採用注入式模型呼叫、明確輸出契約、有限詞彙、未知狀態、失敗封閉，以及將 SLOT 與已驗證的真實 Runtime 分開標示。交接也明確承認 FINAL_TEST、真實 adapter、Runtime 效果尚未驗證，這比把合成測試說成真實驗收更可靠。

但這批交付還不能驗收。第一，交接的 ZIP 身分校驗不成立；第二，新增加的 feedback／intake 對「有填證據 ID」與「證據真的存在且支持該主張」沒有建立參照完整性。後者會讓形式正確的模型輸出被錯誤升格為已支持的根因或已測量的採納決策。這不是靠提示詞提醒模型就能補足的。

目前可證明的是：封包內部完整、清冊有列出預期數量、契約測試程式存在。不能證明的是：交接和封包同版、131 項測試在本次環境重新通過、模型推理品質合格、adapter 已接入真實 Runtime、FINAL_TEST 通過。

## 4. 優點（有證據支持）

1. **狀態標示相對誠實。** `blueprint.json` 將真實 adapter、真實 Runtime 與 FINAL_TEST 保留為未執行／未驗證，而非宣告整體系統已通過。
2. **模型輸出有基本契約。** `adapters/model_adapter.py` 對 task_id、必要欄位、狀態詞彙及部分違規輸出做檢查，並把模型無法自行觀察的執行證據降級。
3. **失敗後的規則蒸餾有正確的安全意圖。** feedback 在根因未知時清除 `rule_candidate`；intake 在沒有非空「已測量」基線證據列表時將 ADOPT 降為 DEFER。
4. **清冊規模與表格標題相符。** COVERAGE_REPORT 分別列出 54 個問題、121 個功能、44 個流程；各區段內未發現重複 ID。
5. **可恢復／不可信資料風險有被納入設計。** 包內有 release transaction、state bundle、content guard、retry policy 與對應測試；這些只代表程式及測試存在，不能外推為真實 Runtime 已有效。

## 5. A 級問題

### A-001 — ZIP 身分校驗不一致

證據與修復條件見第 2.2 節。此問題阻擋 B17 最終驗收。

### A-002 — feedback／intake 接受未經查證的證據 ID

**位置：** `adapters/model_adapter.py` 的 `parse_output("feedback")` 與 `parse_output("intake")`；`tests/test_model_adapter.py` 中的 `FB`／`IN` 測試資料。

**觀察：**
- feedback 將 `root_cause_status=SUPPORTED` 的最低門檻實作成 `evidence_ids` 清單非空；沒有檢查 ID 是否存在於實際 evidence records，也沒有檢查證據狀態、種類或是否支持根因。
- intake 將基線比較視為「已測量」的最低門檻實作成 `status == MEASURED` 加上非空 `evidence_ids`；沒有比對該 ID 是否存在、證據是否屬於該基線比較，或 `existing_capability_ids` 是否存在於 `known_capabilities`。
- 目前測試使用 `E1` 即可讓 feedback 保留 SUPPORTED／rule_candidate，且讓 intake 保留 ADOPT；測試沒有提供可查對的證據索引。這證明契約允許未綁定的 ID，不只是尚缺某個測試案例。

**最壞後果：** 模型可以輸出一個不存在或不相關的 ID，通過表層驗證；未被證明的根因可能被蒸餾成規則，未被證明的能力比較可能被接受。這直接削弱 PR-006／PR-011／PR-037／PR-048 的原本控制意圖。

**成熟做法與取捨：** OWASP 指出，將不可信內容在 prompt 中標記為資料不是安全邊界；輸出與工具參數仍須在模型外部、靠確定性程式驗證，並在實際工具邊界執行權限與最小權限控制（[OWASP LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)）。本案不需要先增加更多角色或模型；先在 adapter 契約層建立明確的 evidence/capability lookup 即可。代價是必須讓 adapter 接收可查證的證據索引，並處理缺失、衝突、過期與錯誤引用。

**修復驗收：**
1. 把本輪可用的 evidence records／可信 evidence index 傳入 feedback；只有 ID 存在、狀態允許、來源／版本可追溯且符合該主張的證據才可支持根因。
2. intake 必須對照輸入的可信基線測量記錄，而非只相信模型自報 `MEASURED`；採納決策引用的 evidence IDs 必須存在且與該比較綁定。
3. 對 `existing_capability_ids` 執行 registry membership 檢查；未知 ID 不得當成可相容或未被覆蓋。
4. 加入至少四個負向／回歸案例：不存在 ID、存在但來源不相干、狀態為 CLAIMED／UNVERIFIED、基線過期／與候選版本不符。這些案例必須拒絕升級為 SUPPORTED／ADOPT，並保留可診斷的原因。
5. 不得只以模型 prompt 說明或增加同義詞黑名單作為修復。

目前未有 B16 封包可作直接逐檔比對；本缺陷確實存在於 B17 封包中的 feedback／intake 契約，但其相對 B16 是否為本批新增的退化，標為 **NOT_PROVEN**。

## 6. B 級問題

### B-001 — 方法路由的實際契約弱於 prompt 要求

prompt 要求 route 至少列出兩個候選方法；但 adapter 只拒絕空的 `candidate_methods`，允許只有一個候選的方法輸出。結果是提示層要求「比較替代方案」，契約層並未強制這個條件。

**修正：** 若「至少兩個候選」是必要接受條件，應由 validator 強制，並測試零個、一個、兩個、重複候選、所選方法不在候選清單等案例。若有任務允許單一候選，應把條件設成依任務型態決定，而不是 prompt 與 validator 不一致。

### B-002 — 覆蓋清冊未綁定它所描述的產物版本

COVERAGE_REPORT 有 54／121／44 的條目，但本檔未記錄來源 commit、產生時間、ZIP SHA-256 或 coverage 工具版本，無法證明它是從目前這個 B17 ZIP 產生。交接雖稱由工具產生，但該聲明不能代替來源綁定。

**修正：** 報告頂部加入生成環境、完整 source commit、ZIP SHA-256、工具版本／命令、各清單 ID 摘要及錯誤數。若來源 digest 不一致，報告不得用於驗收。

### B-003 — 回復點目前未能在可見庫存中確認

HANDOFF 指定使用 B16 ZIP 回到本批起點，但本次檢查的 `forAVAr/進度` 現行檔案與 `forAVArb` 目前可見檔名樹中，未找到名稱匹配的 B16 ZIP／HANDOFF。這不證明 Git 歷史或其他位置一定沒有備份，但本輪無法確認回復點可取得。

**修正：** 明列回復包的實際 repo/path、完整 SHA-256、基線 commit 與還原前提；執行一次只讀還原演練，確認產物能回到記錄中的基線。沒有可用回復檔時，狀態必須標 NOT_VERIFIED。

## 9. 最小修正路線

1. **先修交接身分：** 重算並校正 HANDOFF 的 ZIP SHA-256；讓覆蓋清冊綁定同一個產物；確認 B16 回復點。
2. **再修證據參照完整性：** 為 feedback／intake 加入可信 evidence lookup 與 capability registry lookup，並加入負向測試。
3. **修正契約落差：** 讓 route 候選數規則在 prompt、schema、validator、測試間保持一致。
4. **執行驗收：** 在可重現的 Python 3.12 環境執行 `python -m unittest discover -s tests`、`python tools/check_consistency.py`、`python tools/coverage.py`、`python tools/standard_verify.py`；保存原始輸出、命令、環境、起訖狀態與產物 SHA。這些命令本輪未執行。
5. **最後才跑 FINAL_TEST：** 先固定 rubric 與樣本；真實模型由同一對話產生的輸出，只能標 CALLER_SUPPLIED／非獨立驗證。不可把它當成獨立 Runtime 測試。

## 10. 本次對審核題詞的實測結論

**首輪題詞試審有效，但不能據此宣稱題詞已被全面驗證。** 它促使審核者檢查封包實際位元組，而非只相信 HANDOFF，因而發現 SHA-256 不一致；也從新增 adapter 的程式與測試中定位到「非空 evidence ID 被當成證據成立」的契約問題。這兩項都能導向具體、可驗收的下一步，而不是再增加一輪泛化檢查。

題詞的使用原則應保留：先核對身份與權威、全量對帳、區分 FACT／CLAIM／INFERENCE／UNKNOWN、以反例測試關鍵控制，並在無新證據時停止。後續可再把「證據 ID 必須解析到可信來源」列為固定檢查項；不需要擴大角色清單或增加新的驗證層級。
