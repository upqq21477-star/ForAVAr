## 1. 大方向判斷

你的疑慮有文件證據支持。問題不只是執行者可能跳步，而是**完成定義與階段放行規則有落差**：B17 把「每個 SLOT 有 adapter 範本／契約入口、GAP=0」當成建置完成的主要依據，接著排入 B18 FINAL_TEST；這不等於所有必要功能的規劃、語意契約及整批閉環已完成。

四階段本身有明確順序：PLANNING → REALIZATION → CLOSURE → FINAL_TEST。局部測試可以協助施工，但不能代替規劃完成，也不能把未規劃完整的功能直接交給使用者做最終驗收。

目前不能單憑缺少紀錄斷言每一步都「一定沒做」；準確裁定是：**沒有足夠證據證明當前批次已通過前置 Gate，因此宣稱 BUILD_COMPLETE_PENDING_FINAL_ACCEPTANCE 及排入 FINAL_TEST，依現有證據不成立。**

## 2. 核心流程漏洞

### A-003｜把「有入口／有映射」當成「已規劃完成」，階段放行失去意義

- **正式契約：** [operating_contract.json — build_stage_flow](../docs/operating_contract.json) 定義 PLANNING 要凍結 175 項登錄／PR／SOP 對帳、Runtime contract、StateBundle、生命週期、權限及驗收範圍；REALIZATION 只能實作已通過規劃與授權的增量；CLOSURE 要核對依賴、狀態、權限、回復、索引與退場風險；FINAL_TEST 必須在版本凍結後執行。
- **批次規則來源：** [施工計畫 v0.2](https://github.com/upqq21477-star/forAVArb/blob/main/%E6%96%BD%E5%B7%A5%E8%A6%8F%E5%8A%83/forAVAr_v0.7%E6%AD%A3%E5%BC%8F%E8%97%8D%E5%9C%96%E8%90%BD%E5%9C%B0%E6%96%BD%E5%B7%A5%E6%8E%92%E7%A8%8B/00_%E6%95%B4%E9%AB%94%E6%96%BD%E5%B7%A5%E8%A8%88%E7%95%AB_v0.2.md) 與[工作包／驗收矩陣 v0.2](https://github.com/upqq21477-star/forAVArb/blob/main/%E6%96%BD%E5%B7%A5%E8%A6%8F%E5%8A%83/forAVAr_v0.7%E6%AD%A3%E5%BC%8F%E8%97%8D%E5%9C%96%E8%90%BD%E5%9C%B0%E6%96%BD%E5%B7%A5%E6%8E%92%E7%A8%8B/02_%E5%B7%A5%E4%BD%9C%E5%8C%85%E8%88%87%E9%A9%97%E6%94%B6%E7%9F%A9%E9%99%A3_v0.2.md) 明確要求工作包不得自行跨階段；每個施工批次都要依序完成四階段，任一必要項未過 Gate，整批不得放行。
- **直接證據：** [HANDOFF_B17.md](HANDOFF_B17.md) 把 B17 狀態標為 `BUILD_COMPLETE_PENDING_FINAL_ACCEPTANCE`，主要完成依據是「所有 SLOT 有入口／範本／契約驗證；PROCESS 依既有裁決維持流程」，並把 B18 指定為 FINAL_TEST。這證明了 adapter scaffold 和部分契約測試存在，但沒有逐項展示每個必要功能已完成規劃的責任矩陣，也沒有附整批 CLOSURE 的完整核對證據。
- **漏洞本質：** 「清冊有 mapping」、「有程式入口」、「有測試檔」是不同成熟度，不能互相替代。COVERAGE_REPORT 的 `GAP 0` 只表示清冊列出的每項都有某種機制標籤；同一份報告明確保留 SLOT（效果未驗證）及 PROCESS（人工流程）。它不代表 121 個功能均已完整規劃或實作。
- **建議：** B17 不應直接以現有證據進入 FINAL_TEST。先回到當前批次 PLANNING，補齊缺少的功能規劃與接受條件；再完成整批實作、CLOSURE 與最終驗收。
- **驗收條件：** 每個納入當前批次的必要 ID 都有可追溯的需求來源、觸發條件、輸入／輸出、責任映射、依賴、權限、副作用、錯誤／拒絕／UNKNOWN 出口、停止／回復方式、接受條件與負向案例；未完成項必須明確延期或排除，不能留在批次內卻當成已完成。

### A-001｜ZIP 身分校驗不符 — 仍阻擋驗收

實際 ZIP SHA-256 為 `3af5194f88bb3d3a8090b0171c6f53ad5b5a9a0faadda0f22bd1951a19bf1702`，而 HANDOFF 宣稱前 16 碼是 `909f94267638d853`。ZIP 內 38 項 CRC 均通過；目前證明的是封包識別不一致，而非封包損壞。先把 ZIP、HANDOFF、COVERAGE_REPORT 綁定到同一個完整 SHA-256，再談驗收。

### A-002｜feedback／intake 接受未經查證的證據 ID

新增 adapter 只檢查根因／基線的 evidence ID 清單非空，沒有查證 ID 是否存在、來源狀態／版本是否適用，也沒有完整核對 capability ID。可能把未證明的根因蒸餾成規則，或接受缺乏實測依據的能力。

注意：既有 `runtime/foravar_vertical_slice.py` 的 evaluation 路徑已做 evidence lookup；漏洞範圍是新增加的 feedback／intake 介面，不應擴大描述成整條主流程都沒有證據查核。修復方式是把可信 evidence index／capability registry 傳入並在程式端查核，為不存在、無關、未驗證、過期 ID 加負向測試。

### B-001｜路由規則不一致

route prompt 要求至少兩個候選方法，但 model adapter 只要求清單非空。主流程已有檢查重複候選及 selected method 是否在清單內；缺口是「至少兩個」沒有被一致地定義為硬性條件。應在 prompt、validator、主流程與測試間統一規則。

### B-002｜覆蓋清冊與回復證據不足

COVERAGE_REPORT 沒記錄來源 commit、ZIP SHA-256、生成時間與工具版本，無法證明清單對應本次封包。B16 回復包在本輪可見位置中未找到，故回復能力標記 NOT_VERIFIED；不能假設不存在，但也不能假設可用。

## 3. 為什麼會發生

1. **成熟度混用：** CODE／SLOT／PROCESS 都被算成「已映射」，但這三種狀態的含義完全不同。SLOT 有入口，不代表能力有效；PROCESS 有 SOP，不代表流程已執行。
2. **完成條件過弱：** `build_scope` 的「完成」偏重範本與契約入口是否存在，沒有要求所有必要功能的規劃欄位與 CLOSURE 證據逐項通過。
3. **Gate 是描述，不是有效阻擋條件：** 四個階段寫在流程裡，但交接沒有逐 Gate 列出 PASS／FAIL／UNKNOWN 及對應證據；所以狀態可以在前置條件未被證明時被推進。
4. **把驗證當成補規劃：** 測試可以驗證已定義的行為，或在規劃階段做有明確假說的小型探索；但不能讓使用者替尚未完成的規劃補決策，更不能把探索結果當最終驗收。

這是流程定義與放行控制的系統性缺口，不應只歸咎於某一位執行者。

## 4. 必須改成的放行規則

- **PLANNING 未完整，不得 REALIZATION：** 當前批次所有必要功能的責任、契約、依賴、接受條件與失敗路徑都要可判定；未決項須移出範圍或明確標為阻塞。
- **REALIZATION 未完成，不得 CLOSURE：** 所有已批准的批次項目都要有實際改動或明確的非實作裁決；局部測試只能做施工診斷。
- **CLOSURE 未完成，不得 FINAL_TEST：** 要有呼叫鏈、跨檔依賴、狀態／錯誤傳遞、權限、封包身分、回復與未解項清單。
- **前置 Gate 未通過，不可把正式驗證責任交給使用者：** 先由執行者完成可自行完成的整理與測試；只有真正需要使用者權限、外部環境或產品決策時，才提出單一、具體請求。規劃階段若需要探索性測試，必須標成探索／診斷，不得稱作 FINAL_TEST。
- **最後才 FINAL_TEST：** 凍結版本、測試名冊、rubric 與樣本；保存可回讀的實際輸出。由同一對話模型提供的輸出只能標 CALLER_SUPPLIED，不能當成獨立驗證。
