## 三、主要缺陷與風險裁定

### B8-R01｜S1｜整體完成狀態容易被過度解讀

證據：交接檔標題為「B8 完成（計畫內批次全部走完）」並稱 B1–B8 均已落地，但同檔亦明確指出真實 C0/C1/C2、adapter、Runtime 觀察及部分自動化未執行，rubric 與操作定義仍待裁決。

批判：批次計畫完成，只能證明該批次按其計畫完成；不能推導整體架構已驗收、實際效益已成立或 Runtime 已驗證。此交接在內文有揭露限制，但標題與摘要仍有混淆整體完成度的風險。

裁定：交接／發布狀態應明確拆分為 PLAN_BATCH_COMPLETE、PACKAGE_REVIEW_PENDING、REAL_RUNTIME_NOT_EXECUTED、ADOPTION_PENDING 等不同概念。當前整體狀態為 PARTIAL／NOT_PROVEN，而非整體 PASS。

### B8-R02｜S1｜C0/C1/C2 定義未經權威裁決

證據：交接檔明言 C0/C1/C2 定義是作者推定的；C0＝無框架單次、C1＝最簡替代、C2＝完整 forAVAr 迴路。現行藍圖沒有確認這組定義。

批判：比較結果高度依賴基線定義。若條件、工具、資源、輸入難度或接受條件不一致，品質／成本比較就可能失去可比性。作者自行推定可用於探索性 harness，但不能用來證明系統優越或決定正式採納。

裁定：保留為 CANDIDATE；在使用者裁決前，不得把此比較用作整體系統優勢的正式證據。正式採納前需固定各組條件、測試集、指標與允許成本，再按相同條件重跑。

### B8-R03｜S1｜本次最終 rubric 結果為 INCONCLUSIVE，不是通過

證據：交接檔報告成本比 3.625 > 3.0，雖其他合成計分項符合其描述，但決策為 INCONCLUSIVE。

批判：這是正確保留失敗／未知的做法，但它只證明 harness 對這組合成條件產生了 INCONCLUSIVE，不代表 forAVAr 的真實表現通過或失敗。不可為了讓結果變成 ADOPT 而在看到結果後放寬 3.0 門檻；若需改門檻，必須由有權者決定並重新登記版本與指紋。

裁定：目前 rubric 不得標為已採納，SOP-004/005 不得依此自動升格為已決。

### B8-R04｜S1｜ZIP 原始碼尚未完成獨立審核

證據：本輪只能核實 ZIP 的 GitHub 檔案 metadata，無法解包讀取內部檔案。HANDOFF 的 modified_paths 是交接者摘要，不能替代逐檔 diff。

批判：沒有程式碼內容，就無法判定是否有核心偏移、錯誤接線、重複權威、錯誤測試條件、隱藏副作用或測試與實作不一致。這是審核範圍限制，不是已證明 ZIP 內有程式缺陷。

裁定：程式碼級審核為 NOT_COMPLETED。封包保持候選狀態；待可實際解包、取得逐檔清單及差異後，才可以對程式品質作裁定。

### B8-R05｜S2｜封包識別資訊不足以完整重現

證據：HANDOFF 只寫 ZIP SHA-256 前 16 碼 4bafd0c7d290064a，另稱封包不含 .git；未提供完整 SHA-256 與封包內全量檔案清單。Git blob SHA 是另一種識別碼，不能代替封包 SHA-256。

批判：短雜湊不夠支援可靠的跨版本追溯；「B1–B8 改動」與「本批 modified_paths」也不是同一份完整差異清單。未來若同名 ZIP 被覆寫，難以確保審核紀錄指向相同位元組。

裁定：下次交接必須提供完整 SHA-256、封包檔案清單、完整累計變更表，以及各項測試結果的檔案／log 位置。不得覆寫仍被審核紀錄引用的封包。

### B8-R06｜S2｜交接的保存位置指示已被目前工作流程取代

證據：HANDOFF_B8 的抬頭寫「本檔不放進 forAVAr repo（可歸 forAVArb）」，但使用者目前已明確指定以 forAVAr 根目錄的進度資料夾接收 ZIP 和交接檔。

批判：這是舊交接的流程指示與目前明確授權不一致；不能照抄舊指示要求使用者改放位置，也不能因新規則便把封包當成正式程式碼。

裁定：本輪遵循目前使用者指定的進度資料夾接收流程。ZIP/HANDOFF 在此僅作審核輸入；正式採納、原始實驗輸出與長期歸檔仍按權威文件及使用者授權治理。

### B8-R07｜S2｜測試結果可追溯資料仍不完整

證據：交接檔提供了測試命令、Python 版本、測試總數和總結果，但本輪未取得完整原始 log、封包全量清單及實際程式碼，因而無法獨立核對 87 項測試究竟涵蓋哪些功能、哪些案例被略過。

批判：單一總數不能表達測試覆蓋、失敗路徑、真實整合程度或風險。特別是測試 harness 的合成自測與真實 adapter/Runtime 測試必須分開報告。

裁定：維持為「交接者報告，未獨立重跑」；接續審核時取得原始輸出，並將 unit／contract／integration／negative／recovery／end-to-end 分開列示。

### B8-R08｜S3｜ResourceWarning 為已揭露維護瑕疵

證據：交接檔表示 test_check_consistency 寫檔未關閉，引發 ResourceWarning，並稱不影響結果。

批判：即使不影響本次結果，仍應修復資源生命週期，並檢查是否在重複執行或不同環境造成可累積問題。未有失敗證據前，不應擴大宣稱為功能故障。

裁定：列低風險待修；修正後至少重跑相關測試及一致性檢查，記錄真實結果。

## 四、核心與主軸偏移判斷

本輪結論：UNKNOWN／NOT_CHECKED（封包程式碼尚未解包），不能宣稱已確認無偏移，也不能僅憑交接檔推斷已有偏移。

可讀交接內容中的以下做法與藍圖方向一致：
- 沒有把合成自測誇大成真實系統優越性。
- 成本超過預設門檻後保留 INCONCLUSIVE，而不是事後降低門檻。
- 未經使用者裁決，沒有將 DISC-SOP-004/005 在 registry 直接標成已決。
- 將真實 C0/C1/C2 和 Runtime 保留為 NOT_EXECUTED／NOT_VERIFIED。

仍待核對：
- ZIP 裡的實作是否映射到現有 A1–A6、N01–N18、F0–F7 及現有能力責任。
- final_test_harness 是否真正檢測假 PASS、安全副作用、證據缺失和成本界線，且在條件缺失時 fail closed。
- 新增測試是否可能在實作缺失、adapter 未接線或只跑合成條件時假通過。
- README、docs/index.json、docs/blueprint.json 的修改是否只更新必要欄位、是否和正式 v0.8 基線衝突。
- ZIP 內是否存在未列入交接的檔案、重複責任、錯誤引用或非預期副作用。

## 五、既有問題／功能／流程覆蓋核對（本輪新增的首要發現）

### B8-R09｜S1｜全量覆蓋無法由現行登錄證明

審核了本輪可讀的正式權威檔 `docs/capability_registry.json` 與 `docs/problem_register.json`，結果如下：

- 能力登錄共 175 項、175 個唯一 ID、0 個重複 ID、0 個解析錯誤；問題登錄共 54 個 PR ID。這只能證明登錄的基礎完整性，不代表功能已實作或問題已解決。
- 175 項中有 78 個 `BASELINE_CAPABILITY`（P1-F01–F48、P2-F01–F30）沒有 `mapping` 欄位，無法從這份權威登錄確認各功能對應到哪些 A/N/F、現有能力、SOP 與驗收案例。
- 54 個 `PROBLEM_REMEDIATION`（PR-001–PR-054）全部沒有 `mapping` 欄位，且全部缺少 `decision` 欄位；因此 54 個問題雖有問題描述和來源，但這個登錄本身尚不能證明每一題都具有明確控制點與回歸驗收映射。
- 另有 16 個跨切面／架構／視圖類項目缺少 `decision` 欄位；其中可讀明確標記 `VIEW-006` 的 P1/P2→四層映射「缺少單一受稽核矩陣」，`VIEW-008` 的問題→控制點→回歸／復發追溯「尚未驗證」。
- 交接檔說 B8 增加 FINAL_TEST harness，但沒有提供 175 個功能、54 個問題、全部流程／SOP 與該 harness、A/N/F、測試案例之間的覆蓋對帳；四項 harness 測試不能替代整體需求覆蓋證明。

**批判裁定：** 目前不能得出「所有問題、功能與流程都能處理」的結論。這是權威清單的既有可追溯性／驗收覆蓋缺口；因 ZIP 程式碼未能逐檔審閱，不能推論所有對應功能都不存在，也不能把它全部歸因於 B8。本次 B8 的交接證據沒有證明缺口已被解決。整體完整性維持 `NOT_PROVEN`，不得採納為已完成的全系統版本。

### B8-R10｜S1｜正式功能清單的必填欄位與實際資料不一致

`docs/capability_registry.json` 的 `source_manifest.required_fields` 將 `mapping`、`implementation/evidence`、`acceptance`、`decision` 列為必要欄位，但實際 175 項中有 132 項缺少 `mapping`，70 項缺少 `decision`。其中 78 個 P1/P2 能力項目缺少 mapping，54 個 PR 關聯項目同時缺少 mapping 和 decision。這是可直接由現行 JSON 核對的 schema／資料完整性不一致。

交接檔稱「registry 的 items 沒有統一的 decision 欄位」並以此作為不變更理由，但目前權威文件已把 `decision` 列為必填欄位；精確問題應是大量 item 未填欄位，而不是沒有欄位規範。這一差異必須先澄清資料契約與適用狀態，不能只憑描述就裁定無須處理。審核者本輪不自行補填或變更 175 筆正式登錄，避免在缺少語意裁決時臆造每個 item 的 decision。

### B8-R11｜S1｜流程完整性也尚未完成對帳

目前正式架構定義 F0–F7 條件式框架，運作契約定義 INTAKE→AUTHORIZE→SELECT_SOP→PLAN→EXECUTE→VERIFY→PERSIST→REVIEW，施工則分 PLANNING／REALIZATION／CLOSURE／FINAL_TEST 四階段。B8 交接未呈現全部流程／SOP 到 F0–F7、能力 ID、處理輸出、失敗出口和驗收案例的完整矩陣，所以無法確認所有既有流程都能被適時選取、完成、回寫和恢復。這是覆蓋證據缺口，尚不是已證明的 Runtime 故障。

下一階段優先工作應是建立／補足問題—功能—流程—架構—驗收的逐項追溯矩陣，先保留所有 ID 和原始語意，再找重疊、衝突與可合併項目；不是先增加更多功能或單純擴大測試數量。
