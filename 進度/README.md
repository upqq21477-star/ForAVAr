# 進度與審核入口

本資料夾是 forAVAr 現階段指定的壓縮檔、交接檔接收區與審核工作入口。審核主軸是檢查更新是否有缺陷、方向錯誤、核心／主軸偏移或遺漏，並核對問題清單、功能清單、流程／SOP 清單的完整覆蓋。每份新封包先審核、後裁決；未經審核與正式採納，不得視為主系統已更新。

## 接手順序

1. 先讀根目錄 README.md，確認本專案讀寫範圍與權威入口。
2. 讀取審核標準與接手流程.md，依固定流程審核，不以交接者自述取代證據。
3. 讀取本次最新 HANDOFF 與 ZIP，核對兩者版本、基線、雜湊、改動清單及待裁決事項。
4. 查閱審核紀錄，確認上一輪哪些問題已解、仍未解、需要回歸測試。
5. 對照 docs/blueprint.json、docs/operating_contract.json、docs/capability_registry.json、docs/problem_register.json 及 docs/index.json；不得以封包內較新的文件自行覆蓋現行權威。
6. 完成審核後新增一份有日期／批次編號的審核紀錄，標明審核範圍、證據、缺陷、結論與未完成項目。

## 新封包提交規則

每次上傳需有可辨識的版本／批次名稱，且交接檔需附完整 SHA-256、基線 commit、變更清單、測試命令與原始結果、未執行項目、主要決策、未解問題及回復方式。不要只附摘要或只寫「已完成」。

不要覆寫仍被審核紀錄引用的封包。若更新同一批次，請提高版本或加入日期後綴，並保留舊封包供差異比較。大型原始測試資料、暫存輸出與長期歷史材料依規則歸檔至 forAVArb；進度資料夾以接手和審核必要材料為主，避免成為第二套權威文件庫。

## 審核紀錄原則

- 只記錄有證據的完成狀態；尚未讀取、未跑、未驗證必須明確列出。
- 缺陷與改進建議分開；先判定根因和核心影響，再談修正。
- 不因為增加流程、測試或文件數量而認定品質提升。
- 不為了驗證而無限驗證：每輪必須有明確問題、可區辨的證據、停止條件及結論。
- 任何核心藍圖更新都必須依正式授權及既有變更流程；審核者不可直接將候選封包升格成正式基線。
