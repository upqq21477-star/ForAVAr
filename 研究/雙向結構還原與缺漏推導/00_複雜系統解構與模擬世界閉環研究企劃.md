## 摘要與核心裁決

本研究要建立一套有方法性的複雜系統解構方法，能從有限的目標、資料與既有材料開始，逐步建立一個具備明確實體、狀態、規則、數據、時間、依賴和因果機制的世界模型，並找出缺漏、矛盾、未定義的邊界行為，以及無法由目前證據判定的部分。主要驗證方式是把模型放進可檢查的情境中進行推演與模擬，而不是只看文件是否完整、圖是否連通，或某個 JSON 格式是否能通過 Schema。

遊戲系統是典型案例：遊戲看似已列出地圖、兵種、資源、移動、戰鬥和經濟等功能，但若沒有明確定義資源的產生與消耗、狀態轉換、運算順序、單位及資料所有權、跨系統接口、失敗與恢復路徑，系統仍會在整合或運行時出現數值異常、狀態矛盾、因果斷裂、資料重複計算及難以解釋的錯誤。

**本研究的目標不是保證能一次窮盡任何世界的全部細節，而是建立一種可重複的方法：把範圍內的重要內容顯式化、讓每項主張有來源或假設、使必要依賴與狀態轉換可追溯、讓資料流與因果機制可檢查，並用預先定義的模擬情境找出尚未閉合的部分。** 對尚不能確認的內容，必須保留為未知、假說或待決策，不得為了讓模型看起來完整而自動補成事實。

### 本研究與相鄰課題的邊界

本課題**獨立於「AI 理解可視化與框架編輯介面」**。可視化課題關心如何將已形成的理解呈現、檢視、修改和管理；本課題關心如何建構可信的理解本身，尤其是大型世界的內部邏輯、資料和動態行為。圖、樹、矩陣、清單或編輯器都只是可能的表達工具，不是本研究的目的，也不能取代系統建模、缺漏推導和模擬驗證。

## 1. 問題定義：為什麼複雜系統會「看似規劃了，運行卻滿是問題」

### 1.1 表面現象與真正失效原因

| 表面現象 | 可能的根因 | 為何一般功能清單不夠 |
|---|---|---|
| 系統功能很多，整合後仍有大量錯誤 | 功能只按名稱列出，沒有定義輸入、輸出、條件、狀態和接口 | 「有功能」不代表它能與其他功能共同運作 |
| 因果鏈走到一半中斷 | 中介機制、觸發條件、時間延遲或結果回饋沒有定義 | 只有 A 連到 B，沒有說明如何、何時、在什麼條件下影響 |
| 資源忽然變多、變少或負數 | 產生、轉移、消耗、扣除和回補缺少單一核算規則 | 只驗證欄位型別，不能驗證整體帳目是否守恆 |
| 狀態重疊或互相矛盾 | 狀態空間、合法轉換、優先序和終止條件不完整 | 單一模組內看似合理，不代表跨模組狀態可共存 |
| 同一輸入每次得到不同或不合理結果 | 更新順序、隨機源、競態、數值精度或隱性副作用不明 | 未定義時間語意，就無法判斷差異是否合理 |
| 修好一處，又在其他地方出現新錯誤 | 影響路徑未知，沒有跨系統約束與回歸情境 | 局部修補沒有追到共享狀態與下游後果 |
| 長上下文閱讀後仍遺漏細節 | 依賴模型臨時記住大量敘述，而非依靠穩定的外部結構、追溯與局部契約 | 增加摘要長度不能自動補齊缺失規則，也不能修復矛盾資料 |

長上下文造成的遺漏或錯誤理解是重要風險，但不應把所有問題都歸因於上下文長度。若原始需求本身未定義、材料互相矛盾、資料語意模糊、運算順序不明，即使將內容切短，錯誤仍然會存在。

### 1.2 必須分開的三類問題

1. **理解與規劃缺漏：** 沒有識別出必要實體、規則、狀態、資料路徑、例外或依賴。
2. **模型本身不一致：** 規則、數值、狀態或接口已被寫出，但彼此衝突、不可同時成立或無法完成計算。
3. **實作偏離模型：** 設計本身合理，但程式、資料轉換、排程或執行行為沒有遵循規格。

這三類不能混為一談。需要先判斷錯誤位於哪一層，再決定是否修改世界模型、資料契約、演算法、執行順序或程式實作。

## 2. 核心概念與閉環定義

### 2.1 雙向結構還原

**逆向還原（Reverse Reconstruction）**：從已有的程式碼、文件、資料結構、配置、測試、輸入輸出、記錄和可重現行為，重建現有系統實際包含的實體、狀態、規則、資料流、時間順序和外部依賴。它必須區分「實際存在」「文件聲稱存在」「由證據推得」和「仍然未知」，不能把文件描述直接當成實作真相。

**正向缺漏推導（Forward Gap Inference）**：從明確目標、邊界、已知世界法則與約束開始，推導要使系統成立或可運作，還需要哪些機制、數據定義、條件、狀態轉換、接口、失敗處理和驗收依據。候選必須說明其必要性來源，不能因為某項功能在其他遊戲或軟體裡常見，就自動把它列成必需。

**雙向交叉核對**：比較兩個方向的結果。逆向發現實作已有但規格未描述的行為；正向發現目標要求但目前材料無法承接的機制；兩者不一致時產生待解釋差異，而不是直接認定任一方正確。

### 2.2 世界模型不是功能清單，也不是關係圖

世界模型至少要能明確表達下列語意。這些是概念類別，不要求每個類別都實作成獨立服務或資料表。

| 類別 | 必須回答的問題 |
|---|---|
| 目標與邊界 | 此模型要解釋或模擬什麼？哪些內容被排除？解析度到哪裡？ |
| 實體與身分 | 世界中有哪些對象？各自如何識別、建立、合併、銷毀或持續存在？ |
| 屬性與狀態 | 哪些數值會變？允許範圍、單位、精度、預設值與缺失值語意是什麼？ |
| 規則與條件 | 哪些前置條件、觸發條件、公式、門檻、優先序和禁止條件會決定行為？ |
| 過程與事件 | 何時執行什麼過程？事件由誰觸發、是否可重入、是否延遲或重複處理？ |
| 資源與流量 | 哪些量可以產生、消耗、轉移、儲存、損耗或轉換？帳目如何核對？ |
| 時間與空間 | 時間單位、離散／連續更新、空間尺度、路徑和碰撞規則如何定義？ |
| 因果機制 | 變化經由何種機制、在什麼條件下、經過多久影響哪些結果？ |
| 子系統接口 | 各子系統需要什麼輸入、提供什麼輸出、由誰負責更新和處理失敗？ |
| 約束與不變量 | 哪些事情永遠不能發生，哪些關係必須持續成立？ |
| 例外與恢復 | 無效輸入、資源不足、失敗、中斷、回滾、重試、載入存檔或外部服務失效時如何處理？ |
| 觀測與驗收 | 如何判定世界模型的行為符合本次用途？哪些情況仍不能被證明？ |
| 未知與假設 | 哪些內容有直接證據，哪些是推導，哪些是假說或尚待決策？ |

### 2.3 什麼才算「邏輯閉環」

本研究不把「所有節點都連起來」或「每條路徑都形成循環」當作閉環定義。合法的系統可以具有無環的依賴圖；某些系統也有真正的回饋循環。兩者不能混為一談。

在本研究中，**閉環是指：在明確指定的用途、範圍、解析度及情境內，重要的定義、前置條件、狀態轉換、資料變化、因果機制、下游結果和驗收方式都有可追溯的承接；無法閉合的內容被明確標示，不會被假裝為已解決。**

需要分開檢查的閉環包括：

- **語意閉合：** 重要名詞、數值、條件和狀態有明確定義。
- **結構閉合：** 必要實體、依賴、接口和責任歸屬不存在未解釋的斷點。
- **狀態閉合：** 重要狀態有合法進入、轉換、退出和終止語意。
- **因果閉合：** 重要結果有具體機制，不以無根據的連線取代解釋。
- **資料閉合：** 每個重要值的來源、轉換、單位、更新者、有效範圍與用途可追溯。
- **時間閉合：** 更新頻率、執行順序、延遲、同時事件和衝突處理有明確政策。
- **失敗閉合：** 範圍內的重要異常有明確的拒絕、降級、重試、補償或停止語意。
- **驗收閉合：** 可以用預先指定的觀測、性質、參考結果或人工判定來區分正確與錯誤。

## 3. 研究範圍與明確非目標

### 3.1 主要研究問題

1. 如何把一個大型課題拆成可以單獨理解、但接口和相互影響不會遺失的分層世界模型？
2. 如何辨識必要機制的缺漏，而非只是產生更多看似合理的功能？
3. 如何將自然語言描述轉換成可計算、可追溯、可模擬的規則和資料定義？
4. 如何發現數據處理粗糙造成的錯誤，例如單位錯用、重複計算、權威值混亂、精度損失、非法狀態及更新順序錯誤？
5. 如何以少量但具區分力的模擬情境，證明某個候選世界模型仍有矛盾或缺漏？
6. 如何在上下文長度受限、來源分散或資料互相矛盾時，依靠穩定的外部模型和追溯資訊保持一致，而不是要求模型在每次工作中重新讀完全部材料？
7. 如何界定「此範圍已足以進入下一階段」而不是無限補充細節或一直驗證？

### 3.2 非目標

本研究不承諾：
- 一次性還原所有現實世界的全部因果關係；
- 只靠 LLM 自評、自然語言摘要或一張圖證明模型正確；
- 強迫所有系統使用同一套固定實體、關係類型或單一演算法；
- 把每個缺口變成新功能、角色、微服務或永久資料欄位；
- 用「所有欄位都填了」取代語意合理性、計算正確性與情境驗證；
- 先設計可視化介面，再反過來限制世界模型只能表示介面容易顯示的內容；
- 在沒有真值、參考行為或可執行不變量的情況下宣稱完整率、準確率或品質提升。

## 4. 方法骨架：從定界到可驗收世界模型

這是待研究和驗證的工作方法，不是聲稱已經實作完成的流水線。各階段按依賴順序推進；前一階段的必要輸出未形成前，不應用後面的測試掩蓋前面的定義缺失。

| 階段 | 主要工作 | 必須產生的結果 | 主要失敗訊號 |
|---|---|---|---|
| 0. 任務定界 | 固定目標、非目標、使用情境、世界邊界、細節解析度、成本與停止條件 | 可判定的範圍契約 | 目標含糊、邊界不明、不同人對「完成」理解不一 |
| 1. 證據盤點 | 整理既有程式、文件、資料、行為、版本與缺失範圍 | 來源清冊與證據等級 | 把推測寫成實際行為，或把舊版當現行版 |
| 2. 世界骨架 | 建立主要實體、子系統、環境、資源、狀態與時間／空間尺度 | 可分解的世界骨架 | 只有功能名稱，沒有責任、狀態與輸入輸出 |
| 3. 資料語意 | 定義每個關鍵量的單位、型別、有效範圍、權威來源、更新者、精度和生命週期 | 資料字典與資料責任圖 | 同一數值多個權威版本、單位不一致、缺失值語意不明 |
| 4. 規則與狀態 | 定義前置條件、守衛條件、轉換、公式、門檻、終止和非法情況 | 狀態轉換與規則表 | 某狀態無入口／出口，規則互相衝突或順序未定 |
| 5. 時間與執行語意 | 定義 tick／事件、階段、更新順序、延遲、並行與衝突解決 | 可重現的執行時序 | 同一輸入因執行順序不同而無法解釋 |
| 6. 因果與資源流 | 把相關、依賴、資料傳遞和因果分開；定義機制、條件、方向、延遲和回饋 | 因果機制與資源收支模型 | 只有箭頭，缺少中介機制或數據帳目無法對上 |
| 7. 接口與整合 | 定義跨子系統的輸入輸出契約、所有權、錯誤回應和更新責任 | 接口契約與整合關係 | 模組各自合理，但合併時語意、單位或責任不一致 |
| 8. 逆向還原 | 從現有材料和行為重建既有世界，標記證據與未知 | 逆向模型及來源映射 | 文件和實作不一致，卻沒有差異與裁決紀錄 |
| 9. 正向缺漏推導 | 從目標與約束推導必要機制候選，評估替代解釋和必要性 | 候選缺口、推導依據、待決策項 | 大量新增常見功能，卻沒有清楚目標或反事實理由 |
| 10. 雙向比對 | 比較目標模型與既有模型，找出缺項、衝突、無來源主張和冗餘 | 差異集與裁決狀態 | 一方結果被直接當作真值，或同一差異重複建檔 |
| 11. 模擬與反例 | 以小型可重現案例測試核心機制、邊界、失敗和跨系統互動 | 輸入、初始狀態、規則版本、預期與實際結果 | 測試沒有正確結果判準，或只在正常情境運作 |
| 12. 根因回饋 | 分清觀察錯誤、根因假說與已確認根因；只將可重用的根因修正回方法和權威規格 | 修正決策及受影響範圍 | 對每個症狀新增一條規則，導致規則膨脹和互相衝突 |

### 方法原則

- **先定義再補全：** 若目標、尺度或資料語意未定義，先列為待決策，不用推導掩蓋前置資訊不足。
- **先骨架後細節，但必須反覆交叉檢查：** 骨架要讓系統可分解；細節補充後必須回檢上層假設和接口。
- **局部模型必須帶著邊界和接口：** 子系統不需要記住所有上下文，但必須知道自己承接什麼、輸出什麼、依賴什麼、哪些事情不負責。
- **未知不是錯誤，隱藏未知才是風險：** 對目前不可識別的機制保留假說，並標示哪些決策會受它影響。
- **驗證不等於建模：** 測試能暴露模型矛盾，但不能替代缺失的規則定義；不能因測試未失敗就宣稱其他情境必然正確。
- **只為真實根因增加規則：** 每個修正都要說明它修復的是哪個通用失效模式、影響哪些既有模型、如何避免建立重複能力。

## 5. 關鍵方法一：把「世界」變成可操作的資料與規則

### 5.1 每個重要數值都要有語意契約

單一數值至少要能回答：

- 名稱與意義：它在世界中代表什麼？
- 單位與尺度：例如秒／回合、米／格、個體／群體、整數／小數。
- 型別、範圍和精度：允許值、上下界、溢位及四捨五入政策。
- 來源與所有權：誰能建立或更新它？哪一份才是權威值？
- 產生與消耗：哪些機制改變它？每種改變的公式和條件是什麼？
- 更新頻率與時序：即時、每回合、每個 tick、事件觸發或批次處理？
- 派生關係：它是直接狀態，還是由其他值計算而得？能否被直接修改？
- 缺失與非法值：null、未知、零、負值、無限大和未初始化必須有不同或明確定義的語意。
- 持久化與恢復：存檔、讀檔、重播、回滾或重新計算時如何維持一致？

沒有這些資訊的數字，只是表面上可用的資料，不能當成穩定的模擬狀態。

### 5.2 權威狀態、派生值與快取要分開

對每個重要狀態，必須指定唯一的權威來源，或明確說明衝突合併政策。派生值應能指出它依賴哪些輸入及計算規則；快取與顯示值不得反向覆寫權威狀態，除非已明確定義同步或回寫流程。

否則可能出現：畫面顯示糧草為 20，軍隊資料顯示 17，後勤模組還保留舊值 24；三個模組都「有數字」，但世界本身已沒有唯一狀態。

### 5.3 對可守恆的資源建立收支約束

對適用的數量，使用明確的收支式，例如：

[
S_{t+1}=S_t+P_t+I_t-C_t-O_t-L_t
]

其中 (S) 是庫存，(P) 是產生量，(I) 是流入，(C) 是消耗，(O) 是流出，(L) 是損耗。此式只是可守恆資源的通用模板，不適合無限制套用到士氣、聲望、偏好等非守恆量。

需先定義所有項目的單位、時間區間、計算順序、四捨五入規則與允許的例外。若某資源可以無中生有或被銷毀，必須由明確機制說明，而不是讓數值變化沒有來源。

### 5.4 區分關係、依賴與因果

- **結構包含：** A 裡面有 B。
- **依賴：** A 要運作必須取得 B。
- **資料流：** A 把某種資料送給 B。
- **時間先後：** A 先於 B 執行。
- **因果：** 在特定條件下，透過具體機制改變 A，會使 B 的分布或狀態發生可解釋的變化。
- **回饋：** 結果再影響先前的決策、輸入或狀態，使系統行為隨時間改變。

不能把所有關係都畫成相同的箭頭。重要因果主張應至少說明起始條件、作用機制、被改變的狀態、時間尺度、可能的中介與可觀察結果。若只有直覺或類比，就應標示為假說，而不是已證明的因果規則。

## 6. 關鍵方法二：以遊戲系統作為世界閉環範例

以下以「軍隊沿路移動並消耗糧草」為微型案例。它不是完整遊戲設計，而是用來說明只列功能名稱為何不足，以及應如何推導和核對機制。

### 6.1 初始規劃常漏掉的細節

若規劃只有「地圖、軍隊、移動速度、糧草消耗」，仍缺少：

- 距離如何計量、地圖格和世界距離如何對應、道路是否可通行。
- 速度的單位、地形修正、疲勞／天候是否影響速度，以及這些效果何時更新。
- 糧草是軍隊持有、城市儲存、補給線運送，還是多者並存；哪一份庫存是權威值。
- 消耗率是每兵每時、每單位時間每軍隊，還是每回合固定量；軍隊人數變化時如何重新計算。
- 行軍和消耗是先算後移、先移後算，或在同一 tick 同步結算。
- 糧草不足時是停止移動、減少士氣、產生傷亡、強制撤退，還是由玩家選擇；多個效果的順序是什麼。
- 途中遇敵、道路阻斷、軍隊被拆分、合併、解散或全滅時，剩餘糧草如何處理。
- 存檔讀檔、重新計算或事件重放時，如何避免同一次消耗被扣兩次。
- 哪些規則已有依據，哪些是尚待設計的選項。

### 6.2 把機制寫成可核對的規則

| 項目 | 必須固定的語意 | 典型錯誤 |
|---|---|---|
| 距離 | 座標、格距、道路成本、不可通行條件 | 直線距離被誤當實際路程 |
| 移動 | 速度單位、更新頻率、阻擋規則、剩餘移動量 | 一回合內移動過遠或停留狀態不一致 |
| 糧草 | 權威庫存、單位、消耗公式、來源與流向 | 從軍隊和城市重複扣款 |
| 更新順序 | 行軍、補給、戰鬥、傷亡和士氣的結算次序 | 同一結果受隱性程式順序影響 |
| 糧草不足 | 觸發門檻、效果、優先序、解除條件 | 糧草已歸零，軍隊卻持續無代價行軍 |
| 軍隊生命週期 | 建立、分拆、合併、解散、全滅後資料處理 | 殘留幽靈軍隊或遺失資源 |
| 驗收 | 一步行軍、跨地形、補給中斷、資源歸零、讀檔重放等案例 | 只測正常路徑而漏掉交界條件 |

### 6.3 用收支式和狀態式暴露缺口

若軍隊糧草為 (S_t)，當期補給為 (I_t)，消耗為 (C_t)，丟棄或損失為 (L_t)，就必須明確定義：

[
S_{t+1}=S_t+I_t-C_t-L_t
]

若每個士兵每小時消耗率為 (r)，兵力為 (N_t)，模擬時間長度為 (Delta t)，在假定消耗率固定且單位一致時：

[
C_t=rN_tDelta t
]

這兩式不應直接視為正確遊戲規則。它們是讓假設顯式化的模板。研究必須另行確認兵力是否於本階段變動、糧草是否可負、部分時間是否允許、數值如何取整，以及消耗是否有地形或狀態修正。

### 6.4 最小模擬案例

建立可人工核算的小型狀態：軍隊 100 人、糧草 100 單位、固定路程及固定消耗率。固定所有單位和更新順序後，計算一步的預期移動位置及糧草結果，再與程式或候選模擬實際輸出比較。隨後逐一加入糧草不足、路線不可通行、兵力變化、事件重放和存檔恢復。

重要的是每個案例要有獨立可核對的預期結果，且一個案例盡量辨別一類根因。不能只問「模擬有沒有崩潰」，還要核對數值帳目、狀態合法性、事件順序與下游後果。

## 7. 關鍵方法三：雙向推導如何避免憑空補功能

### 7.1 候選必要性分級

每個缺漏候選需回答「為什麼需要」，並區分：

1. **明確要求：** 需求或使用者指示明確要求。
2. **外部規範：** 由適用標準、合約或政策要求。
3. **設計依賴：** 在目前選定的架構下，若不具備它，指定目標便無法成立。
4. **條件性必要：** 只有在特定假設、世界規模或情境成立時才必要。
5. **可選方案：** 可能有價值，但存在不需要它也能達成目標的合理替代方案。
6. **假說／未知：** 目前證據不足，需要試驗、查證或人類決策。

不應以單一未校準分數把這些類別混在一起。特別要分開「目前設計需要」與「所有可能方案在邏輯上都不可缺少」。

### 7.2 正向推導的固定檢查面向

對每一個子系統依序檢查：

- 它承接哪個目標，哪些事情不屬於它？
- 它需要哪些輸入、前置條件、來源與有效狀態？
- 它讀取和修改哪些權威狀態？
- 它使用哪些公式、規則、條件、門檻和執行順序？
- 它產生哪些輸出、事件或副作用，由誰接收？
- 什麼條件下不運作，如何回報錯誤或處理失敗？
- 哪些下游結果由它影響，機制和時間尺度是否可解釋？
- 有什麼不變條件、數值約束或資料帳目需要持續成立？
- 哪些情況會與其他子系統互相衝突？
- 如何用小型案例證明它的預期行為，或反證目前的假設？

以上是共通提問方式，不是每個項目都必須新增一個模組。若某項檢查的答案是「不適用」，需保留簡潔理由即可，不應人為製造功能。

### 7.3 缺漏候選的處置狀態

候選提出後，只能進入下列狀態之一：

- **接受：** 有足夠依據，且與現有世界模型相容。
- **否決：** 已有理由表明不必要、錯誤或與目標不符。
- **條件接受：** 只在明確前提下成立。
- **待決策：** 需由設計者選擇替代方案。
- **待證明：** 有可檢驗假說，但缺少足夠證據。
- **範圍外：** 不屬於本次用途，但應避免被誤認為已建模。
- **合併：** 已被既有規則或子系統承接，不新增重複能力。

不可把「提出候選」當成「找到缺漏」，也不可把「沒找到缺漏」當作「已證明不存在缺漏」。

## 8. 模擬驗證策略：用可區分結果的案例，不做無止境檢驗

### 8.1 驗證必須有判定依據

每一個重要驗收案例至少固定：初始狀態、輸入、模型版本、參數、隨機種子或外部條件、預期結果／可檢查性質、實際結果、差異和結論來源。若問題沒有唯一數值答案，仍可使用範圍、排序、單調性、守恆、不可達狀態或其他事先定義的性質。

### 8.2 測試組合

| 類型 | 要發現的問題 | 例子 |
|---|---|---|
| 最小正常案例 | 基本規則是否按定義運作 | 單一單位完成一個時間步 |
| 邊界案例 | 門檻、上下界和取整錯誤 | 資源恰好為零、剛超過容量 |
| 不變量測試 | 全程不可被破壞的規則 | 不允許負庫存、唯一 ID 不重複 |
| 收支／守恆測試 | 數量變化是否都有明確來源 | 分拆／合併軍隊前後的總兵力及資源 |
| 狀態轉換測試 | 非法狀態、缺少出口和狀態殘留 | 單位死亡後仍被指派任務 |
| 時序測試 | 執行順序與事件延遲是否正確 | 同一 tick 的補給、移動和戰鬥結算 |
| 跨系統整合測試 | 接口、單位、權限與資料契約不一致 | 城市補給、軍隊庫存和路線系統協作 |
| 故障注入 | 失敗、重試、重放或資料損毀時是否安全 | 事件重複送達、存檔中斷、外部來源缺失 |
| 差異／變形測試 | 在已知變換下應保持哪些性質 | 拆成兩支隊伍再合併，總量是否符合規則 |
| 長期／壓力模擬 | 積累誤差、數值漂移和級聯影響 | 長時間運行、極端資源、密集互動 |
| 靈敏度與不確定性 | 結果是否過度依賴未確認假設 | 消耗率略變時，結果如何改變 |
| 逆向與正向對照 | 方法是否真的能找出已知缺項 | 將答案封存，測試方法是否能發現預設的缺漏 |

不是每個專案都需要完整的統計模型或所有測試類型。應依風險、世界複雜度和用途選擇測試，並預先說明取捨。

### 8.3 反例必須有辨別力

優先建立能區分兩種合理但不同的模型的最小案例。例如：若兩種更新順序在一般情境結果相同，就選一個順序會導致不同結果的邊界案例。這比對相同的普通情境反覆執行更能檢查規則是否定義清楚。

### 8.4 停止條件

當指定範圍內的主要目標有承接機制，重要狀態／資料／因果／時序規則可追溯，重大矛盾已解決或明確接受風險，關鍵反例已有判定依據，且剩餘未知不會使當前交付失效時，才能宣告「對指定用途達到目前閉合」。這不表示其他用途、情境或解析度已被證明正確。

若失敗只導致再增加清單和抽象層，卻未提出新的可辨識根因或可區分案例，應停止擴張，回頭判斷是範圍錯誤、規則定義不足、資料品質問題、模型失效，還是實作偏離。

| 思考核心的工作責任 | 本研究的對應工作 | 不可混淆的邊界 |
|---|---|---|
| 任務定向：確認目標、非目標、限制、成功／停止條件及風險 | 固定世界模型用途、範圍、解析度、情境及可接受差異 | 不能先選演算法，再反過來重寫使用者目標 |
| 問題表徵：建立問題模型，分清已知、推論、未知與衝突 | 建立世界骨架、資料語意、狀態、時間、空間、規則、因果與接口模型 | 問題模型不只是摘要；需保存可核對的規則和數據語意 |
| 推理生成：比較候選方法與假設，按問題選擇工具 | 分開執行逆向結構還原和正向缺漏推導，再交叉比較 | 候選產生只提出可能性，不等於證明缺漏或正確性 |
| 結果校驗：按預先定義的接受條件獨立檢查結果 | 使用收支約束、不變量、狀態轉換、最小模擬、反例與基線比較 | 文件齊全、圖連通或生成模型自評都不能代替結果判定 |
| 認知調節：遇到錯誤、未知、衝突或假設失效時回到思考／研究 | 將失敗分類為範圍、語意、資料、模型、時序或實作根因；有限修正後回歸 | 不對每個症狀另加一條規則，也不以不斷重測代替根因修正 |

P2 藍圖所描述的 Problem Model、Method Map、Resource Map、Epistemic State 及 Current Plan，是當前思考工作可重建的五個區域，而不是五個必須永久保存的新子系統。本研究可將它們落實為一次複雜建模工作的最小工作狀態：目標與邊界、方法與限制、來源與資料位置、已知／未知／衝突、當前建模進度與下一個可判定決策。

### 9.3 本研究補足的是領域方法，不是控制權

一般思考核心即使能正確地辨認目標、選擇方法和核對證據，也不會自動知道某個遊戲的兵力、補給、戰鬥、地形、時間步進和資源帳目該如何建模。這需要一套領域可用的建模程序，將抽象的「想清楚、找缺漏、驗收結果」落成可重複執行的操作方法。

因此，本研究的貢獻應是：
- 為複雜系統提供可反覆使用的解構及模型建構方法；
- 把數值、狀態、時間和跨系統因果轉成可核對的契約；
- 產生可被反例否證的缺漏候選，而不是自動增加功能；
- 用有真值或可核對性質的模擬案例評估方法本身；
- 將已確認的根因回饋到權威方法，避免依賴聊天上下文重新推導全部細節。

這份研究不是「AI 理解可視化與框架編輯介面」的子模組。前者研究世界模型如何被建立和驗證；後者研究理解結果如何被呈現與編輯。兩個課題可以在未來選擇交換資料，但不能因此共享研究目標、驗收標準或權威文件。
 
## 10. 研究評估計畫

### 10.1 主要對照方法

至少比較三種方案，避免只證明新方法能產生一份看似完整的文件：

- **基線 A：** 一般自由形式的 AI 規劃與摘要。
- **基線 B：** 功能清單加固定檢查表。
- **候選方法 C：** 雙向還原、型別化世界模型、缺漏候選分類、跨系統約束和有判定依據的模擬案例。

對照時使用相同輸入、相同目標與相同資源限制。評分者不能只使用產生候選的同一個模型自我宣告通過。

### 10.2 建立有真值或可核對性質的案例

- 小型已知世界：完整規則、資料、更新順序和預期結果由研究者先固定，再遮蔽部分規則給候選方法重建。
- 受控缺漏：預先隱藏單位定義、接口、狀態轉移、資料來源或錯誤處理其中一項，衡量是否能指出正確缺口。
- 矛盾輸入：混入舊版規則、互相矛盾的單位或不同更新順序，觀察能否分辨衝突而非自行融合。
- 連鎖情境：單一局部變化經由數個子系統傳遞，檢查是否漏掉中介、延遲或下游效果。
- 上下文壓力情境：將同一材料分段、延後提供、引入重複與過時內容，觀察外部模型及來源定位是否能避免遺漏和錯誤沿用。
- 反例與邊界情境：使用能讓不完整方案產生錯誤結果的最小案例。

### 10.3 評估指標

| 指標 | 定義方向 | 注意事項 |
|---|---|---|
| 缺漏召回 | 預先標註的必要缺口中，有多少被找到 | 不能以候選總數當作成功 |
| 候選誤報率 | 被提出但不成立／不必要的候選比例 | 需要獨立判定真值或明確裁決 |
| 矛盾發現率 | 能找出預置規則、單位、版本或狀態衝突的比例 | 各類矛盾應分開統計 |
| 因果承接率 | 重要狀態變化是否有明確機制與可觀察結果 | 有邊不等於有因果解釋 |
| 資料不變量違反 | 模擬中出現的非法值、重複核算或不守恆次數 | 必須依量的性質定義適用性 |
| 可重現性 | 固定條件後能否重現結果與差異 | 非決定性系統要記錄隨機源與容許範圍 |
| 下游影響漏收率 | 變更後未被預測到的受影響規則或輸出 | 需要已知影響真值或可核對預期 |
| 成本與時間 | 找到問題的閱讀、推理、模擬與修正成本 | 不預設一定比基線更快 |
| 未知處理品質 | 能否保留未決項而不是自動補成事實 | 需檢查其是否影響當前決策 |

### 10.4 評估限制

若沒有獨立真值、可重現輸入或可執行性質，結果只能是專家評議或案例分析，不能包裝成客觀準確率。外部研究支持的是模型描述、架構還原、驗證和不確定性管理的特定方法，不能直接證明本研究的候選方法有效。

## 11. 分階段研究與進入條件

### 第一階段：釐清核心方法與術語
輸出：明確的世界模型定義、閉環定義、正逆向邊界、資料語意要求與停止條件。此階段不製作可視化介面，不直接開始大量補功能。

### 第二階段：建構最小參考世界
選擇能同時呈現資源流、狀態轉換、時間順序、跨系統依賴和失敗處理的小型遊戲情境。先人工固定規則及預期結果，作為後續盲測基線。

### 第三階段：做逆向還原與正向缺漏推導
分別讓方法只取得部分材料和粗略目標，保留未提供的規則作為隱藏真值。記錄找出的正確缺漏、誤報、衝突、未知和所需成本。

### 第四階段：模擬、故障注入與對照
針對狀態、資源、時間、因果、接口和跨系統影響建立有限案例；比較自由形式 AI、固定清單與候選方法。失敗時先找根因，再決定是否改方法。

### 第五階段：判斷是否值得進入工程化
只有當方法相對基線在缺漏發現、誤報、數據一致性、因果解釋或可重現性上有明確價值，且新增成本可接受，才把它轉換成正式工具或程序。若研究結果顯示效益有限，應縮小方法或停止，而不是為完成企劃而強行產品化。

---

## 12. 最低可接受的研究成果

未來任何聲稱已完成的世界模型，至少應具備：

1. 可判定的用途、範圍、解析度和明確排除項。
2. 核心實體、狀態、數值、時間／空間尺度、規則和子系統責任的定義。
3. 重要數值的單位、來源、權威性、更新者、取值範圍與派生方式。
4. 重要狀態轉換的前置條件、觸發、結果、結束方式及非法情況。
5. 跨系統接口的輸入、輸出、單位、錯誤語意、更新順序與所有權。
6. 對因果主張說明機制、適用條件、時間尺度及證據／假設狀態。
7. 對可守恆資源提供收支核對，對非守恆量明確說明變動機制。
8. 範圍內關鍵異常、失敗、恢復和邊界情境的規則。
9. 能區分候選、未知、假說、已確認規則和已驗收結果的證據與版本記錄。
10. 具備可重現或可人工核算的最小案例，以及能暴露已知缺陷類型的反例。
11. 明確列出未涵蓋範圍、剩餘未知、使用限制與停止判定。
12. 把已確認的根因回饋到唯一權威方法或模型，而不是建立重複規則和無限增長的文件清單。

以上條件不是一份對所有系統一律套用的硬性功能表。每一項都需依用途判斷適用性；不適用時記錄理由，有條件時說明條件。檢查目標是讓必要內容可判定，而不是讓表格被填滿。

## 13. 風險與禁止的錯誤修法

- **把世界模型當成文件摘要：** 摘要能壓縮文字，但不能取代規則、單位、狀態轉換和數據關係。
- **把圖的連通性當成因果閉環：** 連線不代表機制存在，更不代表因果已被證實。
- **只追求完整清單：** 清單可能越長，卻仍缺少更新順序、失敗邏輯和數據核算。
- **把所有 unknown 自動補成常見做法：** 這會製造看似完整但無根據的設計。
- **用固定流程僵化所有課題：** 方法的順序可受依賴關係約束，但步驟應依系統類型和資訊狀況調整。
- **用另一個 LLM 自評當獨立真值：** 共同錯誤前提可能導致兩個模型一致地判錯。
- **先做視覺化再決定模型：** 會讓需要表達的世界受到介面形式限制，並把表示問題誤當成建模問題。
- **以反覆驗證代替根因修正：** 每輪只新增更多測項，卻不更新有問題的概念或規則，將造成驗證迴圈。
- **宣稱全域完整：** 所有完整性聲明都必須限定用途、範圍、解析度、情境與已用證據。

## 14. 研究結論

雙向結構還原與缺漏推導的真正用途，是為複雜系統建立可檢查的世界模型。逆向還原回答「現有系統實際有什麼、如何運作」；正向缺漏推導回答「為了讓指定目標成立，還有哪些機制必須被確認」；模擬與獨立判準則回答「這個候選模型是否違反已知規則、資料約束或預期行為」。

此方法的關鍵不是產生更多節點、文件、角色或功能，而是把世界中的關鍵語意、狀態、資料、時間、接口和因果機制從隱性假設變成可以核對的規則。局部模型要能獨立理解，也要能透過清楚的接口和影響關係重新組合成整體；資料要有語意與核算規則；未決事項要能被看見；錯誤要能沿著可追溯的因果鏈找回根因。

**目前狀態仍是研究設計，尚未完成參考世界實驗、盲測、模擬或對照評估。不能宣稱已解決上下文遺漏、已證明完整性，或已提高實際系統的運作品質。** 下一步應先完成核心方法與最小參考世界，再決定是否有足夠實證價值推進工程化。
