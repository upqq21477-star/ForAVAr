## 摘要

本研究要建立一套可重複使用的「現實規律抽象與缺漏推導方法」：從現實世界、成熟領域研究及可觀察系統中找出影響結果的主要因素與作用機制，壓縮成符合指定目標與運行尺度的最小充分模型，再將模型套用到具體設計或遊戲系統，反向提出可檢查、可反駁的缺漏候選。

本階段完成三項工作。第一，建立通用系統總覽與因果關係框架，明確區分狀態、參數、機制與結果。第二，比對概念模型、系統工程、控制分析、架構取捨、風險導向驗證等外部方法，形成分層、可裁剪的工作流程。第三，使用《Shogun: Total War》、《Civilization》早期原型、《Rome: Total War》及《Total War: Rome II》的公開資料進行回顧式可行性初測，檢查方法是否能將已知的發展轉折或問題轉成有因果依據的缺漏候選。

目前的最佳方法候選是：**固定目標與尺度 → 建立最小因果模型 → 按需啟動控制／介面／需求追溯／架構取捨分析 → 產生可反駁的缺漏候選 → 依風險排序 → 用最小成本反證 → 以獨立案例和盲測評估。**

本階段的結論是「方法具有初步可行性，但預測優勢尚未獲得實證」。回顧式案例能說明方法如何解釋結構性缺口，卻不能排除事後偏誤；目前沒有預先封存的盲測預測，也沒有可報告的命中率、誤報率、漏判率或提前量。因此，本文件對本階段研究結案，但不宣稱已證明方法能可靠地提前找出所有開發漏洞。

## 1. 研究目的與範圍

### 1.1 核心問題

當面對一個複雜系統時，如何不靠無止境地列舉功能，而是從現實規律和成熟領域知識中抽取必要因素、因果機制與限制，形成精簡總覽，並用它反向推導具體模型可能缺少什麼？

遊戲開發是方便觀察的應用領域，但不是唯一研究對象。相同方法也可用於戰爭、經濟、人口、供應網路、生態、組織或其他具備狀態、互動、資源和時間變化的系統。

### 1.2 不研究什麼

本研究不把「某款遊戲如何從 Demo 發展到一代、二代、續作」當成核心研究對象，也不將開發歷史、版本變化或 Bug 修復順序當作主要解釋。歷史資料的用途是提供案例、來源與可核對結果。

以下概念必須分開：

- **結構缺漏候選：** 依目標與因果模型推導出的可檢查假說。
- **設計問題：** 有證據顯示現有設計無法滿足已定義目標。
- **程式 Bug：** 實作偏離預期規則，通常需要程式、日誌或可重現行為確認。
- **刻意取捨：** 某項能力被有意省略，以換取成本、效能、簡潔度或其他品質。
- **方向變更：** 產品目標改變後，原本的非目標成為新目標。
- **證據不足：** 現有資料無法判斷，不得將未知補寫為事實。

### 1.3 研究成果的邊界

本階段交付的是整合方法、外部來源判讀、回顧式案例初測與取捨規則；不是一個已經在多個遊戲上完成盲測的預測工具。任何「方法有效」的陳述都必須分成概念合理性、案例支持和盲測證據，不可混為一談。

## 2. 整合研究結論

外部資料比對後，可保留的核心結論有六項。

1. **先定義目的與尺度。** 不先確定要解釋什麼、系統要做到什麼，以及運算和維護成本的限制，就無從判斷因素是必要、可簡化還是非目標。
2. **因素清單不是因果模型。** 必須說明因素如何改變狀態、透過哪些規則影響結果，以及作用會否經由回饋或其他系統傳播。
3. **完整性應以必要關係判斷。** 不是要求所有因素都獨立存在，而是確保核心目標的必要因果路徑、限制、資源流和狀態轉換沒有被忽略。
4. **收斂要簡化表示，不要盲目刪除現實因素。** 可以把作用相近的細節合併成類別、等級、門檻或修正條件；若簡化會改變重要結果，則需保留更細的模型。
5. **專門分析方法按需啟動。** 概念模型、因果推理、控制分析、需求追溯、架構取捨和風險導向驗證互相補位，不應將它們的完整流程全部套在每一個小問題上。
6. **回顧式解釋不等於事前預測。** 真正的預測效力必須透過先封存推論、再揭露後續證據的盲測，並與簡單基線方法比較。

因此，最具希望的候選不是單一既有標準，也不是無限擴大的檢查清單，而是「最小因果核心＋條件式分析方法＋風險排序＋可反駁驗證」。

## 3. 核心方法：正向歸納與反向推導

### 3.1 正向歸納：從現實得到規律

正向工作鏈：

**界定目標與尺度 → 蒐集可核對的領域證據 → 找出會影響目標結果的因素 → 分辨因素的性質 → 抽取相互作用機制 → 比較不同案例 → 明確適用條件與反例 → 壓縮成最小充分模型。**

歸納時不能直接把來源中的分類當成普遍真理。必須確認它們回答的是同一類問題、處於可比較的尺度，並且在不同案例中呈現足夠一致的機制。

### 3.2 反向推導：從模型找出缺漏候選

反向工作鏈：

**固定具體系統的目標與版本 → 將現有設計映射到總覽 → 找出缺少或不一致的狀態、機制、接口及限制 → 解釋它如何破壞必要結果 → 指定可觀察症狀 → 指定可以推翻假說的證據 → 依風險和成本安排最小檢查。**

推導的合格產物不是「應該再加一個功能」，而是一個可以接受反證的陳述，例如：

> 若系統目標包含戰役層決策與戰鬥結果互相影響，但戰後損失、位置或控制狀態沒有回寫戰役層，則兩個玩法層之間的因果閉環可能缺失。檢查戰後狀態是否更新即可支持或推翻此候選。

### 3.3 一項候選缺漏必須包含的最小資訊

每一項候選至少要能回答五個問題：

1. **缺什麼：** 哪個狀態、規則、限制或接口可能不存在／不一致？
2. **為何必要：** 它對應哪個已定義目標或核心情境？
3. **因果理由：** 它缺失時，透過什麼機制改變結果？
4. **可觀察症狀：** 哪種行為、狀態或輸出可作為證據？
5. **反證條件：** 出現什麼資料時，應撤回或降級此候選？

不能回答第五項的內容，可能只是未經檢驗的偏好，不應直接宣告為漏洞。

## 4. 最小系統總覽

下列十三個面向是通用檢查視角，不是每個系統都必須擁有十三個獨立模組。

| 面向 | 要回答的問題 |
|---|---|
| 1. 目標與結果 | 系統要達成什麼？如何知道結果有沒有達成？ |
| 2. 實體與角色 | 哪些對象存在？它們有什麼責任與關係？ |
| 3. 狀態與屬性 | 哪些狀態會變化？哪些必須保持一致？ |
| 4. 能力與限制 | 實體可以做什麼，不能做什麼？ |
| 5. 環境與位置 | 環境如何限制行動、移動、接觸或取得資源？ |
| 6. 資源與流量 | 資源從何而來、如何轉移、消耗、儲存及受限？ |
| 7. 行動與過程 | 什麼行為會觸發什麼狀態變化？ |
| 8. 互動與關係 | 實體如何合作、競爭、阻礙或依賴彼此？ |
| 9. 資訊與決策 | 決策者知道什麼？資訊會否延遲、不完整或錯誤？ |
| 10. 規則與不變量 | 哪些規則必須成立？哪些狀態組合不應出現？ |
| 11. 時間與尺度 | 何時更新？以什麼粒度運行？哪些延遲重要？ |
| 12. 回饋與適應 | 行動結果是否改變後續行為、策略或參數？ |
| 13. 不確定性與觀察 | 哪些資訊未知？如何觀察結果？哪些結論仍需證據？ |

### 4.1 必須區分的四種元素

| 元素 | 定義 | 例子 |
|---|---|---|
| 狀態變數 | 隨時間改變，描述系統目前狀況 | 部隊位置、糧草存量、控制權 |
| 參數 | 在指定情境或模型版本中設定的值 | 路線成本級別、抽象消耗率 |
| 機制／規則 | 描述狀態如何變化、在何條件下轉換 | 移動規則、資源轉運、缺糧門檻 |
| 結果／指標 | 用來判斷目標是否達成或發生什麼後果 | 抵達時間、任務成功、資源短缺 |

把四者混為一談，會導致錯誤的推導：例如把「糧草不足」當成一個 UI 數值，卻沒有定義它如何影響部隊狀態。

## 5. 關係型態與因果閉環

因素之間的關係不止是加法或乘法。必要時要辨識下列關係：

- **直接增減：** 某因素使結果增加或減少。
- **比例／倍率：** 效果依另一因素的大小放大或縮小。
- **門檻／狀態轉換：** 達到條件後，規則或狀態突然改變。
- **瓶頸／容量限制：** 整體效果受最窄、最慢或容量最低的環節限制。
- **條件／分段規則：** 不同地形、狀態或任務使用不同規則。
- **互補／對抗：** 效果取決於相配條件或對手反應。
- **存量—流量：** 存量受取得、輸入、輸出及消耗共同影響。
- **因果中介／回饋：** 一項因素透過中間狀態影響結果，結果又回過頭改變後續狀態。
- **時間／排程：** 順序、延遲、更新頻率改變結果。
- **不確定／隨機：** 結果具有分布或資訊不足，不能假定單一確定值。
- **不變量／約束：** 某些條件必須始終成立，例如資源不能無來源增加。

所謂「閉環」不代表把每一個因素都強行連成循環，而是核心結果必須有足以解釋它的因果路徑；有回饋時要把回饋表示出來，沒有回饋時也不能憑空添加。

## 6. 擴充、收斂與最小充分模型

### 6.1 何時擴充

出現下列情況時，應考慮擴充因素或關係：

- 實際案例出現現有模型無法解釋的結果；
- 某條核心因果路徑缺少必要的中介狀態或限制；
- 同一模型在不同情境下產生不一致結果，而差異可能來自被省略的條件；
- 新證據顯示某個原本合併的因素，在重要情境下具有獨立效果；
- 系統接口、資訊、時間、資源容量或狀態更新可能造成跨系統失效。

擴充要針對「新的重要機制」或「被證據支持的條件差異」，不是因為想得到的細節越來越多。

### 6.2 何時收斂

| 決策 | 採用條件 |
|---|---|
| 核心保留 | 移除後會破壞核心目標、重要因果路徑、不變量或關鍵限制 |
| 合併抽象 | 多個細節在目標尺度下產生相同效果，分開表示不會改變重要結論 |
| 條件擴充 | 只在特定地區、時間、狀態或玩法中影響結果 |
| 延後處理 | 潛在有用，但目前不改變主要決策或缺乏支撐精細設定的資料 |
| 排除本輪 | 與已界定目標、必要結果和品質約束沒有可辨認的關係 |
| 保留為未知 | 可能重要，但目前證據不足，不能直接刪除或自行假定答案 |

「移除後無差異」只對目前的模型、情境和參數範圍有效，不代表該因素在所有情況下都不重要。

### 6.3 最小充分模型的停止規則

當代表性情境中的核心因果路徑已可追蹤、重要限制已標示、主要結果能被解釋、候選能被反駁，而新增細節不再改變重要結果或架構取捨，就可停止本輪擴充。

這表示模型足以回答目前的問題，不代表現實已被完整描述。出現新反例或目標改變時，只需重新開啟受影響的部分，不必重建整份模型。

### 6.4 不以單一分數取代判斷

不建議把影響程度、發生可能性、證據信心、跨系統傳播範圍與驗證成本硬壓成一個精確總分。這些維度不同，資料不足時更不能假裝有精確機率。

採用兩階段排序：
1. 先判斷候選是否觸及核心目標、不可違反的限制或高後果失效。
2. 再比較影響範圍、情境暴露、現有證據、未知程度與檢查成本。

優先度高不代表候選已被證實；證據信心高也不代表影響一定重大。

## 7. 外部方法的整合與取捨

外部研究沒有提供一份適用所有領域的完整因素清單，也沒有任何單一方法能同時解決因果抽象、需求遺漏、控制失效、架構取捨和預測驗證。因此，應按功能分工使用。

| 方法家族 | 主要用途 | 本研究的採用方式 |
|---|---|---|
| 概念建模與 ODD | 說清目的、狀態、尺度、流程、初始化及子模型 | 作為描述骨架；不把文件完整當成因果正確的證明 |
| 因果／存量—流量模型 | 解釋因素如何作用、資源怎麼變、回饋如何傳播 | 作為核心機制模型 |
| 系統理論控制分析（STPA） | 檢查缺少、錯時、錯序或基於錯誤狀態的控制行為 | 在 AI、指揮、排程、資源調度與多系統協調中按需啟用 |
| 需求追溯與介面管理 | 檢查目標是否被機制承接，以及系統接口兩端是否相容 | 建立「目標—行為—機制—接口—結果」雙向關係 |
| 架構取捨分析（ATAM） | 辨認效能、可靠性、可修改性等品質目標之間的衝突 | 針對少數高價值情境分析，不照搬大型工作坊流程 |
| 風險導向測試／風險管理 | 決定有限分析資源先投入哪裡 | 保留影響、暴露、證據和成本等分開維度，不假造精確分數 |
| 模型驗證與確認（V&V） | 區分概念合理性、實作是否符合定義、模型是否適用目標用途 | 分層判定證據強度；設計推演不等於程式執行或現實驗證 |
| 來源追溯與評測基準 | 知道主張來自哪項證據，且評估可以被重複核對 | 保存足夠來源與版本資訊；不重建全部歷史文件演變 |

### 7.1 為何不全盤採用每一套方法

完整 ODD 可能變得過長，且其文獻本身也指出複雜模型、設計理由與適用性評估等方面存在限制。完整 STPA 偏向系統安全與控制危害，不值得施加在每個低風險功能。完整 ATAM 需要結構化的架構情境與跨角色分析，不能每個小問題都啟動。航太級模型可信度標準也不應原樣變成每次概念研究的行政負擔。

因此，最優候選採「核心常駐、分析插件按需啟動」：

- **常駐核心：** 目標與範圍、狀態與尺度、因果／資源流、必要限制與接口、預期結果、證據與未知。
- **按需插件：** 控制分析、需求追溯、品質取捨、風險排序、正式模型或程式驗證。
- **禁止項：** 為了完整感而照搬所有方法、建立無限長的固定檢查表，或把一個方法的分類強制套用到所有領域。

## 8. 示例：漢代戰略地圖中的地形、行軍與糧道

### 8.1 先固定遊戲尺度

假設目標是仿《全面戰爭》式的漢代戰役地圖：玩家在區域與路線尺度調度部隊、安排行軍，並維持糧草供應。這不是逐兵、逐袋糧食、逐秒模擬；模型要支援戰略決策，並維持可接受的運算與設計成本。

### 8.2 擴充後的現實因素

- **地理與地形：** 平原、丘陵、山地、森林、沼澤、隘口等，影響通行成本、路線選擇與瓶頸。
- **道路與節點：** 官道、一般道路、山徑、橋梁、渡口、城邑及糧倉之間的連接。
- **河道：** 陸路障礙、渡河節點、可能的水運通道，以及可被控制或切斷的運輸瓶頸。
- **部隊：** 位置、規模、移動能力、負重或抽象行軍狀態。
- **糧草：** 儲存量、來源、部隊需求、運輸能力、送達與消耗。
- **政治與軍事控制：** 己方、敵方或不可用節點，影響路線安全與補給取得。
- **環境條件：** 只有會改變重要選擇的季節、降雨、水位或道路狀態才保留為修正條件。
- **時間與更新順序：** 行軍、供應、消耗與狀態變化何時結算，以及是否存在延遲。

漢代背景應落在交通網、地點分布、可用運輸方式和當時制度條件，而不只是換一套美術名稱。具體歷史參數需要來源支持；無可靠數據時，只可使用明確標記的遊戲抽象值，不可偽裝成歷史定值。

### 8.3 收斂後的模型

把細節收斂成三個互相關聯的系統：

1. **地圖與通行：** 地形、道路、河流、橋梁和渡口，決定可用路徑、移動成本與通行限制。
2. **部隊與移動：** 管理部隊位置、規模、可移動狀態和抽象補給狀態。
3. **糧草與供應網：** 管理糧倉存量、供應來源、運輸路線、容量與消耗。

三者共用地圖與控制狀態。河流不需要完整流體模擬，但至少同時表達陸路通行限制和可用的水運連接；糧道不需要逐輛追蹤運輸車，但不能是沒有來源、沒有容量、也不會被切斷的無限輸送。

抽象的資源關係可寫為：

**存量變化 = 取得量 + 實際送達量 − 實際消耗量。**

實際送達量還受來源存量、路線連通與運輸能力限制。這比逐人逐日計糧簡單，但仍保留糧道的戰略意義。

### 8.4 從模型反推缺漏

假設一個原型出現以下行為：
- 部隊在沒有渡口、橋梁或其他通行機制的情況下任意越河；
- 運輸路線被敵軍切斷後，糧草仍無限制送達；
- 部隊糧草耗盡後，狀態和行動完全不受既定規則影響；
- 行軍結算改變了位置，但供應系統仍用舊位置計算消耗或送達。

這些不是立即確診的程式 Bug，而是可檢查的結構缺漏候選：通行限制缺失、糧道容量或連通狀態未承接、資源門檻未連接部隊狀態、或更新順序造成狀態不一致。

這個例子證明的是方法如何運作，不是對某款遊戲的實際程式已完成驗證。

## 9. 歷代遊戲資料的回顧式初測

### 9.1 初測目的與限制

初測的問題是：因果總覽是否能將公開的歷史開發資料與已知問題，轉化成有明確機制、可觀察症狀及反證條件的缺漏候選，而不只是整理哪些玩法在後續版本中新增。

方法是先按已知的目標和玩法結構抽取因果關係，再將公開開發資料用作回顧對照。由於已知結果先於推論，存在事後偏誤；這不是盲測，也沒有建立可計算的命中率。

### 9.2 四個案例

| 案例 | 公開資料中的現象 | 因果方法可提出的候選 | 判定邊界 |
|---|---|---|---|
| Shogun: Total War | 初期方向接近傳統 RTS；後來戰役地圖和即時戰鬥形成結合 | 若目標包含雙層戰略玩法，需檢查戰略決策是否決定接戰條件，戰鬥結果是否回寫部隊與領土狀態 | 若原目標只是 RTS，缺少戰役層不是漏洞 |
| Civilization 早期原型 | 早期即時制原型讓玩家等待資源區域逐漸成長，後來的回顧指出玩法欠缺刺激 | 檢查玩家決策密度、行動後回饋與等待時間是否符合目標體驗 | 模型只能提出設計風險；是否無聊仍需遊玩和玩家資料 |
| Rome: Total War | 開發資料指出戰場規模受到記憶體與圖形處理能力等限制 | 擴大單位、地形與系統規模時，要檢查互動成本、硬體預算與整合行為 | 能推導效能風險類別，無法只靠概念模型定位程式瓶頸 |
| Total War: Rome II | 上市後開發者承認部分玩家遇到穩定性、效能、回合結算、AI 與平衡問題 | 將大規模結算、戰役與戰鬥接口、AI 狀態回饋和硬體差異列為待檢查風險 | 公開聲明不能證明每項候選都是根因；具體問題仍需實作證據 |

### 9.3 與單純版本演變法的差異

- **版本演變法：** 擅長記錄後來加了什麼、改了什麼或修了什麼；但新增功能不等同前版漏洞。
- **因果缺漏法：** 依已定義目標推導必要狀態、因果路徑與限制；理論上可在看到後續結果之前產生候選，但需要驗證預測是否命中。
- **整合方式：** 歷史資料提供案例和事後核對；因果模型產生事前假說；後續資料和實作證據負責裁決。

### 9.4 初測裁決

本次案例支持方法能產生有用的結構性檢查方向，例如跨層回寫、決策回饋、容量限制、運算預算和狀態交互。但由於不是盲測，無法排除事後合理化，也沒有數據證明它比簡單基線更準。

因此目前結論是：**具可行性，預測效力未確立。**

## 10. 證據分級與驗證規則

### 10.1 證據分級

| 級別 | 含義 | 可以宣稱什麼 |
|---|---|---|
| E0：假說 | 由通用原理或初步推理提出，尚無獨立資料 | 只能列為候選 |
| E1：單一來源支持 | 有一份具體來源或案例支持 | 可說個案有支持，不可外推成普遍規律 |
| E2：多源／多情境支持 | 不同來源或情境呈現相近機制 | 可提高可信度，但仍須寫清範圍 |
| E3：可重現檢查 | 有可重複的情境、資料或實作結果，且能檢驗預測 | 可判斷候選在該情境是否獲支持 |
| E4：盲測／獨立基準支持 | 推論在後續結果揭露前已封存，並與獨立基準比較 | 才能評估方法的事前預測效力 |

這是本研究建議使用的工作分級，不是任何外部機構的官方評級標準。

### 10.2 必須分開的四種驗證

1. **概念合理性：** 因果解釋是否清楚、有無明顯矛盾。
2. **規則正確性：** 計算或規則是否符合正式定義。
3. **實作正確性：** 程式是否按定義運作。
4. **用途適用性：** 模型是否足以支援既定決策，並將不確定性清楚表達。

其中一種成立，不代表其餘三種自然成立。

### 10.3 未來若要驗證事前預測力

如要另行進行盲測，建議以新驗證任務處理，而非保持本研究無限開放：

1. 選取具足夠公開資料的遊戲與版本截點。
2. 隱藏後續版本、評價、Bug 修復資訊和已知結果。
3. 先封存候選缺漏，包含原因、症狀、反證條件和證據狀態。
4. 同時使用簡單版本差異整理或一般功能清單作為基線。
5. 揭露後續證據，獨立判定命中、誤報、漏判、方向變更、刻意取捨與無法判定。
6. 若樣本與裁決品質足夠，再計算精確率、召回率、誤報率、分析成本及提前量；樣本不足時只報個案，不宣稱普遍準確率。

## 11. 建議採用的標準工作流程

以下為結案後建議保留的精簡版操作流程。它不是要每次生成更多文件，而是用來指導每個新研究任務。

### A. 固定目標與邊界
說明要解釋的現象、目標情境、尺度、品質限制，以及哪些內容不在本輪範圍。目標未定時，不能把不存在的功能直接判為漏洞。

### B. 建立最小系統總覽
列出相關實體、狀態、資源、環境、能力、限制、規則、時間、接口和結果。先確認必要關係，再決定哪些細節值得獨立表示。

### C. 進行擴充
從現實與領域證據尋找已漏掉的因素、必要中介狀態、資源流、控制條件、瓶頸和反饋；記錄來源與適用範圍。

### D. 進行收斂
把作用相近且不改變目標結果的細節合併；將非核心細節延後或保留為未知；以「移除後是否改變重要結果」作為比較依據，而不是追求一張無限長的清單。

### E. 依缺漏類型啟動分析插件
- 因果與資源流不完整：使用因果／存量—流量檢查。
- AI、命令、排程或協調可能出錯：使用精簡控制分析。
- 需求沒有對應到機制、或跨系統資料不一致：做雙向需求與接口追溯。
- 效能、準確性、可玩性、可維護性互相衝突：做小範圍架構取捨分析。
- 風險高或結論會改變架構：安排實際驗證；低風險候選先做較便宜的反證。

### F. 產生可反駁的候選
每項候選包含「缺什麼、影響哪個目標、因果理由、預期症狀、反證條件、證據級別、優先度和查證成本」。區分結構候選與已確認問題。

### G. 以最小成本驗證並更新
先使用來源核對、邊界檢查、簡化推演或狀態表排除薄弱假說；只有在能改變核心決策時，才投入昂貴的程式實驗、效能剖析或高精度模型。

### H. 按邊際資訊價值停止
若新增細節不再帶來新的高影響因果機制、不改變架構決策或重要結果，而核心路徑、限制和未知已標示，就停止本輪擴充。新反例或目標變更時，只重新打開受影響部分。

### 已完成

- 將現實規律歸納、最小系統總覽、因果關係、擴充與收斂原則整合為一套方法。

### 最終結論

本研究本階段正式結案，採用以下整合原則：

**現實與領域證據 → 最小因果模型 → 按需啟動專門分析 → 產生可反駁的缺漏候選 → 風險排序 → 低成本反證 → 以獨立證據評估。**

本方法的價值不在於收集最多資料或建立最長清單，而在於用最少且有根據的關係解釋指定結果，辨識哪些機制不可缺、哪些細節可合併、哪些部分仍未知，以及下一步最值得查證的是什麼。

**結案狀態：研究整理與方法取捨完成；回顧式初測完成；盲測預測效力未驗證。**
