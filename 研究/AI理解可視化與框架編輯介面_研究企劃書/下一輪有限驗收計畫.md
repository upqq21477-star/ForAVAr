## A. 當前工作：候選驗收

### 固定原則

執行環境必須能同時讀取本資料夾中的現行驗證器、Schema、關係規則、跨物件規則與 fixtures。使用 Python 3.10+，記錄 Python／jsonschema 版本、實際命令、stdout、stderr、退出碼與被測檔案 SHA。若環境無法完成實際執行，維持 BLOCKED，不可用靜態檢查代替。不把 GitHub Actions、付費遠端執行或新 API 作為必要依賴。

### 必做測試

1. **語法與結構：** 對現行驗證器執行語法檢查；載入 Schema、關係登錄表、跨物件規則與案例資料。
2. **規則完整性：** 檢查 active rule IDs 唯一、L0–L5 分配完整，17 種關係型別與關係登錄表一致。
3. **歷史回歸：** 把舊版 18 個斷言在現行驗證器與規則上重新執行；逐項記錄，不繼承舊 PASS。
4. **證據關係：** 分開測試 is_evidence_for 與 refutes 的方向、端點及來源條件，並確認不會自動改寫 evidence_status。
5. **循環邊界：** 測試循環搜尋上限、無環稠密圖、精確上限與長鏈，確保分析不完整時輸出 VLD-407 並阻擋發布。
6. **發布安全：** 錯誤／缺欄位輸入 fail-closed；已發布 revision 不可重複發布；只有 proposed 版本可進入發布流程。
7. **版本綁定：** 驗證 JSON model_revision 的精確 SHA-256；檢查 Markdown marker 正確、缺失及不一致三種情況。
8. **診斷與輸入健全性：** 驗證 warning ID 唯一且內容完整；測試錯誤根型別、錯誤 warning 欄位型別、非 UTF-8 Markdown、缺來源、日期格式及未捕捉例外。

### 結果記錄

唯一結果文件是[演進與驗收總結](./驗證/演進與驗收總結.md)。每個案例只能標記 PASS、FAIL、BLOCKED 或 NOT_RUN，且須連結實際輸出和被測 SHA。歷史結果不得覆蓋或借用給新基線。舊案例清單中的 70 個 TC ID 是測試定義，不代表 70 項均已執行。

### 停止條件

所有規劃案例均有狀態與可定位證據。若失敗，最多一輪針對性修正後完整回歸一次；仍失敗或受環境阻擋，就記錄原因與決策選項並停止，不進入無限重測。這一階段通過，只代表原型／規格基線足夠穩定，不代表 UI 或正式 Runtime 完成。

## B. 只有驗收停止條件通過後，才可開始 UI 需求規劃

這是後續閘門，不是目前已啟動的工作。

1. 定義核心使用者任務：檢視 AI 理解、修正節點／關係、核對來源、查看差異、處理衝突、確認與匯出。
2. 定義資訊架構：樹狀／清單主視圖、局部關係圖、屬性與來源面板、差異／衝突檢視、驗證與發布診斷。
3. 定義手機操作：選取、編輯、縮放、刪除保護、復原，以及精準拖曳的替代操作。
4. 將每項操作寫成可驗收行為：前置條件、使用者操作、成功結果、錯誤結果及恢復方式。
5. 確保所有視圖讀寫同一份正式模型，並維持語意資料、版面資料、來源、審核、證據與版本狀態分離。
6. 完成技術方案與最低成本評估後，才寫正式實作計畫；未證明必要之前不加新服務依賴。
