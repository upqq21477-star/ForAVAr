# AI 理解可視化框架：資料契約反方審查

> **日期：** 2026-10-26  
> **檢查基線：** 資料契約 v0.2.0-draft、JSON Schema 0.2.0、relation profile default-v1 草案  
> **審查狀態：** 規格層反方檢查完成一輪；JSON Schema meta-validation、跨物件程式測試及 Runtime 均未執行  
> **用途：** 記錄發現的規格缺陷、已採取的修正與尚未驗證的風險

---

## 摘要

本輪審查沒有把「JSON 可解析」當成整體正確。檢查集中於語意關係是否可精確判定、循環警告是否會在發布階段被忽略、來源與證據的語意是否混淆，以及測試清單本身是否維持唯一穩定 ID。

已完成三項規格修正：

1. 重複邊判定改為依 `relation_type`、正規化端點及正規化 `condition_refs` 判定。相同端點下，不同適用條件可以構成不同關係；來源不同本身不會自動構成另一條邊。
2. 對循環警告增加發布紀錄要求：保留循環路徑，並由審查者明確確認；否則阻擋發布。
3. 新增有向 `refutes` 關係，和 `is_evidence_for` 一起區分支持證據與反證。證據命題須引用來源；關係本身不會自動修改目標主張的 `evidence_status`。

另外，發現測試案例清單中曾重複出現部分測試 ID，已做去重並更新為 v0.2.0。這是文件治理缺陷，不應隱藏；測試案例數量或內容改變後，必須再檢查 ID 唯一性。

## 2. 本輪靜態檢查

目前已實際執行的靜態檢查僅包括：

- Schema 的 `relation_type` 與 relation registry keys 完全相同，現為 17 項。
- relation registry 的每個關係都有 family、meaning、cycle policy 與 impact policy。
- 邊 Schema 不直接重複保存由 registry 推導的 `relation_family`、`cycle_policy` 或 `impact_policy`。
- 測試清單中的案例 ID 已做去重。

這些結果不等於完整 Draft 2020-12 meta-schema 驗證、不等於自訂跨物件規則已實際執行，也不等於 Runtime 或使用者任務驗收通過。

## 3. 應保留的未解風險

### 3.1 關係類型循環與組合約束

目前 v1 按 `relation_type` 檢查循環；不同關係類型組成的循環預設只警告。這是刻意的保守取捨：不同語意的關係不能直接當成同一種依賴。若未來某個子系統明確要求「contains + depends_on + precedes」的組合不能成環，應為該組合子圖註冊一條獨立規則，而不是全圖通用 DAG 禁令。

### 3.2 支持與反證的證據裁決

`is_evidence_for` 和 `refutes` 用於描述關係方向，不是自動真值判定器。同一主張可以有支持來源與反證來源；目標的 `evidence_status` 只有經過來源評估及人工／規則裁決後才能更新。需要保存的不是單純「來源數」，而是來源定位、它支持或反駁哪項主張、適用範圍及未解矛盾。

### 3.3 Schema 驗證器與實作尚未定案

目前未指定正式的 JSON Schema validator 及其 `format` 行為。未完成工具選擇之前，不能宣稱 schema meta-validation PASS。跨集合唯一 ID、懸空引用、邊重複、循環和發布門檻均需要自訂確定性驗證器，不能只依 JSON Schema。

## 4. 後續執行順序

1. 固定 Schema、relation registry、cross-object rules 與 fixtures 的內容 SHA。
2. 執行 Draft 2020-12 meta-validation，記錄驗證器版本及 format 行為。
3. 用有效／無效 fixtures 執行 L0–L3；每項只在有實際輸出及可重現證據後標記 PASS／FAIL。
4. 桌上推演支持／反證、條件不同的重複邊、warning cycle 發布確認和混合關係循環。
5. 修正缺陷後固定一個完整基線，再進入 UI 與最小原型建構。

若沒有新增證據、需求變更或實際失敗，不重複進行相同反方審查。每次重開須指明缺陷 ID、受影響需求和新證據。
