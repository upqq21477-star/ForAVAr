## 摘要

本文件將「人工審核狀態」、「證據評估狀態」和「模型生命週期狀態」分開定義。任何單一狀態都不能取代其他狀態：使用者接受某個模型節點，不代表外部事實已獲證實；JSON 結構通過，也不代表該內容已獲人工接受或可以發布。

本版採取以下決策：

1. 審核、證據、發布是三個獨立軸線。
2. 已接受的物件一旦有語意修改，須進入重新確認狀態。
3. 已否決的內容不能在內容完全相同、沒有新證據的情況下直接重新送審。
4. 已發布版本視為不可變的歷史基線；修訂要建立新草稿版本。
5. 發布不是按鈕點擊結果，而是資料契約、跨物件規則、證據、審核與版本記錄共同通過的決策。
6. 發布規則失敗要明確阻擋並列出原因，不可自動降級、靜默忽略或默默套用最新版本。

以上目前是規格決策草案，尚未由原型或 Runtime 測試證實。

## 1. 三個獨立狀態軸線

### 1.1 人工審核狀態（Review status）

| 狀態 | 定義 | 對發布的影響 |
|---|---|---|
| `pending_review` | 尚未完成必要的人類審核 | 不能發布 |
| `accepted` | 人類接受該物件作為目前模型的一部分 | 仍須通過證據、結構及發布規則 |
| `rejected` | 人類否決目前內容 | 不能發布；要修訂或移出有效模型 |
| `disputed` | 存在尚未解決的實質爭議 | 不能發布 |
| `needs_reconfirmation` | 先前接受的內容已發生語意改變，接受狀態不再自動有效 | 不能發布 |

重要原則：`accepted` 只代表人類接受其作為工作模型的一部分，並不把外部事實、因果主張或 AI 推論自動轉成已證實內容。

### 1.2 證據狀態（Evidence status）

| 狀態 | 定義 |
|---|---|
| `not_applicable` | 此物件不需要事實證據評估 |
| `unverified` | 尚未核實 |
| `supported` | 有可追溯資料支持目前主張 |
| `insufficient` | 存在來源，但不足以支持目前主張 |
| `contradicted` | 存在重要反證或主張與來源直接衝突 |
| `mixed` | 證據彼此衝突、條件限制未解或整體不確定 |

證據狀態是對「內容及其來源」的評估，不等同來源數量。增加來源不會自動增加可信度，來源存在也不代表來源真的支持該項主張。

### 1.3 模型生命週期狀態（Model state）

| 狀態 | 定義 | 允許的下一狀態 |
|---|---|---|
| `draft` | 工作草稿，可持續修改 | `proposed`、`archived` |
| `proposed` | 已提交發布審查，但尚未發布 | `draft`、`published`、`archived` |
| `published` | 通過發布門檻，可供下游指定版本使用 | `superseded`、`archived` |
| `superseded` | 已被新發布版本取代 | `archived` |
| `archived` | 結束使用但保留歷史 | 無 |

生命週期狀態描述整份模型修訂，不描述個別節點的真偽或人類審核結果。

## 2. 人工審核狀態轉換

| 目前狀態 | 觸發事件 | 目標狀態 | 必要條件 |
|---|---|---|---|
| pending_review | 審核者接受 | accepted | 有明確審核決策 |
| pending_review | 審核者否決 | rejected | 保留否決理由 |
| pending_review | 發現實質分歧 | disputed | 記錄爭議點 |
| accepted | 語意欄位改變 | needs_reconfirmation | 計算前後差異並記錄原因 |
| rejected | 內容修訂或新增可追溯證據 | pending_review | 必須有實質改動或新證據 |
| disputed | 爭議解決並接受 | accepted | 記錄裁決及依據 |
| disputed | 爭議解決並否決 | rejected | 記錄裁決及依據 |
| disputed | 新證據需要重新檢視 | pending_review | 證據變更可追溯 |
| needs_reconfirmation | 重新審核接受 | accepted | 審核者檢視變更及影響 |
| needs_reconfirmation | 重新審核否決 | rejected | 保留否決原因 |
| needs_reconfirmation | 新爭議尚未解決 | disputed | 保留爭議依據 |
| needs_reconfirmation | 新證據要求再次評估 | pending_review | 保留新證據引用 |

禁止的捷徑：
- 不能因為物件沒有改動就自動將 `pending_review` 轉成 `accepted`。
- 不能把 `rejected` 原封不動重送後直接視為新一輪審核。
- 不能因為來源增加就自動把 `unverified` 改成 `supported`。
- 不能把單一節點的接受決策直接繼承給所有相連節點。

## 3. 語意修改與重新確認

以下變更原則上會使原接受狀態失效：

- 節點的名稱以外的關鍵語意欄位改變，例如 `function`、`claim_kind`、`entity_kind`、結構角色或適用條件；
- 關係的來源、目標、關係類型、條件、來源依據或影響規則改變；
- 條件的表達式、用途或評估模式改變；
- 支持該物件的來源被刪除、改指向另一來源，或來源內容的相關主張被修正；
- 受影響關係規則或 schema 版本改變，致使先前的判斷不再成立。

純視覺版面變更（節點座標、縮放、折疊狀態）不應單獨使語意審核失效。若一個節點僅改名，是否需要重新確認由專案政策決定；第一版預設為「不自動失效，但要產生可見差異」，除非名稱本身是標準識別或具有領域語意。

影響分析只能找出「需要重新檢視的候選物件」，不能把影響傳播當成已證明內容失效。人類裁決仍需保留。

## 4. 模型生命週期轉換

| 目前狀態 | 觸發 | 目標狀態 | 門檻 |
|---|---|---|---|
| draft | 準備提案 | proposed | 必填資料形狀通過，未解問題已列出 |
| proposed | 審查要求修訂 | draft | 記錄阻擋原因和待修改項目 |
| proposed | 所有發布門檻通過 | published | 通過第 5 節全部條件 |
| draft | 放棄本版 | archived | 記錄放棄原因，保留歷史 |
| proposed | 放棄本版 | archived | 記錄放棄原因，保留歷史 |
| published | 已有新發布版本取代 | superseded | 記錄取代它的版本 ID／revision |
| published | 停止使用但不再有替代版 | archived | 記錄退役原因 |
| superseded | 到達歸檔政策 | archived | 歷史版本與來源仍可追溯 |

已發布內容修訂應產生新的 draft revision。既有 Git commit 本身不可改寫；可以在後續提交中標示舊修訂已被取代，但不能覆蓋歷史內容。

## 5. 發布門檻

`proposed → published` 必須同時滿足下列條件：

1. **契約有效：** JSON 語法與固定版本 Schema 驗證通過。
2. **跨物件完整：** 節點、邊、條件、來源的 ID 唯一；所有參照都指向正確類型的存在物件。
3. **圖規則符合：** 無自我連線、無重複語意邊、無違反關係循環政策的循環；使用中的關係類型都有規則。
4. **審核完成：** 所有有效節點、邊、條件均為 `accepted`。被否決的項目不能留在有效發布模型中。
5. **證據如實：** 未核實、證據不足、遭反駁或混合證據的主張不得呈現為已證實事實；重要核心主張有可追溯來源。
6. **版本一致：** Markdown、JSON 和發布記錄指向同一個不可變修訂。
7. **版本可重現：** 發布記錄固定 schema 版本、關係規則 profile／版本、模型 revision、變更摘要及來源基線。
8. **無靜默降級：** 缺少版本、規則或來源時，拒絕發布或回報阻擋原因，不得偷偷回退到其他版本。

草稿可容納未完成的項目；發布版不能用未解狀態冒充完整模型。若未來確有必要允許有條件發布，必須建立明確的例外授權，記錄核准者、範圍、理由、期限／重審條件及審計位置，不能提供通用的「忽略警告」按鈕。

## 6. 錯誤回報格式

所有阻擋錯誤至少需提供：

| 欄位 | 說明 |
|---|---|
| `rule_id` | 對應規則 ID |
| `severity` | error／warning／info |
| `object_id` | 出錯物件（若可識別） |
| `json_pointer` | 具體欄位路徑 |
| `message` | 人類可理解的原因 |
| `related_object_ids` | 相關節點、邊、條件或來源 |
| `rule_profile_version` | 本次所用規則版本 |
| `action` | 阻擋、修正、警告或需要人工裁決 |
| `evidence_reference` | 可供重現的輸入、輸出或記錄位置 |

錯誤順序需穩定（驗證階段、嚴重程度、JSON Pointer、rule ID），方便差異比較和重現。驗證器不得在驗證時暗中修改輸入；需要修正時，應輸出修正建議或候選變更供人類確認。

## 7. 關鍵反例／待桌上推演案例

| ID | 反例 | 預期處理 | 狀態 |
|---|---|---|---|
| STATE-001 | accepted 節點的 function 被改寫 | 轉為 needs_reconfirmation | NOT_RUN |
| STATE-002 | rejected 內容未改動、無新證據直接重送 | 不得自動重審通過；要求修訂或新證據 | NOT_RUN |
| STATE-003 | published 模型內存在 pending_review 物件 | 阻擋發布 | NOT_RUN |
| STATE-004 | 外部事實主張為 supported，但沒有可定位來源依據 | 標記資料治理缺陷並阻擋核心發布 | NOT_RUN |
| STATE-005 | 使用者接受一個主張，但其 evidence_status 為 contradicted | 保留兩種狀態，禁止以接受決策覆蓋反證 | NOT_RUN |
| STATE-006 | Published V1 修改後繼續沿用同一 revision 身分 | 拒絕變更已發布修訂；建立新的 draft revision | NOT_RUN |
| STATE-007 | 缺失規則 profile 時要求發布 | 阻擋並指出缺少的規則版本 | NOT_RUN |
| STATE-008 | 視圖座標改變但語意欄位未變 | 只記錄版面差異，不使語意審核失效 | NOT_RUN |

## 8. 結案與重新開啟

本文件在規格層的完成條件：狀態軸線彼此獨立、所有允許／禁止轉換有定義、發布門檻可判定、錯誤能追溯到物件與規則、反例已有案例 ID。

實際實作驗收仍為 NOT_RUN。只有當資料契約、狀態轉換或發布案例出現新反例、實測缺陷或新需求時才重開；沒有新資訊時不重複審核相同設計。
