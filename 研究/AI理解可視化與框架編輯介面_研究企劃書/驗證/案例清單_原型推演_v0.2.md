## 1. 使用規則

- 本清單定義要測什麼、如何注入條件、預期結果是什麼。尚未執行的案例維持 `NOT_RUN`；第 2.1 節記錄靜態一致性檢查，第 2.2 節記錄已執行的 Schema meta-validation 及原型斷言。Runtime／使用者驗收仍未執行。
- `PASS` 只能在保留輸入、實際結果、工具／版本、日期及證據位置後使用。
- 桌上推演只能標示 `TABLETOP_REVIEWED`；不能當成 Schema 驗證、程式測試或 Runtime 通過。
- 若規格改變，需記錄受影響測試 ID，不得靜默刪除失敗案例。
- 同一資料、同一規則且無新證據時，不重複開啟相同研究迴圈。

狀態值：
- `NOT_RUN`：尚未執行。
- `TABLETOP_REVIEWED`：只完成人工推演，非程式驗證。
- `PASS`：依預定測試實際執行且結果符合預期。
- `FAIL`：實際結果未符合預期。
- `BLOCKED`：因所需環境或前置條件不足而無法執行。

## 4. 第一輪桌上推演優先順序

不需要一次跑完所有案例。第一輪先處理直接影響資料完整性和版本正確性的案例：

1. `TC-STR-001`：最小有效模型。
2. `TC-STR-003`、`TC-STR-004`、`TC-STR-005`：條件與命題狀態欄位。
3. `TC-GRAPH-001` 至 `TC-GRAPH-006`：ID 唯一與所有引用存在。
4. `TC-GRAPH-009` 至 `TC-GRAPH-016`：不同關係家族的循環政策、全域 ID、重複語意邊與自我連線。
5. `TC-DIFF-001`、`TC-DIFF-003`、`TC-DIFF-004`：語意與版面差異分離。
6. `TC-IMPACT-001`、`TC-IMPACT-003`：影響政策的方向與限制。
7. `TC-EVID-001` 至 `TC-EVID-004`：支持／反證的方向性關係及來源追溯。
8. `TC-PUB-003` 至 `TC-PUB-005`、`TC-STATE-001` 至 `TC-STATE-006`：發布門檻與狀態轉換。
9. `TC-AI-001`、`TC-AI-002`：明確版本取用和禁止默默回退。
10. `TC-LOOP-001`、`TC-TRACE-001`、`TC-TRACE-002`：閉環停止及雙向追溯。

排序理由：先保證模型不破損，再確保修改與版本正確，最後測試較高層的人機流程與研究治理。

## 5. 個案結果紀錄格式

實際開始執行後，每個案例要補上：

| 欄位 | 用途 |
|---|---|
| Case ID／版本 | 確認測試案例本身未被無聲改寫 |
| 被測 Schema／Registry commit | 固定基線，避免用不同規則對照 |
| 輸入檔案或內容雜湊 | 可重現同一測試輸入 |
| 實際步驟 | 記錄工具／UI 操作順序 |
| 預期結果 | 執行前固定，不看結果後才修改標準 |
| 實際結果 | 完整記錄通過、失敗或未執行 |
| 證據位置 | 日誌、差異、截圖或輸出內容的路徑 |
| 缺陷 ID | 失敗時連結問題與修正紀錄 |
| 重新測試結果 | 修正後的新結果，不覆蓋第一次失敗 |

### 簽核規則

- 不能只因 JSON 可解析就宣告模型有效。
- 不能只因 Git commit 成功就宣告資料契約通過。
- 不能只因桌上推演沒有發現問題就宣告 Runtime 可用。
- 任何案例若被修改，須保留修改原因和受影響版本。
- 未執行的案例繼續保持 `NOT_RUN`，不能以推論、預期或主觀信心填成 PASS。
