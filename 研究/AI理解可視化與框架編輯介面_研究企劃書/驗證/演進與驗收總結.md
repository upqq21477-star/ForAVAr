# 演進與驗收總結：問題、修正、結果與下一步

> 更新日期：2026-10-28  
> 此文件是唯一的歷史與現行驗收摘要。原本分散的反方審查、覆蓋率審查、靜態審查、歷史測試報告與變更紀錄已融合在這裡；日常接手不需逐份查讀舊版本。

## 1. 一頁結論

專案已完成架構與資料契約草案，形成 JSON 正式模型、關係規則、分層驗證、獨立狀態軸線與版本發布閘門。歷史原型在舊基線上曾通過有限測試；目前驗證器候選的靜態前置檢查也已完成，但候選程式本身沒有實際執行。

**現況：STATIC_PREFLIGHT_PASS / PYTHON_EXECUTION_BLOCKED。停止條件未達成。不可開始 UI 正式實作。**

**定位裁決（2026-10-28）：** 圖形認知層是既有認知架構的人類使用者側延伸，可以有獨立圖形表示、使用者任務狀態機及固定引導流程，用於降低理解、操作及互動門檻；它不替代機器認知核心，也不要求所有 AI 任務使用固定推理路徑。研究企劃與閉環路線已更新，但候選執行、UI 與使用者效益均不能據此標記為通過。

## 2. 因果鏈：發現什麼、因此如何修正

| 問題／觀察 | 根本原因 | 已形成的規格或程式修正 | 現有證據／剩餘限制 |
|---|---|---|---|
| 結構角色與物件類型、審核與證據、發布狀態容易混淆 | 不同責任壓在同一欄位或狀態 | 分開結構角色／物件類型；分開 review_status、evidence_status、model_state | 資料契約與 Schema 已描述；完整 Runtime 未驗 |
| 層級、流程、因果關係被視為同一種圖規則 | 關係語意及循環政策不同 | 按 relation_type 集中登錄 family、cycle policy、impact policy；邊上不重複保存派生規則 | 17 種關係與 Schema 列舉靜態一致 |
| 重複邊判定可能誤合併不同條件的邊 | 缺少穩定的語意鍵 | 使用 relation_type、正規化端點及正規化 condition_refs；來源不同本身不構成不同邊 | 規則候選已更新；現行程式測試仍待執行 |
| 有來源被誤當成有支持，反證方向不明 | provenance 與證據判定合併 | 定義 is_evidence_for 與 refutes 的有向語意；關係存在不自動改寫 evidence_status | 複合 fixture 曾通過舊 Schema／原型；兩種關係仍需獨立測試 |
| 循環警告可能在發布時被忽略 | 警告路徑與人工確認沒有被當成發布資料 | 保留精確循環路徑、規則 ID 及人工確認；未確認則阻擋發布 | 已寫入現行規則與狀態機草案；發布行為 NOT_RUN |
| 原驗證器可能在輸入無效後仍繼續處理、重複發布已發布版本、版本綁定不可靠 | fail-closed、revision 與狀態閘門不足 | 候選程式加入 fail-closed、JSON SHA-256 與 Markdown revision marker、proposed 狀態限制 | 靜態源碼標記已找到；未實際執行 |
| Warning ID 依賴錯誤文字解析、警告內容可能被改寫 | 診斷識別與內容未被當成結構化資料核對 | 使用穩定 warning ID，發布紀錄核對 rule_id、severity、message 與相關物件 | 靜態審查有涵蓋；定向測試 NOT_RUN |
| 循環探索上限可能無法真正限制工作量 | 計數與終止條件不完整 | 加入探索預算與 VLD-407；預算耗盡需標示分析不完整並阻擋發布 | 已修正候選源碼標記；邊界測試 NOT_RUN |
| 規則與測試文件本身曾重複 ID／反覆保存相同結論 | 每次迭代另開文件，且沒有唯一結果入口 | 測試案例 ID 清理；歷史檢測、審查結論與修正理由集中到本文件；只保留現行候選 | 現行案例清單為 70 個唯一 TC ID；檔案精簡完成 |

## 3. 歷史實驗：只能支持有限結論

在較早的原型與規則基線上，曾執行 JSON Schema Draft 2020-12 meta-validation、三個精確 fixture 的結構驗證，以及 18 個跨物件原型斷言。結果曾符合當時預期，但它們不代表現行候選已通過；本文件不再保留舊程式與舊規則的多份工作副本。

當前仍保留的歷史判斷只有三項：
1. Schema meta-validation 曾在固定 Schema 0.2.0 基線上 PASS。
2. 舊 18 項斷言曾在舊原型／規則基線上 PASS；必須在現行候選上重跑，不可繼承結果。
3. 原型測試不涵蓋正式發布端到端、UI、Runtime 或使用者任務成效。
