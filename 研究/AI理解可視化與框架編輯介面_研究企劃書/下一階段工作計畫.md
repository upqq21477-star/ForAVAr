# 下一階段工作計畫：有限驗證後轉入介面規劃

> 狀態：PLANNED；尚未執行本文件所列的候選 v0.2 測試。此計畫不是測試結果。

## 目的

完成當前資料契約、跨物件規則與驗證器候選的最小閉環，確保版本/發布閘門與診斷結果可追溯；之後轉入 UI/編輯器需求規格，不再無限擴張驗證項目。

## 依序執行

### 第 1 階段：候選靜態檢查

1. 對集中資料夾中的 validator v0.2.1 執行 Python 語法檢查。
2. 解析規則 JSON、案例清單與 Schema，確認可解析且規則 ID/phase 分配完整。
3. 記錄被測檔案 Git blob SHA、Python 版本、jsonschema 版本與實際命令。

### 第 2 階段：既有斷言回歸

1. 以原本 18 個斷言重跑 validator v0.2.1 與 cross-object rules v0.3.0-draft。
2. 逐項檢查通過/失敗/不適用，不以舊 v0.1 的 PASS 代替新執行。
3. 對 TC-EVID-001 與 TC-EVID-002 分別建立獨立輸入，確認支持與反駁關係條件，不只依賴複合 fixture。

### 第 3 階段：針對新增風險的定向測試

1. 循環搜尋預算耗盡時，確認分析標記為不完整且發布被 VLD-407 阻擋。
2. 不合法模型/欄位缺失時，確認 fail-closed，不發生未捕捉 KeyError 或繼續發布。
3. 驗證已發布版本不可重複發布；只有 proposed 版本可進入發布流程。
4. 驗證 model_revision 與 JSON 精確位元組 SHA-256 一致。
5. 驗證 Markdown 匯出標記與 JSON revision 不一致時被拒絕。
6. 驗證 warning_id、related object IDs、rule_id、severity 與完整 message/循環路徑能被精確保存；測試重複 warning_id。
7. 驗證錯誤 release JSON 根型別、錯誤 warning 欄位型別、錯誤 Schema/registry 根型別、非 UTF-8 Markdown 與日期-only published_at 均 fail-closed。
8. 驗證循環搜尋恰好達到上限但無剩餘邊時不誤判 truncated；超限及長鏈圖不得以未受控 RecursionError 結束。

### 第 4 階段：報告與停止條件

1. 新建一份帶有被測 SHA 的結果報告，不覆寫歷史測試報告。
2. 所有預定案例都必須有 PASS/FAIL/BLOCKED/NOT_RUN 狀態及證據。
3. 若出現失敗，最多進行一輪針對已定位原因的修正，再跑受影響案例與完整回歸一次；未解決項目列為阻擋，不再以重跑取代設計決策。
4. 當發布閘門、revision 綁定、循環上限與診斷格式達到既定條件，停止擴大驗證，進入介面需求規格。

## 之後才開始的介面規劃

依企劃書將 UI 規劃拆成：資訊架構與導覽、樹狀/清單主視圖、選取節點的局部關係圖、屬性編輯與欄位驗證、來源/證據追溯、語意差異檢視、發布前診斷、版本回溯與匯出。先寫可驗收的行為規格與行動裝置版面，再決定實作技術；不得在驗證基線未穩定前把 UI 原型冒充為正式完成。
