# 資料去留與歸檔判定

> 日期：2026-10-27　｜　用途：控制文件數量、避免研究正文重複並保留實驗可追溯性。

## 1. 判定原則

依「是否為唯一權威、是否支援重現、是否記錄重要決策／風險、是否被其他文件引用」判斷去留。精簡正文不等於刪除證據；歷史版本只有在替代文件明確且追溯完整後，才可評估退場。本次沒有刪除實驗、規格或測試證據。

| 文件／資料 | 處置 | 理由 |
|---|---|---|

| 正式資料契約 | 保留 | 欄位、關係、條件、來源、狀態與版本的詳細定義 |
| JSON Schema 0.2.0 | 保留 | 可追溯的結構草案與固定驗證基線 |
| 關係登錄表 0.2.0 | 保留 | 關係型別及語意政策 |
| 跨物件規則 0.3.0-draft | 保留為未驗候選 | 目前驗收對象；不可標成已通過 |
| 歷史規則 0.2.0-draft | 保留於歷史基線 | 重現 v0.1 + 舊規則下 18 項 PASS 的必要材料 |

| 參考資料索引 | 保留 | 外部來源集中管理並記錄適用限制 |

## 4. 不建議現在刪除的內容

- 舊版程式、舊規則、歷史測試報告：刪除會讓版本間的 PASS 無法核對。
- 審查記錄：即使結論已蒸餾進主企劃，仍保留發現時間、反方理由與未解風險。
- fixtures 與 NOT_RUN／BLOCKED 案例：未執行不代表無用，這些是待辦和重現邊界。
- 基線清冊中的來源 SHA 與歷史路徑：供確認工作副本是否偏離來源。
- 未定位的第 7 個負向 fixture 紀錄：保留清單缺口；不可自造檔案或虛構測試結果。

## 5. 未來可評估退場的條件

只有在以下條件全部滿足時才考慮刪除：已有明確替代權威文件；不再是任何測試或結果的唯一證據；歷史可由 Git 歷史或明確歸檔還原；所有引用及基線清冊已更新；刪除前後均完成引用搜尋並在變更紀錄中說明原因。

## 6. 本次結論

本次採取的是**正文去重與摘要化，不做破壞性刪除**。維持一份主企劃、一份詳細資料契約、一份精簡技術決策附件、一份外部來源索引、一份唯一驗收清單及一份交接總覽；規格、實驗、審查與結果仍分層保存。
