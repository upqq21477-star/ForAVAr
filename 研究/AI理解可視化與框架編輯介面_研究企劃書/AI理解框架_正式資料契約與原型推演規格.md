## 摘要

本文件將主企劃的資料模型收斂成可供原型使用的資料契約草案。模型以 JSON 作為正式語意資料格式，以穩定 ID 識別節點、關係、條件及來源，並把結構驗證、跨物件規則、證據與人工審核分開處理。

本版做出五項減少重複的決策：

1. 節點的「結構角色」與「物件類型」是兩個不同維度。
2. 邊只保存一個正式的 `relation_type`；關係家族、循環政策和影響傳播政策由規則登錄表推導，不在每條邊重複存放，避免欄位矛盾。
3. 層級關係只用正式邊表示，不再同時維護 `parent_ids`，避免兩份父子關係來源不一致。
4. 人工審核狀態和證據狀態分開；不適用的欄位可標為 `not_applicable`，不強迫所有物件填滿所有狀態。
5. 模型修訂以 Git commit 或等效的不可混淆修訂 ID 定位；`schema_version` 只代表資料契約版本，不代表內容版本。

本文件不是已驗證的生產規格。正式實作前仍要完成 schema 的 meta-validation、跨陣列參照檢查、狀態轉換規則和測試案例推演。

## 1. 範圍與非目標

### 1.1 本契約負責

- 定義一份 AI 理解模型的必要結構。
- 定義節點、關係、條件和來源的最小欄位。
- 定義可接受的狀態值和關係類型名稱。
- 定義 JSON Schema 與額外確定性規則的責任分工。
- 為語意差異、影響分析、版本管理及後續 AI 取用提供穩定資料基礎。

### 1.2 本契約目前不負責

- 不定義最終 UI 的視覺樣式或全部操作流程。
- 不定義任意自然語言條件的通用執行語言。
- 不保證來源內容或 AI 推論為真。
- 不把模型的內容版本塞進模型本身作自我引用；版本由 Git／版本清單定位。
- 不在第一版引入完整 RDF／OWL、圖資料庫、GraphRAG、事件溯源或即時多人協作。
- 不把程式未執行的驗證案例標為通過。

## 3. 核心資料模型

### 3.1 模型外層

| 欄位 | 必要性 | 規則 |
|---|---|---|
| `schema_version` | 必要 | 本契約草案值為 `0.2.0`；格式變更時更新 |
| `model_id` | 必要 | 同一個長期模型的穩定識別碼，不隨每次修改改名 |
| `title` | 必要 | 人類可讀標題 |
| `purpose` | 選填 | 說明這份模型用於何種目標 |
| `model_state` | 必要 | `draft`、`proposed`、`published`、`superseded`、`archived` |
| `rule_profile` | 必要 | 指向目前使用的關係規則集合，例如 `default-v1` |
| `nodes` | 必要 | 節點清單；可以是空陣列草稿，但正式發布另有門檻 |
| `edges` | 必要 | 關係清單 |
| `conditions` | 必要 | 條件清單 |
| `sources` | 必要 | 來源紀錄清單 |
| `attributes` | 選填 | 領域擴充資料；不得重複正式欄位 |

**版本原則：** `model_id` 識別一份長期模型；Git commit 或等效修訂 ID 識別某一時點的完整內容；`schema_version` 識別資料契約版本。三者不能混用。

### 3.2 節點

必要欄位：

- `id`：穩定 ID。改名不換 ID；兩個同名物件不能因此自動合併。
- `name`：人類可讀名稱。
- `function`：一句話說明作用。
- `structural_role`：`core`、`main_axis`、`skeleton`、`module`、`detail` 或 `unassigned`。
- `entity_kind`：`goal`、`requirement`、`capability`、`function`、`concept`、`condition`、`decision`、`claim`、`process`、`data_object` 或 `custom`。
- `review_status`：目前人工審核狀態。
- `provenance_refs`：來源 ID 清單；草稿可為空，但關鍵內容在發布前必須符合來源政策。

視情境使用的欄位：

- `claim_kind`：使用者陳述、使用者需求、設計決策、外部事實主張、模型推論、假說、開放問題、觀察或其他。
- `evidence_status`：不適用、未核實、有支持、證據不足、有反證或混合證據。
- `condition_refs`：參照啟動、完成、失敗、取消或守衛條件。
- `attributes`：額外領域資料。
- `description`：更完整的說明。

若 `entity_kind=custom`，必須提供 `custom_kind`。若 `claim_kind=external_fact_claim`，必須提供非 `not_applicable` 的 `evidence_status`。

### 3.3 關係

每條邊只保存以下主要語意：

- `id`：穩定關係 ID。
- `source_id`、`target_id`：起點與終點節點 ID。
- `relation_type`：具體關係類型。
- `review_status`：人工審核狀態。
- `provenance_refs`：來源紀錄 ID 清單。

可選欄位包括 `description`、`evidence_status`、`condition_refs` 和 `attributes`。

**不得在每條邊重複保存 `relation_family`、`cycle_policy` 或 `impact_policy`。** 這些資料由 `rule_profile + relation_type` 查找。若日後確實需要個別關係例外，必須增加明確、受控且可審核的 override 機制，不可隨意覆寫全域規則。

另新增 `refutes` 作為有向反證關係：來源端是帶有來源引用的證據命題節點，目標端是被檢視的主張節點。`is_evidence_for` 表示來源端命題被提出作為目標主張的支持性證據。兩者都不會自動改寫目標節點的 `evidence_status`；整體證據狀態仍需依來源內容、適用條件與反證，由驗證規則及人工審核作出判定。

層級關係也只由 `contains` 邊表達；第一版不另設 `parent_ids`。這可以避免節點欄位和邊清單保存兩套互相衝突的父子資訊。

### 3.4 條件

條件分成五種用途：

- `start_condition`
- `completion_condition`
- `failure_condition`
- `cancel_condition`
- `guard_condition`

每項條件需具備 ID、用途、自然語言描述、`evaluation_mode`、審核狀態和來源引用。

`evaluation_mode=descriptive` 代表只供人理解，不承諾可執行。  
`evaluation_mode=machine_evaluable` 必須有 `expression` 和 `expression_language`，但在正式選定語法前，不應聲稱系統能執行任意表達式。

### 3.5 來源

來源紀錄至少保存：

- ID；
- 來源類型：使用者輸入、外部來源、專案檔案、工具輸出、模型推論、規則推導、計算或其他；
- 人類可讀標籤；
- 擷取時間。

URI、原始位置、短摘錄、操作者類型及擴充屬性可依來源類型選填。若來源是 AI 推論，來源紀錄應說明推論依據或方法摘要，不應把模型內部隱藏推理逐字存成所謂證據。

### 3.5.1 來源、證據命題與目標主張的分工

只把來源 ID 放進 `provenance_refs`，表示內容可追溯到該來源；它本身不表示該來源支持、反駁或僅提供背景。當「某來源到底支持哪個主張」有獨立語意時，v1 使用現有圖模型而不新增另一套頂層關係表：

1. 建立一個證據命題節點（通常為 `entity_kind=claim`，`claim_kind=observation` 或適用的命題類型）。
2. 在證據命題節點的 `provenance_refs` 中引用精確來源紀錄；應盡可能填入 `locator` 或可定位的 `excerpt`。
3. 用 `is_evidence_for` 將支持性證據命題連到目標主張；用有向 `refutes` 將反證命題連到目標主張。
4. 目標主張的 `evidence_status` 是整體評估摘要；連線新增、來源數量增加或人工接受某條邊，都不能單獨自動改寫摘要狀態。

泛用的 `supports` 保留給理由／設計依據；不能僅憑 `supports` 就聲稱有外部證據。反證也不能只靠一條無方向的 `conflicts_with` 來代替，因為「兩個物件衝突」與「此項證據反駁該主張」是不同語意。

### 3.6 人類審核與證據評估

這兩種狀態是不同軸線：

| 狀態欄位 | 值 | 意義 |
|---|---|---|
| `review_status` | `pending_review` | 尚未檢視 |
| | `accepted` | 人類接受此項作為目前工作模型的一部分 |
| | `rejected` | 人類否決 |
| | `disputed` | 存在未解決爭議 |
| | `needs_reconfirmation` | 相關內容變更後，既有接受可能不再適用 |
| `evidence_status` | `not_applicable` | 不適用於證據評估 |
| | `unverified` | 尚未核實 |
| | `supported` | 有支持證據 |
| | `insufficient` | 證據不足 |
| | `contradicted` | 有反證或被反駁 |
| | `mixed` | 證據相互混合或結論不確定 |

「未修改」不會自動變成 `accepted`；來源存在不代表內容已被證實；使用者接受設計決策不代表外部事實已被科學證實。

目前欄位保存的是最新狀態，狀態歷史可先由 Git 記錄保留。若後續正式產品需要逐項審核者、時間、理由和覆核軌跡，應另設審核事件紀錄，不把完整審核歷史硬塞進單一節點物件。

靜態一致性檢查已比較 Schema 的 17 個 relation_type 與 registry 的 17 個 key，確認集合完全一致且每類關係都有必要規則欄位。Draft 2020-12 meta-schema 已另行驗證通過。完整記錄與基線 SHA 收錄於 [原型推演案例清單第 2.1–2.2 節](./驗證/案例清單_原型推演_v0.2.md)。這不代表完整的跨物件規則、發布流程、Runtime 或使用者任務已驗收。

## 4. 關係規則登錄表原則

完整規則位於 `relation-rules.default-v1.json`。本文件摘要如下。

| 關係類型 | 核心語意 | 循環原則 | 修改影響方向（初稿） |
|---|---|---|---|
| `contains` | 起點包含終點 | 禁止循環 | 雙向直接檢視 |
| `depends_on` | 起點依賴終點 | 禁止循環 | 被依賴項改變時，反向檢查依賴者 |
| `precedes` | 起點先於終點 | 禁止循環 | 先後兩端直接檢視 |
| `causes`／`influences` | 因果／影響主張 | 允許循環 | 提醒式，不等同依賴失效 |
| `triggers` | 起點觸發終點 | 預設警告 | 起點改變時直接檢查終點 |
| `transfers_data_to` | 起點將資料送至終點 | 預設警告 | 兩端直接檢視 |
| `conflicts_with` | 兩者在特定規則下衝突 | 允許循環 | 雙向直接檢視 |
| `supersedes` | 起點取代終點 | 禁止循環 | 兩端直接檢視 |
| `explains` | 起點用以解釋終點 | 允許循環 | 提醒式 |
| `supports` | 起點支援終點 | 允許循環 | 支援內容改變時檢查被支援項 |
| `implements` | 起點實作終點 | 允許循環 | 目標需求變更時檢查實作 |
| `derived_from` | 起點由終點衍生 | 禁止循環 | 來源改變時檢查衍生項 |
| `satisfies` | 起點滿足終點要求 | 允許循環 | 兩端直接檢視 |
| `verified_by` | 起點由終點驗證 | 允許循環 | 兩端直接檢視 |
| `is_evidence_for` | 起點作為終點的證據 | 允許循環 | 證據或主張改變時直接檢視 |

這些是可供原型推演的預設政策，不是任何領域的普遍法則。真正採用前，要透過測試案例檢查方向是否符合使用者任務。如果某種領域的回饋流程合理地存在循環，就不能直接使用「全圖必須是 DAG」的規則。

### 4.1 規則登錄表的必要欄位

每個關係類型至少需定義：家族、語意、方向／對稱性、循環政策、起點變更影響、終點變更影響及條件需求。規則需有版本；不允許缺少規則時默默採用猜測。

### 4.2 影響分析的操作定義

- `forward_direct`：直接檢視關係目標。
- `reverse_direct`：直接檢視關係來源。
- `reverse_transitive`：沿反向依賴關係找出所有下游依賴者。
- `both_direct`：直接檢視關係兩端。
- `forward_advisory`／`reverse_advisory`：提供警示，不自動宣告下游失效。
- `none`：不依此關係傳播影響。

若同一物件由多條路徑抵達，只列一次結果，保留至少一條可解釋路徑及觸發政策。第一版若無法計算可靠影響，應標明未知或需要檢視，不得假稱沒有影響。

## 5. 分層驗證與發布門檻

### 5.1 驗證層次

| 層次 | 檢查內容 | 工具／方法 | 失敗處理 |
|---|---|---|---|
| L0 | JSON 語法 | 標準 JSON parser | 不接受載入 |
| L1 | 欄位、型別、列舉、條件欄位 | JSON Schema 2020-12 | 阻擋不符合契約的資料 |
| L2 | ID 唯一、所有引用存在、不得自我連線等 | 自訂確定性檢查 | 結構錯誤或警告 |
| L3 | 關係端點與循環政策、條件需求、影響規則 | 規則登錄表＋圖演算法 | 按規則嚴重性處理 |
| L4 | 來源是否支持命題、是否矛盾或過度主張 | 來源查核、規則和人工檢視 | 標記證據狀態，不可由 AI 自動定真偽 |
| L5 | 是否符合正式發布門檻 | 發布規則 | 留在草稿／提案狀態，說明缺失 |

JSON Schema 不負責跨陣列的 ID 唯一性或節點引用是否存在；這些需要 L2 自訂驗證。Schema 中的 `format: uri` 或 `format: date-time` 也要看驗證器設定，不能假設所有執行環境都會把 format 當成阻斷式驗證。

### 5.2 發布前最低條件

1. JSON Schema 驗證通過。
2. 節點及邊 ID 不重複，所有來源和條件引用存在。
3. 不存在禁止的自我連線或違規循環。
4. 所有使用中的關係類型在選定的 `rule_profile` 有明確規則。
5. 核心目標及重要限制有來源或清楚的使用者需求／設計決策標記。
6. 未核實或矛盾的事實主張沒有被呈現成已證實事實。
7. 核心與必要決策已被明確接受，或這份版本仍標記為草稿。
8. Markdown 與 JSON 輸出指向同一個模型修訂。
9. 已有變更摘要與可回復版本。

發布門檻不是要求所有草稿都完整；未知內容可以留在草稿，正式發布必須明確顯示其未解決狀態。

## 6. 版本與變更契約

### 6.1 版本識別

- `model_id`：同一長期模型的穩定 ID。
- `schema_version`：資料格式契約版本。
- Git commit SHA 或等效修訂 ID：某一份實際內容的唯一修訂基準。
- `model_state`：該份模型目前處於草稿、提案、發布或歷史狀態。

不把 Git commit SHA 寫回它自己所描述的同一份檔案，避免自我引用。版本清單或產出報告可以記錄所用 commit SHA。

### 6.2 語意差異

差異演算法依穩定 ID 比較：

- 新增節點／邊／條件／來源；
- 刪除節點／邊／條件／來源；
- 已存在物件的語意欄位改變；
- 關係起點、終點或類型變更；
- 審核狀態與證據狀態改變；
- 視圖版面變更（若版面有獨立檔案，則另行比較）。

移動節點不是語意變更；同名節點但 ID 不同不能自動視為同一物件；改名且 ID 不變則應視為同一物件的欄位修改。

### 6.3 三方合併

比較共同基準、使用者版本及 AI 提案。非重疊且無語意依賴的修改可提出自動合併候選；同一欄位衝突、刪除與修改衝突、關係方向互斥或條件邏輯衝突，必須明確裁決。所有合併候選都要重新通過 L0–L3 驗證。
