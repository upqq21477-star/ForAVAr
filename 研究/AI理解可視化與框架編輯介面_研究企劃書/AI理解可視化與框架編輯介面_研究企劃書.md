## 摘要

本企劃研究一套建立在既有 AI 認知架構之上的**人類理解與操作延伸層**：把 AI 對需求、限制、假設、關係和未知的理解，轉成可視化、可修改、可追溯、可比較且可供後續工作使用的結構。圖形認知層可以有獨立的視覺語法、圖形模型、引導式操作及固定的人類任務流程，用來降低理解與使用門檻；它不是與既有機器認知核心競爭的第二套推理核心，也不要求 AI 的所有任務都走同一條固定推理路徑。圖形層與底層認知核心透過明確的資料契約、版本和變更回饋接口連接。

現階段已建立資料契約草案、JSON Schema、關係規則、跨物件驗證規則、狀態機、70 項測試案例、8 個 fixtures 及驗證器原型。Schema 0.2.0 的 Draft 2020-12 meta-validation 與舊基線的有限原型測試已有歷史證據；候選驗證器 v0.2.1 與跨物件規則 0.3.0 尚未實際執行。2026-10-27 的 7 項靜態前置檢查全數通過，但 Python 語法、CLI、回歸與定向測試受環境限制而 BLOCKED。**停止條件尚未達成，因此不能將 UI 正式需求規劃、正式實作或使用者驗收標為開始或通過；研究路線圖與結案條件的整理不等於啟動 UI 實作。**

建議起始技術組合為 JSON 正式資料、Git 版本快照、JSON Schema 結構驗證、自訂確定性跨物件規則，以及以穩定 ID 為基礎的語意差異。先解決資料正確性、來源／證據、版本與發布閉環，再考慮圖形套件、資料庫或檢索架構；GraphRAG、圖資料庫、即時多人協作與事件溯源均非第一階段必要依賴。

## 1. 目的、問題與成功條件

### 1.1 要解決的問題

自然語言需求往往混合目標、限制、假設、條件、依賴及未確認內容。單純摘要不容易呈現它們的結構；單純畫圖則容易出現線條含義不清、來源消失、版本不同步及已確認內容被靜默覆寫等問題。若後續 AI 只取得畫面或不明確的摘要，也可能使用錯誤版本。

### 1.2 研究目標

- 讓人能看出 AI 對需求的理解、未知事項、來源與未解衝突。
- 讓人直接修正語意內容，且修改能回寫同一份正式模型。
- 讓每一重要內容可追溯來源、人工審核狀態、證據狀態與版本。
- 能輸出完整模型及相對明確基準的差異，並揭露衝突與下游影響。
- 在行動裝置及低成本環境下仍可理解、校正與匯出。

### 1.3 成功條件

成功不是「畫面可顯示」，而是核心模型可解析、引用完整、規則可判定、未確認內容不被誤標為已接受、差異可重現、發布版本與輸出內容一致，且使用者能完成預先定義的建模／修正／確認／匯出任務。這些條件仍需實際驗收，不可由規格文件存在推定已達成。

## 2. 核心設計決策

1. **單一真相來源：** 正式語意模型只保存一份；樹狀、清單、關係圖、流程和差異畫面都是同一份資料的視圖。
2. **資料與版面分離：** 節點語意、關係、條件、來源、審核和版本屬正式資料；座標、縮放、折疊與視覺設定不得成為第二份語意真相。
3. **結構角色與物件類型分離：** 「核心／主軸／骨架」是結構角色；「目標／需求／功能／條件」是物件類型，兩者是不同欄位維度。
4. **關係規則集中管理：** 每條邊只保存正式的 `relation_type` 與必要端點／條件引用；關係家族、循環政策、影響傳播政策由關係規則登錄表查得，避免重複欄位互相矛盾。
5. **層級以正式關係表示：** 不再另維護重複的 `parent_ids`，避免父子關係與邊資料不一致。
6. **狀態不混用：** 人工審核狀態、證據狀態與模型生命週期狀態獨立。來源存在不代表來源支持主張；使用者接受不代表外部事實已被證實；Schema 通過也不代表可發布。
7. **支持與反證保持方向：** `is_evidence_for` 與 `refutes` 描述證據命題和主張的關係，不能單靠一條邊自動改寫 `evidence_status`。
8. **版本綁定與可追溯：** 差異必須指定基準版本；內容修訂 ID 不等於 Schema 版本。發布、匯出及後續 AI 取用必須明確對應同一修訂。
9. **保守 fail-closed：** 關鍵欄位、引用、版本身分或發布檢查無法判定時，拒絕發布並輸出可定位診斷，不以猜測補齊。
10. **增量審查而非無限重審：** 影響分析用來找出需要重看之物件，不代表下游內容已被證明失效；只有新證據、明確缺陷、規格變更或驗收失敗才重開已結案工作。

### 2.1 圖形認知層與固定互動流程的定位

本企劃正式採用「**獨立的人類互動與圖形認知延伸層**」作為設計定位。這一層可以自行設計圖形結構、資訊分層、操作狀態機、使用者任務流程、教學／引導步驟、錯誤回復與人類確認方式。這些是原有認知架構的使用者側延伸與優化，不應因為它們具有自己的結構或流程，就被誤判為核心偏移。

必須分清兩種流程：
- **人類操作流程：** 可以是明確、固定、可學習的流程，例如檢視理解、標記未知、修改關係、查看影響、驗證、確認版本、回傳或復原。其目的在於讓使用者容易理解、操作與互動。
- **AI 認知流程：** 仍由既有認知核心依任務、風險、證據及資源選擇合適路徑；介面不強迫所有機器任務採同一固定步驟，也不取代既有核心的推理、驗證和自我修正責任。

圖形層可以保有適合編輯和展示的獨立表示模型，但必須有可檢查的映射契約，把有語意意義的使用者修改轉為有版本、有來源、有驗證結果的正式變更，再回饋給既有認知核心。版面座標、縮放、折疊等純展示狀態可獨立保存；會改變目標、限制、節點語意、關係或確認狀態的內容，不得只停留在畫面狀態中。

因此，成功條件不只是資料格式有效或圖能畫出來，也要驗證人類是否更容易理解 AI 的現有模型、能否準確修正錯誤、是否知道哪些內容未確認、能否安全完成版本確認與復原，以及修改是否確實影響後續工作。以上人因效益在實測前仍屬待驗假說。

## 3. 建議架構與資料流程

### 3.1 邏輯分層

| 層 | 責任 | 最低要求 |
|---|---|---|
| L0 輸入解析 | JSON／Markdown 輸入與基本型別 | 可解析；錯誤有明確位置 |
| L1 結構驗證 | JSON Schema | 必填欄位、型別、列舉與結構符合契約 |
| L2 引用完整性 | 全域 ID、端點、來源與條件引用 | 唯一 ID；引用存在且類型正確 |
| L3 關係及圖規則 | 重複關係、自我連線、循環政策、關係端點 | 依關係登錄表判定，不用一條全圖規則取代所有語意 |
| L4 來源、證據與人工審核 | 來源可追溯、支持／反證、未確認內容 | 不由來源數量或關係數量自動判真 |
| L5 版本與發布 | 修訂綁定、警告確認、發布條件及匯出 | 任一必要檢查未通過即阻擋發布 |

以上是責任分層，並不代表六層已完成實作或均已自動化。實際程式覆蓋率以測試結果為準。

### 3.2 建議資料流

1. AI 根據使用者需求建立候選模型，並標示來源、假設及未知。
2. 驗證器先檢查結構、ID、引用、關係與發布規則。
3. 人類檢視並修改模型；修改過的已接受內容需重新確認。
4. 系統按固定基準產生語意差異，標出新增、刪除、修改、狀態變更、衝突及影響路徑。
5. 發布前再次驗證，保存所需警告的確認紀錄並綁定確切修訂。
6. 匯出正式 JSON 與可閱讀 Markdown；下游 AI 只能使用明確指定且可追溯的已發布版本。

## 4. 視圖及操作原則

UI 尚未進入正式需求規格階段。通過驗收閘門後，才將以下內容轉換成可測試的行為需求：

- **樹狀／清單視圖：** 瀏覽層級、快速尋找、排序與篩選。
- **局部關係視圖：** 只顯示所選節點附近的依賴、條件與影響，避免一次展示整張密集圖。
- **屬性與來源面板：** 編輯欄位、查看出處、審核狀態、證據狀態及未決問題。
- **差異／衝突視圖：** 以固定基準比較兩個版本或三方變更；避免只顯示原始 JSON Patch。
- **驗證／發布面板：** 明確區分錯誤、警告、需人工確認及已通過項目。
- **手機優先：** 避免把精準拖曳當成唯一操作；提供清單選取、表單編輯、復原及可讀的局部圖。
- **匯出／回復：** 保留正式 JSON、Markdown、基準修訂、差異及必要審核紀錄。

不可將原型畫面、設計稿或靜態圖示當成 UI 已實作或可用性的證據。

## 6. 風險、缺口與限制

1. **候選程式尚未執行：** 最重要阻擋。靜態檢查只能說明來源檔案具備某些標記，不能證明語法或執行行為正確。
2. **第 7 個負向 fixture 未定位：** 不造檔、不推測測試結果；先核對舊紀錄，無法定位則記錄為清單差異。
3. **狀態機與發布門檻仍是草案：** 需透過候選驗證器與測試案例確認。
4. **影響分析及差異演算法未實測：** 尚無證據支持特定效率或準確率數值。
5. **UI／Runtime／使用者研究未開始：** 不能推斷介面提升了 AI 理解或使用者效率。
6. **外部來源的適用範圍有限：** 標準與論文支持的是各自的技術／研究主張，不能代替本專案成效評估。

## 7. 續作順序與停止條件

### 7.1 當前唯一主線

先以可取得集中資料夾固定檔案的同一 Python 環境，執行[下一輪有限驗收計畫](./下一輪有限驗收計畫.md)。不得用靜態閱讀替代程式測試，也不得用舊版測試結果替新版背書。

### 7.2 必做驗收項

- 對驗證器 v0.2.1 執行語法檢查與 `--check-schema`。
- 用規則 0.3.0-draft 重跑舊 18 項斷言，逐項記錄預期與實際結果。
- 分別測試 `is_evidence_for` 與 `refutes`。
- 測試循環搜尋上限、無環稠密圖與長鏈邊界。
- 測試缺欄位／錯誤輸入時 fail-closed、發布版本不可重複發布。
- 測試 JSON 修訂 SHA-256、Markdown revision marker 及 warning 診斷內容。
- 記錄環境、命令、實際輸出、工具版本、檔案 SHA 及所有 BLOCKED／NOT_RUN 項。

### 7.3 停止條件與 UI 閘門

所有規劃案例都必須有明確狀態與可定位證據。若有失敗，最多進行一輪針對性修正，然後完整回歸一次；仍有失敗或環境阻擋就停止，記錄架構決策，不無限重測。**只有候選驗收所列停止條件全部達成，才可開始 UI／編輯器需求規格；這仍不等於正式產品完成。**

下一階段的有限驗收、UI 需求、互動原型、核心接口、閉環模擬及使用者評估均納入[唯一續作與閉環計畫](./下一輪有限驗收計畫.md)。現階段仍先處理候選程式驗收；候選未通過前不得提前啟動 UI 正式實作。研究規格與路線圖可以先定稿，但不等於執行證據已完成。
