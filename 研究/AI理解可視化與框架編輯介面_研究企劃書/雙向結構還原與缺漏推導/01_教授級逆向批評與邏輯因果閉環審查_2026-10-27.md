## 摘要

**總判定：研究方向合理，但目前尚不能判定邏輯鏈與因果鏈已閉環。** 「逆向還原＋正向缺漏推導」可共用一份有型別、可追溯的結構模型；以明確目標、來源與獨立評估器限制候選生成，也比單純要求模型「自行完整思考」更可檢查。然而，現有企劃仍把幾種不同層次的閉環放在一起討論：資料結構可解析、需求追溯完整、推論有足夠證據、因果主張成立，以及發布流程正確，彼此不是同一個性質。

本次靜態逆向審查找到四個核心級缺口：

1. **必要性定義不夠嚴格。** 「使用者明確要求」「規格規定」「在目前方案中不可缺少」和「在所有符合目標的替代方案中都不可缺少」是不同判斷。現行研究分類仍可能把「有需求或約束依據」直接叫作「已確認必要」，但這只能證明有要求或有條件依據，不能自動證明不存在替代方案。
2. **沒有可判定的最低語意閉合門檻。** 現行 Schema 允許空的 nodes／edges／conditions／sources 陣列；候選發布流程沒有明確規則要求模型至少包含目標、範圍、關鍵需求與驗收路徑。因此，依目前 schema 與程式分支可推得，一份形式上合法但語意為空的模型可能進入發布流程。這是靜態推演結果，尚未動態執行。
3. **因果關係的證據要求沒有落到驗證器。** 關係登錄表對 causes／influences 指出，當它們被當成事實時需要主張與證據狀態；但現行候選驗證器主要檢查節點上的 claim_kind／provenance_refs，沒有對這兩類邊實施同等的必要條件檢查。因果線可以是研究假說，但不能僅因為邊合法、審核狀態 accepted，就被當成已成立的因果鏈。
4. **來源追溯未等同推導可重現。** 目前 VLD-302 對節點推論／假說的實作主要檢查 provenance_refs 是否為空；而 source 物件的 URI、locator、excerpt 等欄位可選。只要引用了一個只有標籤與擷取時間的來源紀錄，就可能通過「存在來源引用」檢查，卻仍無法重建推導的輸入、規則、來源版本或轉換過程。

此外，循環探索上限、Markdown／JSON 版本一致性、警告保留、自由擴充 attributes 的欄位衝突、人工審核規則的觸發契約，以及需求／實作／驗收追溯是否真正閉合，都需要補強。

**結論不是推翻整套架構，而是將其定位為「方向正確的候選研究架構，尚未形成可證明閉合的操作契約」。** 應先修正必要性語意、最低發布完整性、因果邊治理、可重現來源與反例測試，再判斷是否有理由擴大演算法或增加新元件；不應先做更多大範圍研究或 UI。

## 1. 審查範圍與判定準則

### 1.1 審查對象

本次檢查：
- 雙向研究企劃 v1.0 的目標、術語、候選分類、證據鏈與實驗設計。
- 現行主企劃、資料契約、Schema、關係規則及跨物件規則的相容性。
- 候選驗證器中與來源、因果關係、循環、發布和輸出版本綁定有關的程式路徑。
- 外部研究是否支持現有方法論，以及這些外部結果能否合理外推到本專案。

本次不修改正式 Schema、關係登錄表、跨物件規則或驗證器；本文件是逆向批評紀錄，不等於正式企劃更新。

### 1.2 嚴重度定義

| 等級 | 定義 |
|---|---|
| **S 級** | 會使核心結論失去判定基礎：例如把假說當成必要、可發布語意空模型、把未受證據約束的因果邊當成有效閉環，或無法重現關鍵推導來源。未處理前，不應宣稱架構邏輯閉合。 |
| **A 級** | 在可合理預見的輸入下會造成錯誤阻擋、漏檢、證據遺失或審核無法落實；需在擴大研究／整合前處理。 |
| **B 級** | 規格或研究設計仍有模糊，但可在小範圍試驗中逐步釐清；不能因此聲稱已驗證。 |

### 1.3 本次所稱的「閉環」

閉環必須限定範圍。至少分為：

- **資料閉環：** 輸入、版本、來源與輸出可定位，重要內容不會在轉換中失去依據。
- **邏輯閉環：** 目標、前提、規則、候選結論和驗收條件之間沒有未揭露的跳躍。
- **需求閉環：** 已確認目標及需求有下游承接、驗收方法及結果；無法驗收的要求有明確處理方式。
- **證據閉環：** 每個重要外部主張能追至精確來源、相關位置與適用性判斷；證據不足時不升格。
- **因果閉環：** 因果主張不只存在圖路徑，還需條件、機制、觀測或適當的反事實／介入依據；未證成者保持假說。
- **發布閉環：** 被驗證的模型、Markdown、規則版本、警告及審核決策對應同一不可變修訂。

以上性質不可互相替代。Schema 通過不等於需求完整；圖連通不等於因果成立；來源存在不等於來源支持主張；測試案例已定義不等於測試已通過。

## 2. 總體裁決：合理性不等於閉環

### 2.1 合理的部分

目前方向有四項值得保留的設計：

1. 逆向結構還原與正向缺漏推導共用結構資料，避免平行資料模型。
2. 把結構角色、物件類型、人工審核、證據評估及模型生命週期分開，避免一個狀態欄位承擔多種語意。
3. 對可程式化的結構規則使用獨立驗證器，而不是只靠生成模型自行宣告正確。
4. 承認低秩、網路補全、Hankel 與 MDL 都有條件，沒有宣稱通用反演、固定精度或固定加速倍數。

這些是合理的架構原則，但還不是成效證據。

### 2.2 目前不能成立的主張

目前不能宣稱：
- 雙向推理能找出所有必要缺口；
- 六種閉合視角足以證明一般系統完整；
- 「反事實移除後模型失敗」已證明某元件在所有替代方案中不可缺少；
- 每個候選的來源引用足以重現其推導；
- 現行發布驗證能阻止所有不完整或自相矛盾模型；
- 每一條因果邊都通過了因果驗證；
- 目前的圖模型已執行變更影響分析；
- 任何一個 PASS 可跨版本轉移，或可由靜態檢查替代程式執行。

這些不是小型文件修飾，而是必須被明確限制的推論範圍。

## 3. 邏輯鏈與因果鏈逐段檢查

### 3.1 從任務到發布的主邏輯鏈

| 階段 | 應成立的關係 | 現況 | 判定 |
|---|---|---|---|
| 1. 任務／邊界 | 目標、非目標、操作環境、假設和限制被明確記錄 | 研究文字有要求；正式模型沒有發布前必須存在的最小目標／範圍門檻 | **部分成立** |
| 2. 來源盤點 | 輸入材料有不可混淆的版本、位置、來源類型及可重現定位 | source URI、locator、excerpt 可缺省；沒有必填的內容摘要雜湊或來源 revision 欄位 | **不閉合** |
| 3. 結構萃取 | 每項被萃取的元件／關係可追溯至來源與擷取依據 | provenance_refs 存在，但沒有強制來源定位和擷取器版本 | **部分成立** |
| 4. 缺漏推導 | 每個候選對應目標／約束、推導規則、假設和反例 | 有研究方法與候選分類，但沒有可驗證的正式推導紀錄契約 | **不閉合** |
| 5. 必要性判定 | 區分明確要求、條件必要、方案依賴及可替代設計 | 目前的「已確認必要」可能把不同判定合併 | **不閉合** |
| 6. 模型建構 | 候選對應正式欄位與語意一致的關係 | 共用 JSON／關係登錄表的方向正確 | **原則成立，規則仍待驗收** |
| 7. 獨立驗證 | 驗證器檢查所有聲稱可機械判定的規則 | 已有多層規則候選，但因果邊、最小語意完整性、部分警告保留等仍有缺口 | **不閉合** |
| 8. 人工審核 | 無法機械判定的項目有具體觸發、責任人、決策紀錄及退回路徑 | 有人工審核概念；VLD-303 的可觀察觸發與工作紀錄格式不完整 | **部分成立** |
| 9. 發布／匯出 | JSON、Markdown、規則版本、警告與決策對應同一實際內容 | Markdown 檢查主要比對宣告的 revision marker，不驗證 Markdown 內容確由該 JSON 確定性產生 | **存在可繞過的語意缺口** |
| 10. 下游 AI 使用 | 下游取得正確版本、未決項、警告和證據狀態 | 主企劃有使用契約方向；對非循環類警告的保存／傳遞驗證不完整 | **部分成立** |
| 11. 實際結果回饋 | 實際錯誤與驗收結果能更新模型且保留因果紀錄 | 有候選驗收計畫；現行候選程式仍 BLOCKED／NOT_RUN，使用者任務尚未驗收 | **尚未成立** |

**總結：** 目前鏈條在「概念上有各階段」這個層次成立；在「每個階段都有明確輸入／輸出、可判定條件、可重現結果，且失敗會被攔下」這個層次尚未閉合。

### 3.2 為何關係圖連通還不夠

一份模型即使所有節點都有邊，仍可能缺少目標、假設、反例或驗收。反過來，一個尚未有下游實作的需求節點，也可能是刻意保留的草案，不應被錯誤地判定為無效。

所以不能只用「孤立節點數」「所有核心都有來源」或「所有引用均存在」當作完整性證明。需要以已確認目標為起點的、分層的閉合規則；而這些規則必須容許明確的草稿／未知狀態，不能把不完整草案與錯誤發布模型混為一談。

## 4. S 級核心缺口

### S-01｜「必要性」有四種語意，現行分類可能混為一談

**問題：** 研究企劃把有明確需求／約束來源的候選放入「已確認必要」。然而，下列命題不同：

1. **使用者明確要求：** 這是約定或要求，無論是否存在替代方案，都必須尊重需求治理規則。
2. **法規／外部標準要求：** 在特定適用範圍下必須滿足。
3. **相對於目前方案的必要條件：** 在本次選定的結構裡，沒有此元件就無法滿足某條件。
4. **相對於所有合規替代方案的邏輯必要條件：** 任何滿足固定目標與假設的有效方案都不能省略此能力。

第一類不是對邏輯必要性的證明；第三類也不能直接推成第四類。

**反例：** 目標是「在手機上保存使用者確認的框架」。若需求草案指定「使用 SQLite」，可以將其記錄為明確指定的技術要求；但在一般產品目標下，SQLite 未必是邏輯上不可替代，其他儲存方式可能同樣滿足目標。若引擎把這項要求直接分類為「邏輯必要」，就會誤把需求治理與架構證明混為一談。

**裁決：S 級。** 在定義必要性類別之前，不應以「已確認必要」作為單一結果。未來至少要分開「使用者／政策明確要求」「正式約束要求」「在指定方案下必要」「在已列明假設下可證明必要」「偏好／可選」「未知」。其中「可證明必要」必須同時記錄前提、候選替代集合與證明方法；找不到所有替代方案時，應降低結論強度。

### S-02｜候選發布規則缺少最低語意完整性門檻

**可定位依據：** [Schema](../規格草案/ai-understanding-model.schema.json) 的 nodes、edges、conditions、sources 是陣列；沒有以最低元素數或跨物件規則要求至少存在目標／範圍／需求／驗收連結。候選驗證器的發布流程主要檢查 schema、引用、圖循環、審核狀態、核心節點來源、版本與警告。

**反例推演：** 若模型有合法的 model_id、title、model_state=proposed、rule_profile，且四個陣列均為空，Schema 層本身沒有禁止它。發布流程亦沒有明確的「至少有一個已確認目標或需求」規則。只要外部 release record 和 Markdown marker 具備其所要求的值，程式路徑便沒有一條明確的語意最小規模規則會拒絕空模型。

此處是依 schema／程式分支推導的**靜態反例**，不是已執行的端到端重演。

**裁決：S 級。** 不是簡單地把所有陣列設為非空即可，因為合法草稿可能只有目標，或暫時沒有邊。應在發布層定義「模型最低語意契約」，例如：本版本聲稱要交付的目標範圍必須明確；每個已確認需求都要有適用的承接／明確豁免；每個需要驗收的要求要有可核對驗收路徑；沒有要求連結的項目須被標為未決或被排除。這些條件需要按模型用途而定，不能用固定節點數代替。

### S-03｜因果關係目前沒有完整的證據閘門

**可定位依據：** [關係規則](../規格草案/relation-rules.default-v1.json) 對 causes／influences 註明，若作為事實主張需有 claim 與 evidence status；但 [候選驗證器](../實驗/validator_prototype.py) 的 VLD-302 主要檢查節點的 claim_kind 與 provenance_refs，VLD-206 只對 is_evidence_for／refutes 有來源命題及目標主張的端點規則。沒有對每條被當作事實的 causes／influences 邊實施同等條件要求。

**反例推演：** 兩個普通節點之間建立 causes 邊，edge 的 review_status=accepted、provenance_refs=[]，沒有可定位來源，也沒有明確標示為假說。按目前已讀到的檢查路徑，VLD-302 不會因這條邊而發出節點層警告；發布閘門亦沒有一般性的「因果邊必須有證據狀態／假說狀態」檢查。實際是否整體可發布仍受其他條件影響，但因果邊自身缺少完整治理。

**裁決：S 級。** causes／influences 應只能表示「已被標記的因果主張」，不能因圖上連線就認定因果成立。至少要清楚區分已驗證因果主張、待驗因果假說與僅表示相關／影響的關係；已驗證主張需有來源、適用條件和驗證依據，假說則在匯出及下游取用時必須保持假說身分。不能以一般的 review_status=accepted 取代因果證據判定。

### S-04｜「有來源 ID」不等於能重建推導

**可定位依據：**
- Schema 的 source 必填欄位主要為 id、source_type、label、captured_at；URI、locator、excerpt 都是可選。
- VLD-302 的候選實作主要判斷節點的 provenance_refs 是否為空，沒有判斷引用來源是否含可重現位置、版本、內容摘要或精確支持片段。
- 研究企劃要求保留推導依據，但尚未定義完整的推導活動紀錄契約。

**反例：** 一項核心節點引用來源 SRC-01；該來源只有 label 與 captured_at，沒有 URI、commit、內容雜湊或可定位 excerpt。從結構看它「有來源」，但後續接手者無法確定原始材料是哪個版本，也無法確認此來源是否支持主張。對模型推論而言，只有一個 source_type=model_inference 的來源紀錄，仍不等於保留了該推論使用哪些輸入、依據哪個規則或哪個模型版本。

**裁決：S 級。** 必須區分來源存在、來源可定位、來源版本固定、來源支持主張與推導可重現這幾個層次。無需儲存隱藏思維鏈；但應能保存簡潔、可稽核的推導紀錄，例如輸入物件 ID 與 revision、來源定位／雜湊、規則或演算法版本、生成器版本、候選輸出、評估器版本與結果。這是工程上的 provenance，不是要求保存模型私有的逐字內部思考。

## 5. A 級高風險缺口

### A-01｜循環探索上限可能把無環長鏈誤判為分析不完整

**可定位依據：** [候選驗證器 L185–L230](../實驗/validator_prototype.py) 中 enumerate_cycles 會從每個排序後的節點開始遞迴枚舉簡單循環候選；cycle_cap 固定為 500，對每次探索到的轉移累計，不是只計算實際發現的循環。

**反例推演：** 對一條方向與排序 ID 一致的單純鏈，假設 33 個節點、32 條邊。以每個節點作為起點重複探索其後續鏈，轉移檢查次數為：

\[
32+31+\cdots+1=\frac{32\times33}{2}=528
\]

528 大於 500，因此即使這個圖沒有任何循環，也可能觸發 VLD-407，將分析標為不完整並阻擋發布。這是從演算法控制流程推導出的邊界反例；尚未在 Python 環境實際執行。

**裁決：A 級高風險。** 不能只提高常數，因為枚舉所有簡單循環的成本可能快速增長。應先明確定義目的：若只需判定被禁止的循環，使用適當的線性圖算法／強連通分量或拓樸檢查；若需產生警告，定義每個相關區域至少提供哪些代表路徑；只有在確實需要所有簡單循環且可承受成本時才枚舉全部。探索預算需有明確單位、可配置來源、可重現輸出與超額狀態。相關測試已在現行有限驗收計畫中列為 NOT_RUN，不能視為已驗證。

### A-02｜Markdown 與 JSON 只比對同一個 revision marker，不能證明內容相同

候選驗證器會比對 Markdown 內的 foravar-model-revision marker 與 JSON 的 SHA-256。這證明兩者**宣告**同一 revision，不證明 Markdown 的實際內容是由該 JSON 確定性生成，也不證明 Markdown 中沒有手動修改或過期段落。

**反例：** 將舊版 Markdown 保留大部分內容，只把 marker 改為新版 JSON 的 SHA-256；若驗證器只檢查 marker，就無法發現正文仍舊。這會使版本標記看似一致，實際內容不一致。

**裁決：A 級。** 要嘛 Markdown 必須由固定版本的確定性 exporter 自動產生並在驗證時重生成／比較；要嘛必須能將 Markdown 解析回資料模型並做語意比對。單純 marker 不足以證明兩份內容一致。

### A-03｜非循環類 warning 並未全面進入發布保留與下游契約

VLD-302 可以對缺來源的節點發出 warning，但發布時現行程式對 release warning 的嚴格比對主要針對 VLD-202／VLD-203 的循環警告。這代表「其他 warning 也不得在 Markdown／下游 AI 中靜默消失」這個廣泛原則，尚未被同等完整地落實在驗證流程。

**風險：** 候選模型可能保留一個已接受、但來源不足的非核心推論；若匯出或下游 AI 不保留這個警告，使用者看見的模型就可能比實際證據更確定。

**裁決：A 級。** 所有影響理解或決策的 warning 應有一致的保存政策：哪些必須隨發布攜帶、哪些阻擋發布、哪些允許但需顯示、哪些不影響下游。發布記錄需能對照當次評估產生的 warning 集合，而非只校驗部分種類。

### A-04｜自由 attributes 可能覆寫或重複正式語意

正式契約明確表示 attributes 不應重複正式欄位；但 node／edge／condition 的 attributes 允許任意 key。現行規則未見對保留欄位名稱做統一拒絕。

**反例：** 節點正式欄位為 review_status=accepted，但 attributes 另放 review_status=rejected；或 edge 的正式 relation_type=causes，同時 attributes 又記錄 relation_type=influences。即使底層驗證器只讀正式欄位，下游讀取者也可能使用錯誤版本。

**裁決：A 級。** 要求正式欄位不能出現在相同物件的 attributes 中；並對允許的領域擴充定義 namespace／owner 或最小 schema。不要用「文件規定不能重複」取代機械規則。

### A-05｜VLD-303 的人工審核規則缺少可操作的觸發契約

規則登錄表將 VLD-303 描述為人類發現 evidence_status 與 review_status 被混用時，必須進行人工審核；並註明無法由兩個 enum 自動推定。但目前尚未定義：
- 哪個人或流程能提出這個 flag；
- flag 存放在哪裡；
- 哪個發布／審核步驟會檢查它；
- 如何記錄審核理由與結案結果。

**裁決：A 級。** 可以保留人工規則，但必須把它明確定義成一項審核程序，而不是讓它看似已由驗證器覆蓋。不能自動判定的規則應有可定位的人工審核紀錄與發布閘門。

### A-06｜需求、實作與驗收的結構閉合目前仍多半停留在清單層

現行模型已有 satisfies、verified_by、implements 等關係，方向合理；但候選驗證器沒有完整規則要求：
- 已確認的目標／需求必須有適用的下游承接或明確豁免；
- 被標為已交付的核心能力必須有驗收依據；
- 驗收依據必須是可定位的測試／觀測結果，而不只是名為「測試」的節點；
- 無父目標的需求、無目標依據的設計元素與無驗收路徑的核心需求能被區分；
- 已知不適用的項目有明確理由，而不是靠沒有連線暗示。

**裁決：A 級。** 不應把所有無關聯節點一律視為錯誤；應依目標類型與發布聲明建立具型別的完整性規則，讓「有意保留的草稿／豁免」與「漏接需求」有不同狀態。

### A-07｜影響分析規則已被描述，但不可據此推定引擎已存在

關係登錄表有 impact 與 impact_walk 政策，研究文件也將影響分析放入總體架構。但候選驗證器目前呈現的是輸入驗證、引用、循環與發布檢查的程式路徑；不能把規則 JSON 中的 impact_walk 欄位等同已實作的影響分析引擎。

**裁決：A 級範圍風險。** 將「已有影響政策定義」與「已可計算、產生路徑且經驗收的影響分析」分開標記。尚未實作的能力保留在研究／設計狀態，不應以規格存在暗示執行能力。

### A-08｜發布紀錄有必填欄位，還沒有完整的資料契約

release record 目前採獨立 JSON，是合理的分離方式；問題不是「一定要放進模型 JSON」，而是其欄位、型別、允許值、人工決策參照與警告集合規則尚未由獨立 schema 完整限制。候選程式檢查部分必填欄位和部分型別，但像 change_summary、review_decision_reference 是否可定位、警告 ID 集合是否完全對應等仍有缺口。

**裁決：A 級。** 為 release record 定義單獨且版本化的資料契約，並驗證：所有必要欄位型別正確、review_decision_reference 真正可定位、warning IDs 不重複、被確認的 warning 必須存在於此次報告、需要保留的 warning 不能遺失；這些都是發布閉環的一部分。

| RC-06 | Markdown 正文是舊版，但 marker 被換成當前 JSON hash | 應發現正文不符合當前模型的確定性輸出 | 目前 marker 比對不足以證明正文同步 |

| RC-10 | release record 填了不存在的 review_decision_reference 或多餘 acknowledged_warning_ids | 應要求可追溯的決策依據並驗證集合一致 | 必填欄位存在檢查不足以證明參照真實有效 |

### 6.1 優先順序

先做 RC-01、RC-02、RC-03、RC-05、RC-06。這五項可直接挑戰：空模型能否發布、因果證據是否受控、來源是否可重現、循環算法是否對一般圖可用，以及輸出版本是否真正一致。這些反例的結果比繼續增加一長串抽象原則更能改變架構決策。

## 7. 因果鏈為何尚未閉合

### 7.1 結構連線不等於因果證明

目前關係模型正確地把 causes、influences 與 depends_on、precedes 分開，避免把依賴或時間先後直接當成因果。但單純有向圖上的 A → B → C，只表示模型記錄了相關主張，並不證明 A 對 B、B 對 C 的因果關係成立。

若系統要把「原因 → 機制 → 結果」當成已驗證的因果鏈，至少要明確回答：

1. **主張範圍：** 在什麼系統邊界、時間範圍與條件下成立？
2. **機制：** 透過什麼中間作用，A 可能影響 B？
3. **觀測：** 有何資料、測試或來源支持各段連結？
4. **替代解釋：** 是否存在共同原因、混淆變數或其他機制，同樣能解釋觀測？
5. **反例／介入：** 哪些觀測、移除實驗、干預或反事實結果會削弱該因果主張？
6. **不確定性：** 現有依據支持的是事實、工程假說、相關性還是尚未檢查？
7. **失效條件：** 在何種環境、負載、狀態或時間下可能不成立？

並非每個軟體專案都需要完整的統計因果推論模型；但如果沒有符合任務的因果驗證方法，結論就應維持為有來源的因果假說，而不是把鏈接存在視為證明。

### 7.2 本專案的因果閉環建議

對每個高影響 causes／influences 主張，建立有限且可檢查的閉環：

- 明確的因果主張與適用條件；
- 指向來源或證據命題的引用；
- 至少一個支持該主張的可定位觀測／測試，或明確標示目前只有假說；
- 若有反證，保留 refutes 關係，不因已有支持邊而忽略；
- 評估結果由規則／人工審核記錄，不由連線數或 LLM 自評決定；
- 下游匯出必須帶上證據狀態與未決條件；
- 當來源、條件或適用環境改變時，重新檢視相關因果主張。

若沒有可執行的因果判定，就應把狀態保留為「待驗假說」。這並不妨礙它成為設計候選；它只阻止候選被誤當成已驗證事實。

## 8. 外部研究對照與能支持的結論

### 8.1 需求完整性需要逐項與整體檢查

NASA Software Engineering Handbook 的 SWE-051 將需求分析涵蓋到正確性、一致性、清晰度、完整性、可追溯性、可行性與可驗證性，並建議對需求集合及操作情境進行檢查。[NASA SWE-051](https://swehb.nasa.gov/spaces/7150/pages/16450593/SWE-051%2B-%2BSoftware%2BRequirements%2BAnalysis)

這支持本專案使用分層的需求閉合檢查，但不支持「六個 checklist 一定能發現所有缺漏」。要求是否足夠，仍取決於目標、系統邊界、假設、操作情境與驗收依據是否完整。

NASA 的[Verification Requirements Matrix](https://www.nasa.gov/reference/system-engineering-handbook-appendix/)也強調需求須有唯一識別碼、明確來源以及對應的驗證方式。對本專案的含義是：圖中的滿足／驗證連線需落到可定位的驗收方法和結果，不只是有一個名為「測試」的節點。

### 8.2 架構還原需要 ground truth、多工具與明確範圍

Schneider 等人在 2025 年比較微服務架構靜態還原工具，研究中辨識 13 個工具，9 個可執行，並以 17 個微服務應用與人工建立的 ground truth 比較；研究報告中，單一最佳工具的整體 F1 為 0.86，特定四工具組合達 0.91。[原始論文](https://doi.org/10.1007/s10664-025-10686-2)

這些數字只適用該研究的工具、資料集、元件／連線定義與評分方式。它們支持的結論是：架構還原應有可核對的真值、範圍與指標，也可以研究多來源融合；它們不能直接變成本專案的預期準確率或效能承諾。

2026 年的 ArchAgent 研究報告結合靜態分析、程式碼分段、依賴上下文和 LLM 合成，並報告依賴上下文對其架構還原有幫助。[ArchAgent（IEEE／arXiv）](https://doi.org/10.1109/ICASSP55912.2026.11462552) 這與本企劃的混合流程方向相符，但其研究資料和專案範圍仍不能證明本企劃的具體資料模型或候選驗證器有效。

### 8.3 Provenance 要能說明資料如何產生，不只是存在 URL

W3C PROV-DM 將 provenance 描述為涉及實體、活動與責任主體的產生資訊，並明確提醒：即使有生成／使用鏈，衍生關係也不能只依連線存在便自動成立。[W3C PROV-DM](https://www.w3.org/TR/prov-dm/)

因此，本專案不一定需要完整導入 PROV 標準，但必須保留足以重現關鍵結論的最低資料：來源版本／定位、產生或轉換活動、採用規則／工具版本、輸入 revision，以及評估結果。這不等於保存隱藏思維鏈；它是為了可稽核、可重現和版本隔離。

### 8.4 獨立評估器仍會面臨 oracle problem

軟體測試研究的 Oracle Problem 指出，測試不只要執行程式，還要知道正確結果是什麼；當規格、模型或可用預言不足時，最終仍需要人類或其他可信的 oracle 資訊。[Barr 等人，The Oracle Problem in Software Testing](https://doi.org/10.1109/TSE.2014.2372785)

因此，「用另一個 LLM 檢查第一個 LLM」不能自動解決評估獨立性。若兩者共用相似偏見、同一錯誤前提或被同一個錯誤標準引導，兩者可能一致地犯錯。關鍵是預先固定驗收標準、建立獨立真值或可執行不變條件，並把人工判斷和機械檢查的範圍分開。

近期 LLM-as-a-judge 調查也把一致性、偏差與評估可靠性列為仍需處理的核心議題，而不是將 LLM 評分視為通用真值。[A Survey on LLM-as-a-Judge（2026）](https://doi.org/10.1016/j.xinn.2025.101253)

### 8.5 品質範圍不能只看功能與關係

ISO/IEC 25010:2023 定義軟體與 ICT 產品品質模型，提供九項特性及子特性作為規格、量測與評估的參考模型。[ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html)

對本專案的合理用法不是把九項品質特性全部塞成必要功能，而是依使用情境選擇相關的可靠性、效能、可維護性、安全性、可移轉性等品質需求。若目標只記錄概念框架，需求負擔可以很小；若要長期作為可靠資料治理系統，則不能只以「所有節點已連線」代表完整。

### 8.6 外部研究不能替代專案本身的驗收

NIST Generative AI Profile 提供 AI 風險識別、管理與評估的參考框架。[NIST AI 600-1](https://doi.org/10.6028/NIST.AI.600-1) 這支持明確記錄風險、測量方法和剩餘不確定性；它不是對本專案架構的認證或效果證明。

## 9. 應採用的閉環定義與最小修正順序

### 9.1 將「完整」改為範圍限定的閉合聲明

不要輸出「框架已完整」這種沒有範圍的絕對聲明。每次應明確聲明：

> 在指定目標、系統邊界、假設、來源版本、關係規則及驗收範圍下，已完成哪些閉合檢查；哪些已通過，哪些為人工接受的例外，哪些尚未檢查，哪些因資料或預算不足而無法判定。

建議把閉合狀態至少分為：
- STRUCTURAL_CLOSED：Schema、ID、引用與已登錄圖規則符合。
- TRACEABILITY_CLOSED：已確認需求與核心元素有來源／父項、承接與驗收路徑，或有明確豁免。
- EVIDENCE_CLOSED：高影響主張有可定位依據及適用性評估；其他主張保持已標示的不確定狀態。
- BEHAVIOR_CLOSED：指定的操作情境與狀態轉換有對應測試／分析結果。
- RELEASE_CLOSED：發布紀錄、警告、JSON 與 Markdown 對應同一實際 revision。
- INCOMPLETE／INCONCLUSIVE：任何必要範圍未檢查、受阻或證據不足。

以上為審查建議的研究分類，不是已核准的新 Schema 欄位；要正式使用需經契約變更審查。

### 9.2 最小修正順序

**第一優先：定義必要性與閉合語意。**  
在任何演算法之前，先分開「明確要求」「政策／法規約束」「相對方案必要」「邏輯必要」「可選」「假說」。同時明確定義一個模型何時可以被稱為結構閉合、需求閉合、證據閉合及發布閉合。

**第二優先：先處理四個 S 級反例。**  
RC-01 空模型發布、RC-02 因果邊無證據、RC-03 來源存在但不可重現、RC-04 必要性被替代方案反證。先用明確 fixture 或人工核對案例重演；不要先擴增測試總數或引入新技術。

**第三優先：修正可定位的發布／演算法缺口。**  
測試 RC-05 循環 cap、RC-06 Markdown marker、RC-07 warning 遺失、RC-08 attributes 衝突、RC-10 release decision reference。這些問題有具體反例，適合做單點修正與一次完整回歸。

**第四優先：才測試雙向推理成效。**  
在目標、必要性定義、來源規則與評估器契約固定後，再做一個已知答案的逆向還原案例和一個正向缺漏推導案例。每個案例至少要有獨立標註的真值、評分規則、反例和基線比較。無法達成可信真值的內容要標為不可判定，不能讓產生器自己兼任唯一評分者。

**第五優先：只有實測證明瓶頸後才引入進階演算法。**  
不要因為圖、矩陣、低秩或 Network Completion 看起來有理論吸引力，就預先加入架構。先確認瓶頸來自來源解析、結構抽取、候選推導、規則驗證、真值不足還是輸出同步。

### 9.3 建議的最低追溯鏈

對每個已確認的目標／需求，建立下列可查詢鏈：

目標／需求 → 約束與假設 → 候選機制／設計決策 → 實作或承接物 → 驗收方法 → 實際結果 → 發布 revision

不是每個項目都必須有機器測試：若某要求只能由人類檢查，必須明確登記人工驗收方法、判定人、日期、結果及依據。不能把「沒有測試」默認為通過。

對每個推導候選，另保存：

輸入 revision + 來源定位 + 推導規則／工具版本 → 候選結果 → 獨立評估結果 → 人工決策 → 下游使用狀態

這樣能將推導鏈與需求實作鏈連起來，但不需要將隱藏思維鏈逐字存檔。

## 10. 有限的後續驗收條件

本節只提出最少量、最能改變架構判斷的驗收條件，不再無限擴張測試目錄。

| 優先 | 必須回答的問題 | 最低證據 | 不能用什麼代替 |
|---|---|---|---|
| P0 | 空模型或缺少目標／需求承接的模型能否發布？ | 空模型、最小合法模型及缺項模型的實際 CLI 結果；固定 SHA | 靜態閱讀 Schema |
| P0 | 沒有證據的 causes／influences 邊是否會阻擋或被明確標為假說？ | 兩個邊 fixture：無來源與有來源；發布閘門實際結果 | 只測 is_evidence_for／refutes |
| P0 | 來源引用是否可重現？ | 無 URI／locator、可定位 URL、固定 Git commit／雜湊三類來源案例 | 只確認 provenance_refs 非空 |
| P0 | 無環長鏈會不會觸發 VLD-407？ | 依節點數遞增的長鏈邊界測試及實際探索次數 | 假設 500 的上限足夠 |
| P1 | Markdown 即使 marker 相符但正文過時，會否被發現？ | 人為修改 Markdown 正文但保持 marker 的負向案例 | 只比對 marker 字串 |
| P1 | 非循環 warning 是否完整到達 release record 與下游輸出？ | 對比本次所有 warnings 與發布資料，驗證多出／缺少／被改寫時的結果 | 只檢查循環警告 |
| P1 | attributes 能否覆寫正式欄位的語意？ | 注入重複欄位名的 Schema／validator 測試 | 只依賴文件禁令 |
| P1 | release decision reference 是否真實可定位？ | 有效、缺失及不存在的參照案例 | 只檢查字串非空 |
| P1 | 需求是否存在未處理孤兒、重複或無驗收路徑？ | 最小 goal→requirement→implementation→verification 案例及明確豁免案例 | 只計算節點／邊數 |

**執行治理：** 這些項目應併入現有唯一案例清單與「演進與驗收總結」，不要再建立另一份平行測試清單。先檢查既有案例是否已覆蓋；只有真正缺失的案例才新增。執行前固定候選程式、Schema、關係規則與跨物件規則 SHA。若環境仍不能執行，就保持 BLOCKED，不用文字推演冒充 PASS。失敗最多做一輪針對性修正及一次完整回歸；仍失敗則記錄阻擋與決策，不繼續無限審查。
