## 摘要

本企劃研究兩種互補能力：一是從既有程式、資料、文件、設定及可觀察行為，逆向還原元件、依賴、資料流、條件與狀態轉換；二是從明確目標、有限核心或不完整規格，正向推導可能缺少的必要機制，再以來源、約束、反例及獨立評估器篩選。兩者共用同一套可追溯的結構模型，但推理依據、候選產生方法與驗收方式必須分開。

本研究不是重新設計一套與現有專案並行的資料格式。現有 AI 理解框架已定義 JSON 正式模型、穩定 ID、節點與關係、條件、來源、審核狀態、證據狀態、模型生命週期、關係規則登錄表、跨物件驗證及發布閘門。雙向引擎應優先映射到這些既有定義；若現有契約無法表達新資訊，先以研究候選與來源紀錄保留，不得私自新增正式欄位或枚舉值。

研究採用「證據與目標先行、圖為權威結構、矩陣作特定任務的衍生視圖、候選與正式內容分離、可程式化規則由獨立評估器判定」的原則。低秩近似、Network Completion、Hankel 系統辨識、MDL 等方法皆有適用條件，不能被提升成通用的軟體反演演算法。量子電路研究支持的是「生成器提出候選、獨立評估器檢查」的工程模式；它不證明一般軟體可以透過 uncompute 或矩陣求逆完整還原。

目前專案資料顯示：原型驗收仍為 STATIC_PREFLIGHT_PASS／PYTHON_EXECUTION_BLOCKED；現行驗證器與跨物件規則候選尚未完成實際執行，UI 規劃閘門未通過。本文件只定義研究問題、資料映射、候選方法與後續實驗設計，**不改變目前唯一工作主線，不代表雙向引擎已實作、已驗收或已獲正式企劃核准**。

**核心研究命題：** 在目標、證據、約束與資源預算清楚的前提下，產生可追溯的結構模型，顯示必要缺口與未決假說，並透過獨立驗證逐步縮小不確定性；不能證明「沒有其他缺漏」，只能說明指定範圍內已檢查的項目及剩餘未知。

## 1. 研究定位與決策摘要

### 1.1 研究定位

本模組研究「如何建立與補全可追溯的系統理解」，不是繪圖功能本身，也不是新的驗證器副本。它可能為現有 AI 理解模型提供兩種資料來源：從已存在的材料萃取結構，或從目標與約束推導待確認候選。其結果仍須進入現有資料契約、跨物件規則、證據治理與發布流程。

### 1.2 決策摘要

| 項目 | 研究裁決 | 原因與邊界 |
|---|---|---|
| 共用結構表示 | 沿用現行 JSON 模型與型別化關係圖 | 避免建立第二份真相來源 |
| 逆向還原 | 多來源萃取、由下而上與由上而下核對 | 程式、文件、設定與行為各自只揭露部分結構 |
| 正向補全 | 從目標、依賴、資料、狀態、約束及驗收六個面向產生候選 | 防止由「常見做法」直接臆造需求 |
| 候選決策 | 分開判斷必要性、證據品質、人工審核與發布狀態 | 避免將「有來源」等同「已證實」 |
| 獨立評估 | 結構與可執行規則交由確定性檢查；語意適用性保留人工覆核 | 生成者不應自我宣告通過 |
| 矩陣與低秩 | 僅在特定任務及實測假設支持時採用 | 稀疏性不等於低秩，近似不等於精確還原 |
| 成效宣稱 | 只依有真值標註的案例及實測結果 | 目前沒有本專案準確率、加速倍數或完整性保證 |
| 施工狀態 | 本文件僅為研究設計 | 現行驗收與 UI 閘門維持原狀 |

### 1.3 與主企劃的關係

主企劃處理 AI 理解的資料治理、人工修正、多視圖、版本比較與下游取用；本模組處理產生該理解模型前後的結構萃取與缺口假說。兩者共用資料契約及證據治理，但功能邊界不同。

本文件不得：
- 改寫目前正式 Schema 或關係規則；
- 以新增候選取代人類審核或證據狀態判定；
- 將研究中提出的測試當作已執行結果；
- 繞過「候選驗收停止條件達成後才可啟動 UI 規劃」的現行閘門；
- 另建第二份現行驗證器、案例清單或驗收結果文件。

## 3. 研究問題、目標與非目標

### 3.1 逆向問題

當系統已有部分或多種材料，如何重建其可追溯結構，並清楚區分直接觀察到的事實、由材料推得的結論與仍無法識別的部分？

### 3.2 正向問題

當輸入只有目標、核心概念、限制或部分規則，如何推導完成該目標所需的候選機制；又如何避免把「常見功能」「偏好的架構」或模型自行聯想的內容誤認成必要需求？

### 3.3 研究目標

1. 建立兩種引擎共用、但推理基礎可辨識的結構資料輸出。
2. 把每個重要節點、關係與候選主張連結到來源、明確需求、推導步驟或待確認假設。
3. 支援不同還原目標，避免將結構重建、行為等價與原始形式精確恢復混為一談。
4. 用獨立評估器檢查可程式化的結構與不變條件。
5. 用有限候選集、局部分析、增量重算及停止條件控制資源。
6. 透過帶有可核對真值的案例量測缺漏、誤報、證據追溯及計算成本。

### 3.4 非目標

本研究不承諾：
- 從任意輸出唯一反推出原始程式或作者意圖；
- 在沒有真值、輸入／輸出觀測或明確規格時證明完整；
- 以單一圖模型或矩陣反演通用地理解所有軟體；
- 在未測量之前聲稱準確率、完整率、速度提升或成本節省；
- 第一階段導入圖資料庫、GraphRAG、完整本體推理、事件溯源平台或多人 CRDT；
- 直接開始正式 UI 或 Runtime 實作。

## 4. 還原層級、術語與證據界線

### 4.1 三種還原目標

| 目標 | 問題 | 可用證據 | 主要限制 |
|---|---|---|---|
| 原始形式精確恢復 | 能否還原原始程式、文件或序列化形式？ | 原始版本、完整來源與可逆轉換 | 通常需要完整來源或可逆映射 |
| 結構重建 | 能否重建指定範圍的元件、依賴、資料流與狀態？ | 程式靜態分析、文件、設定、資料與多來源交叉核對 | 多種結構可能符合相同觀測 |
| 行為等價 | 候選是否在指定輸入與條件下產生等價行為？ | 執行重放、參考輸出、規格、性質測試或形式化模型 | 有限測試不代表所有輸入都等價 |

每次研究開始前必須指定還原目標、輸入範圍、可用證據、不能接受的差異與驗收方式。未指定前不得將「還原成功」當成可判定結論。

### 4.2 資料狀態分類

研究輸出必須能區分：
- 直接觀察：來源材料可直接指出的內容。
- 外部主張：由可定位來源提出，仍須檢查來源與適用條件。
- 推導結論：由明確前提與規則導出，需保存推導依據。
- 假說：合理但未獲充分證據支持的候選。
- 未知：資料不足或有多個無法區分的解釋。
- 衝突：不同來源、規則或候選之間不能同時成立。
- 排除項：在現有任務範圍下不採用，並記錄排除理由。

這些是本研究的分析分類，不是對現行 Schema 新增枚舉值的授權。若要進入正式資料模型，必須先確認現有欄位是否足以表達；不足時另依專案變更流程審查。

### 4.3 不能混淆的關係

結構包含、執行先後、資料流、依賴、因果、一般影響、支持證據與反證是不同語意。邊的存在只表示該關係被記錄，不自動證明它為真、必要或已被人類接受。

本模組使用現行關係登錄表已定義的 relation_type；未登錄關係不能自行擴充到正式模型，必須回報未知關係並阻擋依賴該規則的發布或影響分析。

## 5. 與現行資料契約的對接方式

### 5.1 沿用正式模型，不創建平行格式

現行契約的外層包含 schema_version、model_id、title、model_state、rule_profile、nodes、edges、conditions、sources，以及契約允許的其他欄位。雙向引擎的產出應在這個模型內表達；研究期間如需臨時記錄候選評分、候選群或推導日誌，應留在研究產物，不得將尚未審查的欄位塞入正式模型。

### 5.2 欄位與責任映射

| 現行資料概念 | 在雙向引擎中的責任 |
|---|---|
| nodes | 系統元件、目標、需求、功能、條件性主張及可追溯的結構項目 |
| edges | 元件關係、資料流、依賴、需求追溯、支持／反證等已登錄關係 |
| conditions | 關係守衛、執行條件、適用範圍與可檢查條件 |
| sources | 原始程式、文件、設定、外部標準、可重現觀測及其他來源定位 |
| stable ID | 維持來源、關係、修訂與影響分析的跨版本識別 |
| provenance_refs | 由節點或關係追到可定位來源 |
| condition_refs | 指向適用的條件；依現行規則，v1 多條件按 AND 解讀 |
| structural_role | 表達 core、main_axis、skeleton 等結構角色，不得與 entity_kind 混用 |
| entity_kind／claim_kind | 表達資料物件類型與主張性質，不應被結構層級取代 |
| review_status | 人工檢視／接受／否決／重新確認狀態 |
| evidence_status | 主張的證據評估摘要 |
| model_state | 整份模型的草稿、提案、發布或歷史狀態 |
| model revision／release record | 精確綁定匯出版本、Schema、關係規則與變更摘要 |

表中的名稱用於對應既有契約；正式欄位定義及允許值仍以[資料契約](../AI理解框架_正式資料契約與原型推演規格.md)及[JSON Schema](../規格草案/ai-understanding-model.schema.json)為準。

### 5.3 關係類型的使用原則

引擎不為每一種演算法創建自己的邊類型，而是使用已登錄且語意相符的關係，例如：

- contains：組件／子結構包含關係。
- depends_on：成立或執行所需的依賴。
- precedes：明確的先後順序。
- transfers_data_to：資料或資料產物的流向。
- causes／influences：因果或影響主張；不能單靠連線推定已證實。
- derived_from：候選由哪些材料或主張推導。
- satisfies／verified_by：需求或驗收條件與承接物／驗證依據的追溯。
- supports／is_evidence_for／refutes：理由、支持證據及反證；這些關係不能自動改寫目標的 evidence_status。

其中 supports 與 is_evidence_for 是不同關係類型，應依現行登錄表各自語意使用，不得因文字相近而混用。關係家族、循環政策與影響政策必須從登錄表取得，不能重複存放在每條邊上。

### 5.4 對接既有驗證層

輸出模型應送入現行 L0–L5 驗證流程：
- L0：JSON 解析。
- L1：固定版本 JSON Schema 與關係 profile 一致性。
- L2：全域 ID、端點、來源、條件引用、自我連線與重複語意邊。
- L3：型別化圖語意、指定關係的循環與影響規則。
- L4：來源、主張、證據與人工審核治理。
- L5：不可變修訂、警告確認及發布門檻。

這裡的 L0–L5 是現行驗證管線，不是雙向推理演算法的階段代號。為避免混淆，下方兩個引擎使用 A0–A5 與 B0–B5。

## 6. 引擎 A：逆向結構還原

### 6.1 輸入盤點與範圍封存（A0）

先登記可用材料，至少包括：來源 URI／檔案路徑、版本或 commit、時間、材料類型、可讀範圍、擷取方式、缺失範圍與完整性限制。對不可讀檔案、外部服務狀態、沒有來源的推論及未能重現的行為，明確記錄未知，不得假裝已檢查。

### 6.2 分層提取（A1–A3）

1. **元件層：** 盤點模組、檔案、資料表、介面、服務及外部依賴。
2. **關係層：** 提取引用、呼叫、資料交換、包含、狀態轉換及需求追溯等關係。
3. **行為層：** 在有證據時建立輸入、輸出、狀態、前置條件、失敗路徑及可觀察行為。
4. **來源層：** 每個重要項目記錄來源與擷取規則；不同來源描述同一對象時，不立即覆蓋，而先建立可比對的候選映射。
5. **缺口層：** 記錄未解析引用、文件與實作不一致、無法觀察的外部行為及證據衝突。

這些層是分析次序，不代表每一項來源都能提供所有層級資訊。

### 6.3 由下而上與由上而下核對（A4）

- **由下而上：** 從程式、資料、設定及局部行為推導可觀察的結構。
- **由上而下：** 從需求、文件、介面契約及使用者目標檢查實作是否承接要求。
- **交叉核對：** 比較兩條路徑得到的元件、關係與條件，標出支持、矛盾、未覆蓋或多解情況。

兩條路徑的差異是診斷線索，不自動代表文件或程式哪一方正確。若文件與實作不一致，需要依權威來源、版本、目標及驗收政策裁定。

### 6.4 還原輸出（A5）

逆向引擎應交付：
- 指定範圍的結構模型與可追溯來源。
- 需求／元件／驗收項的雙向追溯關係。
- 未解析引用、矛盾與不可識別項清單。
- 每個候選結構的證據與推導依據。
- 相對明確版本基準的結構差異。
- 已檢查、未檢查、被排除及仍未知的範圍。

不得只輸出一張圖或一篇自然語言摘要，因為兩者都不足以表示精確來源、穩定 ID、衝突及未決範圍。

## 7. 引擎 B：正向缺漏推導

### 7.1 先定義目標，才能定義缺漏（B0）

候選是否必要，取決於指定任務。每次推導至少固定：
- 目標與非目標。
- 必須滿足的功能、品質、資源與安全約束。
- 輸入、輸出及系統邊界。
- 正常、失敗、中斷與恢復情境中哪些屬於目標範圍。
- 可用來源、領域假設及未知資訊。
- 完成條件、驗收方式與不可接受的錯誤。

未被目標或約束支持的「常見功能」應先作為可選候選，不得升格成必要設計。

### 7.2 六種缺口檢查（B1）

| 視角 | 要問的問題 | 輸出候選的例子 |
|---|---|---|
| 目標覆蓋 | 每個已確認目標是否有承接機制與驗收方式？ | 無元件承接的需求、缺少的驗收條件 |
| 依賴閉合 | 各功能的前置條件、服務依賴與責任歸屬是否存在？ | 缺失依賴、未解析介面 |
| 資料閉合 | 資料在哪裡產生、轉換、驗證、保存、失效及被使用？ | 未定義來源、型別／單位不一致 |
| 狀態閉合 | 適用狀態與轉換是否完整，失敗和恢復出口是否明確？ | 未定義轉移、無法到達的狀態 |
| 約束閉合 | 已確認的不變條件、資源限制、順序與跨元件規則是否互相一致？ | 矛盾條件、無法同時滿足的規則 |
| 驗收閉合 | 每個重要需求是否可觀察、檢查或測試？ | 缺少預期結果、無判定條件 |

六種視角是檢查方法，不是六套必須新增的服務。若某項檢查沒有揭露真實缺口，就不新增功能。

### 7.3 有行為觀測與無行為觀測的兩條路徑（B2）

**有參考行為時：** 先建立模型預測，再比較預測與觀測的殘差。系統性偏差可能顯示缺少變數、條件或機制，也可能來自觀測誤差、錯誤前提或不適用的模型。殘差只能協助定位，不能直接替缺漏命名。

**沒有參考行為時：** 不得虛構「預測誤差」。改用目標分解、領域規則、依賴閉合、狀態機、單位／範圍約束及反例分析提出候選，並把缺少的前提明確列為未知或假設。

兩條路徑使用相同正式資料模型和驗收契約，但必須保存候選產生所依據的資訊種類。

### 7.4 候選推導與淘汰（B3–B5）

對每個候選逐一檢查：
1. 對應哪個已確認目標或約束？
2. 缺少它是否會導致該目標／約束失敗？
3. 依據是直接來源、獨立佐證、正式規則還是類比推論？
4. 是否已有其他元件承接相同責任？
5. 是否與現有規格或證據矛盾？
6. 引入後新增哪些依賴、狀態、失敗路徑與成本？
7. 哪一個觀測或測試能區分此候選與其他解釋？

候選若既無明確目標依據、也沒有合理推導或可驗證假說，應排除而不是保留成為永久需求。重要候選可做反事實檢查：暫時移除候選，查看目標或不變條件是否失敗。失敗可支持必要性，但仍須排除因模型缺漏而導致的假性失敗；不失敗也不能單獨證明候選毫無價值。

## 8. 候選分類、必要性與證據治理

### 8.1 分開判斷候選必要性與證據品質

研究候選可以用以下決策類別整理：
- 已確認必要：有明確需求／約束或可核對規則支持。
- 強力候選：多個適用來源或推導支持，但必要性仍依賴條件。
- 可選設計：可能有價值，但不屬於目前目標成立的必要條件。
- 待驗假說：主要由推論、類比或不足的來源支持。
- 衝突項：與現有規格或其他候選不一致。
- 已排除候選：有明確範圍、反例或成本理由不採用。

這些決策標籤是研究分類，不等同正式的 review_status、evidence_status 或 model_state，不可直接互相映射。

### 8.2 證據強度

可用 E0–E3 作為研究分析用標記：E0 無可定位依據；E1 間接或類比依據；E2 有直接來源但範圍有限或缺乏獨立佐證；E3 有直接依據及適用的獨立佐證。此分類不是機率，不是正式 Schema 欄位，也不應用來自動決定證據狀態。

「證據品質高」不代表「候選對這個任務必要」；一個已被驗證的通用技術仍可能與目前目標無關。

### 8.3 與現行狀態軸線保持一致

現行契約把人工審核狀態、證據狀態與模型生命週期分開。雙向引擎必須遵守：
- 人工接受候選，不等於其外部事實已獲證實。
- 有來源，不代表來源支持該主張。
- 推導結論不應偽裝成使用者要求或外部觀測。
- 新增來源或支持／反證連線，不得自動改寫目標的 evidence_status。
- 已接受內容發生語意修改時，依現行政策進入重新確認流程。
- 已發布版本是不可變基線；修改應形成新修訂，而不是覆寫舊版。

現行發布門檻與確定性規則未經執行的部分仍是 NOT_RUN；本研究不能宣稱其已在 Runtime 中生效。

## 9. 圖、矩陣與專門演算法的適用範圍

### 9.1 關係圖是權威結構，矩陣是任務視圖

以有型別、可追溯的關係圖保留節點、邊、條件、來源與語意；需要計算時，再從同一份正式資料生成特定矩陣或索引。不可讓矩陣、文字規格及圖形各自演變成互不一致的權威副本。

| 表示方式／方法 | 適合回答的問題 | 不可直接推論 |
|---|---|---|
| 依賴鄰接矩陣 | 節點間是否有指定類型的直接依賴 | 連線即代表因果或必要 |
| 可達性／傳遞閉包 | 沿特定關係能否到達某節點 | 可達即代表路徑符合所有條件 |
| 資料流矩陣 | 資料來源、去向與轉換關係 | 連通即代表語意完整 |
| 狀態轉移表示 | 已建模狀態與條件的轉移 | 未列出的狀態不可能存在 |
| 需求追溯矩陣 | 需求由何物件承接、以何方式驗收 | 有映射即代表測試通過 |
| 證據追溯視圖 | 主張依賴哪些來源、支持或反證 | 引用數量多即代表真實 |
| 低秩近似 | 特定矩陣是否可在可接受誤差下壓縮 | 近似即可取代精確規格 |
| Network Completion | 在特定網路模型下推估缺失節點／邊 | 可自動決定節點的領域語意或必要性 |
| Hankel／系統辨識 | 有序列觀測且符合相應假設時分析動態系統 | 可直接識別任意靜態軟體的內部機制 |

### 9.2 稀疏與低秩不是同一性質

若圖有 N 個節點、E 條關係，稀疏儲存可依節點與關係數規模化；完整稠密鄰接矩陣則有 N² 個位置。但這不代表所有圖算法均為線性時間，也不代表稀疏矩陣低秩。

只有在矩陣定義與任務明確後，才量測奇異值衰減、近似誤差、記憶體、執行時間及下游任務影響。若低秩假設不成立，就不使用低秩方法。不能指定通用 rank，也不能預先宣稱固定加速幅度。

### 9.3 演算法採用門檻

- **Network Completion：** 僅當輸入確實是部分可觀測網路、圖生成假設可說明，且有真值或可檢查的下游任務時評估。其輸出應視為節點／邊候選，不直接視為語意結論。
- **Randomized SVD／其他低秩方法：** 僅當矩陣的數值定義合理、量測支持近似假設且誤差符合任務要求時評估。
- **ACA／ID／Nyström：** 僅在矩陣條目可可靠取得、抽樣方式符合方法假設且目標是特定近似時評估。
- **Hankel 與系統辨識：** 僅當有輸入／輸出序列、動態系統假設及可識別性條件時評估。
- **MDL：** 可協助比較模型複雜度與資料解釋，但不得以短描述碼或較少節點為由刪除已確認必要的需求。
- **矩陣求逆／uncompute：** 不作一般軟體反演方案。量子電路的可逆性約束與特定電路 evaluator 的成果，不足以推論任意程式都能透過逆操作還原。

工具選擇的優先次序是：問題適配、可驗證性、誤差風險、成本與可維護性，而不是演算法新穎程度。

## 10. 驗證、影響分析與發布邊界

### 10.1 產生候選與判定候選分離

引擎可以由程式分析、規則、LLM、圖方法或外部資料產生候選，但必須由另一條獨立評估路徑檢查。能以確定性規則判定的內容，不應只由第二個 LLM 自評。

至少需要下列評估責任：
1. 結構／Schema 檢查。
2. ID、端點、來源及條件引用完整性。
3. 關係類型、循環政策、重複語意邊及未知規則檢查。
4. 需求、約束、證據與人工審核追溯。
5. 有參考行為時的重放、差分及性質測試。
6. 成本與搜尋預算紀錄。
7. 發布修訂及 Markdown／JSON 的版本一致性。

以上是研究對現有管線的使用方式，不代表這些功能已全部實作。

### 10.2 影響分析必須使用現行關係政策

變更影響不能單靠無差別 BFS／DFS 擴散。需從現行關係規則取得依關係類型定義的傳播政策，並保留觸發變更、關係路徑、規則版本及理由。未知邊規則時，應停止受影響路徑並報告未知；找不到路徑只能回報「未找到路徑」，不可宣稱「不存在影響」。

增量分析只在依賴圖與版本追蹤可靠時安全。來源版本未知、存在未解析引用或可能影響全域約束時，應擴大檢查範圍，並說明原因。

### 10.3 驗證層級與可宣稱範圍

| 層級 | 能提供的證據 | 結論限制 |
|---|---|---|
| 靜態檢查 | 檔案格式、欄位、引用與來源程式標記 | 不證明程式執行正確 |
| 桌上推演 | 在明確假設下逐步核對案例 | 僅限指定案例與假設 |
| 有限程式測試 | 固定環境、版本與輸入下的實際結果 | 不等於所有輸入正確 |
| 差分／性質測試 | 在已定義 oracle 或不變條件下的結果 | 取決於測試分布、覆蓋及 oracle 品質 |
| 形式化證明 | 明確模型、假設與命題的證明 | 僅支持該命題及假設涵蓋範圍 |
| 使用者任務評估 | 按預先定義任務記錄成功與操作負擔 | 不可僅憑主觀印象宣稱提升理解品質 |

### 10.4 發布不能由引擎自行核准

候選引擎不得自動將模型從 draft 或 proposed 升級至 published。需要發布時，仍須通過現行 Schema、跨物件規則、證據與審核治理、關係規則、版本綁定及 release record 的閘門。任何未執行、BLOCKED 或無法判定的必要檢查都不能視為 PASS。

## 11. 成本控制與停止條件

### 11.1 成本來源

成本包括資料解析、跨來源對齊、圖建置、局部查詢、外部檢索、候選生成、矩陣計算、模擬、驗收與保存可重現證據。若沒有輸入規模、模型、環境、資料量及測試需求，不能給出可信的總成本或加速估算。

### 11.2 限制無效擴張

1. 先在系統／模組層分析，對高影響缺口才展開到函式與資料欄位。
2. 新查詢必須對應具體缺口、衝突或待裁決假說。
3. 先做低成本結構及引用檢查，再對高風險項目使用較昂貴的方法。
4. 限制每輪候選數，保留質性不同的方案；只有共同失敗或新證據足以改變決策時才擴大。
5. 重用既有結果時核對來源版本和規則版本；不能重用不明版本的 PASS。
6. 分別記錄搜尋、LLM、解析、矩陣、模擬與驗收成本。
7. 預算耗盡時停止擴展並列明未覆蓋範圍，標記 BUDGET_EXHAUSTED／INCONCLUSIVE，不可標為 COMPLETE。

### 11.3 停止條件

研究範圍只有在以下條件均有紀錄時，才可標記為「本輪研究完成」：
- 目標、輸入範圍、還原層級及驗收規則已固定。
- 已確認需求都有對應結構或明確的缺口狀態。
- 高影響候選有來源、推導依據或待驗條件。
- 重大衝突已解決，或以未決問題與阻斷理由保留。
- 本輪約定的評估器與測試有可定位結果。
- 未檢查範圍、未知與成本限制明確記錄。
- 研究結果沒有冒用其他版本的 PASS。

連續數輪沒有找到新候選，可以是停止擴張的實務訊號，但不能證明系統已完整或不存在未知缺口。

## 12. 研究實驗與評估設計

本節定義日後實驗應回答的問題，不表示現已執行。實際執行時必須固定輸入、標註真值、版本、工具、預算與評分規則，並保存原始輸出。

### 12.1 案例 A：已知答案的逆向還原

建立規模可控、具有已知元件與關係的程式／資料案例，事先凍結參考結構與可觀察行為，再隱去部分文件或關係。量測元件／關係 precision、recall、F1（僅在有可靠真值標註時）、未解析引用數、證據追溯完整度、未知標記正確性、時間與記憶體。

測試重點不是摘要是否流暢，而是重建結果是否有可核對的來源、能否辨別唯一解與多解，以及有沒有把未觀察到的內容偽裝成事實。

### 12.2 案例 B：從粗略遊戲框架推導候選閉環

輸入只給定地形、移動速度、糧草消耗和部分規則。獨立建立隱藏的必要條件清單，檢查引擎是否：
- 找出目標成立所需的依賴和資料流；
- 補出適用的時間、單位、資源更新與失敗狀態問題；
- 保留「糧草按人數、單位或時間步計算」等未決政策；
- 區分必要、可選、假說與衝突；
- 避免把常見遊戲機制自動加入必要需求。

公式只可在列明假設後使用。例如，若路段可通行、距離和速度定義明確且速度視為固定，才可以距離除以速度估算路段時間。若每單位每時間的消耗率為 c(t)，單位數量為 N(t)，才可在相應時間基準下累計需求量。這些是模型形式示例，不是對所有遊戲都成立的事實。

### 12.3 案例 C–G：反例與資源控制

| 案例 | 注入條件 | 期望能力 |
|---|---|---|
| C 資料不足 | 刪除關鍵來源、依賴或條件 | 保留 UNKNOWN／ASSUMPTION，不捏造補全 |
| D 規則衝突 | 注入互斥條件、錯誤單位或不一致規則 | 顯示衝突，不在未裁決前宣稱閉合 |
| E 功能重複 | 多個名稱不同但責任重疊的候選 | 識別重複，保留行為差異與來源 |
| F 預算限制 | 限制時間、查詢、候選數或模擬量 | 優先處理高影響項，正確標記未完成 |
| G 錯誤注入 | 注入錯誤邊、非法轉移或版本不一致 | 獨立評估器定位缺陷及受影響路徑 |

### 12.4 評估防洩漏

- 真值清單、測試集、評分規則與門檻須在執行前凍結。
- 若候選生成流程看過完整真值，該案例不得再當盲測。
- 以相同資料與相同規則反覆重跑，不算新的獨立證據。
- 修改規格或測試門檻時，保存理由並標明受影響案例。
- 報告所有失敗、不可判定、成本超額與未執行項，不能只選擇成功案例。

### 12.5 何時加入進階方法

先完成一個已知答案的逆向案例與一個正向缺漏案例，才能判斷主要瓶頸究竟是來源解析、語意對齊、圖規則、候選排序還是驗證器。只有測量證明某一瓶頸存在，才評估專門演算法；不得因文獻中有某方法就預先加入架構。

## 14. 風險、限制與反例

1. **不可識別性：** 相同觀測可能對應多個內部結構；應保留多個候選或標記無法唯一判定。
2. **觀測偏差：** 文件過時、測試涵蓋有限、外部依賴不可觀察，都會使還原結果不完整。
3. **語意過度推斷：** 模型可能把常見設計模式、領域習慣或名稱相似當成證據；候選必須有目標或來源依據。
4. **假性閉合：** 圖中每個節點都有連線，不代表流程、狀態、資料與驗收真正閉合。
5. **近似失真：** 低秩或矩陣近似可能丟失關鍵語意，不能覆蓋原始證據。
6. **評估器盲點：** 確定性檢查只能覆蓋其規則；通過不能證明未建模的語意正確。
7. **循環與預算：** 圖探索若超出已設定上限，必須明確報告分析未完整，不能把「沒找到循環」等同「沒有循環」。
8. **版本污染：** 舊版 PASS 不得移轉到新候選；來源及規則版本必須精確記錄。
9. **成本爆炸：** 無界搜尋、反覆生成與全圖重算會耗費資源；每輪必須有預算與停止條件。
10. **引用過度外推：** 文獻只支持其方法、資料集與假設涵蓋的範圍；不能以外部研究結果宣稱本專案已提升準確率。

## 15. 結論與待決策事項

### 15.1 現階段結論

雙向結構還原與缺漏推導可作為現有 AI 理解框架的候選研究模組。兩種引擎共用現有資料契約與來源治理，但必須保留不同的推理基礎與驗收方式。研究的核心價值在於可追溯、能揭露未知、可比較候選以及避免無證據的必要性宣稱，而不是一次產生大量節點。

### 15.2 已能作出的裁決

- 共用現有 JSON／型別化關係圖，不建立第二套正式模型。
- 使用現行關係規則與影響政策；未知關係不能被靜默忽略。
- 分開候選必要性、證據品質、人工審核與發布生命週期。
- 程式化規則由獨立評估器執行；語意不確定性要明確呈現。
- 低秩、網路補全、Hankel 與 MDL 均採條件式評估，不預先設為必要依賴。
- 未有實測之前不宣稱精度、完整率、效率或加速成果。

### 15.3 仍需新證據才能裁決

- 現有節點與屬性是否足以表達候選及推導鏈，或將來需要受控擴充。
- 最適合的來源擷取粒度及跨來源對齊方式。
- 候選排序是否應使用量化分數；在校準前不採用未經驗證的加權總分。
- 哪些結構還原情境適合矩陣或網路補全。
- 雙向引擎是否能在固定預算內提高真值覆蓋、降低誤報，並把新增成本控制在可接受範圍。

任何決策都必須由案例結果、外部證據或明確需求推動，不得因文件完備便認定研究已驗證。
