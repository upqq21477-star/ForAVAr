## 摘要

本研究將 P2 的思考核心、AI 理解可視化與框架編輯介面，以及雙向結構還原／缺漏推導研究進行對照，並將前一輪逆向批評的 S 級、A 級缺口重新歸因。

**核心裁決：三者應採取「控制層—表示層—方法層」分工，而不是三套平行的思考系統。**

- **控制層：思考核心（Brain／Cognitive Decision）**：判斷真正目標、範圍、問題模型、未知與衝突、候選方法、資源／權限、成功條件、停止條件及下一步。其責任不是只產生一張圖，也不能自行宣告施工結果已通過。
- **表示層：AI 理解模型**：把已知、推論、假設、來源、需求、關係、條件、人工判定和版本外顯成可檢視與修正的資料，讓人類和後續工作可以引用同一個明確版本。它是思考可以使用的外部問題模型，不是思考本身。
- **方法層：逆向還原／正向缺漏推導**：從現有材料萃取結構，或從目標與約束提出缺口候選；方法負責產生候選和可查證的推導紀錄，不擁有目標裁定權、發布權或最終驗收權。

這份企劃主要解決的是：**AI 對使用者需求與系統狀態的理解原本隱含在文字、上下文和推論中，不易檢查、修正、追溯、版本化，也不容易可靠地交給下一個 AI／任務使用。** 它嘗試把這種理解轉成可治理的外部模型，讓錯誤更容易被發現和修正。

它不能單獨解決一般 AI 推理不可靠、使用者意圖辨識錯誤、外部事實錯誤或因果關係錯判。若沒有獨立的驗收依據、來源可重現性和結果回饋，視覺化模型可能只讓錯誤理解看起來更完整。這是本專案與思考核心必須接起來的因果關係。

本次將前一輪缺口歸納為五個根因群：  
1. **語意／認知分類不足**：要求、必要性、假設、證據、人工接受等不同維度可能被混用。  
2. **結構驗證與語意完整性混淆**：Schema 能驗證資料形狀，但不能單獨證明模型有足夠目標、需求承接及驗收路徑。  
3. **規則規格與候選程式的覆蓋落差**：有關係政策不代表規則已實作；有驗證器不代表完整閉環已執行。  
4. **來源／衍生／評估證據沒有形成可重現鏈**：來源 ID、推導紀錄、評估者與發布版本之間的連接仍不充分。  
5. **版本權威與來源版本辨識存在混亂**：ForAVAr 研究根目錄保留較早長版企劃，而權威工作目錄有精簡後主企劃；P2 的藍圖標題版本與運行契約內文版本也出現不一致。

修正方向不是大量增加功能、角色、資料欄位或測試文件，而是先固定語意、權威及完成判準，再把現有功能和驗收規則對齊。最小可行修正應包含：區分必要性的不同來源與邏輯強度、為不同用途定義範圍限定的閉合條件、將因果邊的證據要求落實到驗證規則、讓來源／推導可重現、改善發布輸出與警告完整性，以及用少量具區分力的反例驗收根因修正是否有效。

**最後裁決：研究方向與 P2 思考核心相容，但目前是「可以形成閉環的候選設計」，不是「已證明閉環的系統」。** 正式 Schema、驗證器、驗收閘門不應在本研究文件內被直接改寫；修正要先進入單一權威規格的變更流程，並以實際執行證據決定狀態。

## 2. 原始思考核心與本企劃的目標比較

### 2.1 思考核心的工作不是固定照流程走

P2 系統藍圖的核心設計是：每個重要工作開始前、重大變化後或工作收口時，Brain 先取得目前必要的資料，建模目標與環境，辨認 UNKNOWN／CONFLICT，比較候選方法，選擇運行模式及責任分工，之後才提出有範圍和驗收條件的工作方案。結果由獨立驗收責任確認；若結果偏離，需將觀察事實、根因假說及已確認根因分開，再把可重用修正蒸餾到正確層級。

P2 的 Brain 最小工作模型包含五個相互連結的區域：

1. **Problem Model：** 目標、問題類型、限制、成功／停止條件、風險與影響。
2. **Method Map：** 候選方法的用途、觸發條件、輸入／輸出、限制與備援。
3. **Resource Map：** 必要資料、來源位置、存取範圍、信任與成本。
4. **Epistemic State：** 目前已知、推論、未知及所需證據。
5. **Current Plan：** 現行工作、開放問題、假設、阻塞、目前方法、最近有效結果及下一個決策。

這五個區域是為了當前決策而組織的工作模型，不要求全部變成永久記憶庫或獨立 Agent。

### 2.2 將思考品質拆成五個檢查面向

以下將任務定向、問題表徵、推理生成、結果校驗、認知調節作為分析座標。它們是檢查本企劃是否支援思考核心的面向，不代表 P2 現有 schema 已把它們定義成五個獨立狀態欄位。

| 思考面向 | 思考核心要做到的事 | AI 理解框架能提供什麼 | 不能代替的責任 |
|---|---|---|---|
| 任務定向 | 釐清真正目標、範圍、非目標、硬限制、成功條件及停止條件 | 把明確需求、目標、限制及開放問題表示成可追溯模型 | 不能自行決定使用者真正想要什麼，也不能把候選功能升格為使用者需求 |
| 問題表徵 | 將模糊問題整理成可檢查的元件、關係、條件、假設、衝突與未知 | 提供結構化節點、型別化關係、來源及版本，允許人類校正 | 不能因模型內已有連線就推定沒有遺漏 |
| 推理生成 | 選擇適合的方法，從證據與約束產生可反駁的候選 | 逆向還原從現有材料提出結構候選；正向推導從目標提出可能缺口 | 不能裁決候選必然正確，也不能自行決定執行權限或架構變更 |
| 結果校驗 | 預先定義正確判準，以獨立方法檢查候選和實際結果 | 提供關係規則、追溯矩陣、驗收依據、差異與衝突資料的承載位置 | 不能只靠 Schema、同一個生成模型或圖形完整度證明語意正確 |
| 認知調節 | 在錯誤、新證據、環境變化或成本超限時回到 THINKING／RESEARCH，修正方法或停止 | 透過版本、差異、缺口、評估結果及來源保存可回饋的問題證據 | 不能自行決定重開研究、重審或改寫正式規則；仍須由思考核心按根因與停止條件控制 |

### 2.3 正確的架構關係

建議採以下單向授權、雙向回饋的分工：

- **思考核心決定何時、為何使用理解模型。**
- **理解模型承載當下的問題表徵，不成為全系統 Current 或思考模式控制器。**
- **雙向推理是可替換的方法能力，產生候選結構，不建立第二份權威模型。**
- **獨立驗證依預先定義的規則與驗收條件判定；人類負責不可由機械規則確定的語意裁決。**
- **實際結果與新證據可以觸發問題模型修正；只有被證實可重用的根因，才進入方法、契約或系統規則的演進流程。**

因此，這份企劃是思考核心的「外部問題模型與修正介面」及其資料治理基礎，不是用視覺化替代思考核心，也不是新的 Brain。將它當成一個完整的獨立大腦會重複實作目標判定、方法選擇、證據管理和自我校正，增加責任衝突。

## 3. 本企劃主要解決什麼問題

### 3.1 核心問題

原始長版主企劃將問題描述為：自然語言需求混合目標、限制、隱含假設、條件、依賴和未確認內容；純文字摘要難以呈現完整關係；單純圖形又可能使語意不明、來源消失、版本不同步或已確認內容被靜默改寫。主要目標是讓 AI 的理解可被人類檢查和修正，並以明確版本交給後續 AI 使用。

精簡後的現行主企劃保留了同一核心：正式語意資料只有一份，多視圖只呈現同一模型；重要內容要有來源、狀態與版本；修改要有基準、差異及下游影響；尚未確認的內容不能被呈現為已接受。

所以本企劃的首要問題不是「如何畫圖」或「如何找到所有功能」，而是：

> **如何把 AI 當下對使用者需求、系統結構及未解問題的理解，轉成可檢查、可修正、可追溯、可比較、可明確交付給下游任務使用的外部模型。**

### 3.2 它能直接解決與不能直接解決的問題

| 問題 | 本企劃能提供的直接改善機制 | 無法單獨保證的事 |
|---|---|---|
| 上下文遺失或跨任務交接錯版本 | 正式模型、穩定 ID、版本基準、明確匯出契約 | 下游 AI 一定完整載入或正確使用所有相關資料 |
| 使用者無法看出 AI 對需求的理解 | 顯示節點、關係、來源、未知、衝突及變更 | 使用者必定能辨識所有語意錯誤 |
| AI 把推論誤當事實 | 命題類別、證據狀態、來源與人工審核分開 | 模型一定正確分類所有推論或找出所有錯誤來源 |
| 系統結構漏項或關係矛盾 | 逆向萃取、正向缺口候選、引用／關係／閉合檢查 | 在缺少真值、完整來源或適當測試時證明不存在其他缺項 |
| 變更造成下游內容過期 | 依關係政策計算受影響範圍、產生可解釋差異 | 所有傳播政策已正確定義或已經程式驗收 |
| 因果主張被錯誤確定化 | 因果／影響關係型別，證據和假說狀態，支持／反證鏈 | 連線本身足以證明因果；仍需符合任務的觀測與驗證方法 |
| 思考方式本身需要改進 | 將失敗和模型差異以證據交回思考核心 | 光有模型就能自動修正推理策略或根因 |

### 3.3 本企劃的價值來自人機校正閉環，而不是資料量

模型節點增加、關係變多、資料欄位更細，不代表理解品質更高。真正價值要從三個結果看：

1. 是否讓原本隱藏的歧義、假設、反證和缺漏變得可見。
2. 是否讓人類能以更少的錯誤修正正式模型，而不是只調整畫面。
3. 是否讓下游工作得到可追溯且與實際結果相符的版本。

如果沒有使用者任務、已知答案案例或可執行不變條件，這些仍是待測的設計假說，不能由文件完整度推定已實現。

## 4. 問題、症狀與根因的因果關係

### 4.1 系統性因果鏈

本企劃預期支援的正向因果鏈為：

使用者意圖／現有系統材料
→ 思考核心定義目標、邊界與證據需求
→ 建立可追溯的問題模型
→ 逆向萃取或正向提出缺口候選
→ 確定性規則／獨立評估／必要人工審核
→ 修正並發布明確版本
→ 下游任務按指定版本使用
→ 實際結果、偏差及新證據回饋
→ 思考核心分析根因並決定是否更新模型或方法

其中每個箭頭都需要明確的輸入、輸出、判定條件及失敗語義。若任一段沒有證據，就不能把整條鏈描述為已閉合。

### 4.2 同一條鏈的失敗型態

| 斷點 | 直接症狀 | 根因 | 可能後果 |
|---|---|---|---|
| 意圖 → 問題模型 | AI 把偏好、假設或推論當成明確要求 | 任務來源、要求義務、推論與未知未充分分開 | 問題一開始就被錯誤定義，後續完美驗證也只會驗證錯誤目標 |
| 問題模型 → 候選生成 | 產生大量常見功能，卻無法指出哪些真正支援目標 | 缺漏候選缺少必要性定義與候選淘汰契約 | 架構膨脹、設計偏移、重複職責 |
| 候選 → 驗證 | 候選有 ID／連線便看似有效 | 以結構可解析替代語意閉合，或規格規則未落實到程式 | 空模型、未經支持的主張、缺少驗收路徑仍可能被過度確定化 |
| 驗證 → 發布 | 版本 marker 一致，但輸出正文或警告可能已變 | 發布紀錄及匯出驗證只覆蓋部分一致性條件 | 下游 AI 取得錯誤版本或看不到重要不確定性 |
| 發布 → 下游使用 | 將未驗證候選當成確定事實使用 | 證據狀態／警告在匯出、上下文剪裁或版本轉接時遺失 | 錯誤被放大且難以追溯 |
| 結果 → 系統改進 | 發現錯誤後重複修補，卻沒有修正機制 | 缺少觀察事實、根因假說、反證、區分測試和蒸餾條件的閉環 | 同類錯誤反覆發生，維護成本提高 |

### 4.3 根因群，而不是把每個缺陷當成獨立功能

前一輪批評中的多個問題並非互相獨立。例如「必要性混淆」「空模型發布」「因果邊不受證據約束」都指向：模型的正式契約和候選驗證器沒有完整表達／強制「這份模型聲稱已完成什麼，以及哪些結論可被宣稱」。若每個症狀只新增一條規則，而不先清楚定義語意，可能產生更多互相衝突的局部規則。

建議先採以下根因層次：

1. **認知／語意根因：** 概念本身未分開，或判定詞太粗糙。
2. **契約根因：** 已有概念，但沒有明確輸入、輸出、狀態、條件或允許／禁止轉換。
3. **落地根因：** 契約已寫明，但 validator／exporter／review flow 沒有實作該規則。
4. **證據根因：** 有程式碼或文件，卻無法取得實際執行結果、真值或可重現測試。
5. **來源治理根因：** 權威檔案或版本標記互相矛盾，無法確定比較的是哪一個基線。
6. **演進根因：** 修正沒有回到正確權威位置，或將一次性假說永久固化。

這種分層能避免把所有缺口都當成「再加一個功能」處理。

## 5. 前一輪缺口與思考核心的對照矩陣

### 5.1 S 級缺口

| 前一輪問題 | 對應思考面向 | 根本原因 | 修正方向 | 判定方式 |
|---|---|---|---|---|
| S-01 必要性語意混淆 | 任務定向、問題表徵、推理生成 | 「使用者明確要求」「政策／標準約束」「相對方案必要」「邏輯必要」被壓成單一必要性判定 | 分開記錄義務來源、必要性適用條件、證據／推導依據及人工決策；不可直接以來源存在證明邏輯必要 | 用有替代方案的反例測試：系統是否仍保留明確要求，但拒絕宣稱它是唯一必要方案 |
| S-02 缺少最低語意閉合門檻 | 問題表徵、結果校驗 | Schema 只檢查資料形狀，發布規則未充分表達所宣稱用途的最低完整條件 | 依模型的預期用途定義閉合條件；發布時檢查目標／範圍、已確認要求、承接／豁免及必要驗收路徑；不能只用節點數門檻 | 空模型、只有目標的草稿、正式交付模型分別測試，避免將合法草稿與非法發布混為一談 |
| S-03 因果邊缺少完整證據閘門 | 推理生成、結果校驗 | 關係規則指出因果／影響主張需要證據狀態，但候選驗證器未將條件落到 edge 層 | 把因果邊視為主張；規定必要證據狀態、來源及條件；未證成者保持假說，不因 accepted 或連線存在就升格 | 分別測試無來源因果邊、有來源但不支持的因果邊、待驗假說與已有驗證依據的邊 |
| S-04 來源存在不等於推導可重現 | 問題表徵、結果校驗、認知調節 | source ID 的存在被當作足夠追溯，卻未定義何時需要來源定位、版本、內容識別與產生活動 | 依來源類型定義可定位最低要求；對推導結果保留輸入 revision、來源定位／雜湊、規則／工具版本、候選輸出與評估結果；不保存隱藏思維鏈 | 對只有 label 的來源、可定位來源、固定版本來源及工具推導來源做差異測試 |

### 5.2 A 級缺口

| 前一輪問題 | 根因層 | 修正方向 | 對整體系統的影響 |
|---|---|---|---|
| A-01 固定循環探索上限可能阻擋無環長鏈 | 演算法／資源控制 | 若目標是判斷是否存在禁制循環，採取適當的線性圖算法或強連通分量；若要列舉循環，限制輸出的代表路徑和預算，不為了完整列舉所有簡單循環而無界搜尋 | 減少誤阻擋及無效計算，同時維持「搜尋不完整不得當作無循環」 |
| A-02 Markdown marker 不證明正文與 JSON 相符 | 契約／發布落地 | 使用固定版本的確定性 exporter，重新生成並比較正文；或解析輸出後比較語意模型。marker 只能作版本聲明，不能單獨作內容一致性證明 | 防止舊正文換新 marker 的版本假一致 |
| A-03 非循環警告可能沒有完整保留 | 契約／發布落地 | 先定義警告類別、阻擋級別、人工確認規則及下游保留政策；對發布報告做集合層級的警告完整性檢查，而非只核對一類警告 | 防止未驗證與警告在匯出或下游上下文剪裁時消失 |
| A-04 attributes 可與正式欄位重複衝突 | 契約／資料治理 | 保留正式欄位名稱清單，拒絕在同物件 attributes 中重複正式語意；必要的領域擴充使用受控 namespace 或擴充 schema | 避免不同消費端讀到互相衝突的狀態 |
| A-05 VLD-303 人工審核缺少可執行觸發契約 | 治理／交接 | 把不可機械判定的規則變成可定位的人工審核程序：觸發來源、審核責任、被審物件、決定、理由及結案狀態 | 不假裝人工規則已由程式覆蓋 |
| A-06 需求／實作／驗收沒有完整閉合檢查 | 問題表徵／驗收契約 | 對已確認目標與需求定義適用的承接、驗收或明確豁免；區分草稿孤兒、待補項與正式交付缺項 | 改善正向／反向需求追溯，而不是一律禁止孤立節點 |
| A-07 影響政策存在不等於影響分析已實作 | 證據／責任邊界 | 明確區分政策定義、算法程式、呼叫接線與實測結果；只有後三者具備證據，才可標記相應執行能力 | 防止設計文件取代實際功能證據 |
| A-08 release record 欄位未形成完整契約 | 發布／版本治理 | 為發布紀錄定義獨立、版本化的資料契約；核對必填欄位型別、實際決策參照、warning ID 集合、版本及不可變修訂 | 發布閉環可重現，警告和人類決策不只是字串 |

### 5.3 哪些問題是同一根因的不同表現

- S-01、S-02、A-06 同屬「需求／必要性／完整性語意未形成可判定契約」。
- S-03、S-04、A-03、A-05 同屬「證據、來源、人工判定與發布之間的責任鏈沒有完全落地」。
- A-02、A-08 同屬「發布資料的內容、宣告修訂、審核紀錄及實際輸出沒有完全綁定」。
- A-01 單獨屬於「圖算法與成本上限的設計問題」，不應把它修成另一個語意狀態。
- A-07 是重要的證據層級問題：規則設定、程式存在、程式接線、實際執行是不同事實，必須分開記錄。

因此，優化應以這些根因群來設計修改批次，而不是照 S-01、S-02、A-01 的列表各自增加新的永久功能。

## 6. 邏輯鏈與兩種閉環應如何接通

### 6.1 必須分開管理的兩種閉環

**閉環一：理解模型的語意閉環**

使用者意圖／現有來源 → 問題模型 → 結構候選 → 人類修正／規則驗證 → 明確版本 → 下游任務取用 → 實際結果／新證據 → 更新該模型

它處理的是某個框架或問題模型本身是否準確、可追溯、可用於指定任務。

**閉環二：思考核心的認知調節閉環**

偏差／矛盾／未知 → 觀察事實 → 有限根因假說 → 支持／反證 → 區分假說的最小測試 → 根因判定或保留 UNKNOWN → 選擇修正層級 → 驗收修正效果 → 蒸餾可重用規則／停止

它處理的是「為什麼本次理解或方法失敗」以及「是否需要修正思考方法、資料契約、能力、責任或驗收機制」。

兩個閉環相接，但不合併。模型內容錯誤可能只是一次輸入／意圖辨識錯誤，不必然表示認知架構有缺陷。只有可重複、可泛化且有證據支持的機制問題，才應進入永久方法或架構演進。

### 6.2 從思考核心到正式模型的最小交接

P2 的運行契約已要求重要研究包含來源、支持證據、反證及可區分假說的測試；工作計畫則包含目標、範圍、接受條件、風險、成本、權限與停止條件。應讓這些條件成為理解模型生成／補全時的輸入，而不是要求理解模型自己發明或默認它們。

研究方法產出的最低可稽核紀錄建議包含：

- 此次工作要回答的問題及預期用途。
- 明確輸入版本與來源定位。
- 被使用的規則／工具版本及其適用限制。
- 產出的候選、前提、假設與待決事項。
- 哪些規則可由程式檢查，哪些需要人工裁決。
- 實際執行的驗收方式與結果；未執行項需有明確狀態。
- 產出或修訂的正式模型 ID／revision。

這是推導活動的工程紀錄，不是要求保存模型隱藏思維鏈，也不應因為欄位齊全就把推論升級成已證實事實。

### 6.3 「閉合」必須是針對用途的聲明

本研究不建議新增一個全域的 complete=true，也不建議以固定節點數、邊數或「所有節點都已連線」判定完整。應先指定模型用途和本次宣稱的範圍，然後分別判斷：

- **結構閉合：** 固定 Schema、ID、引用與適用關係規則皆通過。
- **需求追溯閉合：** 已確認目標／需求有適用的設計承接、驗收方法和結果，或有明確豁免。
- **證據閉合：** 高影響主張有可定位依據及適用性評估；其他未知與假說仍被明確標記。
- **行為閉合：** 指定行為／情境已有適用的測試、演示、檢查或分析證據。
- **發布閉合：** JSON、Markdown、規則版本、警告及審核決策對應同一實際 revision。
- **未完／不可判定：** 需要的資料、範圍、測試或資源不足；不能把未知變成 PASS。

這些是建議的概念分類，不是已核准的正式欄位或新狀態值。下一步應先確認它們是否能以現有欄位、release record 與規則表表達，再考慮任何契約變更。

## 7. 系統性修正方案：不重複新增能力

### 7.1 修正一：把「要求義務」與「邏輯必要性」分開

每個候選的必要性至少需能回答兩件不同的事：

1. **為什麼要保留？** 例如使用者明確要求、適用的政策／標準、目標約束、現有方案依賴，或尚未驗證的假說。
2. **必要性強度到哪裡？** 例如明確要求但可被替代、在目前選定方案下必要、在明列假設下可證明必要、可選偏好或未知。

「使用者要求 A」可足以讓 A 成為本次需求，但不能直接證明 A 是唯一可滿足目標的技術。這能同時避免違反使用者明確要求，也防止把方案偏好錯誤永久化。

不建議立刻引入未校準的必要性加權分數。先採取可解釋的分類、來源／假設與反例，再依有限案例判斷是否真的需要量化排序。

### 7.2 修正二：定義用途限定的最低語意契約

不是所有合法草稿都必須有相同規模。模型的 intended use 可能是：空白模板、初始草稿、正在研究的候選架構、正式需求框架、已驗收發布版本。各用途的最低要求應不同。

正式發布時，應以模型本身聲稱交付的用途作為驗收依據，檢查：
- 所聲稱的目標／範圍是否明確；
- 已確認的需求是否被承接，或有清楚的豁免／未決狀態；
- 需要驗收的要求是否有可定位的驗收依據；
- 關鍵主張是否有適用的來源／假設／證據狀態；
- 未執行、未知、預算耗盡或受阻項目是否仍保留在交付結果中。

這比「陣列不能為空」精確，因為空白模板或早期草稿可合法不完整，而宣稱已完成的發布版本不能把同樣缺口隱藏起來。

### 7.3 修正三：讓來源治理覆蓋推導活動

來源可重現性應依來源類型決定，而不是對所有來源一律強制 URL：

- 對 Git 檔案：使用 repo／path／commit 或不可混淆的 revision，必要時保存內容 SHA。
- 對外部網頁／文件：使用 URI、定位資訊、存取日期和適用時的摘錄或內容摘要。
- 對使用者意圖：保留可定位的訊息／工作引用或穩定的輸入版本，不把 AI 改寫誤當成原始要求。
- 對模型推論／規則推導：記錄所用輸入 revision、方法／規則版本、候選輸出及評估結果；不要求存下隱藏思維鏈。
- 對計算／測試：保留輸入、計算方法或程式版本、參數、預期與實際結果。

重要的不是每筆來源都要長，而是讓後續工作能回答：這個內容從哪個材料或活動而來、用的是哪個版本、為什麼它支持目前的主張，以及哪些轉換仍未重現。

### 7.4 修正四：將因果關係當成受治理的主張

在本專案中，causes／influences 不是普通裝飾性連線。若將其用作已成立的事實，就必須有適用條件與相應證據；若只是設計假說，就應明確保留未驗狀態，不能因為人類接受某個設計或模型有一條邊而直接升格。

建議流程：
1. 先說明因果主張及適用範圍；
2. 保存支持、反證及必要條件；
3. 指出此主張是觀察結果、工程假說還是已有驗證；
4. 使用與問題相稱的證據方式，例如可重現測試、介入／移除測試、觀測資料或人工審核；
5. 在下游匯出時保留未決條件，不將因果線直接渲染成「已證實」。

這不表示所有工程關係都要使用正式的統計因果推論；而是只有在沒有相稱證據時，降低主張強度，不能把存在關係等同證明因果。

### 7.5 修正五：依目的選擇圖算法，避免以枚舉所有循環作為預設

候選驗證器的 cycle enumeration 使用固定 cap 500，並重複以每個節點作為起點探索。對 33 個節點、32 條邊、排序方向一致的無環長鏈，按目前控制流程可推得累計探索可能到達：

32 + 31 + … + 1 = 528

因此有可能觸發 VLD-407，儘管沒有循環。這是靜態算法推導，還未執行測試。

修正原則：
- 如果目標是檢查某一關係家族是否有禁制循環，應用適當的拓樸檢查／強連通分量方法，避免枚舉所有簡單循環。
- 若警告需要展示循環路徑，應規定代表路徑的輸出策略與有界預算。
- 搜尋超額仍必須標示 INCOMPLETE 並阻擋依賴該結果的發布；不能將預算限制刪掉來取得表面 PASS。

這是算法任務適配問題，不應靠無條件提高常數掩蓋。

### 7.6 修正六：建立發布輸出與警告的實際一致性契約

Markdown 中的 revision marker 只是版本聲明，不能證明正文確由當前 JSON 生成。建議使用固定版本的確定性 exporter，在發布驗證時重新生成或比較輸出；如果採解析比對，則需有明確的語意對應規則。

同樣地，warning 不只是 CLI 畫面文字。要定義哪些警告必須阻擋、哪些可以經人工核准、哪些需隨發布輸出及下游上下文保留；並對本次實際產生的 warning 集合與 release record 進行完整比對，而不是只核對部分警告。

attributes 的擴充規則也要能拒絕與正式欄位重複的 key。正式欄位有唯一語意權威，不能讓一份資料同時出現 review_status=accepted 與 attributes.review_status=rejected。

### 7.7 修正七：人工規則必須有明確的操作入口

人工審核不能只是一條標記為 manual review required 的規則。它至少需要定義：
- 觸發方式和提出者；
- 要審查的物件／關係與規則 ID；
- 審查需要的來源或資訊；
- 決策、理由及未解項目；
- 誰有權核准、拒絕或豁免；
- 審核結果如何進入發布閘門。

不一定需要立即導入複雜的審核事件資料庫；可以沿用現有 Git／release record 形式，只要決策可定位且可重現。不要把無法自動判定的項目假裝由 LLM 評語或欄位值代替。

### 7.8 修正八：把需求／設計／驗收的雙向追溯變成按用途可判定的規則

每個重要目標／需求應能追到負責的設計或機制、驗收方式與結果；每個重要設計元素也應能反查其服務的目標，或具備明確的技術／治理理由。

但不應把所有孤立節點一律判為錯誤：
- 草稿中的孤兒可以是待分類內容；
- 正式需求沒有承接或驗收依據，可能是發布阻擋；
- 有意不實作的需求應保留明確豁免／排除理由；
- 研究假說尚未連到正式設計，不代表必須立即施工。

閉合規則應以物件類型、狀態、模型用途及發布聲明為條件，避免以「圖連得漂亮」或「所有節點都需有邊」取代真正的需求分析。

## 8. 有限修正與驗收順序

### 8.1 第一階段：只定義語意，不改程式

先確認以下共用定義：
1. 使用者明確要求、外部約束、方案內必要、邏輯必要、可選、假說和未知如何區分；
2. 哪些內容屬於意圖模型，哪些屬於候選推導紀錄，哪些屬於實際驗收結果；
3. 不同用途的模型何時可以發布；
4. 哪些來源類型需要哪些可定位資訊；
5. 哪些關係需要證據／條件，哪些可以是待驗假說；
6. 哪些警告必須阻擋，哪些需人工核准，哪些需隨版本傳遞。

本階段的產出是可對照現有 Schema／規則的定義表，不新增永久角色或第二份驗收規格。

### 8.2 第二階段：用最少反例驗證根因

先以少數反例測試是否擊中根因，然後才決定需要增加哪些正式規則：

| 優先 | 案例 | 要驗證的設計疑問 |
|---|---|---|
| P0 | 空模型、合法草稿、正式交付三種用途 | 是否能區分「允許不完整」與「不應宣稱已完成」 |
| P0 | 明確要求但存在等效替代方案 | 是否把要求義務誤當成邏輯唯一必要性 |
| P0 | causes／influences 無來源、來源不支持、待驗假說、已有驗證依據 | 因果主張是否被正確標記及治理 |
| P0 | source 只有 label 與 captured_at、可定位來源、固定 revision／hash | 來源引用是否足以重現所聲稱的推導 |
| P1 | 33 節點無環長鏈與真正的關係循環 | cycle cap 是否導致誤阻擋；新算法是否保留 fail-closed |
| P1 | 修改 Markdown 正文但保留匹配的 revision marker | 發布驗證是否能發現內容與聲明版本不一致 |
| P1 | 移除非循環 warning、attributes 重複正式欄位、release decision reference 不存在 | 警告、擴充欄位與人工決策是否真的受控 |

先核對現有唯一案例清單是否已覆蓋；只有缺失的案例才加進現有清單，不能另建第二份平行驗收計畫。

### 8.3 第三階段：將確認的修正寫入正確權威位置

只有完成語意裁決後，才依實際改動更新：
- 主企劃：目標、用途和成功條件；
- 資料契約／Schema：正式可表達的欄位、型別及狀態；
- 關係登錄表：關係的適用語意、循環、影響及證據要求；
- 跨物件規則／驗證器：可機械判定的條件；
- 案例清單與唯一驗收計畫：要測的輸入、預期和可定位結果；
- 演進與驗收總結：根因、修正、實際結果和剩餘風險；
- 基線清冊／README：目前權威 SHA、入口及阻塞狀態。

不應把所有設計概念都塞進 Schema；不應把所有規則都變成 AI 角色；不應把每次研究都變成一份永久文件。

### 8.4 第四階段：有限執行、修補、一次完整回歸

現行工作目錄記錄的驗證器候選狀態為 BLOCKED／NOT_RUN，UI 規劃閘門未達成。因此本研究不能將任何修正標為已驗收。可執行環境恢復後，按現有唯一驗收計畫核對現行候選 SHA、執行必要反例、記錄輸出及退出碼；失敗按根因分組、做一輪針對性修正，再執行一次完整回歸。若仍有失敗或環境阻擋，停止並保留證據，不無限重試。

### 8.5 第五階段：只用一個垂直切片確認端到端價值

在資料與驗證契約穩定後，才研究最小垂直切片：
- 一個已知答案的逆向還原案例；
- 一個從粗略目標推導缺漏的案例；
- 使用同一個正式模型、候選生成／驗證／人工修正／版本輸出的流程；
- 預先固定真值、評分方法、允許的未知和成本量測。

成功指標應是缺漏與誤報、來源／推導可追溯性、需求承接與驗收路徑、使用者修正能否留在正式版本，以及成本；不能用新增的節點數、生成文字流暢度或第二個 LLM 的主觀分數替代。

## 9. 風險、非目標與禁止的錯誤修法

### 9.1 不要把此企劃升格成第二套思考系統

不應新增另一個永久 Brain、另一份 Current、另一套角色路由或另一個版本權威。雙向還原／缺漏推導應是可在 Method Map 中調用的能力／方法，按任務與證據需求啟用。

### 9.2 不要用固定完整性清單假裝能涵蓋所有系統

每種用途、領域和操作環境不同。固定清單可以提供起始檢查，但必須依目標、非目標、情境、品質要求及已知風險做範圍限定。不能宣稱「檢查了所有類別」就證明沒有缺口。

### 9.3 不要用欄位存在代替語意真實

- 有 provenance_refs 不等於該來源支持主張。
- 有 evidence_status 不等於判定方法正確。
- 有 accepted 不等於外部事實已被驗證。
- 有 causes 邊不等於存在因果證據。
- 有 release record 不等於其內容／參照均有效。
- 有 JSON SHA 或 Markdown marker 不等於兩份實際內容相同。
- 有程式碼不等於已執行，有測試定義不等於 PASS。

### 9.4 不要要求保存隱藏思維鏈

要的是可稽核的決策依據與推導活動資料：用到哪些版本、依據哪些來源、採用何種規則／方法、生成了什麼候選、怎樣評估、還有什麼未知。這與逐字保存模型的內部思維不同，也更有利於隱私、精簡與可重現。

### 9.5 不要以無止境研究取代有限驗收

只要根因和可區分測試已足以裁決某一方案，就停止該研究分支。若缺少執行環境，明確記錄 BLOCKED；不要以更多文檔、更多假想測試或更多外部算法清單冒充進度。

## 10. 外部研究對照

### 10.1 需求分析：需要個別與整體檢查

NASA 的 SWE-051 要求軟體需求分析涵蓋正確性、一致性、清晰度、完整性、可追溯性、可行性、可驗證性及可維護性，並建議同時檢查每項需求和需求集合。其指引也要求雙向追溯、核對不必要需求以及確認每項需求是否有可行的驗證方法。  
來源：[NASA SWE-051 — Software Requirements Analysis](https://swehb.nasa.gov/spaces/7150/pages/16450593/SWE-051%2B-%2BSoftware%2BRequirements%2BAnalysis)。

**對本企劃的結論：** 只檢查每個節點是否合法還不夠；但也不能把清單通過宣稱為絕對完整。必須以用途、場景與要求集合為單位制定可核對的閉合條件。

### 10.2 架構還原：多工具和真值基準的價值

Schneider 等人於 2025 年比較微服務架構還原工具；研究辨識 13 個工具，其中 9 個能執行，並以 ground truth 評估輸出。其資料集範圍內，最佳單一工具整體 F1 為 0.86，特定四工具組合達 0.91。  
來源：[Comparison of static analysis architecture recovery tools for microservice applications](https://doi.org/10.1007/s10664-025-10686-2)。

**對本企劃的結論：** 多來源／多方法可能補足單一工具的盲點，但成效必須用本系統的真值與適用任務驗證，不能直接採用論文 F1 作為預期。F1 只適用於有清楚標註的特定輸出，不可用來評估全部的語意理解。

2026 年的 ArchAgent 研究結合靜態分析、程式碼分段、依賴上下文及 LLM 合成，並報告 dependency context 對其架構還原效果有幫助。  
來源：[ArchAgent: Scalable Legacy Software Architecture Recovery with LLMs](https://doi.org/10.1109/ICASSP55912.2026.11462552)。

**適用限制：** 它支持將工具證據與 LLM 語意合成組合成候選流程的研究方向；不證明本企劃的資料契約、必要性分類或發布閘門已經正確。

### 10.3 資料來源：PROV 的實體／活動／責任主體區分

W3C PROV-DM 將 provenance 描述為與資料產生有關的實體、活動和責任主體資訊，可用來評估資料品質、可靠性與可信度。  
來源：[W3C PROV-DM](https://www.w3.org/TR/prov-dm/)。

**對本企劃的結論：** 來源指向、推導活動、方法版本與產出修訂之間應有清楚關係。但沒有必要為第一版完整導入 PROV 全套模型；可以用最小、可重現的衍生紀錄滿足已確定的用途。

### 10.4 LLM 評估：獨立評估器不會自動成為真值

Mohammadi 等人的 2025 年 LLM Agent 評估調查整理了不同評估目標與評估流程，包括資料集、基準、指標與工具，並指出長時程互動、可靠性與安全性等情境仍有挑戰。  
來源：[Evaluation and Benchmarking of LLM Agents: A Survey](https://doi.org/10.1145/3711896.3736570)。

2026 年的 LLM-as-a-judge 調查將評判一致性、主觀性與可靠性列為重要研究問題，並提出評估 judge 自身可靠性的框架。  
來源：[A Survey on LLM-as-a-judge](https://doi.org/10.1016/j.xinn.2025.101253)。

**對本企劃的結論：** 第二個 LLM 可以協助發現語意風險，但不是獨立真值來源。重要結論需要預先定義的判準、可信的真值／觀測、可執行不變條件或明確的人工裁決。

## 11. 結論與決策

### 11.1 主要研究結論

1. 本企劃的核心目標是建立可檢查、可修正、可追溯、可比較及可交付的外部問題模型；不是打造另一個大腦。
2. 它與 P2 思考核心的正確關係是控制層決定如何思考與驗收，表示層保存被理解的問題，方法層產生可追溯的結構候選。
3. 前一輪 S 級與 A 級問題彼此有因果關係，主要集中於語意分類、最低閉合契約、來源／推導可重現性、因果證據閘門、發布輸出一致性及規則實作落差。
4. 修正方向應先處理語意和契約，再修正機械驗證與發布流程，最後使用有限案例驗證端到端價值；不要先增加功能、角色或更複雜的演算法。
5. 要把問題回饋到思考核心，必須分開「本次模型錯誤」與「可重用的系統根因」。只有已證實可泛化的機制缺陷才應蒸餾為長期規則。

### 11.2 建議的實施決策

- 保留現有主企劃、資料契約、關係規則、有限驗收計畫與唯一結果總結，不建立重複權威。
- 先審定必要性分類、用途限定的語意閉合、來源／推導紀錄及因果主張的證據門檻。
- 檢查現有案例清單，將本報告的最小反例整合到原有清單，而不是新建另一份測試系統。
- 依現行停止條件，候選程式與發布流程仍須實際執行驗收；在取得執行證據前，維持 BLOCKED／NOT_RUN。
- 只有當雙向垂直切片在固定真值、驗收規則與成本預算下顯示實際價值，才考慮把該方法提升為正式能力。

### 11.3 當前狀態與剩餘未知

本文已完成文件與源碼的靜態對照、根因分組、外部研究對照和修正方案設計，但尚未執行候選驗證器、發布流程或使用者任務測試。前一輪觀察到的 P2 版本標記不一致也仍是只讀來源中的待核對事項；本研究沒有修改 P2。

**最終裁決：目前研究架構在概念上可與 P2 思考核心整合，但未形成可由證據支持的完整運作閉環。最有效的優化不是繼續擴大架構，而是先讓目標、候選、證據、必要性、驗收、版本及根因回饋之間的關係可判定、可重現、可被反例否證。**
