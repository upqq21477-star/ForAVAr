# 1. 企劃摘要

本企劃提出將 P2 的底層運作收斂為一套非常簡單的「封包式問題解決流程」。最上層不再依照 Brain、Central、Role、Runtime、Knowledge、Assurance 等既有責任名稱拆成多套並列系統，而是先以一條穩定的因果流程處理問題，再將角色、技能與系統能力映射到流程節點。

核心定義：

- **H0：解決問題。**
- **H1：理解問題 → 決定做法 → 執行做法 → 檢查結果 → 修正與結案。**
- **H2：每個環節的基本步驟。** H0–H2 是固定骨架，保持簡單、穩定。
- **H3：真正需要分歧的位置。** 例如選擇能力、判斷是否研究、選擇 BUILD／REPAIR／EXTEND／REBUILD、決定回退到哪一步。分歧以明確條件形成分支；完成選擇並滿足接受條件後，回到同一條主流程。
- **封包：** 每一次規劃、藍圖、施工、驗收或修正，都視為一次有明確目標、輸入、動作、輸出與下一步的問題處理單位。
- **中控：** 只負責定位封包、檢查必要條件、派送工作、收取結果、更新狀態及推進／阻止流程，不重新推理整套架構。
- **功能啟用：** 功能不是因為 AI 想到它就被調用，而是必須符合其觸發條件、輸入、權限及資源規則。
- **資料生命週期：** 封包閉環時，保留最終結果、關鍵決策與必要證據；把下一步需要的資料傳遞出去；讓不再有價值的暫存與重複資料退場。

本方案要降低的，不是功能數量，而是 AI 每次執行任務時必須自行重建、記憶與同步的複雜關係。系統可以保有多種功能，但底層只使用一套流程、一套封包約定，以及可被檢查的啟用條件。

**重要界線：** 本文件只完成概念架構整理與既有功能的初步歸位。它不表示 P2 已將 F01–F30 全部接線，也不表示程式測試、整批驗收或真實 Runtime 已通過。既有功能狀態仍須以 P2 儲存庫中的 Current、功能實作／證據矩陣及當前執行證據為準。

# 2. 問題定義與設計目標

## 2.1 現有設計容易發生的問題

1. 同一功能可能分別出現在功能樹、角色圖、系統圖及因果圖中，各自描述、各自維護。
2. AI 需要自行記住各圖之間的對應關係，局部修改後容易漏改其他視圖。
3. 功能名稱或角色名稱容易被誤當成啟用理由，導致過早、重複或不必要的調用。
4. 每個工作階段可能形成不同流程，規劃、藍圖、施工、驗收各自複雜化。
5. 狀態欄、交接契約與進度記錄容易隨功能增加而膨脹，讓中控本身成為另一套複雜系統。
6. 上下文、臨時研究與施工產物缺少一致的閉環與退場規則，長期累積成噪音。
7. 文件寫入、程式存在、推理推定、局部測試及真實執行容易被混作同一種「完成」狀態。

## 2.2 設計目標

- 只保留一條最上層問題解決主線。
- H0–H2 固定、簡單、可重複；第三層以後才處理條件分支與具體方法。
- 所有功能各自有唯一主要歸屬，不因被多個環節使用而複製節點。
- 技能／功能只能在觸發條件和前置條件成立時啟用。
- 每個封包都能看出目前位置、需要什麼、做了什麼、產生什麼以及下一步去哪裡。
- 中控採用最少狀態與確定性的推進規則。
- 任務失敗時只回到真正受影響的節點，不無條件重做全部工作。
- 封包間透過引用傳遞必要上下文，而非不斷複製全文。
- 封包閉環後，能集中整理結果、保留必要證據並清理無用資料。
- 在不改寫使用者已確認的目標、權限、成本限制與證據標準的前提下，降低調用錯誤、重複工作及上下文成本。

## 2.3 非目標

- 不要求把所有功能合併成一個巨大模組。
- 不取消既有責任分工、權限界線或獨立驗收。
- 不把因果、狀態、角色責任與執行證據混成一個欄位。
- 不要求每個 H2 步驟都生成獨立檔案；只有需要持久化、交接或驗收的結果才建立正式封包記錄。
- 不以「流程簡單」為由略過權限、成本、安全或證據檢查。
- 不在本提案階段直接修改 P2 程式、Current、測試名冊或唯一施工藍圖。

# 3. 核心原則

## 3.1 一條流程，不是多套平行流程

規劃、藍圖、施工、驗收與修正都使用同一套問題處理規則。它們的工作內容不同，但封包運作方式相同。差異放在輸入、動作、接受條件和輸出，不再各自發明狀態機與交接流程。

## 3.2 H0–H2 固定，H3 才分歧

H0–H2 是全系統共用的骨架。遇到不同方法選擇、環境、工具、角色或回退需求時，才在 H3 或更深層展開分支。分支必須說明條件與結果，不能只列一堆功能名稱。

## 3.3 樹形位置表示歸屬，條件及封包引用表示流程

樹狀層級回答「這個步驟屬於哪裡」。前置條件、啟用條件、上一個封包與下一個封包的引用，回答「何時可以做、為什麼往下一步」。不另外維護一套內容重複的關係圖；需要的因果連結以節點 ID、封包 ID 和明確條件引用表示，所有圖表都從權威資料生成。

## 3.4 一個功能只建一次，跨環節使用以引用連結

例如 F21 可能影響理解、規劃、施工和回退，但它仍只有一個正式功能定義。其他位置引用它，不複製內容、不建立第二個同名功能。

## 3.5 先確認位置，再確認選項

新功能或新技能先找到其上層目標與主要流程位置，再檢查是否已有相同能力。找不到合理位置、觸發條件或輸出契約時，不直接新增正式功能，而是保留為待評估提案。

## 3.6 條件不成立就不啟用

候選能力只有在觸發條件成立、必要輸入存在、權限與資源限制通過、且沒有未處理衝突時，才可以進入可執行範圍。AI 判斷「可能有幫助」不能取代硬性條件。

## 3.7 狀態與證據分離

狀態表示封包目前走到哪裡；證據表示我們為何能相信某個結果。`PASS` 只能依預先定義的接受條件與足夠證據設定，不能由施工者自行宣告，也不能由文件存在或模型推理代替實際執行證據。

## 3.8 只傳遞必要上下文

封包引用上游結果或必要資料來源；不必把整段歷史複製到下一個封包。每一輪只載入當前步驟與其必要前後因果，整體一致性檢查則在適當驗收點執行。

# 4. H0–H3：單一問題解決流程

## 4.1 H0：唯一最高目標

**P2：解決問題。** 將目標轉化為符合限制、可以檢查的實際結果。

## 4.2 H1：五個基本環節

```text
H0：解決問題
└── H1
    ├── 1. 理解問題
    ├── 2. 決定做法
    ├── 3. 執行做法
    ├── 4. 檢查結果
    └── 5. 修正與結案
```

五個環節構成最小閉環。一般情況依序推進；出現失敗、阻塞或前置條件失效時，依明確引用返回受影響的步驟。

## 4.3 H2：目前確認的粗略骨架

### 1. 理解問題

- 1.1 要達成什麼目標。
- 1.2 目前是什麼情況。
- 1.3 有哪些限制。
- 1.4 怎樣才算成功。

### 2. 決定做法

- 2.1 找出需要的資料。
- 2.2 找出可行的方法。
- 2.3 選擇合適的方法。
- 2.4 安排執行順序。

### 3. 執行做法

- 3.1 決定由誰執行。
- 3.2 提供必要的工作資料。
- 3.3 執行工作。
- 3.4 回報結果與狀態。

### 4. 檢查結果

- 4.1 比較目標與實際結果。
- 4.2 確認證據是否足夠。
- 4.3 判定成功或失敗。

### 5. 修正與結案

- 5.1 找出失敗原因。
- 5.2 修正問題。
- 5.3 必要時重新執行。
- 5.4 更新結果與收尾。

## 4.4 H3：條件分支出現的位置

H3 不必在每一個節點都預先製作大量分類。只有當步驟確實需要選擇時才展開。例如：

- 2.2／2.3：需要哪些能力？有哪些候選方法？選哪一個？
- 2.4：哪些步驟必須先完成？哪些工作可以並行？
- 3.1：哪個角色具備能力、權限與可用資源？
- 4.2／4.3：證據足夠嗎？符合接受條件嗎？
- 5.1：已確認根因、存在多個假說，還是資訊不足？
- 5.3：修正後重新執行、回到藍圖修正，或因權限／資源不足而停止？

分支基本形式：

```text
步驟到達
  → 檢查條件
      ├─ 條件 A 成立：執行方案 A
      ├─ 條件 B 成立：執行方案 B
      └─ 條件不成立／資訊不足：不調用；補資料或 BLOCKED
  → 產出結果
  → 驗證步驟接受條件
  → 確認完成後進入下一步
```

選擇結果需要被記錄；未確認的推論不得被當成已批准方案。若選擇會改變目標、權限、成本或不可逆性，必須使用相應的確認／治理閘門。

# 5. 封包式工作模型

## 5.1 定義

**封包是一次有邊界的問題處理單位。** 它具有目標、必要輸入、可執行動作、接受條件、結果及後續指向。一次任務可以由多個封包串接；上一封包經接受的輸出成為下一封包的輸入。

規劃、藍圖、施工、驗收與修正不是五套獨立系統，而是同一種封包依其目標與動作不同形成的不同類型。

## 5.2 最低封包內容

為避免封包本身變成複雜系統，最低資料先收斂為五組：

1. **位置與目標：** 封包 ID、所屬主任務／步驟、這次要解決的問題。
2. **輸入與條件：** 必要資料引用、啟用條件、前置條件、限制及權限要求。
3. **動作：** 本封包實際允許執行的工作與責任角色／能力。
4. **結果與證據：** 產出引用、完成條件的核對結果、可支持結論的證據。
5. **狀態與下一步：** 目前狀態、下一封包或返回位置、阻塞／失敗原因（如有）。

不需要在每個封包重複整份核心藍圖、所有角色定義或完整歷史。穩定規則應由權威來源引用，只有本封包的差異與必要資訊放在封包中。

## 5.3 封包類型以工作內容區分，不另外發明流程

- **規劃封包：** 把原始目標整理成可執行的範圍、方法與接受條件。
- **藍圖封包：** 將已確認規劃定位到既有架構，明確定義依賴、變更與驗收要求。
- **施工封包：** 在核准範圍內修改、建立或執行，回傳結果與證據。
- **驗收封包：** 依事先定義的標準獨立比對結果。
- **修正封包：** 只處理被證據定位的失敗或缺口，再返回必要驗收步驟。

這些類型共用一種最小封包契約和狀態規則。不同類型只增加自己必要的欄位，不各自創造平行控制器。

## 5.4 封包閉環

單個封包閉環：輸入有效 → 條件檢查 → 執行 → 輸出形成 → 接受條件驗證 → 封包結果定案。

整體任務閉環：所有必要封包依因果順序完成 → 最終驗收符合原始目標 → 更新唯一 Current／進度 → 清理或封存中間資料。

單一封包 `PASS` 不代表整體任務完成。只有整體接受條件滿足、必要證據齊備且權威狀態完成更新，整體任務才能結案。

# 6. 封包狀態與中控最小職責

## 6.1 初步建議狀態

先以六種狀態作為最小方案討論，不再按每一種角色或功能建立獨立狀態欄：

| 狀態 | 意義 | 可否直接推進 |
|---|---|---|
| `WAITING` | 等待前置封包或條件 | 否 |
| `READY` | 前置條件與必要輸入已滿足 | 可以開始執行 |
| `RUNNING` | 工作已開始，尚無最終結果 | 否，等待結果 |
| `PASS` | 預定接受條件已滿足且證據足夠 | 可以依 `next` 推進 |
| `FAIL` | 工作有結果，但未達接受條件 | 轉入診斷／修正流程 |
| `BLOCKED` | 無法合法或可靠地開始／繼續 | 停止受影響流程，處理阻塞 |

這是討論稿，不是已核准 Schema。狀態欄只表示封包生命週期；失敗原因、阻塞原因、證據層級與執行授權應作為相應資訊，不能無限擴充狀態列舉值。

## 6.2 狀態轉移規則

- `WAITING → READY`：前置封包通過，必要條件及輸入可用。
- `READY → RUNNING`：執行範圍、權限、資源限制均通過。
- `RUNNING → PASS`：結果存在且接受條件通過。
- `RUNNING → FAIL`：工作完成或產生結果，但接受條件不通過。
- `WAITING/READY/RUNNING → BLOCKED`：必要輸入、權限、成本、安全條件或衝突使合法推進不成立。
- `FAIL/BLOCKED → 修正或補足後重評`：不能直接假裝成功，也不能跳過未滿足的條件。
- `PASS → 下一封包`：使用封包中已確認的 `next`／因果引用推進。

如果實際失敗要求重新思考，應建立或返回指向正確步驟的修正封包。不得讓中控自行發明新流程或自行改寫語意目標。

## 6.3 中控只做五件事

1. 定位目前封包與合法下一步。
2. 檢查前置條件、權限及資源限制。
3. 將已授權封包交給具備資格的角色／能力。
4. 接收輸出與證據，更新封包狀態。
5. 依 `PASS／FAIL／BLOCKED` 推進、回退或停止。

中控不代替 Brain 選擇語意目標，不代替 Executor 施工，不代替 Verifier 驗收，也不建立第二份 Current。它維持流程秩序，不成為另一個複雜的大腦。

# 7. 功能、技能與角色的歸位方式

## 7.1 功能是流程節點的能力，不是另一條流程

每個功能應有一個主要節點位置；它可以被其他節點依條件引用，但正式定義只保留一份。功能卡／能力卡只描述該能力的用途、條件、輸入、輸出和限制，不重新描述整套 P2。

## 7.2 角色只回答「誰負責」

| 現有責任域 | 在這套流程中的主要作用 |
|---|---|
| Brain／Cognitive Decision | 理解目標、決定方法、處理必要的方案選擇與策略回退 |
| Knowledge Acquisition | 在資料不足或需要來源時取得、正規化資料並標示來源與不確定性 |
| Realization／Builder／Executor | 執行已授權的工作並回報結果 |
| Assurance／Verifier | 依事先定義的接受條件獨立檢查結果與證據 |
| Central／Coordinator | 檢查契約、派送、更新狀態與推進／阻止流程 |
| Runtime／Current Authority | 記錄實際運行狀態，維持唯一現況權威 |
| Governance | 管理權限、成本、安全、風險及停止條件 |
| Evolution | 在有證據支持時，把可重用根因與修正蒸餾成規則或能力改進 |

以上是責任映射，不代表每一項責任都必須是常駐 Agent。角色可由既有責任域、短期角色或組合能力承擔；新增永久角色需證明有無法被現有責任吸收的持續任務。

## 7.3 環境與模式作為啟用條件，而非另一棵功能樹

同一功能的可用性可受環境、資料、權限、資源、工作模式或前一步結果影響。這些差異用條件限制其是否可執行，不必再建立另一份完整架構分類。

# 9. 功能啟用條件與因果規則

## 9.1 共用啟用判斷

候選功能至少需通過下列檢查：

1. **位置成立：** 目前流程確實到達這個功能所屬的步驟。
2. **觸發成立：** 該功能定義的具體觸發條件已成立。
3. **輸入齊備：** 必要資料存在且版本／來源可接受；未知必須保留為未知。
4. **授權通過：** 目前角色和工作封包擁有足夠權限，未越過允許範圍。
5. **資源允許：** 成本、時間、上下文、外部工具額度及安全限制允許執行。
6. **無未處理衝突：** 必要的目標、來源、範圍或依賴不互相矛盾。

全部必要條件成立才可執行。若觸發不成立，保持不調用；若資訊不足且可以補足，建立對應的資料取得步驟；若權限／成本／安全硬性條件不成立，轉為 `BLOCKED`，不得以模型推理自行豁免。

## 9.2 條件分成兩種處理

- **硬性條件：** 權限、成本、安全、必需欄位、封包身份、前置狀態、證據門檻。能以程式檢查的應盡量由確定性程式／驗證器檢查。
- **語意條件：** 使用者意圖、問題類型、候選方法是否適用、研究是否能解決未知。由 Brain 根據可追溯資料作判斷，必要時記錄假設或詢問最少量的澄清問題。

語意判斷不能覆蓋硬性條件。功能「可能有幫助」不等於它有權執行。

## 9.3 啟用條件的最小描述

每個功能只需要明確定義：

- 何時需要它（觸發條件）。
- 執行前需要什麼（輸入／前置條件）。
- 它會做什麼（允許動作）。
- 它必須回傳什麼（輸出）。
- 什麼情況下不可執行（禁止條件）。
- 結果讓哪個後續步驟可以啟動，或失敗時回到哪裡。

不要只寫「複雜時啟動研究」這種主觀文字。應改成可以觀察的狀況，例如必要事實無法確認、候選方案有重要取捨而現有證據不足、執行結果與預期不符、同類錯誤反覆出現，或必要權限／成本資訊缺失。

## 9.4 防止錯誤調用的基本規則

- 不在目前步驟以外調用無關功能。
- 不因一個功能存在，就讓它成為所有工作的必經步驟。
- 不重複啟動已有有效結果且未發生漂移的工作。
- 不因過程資料存在，就自動把它視為可信或仍有效。
- 不因封包 `PASS` 就越過整體任務的接受條件。
- 不把提案、模擬、靜態檢查或文件寫入升格成實際執行證據。

# 10. 上下文、因果與進度追蹤

## 10.1 以引用取代大量複製

封包應引用上游封包、藍圖節點、能力定義與證據來源的識別碼／位置／版本指紋。下一個封包只載入當前任務需要的片段，不把整段歷史複製進上下文。

## 10.2 最小因果記錄

每次推進只需保留：

- 由哪個封包／條件觸發。
- 哪些前置條件被判定成立。
- 選擇了哪個分支及理由／證據（必要時）。
- 產生了什麼結果。
- 因此允許哪個下一步，或為何停止／返回。

不要求為每次無意義的內部推理保存完整逐字歷史。重要決策、可重現失敗、權限／成本判定及驗收證據則應保留必要記錄。

## 10.3 進度可以由封包狀態推導

全案進度不應只依賴 AI 的文字回報。它可由必要封包的狀態、依賴與完成證據推導。若所有子封包完成但整體接受條件未滿足，任務仍未結案。若資料缺失，標記未知／阻塞，不猜測完成。

## 10.4 單一權威與派生視圖

只保留一份權威的封包／狀態來源。樹狀圖、流程圖、角色責任視圖、進度摘要及查詢結果都應由權威資料派生，而不是各自手工維護。若需要跨節點關係，使用明確 ID 引用；不可建立第二份內容重複的關係真相。

# 11. 封包結案與資料退場

## 11.1 封包結案時處理四類資料

1. **留存核心結果：** 最終產出、已確認決策、必要約束與下一步需要的事實。
2. **保留證據：** 支持關鍵判定、實際執行狀態、驗收與問題復現所需的最小資料。
3. **交接必要資料：** 用引用把下一封包需要的輸出、來源與當前狀態交出去。
4. **處理暫存資料：** 無後續用途的草稿、重複副本、臨時掃描結果和中間產物可以清理；需要追溯但不需常駐的資料則封存。

## 11.2 不可過早刪除

資料仍被開啟封包引用、仍用於失敗診斷／重現、仍支撐未完成驗收，或受到明確保留規則約束時，不得提前刪除。結案也不表示所有資料都一律清空。

## 11.3 不增加複雜的資料狀態機

資料保留判定以封包是否仍在使用、是否為最終結果／證據、是否需要追溯及現行保留規則決定。初始方案不另建大量資料生命週期狀態，只維持簡單、可檢查的結案處理規則。

# 12. 失敗、阻塞與回退規則

## 12.1 `FAIL` 與 `BLOCKED` 的差異

- `FAIL`：已執行或已有可評估的結果，但未達接受條件。
- `BLOCKED`：尚不能合法或可靠地執行／繼續，例如缺少必要輸入、權限／成本未確認、來源衝突或硬性條件不成立。

兩者都不能被默認視為成功。`FAIL` 通常進入根因分析與修正；`BLOCKED` 先處理阻塞原因或結束工作。

## 12.2 回退到真正出錯的位置

- 使用者目標或範圍誤解：回到問題理解／意圖確認。
- 方法選擇不合適：回到決定做法。
- 藍圖依賴／架構假設錯誤：回到藍圖規劃封包。
- 執行錯誤但設計有效：回到施工／修正封包。
- 驗收標準未滿足：回到失敗原因所在的上游步驟；不能自行放寬接受條件。
- 權限、成本或安全問題：停在硬性 Gate，直到得到合法的解決方式。

回退必須有原因和目標位置，不能讓流程陷入無限反覆。對可修正失敗可設定重試限制；超過限制後重新研究、修訂方案或回報阻塞。

# 13. 最低封包資料契約

以下為方便討論的概念格式，不是正式 JSON Schema：

```yaml
packet_id: 唯一識別碼
position: 所屬 H0-H3 節點／步驟
goal: 本封包要解決的問題
inputs: 必要資料與來源引用
conditions: 啟用條件、前置條件及限制
action: 允許執行的動作與負責角色／能力
expected_output: 預期產出與接受條件
status: WAITING | READY | RUNNING | PASS | FAIL | BLOCKED
result: 實際結果摘要與輸出引用
evidence: 必要證據引用
next: 下一封包、回退節點或停止原因
```

上述只表示資料概念。正式 Schema 應先檢查 P2 現有 Task／Result／Execution／Current 契約，能重用就重用，不應建立與既有契約重複的新格式。為保持極簡，可把欄位依五組組織，避免把每個欄位變成另一套治理機制。`goal` 之前的空格只用於示例可讀性，正式 Schema 需要採用標準格式。

# 14. 治理、權限與證據邊界

## 14.1 權限邊界不能被簡化掉

封包的動作必須在已核准的角色、能力、範圍與資源權限內。Executor 不能自我授權、直接改寫不屬於自己的權威狀態，也不能自行宣告獨立驗收通過。

## 14.2 成本與環境條件

功能條件必須包含必要的成本／資源檢查。外部工具、計量 API、付費環境或不確定額度的操作，在成本與權限狀態未確認時應 BLOCKED；不能藉由重試或更換工具繞過限制。

## 14.3 證據層級不可互換

至少要分清：

- 設計／文件已寫入。
- 靜態閱讀／契約檢查。
- 局部案例推演或模擬。
- 實際程式測試。
- 整批整合驗收。
- 真實 Runtime 觀測。

一個層級不能冒充更高層級。封包可 `PASS` 其局部接受條件，但全案 Runtime 狀態仍須依獨立真實證據判定。

# 15. 預期效益與主要風險

## 15.1 預期效益

- **降低結構混亂：** H0–H2 不因新功能不斷膨脹；新增能力必須找到唯一主要位置。
- **降低錯誤調用：** 觸發、輸入、權限與狀態條件不成立就不執行。
- **簡化中控：** 中控不處理所有語意決策，只依封包契約推進。
- **提高交接品質：** 規劃輸出成為藍圖輸入，藍圖輸出成為施工輸入，施工結果成為驗收輸入。
- **進度更可見：** 目前封包、狀態、阻塞原因與下一步可明確查詢。
- **減少上下文負擔：** 以來源引用傳遞必要資料，不反覆載入完整歷史。
- **改善資料治理：** 結案時集中處理證據、核心結果、暫存產物與退場。
- **更容易測試：** 每個封包都可針對正常、負例及邊界條件檢查。

## 15.2 主要風險

1. **過度壓縮欄位**：如果移除必要的來源、權限或證據欄位，系統會變得短小但不可靠。解法是簡化呈現，不刪除必要契約。
2. **條件寫得模糊**：例如「複雜時才研究」不可穩定驗證。解法是把條件寫成可觀察事件或明確的語意判斷規則。
3. **所有步驟都封包化**：若每個微小動作都產生持久化檔案，反而增加維護成本。解法是簡單步驟可在工作上下文內完成，只有交接／保存／驗收需要時才建立正式封包。
4. **回退循環**：失敗後不斷重做。解法是封包記錄失敗原因、返回目標與重試限制。
5. **單一流程掩蓋真正不同的責任**：流程統一不等於權限統一。解法是保留責任、資料所有權及獨立驗收界線。
6. **局部 PASS 被誤認為全案 PASS**：解法是分開封包接受結果與整體任務結案條件。
7. **新架構與現有 P2 契約重複**：解法是先對帳 Task／Result／Execution／Current 和既有 Schema，再決定如何映射，不另建平行權威。

# 16. 導入與驗證順序

本節是建議順序，並不表示已執行。

1. **凍結概念骨架：** 確認 H0–H2，僅在 H3 展開必要分支。
2. **核對功能映射：** 逐項比對 F01–F30、唯一施工藍圖和功能矩陣，確認唯一主要歸屬、啟用條件及是否重複。
3. **盤點現有封包契約：** 檢查 Task Packet、Result Packet、Execution、Brain Proposal、Current 和相關 Schema，避免建立重複格式。
4. **設計最小共用封包契約：** 只新增既有契約沒有且確實需要的內容；保持五組欄位概念。
5. **定義狀態與轉移 Gate：** 驗證 WAITING／READY／RUNNING／PASS／FAIL／BLOCKED 的合法轉移，確認失敗和阻塞不能直接被視為完成。
6. **整理功能觸發條件：** 優先處理高風險或高頻功能，例如外部研究、全庫掃描、角色派送、施工、驗收、藍圖變更和資料清理。
7. **建立封包閉環測試：** 選一條低風險的端到端流程，覆蓋正常路徑、前置條件缺失、功能不應啟動、執行失敗、驗收失敗、回退與資料退場。
8. **比較簡化前後：** 觀察重複功能數、錯誤調用、上下文讀取量、交接失敗、狀態不一致與閉環成功率。沒有實際量測時標示 `UNMEASURED`，不憑感覺宣告改進。
9. **通過證據後才推廣：** 先在受控工作單元驗證，再按 P2 現有藍圖的規則更新唯一權威文件與相關派生視圖，不直接全庫重構。

# 17. 驗收標準

新架構最少應通過以下檢查：

- 每項正式功能在 H0–H3 中有唯一主要歸屬。
- 任何新功能都能說明上層目標、觸發條件、輸入、輸出及後續因果。
- 所有條件不成立的功能都不會被調用。
- 缺少權限、必要輸入或成本資訊時，不會越過 Gate。
- 中控能只靠封包身份、狀態、前置條件與下一步引用推進流程，不依賴隱藏對話記憶。
- 單個封包閉環與全案閉環不會混淆。
- `FAIL`、`BLOCKED` 與 `PASS` 有清楚區別；失敗不會被覆蓋成成功。
- 規劃、藍圖、施工、驗收共用同一封包運作規則。
- 封包間透過引用交接必要上下文，不需要複製完整歷史。
- 結案可以保留核心結果與證據，安全處理無用暫存資料。
- 具備正常、負例、邊界測試與可回讀證據；未執行的測試明確標示未執行。
- 唯一 Current、唯一 P2 施工藍圖及既有資料責任不會因新方案另立平行真相。

# 20. 附錄 B：設計用語

- **H0：** 本系統最高目標。
- **H1：** 核心問題解決環節。
- **H2：** 各環節的基本步驟。
- **H3：** 具體選項、條件分支與能力選擇開始明顯展開的層級。
- **功能／能力：** 可被流程調用的具體工作能力；具有用途、條件、輸入、輸出和限制。
- **技能／方法：** 達成特定任務的操作方法；不是自動獲得權限的主體。
- **角色：** 對特定工作負責的責任承擔者；角色名稱本身不構成授權。
- **封包：** 一次有明確邊界與結果的問題處理單位。
- **啟用條件：** 決定功能是否可進入可執行範圍的條件。
- **閉環：** 執行後有結果、有驗收，且狀態／後續關係已被正確更新。
- **Current：** P2 現有架構中唯一的執行現況權威；本提案不另建一份。
- **證據層級：** 區分設計、靜態檢查、模擬、程式測試、整批驗收與真實 Runtime 的依據。

---

**結論：** P2 的底層應保持簡單。先以單一問題解決流程定位所有功能，讓 H3 的條件分支決定何時啟用能力，再用共用封包交接每一步的輸入、結果與下一步。中控只依明確狀態與條件推進；功能、角色、上下文、因果與資料退場都服務於同一條流程，而不是各自建立平行系統。此設計的成敗，最終要以錯誤調用、交接一致性、閉環證據、上下文成本與實際驗收結果驗證，而不是只靠架構看起來更簡潔來判斷。
