## 1. 系統定位與文件分工

本文件是 SOP 的生命週期與管理權威，不是所有領域流程的重複大全。依各文件唯一責任分工：

- [對話流程列表](./對話流程列表.md)：只負責流程目錄、觸發條件、簡介及專用規格入口。
- 各領域 SOP／專用流程文件：保存該任務的實際步驟、分支條件和驗收標準，例如[解析步驟流程](./解析步驟流程.md)。
- [SOP 文件標準欄位與蒸餾建置流程](./SOP文件標準欄位與蒸餾建置流程.md)：唯一維護 SOP 建檔欄位、可複製模板，以及從對談／操作紀錄蒸餾成 SOP 候選的流程。
- 本文件：規定 SOP 如何選用、試行、驗證、改良、升級、停用，以及哪些內容可以成為固定標準。
- [SOP 執行與演化台帳](./SOP執行與演化台帳.md)：每次重要流程執行的精簡紀錄、偏差、驗收結果和流程改良決策。
- [變更追溯總表](./變更追溯總表.md)：記錄檔案／版本層級的重要變更；不取代 SOP 的執行成效紀錄。

SOP 是「目前證據支持的最佳已知執行方式」，不是宣稱數學上已證明的全球最優解。只有經過符合明確驗收條件的重複驗證，才能從候選升級為固定標準。

## 2. 固定執行主流程

一般非瑣碎任務的基線流程：

`INTAKE → AUTHORIZE → SELECT_SOP → PLAN → EXECUTE → VERIFY → PERSIST → REVIEW`

| 階段 | 必須回答的問題 | 通過條件／產物 |
|---|---|---|
| INTAKE | 任務要解決什麼？成功輸出是什麼？ | 目標、交付物和可驗收條件明確 |
| AUTHORIZE | 可讀／可寫範圍、禁止項和高風險操作是什麼？ | 權限明確；涉及未授權範圍時停止寫入 |
| SELECT_SOP | 是否存在符合觸發條件的 CURRENT SOP？ | 選定 SOP ID／版本；不存在則建立候選流程，不假裝已有標準 |
| PLAN | 前置依賴、變更清單、必要檢查和回復路徑是什麼？ | 最小可行執行計畫與預期產物 |
| EXECUTE | 依標準步驟及條件分支執行到哪一步？ | 產物符合格式及責任邊界；每個中間狀態可追溯 |
| VERIFY | 內容、來源、連結、範圍和行為分別驗了什麼？ | 逐項驗收結果；未執行項明確標記 |
| PERSIST | 有需要長期使用的結論、狀態或產物嗎？ | 更新唯一責任文件、主軸／分支索引及雙向引用 |
| REVIEW | 本次是否出現可重用的新證據、偏差或更短路徑？ | 記錄結果；只把可重複且有證據的改良送入候選流程 |

執行原則：先走已驗證的標準路徑；只在觸發條件成立時啟用分支。不得每次從頭重新設計，也不得為了遵守流程而對不需要的低風險任務執行所有重型檢查。

### 更新任務的增量修正與職責歸位

**觸發：** 凡改變功能、邏輯、能力、流程或架構的更新均適用；純讀取或不改語意的機械修正走 Δ0。

`BASELINE → DIAGNOSE → CLASSIFY_CHANGE → MAP_OWNERSHIP → MINIMAL_DIFF → IMPACT_TEST → APPLY → REGRESSION_VERIFY → TRACE → RECURRENCE_CHECK`

1. **基線／根因：** 以最新權威資料重建現況、目的與不變量；對照預期／實際，記錄證據、影響和根因可信度。未知即 HYPOTHESIS，不得當成修復完成。
2. **職責：** 分開功能執行責任、文件權威、批准／權限；每項行為一個主要功能責任節點。協調層可編排，不能複製底層執行權。
3. **先盤點、後新增：** 每次語意更新先查[能力登錄](./功能清單_基礎能力覆蓋登錄_v0.1.json)、[功能骨架](./解析文檔/架構映射/P1-P2-功能骨架樹-全面重整版.md)及相關 SOP／PR；記錄已查 ID、重疊／衝突、缺口及既有能力為何不能修正／擴充。預設修正／擴充既有節點；僅有證據證明現有能力／契約不能承載時才新增，並定義輸出、依賴、副作用、驗收、回退、退場。盤點不全或理由不足即 BLOCKED。
4. **按影響驗收：** Δ0 非語意只讀回；Δ1 局部重現與回歸；Δ2 跨節點／契約做依賴和受影響回歸；Δ3 核心／權限／安全改動須配對模擬、回退及適用的獨立檢查。Δ 級與任務風險 L 級分開。
5. **結案：** 讀回寫入，更新問題／索引／台帳，執行原失敗與直接回歸；安排後續代表性任務檢查復發。未測項保持 NOT_VERIFIED，不因文件寫入就關案。

每次語意更新先盤點直接相關能力；不要求全域比較。僅核心／共享契約、跨節點依賴、職責重疊、新能力類型、影響未知或重大品質／成本／風險差異才擴大掃描；授權邊界不變。案例詳見[增量更新紀錄](./解析文檔/增量更新能力_根因修正與職責歸位_2026-10-22.md)；規範以本節為準。

## 3. 任務分級與條件分支

| 等級 | 判定條件 | 執行方式 |
|---|---|---|
| L0｜簡單 | 一次性回答、無文件持久化、無外部副作用 | 只做必要的理解與事實核對；不建立執行紀錄 |
| L1｜單一產物 | 一份文件或單一明確交付物，風險低且有現成 SOP | 使用對應 SOP；計畫併入執行清單，不另建計畫文件；寫入時讀回本次產物 |
| L2｜跨文件／多來源 | 涉及多份文件、來源彙整、索引、版本或引用更新 | 只盤點直接相關主軸／SOP／問題分支與受影響文件；先固定變更集，再按責任分支執行與集中驗收 |
| L3｜高影響／不可逆 | 權限、刪除、正式企劃、不可逆操作、重大衝突或高風險外部效果 | 在 L2 基礎上增加明確授權、影響評估、回復計畫與獨立驗收；缺任一必要條件即停止相關操作 |

等級只用來決定必要檢查，不代表可以略過權限、證據或真實性要求。若任務跨級，採用符合最高實際風險的流程。

### 最小必要路徑與批次處理

- **L0：** 一次性回答且不寫入文件、不產生外部副作用時，直接完成必要理解與事實核對；不執行 SOP 選擇、持久化或台帳登錄。
- **L1：** 使用現有 SOP，將規劃壓縮成執行前清單；不為單一低風險產物另建規劃文件、重複事件長文或全庫掃描。
- **L2：** 先列出本次變更集與直接相關文件；先完成各文件內容草案，再依唯一責任順序寫入。每個檔案盡可能只寫一次；正文完成後集中讀回所有變更檔，再依讀回結果更新索引／追溯，台帳只記一列。
- **L3：** 沿用 L2 路徑，另加授權、影響與回復檢查；高影響內容需獨立驗收，不以縮短操作數降低安全要求。
- **所有等級：** 只讀取任務所需的主軸與直接相依文件。只有在影響範圍未知、跨主題或發現衝突時才擴大檢索；不預設每次掃描全庫。
- **部分失敗：** 多檔變更不是原子交易。任一寫入／驗收失敗時標記 `PARTIAL`，讀回現況並只修復失敗或不一致項，不盲目重跑整批。
- **未知與爭議：** 不影響已確認安全工作的疑問，先記入問題清單並保留待定狀態；若疑問涉及目標、授權、風險或結果正確性，則停止受影響部分，不能自行假定答案。

這些規則是依現有文件分工、任務分級與單次模擬中已辨識的操作風險所作的執行規格精簡；不代表跨任務省時幅度已獲實驗證明。

## 4. SOP 的標準格式

完整欄位表、欄位驗收要求與可複製模板以[SOP 文件標準欄位與蒸餾建置流程](./SOP文件標準欄位與蒸餾建置流程.md)為準；本節只列最低必要門檻，避免在兩份文件維護不同版本的模板。

每個可重用 SOP 至少要有：

1. `SOP_ID`、版本、狀態與唯一責任。
2. **觸發條件**：什麼情況必須使用；什麼情況不得使用。
3. **必要輸入／前置條件**：開始前必須存在或核對的資料。
4. **預期輸出**：交付物、格式、存放位置及完成狀態。
5. **標準步驟**：使用明確動詞、順序、輸入和產物描述每步。
6. **條件分支**：用可判斷的條件導向不同路徑；不得只寫「視情況處理」。
7. **停止與回復條件**：授權不足、來源不可用、狀態衝突、驗收失敗時如何停止或回復。
8. **驗收閘門**：逐項可觀察、可重做的通過／不通過條件。
9. **已知限制與證據**：哪些已驗證、哪些未驗證、依據哪些案例。
10. **相依文件與輸出紀錄**：避免同一規則在多份文件重複維護。

缺少可判斷的觸發條件、明確輸出或驗收方法時，該文件只能算作做法備忘，不能升級為固定 SOP。

## 5. 流程演化與定版生命週期

流程狀態按下列順序管理：

`CAPTURED → DRAFT → TRIAL → VALIDATED → CURRENT → SUPERSEDED／RETIRED`

| 狀態 | 意義 | 升級條件 |
|---|---|---|
| CAPTURED | 從實際任務抽取到一項可重用做法 | 已描述問題、步驟及可觀察結果 |
| DRAFT | 已把做法整理成完整 SOP 候選 | 觸發、輸入、輸出、分支及驗收齊備 |
| TRIAL | 在真實任務中試行，仍允許修訂 | 每次試行都有執行紀錄與驗收結果 |
| VALIDATED | 代表性案例的必要驗收全部通過 | 至少兩個不同輸入／情境的獨立案例通過；或有涵蓋主要分支的可重複回歸測試集全數通過 |
| CURRENT | 被指定為此 `SOP_ID` 唯一現行標準 | 已核對相依流程、引用、回退方式與版本 |
| SUPERSEDED | 被新版取代；只供版本比較 | 新版已驗收並明確取代舊版 |
| RETIRED | 不再適用或已失去用途 | 記錄退役原因、替代流程及仍需保留的歷史證據 |

啟動期例外：`SOP-META-001` 依使用者明確要求暫採 `PROVISIONAL_CURRENT`，讓後續非瑣碎工作有固定預設流程；其有效性仍標記 `UNVALIDATED`，不可宣稱已證明通用性。其他領域 SOP 不適用此例外，仍需按代表性案例與回歸條件升級。高影響／不可逆 SOP 必須覆蓋失敗與回復情境並完成獨立檢查；必要時取得使用者明確核准。只有一次成功個案時只能標記 TRIAL。

### 重大語意變更的模擬比較閘門

本閘門自 v0.5 起生效，屬於 forAVAr 文件治理層的強制前置判斷；本文件不會自行形成工具層的 Runtime 攔截器。

**觸發範圍：** 凡擬修改系統規則、現行 SOP、工作流程、架構規劃、正式藍圖或其他會改變決策分支、權限、停止條件、輸出結果、回復方式或跨文件責任的重大語意內容，寫入前必須比較現行方案與候選方案。拼字、純格式、無語意變化的機械性索引同步不觸發重型模擬；若表面格式變更實際改變含義，仍須觸發。

**最小配對模擬：**
1. 固定同一組代表性輸入／情境與同一驗收標準，分別走現行方案及候選方案；至少涵蓋正常情境、失敗／部分完成情境，以及相關的安全、授權或回復邊界。
2. 比較內容完整性、正確性、權限與安全、可回復性，以及可觀察的時間、操作／工具步數、返工、錯誤和成本。不得只以步驟較少就宣稱效率更高。
3. 若沒有可比的實測基線，可先做最簡桌上推演，但必須標記「定性模擬／未實測」，列出輸入、假設、結果和未知；不得把桌上推演寫成 Runtime 或實際效率提升證明。

**GO／NO-GO：**
- 一般優化提案只有在不損害任何必要安全、授權、正確性及內容完整性不變條件，且比較結果顯示明確的效率改善與有效價值時，才可推進。
- 必要的安全、權限、正確性或內容完整性修正，若有具體證據顯示能降低重大風險，即使增加必要步驟或耗時仍可推進；須明確記錄其效益與成本，不得把它包裝成「效率提升」。
- 若沒有明確淨收益、有效價值不清楚、關鍵情境未覆蓋或結果互相矛盾，判定 NO-GO：停止該優化變更、保留現行版本，並向使用者提出警告及缺失證據；不得以主觀感受推進。
- 若等待模擬本身會帶來具體且更大的安全、資料完整性、權限或服務風險，可先採取最小範圍、可回復的緊急緩解。不得趁機進行全面優化；事後必須補做配對模擬、回歸驗收並登錄跳過前置模擬的理由。

**授權優先：** 模擬通過不代表獲得寫入授權。正式企劃仍須有使用者明確「更新企劃」授權；唯讀參照 repository 不得寫入。任何模擬結果均不能覆蓋更高層級的安全、權限或回復要求。

**紀錄：** 將基線、候選方案、測試情境、比較結果、GO／NO-GO、未測量項、警告及例外寫入 [SOP 執行與演化台帳](./SOP執行與演化台帳.md)；只有通過本閘門及必要回歸驗收的變更才更新現行規範。

## 6. 失敗路徑的處理

核心原則：**保留失敗的證據，但不把失敗步驟收編成標準路徑。**

- 每次失敗只記錄足以追溯的資訊：觸發條件、失敗階段、根因是否已證實、影響、回復結果和證據位置。
- 已證實且可預防的根因，轉換成一條簡短的「前置檢查／禁止條件／回復規則」，放入 SOP 的適當位置。
- 根因未知、只對單一偶發環境成立或尚無法重現的失敗，留在執行台帳或案例證據；不得為它添加永久步驟。
- 同一失敗重複出現時，依「更新任務的增量修正與職責歸位」回查既有問題 ID、根因、責任節點、已採控制及回歸紀錄；先判斷舊控制未觸發、設計不足或根因不同，再決定修正，不得只累積同義規則。
- 新規則必須說明降低哪一類錯誤、增加什麼成本，以及如何驗證有效；不能證明有益時維持候選狀態。
- 只有在候選改良通過回歸驗收後，才修改 CURRENT SOP。舊版依版本治理規則保留，不直接覆寫唯一歷史證據。

## 7. 驗收指標與改良準則

每個 SOP 都要設置與任務相符的驗收指標，至少檢查：

- **完整性**：所有必要輸出、節點、來源或欄位都有明確處理狀態。
- **正確性**：重要主張及引用可以回到有效來源；未知與衝突未被改寫成確定結論。
- **範圍遵循**：寫入位置、權限、禁止事項與副作用均符合授權。
- **可重複性**：相同前置條件依 SOP 執行時，可依相同標準驗收。
- **成本與返工**：只記錄實際觀察到的步驟數、重複操作、回復次數、工具調用或耗時；未測量就標 UNKNOWN。
- **責任唯一性**：功能行為、文件權威及批准／權限責任分開標明；同一行為不得有互相衝突的多個主要負責節點。
- **復發控制**：對修正過的問題，記錄原失敗案例及後續復發檢查；尚未重測的情況標 NOT_VERIFIED。
- **回歸安全**：改良後，既有通過案例仍須通過，且不得引入已知重大漏失或權限違規。

改良排序採硬性優先級：先消除安全／權限違規與內容漏失，再降低引用錯誤與返工，最後才優化速度或步驟數。不得用更快但漏失更多的路徑取代已驗證流程。除非有可比的實測資料，不得宣稱效率提升或「最優」。

## 8. 每次執行的紀錄規則

每次執行非瑣碎 SOP，於[執行與演化台帳](./SOP執行與演化台帳.md)新增一筆精簡紀錄，至少含：

`RUN_ID`、日期、`SOP_ID/版本`、任務級別、觸發情境、結果狀態、必要驗收、偏差／失敗分類、證據或交付連結、是否提出 SOP 改良。若為更新類任務，另記變更類型、功能責任、文件權威、批准權限、Δ 影響級別、根因信心、回歸／回退與復發檢查狀態；不適用欄位可標 N/A，不應為常規成功填寫長篇分析。

- 常規成功只寫一列；不複製整份對話或整個報告。
- 有失敗、偏差、來源衝突、遺漏或改良候選時，才連結詳細事件或案例證據。
- 每次執行紀錄不等於每次都改 SOP；只有通過改良閘門才更新標準流程。
- 台帳保留操作經驗與決策理由；SOP 正文只留目前有效的步驟、必要例外和驗收規則。
- 當台帳超過 8,000 字元，按年份或 SOP_ID 分支，保留一份精簡總索引，不截斷歷史紀錄。

## 9. 固定啟動規則與限制

凡遇到多步驟、跨文件、重複類型或需要持久化的任務，預設先查[對話流程列表](./對話流程列表.md)，再依本規範選用現行或暫行 SOP；使用者不需要重複提醒。涉及既有問題修正、能力擴充／替換／退役、責任重疊或核心契約時，必須依第 2 節的增量更新流程執行。已有合適功能節點時優先修正／擴充，不重複建構；只有舊分類／契約無法承載且有證據支持時才提出新類別。新增類別與流程規則都要經試行與回歸驗收；文件存在不等於流程已生效。

當對談或既有操作首次被整理成 SOP，或形成重大流程決策時，使用[SOP 文件標準欄位與蒸餾建置流程](./SOP文件標準欄位與蒸餾建置流程.md)；將 SOP 標準步驟與對談參考紀錄分開保存。只有本輪需求、決策或異常值得追溯時才建立詳盡對談紀錄，常規成功不複製整段對話。

本規範是 PROVISIONAL_CURRENT 的文件化操作標準；第 5 節的重大變更模擬比較閘門自 v0.5 起在 forAVAr 文件治理流程中生效，但文件本身不會自動注入模型、攔截工具或提供 Runtime 強制。規則遵循的一致性及閘門淨效益仍須由[台帳](./SOP執行與演化台帳.md)中的實際案例與回歸驗收驗證；流程目錄只提供入口。
