## 1. 事件欄位與狀態

每筆事件使用固定欄位：`EVENT_ID`、`DATE_TZ`、`TOPIC_ID`、`OP`、`DOC_ID/PATH`、`DELTA`、`REASON`、`SOURCE_REF`、`VERIFY`。只登錄語意上有意義的事件；單純字體／標點修正可併入對應提交批次，不逐行複製 Git 歷史。

狀態定義：
- `PREPARED`：變更方案與受影響引用已列出，尚未完成寫入。
- `APPLIED`：已提交寫入，但驗收尚未完成。
- `VERIFIED`：提交、內容讀回、引用和必要檢查已完成。
- `PARTIAL`：只完成已明列範圍；仍有未涵蓋項目。
- `BLOCKED`：來源或操作受阻，不能作出完成判定。
- `SUPERSEDED`：事件／文件所描述的狀態已由較新事件取代；保留歷史，不再作現行狀態使用。

## 3. 現行治理變更

### EVT-0011｜目前已寫入的政策

- 邏輯文件在工作目錄最多保留三份完整版本：一個 CURRENT、兩個 BACKUP。
- 同主題不同分析角度以 BRANCH 歸位；每個分支獨立計算 CURRENT＋兩個舊版。
- 同一上下文的多次對話彙整成一份 MASTER；每次原始對話是獨立 SOURCE 事件，可保存多份原始紀錄，不作平行的現行知識入口。
- MASTER 目標不超過 6,000 字元；一般 AI 可讀文件硬上限 8,000 字元；超限分流並為各彙整建立目錄／索引。
- 索引只以 MASTER 作主要入口；MASTER 指向 CURRENT BRANCH／SOURCE，分支回鏈到 MASTER；變更追溯表可定位備份。
- 任何移動、合併、分流、取代或刪除前，先建立變更與引用遷移方案；驗收成功後才輪替備份。
- 本事件不代表全庫所有長文件已完成拆分、所有引用已雙向核對，亦不代表 Git 歷史的舊物件已清除。

### 自我更新規則

本表是事件登錄本身；本表自身的修訂由 Git 歷史追蹤，不為每次增補再產生無限遞迴的「本表更新本表」事件。每次其他邏輯文件的有意義變更仍須記錄一筆事件或納入可識別的變更批次。若一批變更涉及本表以外多個文件，EVENT 須列出完整受影響集合及實際 commit。

## 5. 更新本表的規則

1. 事件 ID 按 `EVT-000001` 之類單調遞增；不得重用 ID。
2. 先記錄預定操作與引用影響，再實際修改；完成後把實際 commit、驗收結果及未解限制回填。
3. 不確定的日期、來源或操作標記為 `UNKNOWN`，不以檔名或現行內容臆造歷史。
4. 同一變更批次內的機械性索引同步可合併為一筆事件，但受影響文件清單必須完整且可核對。
5. 已移出工作目錄的內容必須指明恢復來源；不能只留下「已刪除」。
6. 重要負面證據、衝突與阻塞均要保留；不可將「未查到」翻譯為「不存在」。
