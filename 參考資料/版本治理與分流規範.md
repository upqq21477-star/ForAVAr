## 1. 不可變更的治理原則

1. 每個邏輯主題只有一份現行主軸彙整；索引的主要入口只指向彙整檔，不把所有分支、歷史備份平鋪為並列入口。
2. 主軸彙整保存現行結論、必要因果、限制、未決問題、分支導航和來源對照；詳細內容各自保留在唯一責任分支，不在多份文件複製全文。
3. 新版不因建立時間較新就自動成為權威。完成差異核對、引用更新及驗收後，才可標記為 CURRENT。
4. 舊版備份只可用於恢復、版本差異核對及歷史稽核；不可作為現行規則、一般答案或新的引用目標。
5. 原始證據、原始對話、原始 ZIP/DOCX、雜湊、反例、負面證據、限制、衝突和未驗證狀態不得因蒸餾或刪除重複而丟失。
6. 文件的文字存在、索引已更新、Git 提交成功、內容驗收通過、行為／Runtime 通過是不同狀態，必須分開標示。
7. 本規範僅授權改動 `upqq21477-star/forAVAr`；P1、P2 只能唯讀參照。

## 2. 文件物件類型與版本計算

| 類型 | 定義 | 一般索引可見性 | 是否計入三版本上限 |
|---|---|---|---|
| `MASTER` | 某邏輯主題的唯一現行彙整與導航入口 | 必須可見 | 是 |
| `BRANCH` | 同一主題中職責不同的詳細分析角度，例如完整性、語意差異、風險或根因 | 只從主軸彙整進入 | 每個固定分支 ID 分別計算 |
| `SOURCE` | 原始輸入、每場原始對話／工作紀錄、原始附件、來源快照 | 不列作主要分析入口；由彙整來源清單調閱 | 否；它是來源事件，不是彙整檔的版本 |
| `BACKUP` | 同一 MASTER 或 BRANCH 的舊完整版本，無現行功能 | 不列入一般索引，只從追溯表按需調閱 | 是 |
| `INDEX` | 目錄、文件與分支索引、雙向引用圖 | 作為導航入口 | 本身也受三版本上限 |
| `LEDGER` | 追加式變更事件追溯 | 作為治理入口 | 本身也受三版本上限；完整事件不因舊版輪替刪除 |
| `PLAN` | 正式企劃／架構提案／施工基線 | 由主軸索引指向其權威入口 | 是；正文修改仍受明確企劃授權規則管制 |

`DOC_ID` 表示邏輯文件身分，不是路徑，也不是檔名。移動、格式變更或小幅措辭修訂原則上不改 `DOC_ID`。不同證據責任、不同分析角度或不同原始對話場次，需依其用途分別分配 `BRANCH_ID` 或 `SOURCE_ID`，不可僅因主題相似而合併來源身分。

## 3. 版本上限與備份規則

### 3.1 標準上限

對每個邏輯 MASTER、每個固定 BRANCH，以及每份其他一般文件：

- `CURRENT`：最多 1 份。
- `BACKUP_1`：最近一個舊版。
- `BACKUP_2`：再前一個舊版。
- **完整可直接調閱版本合計不得超過 3 份。**

新版本通過驗收後，按 CURRENT → BACKUP_1 → BACKUP_2 輪替。最舊版本超出上限時，先確認來源、引用、獨有資訊及恢復路徑，再依保留政策封存或移出工作目錄。禁止為符合上限而直接覆寫唯一證據。

### 3.2 分支上限

相同主題的不同角度是同一主軸下的分支，不是互相競爭的主軸版本。例如壓縮檔主題可以包含來源完整性、檔案分布、OOXML／格式差異、語意分析及問題追蹤分支。每個分支按自己的固定 `BRANCH_ID` 保留 1 個現行版及最多 2 個舊版。

不得把「多角度分支」誤算成主軸的多個版本；也不得把兩份職責不同的分支因內容重疊就直接刪除。

### 3.3 原始對話與來源備份的明確例外

每一場對話、每一份使用者提供的來源檔均為獨立 `SOURCE` 事件，不是同一彙整文件的版本。若同一上下文經過十場對話：

- 建立 1 份主軸彙整，整合十場對話形成的共識、差異、決策、未解事項及下一步。
- 十份原始對話紀錄可作不可變來源備份保存；它們不視為同一主檔的十個版本。
- 日常索引只列主軸彙整。彙整內的來源登錄列出各 `SOURCE_ID` 和可查位置，但不把十份備份當成十個並列的知識入口。
- 只有在核對原始語境、確認授權或稽核來源時才讀取來源備份。

此例外不允許把衍生分析稿任意標為 SOURCE；必須能指出它對應的實際原始輸入／對話事件。

### 3.4 舊版本的唯一用途

舊版標記為 `BACKUP_ONLY`。禁止在 README、主軸索引、一般工作流程或新分析中將舊版當成現行引用目標。需要歷史比較時，引用變更事件或提交識別碼；需要恢復時，依追溯紀錄調取指定備份，恢復後建立新的 CURRENT 版本，不直接把舊版改標成最新而略過驗收。

## 4. 同主題彙整與分支

1. 先建立／確認 `TOPIC_ID`，再判斷現有文件是同一主題的舊彙整、細節分支、獨立子主題或原始來源。
2. 多輪對話的共同內容、決策和仍有效結論進入 MASTER；各輪獨有證據、反例及角度保留為來源或 BRANCH。
3. 不同角度可以保留獨立分析，但 MASTER 必須說明每個分支回答的唯一問題、證據範圍及與其他分支的差異。
4. 如果分支內容超過長度閾值，建立子分支；不得只將同一大檔拆成沒有責任界線的任意片段。
5. 任何不同結論要保留為 `CONFLICT` 並列出各自證據。MASTER 不能在缺少裁決依據時把衝突蒸餾成單一確定結論。

## 5. 長度閾值與分流規則

### 5.1 計量方式

對 AI 使用的 Markdown／文字彙整、分析分支、索引及規範，使用 Unicode 字元數作可重複量測值：

`CHAR_COUNT = 字元總數 - CR 字元數 - LF 字元數`

所有標題、表格、代碼、連結和中繼欄位均計入；只排除換行字元。不同工具的 tokenization 不同，因此不得把字元數冒稱精確 Token 數。

### 5.2 閾值

- MASTER 目標：不超過 6,000 字元。
- MASTER／BRANCH／INDEX／LEDGER／一般 AI 可讀規範硬上限：8,000 字元。
- 超過 8,000 字元：必須分流，不得將超長檔案繼續作為一般 AI 啟動時的整份載入目標。
- 原始證據與原始對話不改寫、不因本閾值而截斷；它們應從日常載入排除，透過 MASTER 的來源索引按需讀取。
- 正式企劃／架構提案若超閾值，必須先在主軸索引建立分流映射，標記 `SPLIT_PENDING_PLAN_AUTH`；企劃正文的拆分和重排仍須遵守明確的「更新企劃」授權閘門。不得藉整理索引之名改寫企劃語義。

### 5.3 超長分流步驟

1. 依 H2/H3 語義邊界和唯一責任拆分，不按任意字元位置截斷。
2. 建立不超過 6,000 字元的 MASTER；開頭必須包含摘要、TOC 目錄、分支索引、現行狀態和未知／衝突聲明。
3. 建立職責明確、各自不超過 8,000 字元的 BRANCH；分支開頭必須有本分支摘要、TOC、主軸回鏈及來源／引用索引。
4. MASTER 的索引指向各分支；分支的回鏈指向 MASTER。若再拆子分支，維持同樣的上下行索引。
5. 回讀原始長檔並對帳：每個原始重要主張、證據、限制、反例及未決事項，須對應到新 MASTER／BRANCH／SOURCE 的某個位置。未對帳即標記 `SPLIT_NOT_VERIFIED`，不可刪除舊內容。
6. 先更新主軸彙整與引用圖，再更新分支內容和來源映射；所有變更作為一組邏輯事件記入追溯總表。
7. 驗收通過後才把舊大檔降為 `BACKUP_ONLY` 或移出一般工作目錄。

## 6. 雙向引用契約

每份可被其他文件引用的 MASTER／BRANCH／規範至少要能表示：

- `DOC_ID`／`BRANCH_ID`。
- `PARENT_MASTER`：所屬主軸彙整；主軸自身填 `NONE`。
- `OUTGOING_REFS`：本文件引用的權威文件／分支／來源。
- `INCOMING_REFS`：哪些文件目前引用本文件。
- 每筆引用包含 `REF_ID`、來源文件 ID、目標文件 ID、引用目的、狀態及路徑。

對每條有效引用 A → B，索引必須有其反向紀錄 B ← A。這表示有可反查的雙向引用關係，不表示正文必須形成互相循環的語意依賴。

引用更新規則：

1. 新增、改名、移動、分拆、合併、取代或刪除目標前，先查其所有 incoming refs。
2. 主軸彙整及雙向引用索引必須先形成變更草案；新目標未建立前，不可將索引標成已完成。
3. 完成目標變更後，核對所有出鏈和入鏈均指向現行目標；不存在的路徑不得標成有效引用。
4. 舊版本只能由變更追溯紀錄／備份索引調閱，不可留在現行 incoming refs 中當作一般知識引用。
5. 所有受影響引用要以 `REF_ID` 追蹤；修改目標時可立即查得所有需要一起更新的來源。
6. 對尚未完成全庫掃描的既有引用，標記 `BACKLINK_COVERAGE=PARTIAL`；不得宣稱雙向索引全面完成。

## 7. 每次更新的標準流程

`DISCOVER → CLASSIFY → PREPARE_MASTER_AND_REFS → WRITE_CURRENT → VERIFY → LOG → ROTATE_BACKUPS`

1. **DISCOVER**：先讀主軸索引、版本治理規範、變更追溯表、去重規範及目標文件。
2. **CLASSIFY**：判斷是新主題、既有主題的新來源、既有分支的新發現、現行文件更新或正式企劃更新。
3. **PREPARE_MASTER_AND_REFS**：先起草 MASTER 摘要／分支索引、incoming/outgoing refs、受影響文件清單及變更追溯事件；列出預期新增、修改、移動、取代或刪除項。
4. **WRITE_CURRENT**：只寫入授權範圍內的現行文件及分支；每個邏輯文件只保留一個 CURRENT。
5. **VERIFY**：重新讀回實際提交版本；核對字元數、檔案存在性、來源指紋、引用雙向性、內容對帳及必要驗收。
6. **LOG**：將實際完成的事件及 Git commit／blob 指紋寫入追溯總表。未執行或失敗的驗收保留 `NOT_VERIFIED`／`BLOCKED`。
7. **ROTATE_BACKUPS**：只有在驗收和引用遷移成功後，才輪替備份；不得先刪舊版再補索引。

若操作介面不支援多檔原子提交，必須用 `PREPARED → APPLIED → VERIFIED` 狀態標示中間狀態，且期間不得移除可恢復來源。不得宣稱尚未完成的一組更新已經一致。

## 8. 刪除、恢復與保留政策

| 狀態 | 精確意義 |
|---|---|
| `CURRENT` | 唯一現行權威文件／分支 |
| `SUPERSEDED` | 已被新版本取代，非現行；歷史來源可回查 |
| `BACKUP_ONLY` | 只供恢復／差異核對，不參與一般引用 |
| `ARCHIVED_SOURCE` | 不可變的原始來源／對話事件，不是現行分析入口 |
| `REMOVED_FROM_WORKTREE` | 已從目前檔案樹移除；不代表 Git 歷史被清除 |
| `PURGED_FROM_HISTORY` | 指定版本來源已從某個明確範圍永久清除；必須記錄其範圍與備份狀態 |
| `RESTORED_AS_NEW_CURRENT` | 從明確來源恢復內容並通過新一輪驗收 |

Git 提交歷史不是工作目錄三版本上限的同義詞。刪除 Git 目前路徑通常不會自動清除過去提交中的正文。任何改寫 Git 歷史或永久刪除操作都視為高風險操作，必須明確授權、先做備份與影響評估；本規範本身不授權改寫歷史。

## 9. 驗收條件

一個主題只有同時符合以下條件才可標記為 `GOVERNED`：

- 正好一份 CURRENT MASTER；每個現行分支都有穩定 ID 和清晰唯一責任。
- 每個一般邏輯文件不超過 3 份可直接調閱的完整版本。
- MASTER 不超過 6,000 字元，所有一般 AI 可讀文件不超過 8,000 字元；例外已明確登記。
- MASTER 與每個彙整分支都有開頭摘要、TOC 和可用索引。
- 現行引用皆指向 MASTER 或 CURRENT BRANCH；舊版不承擔一般知識功能。
- 每條引用具有可反查的 incoming/outgoing 記錄；完整掃描前清楚標示覆蓋率。
- 重要歷史變更、刪除、取代、恢復、來源與內容指紋均可追溯。
- 來源、獨有證據、反例、限制、未知和衝突未因蒸餾而遺失。
- 全部變更讀回驗收成功；未執行項目沒有被標記為 PASS。

## 10. 來源、限制與待辦

本規範是基於現有 forAVAr 的去重蒸餾規範、唯一職責矩陣、檔案稽核、P2 封包主分析及多輪分析文件分流經驗制定的治理規則。這是明確的執行規格，不代表目前已經有程式自動限制版本、計算字數、驗證回鏈或阻止刪除。

初始落地仍需完成：全庫 `DOC_ID/TOPIC_ID/BRANCH_ID` 登錄、歷史事件摘要回填、所有引用的雙向掃描、超長分析文件分流與驗收。完成前，對未稽核區域維持 `PARTIAL`，不得宣稱全庫治理已完成。
