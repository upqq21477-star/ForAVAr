## 1. 根因與設計裁定

這輪不是再新增一套刪除 SOP。現有流程已定義分支檔案刪除、引用盤點、中斷恢復與歷史清除界線；主要缺口是原始短期材料在寫入長期 Git 歷史前，沒有清楚的資料准入決策。

同 repository 的專題資料夾只能隔離路徑與責任，不能隔離 Git 歷史。若整批資料預計結案後退場，獨立暫存 repository 是候選的歷史隔離方式；刪除 repository 仍不等於保證所有副本或歷史內容不可恢復。

## 2. 本次文件變更

- 完善主／暫存 repository 分流提案，增加敏感度與准入規則、批次生命週期、主庫寫回驗收、刪除狀態界線、失敗恢復與採納門檻。
- 新增暫存 repository 開案卡／結案清單模板，規定批次 ID、來源數量對帳、資料准入、主庫讀回及刪除結果的獨立狀態。
- 更新專題工作區入口：先判斷資料准入與預定保留期，再選長期主庫資料夾或短期 repository 候選路徑。
- 更新 README 與全域索引，增加候選文件入口；沒有改寫正式退場藍圖、現行 SOP 或能力登錄。
- 更新專題歸因規劃，補充資料夾路徑隔離與 repository 歷史隔離不同，防止兩個候選流程互相矛盾。
- 將退場事件中的專題識別詞及特定批次提交識別碼從目前版本移除，僅保留通用刪除數量、方法與驗收界線。

## 3. 驗收結果與限制

- 新提案、模板、README、專題工作區入口與全域索引皆可讀回；提案／模板標記為候選，尚未實際批次試行。
- 已對 12 份直接相關的治理／導航文件進行限定詞掃描，未命中已指定的舊專題識別詞；GitHub 搜尋亦回傳零結果。這不是全 repository 全文掃描，不能宣稱所有文字殘留為零。
- forAVArb 仍為私人、空庫狀態；本輪沒有向其寫入資料，也沒有進行任何 repository 刪除。
- Git 歷史沒有改寫。歷史中先前提交的物件／文字可能仍可讀；本次目前版本去識別化不能等同永久歷史清除。
- 未量測實際工時、返工率或多批次成效；尚不能宣稱此候選比原流程更有效率。

## 4. 下一階段

1. 以一個無敏感資料、範圍清楚的批次進行試行前演練。
2. 按模板核對來源數量、唯一證據、主庫准入、寫回讀回、未完成依賴及刪除狀態。
3. 在第二個獨立批次重複驗收後，才比較操作成本與漏失情況。
4. 若要把候選方案合併進正式藍圖／SOP，另行依現有前後方案比較閘門與明確「更新企劃」授權執行。
