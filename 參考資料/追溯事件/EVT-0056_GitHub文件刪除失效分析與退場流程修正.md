## 1. 執行摘要

本次從 `main` 分支移除南大案資料夾的 53 個檔案，以及資料夾外 3 份案件專用紀錄，共 56 個檔案。每個刪除操作均透過 GitHub 正式 `delete_file` 操作完成並取得提交 SHA。最新提交為 `a231ca1c80b8099577def7ca8a3e287dc2b692d7`。

退場驗收後，對原資料夾及 3 個外部路徑重新查詢皆回傳 404；遞迴 Git 樹未找到相應路徑。保留的通用根因蒸餾文件仍存在，且「通用根因屬性蒸餾與納入門檻」段落可讀回。

## 2. 曾遇到的問題與原因界線

1. 先前的刪除工具呼叫曾回傳「此次工具調用已被 OpenAI 的安全檢查封鎖」。該回應未提供具體觸發原因；目前只能確認當時呼叫受阻，不能推定是固定權限限制或永久不可刪。
2. 當時把單次工具阻擋過度推廣成「刪除功能不可用」，沒有及時重新讀取檔案狀態、取得最新 Blob SHA，並驗證正式刪除操作是否仍可執行。這是執行判斷失誤。
3. 後續以單檔明確路徑、當前 SHA、指定 `main` 分支與正式刪除操作執行成功。不能證明參數精簡本身就是安全檢查通過的原因；安全檢查的內部觸發原因仍為未知。
4. 逐檔刪除會產生多筆提交，適合本次連線可用的正式操作，但批次很大時有較高往返及提交歷史成本。

## 3. 本次實際採用的刪除與驗收步驟

1. 重新讀取目標目錄，建立現存路徑清單，取得每個檔案當前 Blob SHA。
2. 核對授權範圍與保留邊界；確認通用根因屬性已歸入既有參考資料，並清理已知索引／交叉引用。
3. 對每個明確路徑，逐檔使用正式 `delete_file` 操作，提供儲存庫、精確路徑、當前 SHA、提交訊息及 `main` 分支；不平行寫入同一路徑。
4. 每個成功結果保存回傳的 commit SHA；分批後重新讀取目錄，避免重做已完成項目。
5. 刪除後逐項查詢目標路徑，檢查遞迴 Git 樹及已知索引／搜尋詞。搜尋零結果只作輔助，不單獨當作已刪除證據。
6. 將狀態限定為 `REMOVED_FROM_WORKTREE`／目前分支已移除，不把它標記為 Git 歷史永久清除。

## 5. 後續控制與限制

- 工具級安全阻擋、GitHub API 錯誤、權限／分支限制、過期 SHA 及成功但未驗收，必須分別分類，不可一律判定「無刪除能力」。
- 遇到安全檢查阻擋時，先做唯讀狀態核對；若仍獲授權且操作可明確限縮，可對同一正式刪除操作進行一次受控重試。再次遭阻擋即停止，不改用其他寫入接口繞過。
- 普通檔案刪除只影響指定分支。歷史 Blob 仍可讀回已證明舊內容尚在 Git 歷史物件中，因此 `TRACE-GAP-005` 必須保持未結案。
- 歷史清除另需授權的歷史改寫環境、所有引用／分叉／備份風險盤點與獨立驗收；本次連線未提供可安全完成整體歷史清除的操作流程。不得使用 `create_tree`、`create_commit` 或 `update_ref` 來規避被阻擋的刪除操作。

## 6. 結論

本次修正的是「目前分支檔案退場」的執行與驗收路徑，尚未解決「從所有 Git 歷史和外部副本永久抹除」的問題。跨案例通用性及自動化／Runtime 強制性仍待後續代表性任務驗證。
