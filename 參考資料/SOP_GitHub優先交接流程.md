## 1. 定位與觸發

本 SOP 是既有文件治理與 CF-004「對話成果轉成可追溯文件」的專用分支，由 SOP-META-001 管理選用、授權、執行及驗收。跨對話狀態沿用既有 StateBundle／工作封包與文件生命週期契約；本 SOP 不另建封包格式、路由引擎、認知骨架或新的 CF 流程。

符合任一條件即啟動：
- 使用者明確要求準備或執行交接。
- 工作即將轉移至新對話、其他執行者或不同工作環境。
- 工作涉及多份文件、重大決策、測試證據、未完成事項或權限限制，對話中斷容易使狀態遺失。
- 工作暫停或階段性結束，仍有待辦、阻塞、未知或放行條件須保留。

未達觸發條件、沒有跨階段延續需求的一次性問答，不建立交接包。明確交接要求不能只以聊天文字宣稱完成。

## 2. 儲存位置與權限

- **forAVAr：** 正式藍圖、已採納規格、權威 SOP、正式索引與變更追溯。正式更新依使用者授權及既有版本治理執行。
- **forAVArb：** 研究、驗證、候選、暫存及交接紀錄。交接包預設寫入 `交接/` 並更新該目錄 README；如屬其他專案，改存該專案政策允許的交接位置。
- **P1／P2：** 永遠只讀；不得新增、修改或刪除。工具顯示有寫入權限不代表獲得授權。
- 一次只向明確允許寫入的 repository 寫入。交接內容引用正式權威來源，不把候選稿寫成正式規格。
- 不保存密碼、存取權杖、私鑰、敏感個資或未獲授權上傳的材料。私有 repository 不代表可忽略資料准入規則。

## 3. 交接文件最低內容

交接文件保留下一位執行者恢復工作所需的最小充分資訊，不是逐字對話備份。

1. **身份與目標：** 專案、工作主題、交接日期、文件版本及本次預期成果。
2. **權威基線：** repository、branch、正式入口、版本；可取得時記錄 commit、tree、blob SHA。明確區分正式規格、參考來源與候選材料。
3. **已完成及證據：** 已完成事項、實際觀察結果、必要來源連結與證據指紋。僅寫真正執行或讀回的內容。
4. **未完成與未知：** 待辦、阻塞、衝突、缺少輸入／證據、所需授權及不確定項目。
5. **下一個動作：** 指定優先順序、明確操作、預期產物與放行條件；不得只寫「繼續研究」。
6. **權限與禁止事項：** 可寫、只讀、禁止操作、變更授權及必要的回復邊界。
7. **已做工作與避免重工：** 已掃描文件、研究問題、已執行測試、結果與對應 SHA；指出何種條件變化才需要重檢。
8. **真實測試狀態：** 分別記錄文件提交、讀回／靜態檢查、模擬、程式測試與 Runtime。可使用 `NOT_RUN`、`NOT_EXECUTED`、`BLOCKED`、`FAIL`、`PASS_STATIC`、`PASS_SIMULATED`、`PASS_RUNTIME`、`INCONCLUSIVE`；只可在相應證據存在時標記 PASS。
9. **接手啟動題詞：** 可直接複製至新對話，要求先讀交接與必要索引、核對最新 GitHub 狀態，依未完成項續作。
10. **必要回鏈：** 交接包索引、正式基線、直接相關文件及證據。原文已存在時優先連結與記錄 SHA，不重貼全文。

## 4. 標準執行步驟

依 SOP-META-001 的 `INTAKE → AUTHORIZE → SELECT_SOP → PLAN → EXECUTE → VERIFY → PERSIST → REVIEW` 執行；按下列交接專用步驟細化，不取代上層流程。

1. **確認基線：** 讀取最新 repository default branch／指定 branch 與必要文件；記錄當前 commit SHA、相關 blob SHA、實際路徑和文件狀態。不得將提示中的舊版本當成最新。
2. **選擇最小範圍：** 讀取相關索引與既有交接紀錄，確認是否已存在同一交接任務的有效文件；不為了交接而重掃無關全庫。先分清正式基線、候選資料及現況證據。
3. **整理恢復狀態：** 以最小充分資訊記錄已完成、未完成、未知、權限、測試真實狀態與下一個具體動作；沿用既有 StateBundle／工作封包契約，不複製另套 schema。
4. **寫入交接文件：** 以專案／主題／日期／版本命名，保留必要歷史，不靜默覆寫上一份不同階段交接。按 repository 權威分工選擇位置。
5. **更新索引：** 更新該目錄 README 或既有權威索引。每個文件只保留一個現行操作入口；候選來源需標記其狀態及正式替代來源。
6. **讀回驗收：** 從 GitHub 再讀取剛建立／修改的交接文件與索引；核對實際存在、內容、路徑、SHA、連結及狀態相符。必要引用應實際開啟／讀取以確認可達。
7. **核對真實狀態：** 確認未將候選規格寫成正式採納、未把未執行測試寫成通過、未超出允許的 repository 範圍。保留變更前後差異、修改理由、驗收與未知。
8. **記錄並回報：** 按 SOP-META-001 在執行台帳新增精簡紀錄；重要範圍變更在追溯索引新增事件。只有讀回與必要連結檢查通過才可回報「交接完成」。

任何寫入或讀回失敗時，標記 `PARTIAL` 或 `BLOCKED`，讀回實況並只修復不一致項；不得在未確認前宣稱完成。

## 5. 新對話接手規則

新接手者按以下順序操作：

1. 先讀交接文件、它指向的 README／索引及指定正式基線，不要求使用者重述交接文件已記載的資訊。
2. 核對當前 GitHub branch／commit／相關 blob SHA，確認交接快照是否仍有效。
3. SHA 未變且證據仍適用時，沿用既有檢查結果；僅在版本已變、引用失效、證據不足或受影響條件改變時，重查相應範圍並記錄差異。
4. 先處理最接近解除阻塞的明確動作；不得只因更換對話就無理由重做全部研究或讀取全庫。
5. 保持原權限邊界。若當前狀態與交接衝突，以核實後的現行正式文件及實際 repository 狀態為準，並記錄衝突。
6. 所有尚未執行的檢查仍保持未執行狀態，不能依交接文件中的計畫推定通過。

**可直接複製的新對話啟動題詞：**

> 請先讀取我提供的 GitHub 交接文件及其指定的 README／索引，將其作為本工作續接入口。不要要求我重述文件已有內容，也不要先把全文貼回聊天。核對當前 repository、branch、commit／blob SHA 與正式基線；若版本未變且證據仍有效，沿用既有結果，只重查變更影響範圍或證據不足處。遵守交接文件列明的寫入授權、P1／P2 唯讀限制及禁止事項。優先完成下一個明確動作與放行條件。不得把候選規範當成正式規格，不得把未執行測試說成通過。完成實際讀回與必要驗收後，再更新 GitHub 交接紀錄；聊天只回報連結、關鍵狀態、阻塞及下一步。

## 6. 驗收與狀態

交接的最低驗收項：

- [ ] 交接文件實際存在於被允許寫入的 repository／branch。
- [ ] 正式基線與相關 SHA／路徑已核對；未知欄位明確標示。
- [ ] 必要欄位足以恢復工作，下一個動作及放行條件明確。
- [ ] 交接文件及索引已從 GitHub 讀回；連結與狀態符合實際結果。
- [ ] repository 寫入邊界、P1／P2 唯讀與未授權項沒有被違反。
- [ ] 測試狀態與證據一致；未執行、失敗、受阻與通過沒有混用。
- [ ] 執行台帳及必要追溯入口已更新。

狀態字義依實際證據判定：`PASS_STATIC` 只代表指定文件／連結等靜態檢查通過；`PASS_SIMULATED` 只代表指定模擬通過；`PASS_RUNTIME` 必須有真實 Runtime 執行證據；`NOT_RUN`／`NOT_EXECUTED` 不代表通過；`BLOCKED`、`FAIL`、`INCONCLUSIVE` 必須保留其原因。

本 SOP 目前是由文件治理採納的手動流程，不代表已有工具或 Runtime 自動觸發、阻止未授權操作或保證交接成功。跨任務效果須由代表性案例及回歸紀錄驗證後再更新成熟度。

## 7. 聊天回報限制

預設只回覆：
- GitHub 交接文件連結。
- 目前最重要的 1–3 項狀態。
- 尚未解除的主要阻塞及下一個動作。

除非使用者明確要求，不重貼交接文件全文、不重複貼出已存在 GitHub 的大量內容，也不把聊天回覆當成交接保存位置。
