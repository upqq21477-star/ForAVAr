# SOP：全系統教授級反方評審與優化方案驗收

- DOC_ID：FORAVAR-SOP-REDTEAM-REVIEW-001
- SOP_ID：SOP-REV-001；流程索引：CF-011
- 版本：v0.2
- 狀態：TRIAL／v0.2 補入運作模型現況還原及規格／實作分層；尚未完成跨任務及 Runtime 驗證
- 唯一責任：對系統、架構、SOP、重大工程方案進行全面性反方審查，產生可反證的優化方案，並對方案再做第二輪教授級評價。
- 依賴：[SOP-META-001](./SOP固定流程與演化管理.md)、[方法選擇框架](./解析文檔/通用問題屬性導向方法選擇框架_v0.2.md)、[能力登錄](./功能清單_基礎能力覆蓋登錄_v0.1.json)、相關問題清單／主藍圖。
- 範圍界線：此 SOP 優化系統級、架構級與高影響決策；不取代領域專用測試、資安測試或正式授權流程。

## 1. 核心原則與方法關係

**反向思維不再作為一個沒有邊界的泛用口號，而是納入本 SOP 的反方攻擊階段。** 本流程在系統級評審時取代未結構化、沒有驗收條件的「只做逆向批判」做法；不移除逆向思考作為局部方法。反方審查只是手段，判斷依據是證據、可觀察結果及成本。

- 先重建目標、權威基線、現有能力和真實狀態，再提新方案；不得先挑工具或預設架構正確。
- 將「沒有淨收益」設為必須認真檢驗的零假說；同時檢查支持與反對證據。
- 先試圖修正／組合既有能力；只有契約或責任確實無法承載，才提新增。
- 安全、授權、不可逆操作及重大正確性要求屬硬性 Gate，不能被效率或平均分抵銷。
- 將文件規格、靜態檢查、桌上推演、實際測試與 Runtime 行為分開標記；未做的測試不得宣稱通過。
- 每一項批判都要形成「證據／推論 → 影響 → 可行控制 → 可驗收測試」；純粹負面評論不算完整評審。
- 複雜度由任務、風險和可觀察效益證明，不因架構更完整或版本更新就升級採用。

## 2. 觸發條件與免用條件

**啟用：** 系統／架構重設、SOP 重大改動、自我改善機制、平台／工具選型、跨模組治理、效能／成本爭議、重大反覆失敗，或使用者明確要求整體批判與指導教授式評審。

**不啟用完整流程：** 一次性低風險問答、格式修正、已定義 SOP 可直接完成的單一任務。此類只用必要檢查，不為了「全面」而生成大型評審。

若存在高風險或不可逆動作，即使只評審一小部分，權限和安全 Gate 仍需保留。

## 3. 強制工作流程

### R0｜任務契約與授權

明確評審對象、預期決策、成功條件、範圍、排除事項、利害關係人及允許寫入位置。確認 repository／文件權威、存取權限和使用者授權；文件宣告唯讀但實際帳號可寫時，記錄權限落差並阻擋寫入。未獲正式企劃更新授權，不改寫正式企劃正文。

輸出：評審範圍、接受條件、權限／風險限制。

### R1｜恢復基線與實作狀態

先讀最新權威文件、相關 SOP／問題 ID、能力清單、依賴與近期變更。分開標示：已提出、已記錄、已實作、已測試、已 Runtime 驗證。檢查重疊責任、過期版本、未決衝突、現有能力可否修正／重用。不得只讀新提案，也不得將全庫未讀誇稱已完成審計。

輸出：基線快照、依賴／責任圖（按需）、已知缺口與未知。

### R1.1｜運作模型現況還原（系統運作評審必做）

當評審對象是整體運作方式，必須先畫出 AS-IS 流程，不得只讀目標藍圖便評分：

`請求／問題 → 任務契約與授權 → 查找權威文件／能力 → 選方法與工具 → 實際執行 → 驗收／回讀 → 結案或失敗分流 → 必要持久化與下次恢復`

對每個步驟標記證據層級：`DOCUMENTED`（文件規定）、`MANUALLY_ORCHESTRATED`（由模型／操作者當次判斷）、`TOOL_EXECUTED`（實際工具呼叫）、`TESTED`、`RUNTIME_OBSERVED`。不能由文件中出現路由／節點名稱推定已有可執行路由器。

同時繪製兩條子流程：
- **問題處理：** 發現問題 → 正規化症狀／重現條件 → 查既有 PR／SOP／能力 → 提出根因假說 → 選最小修正／實驗 → 核對原失敗與回歸 → 標記 RESOLVED／MITIGATED／PARTIAL／BLOCKED／UNKNOWN → 有證據後才提 SOP 候選。
- **能力調取：** README／全域索引 → 能力登錄及分支 manifest → 唯一權威 SOP／PR／來源 → 確認實際可用工具／skill → 呼叫並記錄結果 → 獨立驗收。能力清單、功能映射、Skill 說明與真正可呼叫的工具是不同實體；不存在 dispatcher 時，必須明說路由由當次模型／操作者選擇。

**檔案治理也要畫出實際資料流：** 哪裡是正式權威、哪裡是驗證／暫存資料、哪些來源唯讀、如何建立／更新／讀回、如何更新索引與台帳、何時封存／退役，以及哪些步驟只是人工規則、哪些有實測證據。標記部分提交、歷史殘留、來源衝突及下一次工作階段必須重新載入的入口。

輸出格式至少包括：現況流程圖／序列、每步機制與權威來源、實際接線證據、主要故障路徑、未自動化的人工控制及置信限制。再將 AS-IS 與藍圖 TO-BE 對照，列出設計符合但尚未實作、實作存在但未驗收、直接矛盾和未知四類差距。


### R2｜定義可反駁的問題與假說

先問「系統究竟要改善哪一個可觀察結果？」再設定零假說和替代假說。例如：H0＝新增流程不會改善正確率／漏失／返工，卻會增加成本；H1＝特定控制在明確任務類型中改善預先指定的指標。訂定比較基線、成功條件、不可接受退步及需要的證據；不准事後改門檻來讓方案通過。

輸出：假說、結果指標、底線 Gate、否證條件。

### R3｜教授級反方攻擊

從以下角度選擇適用項，逐條攻擊核心與下游框架：

1. **目的偏移：** 是否把工具、流程、治理或文件本身當成目的？
2. **必要性／重複：** 每個主軸、節點、狀態、角色和步驟是否有唯一責任及獨立收益？移除後會在哪個真實案例失敗？
3. **正確性／證據：** 是否混淆事實、推論、未知、相關與因果？引用是否真的支持主張？
4. **共因／自我驗證：** 設計者、執行者及評分者是否共享同一假設？重述、角色拆分或多模型是否真正提供獨立訊號？
5. **效率／規模：** 端到端時間、上下文、檢索、工具、澄清、返工、維護、遷移及未來能力增加後的成本如何？
6. **安全／權限：** 是否只靠提示或文件守則，而非執行層權限？是否存在越權、提示注入、不可逆副作用和失敗後無法回復？
7. **失效／反例：** 前提不成立、依賴失效、來源過期、狀態衝突、空庫、失憶重啟或部分提交時，系統會如何失效？
8. **演化與退場：** 能否只改受影響範圍？新節點如何准入、替換、回退與退役？紀錄是否會膨脹及產生重複權威？

每一項列出：嚴重度、觀察證據、推論與信心、影響、發生條件、既有控制、反例／反對理由、建議修正及驗收方式。避免稻草人論證；必須同時呈現最強支持論據和最強反方論據。

### R4｜外部研究與業界對照

對時效、技術、業界慣例或學術主張進行外部查證。優先使用官方文件、原始論文、基準／評測報告和可追查資料；重要結論盡可能用不同來源互相核對。記錄來源日期、適用情境、方法、限制和能支持的範圍。供應商文章可證明其公開建議，不能單獨證明普遍因果。

將外部方法映射至本系統的具體缺口：能重用、需要改造、不能直接套用及成本／依賴。無法查證時明確標示 EXTERNAL_EVIDENCE_NOT_VERIFIED；不得填入虛構研究。

### R5｜全域影響與元件逐項判定

對主要模組、流程及規則建立精簡清單，逐項選擇：保留、修改、合併、條件式啟用、降為參考、實驗、退役或未知。評估目的吻合度、證據強度、重複責任、邊際效益、執行成本、故障模式、下游依賴、遷移／回退和退場條件。

不得因評審要「全面」就把所有模組都重建一遍。依影響擴大檢索；若共享契約、權限、核心狀態或依賴範圍不明，才擴大到架構級。候選新增必須先證明既有能力無法修正／擴充。

### R6｜提出可比較的優化方案

至少比較：
- **A｜不變更／保留基線：** 清楚列出目前已知成本與風險。
- **B｜最小修正／薄核心：** 重用既有能力，只新增不可或缺的控制。
- **C｜較大改造：** 只有在已知缺口無法靠 B 解決時才列入。

比較預期收益、證據、風險、成本、時間、依賴、可逆性和未證實假設。明確推薦一個選項與適用範圍；不要把多方案並列當作已解決決策。優先將複雜度條件式啟用，不把高成本流程變成所有任務的常駐負擔。

### R7｜第二輪教授評審（必做）

把**優化方案本身**當成新的待攻擊對象，重跑精簡版 R0–R6，至少回答：
- 方案是否解決原根因，還是只增加文件／流程？
- 是否引入新依賴、權限漏洞、回歸、資料同步或維護成本？
- 有沒有更簡單、成本更低或更容易回退的替代方案？
- 測試是否能推翻方案；評分者是否獨立，是否有保留案例？
- 指標、樣本、預算、責任人、停止條件和失敗退路是否具體？
- 哪些主張仍是推論、哪些不能在目前工具環境實作？

如果第二輪找到致命缺陷，先修訂方案，再評一次；仍未消除時判定 NO-GO／BLOCKED，不得因前一輪分數高就採納。

### R8｜配對試驗與採納門檻

在可安全執行的範圍中，固定或記錄模型版本、輸入、工具權限、測試條件和評分尺規；盡可能使用同任務配對比較、隨機執行順序、盲評、獨立標註或客觀測試。測試集應涵蓋簡單任務、來源衝突、因果／根因、開放式研究、失敗恢復和授權邊界中與方案相關的情境。以小型試點修正量尺，再按觀察到的變異與欲辨識效果決定樣本量，不任意宣稱少數案例代表全體。

至少量測：任務正確／接受條件通過、重大漏失、未知處理、Gate 違反、端到端耗時、token／檢索／工具成本、返工／回復、使用者澄清、文件新增與維護成本。品質與成本分開報告；硬性安全／授權失敗不可由其他分數抵銷。

- GO：硬性 Gate 通過，且預先指定的必要品質底線不退步；至少一項目標指標有可重現淨改善。
- PARTIAL：只在特定任務／風險級有效，縮小適用範圍。
- INCONCLUSIVE：基線、樣本、測量或評分一致性不足。
- BLOCKED：授權、資料、環境或必要獨立驗收缺失。
- NO-GO：無淨收益、成本不合理或有未緩解的重大缺陷。

### R9｜最小實施、回歸及結案

只有取得必要授權且方案過關後，才執行最小差異更新。讀回每個改動檔案，核對連結、索引、責任、權限和回退；程式行為需有實測，不能以文件寫入代替 Runtime。失敗時標記 PARTIAL，僅修復不一致部分。

回報：裁定、主要優缺點、評分與依據、推薦方案、測試結果、成本、未決項、回退方式及下一個行動。紀錄存於唯一責任文件；只把簡短入口放進索引／台帳，不複製全文。

## 4. 效率控制與停止規則

- **按需啟動：** 低風險一次性任務不啟用本 SOP。一般架構評審執行相關步驟；不相關的安全或資料模組標 N/A 並記理由。
- **停止研究：** 下一項研究不太可能改變決策、關鍵風險或驗收結果時停止；重大未知若仍影響安全／正確性，則以 BLOCKED 收口，不得假裝已解決。
- **禁止驗證迴圈：** 同一方法／相同證據重跑沒有新資訊時停止；只有新資料、不同假說、修正或預先定義的測試理由才可重試。
- **文件節制：** 新內容先查現有能力與唯一責任；一般成功不另建長報告，只有使用者要求持久化、出現重大決策或需獨立複核才建檔。
- **成本完整：** 比較成功任務的總成本，不只算步數或 token，也計入返工、失敗影響、人工負擔與未來維護。
- **評分誠實：** 分數必須列量表、權重、證據與信心；主觀專家估分不得冒充統計結果。硬性 Gate 不進入可互相抵銷的平均分。

## 5. 最低交付與驗收清單

結案前核對：
1. 基線與原始目標已恢復；現況、設計、實作、測試和 Runtime 狀態沒有混淆。
2. 核心假說、零假說、接受條件和否證條件在評估前已明確。
3. 反方意見含證據、影響、嚴重度、修正及可驗收測試；支持論點沒有被故意弱化。
4. 外部研究可追查，來源適用性與限制已交代；未查證者保持未知。
5. 既有能力的去重／擴充優先於新增；每個建議模組有成本、觸發條件和退場標準。
6. 有不變更、最小修正與較大改造的比較；推薦方案有清楚的適用範圍。
7. 已對優化方案進行第二輪反方評審，並根據缺陷修訂或拒絕。
8. 試驗方式能區辨方案與基線；沒有把同源自我評論當獨立證據。
9. 分數、GO／NO-GO、未知、未測項、授權及安全 Gate 狀態明確。
10. 寫入範圍合規；讀回與必要回歸已完成，其他未執行項標 NOT_VERIFIED。

若第 1、2、7、9 項任一不成立，評審不得裁為「已驗證成功」。若重大授權／安全缺口未受控制，不得批准相關寫入或部署。

## 6. 業界方法參照及限制

- Anthropic, [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)（2024-12-19）：支持以簡單、可組合模式起步，只有在測得有益時才增加複雜度；是工程指南，不是 forAVAr 成效證明。
- OpenAI, [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)：任務特定資料、評分規則、配對比較與持續評測；不得以主觀「看起來有效」取代測試。
- METR, [2025 developer productivity study](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/) 及 [2026 experiment-design update](https://metr.org/blog/2026-02-24-uplift-update/)：效率結果受任務與研究設計影響，必須明示樣本／測量限制。
- NIST, [AI RMF risks and trustworthiness](https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/)：有效性、可靠性、安全與部署後評估應依使用情境管理；不是可直接照抄的萬用步驟表。

外部方法只作評審依據，不代表來源已評估或核准 forAVAr。本 SOP 仍處 TRIAL；文件化不等於已自動載入、被工具強制或具跨任務淨效益。
