## 5. 分批處理狀態與順序

1. **B1｜封包 B 結構與內容：完成初步解析。** 4 個成員均可解壓，解壓大小與 CRC32 一致；企劃書仍是 PROPOSAL，不代表 P2 已採用。
2. **B2｜封包 B 雙格式比較：進行中。** 對話紀錄標題覆蓋 75/75，企劃書標題覆蓋 72/72；雙向正文初篩未發現高可信度的實質章節缺失，且表格分組／資料列數精確對應（對話 9 表／59 列、企劃書 4 表／78 列）。對話紀錄仍有一處範圍說明措辭差異，5 個 sandbox 連結在 DOCX 中未保留可點擊行為；逐字等價尚未證明。
3. **A1｜封包 A 讀取：BLOCKED。** P2 唯讀儲存庫也存有相同 Git Blob SHA（`0e58526bd35c30a25f3b27033a4952ec5f25bf10`），但從 P2 取回仍遇到同一二進位限制。P2 目前 tree 與精確路徑歷史查詢均未找到交接所指的規劃檔及四個輔助腳本；它們列為 ZIP A 的優先查找目標，但還不能宣稱是 ZIP 成員。不能據此判斷封包損壞。
4. **A2｜封包 A 內部解析：待 A1 解阻。** 取得位元組後，先盤點成員與 CRC，再按 manifest／啟動規程／Current／藍圖／程式／測試／工具分批分析。
5. **C1｜跨文件去重：已建立矩陣，持續補證據。**
6. **C2｜最終蒸餾：待封包 A 與封包 B 正文差異完成後迭代。**

## 6. 絕對限制

- ZIP 原始位元組不可修改；解析結果另存並記錄來源。
- Git Blob SHA 是 Git 物件識別碼，不等於裸檔 SHA-256 或 ZIP 成員 CRC32。
- 「可解壓」「CRC 通過」「文字等價」「語意完整」「實際執行通過」為不同證據層級。
- 不以 HANDOFF、摘要或提案取代原始程式、權威 Current、測試輸出或實際執行證據。
- 所有未知、假說、來源主張與直接驗證結果都要分開記錄。
