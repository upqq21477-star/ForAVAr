## 1. 核心判斷

它的工程價值不在於「多開幾個代理」，而在於把現代化工作限定為可追溯的產物流程，將模型提出的分析／改寫與可程式驗收的證據分開。

主要結構：命令契約 → 專業代理 → 有界工作流 → 驗證腳本 → 報告／可選面板。各階段依賴固定產物交接；必要輸入缺失時應停止，不依賴聊天歷史猜測狀態。

## 2. 三種改造策略

| 策略 | 適用目標 | 關鍵界線 |
|---|---|---|
| Uplift | 保留技術路線，升級版本或工具鏈 | 先確認基線、做單一試點、形成 PLAYBOOK，再依相依分批擴展 |
| Transform | 保留模組行為，改用其他技術重寫 | 先抽取規則與建立特徵測試；以相同輸入比較舊新行為 |
| Reimagine | 以新架構重建 | 先把舊系統抽取成規格並經架構審查；行為變更需明確批准 |

三者不可混用；不能借升級之名無必要地全量重寫，也不能把未批准的行為變更藏在重建裡。

## 3. 核心驗收：Proof Pack

驗證器自行讀取證據，而非採信建置代理的「完成」聲明。主要檢查：

1. 測試確實執行，讀取可解析的真實測試結果。
2. 關鍵規則有實際執行且通過的測試支持。
3. 舊新行為或版本基線符合預定比較條件。
4. 使用開發測試之外的新輸入做實際比對。
5. Canary 故意破壞有意義的行為，確認測試會失敗。
6. 檢查舊程式對照組是否被修改。

判定包括 `PROVEN`、`PARTLY PROVEN`、`NOT PROVEN`。它們只代表工具所定義的檢查條件是否有證據支持，不是對整個系統絕對正確的形式化證明。舊系統無法執行、關鍵證據缺失或存在行為差異時，不應宣稱完整通過。

## 4. 協調、安全與限制

- 先做環境盤點、依賴映射、規則抽取與人工審查，才批准施工計畫。
- 多代理需有明確分工、寫入邊界、相依排序、有限批次、熔斷條件及可重跑清單。
- 舊程式、註解和文件視為不可信資料；規則與安全發現需有來源引用，修補候選需審查。
- 比較器允許遮罩或數值容差，但放寬須有明確理由與記錄。
- 大型工作流有真實的協調及推理成本；分塊、覆核、重跑與報告不可視作免費，也不能假定靜態分析等同真實執行。

## 5. forAVAr／P2 可移植原則

優先重用既有能力，採用產物契約、有界工作單元、前置依賴檢查與獨立驗收；施工者不得自行裁定驗收成功。保留真實執行、模擬、未驗與假說的差別，不另造一套重複生命週期。先確認既有能力的 REUSE／MODIFY／MERGE／NEW，再決定是否建新功能。
