## 1. 核心裁定與非目標

**思考仍是唯一核心；架構、能力、角色、流程、工具、檔案與治理均為手段。** 目前沒有足夠證據支持推翻原始核心、增加第五個認知層，或讓治理程序取代思考。本版修正的是入口、流程觸發與證據標記，不擴張認知主軸。

不得以更多節點、文件、角色或檢查步驟本身作為能力改善證據。低風險簡單任務保留短路；全庫掃描、專家評審、持久化及重型驗證按明確條件啟用，不作每個任務的固定成本。

## 2. 核心不變量與四層架構

`Core → Axes → Skeleton → Conditional Framework`

| 層級 | 固定基線 | 責任 |
|---|---|---|
| 第一層：Core | 思考核心 | 目標忠實、知識誠實、模型可修正、方法適配、品質／成本分離、可區辨驗證、受控更新、誠實收口 |
| 第二層：Axes | A1–A6 | 意圖／問題框定、證據／知識狀態、問題模型、方法選擇、求解、驗證／重框／回饋 |
| 第三層：Skeleton | N01–N18 | 將六主軸展開為可定位的責任節點；不得因新需求就假設必須新增 |
| 第四層：Conditional Framework | F0–F7 | 任務接收、框定、證據模型、路由與預算、受控執行、驗收分流、必要持久化、結案／評測 |

治理、授權、證據、工具、狀態、文件、持久化與評測是橫向支援平面，不是第五層認知架構。只有證據顯示既有節點／契約無法承載，且新項目有明確輸出、依賴、副作用、驗收和退場條件時，才可提案新增能力。

## 3. 三個流程的唯一責任

下列三套模型相互配合，不是三個競爭的工作流引擎：

1. **一般任務流程**：`INTAKE → AUTHORIZE → SELECT_SOP → PLAN → EXECUTE → VERIFY → PERSIST → REVIEW`，由 SOP-META-001 管理；依任務等級走最小必要路徑。
2. **思考操作模型**：F0–F7 是第四層條件式任務模型；依任務特性短路或回流，不要求所有任務完整跑完每節點。
3. **藍圖施工生命週期**：`PLANNING → REALIZATION → CLOSURE → FINAL_TEST`，由四梯次流程管理，只在核心／系統藍圖及整批跨功能施工時啟動。原 Phase 0–7 全屬第一梯次 PLANNING 的設計子流程，不另成平行生命週期。

整批任一項未完成當前梯次放行條件，不得進階。安全、權限、資料完整性等硬性 Gate 橫跨四梯次；第四梯次集中正式整批驗收，不代表安全檢查可以延後。

## 4. 全庫掃描及跨庫流程漏收觸發（C-07）

平常只讀取直接相關權威文件、能力登錄、功能骨架及 SOP／PR，不要求每次任務全庫掃描。僅在明確跨庫／架構稽核、流程漏收、來源索引與實際路徑不一致、核心／共享契約變更、局部範圍無法解決責任重疊，或來源掃描基線疑似過期時，才觸發全域掃描。

觸發後先讀[來源庫掃描計畫示例：P2 全庫逐批掃描 v1.0](https://github.com/upqq21477-star/P2/blob/4be3a6fe6fdea00f54821e76f1cfbf9605e4e4fe/docs/audit/P2-Repository-Complete-Scan-Plan-v1.0.md)，再依下列順序執行：

1. **先找方法，再列路徑**：先查來源 repository 已有的完整掃描計畫、Roadmap 及相關架構／Current／Policy／Schema／Runtime／Work Packet／Run Mode／Test Strategy／Skill 入口；先讀掃描計畫及條件，再遞迴列舉路徑。
2. **凍結來源基線**：記錄 repository、branch、commit SHA、tree SHA、當前 blob 數、API truncated 狀態及取樣時間。commit SHA 與 tree SHA 分欄。
3. **刷新過期分母**：歷史檔案數不直接作現行分母；現行樹與舊清冊不一致時，更新清冊並查差異，不以數量差額直接推定內容遺失。
4. **分離完成狀態**：分開記錄 `PATH_TREE_COMPLETE`、`CONTENT_REVIEW_COMPLETE/PARTIAL`、`TEST_RUNTIME_VERIFIED/NOT_VERIFIED`。樹完整不代表逐檔內容已審；未讀、不可取或未測都不得視為 PASS。
5. **沿用既有掃描法**：C-02 不獨立新增平行 SOP／引擎；按需沿用來源庫既有 A0–A9 清冊方法並刷新基線。未找到不等於不存在；不能讀取即明列阻塞。

此條款只補強既有入口的觸發與順序，不改變一般任務最小路徑，也不要求每次更新讀取上千個檔案。

## 5. 更新、範圍與責任歸位

沿用 SOP-META-001：`BASELINE → DIAGNOSE → CLASSIFY_CHANGE → MAP_OWNERSHIP → MINIMAL_DIFF → IMPACT_TEST → APPLY → REGRESSION_VERIFY → TRACE → RECURRENCE_CHECK`。

先還原原始目標、實際狀態、根因可信度及現有能力，再分類為修正、擴充、新類別、替換或退役。相同責任不得重複新增；只有證據顯示現有分類／契約不能承載時，才提新節點。R1 局部、R2 局部跨檔、R3 核心／共享契約／權限／破壞性變更，採不同深度但共用授權與範圍硬性控制。

沿用 LOAD-0–3 及 M/G/P/T。M 是分析深度，G 是操作控制，P 是持久化需求，T 是協作拓撲，彼此不能代替；不增加第五個通用路由軸。

## 6. 文件與能力退場（C-01 條件式分支）

文件退場與能力退場不同。既有文件生命週期規則繼續處理引用、來源、保留、授權、恢復與刪後驗收；**只有目標是退役能力、方法、路由或共享契約時**，才評估 load-bearing 依賴、正／負／邊界／恢復案例、替代等價性與回退路徑。

C-01 僅是條件式驗收分支，不對每次文件刪除強制加測。目前沒有真實能力退場測試，不宣稱此分支已被實證或已成為現行強制規則，也不建立第二套能力註冊／退役系統。

## 7. 證據、停止與成本控制

文件內容、成功寫入、靜態檢查、桌上推演、可執行測試與 Runtime 是不同證據層級。只有實際觀察、可回查的結果可支持相應通過聲明。

- 同輸入、同方法且無新證據時，不得原樣重複驗證；改用有區辨力的方法／來源、縮小問題，或保留未知。
- 不設普遍適用的固定重試／驗證輪數；按風險、可逆性、重大未知、必要 Gate 及新增資訊價值決定停止。
- 安全、授權、資料完整性及重大正確性是硬性 Gate，不能以平均分或成本抵銷；不明項須標 UNKNOWN／PARTIAL／BLOCKED／NOT_VERIFIED。
- 教授級反方評審是高影響任務的批判技術，不是每項任務都要加上的常規層；評審本身也須有範圍、反證與停止條件。
- 同時量測漏失、過度驗證、返工、讀取／工具成本、延遲、恢復及維護成本。無基線或保留案例時只能判 INCONCLUSIVE。

## 8. 儲存庫及權限邊界

- `forAVAr` 是唯一正式藍圖可寫主庫；`forAVArb` 保存驗證、暫存、實驗與研究紀錄。
- `P1`、`P2` 僅供唯讀。即使 GitHub metadata 回報 `admin=true`／`push=true`，也不得對兩庫寫入、刪除或做測試性修改。此為 `PERMISSION_BOUNDARY_GAP`；平台權限調整屬另一項需明確授權的管理變更。
- 寫入前核對 repository、branch、路徑、來源 SHA、授權與預期差異；寫後逐檔讀回並檢查連結和修改範圍。commit 成功不等於內容或行為通過。
- 來源映射、路徑樹完成或文件描述都不是 forAVAr 能力已實作的證明；本次沒有新能力差集，故不改能力覆蓋登錄本體。

## 9. 四梯次放行與目前證據

| 梯次 | 放行所需內容 |
|---|---|
| PLANNING | 凍結核心不變量、目標／非目標、來源基線、職責／依賴、接受條件與測試名冊；未知明列或阻塞 |
| REALIZATION | 只實作凍結範圍；規格、文件、索引及必要接線最小化且可追溯 |
| CLOSURE | 核對全批一致性、依賴、引用及回復路徑；在隔離環境做具區辨力的局部模擬 |
| FINAL_TEST | 集中完成正式回歸、整合／端到端與必要 Runtime 驗收；未執行項不可算通過 |

本次文件讀回、相對連結與核心不變量屬文件層驗收；C-07 已知案例為回溯桌上重演，不是盲測。跨任務觸發、平台權限修正、真實能力退場案例與 Runtime 行為仍未驗證。
