## 1. 本輪任務

在建立 v0.2 前，反向假設 v0.1 的混合架構與新增的討論／企劃變更治理能力即使看似完整，仍然會在真實使用中失敗。逐項尋找會使系統錯誤更新、漏記、卡住、失去版本一致性或讓使用者必須重複提醒的反例，再根據外部來源及現有文件修正架構。

本輪不是證明 v0.2 已正確。文件審查可找出結構矛盾和已知失效路徑，但架構是否有效仍須用代表性任務測試。

## 2. 逆向假設與失效案例

### RR-01｜使用者批准的是一個方案，但執行時內容已變了

**失效情境：** 系統先列出差異並取得確認，之後在實作過程中又改了欄位、整合範圍、刪除項目或受影響文件，仍以原先的「同意」為授權。

**風險：** 使用者確認的內容與實際寫入內容不一致。版本控制即使保留 Git diff，也無法取代「確認的差異是否就是這次要寫入的差異」。

**修正：**
- 每份整合方案固定記錄基準版本、目標文件、差異清單、預定寫入檔案及方案識別碼／差異指紋。
- 使用者確認只對這個範圍有效。
- 若確認後發生實質改動，必須重新列差異並重新取得確認；純排版或不改變語義的修正可依預先定義規則處理。
- 寫入前再次比較目標現況與確認時的基準；若目標在期間已被其他變更改動，先重新比對，不直接覆寫。

**外部依據：** NASA 組態管理要求對基準變更進行提案、理由與評估，經核准後再實施，並驗證實施結果；GitHub 文件也指出，若 Pull Request 的差異在核准後改變，相關審查核准可失效，需重新核准。  
來源：https://www.nasa.gov/reference/6-5-configuration-management/  
https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets

### RR-02｜把「有文件」誤當成「下次會自動遵守」

**失效情境：** 專案把能力注意事項寫進 Markdown，但新對話、不同 Agent 或不同入口沒有載入該文件，結果使用者仍須重複說明規則。

**風險：** 知識庫保存了正確規則，實際行為卻沒有被規則控制。文件完成被誤報成能力已啟用。

**修正：**
- 將討論與變更治理定義為基礎治理契約，而非僅是可選的分析 Skill。
- 架構需指定唯一的啟動載入位置與載入順序；所有新會話／研究工作從該入口讀取必要規則。
- 在啟動或任務路由的驗收測試中驗證：未經提醒仍會分辨討論紀錄與企劃更新、建立獨立研究紀錄、執行差異比較閘門。
- 在啟動載入和回歸測試尚未完成前，狀態只能記為「已文件化，尚未證明自動生效」。

**限制：** 此要求不能只靠增加 v0.2 的一段文字就保證系統每個新對話自動讀取。實際執行環境需要指定並驗證載入介面。

### RR-03｜「更新」等模糊語句導致越權寫入

**失效情境：** 使用者說「繼續」「完善」「這個修正一下」或「更新資料」，系統自行把它解讀成更新權威企劃。

**修正：**
- 分開辨識「研究／討論」、「新增或更新研究紀錄」與「更新企劃／權威規格」三種授權。
- 企劃更新需有明確目標與範圍；僅有不明確的「更新」而無法從上下文確定目標時，先停在差異／方案階段，不改權威文件。
- 不能把對研究的肯定、對候選方案的認可、同意建立紀錄，推定為批准更新企劃。
- 高風險、破壞性或跨多文件的更新需列明範圍；低風險研究紀錄可按紀錄規則進行。

### RR-04｜紀錄規則與「每個主題另建檔」衝突，造成過度碎片化

**失效情境：** 同一輪討論每一則訊息都新增檔案，或同一份長期記錄不停覆寫；前者造成檔案爆炸，後者讓輪次和決策差異消失。

**修正：**
- 「討論輪次」是紀錄文件的主要單位：同一輪仍在發展的研究紀錄可持續補充；主題不同或同主題在後續重新開展為新研究輪次時，另建新檔。
- 新檔需記錄 record_id、日期、主題、前置紀錄／承接關係、狀態、唯一責任與來源。
- 新紀錄引用舊紀錄，不複製全文；索引需可從目前紀錄找到歷史脈絡。
- 將「持續追加同一輪紀錄」和「開始新的研究輪次」的判準明確寫入治理規則，以免依賴臨時主觀判斷。

### RR-05｜差異分類變成形式儀式，卻未說明變更理由與影響

**失效情境：** 系統列出「融合、取代、保留、淘汰、待驗證」，但每一列沒有證據、理由、受影響介面或下游文件。

**修正：** 每一項差異至少要有：舊內容／新提案、分類、理由與依據、影響範圍、相容性、驗收方式、是否須使用者確認。分類是決策摘要，不得代替實質影響分析。

### RR-06｜治理程序太重，反而阻止正常工作

**失效情境：** 即使只是記錄研究結果，也必須先做完整版本比較、等待批准和跑全套驗收，成本高於記錄本身的價值。

**修正：** 採分級路徑，而非所有變更走同一個閘門：
- **R0 研究紀錄：** 建立／補充本輪紀錄，更新必要索引；不改權威企劃。
- **R1 低風險文件整理：** 不改語義、規格或權威狀態的格式／連結整理，依固定檢查表驗收。
- **R2 企劃／規格變更：** 先新舊對比、分類、影響分析，再取得使用者確認才整合。
- **R3 破壞性／跨權威／權限變更：** 明確列出受影響基線、相容性、回退及更嚴格驗收；未批准不得實施。

分級依實際影響判定，不可只依檔案大小或修改行數。若變更會改變使用者目標、權限、驗收規則或權威地位，不能因差異很短而降級。

### RR-07｜索引、職責矩陣與權威文件互相矛盾

**失效情境：** 新版已建立，README 仍指向舊版；矩陣仍將舊版列為唯一權威；紀錄中引用過期路徑。

**修正：**
- 指定每種內容的唯一 canonical source。
- 整合完成後，按依賴清單同步更新索引、職責矩陣、版本鏈和相關交叉連結。
- 寫後讀回並檢查所有新引用、舊版狀態、檔案數與連結。
- 不能在尚未重掃 Git tree 前，把推算的檔案數寫成已驗收結果。

### RR-08｜使用者確認本身失去可追溯性

**失效情境：** 只留下「使用者已同意」，但不知道他同意哪份差異、哪個範圍，或後續是否又變更。

**修正：**
- 在紀錄中保存確認所指向的方案識別碼／版本、確認時的範圍和時間。
- 不需要保存超出必要的個人資料或每句聊天原文；只保存變更授權所需的最小可追溯資訊。
- 如方案內容改變，舊確認不自動延伸到新方案。

## 3. 對 v0.1 的修正裁定

| v0.1 既有原則 | 裁定 | v0.2 處理方式 |
|---|---|---|
| 封包、能力索引、工作流、證據／版本治理分責 | 保留 | 維持核心架構，不把它們合併成一棵大樹 |
| 一項能力只有一份正式定義 | 保留並強化 | 新增討論／變更治理能力的唯一正式定位，其他文件引用 |
| 依風險與工作大小採最低足夠流程 | 保留並明確分級 | 增加 R0–R3 變更治理路徑 |
| 更新前先做影響分析與測試 | 強化 | 對企劃更新加上明確授權、確認範圍綁定與確認後差異凍結 |
| 使用者確認後才整合 | 強化 | 確認只對被展示的方案與版本生效；實質改動需重新確認 |
| 只靠文件記錄能力規則 | 不足，需補足 | 增加啟動載入責任、啟動驗收與未部署時的狀態限制 |
| 索引及矩陣在更新後維護 | 保留並加驗收 | 增加同步更新檢查及寫後讀回，避免索引成為第二套不一致真相 |
| 沒有候選通過時仍需持續演化 | 不採用 | 保留目前已驗證狀態或明確 BLOCKED；不為了產生新版本而勉強修改 |

## 4. 精煉後的治理狀態機

        │
        ├── 只需保留本輪內容 ──► RECORD_ONLY ──► 驗證紀錄與索引
        │
        └── 提出企劃更新要求
                    │
                    ▼
            TARGET_AND_SCOPE_CHECK
                    │
                    ▼
            BASELINE_AND_DIFF
                    │
                    ▼
            IMPACT_AND_CLASSIFICATION
                    │
                    ▼
            USER_CONFIRMATION
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       REJECTED          CONFIRMED
          │                   │
      保留紀錄                ▼
                       PRE-WRITE_RECHECK
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
                DIFF_CHANGED        DIFF_MATCHES
                    │                   │
               重新比較／確認            ▼
                                  INTEGRATE_NEW_VERSION
                                           │
                                           ▼
                                     POST-WRITE_VERIFY
                                           │
                              ┌────────────┴────────────┐

這是狀態設計提案。各轉移的正式名稱、最小欄位及阻擋行為須在後續 Schema／測試落地時固定。

## 5. 精煉後的架構結論

v0.2 不應把「紀錄與變更控制」做成一個可由路由器任意跳過的普通能力。較合理的設計是：

1. **基礎治理契約：** 說明工作模式、寫入權限、紀錄輪次、確認範圍與權威狀態規則；所有專案型工作必須能找到它。
2. **討論／研究紀錄能力：** 管理獨立主題與輪次的研究紀錄、來源、狀態及歷史連結。
3. **企劃變更控制能力：** 負責基準讀取、差異分類、影響分析、使用者確認、確認後差異核對與正式整合。
4. **版本與驗收治理：** 負責版本鏈、寫後回讀、索引同步、測試結果、回退及狀態標示。
5. **啟動載入與行為驗收：** 確保規則不是只存在於資料庫；在沒有使用者逐次提醒的情況下，跨新會話仍可正確執行。
6. **依風險分級：** 記錄不必走完整企劃批准；權威規格則不能跳過確認。
7. **無合格變更時允許不變：** 不為了「更新」而製造修改；保留當前版本也是有效結果。

這些是 v0.2 的推薦修改。它們保留 v0.1 的分層核心，同時填補批准範圍、實際載入、風險分級、索引一致性及無需改動時的停止條件。

## 6. 驗收框架是否正確的判定標準

目前只能判定修正版在概念上比原方案更完整地處理了已知失效路徑；不能只憑文件審查宣布「已證明正確」。建議至少用下列案例驗收：

1. 使用者繼續研究但未授權更新企劃：只建立／更新研究紀錄，不動企劃。
2. 新主題開始：建立獨立紀錄並連結舊脈絡。
3. 同一研究輪次繼續：更新該輪紀錄，不生成不必要的新檔。
4. 使用者授權更新企劃：先列出新舊差異與分類，確認前不寫入權威版本。
5. 確認後草案被實質修改：重新提出差異並取得新確認。
6. 目標文件在確認後被他人更新：基準檢查必須阻止直接覆寫。
7. 更新企劃方案的某項變更未獲批准：只整合已批准範圍，或整個方案保持待確認，依預先說明的原則執行；不得自行擴張。
8. 寫入後索引／矩陣缺漏：驗收失敗，不宣告更新已完成。
9. 新會話未經提醒：自動載入機制能找到並遵守治理契約；未測試前不得宣稱達標。
10. 反證後沒有可接受的改進：保留舊版本，記錄原因，不強迫更新。

建議比較「只寫在文件中」與「有啟動載入和行為驗收」的差異，以量測是否真正降低了重複提醒與越權修改。

## 7. 外部依據

   https://arxiv.org/abs/2609.24972

## 8. 限制與結論

- 本輪已完成對 v0.1 架構與新增治理要求的反向檢查。
- 外部工程規範支持變更需有基準、授權、狀態追蹤與結果驗證的原則；不直接證明本提案是唯一或最優實作。
- 最大修正是把「明確授權＋確認範圍綁定＋確認後變更偵測＋啟動載入驗收」納入基本治理，而不是僅增加一份注意事項文件。
- 新的討論／企劃變更控制必須成為架構的基礎治理契約；具體能力可拆分，但不得讓企劃授權 Gate 因路由簡化而被跳過。
- **v0.2 狀態仍應為 PROPOSAL。** 在使用者確認精煉框架、相關啟動載入與驗收機制沒有實際測試之前，不能宣稱它已成為執行中的基本能力或已證明完全正確。
