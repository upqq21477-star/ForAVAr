## 摘要

本規格用 R1–R3 限制變更影響範圍，用 LOAD-0–LOAD-3 限制每個任務的檔案載入量，並按任務規模採用零持久化、單一 Run Record 或正式封包。資訊欄位彼此不同，不代表每個欄位都要獨立成檔。

## 1. 核心決策

採用「小批次、範圍先定、直接依賴才擴散、按需載入、單一任務紀錄」。不得把每次更新都變成一次全庫治理；也不得為了局部變更而略過真正受影響的契約、安全控制和必要驗收。

變更小不等於永遠只改一檔；合理的邏輯變更可以同時更新實作、契約、測試和必需引用。禁止的是不相關的順手擴張，以及把所有全域治理動作套用到每個簡單任務。

## 2. 變更影響範圍 R1–R3

| 級別 | 判定條件 | 必要工作 | 不應自動觸發 |
|---|---|---|---|
| R1 局部 | 單一文件／能力內的局部修正，不改共享契約、不改權限、不破壞相容性 | 明確目標與允許路徑；讀目標及必要直接依賴；差異檢查；局部驗收；寫後讀回 | 全庫載入、全域索引重建、所有測試全跑、獨立封包 |
| R2 局部跨檔 | 同一功能的契約、程式、測試或派生視圖須同步變更 | 列出直接受影響清單；同一變更批次內更新必要物件；契約／回歸檢查；更新必要引用 | 變更無關的文件、其他主軸、非受影響的歷史紀錄 |
| R3 全域／破壞性 | 核心契約、共享 Schema、廣泛路由、跨主軸引用、權限、重大遷移或高風險退場 | 全域影響分析、明確授權、遷移方案、完整必要回歸、檢查點、回退及更嚴格驗收 | 未經證據而無限制讀取或改寫整個 Repository |

### 變更契約

持久化變更開始前，記錄以下欄位；R1 可暫存在本次執行上下文，R2/R3 視需要保存到任務紀錄或正式封包：

- change_id、目標、原因及接受條件。
- 允許修改的路徑或邏輯物件。
- 直接依賴與為什麼需要更新。
- 明確不在本次範圍內的項目。
- 基線 commit／版本。
- 驗收方法、回退點、責任與授權。
- 如果必須擴大範圍的觸發條件。

只在下列情況擴大影響範圍：測試證明有相依失敗；共享契約有變動；現行引用因改動失效；安全、權限或資料一致性要求；已確認的全域狀態需更新。發現無關問題時另開任務，不將它納入本次修改。

## 3. 局部變更的執行與讀回規則

1. 確認目標檔案、權威來源、基線版本與允許修改範圍。
2. 只讀主軸入口、目標文件及能改變本次決策／正確性的直接依賴；若不確定是否有依賴，先查輕量索引或精準搜尋，而不是預載全部檔案。
3. 寫入前先定義驗收條件和失敗出口。
4. 執行最小邏輯變更；同一變更批次包含真正需要同步的契約、必要測試和直接引用。
5. 讀回實際寫入版本，核對內容、路徑、版本、驗收結果和是否超出白名單。
6. 只有必要引用被移動、改名、取代或改變語意時，更新相應的入／出鏈；純內容小修不應重建全庫引用圖。
7. 將實際改動路徑、驗收狀態和回退依據記入執行紀錄；若未完成，明確標記部分完成或阻塞。
8. 只有 R3 或變更影響確實跨越全域時，才更新全域索引／追溯總表，並進行相應範圍的完整驗收。

若底層平台無法限制寫入範圍，就以事前白名單、差異清單、寫後路徑比較與停止規則作為必要防線；不能將提示提醒誤認為執行層強制隔離。

## 4. 按需載入模式 LOAD-0–LOAD-3

此命名獨立於思考架構的 L0–L4 層級，避免混淆。

| 級別 | 任務 | 預設讀取範圍 | 升級條件 |
|---|---|---|---|
| LOAD-0 | 一次性短任務、不改檔、無持久化需求 | 當前請求、必要背景；不讀 Repository 或建立文件 | 需要引用、查證或檔案操作 |
| LOAD-1 | 單檔分析／局部變更 | 唯一權威入口（如必要）、目標檔案、必要直接依賴、相關驗收規則 | 發現共享契約或其他路徑被實際影響 |
| LOAD-2 | 多步工作、多檔施工、研究分支或交接 | 主軸索引、相關 MASTER／BRANCH、目標集合、直接依賴與必要測試 | 跨主軸或共享權威被修改 |
| LOAD-3 | 核心架構重整、破壞性遷移、全域退場／權限變更 | 版本治理、權威索引、影響圖、相關核心契約、各受影響文件與驗收基線 | 不可再升級；若範圍仍不明，先阻塞或分拆任務 |

### 載入策略

- 先讀索引與摘要，以穩定 ID／路徑定位詳細資料；只有在資訊會影響當前判斷時才讀取全文。
- 原始對談、歷史備份、未相關主軸和整份能力登錄預設不載入；有具體來源缺口才按需讀取。
- 使用輕量引用與檢索，避免反覆讀取同一內容；必要時保留已核對的來源 ID、commit／版本及關鍵段落位置。
- 若工具或模型上下文有限，先作高保真任務摘要與檢查點，保留目標、決策、依賴、未決、實際變更和下一步；不要把所有工具輸出都複製進持久記錄。
- 依據與核心結論若相互矛盾，不能只依摘要，必須回查權威來源。

## 5. 記錄精簡：欄位與文件分開

過程、路徑、狀態、修改及驗收是不同資訊，不代表必須有不同文件。

| 執行規模 | 預設紀錄方式 | 何時持久化 |
|---|---|---|
| 短任務 | 不另建專案紀錄；需要時只保存最終結果 | 只有產生了需追溯的正式變更或使用者要求留存 |
| 一般多步任務 | 一份精簡 Run Record 集中記錄 | 任務需要續接、返工定位、版本比較或交付證據時 |
| 長期／高風險／跨模組工作 | 一份正式 Work Packet，加上必要執行收據與證據引用 | 有交接、批准、跨會話、不可逆操作、正式驗收或稽核需要時 |

精簡 Run Record 建議包含：
- run_id、task_goal、acceptance_criteria、scope／risk／routing summary。
- base_version／commit、modified_paths。
- status、completed_steps、pending_steps、blockers。
- verification_status、evidence_refs、rollback_ref。
- checkpoint_time、next_action、closure_reason。

細節原始輸出若很大，保存為可追溯的產物或來源引用；Run Record 只保存摘要、指紋、路徑與必要的證據定位。不應將同一段正文重複寫入任務、過程、路徑、狀態及交接五份文件。

## 6. 控制額外治理成本

治理成本也要被量測，不可視為免費。每次變更記錄：
- 載入檔案數、字元總量或可用的 token 估值。
- 修改路徑數、邏輯依賴數、變更範圍級別。
- 追溯／索引更新數、執行時間、工具操作數。
- 驗收耗時、返工次數、回退次數。
- 本次是否新增持久文件，以及新增原因。
- 有沒有因過度讀取、過度紀錄或範圍擴張導致可避免的成本。

字元數不是 token 精確值；跨任務比較須使用一致量測方式。初期先建立基線，不預設虛構改善百分比。若某種治理步驟長期沒有防止錯誤或提高恢復能力的證據，應簡化或移到高風險路徑。

## 7. 必須通過的反例測試

- 單行修正不應讀取整個 Repository，也不應建立正式封包。
- 修改共享 Schema 必須反查消費者、測試和版本相容性。
- 任務中發現不相關小問題，不應自動擴大變更清單。
- 直接依賴測試失敗時，系統必須允許擴大到 R2/R3，而不能為守住小範圍而隱瞞問題。
- 任務中斷時，可從 Run Record／封包恢復，不必重讀全庫。
- 摘要與權威來源矛盾時，系統回查來源並記錄修正。
- 短任務不被迫建立多份文件；高風險任務不能因節省紀錄成本而略過必要控制。
- 實際修改路徑超出白名單時，不標記成功，應停止並報告差異。

## 8. 驗收與外部依據

使用固定代表任務比較舊流程與分級流程，量測：目標成功率、必要文件讀取數、載入字元／token、修改路徑和依賴數、延遲、重複呼叫、返工、回退、驗收漏失與中斷恢復時間。

採納條件：
1. 低風險任務平均載入與紀錄成本下降，且目標達成與證據品質不退步。
2. 高風險／共享契約變更的必要 Gate 漏失率不得增加。
3. 超範圍修改可被可靠發現，回退可被實際驗證。
4. 如果節省只來自省略必要證據或安全控制，視為失敗。
