## 1. 目的、問題與非目標

### 1.1 系統目的

建立一套可面對不同任務類型、在有限時間與資源內形成可靠理解、選擇合適方法、產生可驗收結果、辨認並修正錯誤且能誠實停止的 AI 思考品質系統。它應同時適用於短問答、研究分析、規劃、程式施工、多檔案治理、工具使用、長任務交接及需要高保證的工作。

### 1.2 核心問題

- 目標、實際需求、成功條件及限制可能被誤讀或在過程中漂移。
- 來源、觀察、推論、假設、未知、衝突及過期資料容易混成同一種「事實」。
- 新架構容易重複既有能力、建立平行骨架，或把工具／治理升格成思考核心。
- 驗證可能不足，也可能陷入重複檢查、無限反思及成本失控。
- 模型輸出、工具執行、狀態持久化與任務實際成功可能被錯誤視為同一件事。
- 上游假設或文件變更後，下游結果、依賴、引用與測試可能未更新。
- 研究候選、文件規格、原型、整合、測試及 Runtime 實際觀測之間容易被混淆。
- 多代理、插件、封包、記憶和新規則可能因「可新增」而被納入，缺乏淨效益與退場證據。

### 1.3 非目標

本藍圖不推翻原六主軸／十八節點，不創建平行的通用認知架構，不建立第二套能力清單或問題 ID，不把任務類型硬塞成第五路由軸，不要求所有任務完整執行所有步驟，不把角色數、代理數、文件數、搜尋來源數或重試次數當成品質本身，也不宣稱任何未執行的測試、授權控制或 Runtime 功能已通過。

## 2. 思考品質核心定義與不變量

### 2.1 操作性定義

**AI 思考品質，是在理解真實任務目的、成功條件與限制後，以可追溯且範圍相符的依據建構可檢驗的理解或方案；依問題特性選擇認知方法，適當校準結論和未知；當證據、前提或測試結果改變時，能定位受影響的責任、修正表徵／推論／方法並重驗，在證據價值、剩餘風險與投入成本相稱時交付、部分交付、阻塞或停止。**

思考是核心。角色、工具、插件、Runtime、狀態保存、文件治理、政策、安全和評測都是支援思考可靠運作的機制，不是另立的認知核心。

### 2.2 不變量

| ID | 不變量 | 最低可觀察要求 |
|---|---|---|
| INV-01 | 目的忠實 | 目標、接受條件、硬限制及非目標可核對 |
| INV-02 | 框架可修正 | 反證或新資訊可以觸發框架改版，且保留差異 |
| INV-03 | 知識狀態誠實 | 來源、觀察、主張、推論、假設、未知、衝突、過期分離 |
| INV-04 | 方法適配 | 方法符合問題特性、風險、可逆性、可觀測性及預算 |
| INV-05 | 檢驗有區辨力 | 檢驗可區分重要替代結論，不以重述冒充獨立驗證 |
| INV-06 | 結論校準 | 結論力度、適用範圍及信心不超出證據 |
| INV-07 | 修正傳播 | 上游變更能追蹤並更新所有受影響的下游產物 |
| INV-08 | 執行與品質分離 | 工具呼叫成功不代表任務成功；回答內容不代表工具已執行 |
| INV-09 | 權限獨立 | 授權拒絕可在工具／Runtime 邊界阻擋副作用 |
| INV-10 | 成本有界 | 邊際驗證收益、剩餘風險和總成本共同決定繼續或停止 |
| INV-11 | 狀態誠實 | PASS、PARTIAL、BLOCKED、FAILED、NOT_PROVEN、NOT_EXECUTED、INCONCLUSIVE 有分別 |
| INV-12 | 架構可否決 | 任何候選構件均可被消融、簡化、否決或退役 |

這些是不變量及設計要求；其跨任務成效仍需實驗與 Runtime 驗收。

## 3. 唯一認知架構與責任邊界

### 3.1 唯一架構

`Core → Axes (A1–A6) → Skeleton (N01–N18) → Conditional Framework (F0–F7)`

| 層 | 唯一責任 | 本藍圖處置 |
|---|---|---|
| Core | 思考品質目的與不可違反的不變量 | 維持核心地位 |
| A1–A6 | 六條主軸的認知責任 | 維持現有 ID 與細項契約 |
| N01–N18 | 十八個骨架節點的操作責任 | 不另建九節點替代骨架 |
| F0–F7 | 條件式思考操作、路由、回流和停止 | 按任務條件短路或加深 |
| 橫向支援平面 | 工具、Runtime、policy、SOP、記憶、trace、持久化、評測 | 維持既有責任域，不增加第五認知層 |

### 3.2 A1–A6 的責任摘要

- **A1 意圖與問題框定：** 目標、成功條件、範圍、硬限制、關鍵歧義及初始問題模型。
- **A2 證據與知識狀態：** 來源、觀察、主張—證據關係、未知、衝突、過期及查證狀態。
- **A3 問題模型與解釋：** 元素、關係、因果候選、競爭假說及所需區辨證據。
- **A4 方法選擇與策略：** 方法路由、資源預算、檢驗方案、風險與停止條件。
- **A5 求解與方案形成：** 依選定方法推導、實作、生成候選並整合成果。
- **A6 驗證、重框與回饋：** 檢查結果、定位錯誤、更新受影響內容、重驗及結案。

具體節點輸入、輸出和依賴以正式四層細項矩陣為準；本藍圖摘要不覆蓋原節點契約。

### 3.3 五主軸／九責任只是映射視圖

先前蒸餾出的「問題定界、資訊與依據、候選理解與推論、檢驗與校準、錯誤修正與交付」是壓縮後的責任視圖；「九責任」是操作閱讀視圖。不得將其作為第二組核心層級或新增 ID。所有對應必須回映到 A1–A6、N01–N18、F0–F7 及既有支援能力。

## 4. M/G/P/T 運行路由、角色與執行模式

### 4.1 保留四個正交維度

| 維度 | 唯一回答的問題 | 現有候選值 | 控制責任 |
|---|---|---|---|
| M：方法／分析深度 | 需要多深的理解、取證或診斷？ | M0–M3 | 認知深度與驗證方法 |
| G：治理／安全控制 | 授權、安全、風險與驗收要多嚴？ | G0–G3 | policy gate、授權、風險控制 |
| P：持久化需求 | 需保留多少狀態供中斷恢復或交接？ | P0–P2 | checkpoint、工作封包及持久化 |
| T：協作拓撲 | 任務如何分工、交接及整合？ | T0–T3 | 單一主體、序列流程、平行委派、專家接手／事件協作 |

操作細節以現有 M/G/P/T 藍圖為準；不能單憑新文件的命名改寫 enum 值或實作語意。

### 4.2 禁止新增第五通用軸

新稿中的「任務型態、執行形態、安全事件、深度」混合不同分類。應分別回映：
- 任務類型為 profile/tag 與輸入屬性；
- 方法深度落在 M；
- 安全、授權和副作用落在 G 與 policy gate；
- 狀態保存與 checkpoint 落在 P；
- 序列、平行、協作和專家交接落在 T。

高風險事件可以覆蓋一般任務路由，不能被弱化為單純偏好設定。路由選擇不等於授予執行權限。

### 4.3 三種操作 profile，不取代 M/G/P/T

| Profile | 適用條件 | 最低行為 | 明確禁止 |
|---|---|---|---|
| 快速 | 低歧義、低風險、短任務且容易驗收 | 理解目標、完成必要解答、檢查硬限制、交付 | 為形式完整而讀全庫、完整建帳、多代理或重複反思 |
| 標準 | 一般分析／規劃，有有限不確定性或多個必要步驟 | 目標限制、關鍵依據狀態、合適方法、必要檢查、交付判定 | 不看任務性質便固定呼叫多模型或展開所有節點 |
| 高保證 | 高影響、重大未知、來源衝突、長依賴鏈、不可逆操作 | 明確依據與依賴、獨立且有區辨力的核驗、policy gate、必要核准、回復計畫 | 以信心、角色名稱、平均分或「已檢查多次」取代必要控制 |

### 4.4 升級／降級／停止觸發

可升級的觸發包含：足以改變結論的歧義、來源衝突、關鍵主張不可核對、依賴鏈擴張、首次驗收失敗、反證推翻上游假設、或預定行為可能造成重大副作用。可降級或停止的條件包含：必要接受條件已滿足、重複檢查未產生新證據、額外資訊預期不會改變決策且不實質降低風險，或必要資訊不足而無法安全推進。未知時可標記 BLOCKED／NOT_VERIFIED，不能為了閉環而虛構完成。

## 5. 任務流程、認知操作與四梯次施工的分層

這三條流程有不同的唯一責任，不能合併成平行的新 workflow engine：

1. **SOP-META-001 任務流程：** INTAKE → AUTHORIZE → SELECT_SOP → PLAN → EXECUTE → VERIFY → PERSIST → REVIEW。
2. **F0–F7 認知操作：** 依目標、未知、任務性質及風險選擇必要節點，允許短路、回流及停止。
3. **藍圖四梯次施工：** PLANNING → REALIZATION → CLOSURE → FINAL_TEST，負責架構變更批次的施工與放行。

### 5.1 任務級別與最小路徑

沿用現有 SOP 的 L0–L3 與 Δ0–Δ3，不在本藍圖中另造分級：
- L0 一次性無寫入／外部副作用的簡單回答，採必要理解與核對。
- L1 單一文件或局部低風險任務，使用現有 SOP 與精簡檢查。
- L2 多文件、跨依賴或批次更新，先凍結變更集，完成正文，再集中讀回、回歸與索引更新。
- L3 正式企劃、高影響／不可逆操作或高風險事件，需明確授權、影響評估、恢復方案與獨立驗收。

跨級任務採用最高實際風險所要求的控制。不得把低層級簡化規則用來繞過授權、資料完整性或核心驗收。

## 6. 功能、角色、插件與 Runtime 的整體組織

### 6.1 邏輯責任域

| 責任域 | 主要工作 | 權威來源／邊界 |
|---|---|---|
| 認知核心 | 問題理解、模型建構、方法選擇、推論、修正與結案 | Core／A1–A6／N01–N18／F0–F7 |
| 任務協調 | 拆分、排序、派發、整合、重試策略與停止 | 現有 SOP／F 路徑／T 拓撲；非新認知骨架 |
| Evidence／知識狀態 | 來源、觀察、主張、推論、假設、未知、衝突與來源範圍 | 與執行狀態、長期記憶分離 |
| Tool／Plugin adapter | 封裝外部 API、檔案、瀏覽器、程式執行等工具的輸入／輸出和錯誤 | 只暴露契約；插件不能自授權 |
| Policy／授權 | 權限、敏感資料、禁止行為、人類核准及不可逆副作用 | 必須能在 Runtime／工具邊界實際阻擋 |
| Runtime／Orchestrator | 實際模型／工具呼叫、狀態轉移、timeout、中斷、取消、重試及預算 | 不等於目前 Python vertical slice 已實作的功能 |
| State／Persistence | 任務 checkpoint、Run Record、工作封包、狀態恢復 | 與主庫權威資料及長期記憶分離 |
| Trace／Audit | 實際執行紀錄、授權結果、工具輸入／輸出指紋、成本與失敗 | 按敏感度做最小必要保存 |
| Evaluation／Regression | 任務接受條件、測試資料、rubric、盲評、回歸及成本分析 | 不把被測模型自評當唯一真值 |
| 文件／能力治理 | 唯一責任、版本、來源、引用、退場與權威登錄 | 沿用 forAVAr 現有治理規範 |

表內是邏輯責任域，不要求每個域都部署成獨立服務或 agent。只有在契約、隔離、安全、規模或測量證明需要時才拆分成獨立元件。

### 6.2 角色不是權限本身

可使用協調者、問題分析者、研究／取證者、領域專家、實作者、驗證者、風險審查者、整合者等邏輯角色。角色可以是同一模型／主體的階段性工作，也可以由不同模型／工具承擔。角色名不表示模型獨立、權限隔離或驗證獨立。只有在子任務可分割、輸出有明確契約且整合成本合理時才採多代理。

### 6.3 插件與功能替換原則

- 現有能力登錄是功能 ID 的權威來源；新插件先映射到既有責任和 ID。
- 只有證明既有能力無法承載、且新責任不可合併時才提出新增能力 ID；不以改名或換實作建立重複功能。
- 每個 adapter／plugin 需定義輸入 schema、輸出 schema、錯誤類型、timeout、冪等性、副作用等級、權限要求、證據欄位、版本、替代方案與測試。
- 替換模型、工具或插件時，先做能力／契約兼容比較、錯誤與安全差異、成本影響和回歸，不得只因新元件可用便替換。
- 插件宣告「唯讀」不是可靠安全邊界；實際權限由可驗證的執行身分和工具端設定控制。
- 插件缺失或失敗時，系統應依契約降級、替代、阻塞或部分交付，不得假裝成功。
- 不存在可證明必要性或淨收益的插件，保持候選或退役，不納入核心常駐。
