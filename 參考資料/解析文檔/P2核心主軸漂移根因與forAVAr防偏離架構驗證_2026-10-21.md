## 0. 摘要與最終裁定

### 0.1 核心結論

**P2 偏離核心主軸的根因，不只是對話太長或模型記憶不足；而是「每次工作時的實際權威上下文」沒有被可靠地重建、綁定版本並強制核對。** 在 GitHub 內容無法被當前 Claude 對話直接讀取時，若工作者只拿到最初藍圖，藍圖就會被迫同時扮演目標架構、目前狀態、近期決策、待辦、測試證據與下一步的替代品。它無法承載這些不同職責；每次局部問題出現時，模型只能根據有限的對話摘要重新推理，容易以局部修補取代原始目標，進而新增流程、能力或文件，造成範圍逐步外擴。

外部研究支持這類機制：長上下文模型對資訊位置存在可測量的取用差異；長程軟體代理仍有跨檔案一致性與全域規劃問題；近年的上下文管理研究特別強調，壓縮歷史本身不夠，還要保留穩定任務語意、核實記憶是否仍符合目前儲存庫狀態，並按需重新取回證據。[Lost in the Middle（TACL 2024）](https://aclanthology.org/2024.tacl-1.9/)；[NL2Repo-Bench（arXiv，2025）](https://arxiv.org/abs/2512.12730)；[Context as a Tool（arXiv，2025）](https://arxiv.org/abs/2512.22087)；[MemTrace（arXiv 預印本，2026-10-04）](https://arxiv.org/abs/2610.04838)。

## 1. 根因分析：為什麼改一個問題，後續容易跑題？

### 1.1 將「目標藍圖」當成「目前工作上下文」

P2 的唯一施工藍圖明確標示 `P2_TARGET_BLUEPRINT / DESIGN ONLY`，目的在定義系統應成為什麼，不是證明目前程式已具備哪些能力。它本身不能回答某次最新修改是否寫入、哪一個測試失敗、哪一條工作線仍有效、哪些結論已被新證據推翻。

若 Claude 無法連上或同步 GitHub，而對話只提供最初藍圖，就會缺少下列動態資訊：

1. 最新可確認的儲存庫版本、檔案雜湊與目前工作單元。
2. 上一輪真正修改了什麼、哪些改動尚未驗證、哪些結果只能算靜態分析。
3. 使用者已確認的核心不變量、非目標、已拒絕方案與範圍變更授權。
4. 當前待解問題和原始目標之間的關係，以及不能因新問題而擴張的工作邊界。

**推論：** 此時模型容易把「解決眼前錯誤」誤判為「重新定義系統方向」，因為它沒有足夠可讀的當前狀態來限制方案搜尋空間。

### 1.2 權威雖被宣告，派生視圖與工作線仍會互相競爭

本次封包可以直接觀察到：

- `P1-CURRENT.json` 指向 `P2-B1-B8-CODE-FIRST / IN_PROGRESS`，Active Work 為 `P1-Central-Control/progress/P2-B1-B8.work.json`。
- `P1-CURRENT.json` 的 `p2_target_blueprint_ref` 指向唯一 P2 目標藍圖，藍圖內容版本是 v4.0。
- `docs/handoffs/HANDOFF.md` 與 `handoff.data.json` 仍以 R3d130j（2026-10-16）為主，下一步是 R3d130k 的 W0／W1–W8 工作。
- 根目錄 README 中還存在已標記為凍結舊投影的文字，將 P2 原生核心進度／下一步指向 HANDOFF；同一 README 又明確宣告 Current 與 B1–B8 是目前狀態權威。

這代表文件層已嘗試區分藍圖、Current、Work、Feature Batch、Roadmap、Handoff 的責任，卻沒有做到所有派生視圖都與同一有效狀態一致。讀者如果沒有讀到「凍結舊投影」等限制，就可能被較容易取得或較完整的交接文字帶走。

**推論：** 一旦 Claude 無法直接讀取 Current／Work／Feature Batch，就會依賴自己看到的摘要。摘要越完整、語氣越像指令，越可能壓過較新的事實來源；之後修正一個錯誤，又可能產生另一份不同的狀態敘事。

### 1.3 每次局部修補沒有被穩定連回「核心問題—驗收條件」鏈

P2 藍圖已寫入以下原則：新錯誤／需求／環境改變時回到 THINKING；功能要經由 F28 變更分類；F30 管理批次階段；根因修正要蒸餾到可重用機制；驗收條件先於結果；新方案不得悄悄改變既有接受條件。

然而這些原則能否防止偏題，取決於每次局部變更是否真的產生並驗證下列鏈條：

```原始使用者目標
  → 被保護的核心不變量與非目標
  → 本次問題／反例
  → 根因假說與證據
  → 對既有能力的 REUSE／MODIFY／MERGE／NEW 裁定
  → 受影響契約、檔案、測試與下游工作
  → 經授權的最小差異
  → 驗收／回歸證據
  → Current 與交接同步
```

如果中間只保存「問題與修法」，沒有保存「為何此修法仍符合核心、為何不用既有模組、哪些其他路徑被影響」，局部成功就會逐步脫離整體目的。

### 1.4 新功能／規則不斷疊加，會擴大上下文與維護面

本次封包包含 159 個控制層腳本、135 個 Schema、177 個測試檔及多組工作、證據、政策和規劃資料。數量本身不表示過度設計，但每新增一個模組都提高跨檔案依賴、引用同步與重新載入的成本。

外部長程程式生成評測也顯示，全庫建造問題依然難以在數百輪互動下維持全域一致性；錯誤不只來自 token 數量，還包括架構規劃、跨檔案依賴與測試契約不一致。[NL2Repo-Bench](https://arxiv.org/abs/2512.12730) 的研究結論不能直接預測 P2 的表現，但與本次發現的治理風險一致。

### 1.5「檔案存在」「有測試」「曾經跑過」容易被錯當成當前已完成

本次快照的官方狀態很明確：

- F01–F30 共 30 個功能，其中 20 個為 `CODE_PRESENT_UNVERIFIED`、10 個為 `PARTIAL`。
- 90 個局部案例（NORMAL／NEGATIVE／BOUNDARY 各 30 個）全部為 `NOT_RUN`。
- 90 個案例中 33 個綁定 `test_method`，57 個的 `test_method` 為 null。
- `P1-CURRENT.json` 把 Runtime Truth 設為 `INCOMPLETE`；工作包標示 `python_tests=NOT_EXECUTED`、`formal_caller=UNKNOWN`、`active_pack=NOT_GENERATED`。
- 保存的歷史 Runtime Observation 是 2026-10-10 舊 Commit 的 `SIMULATION_FAIL`（82 個方法、Operational Reference Pack 子套件 3 個斷言失敗）；文件同時說明後續修補尚未在當前 HEAD 重跑。

因此，不能以程式碼存在、測試檔存在、歷史 Commit 有輸出，推論目前快照已通過。若每次交接沒有保留明確的「證據所屬 HEAD＋狀態＋尚未執行項目」，下游就會用敘述補齊缺失的驗收狀態。

## 3. forAVAr 新架構的防偏離能力審查

### 3.1 已有設計中，哪些部分正好對應根因？

C′ 主企劃與 v0.2 提案已寫入下列方向：

1. **唯一權威與 Current-first：** 目標藍圖、當前執行狀態、工作單元契約、實作／測試證據各有不同責任，不允許以摘要或較新的敘述取代真正的權威資料。
2. **最小充分上下文：** 不常駐整份對話或全庫，應用工作所需的來源／版本／限制／證據與下一步重建狀態。
3. **變更分類與影響分析：** 區分一次性、局部規則、系統性能力與架構不變量；新問題不會自動成為新增永久能力的理由。
4. **確認範圍綁定：** 修改必須受已確認差異、基準版本和範圍約束；實際差異改變要回到比較／確認流程。
5. **證據層級：** 文件存在、靜態分析、程式測試、Runtime 與獨立驗收不得互相代替。
6. **根因蒸餾與退場：** 只有有來源、有理由且能重用的根因修正才進入核心規則；原始研究或診斷紀錄不應不斷累積成活動上下文。
7. **有限工作封包與停止條件：** 每個任務有範圍、輸入／輸出、接受條件、失敗語義、成本及下一步。

這些方向可構成防偏離架構；問題在於每一項是否在實際執行鏈上被載入、驗證、強制及測試。

### 3.2 forAVAr 自己的審查已標示出關鍵阻塞

本次回讀的 `目前架構驗收與逆向批判紀錄_2026-10-20.md` 已明確指出：

- **ARCH-01：** 唯一權威來源尚未全部落到具體資料契約與可裁決的權威映射。
- **ARCH-03：** CONFIRMED／PRE-WRITE_RECHECK 等狀態目前偏向流程設計，尚無足夠證據證明寫入工具會機械性拒絕超出批准範圍的差異。
- **ARCH-04：** 沒有已驗證的唯一啟動載入器，也沒有全新會話在不重複提醒下的行為收據。
- **ARCH-05：** 驗收案例還未全部成為有固定輸入、預期結果、執行方式與實際收據的可重複測試套件。
- **ARCH-06：** 能力關係的證據邊、範圍縮小方式、未知狀態及規模成本尚未形成實作驗證。

因此，**現有新架構在文件層已理解這個問題，但還不能宣稱已經從系統層有效防止。** 把原則寫進更多 Markdown，不會單獨解決載入缺失；每次對話仍需要有可用的現況輸入，而且要有缺載入時的阻擋條件。

### 3.3 可借鑑的外部技術：結構化上下文、按需讀取、狀態一致性

- Anthropic 將 context engineering 描述為每一輪從大量可能資料中挑選高訊號、最相關的上下文；強調 compacting、structured note-taking、just-in-time retrieval，而不只是追加所有歷史對話。[Effective context engineering for AI agents，2025-09-29](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)
- *Lost in the Middle* 發現，長上下文模型在關鍵資訊位置改變時，任務表現可能顯著下降；不能因資訊「曾經放進對話」就假定模型等量取用。[TACL 2024](https://aclanthology.org/2024.tacl-1.9/)
- *Context as a Tool* 指出，長程工程代理若只是一直追加歷史或被動壓縮，會遇到 context explosion 和 semantic drift；研究提出可主動呼叫的上下文管理機制，將穩定任務語意、長期記憶與近期互動分層。[arXiv 2025-12-26](https://arxiv.org/abs/2512.22087)
- *MemTrace* 將歷史紀錄錨定至檔案、符號、測試與執行次序，並在恢復舊證據前確認它仍對應目前儲存庫狀態。這與本次所需的「交接紀錄不能直接被當成當前狀態」高度相關；該來源目前是預印本，其結果不應被視為已獨立重複驗證的定論。[arXiv 2026-10-04](https://arxiv.org/abs/2610.04838)

另需釐清 GitHub 存取假設：Claude 的官方說明描述 GitHub 整合可把所選 repository 檔案加入 Chat／Project，並要求同步更新；private repository 仍需授權存取。[Claude Help Center：GitHub integration](https://support.claude.com/en/articles/10167454-use-the-github-integration)。官方文件本身沒有在此頁證實目前每一種免費方案、帳戶、地區及私有儲存庫權限都一定可用。因此本設計不應依賴「使用者理論上能連 GitHub」；必須把無法讀取 repository 視為可預期的運行模式，而非例外。

## 4. 建議的最小防偏離設計（研究建議，未寫入企劃）

這些項目是從本次根因及外部依據推導的候選控制，不代表已核准規格或已實作能力。

### 4.1 將三種狀態分開，不再以藍圖替代現況

每次啟動必須分清楚：

- **Core Anchor（穩定核心）：** 一句話任務目的、不可變核心原則、非目標、成功／停止條件、使用者紅線與核心變更的批准者。
- **Current State（動態現況）：** 快照／repository 身分、基準 Commit 或來源 SHA、Current、Active Work、工作階段、已完成／未完成、最新實際測試證據、引用缺口及阻塞。
- **Task Contract（本次工作契約）：** 本次唯一目標、明確非目標、允許改動範圍、需要讀取的來源、輸出、接受條件、失敗處理，以及下次交接的最小狀態。

藍圖只負責設計意圖。沒有 Current State，不能自動用 Core Anchor 推論出目前程式狀態。

### 4.2 每次任務啟動都建立可攜式「狀態包」，不能只帶初始藍圖

當 GitHub 可用時，狀態包應從唯一 Current、Active Work／Construction、核心藍圖相關段落、開放問題與最新驗收證據按需生成，並綁定基準版本／雜湊。

當 GitHub 不可用時，提供同一套自足狀態包的靜態匯出版本：包含讀取順序、必要檔案片段、來源路徑／雜湊、版本時間、待辦與限制。啟動時先核對版本及 manifest，而不是要求 Claude 自己從一份大型藍圖重建所有事實。

如果狀態包不存在、來源版本互相衝突或必要檔案缺失，狀態應為 `BLOCKED_CONTEXT`／`STALE_CONTEXT`，只允許進行不依賴缺失事實的分析；不允許宣稱已了解現況或進行會擴大偏差的修改。

### 4.3 增加真正的 Core-Drift Gate

每一個候選修改都要回答以下固定問題，並保留對應來源：

1. 此修改正在解決哪一個已登錄問題或哪個接受條件失敗？
2. 它符合哪一個核心 ID？若沒有對應，是否屬於與主軸無關的額外功能？
3. 它是否改變原始目標、非目標、角色職權、資料模型、流程狀態或接受條件？
4. 是否已有能力可以 REUSE／MODIFY／MERGE？決定 NEW 時要寫出現有候選不能滿足的證據。
5. 改動會影響哪些現有引用、測試、狀態來源、工作包與交接？
6. 哪些證據可以證明修正有效？哪些範圍仍未執行？

若無法回答，需保留 UNKNOWN 或 BLOCKED；不得因「想出一個看似合理的新機制」直接新增核心能力。

### 4.4 將局部錯誤分流成兩條路徑

- **局部修補：** 只修正已定位、可重現的失敗；保持核心與整批範圍不變；執行對應案例及必要回歸。
- **核心／架構變更：** 若證據顯示真正根因在核心原則、權限、通用契約或整體方法，則先建立差異提案和影響矩陣，經授權後才重新開啟範圍。

新的問題可以登記到 backlog，但不自動成為目前工作單元，也不應直接重設主軸。這可以降低單一局部問題搶走整個對話的風險。

### 4.5 讓「防偏離」可測量，而不是靠口頭宣告

至少建立以下反例測試，固定輸入、預期結果、執行方式與實際收據：

| 測試 | 輸入／擾動 | 必須觀察到的結果 |
|---|---|---|
| DRIFT-01 | 新會話只提供初始藍圖，不提供 Current | 系統拒絕宣稱掌握現況，要求狀態包或標記 BLOCKED_CONTEXT |
| DRIFT-02 | HANDOFF 與 Current 指向不同工作 | 不自行選較完整或較新的敘事；報告衝突並停止施工 |
| DRIFT-03 | 修正局部錯誤時提出一項與核心無關的新功能 | 先進行變更分類；沒有核心理由與必要授權時不納入本次施工 |
| DRIFT-04 | 基準 Commit／檔案雜湊在確認後改變 | 確認範圍失效，重新比對；不可沿用舊授權或舊證據 |
| DRIFT-05 | 歷史測試 PASS，但目前 HEAD 已改變 | 歷史結果不能當成目前證據；受影響測試須重新執行 |
| DRIFT-06 | 交接摘要省略一條核心限制或把 PROPOSAL 寫成已核准 | 啟動驗證以權威來源及來源狀態糾正摘要，必要時阻塞 |
| DRIFT-07 | 連續數輪修正但核心目標未被重新提及 | 每輪仍維持 Core Anchor 與當前 Task Contract，不以最新局部問題重定義專案目標 |
| DRIFT-08 | 新來源無法存取或必要連結失效 | 明確 UNKNOWN／BLOCKED；不自行填補失蹤內容或宣稱全量驗證 |

評估時必須區分「文件已有要求」「測試已實際執行」「獨立驗收通過」。不能把建立測試表本身算成防偏離能力已通過。

## 5. 對本次 P2 快照的建議處理順序

以下是研究建議，不是已批准施工命令，也沒有修改 P2：

1. **先固定核心基線：** 以使用者指定的最新快照為分析基線，整理主軸、核心不變量、非目標與目前驗收狀態；保留雜湊，不用舊交接取代它。
2. **先解決權威與引用差異：** 核對 Current、B1–B8 Work、Feature Batch、Construction、HANDOFF、README 和唯一藍圖。REF-01 至 REF-03 必須逐項裁定。
3. **清查 F01–F30 的真實接線：** 不以檔案存在作完成條件，將每項的 implementation ref、正式 caller、測試 ref、具體 test_method、執行證據與當前版本指紋對齊。
4. **只在有證據時修改架構：** 如果失效根因是缺少權威上下文或驗收接線，優先修正既有機制；不要先增加新的控制層或另一套工作狀態機。
5. **完成最小範圍閉環後才擴張：** 先驗證一個完整切片的啟動、讀 Current、取得必要上下文、辨識局部問題、受控修改、獨立驗收、更新 Current 與交接，再決定是否推廣。
