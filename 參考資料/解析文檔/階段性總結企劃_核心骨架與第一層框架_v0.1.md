## 0. 結論先行

### 0.1 核心定義

forAVAr 的候選核心是：

**一套以問題為起點、能依問題屬性選擇適當方法，透過可追溯的證據、可組合的能力、受控的工作流程與明確職權，產生可檢查成果，並能依驗證結果安全修正與演化的通用問題處理架構。**

它的核心價值不是堆疊更多工具、角色、流程、檔案或模型，而是把「理解問題、選擇方法、調用能力、管理權限、驗證結果、保存證據、控制變更」組成一套可按任務調整深度的系統。

這是根據現有研究文件整理出的候選核心定義，不是已被實驗證明的最佳定位，也不等於 forAVAr 已經具備上述完整執行能力。

### 0.2 核心外圍的骨架

核心周圍先保留十個一級骨架節點：

1. 專案邊界、治理與職權。
2. 使用者意圖與問題定義。
3. 來源、知識與證據。
4. 方法選擇與推理路線。
5. 問題骨架、模型與關係圖。
6. 能力目錄、外部工具與適配器。
7. 工作流、任務封包與編排。
8. 執行、狀態與產物。
9. 驗收、逆向思考與失效分析。
10. 紀錄、版本、影響分析與持續演化。

這十個節點是職責骨架，不是十個必須依次執行的固定步驟，也不要求一開始建成十個服務或十個 Agent。治理、證據及版本約束會橫向作用於其他節點；實際工作依問題屬性、風險與未知程度選擇需要展開的分支。

### 0.3 本企劃要解決的設計問題

目前研究已提出多個有用的架構元素，但若只把它們平行堆放，仍會產生下列問題：

- 核心、功能分類、執行流程、職權和狀態被混為同一層。
- 文件中描述了某項能力，便被誤認為系統可以執行它。
- 每次遇到新問題，都從頭建立一套流程或盲目套用固定流程。
- 新增功能時只補文件，沒有定義它屬於哪個骨架節點、依賴什麼、由誰授權、怎樣驗收。
- 逆向分析只列出問題，沒有連到可證偽假說、測試與修正裁決。
- 總體架構逐漸變得完整，但沒有證據證明任務品質提高、變更半徑縮小或成本下降。

因此，本企劃不是一次展開全部細節，而是定義「核心 → 骨架 → 第一層框架 → 有條件的細節渲染 → 實測驗收」的工作方法。

## 1. 設計範圍與概念層級

### 1.1 四個層級不得混用

| 層級 | 定義 | 必須回答的問題 | 本層成果 |
|---|---|---|---|
| 核心 Core | 系統存在目的與不可輕易違反的原則 | 為什麼存在？哪些原則跨任務保持穩定？ | 核心定義、非目標、不變量 |
| 骨架 Skeleton | 核心周圍不可缺少的主要責任分區及其關係 | 系統需要哪些主要責任？它們如何連接？ | 一級節點、關係圖、責任邊界 |
| 第一層框架 First-level Framework | 每個骨架節點的第一層可操作分解 | 此節點負責什麼、需要什麼、產出什麼、何時停止？ | 子責任、輸入／輸出、權限、初步驗收條件 |
| 細節渲染 Detail Rendering | 根據具體需求逐枝展開功能、資料欄位、流程、錯誤處理、測試和實作 | 此分支實際要做哪些事？何種條件下執行？如何證明有效？ | 功能清單、契約、測試、實作或待辦 |

「渲染」是一種分層展開的設計方法，不是要求一次產生所有細節。每一層完成後都要檢查父層假設是否成立；發現骨架遺漏、重疊或過早收斂時，允許有紀錄地返回上層調整。

### 1.2 必須分開管理的物件

至少區分下列物件，即使初期都放在同一個 Repository，也不應混成一份無法辨識的巨型文件：

- 問題／任務：本次究竟要解決什麼。
- 方法：用什麼方式取得答案或做出決策。
- 問題模型／骨架：目前如何描述問題中的節點、關係、因果與未知。
- 能力：可被不同工作重用的職責與契約。
- 工具／適配器：能力的具體執行方式或外部介接。
- 工作流：依條件組合方法與能力的順序、分支及停止條件。
- 工作封包：一次具體工作實例的範圍、狀態、授權、產物與驗收。
- 職權：誰可以提出、決定、執行、驗收或發布。
- 證據／產物：來源、觀察、執行結果、測試收據及交付物。
- 紀錄／版本：如何追溯一個主張、一次決策與一次變更的演化。

概念彼此相關，不代表它們可以共用同一個狀態、權限或生命週期。

## 2. 核心：應長期保持的設計不變量

這些是不應因新增某項功能就隨意改變的候選原則。它們仍需在代表性任務中驗證，不因列入本文件就自動升格為已驗證定律。

### CORE-01｜先描述問題，再選方法

不因為系統已經有某個工具、Agent 或流程，就強迫問題配合該工具。先確認目標、輸出、限制、未知與成功條件，再選擇方法。

### CORE-02｜通用性來自方法選擇，而非所有任務走同一流程

量測、現況查證、因果診斷、預測、數學形式化、最佳化、工程施工與開放探索所需方法不同。框架應判斷何時用哪一類方法，以及何時組合、轉向或停止。

### CORE-03｜事實、來源主張、推論、假設、未知與衝突分開

不以文字流暢度取代證據。來源不完整、不同來源互相矛盾或結論沒有測試時，保留其不確定狀態，不製造虛假確定性。

### CORE-04｜每個概念與能力有清楚的唯一責任

相似功能先分析其差異、前置條件、副作用、成本與失效模式，不因名稱相似就合併，也不因有新工具就無條件新增一項正式能力。

### CORE-05｜職權、執行與驗收分離

提出方案不等於有權批准；執行成功不等於驗收通過；文件存在不等於功能可用。高風險行為需有明確授權與獨立可核對的證據。

### CORE-06｜變更必須可追溯、可驗收，必要時可回退

更新前核對基準與影響；更新後讀回實際狀態，確認文件、索引、版本與驗收證據一致。未達接受條件時，允許維持現狀或阻塞，不為了增加版本號而硬改。

### CORE-07｜複雜度與驗收深度隨任務調整

簡單且低風險的任務不必套用完整封包與全套審查；跨系統、長鏈路、高風險、不可逆或核心契約變更才逐步提高檢查深度。簡化流程不得跳過適用的安全、權限和驗收閘門。

### CORE-08｜文件、設計、程式、呼叫路徑、測試與 Runtime 是不同證據層級

每項能力必須明確標示自己目前在哪一層。不得把候選設計說成已實作，把生成的測試說成已通過，或把一次測試結果推廣為所有情境皆有效。

### CORE-09｜反向檢查必須導向可裁決的結果

逆向思考不是無限制提出疑慮。每項重要風險應連到反例、可觀察失敗條件、測試方法及裁決：保留、修正、隔離、延後、拒絕或要求更多證據。

### CORE-10｜架構不因完整而自動正確

任何新增節點、角色、資料欄位、插件、流程或文檔，都必須說明它解決什麼問題、與既有職責的關係、如何衡量收益。沒有足夠收益就維持簡化版。

### 3.1 骨架節點之間的主要關係

- S0 治理與職權是橫向約束，不是每個任務都要額外跑完的獨立流程。
- S1 定義問題，提供 S3 方法選擇所需的目標與限制；S1 不足以定義問題時，應先澄清或採探索方法。
- S2 為 S1、S3、S4、S8 提供來源與證據；證據不足時允許未知，不能被路由流程強制補成事實。
- S3 選擇方法與分析深度，可決定是否需要 S4 建模、S5 能力調用或 S6 任務編排。
- S4 負責描述問題內部結構；S6 負責實際工作步驟與條件。問題關係圖和工作流圖不得互相替代。
- S5 提供可調用的能力及其契約；S6 決定本次是否及如何組合它們。
- S7 產生執行狀態與產物；S8 使用可核對的產物與接受條件判定成果。
- S8 的失敗結果可以觸發 S3 重新選法、S4 修改問題模型、S5 替換能力，或 S6 修正流程，但重試必須有次數／成本／停止條件。
- S9 記錄各節點的來源、版本與結果，並在重要變更後更新受影響關係；S9 不得擅自改變使用者目標或正式驗收條件。

### 3.2 不應畫成一條永遠固定的流水線

骨架是責任關係圖，不代表每個任務都依 S0→S9 完整跑一遍。

簡單查詢可能只需 S1、S2 與短驗證；資料型研究可能重點使用 S1、S2、S3、S8；長鏈路施工可能需要展開 S4–S9。必要節點依任務決定，但相關權限與證據約束始終有效。

## 4. 第一層框架：每個骨架節點的操作邊界

第一層的目的，是讓十個節點都具有足夠清楚的責任與交接，而不是立刻列出所有最終功能。

| 節點 | 主要輸入 | 第一層工作 | 必須產生的輸出 | 不可越過的邊界 |
|---|---|---|---|---|
| S0 治理與職權 | 專案規則、使用者授權、風險與讀寫限制 | 判定工作模式、可讀／可寫範圍、批准條件、停止條件 | 工作權限摘要、授權狀態、風險級別 | 不代替問題分析；沒有授權不能把研究結論寫成正式企劃 |
| S1 意圖與問題定義 | 使用者要求、上下文、預期結果 | 正規化目標、成功條件、限制、未知、歧義與範圍 | 最小問題描述、目標與未決清單 | 不預先指定工具或固定工作流；關鍵歧義不能自行假定 |
| S2 來源與證據 | 原始文件、外部資料、使用者提供內容、既有紀錄 | 核對來源身分、版本、時效、完整性及支持範圍 | 來源紀錄、主張—證據關係、未知／衝突標記 | 不把搜尋摘要、設計提案或來源自述直接視為已實證事實 |
| S3 方法選擇 | 問題屬性、證據狀態、風險、資源限制 | 選擇主要方法、必要輔助方法、分析深度與停止準則 | 方法路線、選擇理由、退出條件 | 不強迫每一問題跑完整流程；不能只因工具可用就選用它 |
| S4 問題骨架與模型 | 問題描述、領域資料、來源與假設 | 建立節點、屬性、關係、條件、依賴與模型缺口 | 核心圖、節點分類、關係表、未決邊 | 不把方便繪製的結構當成真實世界已被完整描述 |
| S5 能力與適配器 | 能力需求、候選工具、來源、相容性限制 | 定義能力契約、分析重疊／互補／依賴／衝突、選擇採用方式 | 能力規格、候選清單、採用／保留／延後／拒絕理由 | 不因相似名稱合併；不把描述檔當成可執行實作 |
| S6 工作流與封包 | 目標、方法路線、能力契約、依賴與授權 | 編排步驟、條件分支、重試、交接、資源上限與回退 | 工作流／封包實例、步驟依賴、接受與停止條件 | 不將功能樹當流程；不建立無必要的永久 Agent 或微服務 |
| S7 執行與產物 | 已批准的工作流、輸入、可執行能力與權限 | 受控調用、狀態更新、產物保存、失敗處理、回復 | 執行紀錄、產物引用、錯誤／重試／復原紀錄 | 不擴大授權；執行者不自行宣告最終驗收 PASS |
| S8 驗收與逆向分析 | 原始目標、接受條件、結果、來源與執行證據 | 檢查主張、挑戰前提、測試負例／邊界／衝突、決定下一步 | PASS／FAIL／BLOCKED、缺陷、反例、修正或回退裁決 | 不以「再想一次」代替新證據；不能私改接受條件以使結果通過 |
| S9 紀錄與演化 | 各節點輸出、版本變更、驗收結果、歷史紀錄 | 分流紀錄、建立版本關係、分析影響、更新索引、管理退場 | 可追溯紀錄、變更交易、索引狀態、待辦與歷史連結 | 不因新增紀錄就自動更新正式企劃；不抹除歷史失敗證據 |

### 4.1 第一層的共同契約

各節點應使用同一組最小交接欄位，而不是各自發明互不相容的格式：

- 唯一識別碼與版本。
- 本次目標／所屬任務。
- 輸入來源及其可信／未知狀態。
- 前置條件與依賴。
- 輸出及其證據等級。
- 負責角色與可執行權限。
- 失敗、衝突與停止條件。
- 驗收方式與結果。
- 下游引用及歷史關係。

此為候選的共通契約欄位，不是現成 Schema。正式化前須用實際任務驗證必填程度，避免每項簡單功能承擔不必要的欄位負擔。

## 5. 依骨架逐層渲染細節的方法

### 5.1 渲染不是一次展開全部功能

建議採四個細化深度：

| 深度 | 名稱 | 展開內容 | 進入下一層的條件 |
|---|---|---|---|
| D0 | 核心與骨架 | 核心定義、十個一級節點、主要連線與非目標 | 節點沒有明顯職責重疊，核心能涵蓋代表性問題類型 |
| D1 | 第一層框架 | 每個節點的輸入、輸出、唯一責任、權限、失敗與驗收邊界 | 各節點可說明如何接入和交出結果，且衝突有處理方式 |
| D2 | 子系統／功能渲染 | 主要子模組、候選功能、資料物件、關係、依賴、責任角色 | 能指出真實需求、預期收益及必要測試；不是純粹為了填滿架構 |
| D3 | 契約／實作／測試渲染 | Schema、介面、狀態機、執行器、測試案例、部署與回退 | 已授權施工，前置條件清楚，驗收結果可以獨立核對 |

不能因為已完成 D0，就直接假定 D1–D3 已經正確；每層通過只代表在該層已達到明確的接受條件。

### 5.2 如何決定某一枝要不要繼續展開

符合下列一項或多項時，才值得加深：

- 該枝直接影響核心成功條件。
- 已有真實需求、重複工作或失敗證據。
- 當前存在影響決策的未知、矛盾或高風險。
- 新增子功能能減少重複、降低變更擴散或提高可驗收性。
- 該枝有可明確定義的輸入、輸出、責任與測試。
- 若不展開，將無法判斷能否安全採用或是否符合使用者目標。

若沒有滿足上述條件，先保留節點與待辦，不必虛構子系統，也不必把每一枝渲染到最深層。

### 5.3 每次渲染必須留下的結果

一次有效的細節渲染至少產出：

1. 所屬骨架節點與唯一責任。
2. 需要解決的具體問題或失敗案例。
3. 功能／子功能候選及其邊界。
4. 與既有功能的重疊、互補、依賴、不相容或未知關係。
5. 輸入、輸出、前置條件、錯誤、副作用及資源需求。
6. 使用／執行權限，以及是否需要使用者批准。
7. 成功條件、負例、邊界與回歸測試。
8. 證據狀態、未決假設、實作成熟度及後續裁決。

## 6. 依第一層框架展開的候選功能清單

以下是功能方向的初步清單，用於確定後續渲染的範圍。這些是候選功能，不代表已存在、已通過測試或全部都應實作。

### S0｜專案邊界、治理與職權

- 專案身分及可寫入目錄識別。
- 只讀來源與可寫入目標的區分。
- 工作模式判定：討論／研究、紀錄、企劃變更準備、核准後整合。
- 授權範圍、批准項、未批准項與停止條件紀錄。
- 風險分級及高風險操作阻擋。
- 新會話／交接時的治理契約載入狀態檢查。
- 對外部內容與工具輸出採不可信資料處理。
- 高風險發布、刪除、覆寫及不可逆操作的批准 Gate。

### S1｜使用者意圖與問題定義

- 要求解析與目標正規化。
- 預期輸出、成功條件及不包含的範圍。
- 問題成熟度與目標清晰度判斷。
- 限制、資源、時限與失敗代價抽取。
- 歧義、缺失前提與未知問題清單。
- 必要澄清問題產生與「先探索而非硬選方案」路由。
- 目標改變偵測及重開問題範圍機制。

### S2｜來源、知識與證據

- 來源清冊、版本、時間、完整性與指紋。
- 來源主張與可支持結論的對照。
- 事實／推論／假設／未知／衝突分類。
- 來源可信度、適用範圍、時效及授權條件紀錄。
- 歷史紀錄、原始資料、彙整稿與正式規格的層級識別。
- 引用／連結檢查及來源變動提示。
- 重要知識的重新驗證觸發條件。
- 對來源不足或矛盾的阻塞／保留機制。

### S3｜方法選擇與推理路線

- 問題屬性分析。
- 量測／現況查證／因果診斷／預測／數學形式化／決策最佳化／設計施工／開放探索方法選擇。
- 多方法組合及切換條件。
- 反證／逆向思考的啟用條件。
- 深度、成本、時間與風險配置。
- 最有價值下一步的選擇。
- 資訊不足時的探索策略。
- 收斂、重框與停止規則。

方法框架的 P1–P8 在既有文件中表示問題屬性代號，與 P1／P2 參考專案名稱不同。新文件與資料欄位應以完整術語或具命名空間的 ID 表達，避免交接歧義。

### S4｜問題骨架、模型與關係圖

- 核心概念、節點及屬性識別。
- 節點之間的依賴、因果、條件、回饋與互斥關係。
- 一級骨架的完整性及重複性檢查。
- 未知節點、缺失因果鏈與矛盾邊。
- 模型邊界、初始條件、狀態變數與觀測量區分。
- 模型版本比較及受影響節點分析。
- 反例導致的重框與節點修正。
- 不同視圖之間的關係追溯。

### S5｜能力目錄、外部工具與適配器

- 能力唯一 ID、目的、輸入輸出與限制。
- 外部工具／方法候選發現。
- 來源、授權、依賴、環境與副作用分析。
- 能力關係：重疊、互補、替代、包含、依賴、矛盾、不相容、未知。
- 採用裁決：抽取方法、內部重作、保留外部工具加適配器、組合、延後、拒絕或退場。
- 模型／工具版本與相容性資訊。
- 候選、實驗、合格、穩定、棄用、退役等成熟度管理。
- 能力登錄與工作流路由的一致性檢查。

### S6｜工作流、任務封包與編排

- 工作流模板與工作實例區分。
- 條件分支、依賴、並行／序列執行與停止條件。
- 封包建立、准入、執行、驗收、阻塞、結案及退場。
- 子封包拆分、父子關係與交接條件。
- 重試預算、資源限制與失敗復原。
- 按風險調整欄位與驗收深度。
- 執行期間的範圍偏移檢查。
- 未達接受條件時重新路由或停止。

### S7｜執行、狀態與產物

- 能力／工具調用介面。
- 執行前置條件及權限檢查。
- 結果正規化、錯誤分類與可觀測性。
- 產物、暫存、日誌和執行紀錄的引用。
- 狀態轉移與非法狀態阻擋。
- 執行中斷、部分寫入與恢復點管理。
- 外部副作用及回復能力紀錄。
- 執行版本與封包所固定版本的對照。

### S8｜驗收、逆向思考與失效分析

- 原始目標及接受條件追溯。
- 正常、負向、邊界、權限、衝突及回歸測試。
- 獨立驗證與循環驗證風險檢查。
- 反向假設、失效模式及替代解釋列舉。
- 測試品質與評估本身的有效性檢查。
- 缺陷嚴重度、影響範圍、可逆性與修正優先序。
- PASS／FAIL／BLOCKED／NOT_EXECUTED 的證據化判定。
- 修復、局部重測、完整回歸、拒絕、回退及保留現狀的裁決。

### S9｜紀錄、版本、影響分析與持續演化

- 不同主題與研究輪次的獨立紀錄建立。
- 歷史母檔、專題紀錄、總結文件、提案與正式規格分層。
- 唯一職責矩陣與單一導航索引。
- 變更前基準、差異、影響及授權紀錄。
- 寫入前重核、寫入後讀回與索引同步。
- 版本／相容性、棄用、回退、封存與退場。
- 負面證據、未解問題及已撤回假設保留。
- 文件數、實作能力與有效成果三者的差異檢查。

## 7. 職權劃分：誰能提出、決定、執行與驗收

職權是橫跨所有骨架的治理面，不能從功能所在的分類位置推導權限。以下是候選責任矩陣；它定義邏輯責任，不要求每個角色都由獨立 Agent 承擔。

| 角色 | 可以做什麼 | 不可自行做什麼 | 必須留下的結果 |
|---|---|---|---|
| 使用者／授權者 | 設定目標、限制、批准範圍、決定是否採納正式變更 | 系統不能假定未表達的批准 | 目標、批准／未批准範圍、必要的確認紀錄 |
| 問題分析／研究者 | 解析問題、找來源、列假設、建立候選方案及反例 | 不因產生方案就直接改正式企劃或宣稱驗收通過 | 問題模型、證據、差異與建議 |
| 流程協調者 | 選擇工作流、檢查前置條件、安排任務與依賴 | 不得擴張授權、重設接受條件或繞過權限檢查 | 執行計畫、分支、停止條件與狀態 |
| 能力執行者 | 在授權範圍內使用工具、寫入指定檔案、產生產物 | 不得自行批准自己的高風險變更或將未執行標記為通過 | 執行紀錄、產物、錯誤及副作用 |
| 獨立驗收者 | 依事先固定的接受條件檢查結果，判定通過、失敗或阻塞 | 不得暗中修改產物或接受條件以產生 PASS | 可核對的驗收收據、缺陷與理由 |
| 治理／版本管理者 | 管理權威路徑、版本、相容性、變更交易與回退 | 不可用摘要文件覆蓋權威來源，不能擴大批准範圍 | 版本關係、基準核對、變更與回退狀態 |
| 紀錄／證據保管者 | 保存來源、歷史版本、索引、職責及追溯連結 | 不得把假說提升為事實，或將摘要冒充逐字稿 | 來源清冊、主張—證據鏈、歷史引用與索引狀態 |

### 7.1 權限最低原則

- 讀取權限與寫入權限分開。
- 紀錄權限與企劃更新權限分開。
- 企劃差異準備與正式整合分開。
- 執行權限與驗收權限分開。
- 發現能力與批准採用能力分開。
- 高風險外部內容預設不可信；未知授權、未知副作用或未核准操作應阻塞。
- 同一模型可以協助不同角色，但角色名稱不等於獨立驗證。重要結果必須由獨立測試資料、可核對外部證據、人工審查或不同驗證機制支持。

## 8. 新增功能時的標準程序

新增系統功能不是「在某個文件多加一段」，而是一次受控的設計變更。以下程序先定義最低需求；正式實作前仍須落地成契約、操作流程或自動測試。

1. **確認需求。** 說明要解決的真實問題、使用情境、預期輸出、成功條件、風險及不做的範圍。
2. **歸位骨架。** 指定它主要屬於 S0–S9 哪個節點。若跨節點，明確寫出主責節點與依賴節點，不把同一功能複製到多處。
3. **分類物件類型。** 判斷它是問題屬性、方法、模型、能力、工具適配器、工作流、封包模板、角色權限、紀錄或驗收規則；不要把不同類型混成一個「功能」。
4. **定唯一責任。** 描述此功能負責什麼、不負責什麼，以及既有哪個功能可能已部分完成相同責任。
5. **定契約。** 至少定義唯一 ID、輸入、輸出、前置條件、錯誤語意、副作用、權限、資源限制、依賴、版本與退出條件。
6. **做關係分析。** 檢查重疊、互補、替代、包含、依賴、矛盾、不相容及未知。不能因名稱相似就合併，也不能因為沒找到依賴就假定它不存在。
7. **做逆向批判。** 從預期失敗、錯誤前提、誤用、惡意輸入、邊界與回退失敗反推設計需要哪些保護。
8. **定驗收條件。** 至少包括正常案例、負向案例、邊界案例及相關回歸案例；高風險功能另加權限和副作用測試。
9. **定變更等級。** 根據語義與影響，而不是檔案數量，判斷是研究紀錄、低風險整理、企劃／契約變更或高影響變更。正式企劃更新需依既有確認程序。
10. **先隔離驗證，再整合。** 候選功能在符合前置條件的隔離範圍測試；未通過時維持候選、修正、延後或拒絕，不直接切換正式路由。
11. **寫入後驗收。** 重新讀回實際檔案，檢查內容、版本、連結、索引、職責矩陣與驗收證據，確定結果與批准範圍一致。
12. **保留退場路徑。** 記錄何種條件下要棄用、替換、回退或刪除，以及仍需保留的歷史與證據。

## 9. 逆向分析與批判：從可能失敗的地方倒推設計

逆向分析應作為按風險啟用的方法模組，不是所有問題都要執行同樣深度的完整紅隊研究。

### 9.1 通用逆向分析流程

1. **界定被檢查的對象。** 是一個主張、功能、流程、資料模型、架構或執行結果？指定版本和範圍。
2. **還原它聲稱成立的條件。** 記錄成功目標、前提、輸入、環境、依賴、權限與接受條件。
3. **分離事實與假設。** 標示哪些已觀察、哪些由來源聲稱、哪些是本輪推論、哪些仍未知。
4. **建立失敗情境。** 假設目標未達成、輸入缺失、資料矛盾、權限不足、依賴失效、外部內容惡意、狀態不同步或操作中斷。
5. **尋找反例與替代解釋。** 至少檢查典型情境、負向情境、邊界情境、跨模組情境及回退情境中哪些會推翻核心主張。
6. **把批判轉成可檢驗條件。** 每個重要漏洞都要有可觀察的失敗條件、測試方法與預期阻擋行為。純粹說「這有風險」不足以結案。
7. **分級及裁決。** 決定保留、修改、隔離、實驗、延後、拒絕、阻塞或回退；說明證據、影響與不確定性。
8. **重新驗證修正。** 確認修正真的處理了失效路徑，且沒有引入更大範圍的新問題。
9. **設定停止條件。** 當剩餘未知不影響本輪決策，且風險在可接受範圍時，可標示限制並前進；安全、權限、資料完整性等核心未知仍須阻塞相關動作。

### 9.2 最低反證清單

| 反證面向 | 核心問題 | 典型反例 |
|---|---|---|
| 目標錯置 | 系統是否解決了錯誤問題？ | 產出格式完整，卻沒有滿足使用者真正目標 |
| 前提錯誤 | 必要假設是否有證據？ | 使用錯誤或過期的來源版本 |
| 遺漏節點 | 骨架是否少了關鍵責任？ | 缺少權限審查、獨立驗收或回退 |
| 邊界錯誤 | 功能是否跨越不該跨越的責任？ | 路由器直接改寫領域邏輯或驗收標準 |
| 關係錯誤 | 是否把衝突當成重疊，或把依賴當成不存在？ | 兩方法對同一安全條件有相反要求 |
| 權限錯誤 | 執行者是否能超出批准範圍？ | 未批准項目被混入同一次寫入 |
| 評估錯誤 | 測試能否揭露實質錯誤？ | 錯誤實作能通過由同一假設產生的弱測試 |
| 狀態錯誤 | 權威狀態與索引是否一致？ | README 指向舊版，正式資料已更新 |
| 失敗恢復 | 中途中斷後會留下什麼狀態？ | 新版已部分啟用，但舊版無法恢復 |
| 成本失控 | 治理流程成本是否高於它帶來的收益？ | 簡單低風險任務被迫執行整套流程 |
| 演化失效 | 文件變多是否真的改善行為？ | 每輪都補規則，但任務成功率和返工未改善 |
| 停止失效 | 是否有條件結束分析？ | 永遠研究所有分支，無法交付有界結果 |

### 9.3 批判後的處置格式

每個重要問題都以一致欄位紀錄：

- issue_id 與嚴重度。
- 被檢查的主張／節點／版本。
- 觀察事實及證據來源。
- 假設與未知。
- 反例與失效路徑。
- 影響範圍及風險。
- 可重複的測試方法及預期結果。
- 裁決及理由。
- 修正版本、重新驗收結果與剩餘限制。

批判的目標不是讓文件列出更多問題，而是降低未被發現的錯誤，並把未解事項轉為可管理的決策。

## 10. 證據與成熟度：不准用單一完成狀態包辦所有意義

建議分開記錄四種不同的狀態軸。這些詞彙是候選模型，正式化前仍需建立 Schema。

| 狀態軸 | 候選狀態 | 回答的問題 |
|---|---|---|
| 來源狀態 | UNCHECKED／VERIFIED／PARTIAL／CONFLICT／UNKNOWN | 我們是否核實來源及適用範圍？ |
| 設計／能力成熟度 | CANDIDATE／EXPERIMENTAL／QUALIFIED／STABLE／DEPRECATED／RETIRED | 這項能力被評估到什麼成熟程度？ |
| 實作／執行證據 | DESIGN_ONLY／CODE_PRESENT／CALL_PATH_CONFIRMED／TEST_EXECUTED／TEST_PASS／RUNTIME_OBSERVED | 是否有可核對的實作及執行證據？ |
| 治理裁決 | PENDING／APPROVED_FOR_EXPERIMENT／APPROVED_FOR_USE／REJECTED／BLOCKED | 是否被允許進入實驗或正式使用？ |

不同狀態軸不得互相替代。例如，來源 VERIFIED 不代表抽取出的原理有效；能力 QUALIFIED 不代表目前部署版本沒有故障；治理 APPROVED 不代表測試已通過；文件存在不代表有可執行的 caller。

## 11. 阶段實施路線：先定骨架，再逐枝加深

### Phase 0｜整理現有基線

- 確認核心相關文件、候選提案、方法框架、研究紀錄、稽核紀錄與各自唯一責任。
- 分開保存主題及研究輪次，保留歷史母檔與來源限制。
- 標示事實、候選設計、尚未驗證假說與已知缺口。
- 不因整理文件而自動修改正式企劃或 P1／P2。

完成條件：索引、職責矩陣與各研究紀錄可以互相對應，沒有把候選方案誤標為已實作。

### Phase 1｜確認核心與骨架

- 由核心不變量檢查十個一級節點是否足夠。
- 做逆向批判，找出缺失責任、重複責任、錯誤假設及不必要節點。
- 確認問題骨架、功能樹、工作流、職權和狀態視圖的差別。
- 將未決項明確標出，不以自行猜測填滿。

完成條件：核心定義可清楚解釋；每個一級節點有唯一責任；主要關係和停止條件明確；不存在明顯必需責任漏項。這只表示 D0 可作暫定基線，不表示架構永遠正確。

### Phase 2｜完成第一層框架

- 對 S0–S9 補齊輸入、工作、輸出、權限、依賴、失敗與驗收邊界。
- 定義最低共通交接欄位。
- 對需要跨節點交接的資料建立引用方式。
- 針對每一枝設計至少一個正常案例及一個失敗案例。

完成條件：每一節點都可以說明自己做什麼、不做什麼、需要什麼、產出什麼及何時停止。

### Phase 3｜選擇性細節渲染

- 根據真實需求、風險與未知程度，選擇要展開的節點。
- 將候選功能、資料物件、關係、責任、依賴、權限與測試逐一列明。
- 對跨節點功能指定一個主責節點，其餘作引用或依賴，不重複定義。
- 把逆向分析和驗收案例綁定到具體功能或設計決策。

完成條件：展開的分支有清楚用途、契約、測試與處置；沒有因為其他分支尚未展開而自行捏造內容。

### Phase 4｜定最小可執行原型

- 先挑選一組代表性任務，不直接施工整個十節點系統。
- 優先選可衡量的垂直切片，例如：任務進入、問題描述、方法路由、受控能力呼叫、證據紀錄、結果驗收與結案。
- 為該切片定義正式契約、可執行測試、失敗路徑及回退方式。
- 所有實作依授權範圍執行，並保存版本與測試收據。

完成條件：可從真實輸入走完整條受限工作路徑，並以實際結果證明成功及阻擋失敗情境。

### Phase 5｜對照驗證與修正

- 建立簡單基線與候選架構的同任務比較。
- 測量品質、成本、延遲、返工、錯誤漏檢、變更影響範圍及驗收證據完整性。
- 先檢查品質與安全最低門檻，再討論效率。
- 對失敗案例進行逆向分析，決定修正、縮小範圍、回退或拒絕採用。

完成條件：結果與預設接受條件一致，並有可重複核對的證據。沒有量測結果時，不宣稱方案效率更高或為最優方案。

### Phase 6｜受控擴充與持續演化

- 只擴充具有需求或實證收益的節點。
- 任何新增能力都走功能新增程序與適用的風險 Gate。
- 版本、相容性、索引、職責矩陣、驗收紀錄與退場條件一起管理。
- 定期淘汰無價值、重複、過期或維護成本過高的能力。

完成條件：新增能力的收益可量測、變更可追溯、舊版可受控退場，整體複雜度未失控。

## 12. 量測與正式採納條件

正式採納不應只依文件完整度或主觀認為架構合理。

| 指標 | 要測量的內容 | 用來揭露的問題 |
|---|---|---|
| 任務成功率／品質 | 是否達成預先定義的目標 | 架構是否真的有用 |
| 方法路由準確度 | 選擇的主要方法是否適合問題 | 是否過度使用固定流程或錯選工具 |
| 證據完整率 | 重要主張是否有相符的來源或執行證據 | 是否把推論當成事實 |
| 變更擴散面 | 一次變更影響的文件、能力、流程及測試數量 | 模組邊界是否有效 |
| 返工率 | 初次驗收失敗後的修正次數與成本 | 契約與計畫是否清楚 |
| 回退成功率 | 故意製造發布失敗後能否恢復 | 版本治理是否真能保護系統 |
| 未授權變更阻擋率 | 未批准項是否被攔截 | 職權是否只是文件文字 |
| 啟動載入遵守率 | 新會話是否載入正確契約並遵守規則 | 治理是否真正生效 |
| 重複能力率 | 多份能力定義實際重疊的比例及維護成本 | 分工是否失控 |
| 全生命週期成本 | 時間、工具成本、返工、人工介入與維護成本 | 額外架構是否值得 |

不預先虛構量化門檻。先以代表性任務建立現況基線，再設定可接受門檻。正式採納需同時滿足品質／安全最低門檻和有證據支持的效益要求；任何無法量測的重大主張應保留為假說。

## 13. 主要風險與防錯原則

- **過早收斂：** 在核心不明確前建立過細樹狀圖。防錯：先確認問題與目標清晰度；不清楚就先探索。
- **架構膨脹：** 每個子問題都新增永久模組、角色或服務。防錯：要求唯一責任和收益證據；先模組化，不先微服務化。
- **細節遮住核心：** 細節越完整，越難看出主體方向是否錯誤。防錯：每層渲染前後都回看核心不變量。
- **樹與流程混用：** 把功能分類當成執行順序。防錯：功能歸屬、問題關係、工作流程和職權各用適合的視圖表示。
- **錯誤抽象放大：** 從不完整來源抽取原理，再當共用能力重用。防錯：來源、假設、適用條件與驗證結果一起記錄，未驗證者保持候選。
- **循環驗證：** 同一 AI 形成方案、生成測試並批准結果。防錯：接受條件先定、保留獨立反例、使用可核對執行證據。
- **權威狀態不一致：** 摘要、索引、正式資料各自維護。防錯：指定唯一權威來源，將其他視圖當派生資料並做一致性檢查。
- **永無止境的逆向分析：** 不斷找更多可能漏洞，無法交付。防錯：設定任務相關性、風險門檻與停止條件，明列未覆蓋範圍。
- **把文件變多當成演化成功：** 架構越來越長，但任務結果沒有改善。防錯：用相同任務集比較品質與成本，允許刪減和維持現狀。
- **研究內容被誤升格為企劃：** 某個研究結論被當成已批准決策。防錯：研究紀錄、候選架構、正式企劃、實作證據與採納批准分開標示。

## 14. 階段性驗收清單

在宣稱本階段總結完成之前，逐項確認：

- [ ] 核心定義清楚，而且不以工具或流程數量代替核心價值。
- [ ] 核心不變量已列明，且每條都可以轉成可檢查的設計或行為條件。
- [ ] 一級骨架涵蓋必要責任，節點之間沒有明顯重複或必需責任缺口。
- [ ] 問題骨架、功能樹、工作流、職權、狀態與證據視圖彼此分離。
- [ ] S0–S9 第一層框架皆具備輸入、輸出、唯一責任與邊界。
- [ ] 重要跨節點交接有 ID、版本、依賴、證據與權限資訊。
- [ ] 細節渲染按需求、風險與未知程度啟用，不強制一次展開全部枝節。
- [ ] 新增功能有唯一歸位、關係分析、契約、權限、反例及驗收方法。
- [ ] 逆向分析能導向可測試的失效條件與具體裁決。
- [ ] 來源、設計、程式、測試和 Runtime 證據沒有被合併成同一完成狀態。
- [ ] 正式企劃更新具有基準比較、具體批准範圍、寫前重核及寫後驗收。
- [ ] 代表性任務與現況基線已定義，並能以實際結果比較收益與成本。
- [ ] 參考索引、唯一職責矩陣、連結和歷史版本已同步。
- [ ] 所有未核實、未執行與待裁定事項仍被明確保留。

在尚未實作或執行的項目上，驗收狀態必須標記 NOT_EXECUTED／BLOCKED，不可為了讓清單全勾選而宣稱通過。

## 15. 本階段裁定與後續方向

### 15.1 本階段已形成的成果

- 形成一個可供後續批判的候選核心定義。
- 建立十個一級骨架節點與節點關係。
- 定義各節點的第一層輸入、工作、輸出、責任邊界與初步驗收方向。
- 定義後續逐層渲染、功能新增、職權劃分、逆向分析、成熟度與驗收的共同程序。
- 明確規定這是一個適應式架構，不是所有任務都要依序通過十個節點的固定流水線。
- 將實作、測試、Runtime 與正式採納保留為後續 Gate，而不是提前宣告完成。

### 15.2 尚未完成、不得宣稱完成的事項

- 十個節點仍是候選骨架，尚未透過代表性任務證明沒有更簡單或更合適的替代結構。
- 第一層框架尚未成為正式 Schema 或強制執行契約。
- 候選功能清單不表示功能已實作，也不表示所有候選功能都有必要實作。
- 職權矩陣與更新程序尚未被證明已由 Runtime 強制執行。
- 逆向分析流程與量測指標仍需用固定案例和實際執行收據驗證。
- 本文件未獲正式架構採納授權；不取代既有架構提案 v0.2。

### 15.3 建議下一步

下一輪應以本文件的 D0 核心與骨架為唯一討論焦點，先做一輪逆向批判，不要立即增加更多功能細節。重點檢查：核心是否夠根源、十個骨架節點是否過多／不足、節點責任是否重疊、主要關係是否遺漏，以及是否能涵蓋不同類型問題而不被固定流程限制。

若 D0 仍有重大問題，先修正核心與骨架；只有通過這輪反證後，才依序驗收 D1 第一層框架。D1 通過後，再選擇一至兩條高價值分支進行 D2/D3 渲染與最小可執行原型。這樣可以避免在錯誤骨架上投入大量細節和施工成本。
