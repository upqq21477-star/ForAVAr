## 摘要

1. 上一輪已知寫入動作為 5 次：主紀錄建立、事件長文建立、主紀錄中繼資料補改、索引更新、追溯總表更新。主紀錄被寫入兩次，是可直接避免的重工。
2. 優化候選是在任何寫入前一次定妥主紀錄內容、文件 ID、事件 ID、索引與引用編號；一般低風險紀錄不另建重複事件長文，事件摘要只放追溯總表；依規定補 SOP 執行台帳。
3. 單次桌上推演中，已知寫入操作由 5 降至 4（減少 20%）；寫入加末端讀回由 9 降至 8（減少 11.1%）。這是可查操作數的比較，不是實際耗時百分比。
4. 可把多筆 GitHub 操作收束在一次工具編排中，最後集中讀回；但底層仍是多個檔案 API 操作與多個提交，不是真正的原子交易。
5. 模擬欄位、導航與狀態契約未發現預定資料漏項；故障注入則確認多檔寫入可能留下部分提交。必須停止後續寫入、標記 PARTIAL，僅修復未完成步驟，不能宣稱完全原子或全庫無錯。
6. 使用者回報上一輪實際耗時接近 20 分鐘，但現有紀錄沒有完整計時器與逐次工具延遲；不得直接換算成節省幾分鐘。跨任務有效性、實際耗時改善及自動化強制執行仍未驗證。

## 1. 任務範圍與基線

### 1.1 同一工作負載

模擬工作負載固定為：建立一份有摘要與目錄的討論紀錄，並同步必要的導航入口、重要變更事件及 SOP 執行結果。不改變內容品質要求，也不刪掉必要的驗收。

### 1.2 可重建的舊流程

| 操作 | 次數 | 問題 |
|---|---:|---|
| 建立主紀錄 | 1 | 必要 |
| 建立獨立事件長文 | 1 | 與主紀錄重複保存部分目的、結論與檔案清單 |
| 再次更新主紀錄中繼資料 | 1 | 文件 ID／引用編號等資訊未在首寫前全部定妥 |
| 更新文件索引 | 1 | 必要導航 |
| 更新變更追溯總表 | 1 | 必要追溯 |
| 末端讀回既有四個產物 | 4 | 必要驗收，不列為冗餘 |

可辨識基線為 5 次寫入加 4 次末端讀回，共 9 次內容操作。先行查規範、分析推理、工具重試與等待的完整數量未有可靠逐次日誌，故不把 9 冒充上一輪全部工具呼叫數。使用者回報的接近 20 分鐘只作外部觀察基線，不視為精密量測。

## 2. 優化後的流程模型

### 2.1 寫入前一次定案

先建立單一變更清單，固定任務 ID、目標內容、檔案路徑、索引條目、引用 ID、追溯事件 ID、驗收條件及停止條件。所有中繼資料在主紀錄第一次寫入前完成，不允許為補欄位而重新寫入主紀錄。

### 2.2 依唯一責任保存資料

- 主討論紀錄：保存完整推理依據、基線、候選流程、量化方法、風險及未知項。
- 文件索引：只新增一個導航入口與必要的雙向引用。
- 變更追溯總表：只保留事件摘要、涉及檔案、提交依據與驗收範圍，不重複複製分析正文。
- SOP 執行台帳：追加一列執行結果與流程候選；不複製整份報告。
- 獨立事件長文：只有在事故、重大衝突、複雜遷移、不可逆操作或需要單獨稽核的詳細證據足以證明其必要時才建立。一般紀錄不預設新增。

### 2.3 工具編排

1. 一次讀取本次必要的索引、追溯表與執行台帳；不為低風險紀錄載入整個倉庫。
2. 在記憶體中形成所有目標文件的最終內容，再執行寫入。
3. 對同一分支的多檔寫入採序列執行，不平行競爭更新同一個分支指標。
4. 最後集中讀回所有受影響檔案，驗證實際內容、路徑、引用、字數與狀態。
5. 任何寫入或驗收失敗，停止宣告成功；保留已成功提交的清單，標記 PARTIAL／BLOCKED，只重試失敗項目。
6. 將底層多檔操作收束在單一編排回合可減少模型與工具之間的往返，但不代表底層 API 數、提交數或等待時間歸零。

## 3. 單次模擬與量化結果

### 3.1 操作數比較

| 指標 | 舊流程基線 | 優化模型 | 差異 |
|---|---:|---:|---:|
| 主紀錄寫入次數 | 2 | 1 | -50% |
| 已知寫入操作 | 5 | 4 | -20% |
| 末端檔案讀回 | 4 | 4 | 0%；保留驗收 |
| 已知寫入＋末端讀回 | 9 | 8 | -11.1% |
| 獨立解說／事件長文 | 1 | 0 | -100%；事件摘要仍保留在追溯總表 |
| 詳細敘事的權威紀錄 | 主紀錄＋事件長文 | 單一主紀錄 | 減少一份重複敘事 |

### 3.2 往返成本怎麼解讀

若舊流程把 5 次寫入與 4 次讀回各自作為外層工具回合，則可設計成一個編排回合依序完成寫入，再用集中讀回完成驗收；此模型可將這一階段的外層往返由 9 次收束成 2 次。這是流程編排設計值，不是完整歷史日誌實測，不能把 77.8% 直接解讀成總耗時改善。

GitHub 檔案內容 API 仍需要分別處理不同路徑，這次不宣稱已形成單一原子提交。若以使用者回報的接近 20 分鐘作背景，現有證據不足以計算實際節省分鐘數，也不足以證明總耗時會同比下降 11.1% 或 77.8%。後續需要在至少兩個可比任務中記錄開始／結束時間、讀寫操作、重試和驗收結果。

## 4. 錯誤、失真、遺漏及故障注入

| 檢查項 | 模擬方式 | 結果與風險 |
|---|---|---|
| 主內容完整性 | 檢查摘要、目錄、舊流程基線、優化步驟、量化結果、風險、驗收邊界是否都有欄位 | 預定欄位全部列入；實際文件仍須讀回驗收 |
| 追溯完整性 | 不建事件長文，但要求追溯總表有事件列，並記錄主紀錄提交依據 | 不因移除重複文件而移除事件身分或提交證據 |
| 索引可達性 | 索引入口與主紀錄回鏈都列入變更清單 | 應逐條檢查路徑存在；索引局部通過不代表全庫引用圖通過 |
| 重複／失真 | 將完整分析只放在主紀錄，其他台帳只保留摘要和定位 | 可減少同一結論多處文字版本不同步；但摘要必須保留狀態、限制與未驗證項 |
| 寫入中途失敗 | 假設第三個檔案寫入失敗，前兩次提交已成功 | 多檔案內容 API 非原子；會留下部分更新。正確處理是停止、列出已提交檔案、標記 PARTIAL，再只修復未完成項，不可謊稱整批回滾 |
| 來源／權限越界 | 檢查寫入目標是否只在 forAVAr | 本次模擬範圍僅限 forAVAr；P1／P2 不寫入，正式企劃不修改 |
| 全庫缺漏 | 檢查是否有全 repository 連結掃描及跨任務回歸證據 | 未執行；維持 NOT_VERIFIED，不宣稱全庫無錯或沒有任何資料遺漏 |

### 4.1 單次模擬結論

- **已改善的風險：** 主紀錄重複寫入、事件與主紀錄重複敘述、分散決定中繼資料造成的返工。
- **沒有被消除的風險：** 多檔寫入的非原子性、外部工具延遲、部分失敗後的暫時不一致、全庫引用與內容完整性未掃描。
- **未證明的事項：** 真實執行耗時提升、廣泛任務適用性、所有引用均有效，以及 AI Runtime 會自動遵循流程。

## 5. 集中資料管理規則

這是本次試行所採用的資料分工，不是已核准的新固定 SOP：

1. 一份任務只有一份完整的討論／分析正文。
2. 同一變更批次用一個事件 ID，追溯總表只記摘要、受影響檔案及驗收狀態。
3. SOP 執行台帳只記一列 RUN 與候選編號；完整分析不複製到台帳。
4. 索引維護入口與反向引用，不複製正文摘要以外的內容。
5. 不因追求少文件而刪除來源、未知、反例、提交依據或驗收證據。
6. 遇到重大事故或需獨立稽核的複雜操作，仍可新增專用事件詳文；「集中」不等於禁止合理分支。

## 6. 結論與驗收邊界

本次單一桌上推演支持將「預先定案、單一主敘事、分責台帳、集中編排、集中讀回」保留為優化候選。可直接證明的改善是已知寫入操作減少 20%，寫入加末端讀回操作減少 11.1%；外層往返收束是編排設計值，不是實測耗時數據。

流程維持 SIMULATED_ONLY。未有至少兩個具代表性的真實任務，並同時比較漏失率、返工、錯誤、實際耗時與驗收完整率前，不升級為 CURRENT SOP。
