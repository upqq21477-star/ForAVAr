## 1. 問題登錄內容：PR-052

**問題：** 當 Claude／執行代理無法直接讀取 GitHub 的最新檔案時，手邊沒有綁定來源版本、Current、Active Work、核心限制、測試證據和下一步的可攜式狀態包；工作者因此用初始藍圖、舊交接或部分摘要重建目前狀態，並可能在局部修補時逐輪偏離原始目標。

**嚴重度：A（高影響系統性風險）。** 這不是要取代 S 級 PR-001；PR-001 描述目標漂移這個核心風險，PR-052 追蹤一種可治理、可測量的系統性觸發機制。若新的狀態包與載入閘門能被驗收，PR-052 可降級，但不能因此宣稱 PR-001 永久消失。

**原因／原理：**
1. 藍圖是目標規格，不是動態執行狀態；它沒有足夠資訊取代 Current、目前工作包、當前 HEAD、測試結果及未解阻塞。
2. 無儲存庫存取時，模型仍受提示／任務壓力而可能繼續解題，但缺少可驗證的現況輸入，形成「資訊不足但仍推理」的失效模式。
3. HANDOFF、README、Current 和工作包是不同用途的資料；若沒有單一有效來源映射及相容性檢查，較完整、語氣較像指令的舊交接可能被誤用為最新狀態。
4. 局部錯誤與核心不變量／驗收條件之間若沒有明確可追溯關係，修補會朝當前錯誤局部最佳化，並可能新增不必要流程、能力或文件。
5. 文件中有規則或測試案例不代表啟動時必定載入，也不代表控制已接線或執行通過。

**目前處理方向（候選，未宣稱實作）：**
- 每次啟動使用可攜式 State Bundle，分開記錄 Core Anchor、Current State、Task Contract。
- 綁定來源 Commit／檔案 SHA、產生時間、讀取範圍和 manifest；舊證據必須核對是否仍適用。
- 狀態包缺失、過期、關鍵來源衝突或無法核對時，回報 `BLOCKED_CONTEXT`／`STALE_CONTEXT`，禁止依賴猜測現況的高影響施工。
- 每次局部修補都建立「問題 ID → 根因假說／證據 → 核心不變量 → 最小差異 → 受影響案例 → 驗收證據」的變更鏈。
- 用跨會話反例測試驗收；文件規定與實際行為分開記錄。

**狀態：OPEN。** 目前只有研究及設計方向，未找到已通過的唯一狀態包產生／載入程序或跨會話防漂移測試收據。

## 4. 如何解決：按根因治理，不用新增平行狀態機

### R1｜建立可攜式 State Bundle（優先級 P0）

最低欄位需包括：
- 快照識別：repository／branch／commit SHA（若可得）、來源時間、manifest digest。
- Core Anchor：原始目標、不可變核心、不納入範圍、成功／停止條件。
- Current State：權威 Current 路徑及版本、Active Work、Feature Batch、Construction、當前階段、精確下一步、完成／未完成、阻塞。
- Evidence State：每項證據的類型、對應來源版本／SHA、PASS／FAIL／NOT_EXECUTED／UNKNOWN。
- Change Ledger：近期批准差異、明確拒絕／延後項、受影響範圍及測試。
- Handoff Contract：下次工作唯一入口、必要檔案、禁止事項及預期輸出。

State Bundle 應由 Current／Work／Feature Batch／Construction 等既有權威來源派生，不自建第二個 Current。生成物只是一份可攜快照，必須保存來源指紋並指出它不能自行覆蓋的新現況。

**無 GitHub 模式：** 必須把上面所需檔案片段及 manifest 隨工作交接；如果生成資料缺失或過期，設為 `BLOCKED_CONTEXT`，不繼續做依賴當前實作狀態的變更。這能讓免費版無 repository 連線時仍有具體狀態輸入，不依賴模型猜測。

### R2｜新增 Core-Drift Gate（優先級 P0）

每一項候選修正須記錄：
- Problem ID 與直接觀察證據；
- 對應的 Core Anchor／接受條件；
- 根因假說和至少一個替代解釋；
- REUSE／MODIFY／MERGE／NEW 決策與依據；
- 變更範圍、非目標、相依引用、回歸案例；
- 基準指紋與寫入授權；
- 驗收結果、實際證據及剩餘未知。

若修正不能連結到已確認問題或可辯護的根因，先記入待辦，不自動成為目前工作。只有證據顯示核心或通用契約本身錯誤時，才提議重新開啟架構範圍。

### R3｜權威衝突與 stale context fail-closed（優先級 P0）

- Current 決定當前狀態；藍圖決定目標設計；Feature Batch 決定凍結的功能／案例範圍；Work 決定下一個工作單元操作；HANDOFF 是恢復與交接，不可取代 Current。
- 如果不同視圖對同一項狀態相互衝突，要有明確狀態機：`CONFLICT` → 只讀比對 → 找出權威來源／版本 → 修正派生視圖（經授權）→ 回讀驗證。
- 讀不到權威來源、不知道來源是否為最新，或不能證明快照與所需基線一致時，不能自行把信心較高的摘要當成權威；只能做不依賴衝突事實的工作。

### R4｜使證據綁定目前版本並修復路徑參照（優先級 P1）

- 所有重要測試收據綁定目前 HEAD、測試方法、源碼指紋與實際退出碼。
- 每個 Feature 的 implementation ref、正式 caller、Schema、三種局部案例、具體 test_method、驗收證據及下游影響要形成一份可核對矩陣。
- 先解 REF-01／REF-02／REF-03 的來源問題；不能用路徑更名掩飾缺失證據，也不能將歷史成功標成目前成功。

### R5｜用跨會話反例驗收（優先級 P1）

最少執行 DRIFT-01～DRIFT-08：只提供藍圖、HANDOFF／Current 衝突、局部修補加入無關功能、基準雜湊改變、歷史 PASS 但 HEAD 改變、交接漏掉限制、連續數輪後核心不再被重述、來源不可用。每個案例固定輸入、預期、實際結果、版本指紋與收據；未測維持 NOT_EXECUTED。

## 5. 不應採取的錯誤解法

1. **不要只把更多規則塞進初始藍圖。** 這無法提供當前 HEAD、工作狀態和驗收收據，還可能增加上下文負擔。
2. **不要讓每次發現問題都新增永久能力。** 應先分類一次性問題、局部規則、可重用能力、架構不變量；以證據決定是否普遍化。
3. **不要以新增第二個 Current／Roadmap／Handoff 來消除衝突。** 先決定既有文件唯一責任，修正派生視圖，而非增加另一份競爭來源。
4. **不要把狀態包本身當成最新真相。** 它是有來源時間和雜湊的快照；若上游更新或來源指紋不匹配，必須 stale／conflict。
5. **不要把表格填滿算成通過。** 沒有可追溯收據與實際驗收結果，一律不升級狀態。
