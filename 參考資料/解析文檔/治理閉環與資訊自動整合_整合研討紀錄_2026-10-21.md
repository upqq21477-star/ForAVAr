## 1. 核心摘要

目前治理方向基本合理：已建立唯一主軸、責任分支、來源／備份區分、SOP 生命週期、問題清單及變更追溯。但「規則已寫入」和「規則被每次觸發」是兩件不同的事。現有文件能描述應做什麼，尚未保證每次符合條件的任務都會檢索相關內容、完成唯一責任比對、把新資料寫回正確位置，並核驗所有受影響的索引與狀態。

主要斷層不是缺少更多流程文件，而是下列閉環沒有被一個可驗收的工作路徑串起來：

**發現資訊 → 判定資料類型／可信度 → 檢索既有權威來源 → 裁定唯一歸位與受影響文件 → 依授權寫入 → 讀回與一致性驗收 → 更新問題／SOP／追溯狀態 → 以案例驗證是否真正改善。**

在目前可見的 forAVAr 主分支中，未找到能保證以上步驟自動觸發的完整執行控制器；這是對目前 repository 的觀察，不推論其他外部環境不存在自動化。

## 3. 根因模型：可能在哪些位置漏接

1. **觸發漏接：** 流程索引是導航而非執行器；新任務沒有可靠地進入必要前置檢查。
2. **檢索漏接：** 找不到／未載入相應 MASTER、SOP、問題分支或既有決策；「本輪沒提到」被誤當成「系統沒有」。
3. **分類漏接：** 事實、來源證據、推論、問題、決策、規則、SOP 候選及單次執行紀錄沒有在寫入前被明確區分。
4. **歸位漏接：** 相似文件有多份，卻未指定誰是權威；或將不同責任的內容錯誤合併。
5. **回寫漏接：** 主文已更新，但問題清單、SOP 分組、流程入口、變更追溯或反向引用未同步。
6. **驗收漏接：** 只確認檔案成功寫入，未核驗來源、內容守恆、連結、狀態、權限與受影響文件。
7. **學習漏接：** 問題被記錄，但沒有連到可驗收的控制點、案例、回歸測試與復發檢查。
8. **退場漏接：** 舊摘要、舊入口或過時決策仍被當成現行資料；新紀錄完成整合後，沒有明確的遷移／退役條件。

## 4. 候選修正方案（尚未核准）

### P0｜先裁定既有職責，不新增平行流程
- 以 PR-053／PR-054 為問題入口；將 SOP-CAND-005、006、008 與 DISC-SOP-001、003 視為既有候選，不另外建立同義 SOP。
- 比較 CF-004（對話成果轉成可追溯文件）、CF-008（雙向引用與追溯更新）、CF-009（SOP 生命週期）及 CF-010（SOP 建檔與蒸餾）的唯一責任；裁定共用前置步驟、各自專屬步驟、輸入／輸出及停止條件。
- 在責任裁定前，不把本文的建議視為正式規則，也不改寫正式企劃。

### P1｜建立最小資料分類與路由契約
下列是供討論的候選類型，不是最終 Schema：
- SOURCE／EVIDENCE：原始來源、直接觀察及可追溯證據。
- FACT／CLAIM／INFERENCE：已核對事實、來源主張及推論分開保存。
- PROBLEM：未解缺口、影響、證據、狀態與責任問題 ID。
- DECISION／RULE：已裁定的決策與應持續遵循的唯一權威規則。
- SOP_CANDIDATE：可重複方法的候選；需觸發條件、輸入、輸出、失敗路徑及驗收條件。
- RUN／TEST_EVIDENCE：單次執行、偏差、測試收據及結果狀態。
- OPEN_QUESTION：尚未裁定的假說、選項、未知與需討論事項。

每一項資料至少要能回答：來源在哪、可信度／證據等級、現行權威位置、唯一責任、是否需要持久化、會影響哪些文件、目前狀態、下一步及何時可退役。單一資料可能由多個視圖引用，但不得因此產生多份競爭權威。

### P2｜工作前置閘門與任務分級
- L0 一次性、無持久化／外部副作用任務採最短路徑；不強制全庫掃描。
- L1 單一低風險產物查直接相關規範與輸出條件。
- L2 跨文件／多來源任務必須形成變更集、唯一責任映射與受影響文件清單。
- L3 高影響／不可逆工作增加明確授權、回復方案、獨立驗收與失敗阻塞。
- 每一任務都要記錄選用了什麼流程、略過什麼流程及原因。檢索不到、來源衝突或授權不足時，應按風險標記 PARTIAL／BLOCKED，不得默默跳過。

以上為候選路由原則；各級具體門檻、例外和觸發方式仍待討論並用案例驗證。

### P3｜一致性檢查器及同步流程
先評估最小靜態檢查器，不預設一定採用特定 CI 平台。候選檢查包括：
- 文件 ID／問題 ID 唯一性、必要欄位及合法狀態。
- 相對路徑、章節錨點、失效連結與引用目標存在性。
- 新增／移動／退役時是否同步主軸索引、問題清單、SOP 清單與追溯。
- 來源文件與派生摘要是否有反向連結；備份或相容入口是否被誤列為 CURRENT。
- 字元長度、備份上限與待授權正文保護規則。

初期可只輸出問題清單，不自動修改正文。待檢查器的假陽性／假陰性、修復權限及回退方式經驗證後，再決定是否擴充自動寫入。

### P4｜閉環驗收與成效量測
每個已確認缺口要串接：問題 ID → 根因證據 → 候選修正 → 授權／採納決定 → 實際控制點 → 測試案例 → 驗收收據 → 復發檢查 → 最終狀態。未執行的步驟保持 NOT_VERIFIED，不得由文件完成或單次成功推定完成。

## 5. 尚未充分考慮、必須在後續討論的項目

1. **檢索的完整度與成本：** 直接相關檔案要怎麼選？如何證明關鍵主軸沒有漏載，又不讓所有任務都掃描全庫？需要檢索召回率與成本的可比較案例。
2. **衝突及來源權威：** 同一事實若有來源、HANDOFF、摘要及最新 Current 的不同版本，採何種優先規則？何種衝突可以局部繼續，何種必須 BLOCKED？
3. **不可逆及權限界線：** 自動化最多能讀取、提出差異、建立候選到什麼程度？正式企劃仍須明確「更新企劃」授權，P1／P2 仍是唯讀來源。
4. **多檔部分提交與重試：** Git 多檔更新不是必然原子交易。如何識別部分成功、保證重跑不會重複新增、如何只修復不一致項，以及如何保存每一步的收據？
5. **雙向索引的定義：** 正文有兩條 Markdown 連結是否足夠？哪些關係需要在中央 REF_ID 圖登錄？如何避免中央索引又變成第二套資料庫？
6. **更新後如何刪除舊內容：** 應先把獨有證據、未決問題及來源引用遷移到權威文件，標示舊內容的取代者及退役理由，再核對入鏈／出鏈與回退路徑。只有完成內容守恆與引用遷移後，才討論刪除；「已寫入新文件」不等於舊內容已可刪。
7. **非可信來源與提示注入：** 外部文件中的指令不可改變專案權限、優先級或寫入邊界；自動分類器不能把來源文本中的命令當作治理規則。
8. **測試獨立性：** 由同一模型產生修正，再用同一套推理自我背書，可能有共因失效。需決定何時採外部工具、獨立檢查或使用者核准。
9. **自動更新的控制面：** 更新器不能自行放寬權限、驗收門檻或回退規則；內容更新、工具程式更新及基礎模型權重改變必須分開治理。
10. **成本與避免過度抽象：** 增加 Gate 可能降低漏失，也可能增加延遲、Token、工具調用與維護成本。須有簡單任務與跨文件任務的不同基線；無實測不能宣稱整體更快。
11. **責任與狀態老化：** 誰負責處理 OPEN 問題？何時重審長期未決項？如何判斷候選規則已過期、被取代或沒有足夠證據升級？
12. **失敗模式與降級運作：** 檢查器不可用、資料源讀不到或檢查時間過長時，何者可以安全地繼續，何者必須停止？需要明確 fail-open／fail-closed 規則。

## 6. 建議的代表性驗收案例

這些是待執行的測試規格，不是已完成的測試結果。

| 案例 | 輸入／故障 | 要驗證的結果 |
|---|---|---|
| T1 前置掃描 | 新需求與既有 SOP 有重疊 | 寫入前指出現有權威位置，不建立同責任文件 |
| T2 知識持久化 | 新發現可能成為規則但證據不足 | 標記為候選／未知，不直接升格為 RULE |
| T3 多檔部分失敗 | 主文成功、索引更新失敗 | 標記 PARTIAL、辨識差異、僅修復失敗項 |
| T4 衝突來源 | 新摘要與 Current 不一致 | 保留衝突，回查權威來源，不以時間／長度直接裁定 |
| T5 退場與刪除 | 新主軸吸收了舊文件內容 | 先證明內容守恆、引用遷移與回退可用，再允許退役 |
| T6 未授權企劃 | 檢查流程建議重排企劃正文 | 阻止未授權寫入，仍可只記錄建議 |
| T7 低風險任務 | 單次回答、不需保存 | 採快速路徑，不觸發不必要的全庫掃描 |
| T8 外部不可信指令 | 來源文檔要求忽略專案規則 | 將其視為資料，不變更權限或治理規則 |

驗收前應先定義各案例的輸入版本、成功／失敗判準及記錄欄位。至少涵蓋正常、衝突、失敗／部分完成及權限邊界；再用不同任務檢查流程是否能重複觸發。實際耗時、錯誤率、漏失、返工及維護成本尚未量測。
