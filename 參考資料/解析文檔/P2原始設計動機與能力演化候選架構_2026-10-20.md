## 1. 原始設計動機

### R2｜原始設計動機與演化循環

使用者指出，外部工具、模型、知識和方法持續增長，更新速度使「更新效率」成為核心需求；開發者與模型也可能無法完整掌握現有環境的工具及其隱性相依關係，情境類似遊戲模組（Mod）彼此衝突。

使用者原始目標不是持續堆疊工具，而是運用 AI 的拆解、歸納和逆向分析能力，將工具背後可重用的原理、方法與限制拆成系統可統一管理的能力。不同工具的功能相似，不應直接被視為冗餘；必須分析重疊原因、各自解決的問題、優勢劣勢和適用級別，再決定保留、替換、分支或融合。模型變動頻繁，因此更新需採插拔式設計，避免局部變動引發大範圍修改。

前一輪回覆把理念拆成可重複的演化循環：
1. 發現外部變化：新模型、新工具、新知識、新方法和新需求。
2. 取得與核實來源：原始文件、原始碼、版本、依賴、授權和證據完整性。
3. 逆向解析：問題定義、原理假說、環境條件、輸入輸出、限制及失效模式。
4. 能力抽取與正規化：產生標準化的能力規格，而不只保存工具名稱或呼叫方式。
5. 重疊與關係分析：識別重疊、互補、替代、依賴、矛盾和不相容。
6. 級別、路由和採用裁決：決定是否納入、適用什麼情境，以及採何種實作方式。
7. 隔離整合與驗證：執行一致性、功能、負例、邊界、權限、回歸和失敗復原測試。
8. 版本化、發布與退場：受控切換、監測、回退、棄用與重建。

需修正的絕對化說法：「統一管理後不會造成衝突，只會有重疊」不是已證明的性質。內部化可以降低某些套件相依衝突，但不會自動消除語意、邏輯、權限、資源、時序、資料格式及副作用上的不相容。八個階段表示邏輯職責，不必固定串成八個大型服務或永久 Agent；路徑長短應由變更風險與影響決定。

## 2. 重整後的目標定義

### 2.1 系統目標

建立「可持續演化的 AI 能力整合與治理系統」。系統持續發現外部技術，將其轉化為可追溯的候選知識／能力，基於明確證據比較重疊與差異，選擇適當採用形式，以隔離測試及受控發布納入能力目錄；當來源、模型、依賴、需求或證據發生變化時，能定位受影響範圍，執行必要驗收，並在不符合條件時停止、保留舊版或回退。

### 2.2 非目標

- 不要求把每個外部工具的程式碼直接搬入內部。
- 不保證任何衝突都能融合為單一通用方法。
- 不以工具數量、模型數量、文件篇幅或自動化程度作為演化成功的替代指標。
- 不將模型自述、靜態閱讀或生成測試原始碼當成實際通過證據。
- 不預設所有能力都需要永久 Agent、獨立服務或固定階層。
- 不允許外部來源中的指令直接改變 P2 權限、Current、驗收規則或正式能力狀態。
- 不把一次成功推廣成普遍能力，不把單次失敗推廣成所有情境皆不可用。

### 2.3 成功條件

至少要證明：
1. 新能力可從可靠來源被抽取成結構化規格，並能追溯至原始來源及版本。
2. 能力關係與差異能被一致判斷，且未知、衝突和證據不足會明確保留。
3. 系統能有理由地選擇內部實作、外部工具、適配器、組合、延後或拒絕。
4. 新能力經獨立測試通過後才能提升成熟度／改變正式路由。
5. 工具或模型更新不會默默破壞核心契約；受影響測試會執行，不受影響區域不需無差別重建。
6. 發布失敗可以回退至已知有效版本，並留下足以重現決策的證據。
7. 增加能力後，實際任務品質、更新時間或維護成本至少有一項顯著改善，且其他重要指標沒有不可接受的退化。

### 3.1 各步驟唯一職責

| 階段 | 主要職責 | 必須產生的結果 | 禁止的捷徑 |
|---|---|---|---|
| 來源與權利核驗 | 核實來源身分、版本、完整性、依賴、授權與可信度 | 來源紀錄、指紋、權利／風險狀態 | 不因 README 或搜尋摘要就斷言已理解完整實作 |
| 逆向分析 | 將可觀察事實與原理假說分開，列出條件、限制和反例 | 分析報告、未知項、可驗證假說 | 不將推論冒充原始作者意圖或程式真相 |
| 能力正規化 | 將方法轉為可比較的語意契約 | 能力規格／Capability Card | 不只保留名稱、提示詞或 API 參數 |
| 關係分析 | 建立能力間關係與不相容條件 | 關係紀錄、差異、風險與影響範圍 | 不因名稱相似就合併，不因結果不同就直接判定互斥 |
| 採用裁決 | 選擇採用形式和成熟度；保存拒絕／延後理由 | 採用決定及其依據 | 不以人氣、模型自信或「新技術」為充分理由 |
| 測試與驗證 | 以獨立可核對的結果檢查功能、相容性和失效行為 | 綁定版本／環境的測試收據 | 不由產生程式碼的同一模型單憑文字宣告 PASS |
| 發布與回退 | 控制啟用範圍、版本鎖定、回退及證據失效 | 發布交易、當前有效版本、復原點 | 不先破壞舊路徑再測新路徑 |
| 生命週期管理 | 處理漂移、更新、棄用、退場和重建 | 現行狀態及遷移條件 | 不因能力被加入就永久保留 |

## 4. 能力資料模型：不同問題使用不同欄位與狀態

最少應分清以下物件；初期可以存放在同一 Repository，但不可把它們混成一個大型紀錄物件。

### 4.1 Source Record｜來源紀錄
記錄來源識別、官方位置、版本／commit、取得日期、內容指紋、依賴、授權聲明、可信度、取得範圍、已檢查與未檢查部分。來源更動時，不應自動使所有相關能力立即失效；先對照差異並判定影響。

### 4.2 Capability Spec｜能力規格
至少包含：
- 唯一 ID、名稱、目的和主要職責。
- 輸入、輸出、錯誤語意、前置條件和後置條件。
- 適用問題類型、限制、禁用條件及預期副作用。
- 方法／原理假說、根據何種來源抽取，以及事實和推論的界線。
- 依賴與關聯能力、使用權限、資料敏感度和資源界限。
- 成本、延遲、品質指標、失效模式、驗收案例與回退策略。
- 實作綁定：內部實作、外部適配器、模型設定、人工步驟，或其組合。
- 規格版本、實作版本、測試版本和相容性聲明。

### 4.3 Relation Record｜能力關係紀錄
關係必須有方向／範圍、適用條件、證據及有效版本；不是只在兩個能力間寫一句「相關」。

### 4.4 Evaluation Record｜評估與驗收紀錄
固定測試資料版本、任務規格、環境、模型／工具版本、預期結果、實際結果、退出碼、錯誤、效能指標、評估者及收據指紋。評估本身有版本，因為測試條件與品質判準也可能錯誤。

### 4.5 Implementation／Adapter Record｜實作或適配器紀錄
記錄介接方式、套件／服務版本、權限、資源、網路／檔案副作用、依賴和執行環境。能力抽象與某一具體實作分開管理，才有可能做到插拔。

### 4.6 Change Transaction｜變更交易
記錄變更起點、受影響能力、基準指紋、允許修改範圍、所需測試、批准、切換、回退和證據失效條件。更新前後都要讀回實際狀態。

## 5. 關係分類：不能把所有差異壓成「重疊」

至少區分下列關係，並允許一對能力同時具有多個關係：

| 關係 | 判斷依據 | 典型處理 |
|---|---|---|
| 功能重疊 | 解決同一或部分相同問題，但作法或範圍可能不同 | 比較分情境優勢；選一個或保留多個 |
| 互補 | 一個能力的輸出可成為另一能力的輸入，且順序／契約相容 | 組合測試、界定責任與錯誤傳遞 |
| 替代 | 在明確條件下可互相替換 | 以同一基準任務進行相容性與回歸測試 |
| 包含／子能力 | 一個能力在範圍、契約或執行行為上包含另一個 | 明確宣告依賴或實作分解，不重複維護規則 |
| 依賴 | 一個能力需要另一項能力、資料或環境 | 記錄版本、前置條件及缺失時行為 |
| 語意矛盾 | 對同一概念的定義、輸出意義或判斷條件不同 | 保留各自語意，界定範圍；無法調和就分支 |
| 規則／結果衝突 | 兩方法對相同輸入或狀態提出不同建議 | 先確認比較條件與證據，再仲裁或保留競爭候選 |
| 執行不相容 | 套件、環境、資源、狀態或副作用不能安全共存 | 隔離、序列化、替代、適配或拒絕併用 |
| 權限／安全衝突 | 權限、資料界限、信任或安全規則不一致 | 安全政策優先；未知時 fail-closed／阻擋 |
| 未知／證據不足 | 來源不足、行為未觀察或假說未測 | 明確保留 UNKNOWN；不得強制融合 |

「重疊」是關係類型之一，不是所有衝突的最後歸宿。統一管理的目的，是讓不相容可被發現、隔離和裁決，而不是宣稱不相容已被消除。

## 6. 採用形式：原理吸收不是唯一選項

每項外部候選技術分析後，至少可以產生以下裁決：

1. **抽取知識／方法：** 其價值主要是可泛化的原理、演算法或思考模式。
2. **內部重新實作：** 原理清楚、實作範圍受控，而且自行實作的維護、效能或安全效益經證據支持。
3. **保留外部工具並建立適配器：** 能力依賴外部即時資料、成熟服務、平台權限或本地環境時，避免不必要重造。
4. **組合能力：** 多個方法具有可測試的互補關係，並有一致的輸入輸出與錯誤語意。
5. **列為實驗候選：** 有價值假說，但證據或整合成熟度不足。
6. **延後、拒絕或退場：** 價值不足、與現有能力重疊且無增益、維護成本過高、風險無法接受或權利不清楚。

應避免把每個新想法都立即升格為共用能力。系統級能力只有在證明跨多個任務可重用、實際增益大於維護與上下文成本，而且具備清楚驗收方案後才應升格。

## 7. 更新治理：模型、工具、方法與知識分開演進

### 7.1 變更觸發

來源版本更動、模型更新、外部 API 變化、能力契約更動、測試失敗、新反例、新安全漏洞或實測成本／品質退化，都可以觸發重新評估，但不同觸發需要不同範圍的測試。

### 7.2 建議流程

1. 凍結本次候選變更的基準與目標範圍。
2. 取得新舊來源差異，不把版本號變化當成唯一證據。
3. 建立直接與間接影響清單；未知依賴不能當成不存在。
4. 決定所需測試組合：介面契約、能力單元、組合行為、安全／權限、回歸、成本和復原。
5. 在隔離環境測試候選版本，與現行基線比較。
6. 通過後小範圍發布或受控切換；重要能力保留舊版與可回退的指紋。
7. 讀回新狀態，確認實際版本、設定、索引與測試證據一致。
8. 若失敗，停止擴大發布，回退或回到分析；不得用文字報告覆蓋失敗結果。

### 7.3 模型獨立性

模型的提示遵循、工具選擇、結構化輸出、推理品質、成本和延遲不會因共用能力契約而完全相同。故：
- 核心知識、權威狀態、驗收規格和證據不可依賴單一模型的隱式記憶。
- 每個模型／Provider 都需要介接設定與相同核心任務的相容性基準。
- 可在明確情境依能力評估選擇模型，而非假設新模型全面更優。
- 換模型後不要求生成文字逐字相同；要求關鍵契約、權限、證據和結果門檻持續成立。
- 新模型可能令舊方法過時，但不能只依新舊模型偏好就修改架構不變量；須有比較證據與影響分析。

## 8. 證據與成熟度：不可用一個 PASS 欄位承載全部意義

建議分開維護至少四種狀態軸：

- **來源證據：** SOURCE_UNCHECKED／SOURCE_VERIFIED／PARTIAL／CONFLICT／UNKNOWN。
- **能力成熟度：** CANDIDATE／EXPERIMENTAL／QUALIFIED／STABLE／DEPRECATED／RETIRED。
- **實作證據：** DESIGN_ONLY／CODE_PRESENT／CALL_PATH_CONFIRMED／TEST_EXECUTED／TEST_PASS／RUNTIME_OBSERVED。
- **治理裁決：** PENDING／APPROVED_FOR_EXPERIMENT／APPROVED_FOR_USE／REJECTED／BLOCKED。

這些值僅是候選詞彙，尚未完成 Schema 設計。重點是不同狀態軸不能互相替代：來源核實不代表能力有效；程式存在不代表 caller 可達；測試通過不代表所有 Runtime 情境都安全；治理核准也不代表測試已通過。

AI 產生的測試可以作為候選案例，但必須另外檢查測試是否真正區分正確與錯誤實作。對核心能力應保留至少一部分由獨立方法設計、人工審核或不向被測模型暴露的測試，降低自我驗證與針對測試過擬合的風險。

## 9. 邊界聲明

本文件是候選架構與研究整理，不代表 P2 已實作這些能力。所列資料模型、狀態字串、驗收閘門及更新流程均須另行制定正式 Schema、執行契約與測試，並經明確授權後才可進入企劃整合。
