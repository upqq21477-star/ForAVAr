後續目標架構設計另見[未來框架：封包生命週期 × 能力索引融合架構提案 v0.1](./未來框架_封包生命週期與能力索引融合架構提案_v0.1.md)。該文件目前是待裁定的 PROPOSAL，只負責描述未來設計，不取代本文件的來源融合責任，也不代表 P1／P2 已核准或實作該架構。

目前有兩條不同性質的來源：

1. **封包 A｜R3d130j relay 工作包：** 原始位元組已於 2026-10-21 取得並與原始 Git Blob 身分核對。ZIP CRC 通過；774 個成員項目與 773 筆 Manifest 雜湊均驗證通過；312 個 JSON 語法解析、374 個 Python AST 靜態解析通過。原始 ZIP 現由 [P2 main 唯讀來源](https://github.com/upqq21477-star/P2/blob/main/%E5%8F%83%E8%80%83%E8%B3%87%E6%96%99/P2-relay-R3d130j.zip)提供，forAVAr 的二進位副本已依 EVT-0028 退場。完整解壓歸檔、程式執行、測試與 Runtime 驗收尚未完成；HANDOFF 中未經 ZIP 證明的額外主張仍應標為 HANDOFF_CLAIM。
2. **封包 B｜封包式問題解決架構文件套件：** 四個成員已實際解壓，外層與 DOCX 內層結構驗收通過；Markdown／DOCX 正文差異已在限定抽取與正規化範圍內完成分類。企劃書是 PROPOSAL，不是已核准或已實作的 P2 規格。

**融合後的建議：** 把「問題解決流程」「工作封包契約」「角色／功能責任」「工程成熟度」「封包狀態」「證據等級」「會話／批次交接」視為互相關聯但不同的軸。採用一個簡單的因果流程，從共同權威資料派生功能樹、流程圖、角色視圖與進度查詢；只有在必要條件成立時才啟用功能。不要把不同軸壓成一個巨大的狀態欄，也不要建立多套平行真相。

### 1.2 封包驗收狀態

- **封包 A：BLOCKED。** forAVAr 與 P2 的對應 ZIP 具有同一 Git Blob SHA 與大小，但兩邊的 Base64 讀取均回傳空內容，Blob／raw 途徑也未交付原始 bytes。這是取檔阻塞，不是 ZIP 損壞證據。八個分類目錄只是預留位置，沒有已核實成員歸檔。
- **封包 B：結構與限定範圍差異驗收通過。** 四個外層成員大小／CRC 通過；兩份 DOCX 各 17/17 個 OOXML 部件通過；28 個內部 relationship targets 缺失 0；Content Types 缺失宣告 0、孤立 Override 0；標題 75/75 與 72/72；13 張表、137 列、379 格正規化文字差異 0。正文有序字元差異已分類，未發現未解釋的實質內容缺失，但不宣稱原始字元逐字相同。

## 2. 可融合的共同核心

以下項目在封包 B 討論／企劃與封包 A 的交接規程中有交集，可整理成共同原則。共同原則不代表它們已在 P2 程式中實作。

### 2.1 最高目標：解決問題

最高層目標是把使用者目標轉成符合範圍、限制與接受條件的可檢查結果。架構簡化的重點不是刪掉功能、角色或保障，而是減少同一概念被多套文件、圖表和狀態機重複描述，再要求 AI 自己記住它們的對應。

### 2.2 一條簡單的因果流程

討論稿已將 H0–H2 的簡單骨架視為方向正確；企劃書將它明確寫成五個基本環節：

**理解問題 → 決定做法 → 執行做法 → 檢查結果 → 修正與結案**

- **H0：** 唯一最高目標——解決問題。
- **H1：** 五個穩定環節。
- **H2：** 各環節的基本功能與步驟。
- **H3+：** 只有遇到真實方法選擇、能力選擇、條件判斷、依賴排序或回退決策時才展開分支。

前兩層保持愚蠢、穩定、容易判斷；分歧放在需要選擇的更深層，不把每種角色、工具或環境都先製作成新的頂層流程。

**接受狀態：** 這是討論中獲得認同的概念基線；仍屬設計參考，正式成為 P2 權威架構前，須與 P2 唯一施工藍圖及 Current 對帳。

### 2.3 一份權威底圖，多種派生視圖

不同圖表回答不同問題，但不能各自成為一套內容重複、獨立維護的真相：

| 視圖 | 主要回答 | 權威來源要求 |
|---|---|---|
| 功能／能力歸位樹 | 此功能的唯一主要歸屬在哪裡？ | 每項功能只有一個正式定義；跨環節引用 ID |
| 因果／流程圖 | 哪些條件導致下一步，失敗回到哪裡？ | 使用節點、封包與條件 ID 引用 |
| 角色／責任視圖 | 誰有權負責、執行或驗收？ | 維持職權與資料所有權邊界 |
| 狀態／進度視圖 | 目前在哪一步、是否能推進？ | 由唯一權威狀態與事件證據派生 |
| 施工／驗收視圖 | 哪些變更已做、哪些證據成立？ | 引用實際差異、測試輸出與驗收結果 |

樹狀位置表達「歸屬」；前置條件、因果引用與封包連結表達「流程」；角色視圖表達「責任」；Current 與證據表達「現在確實發生了什麼」。不可把這些混成同一欄位，也不可為每種視圖再建一份自己的關係真相。

### 2.4 功能是可條件啟用的能力，不是另一條流程

一個功能只建立一份正式定義，可被多個環節引用；主歸屬不等於只能在一處被使用。功能啟用必須同時考慮：

1. **位置：** 流程確實到達該功能的適用節點。
2. **觸發：** 可觀察的觸發條件成立。
3. **輸入：** 必要資料、來源、版本與依賴齊備。
4. **權限：** 當前角色／工作單元有權執行。
5. **資源與安全：** 成本、時間、上下文、外部工具額度及安全限制允許。
6. **衝突：** 目標、來源、範圍及依賴不存在未解衝突。

必要硬性條件不成立就不調用；資料可補則先補資料；無法合法或可靠地繼續就 BLOCKED。AI 覺得功能「可能有幫助」不能取代這些 Gate。

### 2.5 狀態與證據分開

狀態回答封包走到哪裡；證據回答為什麼可以相信結果。以下層級不可互相冒充：

- 文件／設計已寫入。
- 靜態閱讀與契約檢查。
- 局部案例推演或模擬。
- 實際程式測試。
- 整批整合驗收。
- 真實 Runtime 觀測。

單一封包 PASS 不等於整體任務已結案；模擬、靜態檢查、程式檔存在或摘要內容均不能升格成真實執行證據。

### 2.6 封包傳遞必要上下文與因果

每次推進只須保存可追溯的最小因果鏈：由哪個封包／條件觸發、前置條件如何核對、選了哪個分支及其理由／證據、產生什麼結果、下一步被允許或為何停止。下一個封包引用上游 ID、位置、版本或指紋，只載入本步驟所需的內容，不反覆複製完整歷史。

### 2.7 結案時管理結果、證據、交接與暫存

封包閉環時分成四類處理：

1. 留存最終產出、已確認決策、必要限制與下一步所需事實。
2. 保留關鍵判定、執行狀態、驗收及復現失敗所需的證據。
3. 以引用交接下一步必需的輸出、來源和 Current 狀態。
4. 清除不再被引用、不再支撐驗收或診斷的暫存；必要歷史改封存而非直接刪除。

仍被開啟封包引用、仍用於復現失敗、仍支撐未完成驗收或有保留規則的資料，不得提早退場。

### 2.8 先比對既有，再決定重用或新增

新增能力／系統前先確認既有流程並寫明 REUSE / MODIFY / MERGE / NEW。NEW 必須列出已查的候選與它們為何不能修改或合併；不可因入口、名稱或視圖不同就重造一份功能。對 P2 Schema 與 Current 的變更須先做相容性核對，避免第二份權威資料。
