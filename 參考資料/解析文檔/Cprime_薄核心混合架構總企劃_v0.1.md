## 0. 閱讀入口與重要結論

### 0.1 給第一次接手的人：先讀這一節

這是一份從零描述 C′ 系統的總企劃。目標不是製作一個「流程越多越好」的 AI，而是設計一套能為不同任務選擇合適求解方法、在高風險行動前實際執行權限控制、保留足夠證據與狀態，並能在錯誤時停止、修復或回退的通用問題解決架構。

本案以使用者已選定的 C′ 為規劃基線。C′ 的原則是：

1. 以薄核心作共同控制面，不把所有領域知識或完整工作程序塞進核心。
2. 先辨識問題屬性與真正的知識缺口，再選擇一個或多個合適方法模組。
3. 依風險與未知程度決定驗收、權限、紀錄、持久化和恢復強度。
4. 在需要跨輪記憶、施工、交接或稽核時使用工作封包；不是每個簡單任務都建立完整封包。
5. 重要主張、寫入行動與結案狀態必須有相應證據；自我聲稱、漂亮文檔與流程完整度均不能單獨作為完成證明。
6. 以代表性任務比較基線、完整封包及 C′，再根據結果調整或否決模組；不得預先宣稱 C′ 已經最優。

### 0.2 為什麼不是單純採用一條固定流程？

本案的共同骨架為：

**理解問題 → 決定做法 → 執行做法 → 檢查結果 → 修正與結案。**

這五個部分是完整問題解決的責任地圖，不是要求每個任務逐步填滿五份文件。低風險、定義清楚的問題可以直接採用專門方法；未知多、影響大或需要外部操作的任務，才逐步啟用更完整的框架、封包、反證、獨立驗收及恢復控制。

### 0.3 本企劃的成熟度邊界

本文件已將候選架構展開到可供工程設計、功能拆分、施工排程、交接與驗收的程度，但下列事項仍不可宣稱完成：

- 風險路由器已能正確分類真實任務。
- 權限 Gate 已在執行層阻擋未授權操作。
- 啟動載入、跨會話狀態恢復、封包生命週期或能力登錄已經實作。
- 有獨立驗收者或測試套件可證明所有重要結論。
- C′ 比簡單基線或完整封包在真實任務上更有效率。
- 文件已經形成真正的部署、監控及恢復能力。

以上項目要經由分階段施工、可重複測試與實際讀回後，才能逐項提升成熟度。

## 1. 專案目的、問題定義與成功條件

### 1.1 核心問題

通用 AI 系統面對的任務，在認知目的、可用證據、未知來源、風險、需要保留的狀態及外部副作用上差異極大。若所有任務一律走完整流程，容易產生過度治理；若完全交由模型自由決定，則容易發生目標漂移、幻覺、循環驗證、越權及狀態丟失。

因此，本專案要解決的不是「怎樣為所有任務設計一張最大化的流程圖」，而是：

> 如何建立一個最小但足夠的共通核心，讓系統依問題屬性選擇專門方法，依風險啟用必要控制，以證據判斷是否完成，並在條件改變時有界地重框、修復、停止或回退？

### 1.2 預期成果

企劃與後續實作應最終形成以下可交付成果：

- 明確的核心原則、責任邊界及名詞定義。
- 問題屬性描述、方法選擇規則及可以解釋的路由理由。
- 可組合的專門方法與能力契約，不依賴某個工具名稱推定功能存在。
- 工作流編排、執行狀態、證據紀錄及封包生命週期。
- 可實際執行的權限限制、寫入 Gate、副作用管理及恢復路徑。
- 重要主張、決策、模型／工具變更及結案結果可追溯。
- 代表性任務、對抗案例、回歸案例與可重複驗收方法。
- 新功能由需求到驗收的固定程序、交接規範及文件權威治理。
- 分階段建置路線、各階段交付物、進入條件、退出條件與責任角色。
- 一套能證明「哪些已設計、哪些已實作、哪些已測試、哪些仍未知」的現況紀錄。

### 1.3 成功條件

成功不是取決於節點數、文件長度或使用多少代理，而是下列條件同時成立：

1. **目標正確性：** 能清楚表達使用者真正要完成的目標、限制、非目標與接受條件。
2. **方法適配性：** 能按問題屬性選擇合適方法；不把量測、因果診斷、形式證明、最佳化及開放探索混成同一種方法。
3. **證據可靠性：** 重要主張可追溯，來源支持關係可檢查；未知與衝突不被語言流暢度掩蓋。
4. **權限有效性：** 未授權或超出範圍的外部操作能在執行層被阻擋，而非僅靠提示提醒。
5. **可恢復性：** 失敗有停止、有限重試、替代路線、阻塞、回退或補償方案。
6. **交接連續性：** 新會話可從權威狀態、未決問題、證據、版本及下一步恢復，而不是依賴口頭重新解釋。
7. **成本合理性：** 額外流程帶來的品質或風險改善足以抵銷時間、工具、人工介入和維護成本。
8. **演化可控：** 能力、提示、模型、工具、規則和測試變更有版本、回歸與退場程序。
9. **實證採納：** 只有測試支持的控制才能升格為已驗收能力；沒有證據時明確保持待驗證。

### 1.4 不納入本階段的目標

- 不預先建造所有想像得到的功能或領域能力。
- 不為了模組化而把每個微小操作拆成獨立插件、服務或代理。
- 不要求所有任務都使用完整封包、外部研究、多代理或多輪反證。
- 不把 C′ 直接聲稱為已證明的最優架構。
- 不把 P1／P2 中的任何能力描述或架構提案直接視為 forAVAr 已實作功能。
- 不因為某套技術框架當前熱門，就在未核對需求與現行版本前指定為唯一技術選型。
- 不在本企劃中直接更改既有方法規格與歷史研究正文；這些文件維持各自唯一責任。

## 2. 設計原則與不可違反的不變量

### CORE-01｜先定問題，再選方法

必須先理解任務的目的、對象、邊界、輸出、成功條件、限制與未知，才選擇專門方法。問題類別標籤只能作為線索，不能代替實際問題描述。

### CORE-02｜通用性來自方法選擇能力，不是固定程序

共同核心只管理必要判斷、路由與控制。測量、資料查證、診斷、因果推理、預測、數學證明、最佳化、設計、施工與探索，保留各自的正確方法與驗收方式。

### CORE-03｜事實、來源主張、推論、假說、未知與衝突分離

任何重要結論不得只依語氣或信心表示正確。系統應記錄主張、支持它的證據、證據限制與狀態；沒有足夠依據時可回報 UNKNOWN、CONFLICT 或 BLOCKED。

### CORE-04｜一個概念一個權威定義

能力、工作流、封包模板、權限規則、評測案例與權威現況各自指定唯一權威來源。README、圖表、摘要和查詢結果原則上是派生視圖，不得成為競爭的真相來源。

### CORE-05｜角色分工不等於權限隔離

「研究者」「施工者」「驗收者」等角色先定義責任，再由實際授權機制限制可讀資料、可呼叫工具、可寫入範圍、可批准事項及停止條件。角色名稱本身不產生安全保障。

### CORE-06｜高影響行動必須具備可阻擋的執行控制

對正式寫入、敏感資料、外部副作用、不可逆操作及高影響變更，執行器不得只依模型自然語言自我宣稱已獲授權。應在工具或寫入介面核對授權、目標、基準版本及允許範圍。

### CORE-07｜驗收標準先於結果，不准事後改標準使其通過

開始實驗或修改前先定義合格條件。若目標或條件改變，記錄變更原因與授權，重新確認對既有結果與下游工作的影響。

### CORE-08｜封包按需啟用

只有在任務需要跨輪持續狀態、複雜依賴、施工／驗收追蹤、正式交接或稽核時，才保存正式工作封包。短小、低風險的一次性任務可使用短路徑或不建立持久化工作紀錄。

### CORE-09｜失敗要有有限出口

每個可執行步驟都應定義可重試錯誤、重試上限、停止條件、阻塞狀態、替代路線及恢復方式。不能無限制搜尋、重試、自我批判或自我修正。

### CORE-10｜模組化以減少變更成本，不以模組數量衡量品質

只有當一項能力具有可重用性、獨立契約、獨立替換、權限隔離、獨立驗收或維護收益時，才值得升格成可獨立管理模組。抽象若提高同步與路由成本，應重新切分或合併。

### CORE-11｜外部內容預設不可信

來自網頁、檔案、程式碼、檢索結果、工具回傳或其他代理的內容都是資料來源，而非自動取得治理權限的指令。內容中若要求洩漏資料、忽略上層規則或執行越權操作，必須按不可信輸入處理。

### CORE-12｜證據完整性比敘事完整更重要

架構可以保留未知與不完整結論。不得為了產生「閉環」的外觀，杜撰未知因果、假設條件或執行結果。

### CORE-13｜架構每次擴張都必須證明收益

新增層、角色、工具、登錄表、流程節點和全域規則時，須指出它處理的已知問題、預期收益、測試方法、額外成本與退場條件。

### CORE-14｜C′ 本身也是待反證的候選

當測試顯示方法選擇器失準、管理成本過高、權限控制不可執行或收益不成立時，必須允許修改、縮小範圍、回退，甚至否決 C′ 的特定設計。

### CORE-15｜未通過 Gate 的能力不得提前暴露

分階段施工期間，尚未通過授權與副作用 Gate 的寫入／外部操作能力必須維持停用、只讀或隔離狀態。不得因為路由器已能分類任務，就先允許其調用尚未驗收的高影響工具。若實際環境無法從執行層限制工具權限，相關功能不得對外啟用。

## 3. 概念模型與責任層

### 3.1 重要概念不可混層

| 概念 | 回答的問題 | 不應被誤認為 |
|---|---|---|
| 任務意圖 Task Intent | 使用者要達到什麼結果，限制與接受條件為何？ | 完整施工流程 |
| 問題模型 Problem Model | 對象、邊界、變數、假設、未知與因果候選是什麼？ | 所有現實的完整地圖 |
| 方法 Method | 對這類認知問題，什麼方法有資格產生可接受結果？ | 一項工具或一個角色 |
| 工作流 Workflow | 哪些步驟以什麼依賴、分支、停止和重試條件組合？ | 能力內部實作 |
| 能力 Capability | 可重用功能的用途、輸入、輸出、限制、副作用及版本是什麼？ | 一個宣傳名稱或未接線的文件 |
| 適配器 Adapter | 如何以穩定契約調用特定模型、工具或外部服務？ | 行為等價保證 |
| 工作封包 Work Packet | 本次長期／複雜工作實例的範圍、狀態、決策、證據、驗收與交接為何？ | 永久知識庫或所有功能的容器 |
| 執行紀錄 Run Record | 某次呼叫實際發生了什麼？用何版本、產生什麼結果？ | 成功證明本身 |
| 證據 Evidence | 哪些來源／觀測支持哪項主張，限制是什麼？ | 有引用就等於正確 |
| 權限 Policy / Authorization | 誰可做什麼、對哪個對象、在什麼範圍與期限內？ | 角色名稱或文字提醒 |
| 驗收 Evaluation | 依預先定義的條件，產物是否合格？ | 執行者的自我聲明 |
| 能力演化 Lifecycle | 能力如何審查、啟用、降級、棄用、替換及退場？ | 每次新版本都直接發布 |

### 3.2 邏輯架構

下列層級代表責任分區，不要求一開始拆成獨立微服務。最小可行實作可以是一個模組化單體，並透過清楚介面保持替換能力。

        │
        ▼
L0 治理與授權邊界 ────────────────┐
        │                         │
        ▼                         │
L1 意圖正規化                     │
        │                         │
        ▼                         │
L2 問題屬性與方法路由             │
        │                         │
        ▼                         │
L3 工作流編排器 ◄─────────────────┤
        │                         │
        ├── 能力目錄／契約         │
        │       │                 │
        │       ▼                 │
        │   L4 能力模組            │
        │       │                 │
        │       ▼                 │
        │   L5 模型／工具／資料適配器
        │       │                 │
        ◄───────┘                 │
        │                         │
        ▼                         │
L6 執行狀態、證據、產物與追蹤      │
        │                         │
        ▼                         │
L7 驗收、回歸、版本及能力演化 ─────┘
~~~

治理與授權是跨層控制面，不應只在工作流開頭檢查一次。涉及寫入或外部副作用的操作，在執行前仍要再核對授權與允許範圍。證據與執行紀錄是跨層資料，不要求所有內容存放在同一資料表；但同一項權威狀態必須能確認唯一來源。

### 3.3 各層唯一責任與邊界

| 層 | 唯一責任 | 不負責 | 最小交付 |
|---|---|---|---|
| L0 治理與授權 | 專案邊界、權限、風險 Gate、核准條件、資料政策 | 領域推理、能力內部演算法 | Policy ID、授權範圍、拒絕／批准結果 |
| L1 意圖正規化 | 產生可供路由的任務意圖 | 未經證據判定領域事實 | Task Intent、歧義、已確認限制 |
| L2 方法路由 | 辨識屬性、挑選方法／深度、解釋路由理由 | 直接執行所有工具或強迫使用固定流程 | Route Decision、待處理未知、資源預算 |
| L3 工作流編排 | 管理依賴、分支、重試、停止、狀態轉移 | 複製能力內部實作 | Workflow Run、步驟狀態 |
| L4 能力模組 | 執行已定義且通過適用性檢查的任務能力 | 自行授予權限或自行核准其高風險結果 | Capability Contract、結構化結果 |
| L5 適配器與執行控制 | 呼叫特定模型／工具／服務，檢查輸入輸出契約和授權 | 推定不同提供者行為等價 | Run Record、錯誤、實際回應 |
| L6 證據與狀態 | 保存來源、版本、假設、決策、產物、執行事實 | 把推論升格為已確認事實 | Evidence Record、State Snapshot |
| L7 驗收與演化 | 回歸、接受／拒絕、採用／停用、版本和影響檢查 | 只因文件存在就宣稱通過 | Evaluation Result、Change Decision、退場紀錄 |

## 4. 最重要的架構修正：處理深度、風險與持久化是三個不同維度

早期 C′ 的 T0–T3 描述了快線、證據線、持續工作線和保護線。它適合作為溝通模型，但在真正的路由契約中，不能將「任務持續時間」和「操作風險」混成單一互斥類別。一個長任務可能低風險；一個只有一步的刪除操作也可能高風險。

因此，本企劃將路由正式拆成三個正交維度：

1. **方法深度 M：** 決定需要何種認知方法、證據和分析深度。
2. **控制等級 G：** 決定權限、驗收、審批、副作用防護與恢復要求。
3. **持久化等級 P：** 決定是否需要工作封包、交接、長期狀態和歷史追蹤。

三個維度互相作用，但不能互相替代；不得以「任務短」推斷「風險低」，也不得以「風險低」推斷「不需要保存狀態」。

### 4.1 方法深度 M0–M3

| 等級 | 適用條件 | 必要操作 | 禁止誤用 |
|---|---|---|---|
| M0 直接方法 | 問題明確、穩定、低未知，已有成熟方法可可靠回答 | 直接執行專門方法，必要時短述假設與限制 | 不為形式完整而製造全套框架 |
| M1 針對性證據 | 答案依賴現況資料、來源、計算或局部未知 | 查找足以回答關鍵問題的證據，核對來源／時間／單位／支持關係 | 不把單一摘要或模型記憶當作現況驗證 |
| M2 系統性分析 | 多因素、競爭假說、相互依賴、架構決策或重大歧義 | 建立最小問題模型／候選，對重要假設進行反證與敏感度分析 | 不預設清單已涵蓋所有候選 |
| M3 開放探索／高不確定 | 問題尚未界定、陌生領域、初始框架可能根本錯誤 | 保留多個框架、UNKNOWN／UNCLASSIFIED、框架外訊號；設定探索預算與重框條件 | 不過早鎖定唯一模型，也不無限發散 |

M0–M3 是方法深度的操作定義，而不是任務品質排名。實際方法應依問題屬性組合；任務中發現新證據時，可以回到更適當的深度。

### 4.2 控制等級 G0–G3

| 等級 | 初步定義 | 典型控制 |
|---|---|---|
| G0 只讀／無外部副作用 | 僅回答、讀取或分析；不寫入外部狀態，不觸及敏感資料 | 基本指令優先、來源與不確定性處理、資源上限 |
| G1 低影響且可逆 | 局部、明確授權、可回復的內部變更 | 核對寫入範圍、保存差異、基本測試、寫後讀回 |
| G2 高影響／跨邊界 | 多模組、廣泛使用者影響、重要決策、敏感資料或較高成本的操作 | 事前方案與差異審查、依賴影響分析、獨立驗收、回歸及明確批准 |
| G3 不可逆／安全關鍵／授權不明 | 不可逆或難回復的外部副作用、明顯安全／隱私風險、缺少必要授權或無法確認範圍 | 預設阻擋未授權動作；先補足授權、備份／補償及驗收方案；依政策要求人工批准，否則 BLOCKED |

G3 既是高強度控制路徑，也包含「必須阻擋」的情況；它不表示任務只要標成 G3 就可執行。缺少明確授權時，不得透過降低分類或更多文字理由繞過 Gate。

第一版風險量表先用可解釋的等級與觸發規則，不捏造精確風險分數。待取得基線資料後，才評估是否需要數值化模型；無論採何種量表，明確的安全與授權硬限制均不可被加權平均抵銷。

### 4.3 持久化等級 P0–P2

| 等級 | 使用條件 | 記錄 |
|---|---|---|
| P0 不持久化 | 一次性短問答，不需跨輪恢復，沒有施工或稽核需求 | 只保留本次回覆需要的上下文 |
| P1 精簡任務紀錄 | 多步但範圍有限，稍後可能需要回查或延續 | 目標、路線、關鍵證據／未知、結果、下一步 |
| P2 正式工作封包 | 跨會話、跨模組／多檔修改、高影響施工、需要交接／批准／回歸／恢復 | 完整工作範圍、授權、版本、依賴、執行、證據、驗收、退出與交接 |

持久化本身也涉及資料最小化與保留期限。不得因為系統需要追蹤，就將所有私人內容或原始資料無限制保存；應依目的限制必要紀錄並設定存取、保留和刪除規則。

### 4.4 路由組合與預設規則

一個任務的最小路由結果應同時包含：

- method_depth：M0–M3；
- guard_level：G0–G3；
- persistence_level：P0–P2；
- selected_method_ids：選用的方法模組；
- route_rationale：分類依據與替代候選；
- unresolved_unknowns：仍可能改變決策的未知；
- required_evidence：完成所需證據；
- stop_conditions、retry_budget、resource_budget；
- authorization_scope：允許操作與禁止操作。

若路由需要依賴未確認的風險、授權、資料或操作語意，應保守升級或阻塞。不能僅根據任務用語短、使用者語氣肯定或模型信心高就分流到低控制等級。

### 4.5 路由選擇器的自身驗收

方法選擇器本身是高影響架構元件，需要單獨測試：

- 高風險工作被錯分為 G0／G1 的比例。
- 原本可短路的低風險工作被錯分為高成本流程的比例。
- 重大未知與授權歧義的漏判率。
- 任務中條件改變後，是否會提升深度／控制等級。
- 路由器是否能解釋選擇理由，以及在證據不足時能否拒絕確定分類。
- 同類任務在不同模型／提示／工具版本下路由結果是否穩定。

任何高風險漏判都必須視為優先失敗案例，不能只由平均準確率掩蓋。

## 5. 問題正規化與方法選擇流程

### 5.1 Task Intent 最小任務契約

每項任務至少要識別以下欄位；低風險短任務可以只在記憶體內以簡單物件表示，不必建立正式文件。

| 欄位 | 含義 | 缺漏處理 |
|---|---|---|
| task_id | 本次任務的穩定識別碼 | 建立時產生，不以嚴重度編碼 |
| goal | 最終要達到的結果 | 若多種解讀會改變結果，需澄清或明確採假設 |
| target | 作用對象／問題範圍 | 不可將推測範圍當成已確認 |
| deliverables | 預期產物或回答 | 確認交付格式與邊界 |
| acceptance_criteria | 怎樣算完成 | 無法量化時至少列出可觀測的質性判準 |
| constraints | 必須遵守的限制 | 上層安全、授權和專案範圍不可被一般偏好覆蓋 |
| non_goals | 明確不做的事 | 防止功能或研究範圍悄悄擴張 |
| context_refs | 權威文件、來源、現況基準 | 無法確認來源時標記未知，不捏造檔案存在 |
| assumptions | 暫時採用的假設 | 指出可能影響結果的假設與驗證方式 |
| unknowns_conflicts | 目前未知、證據衝突和阻塞 | 不能以自然語言硬合併 |
| method_depth | M0–M3 | 可隨新資訊重新評估 |
| guard_level | G0–G3 | 依副作用、敏感度、權限與後果判定 |
| persistence_level | P0–P2 | 依持續狀態、交接與稽核需要決定 |
| authorization_scope | 可執行的操作、目標與期限 | 高影響操作缺少有效授權就阻擋 |
| resource_budget | 時間／工具／重試／成本界線 | 不能無限搜尋或重試 |
| current_state | 工作階段狀態 | 只能由合法狀態轉移更新 |

### 5.2 方法選擇依據

延續方法規格 v0.2 的八個問題屬性：

- P1 認知目的：描述／分類、測量／估計、解釋／診斷、預測、決策／最佳化、設計／干預、形式化／證明、探索／問題界定。
- P2 問題結構成熟度：結構成熟、部分結構化、未充分結構化。
- P3 未知來源：語義、資訊、測量、隨機、模型／因果、價值、環境／未來、執行。
- P4 可觀測性／可檢驗性：權威來源、直接觀察、實驗、計算、模擬、測試、形式證明或目前無法直接驗證。
- P5 目標與價值：硬限制、可權衡目標、不同利害關係人偏好。
- P6 候選解結構：唯一成熟路線、離散候選、多維搜尋、競爭假說、未知候選空間。
- P7 系統互動與時間：靜態／動態、因果回饋、單方／多方策略互動、環境條件是否變動。
- P8 失敗代價與資源：可逆性、時限、預算、外部副作用和錯誤代價。

這些屬性是方法選擇的素材，不是一張每次都要填寫完整的表單。路由器只需展開與本次選擇有關的維度，並保留必要理由。

### 5.3 方法選擇步驟

1. 建立最小任務意圖。
2. 套用不能被覆蓋的治理與授權限制。
3. 分別評估方法深度 M、控制等級 G 與持久化等級 P。
4. 找出最可能改變結論、路線或風險的關鍵缺口。
5. 選擇能直接處理該缺口的專門方法或最小方法組合。
6. 列出其必要輸入、輸出契約、假設及失敗出口。
7. 若多個方法同樣合理，優先選擇能滿足接受條件的最小組合；若差異會影響高價值決策，安排可比較的試驗或保留分支。
8. 依方法執行、檢查可觀測結果。
9. 根據證據更新結論、風險、方法與下一步。
10. 條件未滿足時，允許重框、轉路線、阻塞、維持未決或停止，不強迫產生單一答案。

### 5.4 選擇下一步的原理

每次行動前需問：

- 此行動想消除哪個未知或風險？
- 若結果為 A／B／無結果，會改變什麼決策？
- 現在有沒有成本更低且區辨力相同的檢查？
- 是否已有足夠證據，可停止再查？
- 執行是否超出授權、預算或風險界線？

優先採取預期能改變決策、阻止重大錯誤或取得必要證據的行動。若更多搜尋、代理或反思不會改變選擇，且沒有其他明確價值，應停止擴張。

### 5.5 反向思考與框架重建

反證不是固定必經儀式，而是按錯誤代價及框架不確定性觸發。高影響架構決策、根因診斷、多方案比較、陌生領域及初始假設可能導致重大方向錯誤時，必須提高反證強度。

最低反證輸出包括：

- 最可能使目前方案失效的三至五個關鍵假設。
- 能推翻假設的反例或觀測條件。
- 最有可能被初始框架排除的替代解釋。
- 哪些框架外訊號會觸發重新界定問題。
- 若某項反證成立，哪些下游判斷必須重跑。
- 哪些內容尚無法驗證，應保持 UNKNOWN／BLOCKED。

當新證據推翻核心假設、使用者修改目標、接受條件不成立或重要測試失敗時，不能把訊號一律判為偏題；應針對受影響的節點與依賴重新分析。

## 6. 核心證據系統與知識狀態

### 6.1 主張和證據是分開的資料物件

每項影響決策的主張應能追溯到所依據的證據。證據物件至少保存：

- evidence_id、claim_id；
- 來源 URI／文件路徑、發行者／來源類型；
- 發布時間、觀察時間、擷取時間；
- 版本或內容指紋（可取得時）；
- 支持主張的具體片段／欄位；
- 支持類型：直接支持、部分支持、反駁、僅相關或無關；
- 適用範圍、限制及可能的來源偏差；
- 是否獨立於其他來源，是否可能為同一原始來源的轉載；
- 驗證者、驗證方式及驗證狀態。

內容雜湊只能幫助識別位元組版本，不能保證來源內容正確、仍然新鮮或在語意上未變。

### 6.2 主張狀態與證據來源類型要分開

建議將「主張的認知狀態」與「證據是什麼類型」分成兩個欄位，而非用一組標籤混合全部含義。

| 主張狀態 | 意義 | 允許的行動 |
|---|---|---|
| CONFIRMED_WITHIN_SCOPE | 在明確範圍和方法下已有足夠驗證 | 可按接受條件繼續，但不能泛化到未測範圍 |
| SOURCE_CLAIM | 來源如此主張，尚未獨立確認其真實性 | 只能敘述為來源主張 |
| INFERENCE | 依現有證據推導，仍需承認前提與限制 | 在適當範圍內作推論，不冒充直接觀察 |
| HYPOTHESIS | 候選解釋，尚待區分性證據 | 用來設計測試，不直接當結論 |
| UNKNOWN | 目前無法判定或證據不足 | 補證據、縮小結論、保留或停止 |
| CONFLICT | 可信來源／觀測互相矛盾 | 保留分歧並查明差異，不強制融合 |
| BLOCKED | 因授權、必要輸入、資源或安全條件不足無法繼續 | 記錄阻塞原因、解除條件與責任人 |

證據類型可以是原始觀測、權威原始來源、衍生資料、交叉佐證、執行收據、測試結果或模型推論。不能將「多個引用」自動等同獨立佐證，也不能因某主張被標成 CONFIRMED 就省略它適用的限制。

### 6.3 外部研究規則

需要外部研究時，至少做到：

1. 明確說明搜尋要解決的證據缺口，而非只因任務被稱作深度研究就擴大範圍。
2. 優先查找原始規格、官方文件、論文或可追溯的原始證據；必要時用不同來源交叉核對。
3. 分開出版日期、事件日期、擷取時間與現況檢查時間。
4. 對來源的結論做適用範圍限定；不能從一個特定基準或實驗直接泛化為普遍定律。
5. 保留未能查證的事項、相反證據及資料取得範圍。
6. 針對模型、工具、法律、API 和價格等易變事項設定重核條件。
7. 不把搜尋摘要的存在當成已完整閱讀或證據已足夠。
8. 若無可用外部證據，應明確表示限制，而不是合成一個看似可信的來源。

### 6.4 長上下文與交接摘要

持久工作不應只保存完整逐字對話。應維持「最小充分狀態」：

- 原始目標與當前已確認目標；
- 授權範圍及禁止事項；
- 當前基準文件／版本／修訂範圍；
- 已作出的決定與其理由；
- 重要來源／證據與未解矛盾；
- 執行狀態、完成產物及未完成步驟；
- 已測項目、未測項目及失敗紀錄；
- 阻塞條件、預算／停止界線；
- 下一個最有價值的具體行動。

摘要應引用權威來源，不複製多份大段正文；新會話啟動時需核對摘要版本及實際來源。若關鍵權威來源無法取得，必須標示阻塞或降低信心。

## 7. 工作流編排與通用執行契約

### 7.1 工作流是一張依賴圖，不必是一條固定直線

工作流由步驟、輸入／輸出契約、前置條件、依賴、分支、停止和錯誤處理組成。只有當依賴確實存在時才建立順序。互相獨立的只讀分析可以平行；共享同一個寫入基準或可能產生互相衝突副作用的步驟，除非有明確協調與鎖定機制，否則不可任意平行。

最小工作流步驟包含：

- step_id、capability_id、capability_version；
- required_inputs、expected_outputs；
- preconditions、required_authorization；
- dependency_step_ids；
- side_effects、idempotency_policy；
- retryable_errors、retry_limit；
- timeout／resource_budget；
- success_criteria、failure_policy；
- verification_requirements；
- on_success、on_failure、on_blocked 的下一個合法轉移。

### 7.2 工作流執行規則

- 路由器不能選擇不符合輸入／輸出契約、未啟用、已棄用或缺少依賴的能力。
- 已有能力的名稱和說明並不代表功能已實作、已接線或最近通過適用測試。
- 每次執行必須記錄所用模型／工具／能力版本與輸入版本。
- 工作流只能根據明確定義的結果或狀態條件分支；不能把工具呼叫沒有報錯等同任務完成。
- 一項步驟的失敗應退回受影響節點或其前置條件，不必重跑全部工作。
- 工作流一旦超出授權、預算或預先定義的風險邊界，應停止並回報 BLOCKED。
- 只有所有必要接受條件達成且所需證據齊備，才進入 ACCEPTED／CLOSED。
- 接受條件不可由執行者在失敗後私自修改；如需改變，必須建立新的決策／授權紀錄。

### 7.3 停止、重試和資源預算

每個方法與可執行步驟要定義合理的停止條件。重試策略至少區分：

- **瞬時錯誤：** 網路超時、限流等可短暫等待後有限重試的問題。
- **輸入／契約錯誤：** 先修正輸入、Schema 或版本，不可盲目重試相同請求。
- **權限／政策錯誤：** 不得透過重試繞過，應阻塞並要求合法授權。
- **結果未知：** 外部操作可能已執行但回應遺失；先查詢真實狀態，不能直接重複執行非冪等操作。
- **邏輯失敗：** 修改方法／假說／路線後才可再試，不可無限重述同一方案。
- **資源耗盡：** 到達預算或期限後停止、縮小範圍或交接，不得繼續無界研究。

停止規則需同時考慮：成功條件已達成、資訊增益不足、預算耗盡、硬性期限、必要輸入缺失、無法解除的矛盾、授權不足、風險超標及已達最大合理重試數。

## 8. 工作封包與生命週期

### 8.1 封包啟用條件

當以下任一條件成立時，應考慮 P2 正式工作封包：

- 工作跨多輪或跨會話，單靠短期上下文難以恢復。
- 工作有多個依賴、分支、子任務或責任人。
- 工作涉及多檔案／多模組修改、外部寫入或高影響變更。
- 工作要求正式批准、獨立驗收、回歸、退場或交接。
- 工作需要稽核、重建執行歷程、追蹤資源預算與停止原因。

其他工作可以使用 P0 或 P1。不可因「能建封包」就替每個小操作建一份完整封包。

### 8.2 封包三種物件

- **封包模板：** 某類任務共用的必填欄位、預設流程、Gate 和驗收方法。
- **工作封包實例：** 本次任務的目標、輸入、授權、狀態、決策、輸出與驗收。
- **執行紀錄：** 每次工具／能力呼叫實際發生的版本、輸入摘要、結果、錯誤、重試與時間資訊。

模板更新不能暗中改寫已結案實例的歷史；每個實例應固定記錄採用的模板與能力版本。

### 8.3 封包最小欄位

~~~yaml
packet_id: stable-id
packet_type: task-kind
template_ref: template-id-and-version
created_at: timestamp
goal: explicit-goal
deliverables: []
acceptance_criteria: []
constraints: []
non_goals: []
authorization_scope: []
baseline_refs: []
assumptions: []
unknowns: []
conflicts: []
method_depth: M0 | M1 | M2 | M3
guard_level: G0 | G1 | G2 | G3
persistence_level: P0 | P1 | P2
workflow_ref: workflow-id-and-version
capability_refs: []
resource_budget: {}
retry_budget: {}
status: DRAFT
run_record_refs: []
evidence_refs: []
artifact_refs: []
exit_conditions: []
recovery_plan: {}
handoff_summary: {}

closure_reason: null
~~~

以上是語意上的資料契約範例，不代表已選定 YAML 作為 Runtime 儲存格式。正式 Schema 必須根據未來實作技術定義型別、必填／選填欄位、驗證器與向前／向後相容政策。

### 8.4 封包狀態

~~~text
DRAFT → NORMALIZED → ROUTED → READY → RUNNING → VERIFYING
  │          │          │        │         │           │
  ├─CANCELLED├─BLOCKED  ├─BLOCKED├─BLOCKED ├─FAILED    ├─REJECTED
  │          │          │        │         │           │
  └──────────┴──────────┴────────┴─────────┴───────────┘
                         |
          VERIFYING → ACCEPTED → CLOSED
          VERIFYING → REJECTED → 有界修復／重新驗收
          RUNNING → PARTIAL／UNKNOWN／BLOCKED
~~~

所有狀態轉移要由實際狀態機規則限制，不能僅靠手動改一個字串代表完成。狀態名與轉移表在進入實作前需形成獨立契約測試。CLOSED 表示本次工作已依結案規則保存結果、證據、限制與交接；不代表相關能力已經通過所有長期測試。

## 9. 能力目錄、能力契約與模組演化

### 9.1 能力採用門檻

能力候選在成為可路由項目前，必須通過：

1. 用途與非用途清楚。
2. 有穩定 ID、正式責任與版本。
3. 輸入／輸出契約可檢查。
4. 前置條件、權限、資料敏感度與副作用可識別。
5. 有可辨認的實作與呼叫路徑；若僅有規格文字，狀態必須標記為未實作。
6. 有代表性成功、失敗及邊界案例。
7. 有依賴、替換關係與相容性說明。
8. 對其被指派的任務，能證明品質或維護收益足以抵銷使用成本。
9. 有停止、失敗回報、退場與必要的回退方式。

### 9.2 Capability Manifest 範例

~~~yaml
capability_id: capability-stable-id
name: human-readable-name
version: 0.1.0
lifecycle_state: DRAFT
purpose: ""
not_for: []
input_contract_ref: schema-id-version
output_contract_ref: schema-id-version
preconditions: []
permissions: []
sensitivity_level: unknown
side_effects: []
idempotency: unknown
dependencies: []
adapter_ref: null
error_taxonomy: []
retry_policy_ref: null
resource_profile: {}
acceptance_suite_ref: null
last_verified_revision: null
deprecation_policy: {}
replacement_capability_id: null
owner_role: capability-maintainer
~~~

### 9.3 能力生命週期

建議的邏輯生命週期：

- DRAFT：候選定義，不能被正常路由。
- UNDER_REVIEW：契約與證據待審。
- ENABLED：符合啟用條件，可在合格範圍被路由。
- DEGRADED：能力仍存在，但已知品質、依賴或外部服務有風險；按政策縮小適用範圍。
- QUARANTINED：出現安全、資料完整性或重大回歸疑慮，不接收新工作。
- DEPRECATED：已有替代方向，不再新增依賴，等待遷移。
- RETIRED：已不再使用；保留必要歷史與替代映射。
- REJECTED：候選不符合採用門檻，記錄拒絕原因避免重複錯誤。

不能因為新能力存在便直接刪除舊能力；先驗證替代、引用者遷移、回歸和恢復方案。

### 9.4 能力關係

只保留有用途的關係類型，例如：

- REQUIRES：存在明確前置依賴。
- USES：某工作流或能力會呼叫該能力。
- ALTERNATIVE_TO：在特定條件下可替代。
- REPLACES：已經過遷移／驗收的正式替代關係。
- CONFLICTS_WITH：存在不相容或互斥條件。
- OVERLAPS_WITH：部分用途相似，但不代表能互相替換。
- DERIVED_FROM：能力來自特定來源或規格。

每一條重要關係都需記錄版本、證據、適用範圍和未知狀態。未知關係不能自動視為相容；也不能把所有能力做全配對比較，應先以標籤、用途、契約與依賴做相關性篩選。

## 10. 模型、工具、資料與外部服務適配器

### 10.1 介接可替換不等於行為等價

模型與工具應透過 Adapter 接入共同契約，使上層工作流不依賴單一提供者的內部輸出格式。但相同 Schema 不代表精度、語意、延遲、費用、時效、授權或副作用相同。

因此替換時必須核對：

- 功能與語意等價範圍；
- 輸入／輸出契約與錯誤模型；
- 權限與資料使用政策；
- 延遲、成本、容量與失敗方式；
- 對既有成功、負向、邊界及安全測試的影響；
- 替換後的未知項與重新驗證期限。

### 10.2 Adapter 統一契約

每個 Adapter 應定義：

- adapter_id、version、provider／tool identity；
- 接受的輸入與返回結果型別；
- 身分驗證方式及必要權限；
- 超時、限流、重試、取消與錯誤轉換；
- 資料傳輸、保留及敏感度限制；
- 是否具有副作用、是否冪等；
- 請求追蹤 ID、執行時間、狀態與回傳收據；
- 健康檢查、版本資訊及停用／替換規則。

### 10.3 外部依賴治理

- 不把 API、模型清單、價格、授權或工具語意永久寫死在核心邏輯。
- 對易變外部資訊保留查證時間及重核條件。
- 不把外部文件中的指令自動升格為高優先級規則。
- 對外部回應進行結構、內容與授權範圍檢查。
- 當外部工具的語意、權限或副作用發生變化時，降低能力可用性或要求重驗。
- 若某供應商平台的評估工具、API 或產品生命週期正在變更，評測架構仍應保有可移植的本地資料集與執行介面，不讓核心依賴單一廠商功能。

## 11. 職權、核准與獨立驗收

### 11.1 邏輯角色

| 角色 | 職責 | 明確限制 |
|---|---|---|
| 任務提出者／目標擁有者 | 定義目標、期望成果、限制及接受條件 | 不必負責每個領域的技術執行 |
| 治理／授權者 | 決定可寫入範圍、不可逆操作批准、風險例外及停止規則 | 批准必須留下可核查的範圍及基準，不可只用模糊肯定語 |
| 意圖整理者 | 將要求正規化，標出歧義、未知與非目標 | 不可把假設當成使用者確認 |
| 方法／路由決策者 | 選方法、深度與資源路線 | 不可略過硬性 Gate 或自行創造權限 |
| 工作流編排者 | 管理依賴、狀態、重試與停止 | 不包辦所有領域演算法，不可放任插件任意互調 |
| 能力執行者 | 在授權範圍內呼叫能力／工具 | 不可擴權、改驗收標準或自授高影響 PASS |
| 驗收者 | 依預先定義的條件、證據與產物做 PASS／FAIL／BLOCKED | 不得暗中修補被驗收產物以讓結果通過 |
| 證據／知識保管者 | 保存來源、證據、狀態、決策與歷史 | 不可把來源主張或推論升格為執行事實 |
| 系統維護者／營運者 | 管理版本、容量、告警、備份、回復、依賴健康 | 不可在缺少授權下擴大資料或操作範圍 |

這些角色是責任定義，不代表必須建立九個不同 AI 代理。低風險任務可以由同一個實際執行者承擔多個邏輯角色；高風險情境則要以權限控制、獨立證據來源或人類批准建立真實分離。

### 11.2 最低職權矩陣

| 行為 | 提出者 | 路由／編排 | 執行者 | 驗收者 | 授權者 |
|---|---|---|---|---|---|
| 提出目標／方案 | 可 | 可分析 | 可回報建議 | 可提出問題 | 可裁定範圍 |
| 選方法 | 提供需求 | 可在授權內決定 | 可提出實作限制 | 可要求更有效驗證 | 可設定硬限制 |
| 讀取資料 | 依合法範圍 | 按政策路由 | 僅讀授權範圍 | 僅讀驗收必要資料 | 設定權限 |
| 執行內部可逆變更 | 授權範圍內 | 編排 | 可執行 | 不應自我核准 | 按風險批准 |
| 不可逆／外部高影響操作 | 明確提出目的 | 只能進入受控分支 | 不得自行擴權 | 依規則檢查結果 | 必須按政策批准 |
| 修改正式驗收條件 | 提出變更 | 不得自行修改 | 不得自行修改 | 可指出條件不可測 | 明確核准且留痕 |
| 宣告完成 | 提供需求確認 | 提供狀態 | 回報執行結果 | 依證據判定 | 高風險時核准結案 |
| 能力啟用／退場 | 可提議 | 檢查依賴 | 提供測試結果 | 檢查門檻 | 依變更級別裁定 |

### 11.3 高風險驗收如何形成真正獨立性

獨立性不能只看角色名稱或模型是否不同。要依任務選擇實際保障：

- 驗收者有獨立讀取產物／執行結果的路徑；
- 驗收規準在執行前固定；
- 儘量使用可執行測試、外部狀態讀回、不同證據來源或預先保留的反例；
- 驗收者不能修改接受標準以讓產物通過；
- 驗收失敗要留下可重現的失敗證據；
- 角色若共享同一模型與上下文，明確記錄此限制，不能宣稱完全獨立驗證。

## 12. 權限、安全、資料保護與不可信輸入

### 12.1 最小權限

每個工具或能力只取得當前任務所需的最小權限、最小資料與最小操作範圍。只讀工作不應因接入同一個插件而自動擁有寫入／刪除能力。能力若包含本次任務不需要的高危功能，應切分介面或在執行層禁用。

### 12.2 不可信內容與提示注入

網頁、檔案、程式註解、檢索內容、工具回應和其他代理的輸出都可能包含試圖改變模型行為的指令。系統必須在概念與執行上分離：

- 高優先級的治理規則及使用者核准；
- 外部資料所主張的內容；
- 模型根據資料作出的推論；
- 真正已被授權的操作請求。

外部資料不能自己修改角色權限、批准寫入或要求系統洩漏其他資料。工具呼叫時應再次核對操作目標、讀寫權、輸入來源與副作用。不能把「已經做過 RAG」或「加了提示詞」當成已消除注入風險。

### 12.3 資料最小化、保留與刪除

企劃實作前需定義：

- 資料分類：公開、內部、機密／敏感、個人資料或其他受限資料。
- 使用目的與最小必要欄位。
- 哪些資料可傳送至外部模型／工具。
- 哪些需要遮蔽、摘要、去識別或禁止外送。
- 日誌記錄哪些內容，哪些只記指紋／狀態，不儲存原文。
- 保存期限、刪除政策及依法／依約需要保留的例外。
- 誰可讀取、匯出、修正或刪除持久化資料。
- 當來源、權限或保留條件改變時如何重新評估。

不要因為「將來可能用到」就無限保存原始對話或敏感內容。

### 12.4 輸出驗證

模型生成的指令、程式碼、結構化資料、工具參數和檔案差異，都應依下游用途驗證。對結構化資料檢查 Schema，對程式執行使用隔離環境和測試，對寫入動作檢查目標與授權，對自然語言主張檢查證據支持關係。不能直接把自由文字當成可信命令。

### 12.5 安全失敗原則

遇到下列情況，預設不執行高影響動作：

- 授權來源或範圍不明；
- 目標、基準版本或預期副作用不明；
- 工具能力超出當前需要且無法限制；
- 外部輸入可能改變高優先級規則；
- 執行結果未知，重試可能造成重複副作用；
- 驗收條件缺失或不可能觀測；
- 發現資料外洩、越權、完整性破壞或重大回歸。

系統須記錄阻擋原因與解除條件，不可用「提高模型信心」取代必要授權。

## 13. 變更治理、版本與文件權威

### 13.1 三種工作模式

| 模式 | 允許內容 | 不自動授權的行為 |
|---|---|---|
| DISCUSS | 分析、推論、反駁、比較、提出候選 | 不代表可改權威企劃 |
| RECORD | 新增獨立研究／對談／驗收紀錄及必要導航 | 不代表可融合或覆寫其他主題文件 |
| PLAN_UPDATE | 在已確認範圍內修改指定企劃／權威規格 | 不代表可修改未列入範圍的其他專案或檔案 |

本次使用者已明確指示以 C′ 為架構開始撰寫企劃，故建立本總企劃和必要交接附件屬授權範圍。後續若需要把研究結論融合進其他權威規格，仍要辨認目標文件及差異範圍，不可把本次授權無限擴張成所有文件皆可修改。

### 13.2 企劃更動程序

1. 讀取權威文件及現行版本。
2. 明確列出提案目標、變更原因和受影響範圍。
3. 分類變更風險，識別下游引用、Schema、能力、流程與驗收受影響處。
4. 先在差異提案中呈現新增、修改、刪除、保留、延後與拒絕項。
5. 針對已授權的文件和範圍實際寫入；確認後若方案發生實質改變，需重新核對。
6. 讀回所有修改檔案，檢查內容、相對連結、索引與唯一責任。
7. 對受影響能力執行對應測試與回歸。
8. 保存提交、版本、測試證據與未解限制。
9. 沒有合格變更時允許維持現狀，不為「有工作成果」而強行更動。

### 13.3 變更風險判定

先用下列維度定性分級，未有基線前不宣稱精確數值：

- 影響的使用者／能力／文件範圍；
- 權限及資料敏感度；
- 可逆性與外部副作用；
- 是否改變核心契約／狀態／接受條件；
- 是否影響既有能力的輸入輸出與版本相容性；
- 是否能以測試覆蓋風險；
- 失敗是否可能造成不可恢復損害。

低風險文件拼字修正可走短路徑；改變核心路由、授權、資料模型、能力契約、狀態機或重要接受條件，須提高審查及回歸強度。對未知或不能確認的高影響因素採保守處理，而不是以平均分數稀釋。

### 13.4 版本策略

- 概念與能力以穩定 ID 識別；不要把嚴重度、分類名稱或展示文字編進永久 ID。
- 版本需能區分相容變更、行為變更及不相容變更。
- 對行為語意、權限、副作用或輸出契約變更，不因欄位名稱未變就視為相容。
- 每次執行保存確切採用的能力、模板、模型／工具與配置版本（可取得時）。
- 棄用前確認替代能力能處理所有必要案例，且引用者完成遷移。
- 回退要分清楚檔案版本還原、配置回復、資料庫回復、外部副作用補償與操作結果重建；Git 回退不代表外部世界已復原。

### 13.5 權威來源原則

目前在 forAVAr 中的相關權威責任：

- 問題及失效來源：參考資料／（S級）問題清單。
- 跨領域方法選擇：通用問題屬性導向方法選擇框架 v0.2。
- 本 C′ 主企劃的目標架構與施工意圖：本文件。
- 階段進度、測試案例、證據位置與待辦：Cprime 施工台帳與驗收矩陣。
- 文件導航：參考資料／README。
- 文件間唯一責任和引用方向：跨文件重疊與唯一職責矩陣。
- 原始來源、外部研究與具體反證：各自專屬的研究／稽核文件。

如文件互相矛盾，不能把所有內容混合成一個新版本；先辨認哪一份負責此概念，再根據批准範圍提出差異修正。

## 14. 執行狀態、並行、冪等與恢復

### 14.1 執行結果分類

每次工具／能力呼叫要將下列狀態分開：

- SUCCESS：工具呼叫與契約驗證成功。
- FAILED：已確認未達成。
- PARTIAL：只完成部分輸出／副作用。
- UNKNOWN_OUTCOME：無法確認外部操作究竟有沒有成功。
- BLOCKED：未達前置條件或授權／政策禁止。
- CANCELLED：在執行完成前取消。
- TIMED_OUT：超過期限；若有副作用，還需要確認實際狀態。

成功回傳不代表最終目標達成；最終接受條件必須由工作流根據產物、外部狀態和證據另行判定。

### 14.2 冪等性與重複操作

對可造成外部副作用的動作，需標明其冪等性。可以使用冪等鍵、請求 ID、操作紀錄或前後狀態比對，以辨認是否已執行。回應遺失或超時時，先查真實狀態；沒有足夠證據前不重複發送非冪等操作。

### 14.3 並行更新與版本競態

對同一權威文件、工作封包或外部資料，若兩個流程可能同時修改，必須在寫入前比對基準版本。若基準已變，停止套用舊差異並重新分析，不得默默覆蓋較新狀態。

對多檔相依更新，預先列出整批修改清單；能原子更新就採原子更新。若無法原子化，必須提供進度紀錄、部分完成狀態、補償／恢復步驟及寫後逐檔讀回驗收。

### 14.4 部分失敗和恢復

恢復策略依外部可觀測狀態選擇：

1. 確認失敗且無副作用：有限重試或修正輸入。
2. 已部分完成：從最後可信狀態繼續，或執行明確補償。
3. 結果未知：先讀回外部狀態再決定，禁止盲目重做。
4. 版本衝突：保留新基準，重算差異並重新核准必要範圍。
5. 無法安全恢復：封鎖後續高影響步驟，保留證據，轉人工處理。
6. 修復後：重新執行受影響的接受條件與相關回歸；不得只驗證修補的單一行為。

## 15. 交接、知識持續性與新會話啟動

### 15.1 啟動／接手流程

每次接手持續中的 forAVAr 工作，依序核對：

1. 專案寫入邊界與本次授權模式。
2. 主企劃、問題清單、方法規格、施工台帳的目前版本。
3. 當前工作目標、接受條件、已完成範圍及未完成範圍。
4. 上一次可信執行結果與實際產物位置。
5. 已知問題、未知、矛盾、阻塞與風險。
6. 尚有效的核准、基準版本與禁止操作。
7. 下一個待辦是否仍符合當前目標和外部狀態。
8. 重新核對受影響文件與工具的實際現況，不直接信任舊摘要。

### 15.2 啟動載入失敗處理

如果必要治理文件無法取得、權威版本不明或互相矛盾：

- 允許進行無副作用的資訊查找或明確標記阻塞。
- 不允許高影響寫入、不可逆操作或正式企劃更新。
- 先恢復權威來源或由有權者釐清；不能透過模型記憶猜測缺失內容。
- 記錄載入失敗位置、版本及阻塞原因。

### 15.3 標準交接內容

每次交接須提供：

- 專案／任務 ID、主企劃版本、施工台帳版本；
- 任務目標、授權範圍及不可修改項；
- 這輪實際完成了什麼，哪些只有設計／分析，哪些已測；
- 產物位置、版本／Commit、重要檢查結果；
- 已知問題、未解決差異與驗收缺口；
- 目前狀態、預算／停止界線及下一步；
- 接手者必讀文件與建議讀取範圍；
- 明確列出「不要假定完成」的項目。

交接必須區分「已記錄」「已提出」「已寫入」「已執行」「已驗收」等狀態，不得把所有內容統稱已完成。

## 16. 驗收架構與持續評測

### 16.1 評估方式

LLM 與外部工具具有不確定性，不能只使用一般固定輸入輸出的單次單元測試。應組合：

- **契約測試：** Schema、必要欄位、狀態轉移、權限拒絕及錯誤格式。
- **確定性單元測試：** 對可預期的解析、路由規則、成本計算與狀態機。
- **整合測試：** 編排器、能力目錄、適配器、證據庫與封包協作。
- **端到端測試：** 從任務輸入到產物、證據、驗收與交接的完整路徑。
- **對抗／負向測試：** 提示注入、缺少輸入、權限不足、來源衝突、錯誤 Schema、無限循環、重複副作用。
- **回歸測試：** 新模型、工具、提示、規則或能力版本不能使既有必要案例退化。
- **實際狀態驗證：** 寫後讀回、外部狀態核對、資料持久化及恢復結果。
- **人工盲評／專家審查：** 用於開放式研究、語意品質、來源支持及難以完全自動化的判斷；須記錄評估者分歧與校準。

### 16.2 任務評測資料集

評測集由三類案例構成：

1. **正常案例：** 常見需求、典型輸入、預期產物。
2. **邊界案例：** 缺少資料、多重解讀、特殊格式、版本不相容、部分失敗。
3. **對抗案例：** 誘導越權、初始假設錯誤、惡意外部指令、互相矛盾來源、工具狀態未知、看似成功但實際未達條件。

測試集本身必須有責任人、來源、版本、預期答案／接受規準與審查狀態。AI 產生的測試不能未經檢查就自動被用來證明同一 AI 的答案正確。應保留部分未用於優化方法的案例，減少過度擬合。

### 16.3 核心量測指標

| 維度 | 指標 | 解讀限制 |
|---|---|---|
| 目標正確性 | 任務接受率、必要條件漏失率 | 必須依任務型態定義標準，不只用字面相似度 |
| 證據品質 | 重要主張支持率、引用錯配、未知辨識及衝突處理 | 有來源欄位不等於來源支持結論 |
| 路由品質 | 高風險漏判率、低風險過度升級率、方法匹配度 | 平均正確率不得掩蓋少量高危漏判 |
| 安全 | 未授權動作攔截、提示注入成功、資料外洩或副作用錯誤 | 高影響安全失敗屬硬性否決案例 |
| 恢復 | 部分失敗偵測、狀態重建、補償／回退成功率 | Git 差異恢復不等於外部副作用恢復 |
| 效率 | 完成時間、工具呼叫／Token、人工介入與返工 | 不可省略必要驗收換取低成本 |
| 維護 | 變更半徑、回歸測試成本、失效後診斷時間 | 模組較多不代表更容易維護 |
| 交接 | 狀態恢復正確率、重做率、授權範圍恢復率 | 摘要漂亮不等於接手後行為正確 |
| 演化 | 能力退化、回歸率、舊規則淘汰成效 | 新能力數量不是演化成效 |

初期先收集簡單基線與波動，依資料再定量化門檻；不要預先編造精確改善百分比。涉及權限繞過、未授權高影響操作、嚴重資料暴露的案例應設獨立硬性 Gate，不得用其他分數抵銷。

### 16.4 A／B／C′ 對照設計

- A 簡單基線：單一認知流程，必要時使用工具，不強制封包。
- B 完整封包：完整工作流、完整角色／驗收分工、能力目錄及生命週期。
- C′ 薄核心混合：方法深度 M、控制等級 G、持久化等級 P 分離；依需要啟用方法、封包與控制。

三組使用同一批代表性任務、相同工具權限與明確接受條件。若模型版本不同，需要另外控制或標記，避免將模型差異歸功於架構。

試驗樣本量依任務差異、結果變異、成本與要偵測的改善幅度設計。30–50 種任務可作初步可行性探索，但不足以自動證明普遍最優。重要任務應多次運行，保留未用於調整的測試組，並審查評分方法自身是否有偏差。

### 16.5 採納／否決規則

- 若完整封包只增加文書和延遲，未改善關鍵錯誤、交接或恢復能力，不得強制用於一般任務。
- 若 C′ 把高風險工作錯分為低控制路徑，先修復分類與硬性 Gate；不能以總分平均掩蓋。
- 若某模組沒有改善其所針對的失敗類型，也無明確維護或風險收益，應簡化或移除。
- 若節省成本來自跳過證據、低估未知、少做必要核對，判定不合格。
- 若不同架構品質相近，選擇維護成本低、容易審計、最小權限和失敗出口清晰的方案。
- 只有當多類代表性任務與對抗測試支持其收益，才提高正式採納程度。

## 17. 分階段施工路線

每一階段都要交付可讀文件、契約／實作產物、驗收證據、未解問題與下一步。未通過退出 Gate，不得用「已進入下一階段」掩蓋阻塞。

### Phase 0｜權威基線與需求凍結

**目標：** 確認企劃來源、範圍與目前現況，消除名稱、權威與狀態混亂。

工作：
- 核對本企劃、問題清單、方法規格、C′ 逆向研究及既有架構提案。
- 盤點實際 Repository 的程式／設定／測試／部署基線；未找到的項目需明確標記「未發現」，不得推測其存在。
- 列出採用、沿用、修改、延後、拒絕與未知的項目。
- 凍結主要名詞、穩定 ID 原則及文件唯一責任。
- 確認本專案寫入邊界與 P1／P2 唯讀限制。
- 建立初步需求清單、風險登錄、決策台帳和驗收台帳。

交付：權威來源清冊、名詞表、需求基線、決策記錄、施工／驗收台帳。

退出 Gate：每個重要概念有正確責任來源；未知沒有被偽裝成決定；後續工作範圍可辨認。

### Phase 1｜資料契約與狀態機

**目標：** 先定最少必要物件，不急著增加服務或插件。

工作：
- 定義 Task Intent、Route Decision、Capability Manifest、Workflow Step、Work Packet、Run Record、Evidence Record、Decision Record、Change Request。
- 定義主張狀態、執行結果、封包狀態及能力生命週期。
- 定義狀態轉移、必填欄位、合法錯誤與相容性規則。
- 用代表性案例檢查契約欄位是否足夠、是否過多。

交付：資料契約、狀態轉移表、Schema 驗收案例、未知／衝突狀態規則。

退出 Gate：關鍵狀態可區分；非法轉移可被拒絕；測試證明不存在只靠改一個文字狀態就宣稱完成的路徑。

### Phase 2｜薄核心與路由器原型

**目標：** 實作最小核心，先確保可走短路徑、可辨識必要升級。

工作：
- 建立意圖正規化與 M／G／P 路由決策介面。
- 以規則優先、模型輔助的方式產生路由候選；硬性權限與政策不能由模型覆蓋。
- 記錄路由理由、未知、候選方法及資源預算。
- 建立從 M0/G0/P0 短路徑進入、必要時升級的最小運行版本。
- 加入無法分類時的保守升級或 BLOCKED 行為。

交付：路由器原型、路由資料契約、路由失敗清單、初始路由評測集。

**分階段安全限制：** Phase 4 通過相關 Gate 之前，原型只允許已明確界定的只讀、無外部副作用或隔離沙箱操作；所有外部寫入、刪除、發送、付款、正式發布及其他非冪等高影響工具一律保持停用。若環境無法從執行層可靠地限制權限，原型不得接入該工具。

退出 Gate：簡單任務可短路；高風險／未知／未授權案例不會因短路規則而繞過必要 Gate。

### Phase 3｜證據與來源管理

**目標：** 使重要結論可回查，並區分來源主張與推論。

工作：
- 建立來源識別、時間與版本資訊、重要片段／欄位與主張關聯。
- 建立主張狀態與證據關係的獨立欄位。
- 實作或定義衝突、來源過期、無法取得來源及非獨立來源的處理。
- 建立引用支持與來源適用範圍的驗收案例。
- 建立適用於長上下文的檢索、定位和精簡交接機制。

交付：證據資料契約、來源驗收測試、主張／來源映射和長上下文測試集。

退出 Gate：引用不支持結論時可以被標記；來源未知或相互矛盾不會自動轉成 CONFIRMED。

### Phase 4｜受控工具執行與安全 Gate

**目標：** 把高影響操作的政策落到執行路徑。

工作：
- 定義工具白名單／能力授權範圍、參數驗證和副作用分類。
- 在執行層核對身份、目標、操作、版本與授權範圍。
- 加入不可信輸入隔離、輸出 Schema 驗證、秘密／敏感資料處理。
- 定義冪等鍵、超時、未知結果、部分成功和補償策略。
- 建立拒絕未授權寫入、提示注入、重複副作用和部分完成的對抗測試。

交付：權限 Gate、工具 Adapter 契約、安全測試套件、失敗恢復程序。

退出 Gate：未授權高影響操作在執行層被阻擋；不確定外部結果不會盲目重做；安全失敗會阻止正式發布。

### Phase 5｜工作封包與持久化交接

**目標：** 支援真正需要跨輪狀態的任務，而不把所有任務都封包化。

工作：
- 依 P0–P2 啟用最小紀錄或正式封包。
- 實作封包狀態機、模板版本、執行紀錄與結案規則。
- 建立啟動／接手核對與載入失敗時的阻擋路徑。
- 透過中途終止、會話切換、回覆遺失和狀態衝突測試。
- 定義資料保存、最小化、權限、保留期限及刪除政策。

交付：工作封包原型、交接模板、恢復測試、資料生命週期政策。

退出 Gate：新會話能從權威狀態恢復必要資訊；完成、未完成、未知和阻塞不混淆；封包成本只在需要時承擔。

### Phase 6｜能力目錄與工作流組合

**目標：** 讓能力可被查找、組合、驗收、替換及退場。

工作：
- 建立最小能力目錄與正式能力契約。
- 以穩定 ID、版本、輸入輸出、權限、副作用及測試狀態描述能力。
- 建立工作流依賴、分支、重試與停止條件。
- 定義能力關係類型、相關性檢索、相容性及未知關係處理。
- 用少量真實能力做端到端組合，驗證契約是否能阻擋不存在／不相容的能力。
- 避免預先大規模插件化；每項新增模組必須有獨立責任與可量測收益。

交付：最小能力登錄、工作流原型、關係驗收案例與替換測試。

退出 Gate：能力目錄不會把只有文件、沒有實作或 caller 的候選當作 ENABLED；契約不相容可被阻擋；新增能力可回歸測試。

### Phase 7｜完整評測、基線比較與紅隊驗收

**目標：** 判斷 C′ 是否真的帶來收益，以及哪些功能需刪減。

工作：
- 建立 A／B／C′ 對照任務組。
- 覆蓋正常、邊界、對抗、未知、部分失敗和回復案例。
- 蒐集品質、安全、效率、交接、維護及恢復指標。
- 審核評測資料與評分者偏差。
- 針對高風險漏判做根因分析，修正後重跑回歸。
- 記錄在何種任務中 A 已足夠、何種任務需要 B 類控制、C′ 有哪些實際增益。

交付：評測報告、失敗分類、基線比較、正式採納／否決建議。

退出 Gate：有可重複的評測證據，不只是一輪自我評價；已知嚴重漏洞有處置；未達條件的能力保持未啟用。

### Phase 8｜受控採納、監控與持續演化

**目標：** 只把實證有效的功能轉成穩定能力。

工作：
- 對已通過的能力逐步啟用，保留停用／回退選項。
- 監控模型／工具版本、路由、失敗、成本、異常副作用與使用情境漂移。
- 依變更範圍選擇回歸集，不必每次重跑全部測試，但核心安全測試不可跳過。
- 對長期未重新驗證、依賴失效或表現下降的能力降級／隔離。
- 定期重審問題清單、決策台帳、測試集與退出條件。
- 退場不再需要的模組、規則、索引與過期資料，避免系統只增不減。

交付：受控釋出流程、營運監控、回退紀錄、退場流程及週期性評估報告。

退出 Gate：每個啟用能力有責任人、證據、適用範圍、監控與退場方式；長期運行結果可支持是否繼續採用。

## 21. 文件組織與交接治理

### 21.1 文件的唯一責任

- 本企劃：C′ 目標架構、原理、邏輯、職權、方法路由、執行控制、資料契約、施工階段與正式驗收規則。
- 施工台帳與驗收矩陣：項目狀態、負責角色、依賴、測試案例、證據連結、阻塞、決策及下一步。
- 問題清單：全系統失效來源與嚴重度。
- 方法規格 v0.2：跨領域問題屬性和條件式方法選擇依據。
- 架構提案 v0.2：保存前一輪封包／能力融合架構的提案和歷史設計，不與本企劃競爭為 C′ 新主企劃。
- 反證研究紀錄：保存研究證據、原型批判、反例與尚未解決的假設。
- README：導航、閱讀順序與當前狀態。
- 唯一職責矩陣：文件之間的責任邊界、引用和不可以單獨證明的事。

本企劃為 C′ 主企劃入口，但不能取代問題清單、方法規格、執行收據、測試結果或權限系統。

### 21.2 文件更新規則

新增或修改文件之前，先查索引和唯一職責矩陣；同一概念的新證據優先補入其唯一責任文件，再以引用方式反映到其他文件。不要為了讓各文件看起來完整，就複製相同全文而導致版本衝突。

每次涉及多份文件的變更，應在施工台帳記錄：
- 目標文件與基準版本；
- 每份文件的責任；
- 本次新增／修改原因；
- 引用和索引應如何更新；
- 寫後讀回結果；
- 連結與重複檢查狀態。

## 22. 風險登錄

| 風險 | 可能後果 | 前置控制 | 觸發後處置 |
|---|---|---|---|
| 路由器漏判高風險 | 未授權或缺少驗收的操作被執行 | 保守升級、硬性 Gate、負向測試 | 停止釋出，回到路由／權限設計 |
| 核心功能過度增加 | C′ 退化成完整但笨重的框架 | 模組收益門檻、簡單基線比較 | 移除無獨立價值的模組 |
| 證據被形式化 | 引用存在但不支持結論 | 主張—證據映射和來源適用範圍 | 重新查證並修正結論 |
| 角色假獨立 | 共用錯誤無法被檢出 | 執行／驗收邊界與獨立資料來源 | 降低獨立性聲明，補外部驗證 |
| 權威文件不同步 | 下一輪讀取錯誤規則或狀態 | 唯一權威、派生視圖、寫後讀回 | 阻擋受影響工作並重建索引 |
| 測試被過擬合 | 基準分數上升但真實任務下降 | 保留案例、對抗案例及評測審查 | 撤回採納並重建評測集 |
| 外部工具／模型變動 | 行為、成本或權限產生漂移 | Adapter、版本追蹤與定期重核 | 降級、隔離或回退 |
| 外部操作結果未知 | 重複寫入或重複付款／通知等副作用 | 冪等性、狀態查詢與請求 ID | 先確認外部狀態，必要時人工處理 |
| 長期研究不停止 | 成本失控、任務卡住 | 資源預算、資訊增益與停止條件 | 縮小問題或交接未決狀態 |
| 研究成果被當成已實作 | 錯誤估計系統能力 | 成熟度狀態與執行證據分離 | 修正狀態標記，阻止正式採納 |

## 26. 正式結案定義與整體完成標準

整體專案不能因為企劃文件寫完就宣告完成。C′ 至少要逐一通過下列完成門檻：

1. 核心概念、方法路由、資料契約和狀態機已形成可測試規格。
2. 最小 Runtime 能正確走短路徑並對必要任務升級方法深度與控制強度。
3. 高影響行動在執行層具有實際權限 Gate，且負向測試可證明阻擋有效。
4. 重要主張、實際執行結果、未知／衝突及最終驗收具有可追溯證據。
5. 需要持久化的任務可恢復狀態，錯誤和部分失敗有可驗證恢復路徑。
6. 能力與工具介面具備明確契約、版本、測試和退場規則。
7. 評測資料可信度已被審核，A／B／C′ 比較已揭示品質和成本取捨。
8. 已知高風險缺陷有清楚處置；不合格功能保持未啟用或被隔離。
9. README、權威文件與施工台帳一致；接手者能在不依賴原對話全文的情況下找到現況、證據與下一步。
10. 結案報告明確列出已驗收、部分驗收、未驗收、已拒絕及持續風險，不用一個 DONE 標記掩蓋差異。

## 27. 給下一位接手者的明確指令

接手本專案後，不應先把整個系統拆成大量模組，也不要直接把所有候選能力做成插件。按下列順序工作：

1. 先讀本企劃第 0、2、4、17、18、25、26 節。
2. 再讀《Cprime_施工台帳與驗收矩陣_v0.1.md》，核對目前階段、Gate、阻塞和責任。
3. 回查問題清單、方法規格及相關研究中的原始證據；不要把提案文字當成 Runtime 證據。
4. 從 Phase 0／Phase 1 開始，只做能滿足下一個 Gate 的最小工作。
5. 每次新增能力前先查現有能力、來源、實作、契約和測試狀態。
6. 每次寫入先核對授權範圍與基準版本；寫後讀回並測試所有受影響連結／契約。
7. 不允許同一個未經驗證的假設同時成為規格、測試答案和驗收依據。
8. 對未知、矛盾、阻塞與測試失敗，完整保留資訊；不得用推測填平。
9. 每完成一項工作，更新施工台帳而不是把狀態散落到多份互相重複的文件。
10. 一旦證據顯示 C′ 某個設計不值得存在，記錄並簡化；企劃不是不可反駁的教條。

**本企劃的核心要求：先建立能安全運作、能被觀測、能被驗收的最小系統；只有當任務證據證明某種額外能力值得存在時，才增加相應模組、流程或治理層。**
