## 1. 診斷結論

本次核心判斷：**forAVAr 最大的治理問題，不是缺少 SOP 文件，而是既有規則沒有穩定轉化為工作開始前必經的檢查、決策閘門、執行證據與回歸驗收。**

當前系統已有問題清單、唯一職責矩陣、流程索引、版本治理、SOP 生命週期、SOP 建檔規格、執行台帳及追溯事件，但「文件存在」不保證每次重要工作都會先讀取、比較、執行並驗收相關規則。因此可能出現先做局部交付、之後才發現原本已有相近流程、文件責任重疊或應先抽象出通用方法的情況。

這不應簡單歸因為使用者需求描述不清。當既有專案已明確建立方法選擇、問題清單及職責治理時，AI 應主動推導根本目的、檢索舊有處理方式、檢查框架與職責邊界，再選擇最低風險且不重複建構的方案。本次先前的 SOP 工作沒有充分做到這一步，屬於執行前分析與系統整合失誤。

本文件對模型內部機制不作無證據的斷言；根因排序依可觀察行為與現有文件推論，並不等於已量測出模型能力上限。

## 2. 當前治理結構與控制缺口

### 2.1 現有四個層次

1. **入口與狀態導航：** README、文件與分支索引、變更追溯總表。用途是定位現行文件、版本和歷史變更。
2. **治理與權責：** 版本治理、唯一職責矩陣、問題清單。用途是界定唯一責任、版本、重複內容、衝突和問題狀態。
3. **流程與 SOP：** 對話流程列表、SOP-META-001、SOP-DOC-001，以及各領域專用流程。用途是路由任務、規範執行步驟與 SOP 生命周期。
4. **執行與驗收：** SOP 執行台帳、追溯事件、讀回、連結與文件長度檢查。用途是保存結果、偏差與驗收證據。

主要缺口發生在層與層之間：現有文件能描述「應該怎麼做」，卻沒有充分保證重要新需求一進來，就一定會先做目標辨識、既有狀態盤點、職責比對、衝突判定、變更影響分析，再進入寫入。

### 2.2 三個直接弱點

- **問題清單與執行行為連結不足。** PR-001、PR-006、PR-011、PR-012、PR-013 等已記錄目標理解、因果根因、重複犯錯、方法路由及初始框架錯誤。若它們不會觸發具體檢查，就只是一份問題目錄。
- **唯一職責矩陣尚未成為穩定的前置閘門。** 新建文件前未必先確認：同一責任是否已存在、這是擴充還是重複、是否與現行規則衝突、應更新哪份權威文件，以及哪些相依索引必須同步。
- **SOP 生命周期與 SOP 建檔／蒸餾流程是不同責任。** SOP-META-001 管理選用、試行、驗證、改良、定版和退役；SOP-DOC-001 管理 SOP 欄位與建檔。另已觀察到 CF-004「對話成果轉成可追溯文件」和 CF-010「SOP 建檔與對話蒸餾」在來源盤點、分類、分流及驗收上有部分重疊。應明確定義邊界，而不是直接假定要合併。

## 3. 參照成熟軟體團隊的治理做法

參照目的不是照搬大型公司的所有流程，而是辨識可移植的控制原理。

- **事後檢討與改善追蹤：** Google SRE 的 postmortem 文化強調保存事件背景、根因和可執行、可追蹤的改善事項；只記錄問題而不跟進，不足以防止復發。來源：[Google SRE Workbook：Postmortem Culture](https://sre.google/workbook/postmortem-culture/)。
- **開始與完成的明確門檻：** Microsoft Engineering Fundamentals Playbook 將 Definition of Ready 和 Definition of Done 作為團隊約定／檢查清單，降低工作開始時資訊不足，以及未符合完成條件就結案的風險。來源：[Definition of Ready](https://microsoft.github.io/code-with-engineering-playbook/agile-development/team-agreements/definition-of-ready/)、[Definition of Done](https://microsoft.github.io/code-with-engineering-playbook/agile-development/team-agreements/definition-of-done/)。
- **決策理由可追溯：** Architecture Decision Records（ADR）將重大選擇的背景、決策與後果留下可回查記錄。對 forAVAr 可作候選方法，但是否建立獨立正式制度仍待裁定。來源：[Thoughtworks：Lightweight Architecture Decision Records](https://www.thoughtworks.com/en-au/radar/techniques/lightweight-architecture-decision-records)。
- **變更模板、責任審查及自動化閘門：** GitHub 文件描述 PR 模板可要求目的、相關議題與測試資訊；CODEOWNERS 可路由到檔案負責者；受保護分支可要求審查或狀態檢查。這些方法把部分約定放到工作流程中，而不是完全仰賴記憶。來源：[Managing and standardizing pull requests](https://github.com/github/docs/blob/main/content/pull-requests/reference/managing-and-standardizing-pull-requests.md)、[About Code Owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)、[Managing protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches)。
- **依資料與回饋持續改善：** DORA 將 learning culture 視為改善軟體交付績效的重要能力；改善應建立在觀察和學習上，而非只增加流程數量。來源：[DORA：Learning culture](https://dora.dev/capabilities/learning-culture/)。
- **推理模型也需要明確成功條件與評估：** OpenAI 的推理最佳實務建議明確指定最終目標、限制與成功參數，並以評估比較結果；推理能力不能取代完整的任務定義和驗收。來源：[OpenAI：Reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices)、[Model optimization](https://developers.openai.com/api/docs/guides/model-optimization)。

這些來源支持治理控制原理，但不證明任何單一方法能直接解決所有模型失誤；forAVAr 仍須用自身任務案例驗證。

## 4. 改善方向與優先順序

### P0｜意圖辨識、職責掃描與變更影響的前置閘門

適用於非瑣碎、多步驟、跨文件、重複類型或需持久化的任務。建議程序：

1. 解析真正目的：明示要求、根本用途、成功標準、限制及非目標。
2. 掃描既有系統：相關 MASTER、SOP、職責矩陣、問題清單、對談紀錄和執行證據。
3. 分類變更：新增、擴充、重複、衝突、分支、取代、決策紀錄或案例保存。
4. 建立影響表：受影響文件、唯一責任、變更理由、相依引用、權限及回歸風險。
5. 選擇最低必要變更：先擴充現有權威文件；只有確認存在新職責時才新建文件。
6. 逆向驗收：檢查新內容是否正確，是否產生重複／矛盾，是否遺漏索引、回鏈或原始證據。

掃描是必要條件，不是全面改寫的授權。目標是先理解現況，再選擇最小且正確的變更集合。

### P1｜統一資料類型，避免新想法直接變成規則

- **SOURCE：** 原始對話、檔案、工具輸出，保存來源和完整性狀態。
- **IDEA：** 尚未驗證的想法，先比較既有架構與證據。
- **PROBLEM：** 缺口、矛盾或錯誤，記錄問題 ID、影響、證據及狀態。
- **DECISION：** 已選方案與理由，記錄背景、替代方案、取捨和限制。
- **RULE：** 已裁定並應持續遵循的規則，置於唯一權威文件。
- **SOP：** 有輸入、步驟、分支、停止條件和驗收的可重複程序。
- **RUN／EVIDENCE：** 某次執行的結果、偏差、測試及驗收證據。

IDEA 不會因為被提出就自動升格為 RULE；一次成功也不證明 SOP 已普遍有效。

### P1｜定義開始、完成及整合驗收

- **開始門檻：** 目標、授權、來源、既有職責及輸出要求足夠明確。
- **整合門檻：** 新內容與舊規則是否相容；若衝突，是否留下決策及未決狀態。
- **完整性門檻：** 原有證據、反例、限制、未知與引用是否保留。
- **結案門檻：** 每項需求都有交付或清楚標記為未完成／受阻。
- **行為門檻：** SOP 修改需以實際案例驗證，不只檢查文件存在。

### P1｜改善閉環

重要問題應連成：

問題 ID → 已證實根因 → 改善措施 → 負責角色 → 驗收條件 → 驗證案例 → 復發檢查 → 最終狀態。

同一失敗重現時，要檢查上次措施未實施、未被觸發、驗收不足，或根因診斷錯誤。不能只新增另一段說明。

### P1｜逐步加入低成本的一致性檢查

候選檢查包括：文件 ID 唯一性、必要欄位、相對連結與章節錨點、字元上限、索引／責任矩陣同步、狀態合法性及固定回歸案例。工具實作需先評估現有環境及維護成本；不預設採用特定 CI 平台。

## 5. 為什麼 AI 會表現成事後補救

本診斷區分可觀察行為與未知的模型內部原因：

1. **不宜單純歸因智力不足。** 不能直接檢查模型權重或內部決策機制，因此不能斷言此失誤完全由模型能力上限造成，也不能承諾只換更強模型就根治。
2. **本次最明確的執行失誤，是局部完成取代整體問題分析。** 應主動確認「任務真正要解決什麼」、先前是否已有類似流程、現有文件如何承載，以及需要哪些驗收欄位；實際工作未充分完成這些檢查。
3. **治理文件不是自動執行的控制器。** 矩陣不會自行阻止重複建檔；SOP 不會僅因寫入文件而保證每次被載入、遵守或通過驗收。
4. **已知問題沒有穩定連接到觸發條件。** 缺少「已知問題 → 前置檢查 → 失敗判定 → 改善措施 → 回歸測試」的閉環時，錯誤可能被記錄卻不改變下一次行為。
5. **依賴檢索與摘要有風險。** 若先前案例未被找到、錯誤定位或被當成完整狀態，模型可能把舊問題當成新問題；因此需檢查實際來源，而不是假設「應該記得」。

### 根因排序（依本案例可觀察證據）

| 根因 | 判斷 | 後果 |
|---|---|---|
| 前置目標分析與職責掃描未落實 | 主要直接失誤 | 未充分盤點現有系統就執行局部交付 |
| 治理規則缺少必過閘門 | 主要架構缺口 | 文件雖在，執行仍可能跳過 |
| 問題紀錄與回歸測試未閉環 | 主要學習缺口 | 已知錯誤不能穩定轉成防重演機制 |
| 模型偏向局部完成而未主動展開全域分析 | 行為限制 | 產物看似完整但漏掉更高層需求 |
| 檢索、摘要與跨會話狀態依賴 | 輔助風險 | 找不到前例或誤讀狀態會造成重複工作 |

此排序是本案例的診斷，不是模型內部機制的確證測量。

## 6. 建議的共用工作程序

理解目標 → 掃描系統現況 → 找出缺口／衝突／候選解 → 選擇最低必要變更 → 執行與逆向驗收 → 將已證實經驗轉成改善並回歸測試。

流程應依風險和複雜度適配：低風險簡單任務可縮短；跨文件、架構決策、正式變更或高影響任務須完整檢查。不能把所有任務都強迫跑滿同一長流程。

## 7. 衡量改善是否有效

建議在代表性案例建立基線，觀察：

- 重複建立同職責文件的次數。
- 新增／修改前漏掉既有權威文件或流程的次數。
- 未處理職責衝突便寫入的次數。
- 多檔更新漏改索引／引用或形成部分狀態的次數。
- 同一失敗在已記錄改善後再次發生的次數。
- 返工、錯誤、成本、延遲及維護負擔。

未量測以前，只能稱為改善假說，不可宣稱效率提升或最優。

## 9. 診斷邊界

本文件是診斷紀錄和改善建議，不等於新 SOP 已核准、程式已實作或模型行為已改善。具體 SOP 項目與狀態由 [SOP 清單與落實狀態分組](../SOP清單與落實狀態分組.md)唯一維護；問題 ID、嚴重度和狀態由問題清單維護。未經正式驗收，不把文件建立、單次成功或主觀認為更嚴謹當成系統性改善證據。
