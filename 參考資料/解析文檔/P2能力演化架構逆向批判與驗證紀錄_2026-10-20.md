## 1. 本輪批判範圍

### R4｜本輪框架重整與全面逆向批判

使用者要求把本次討論和前面三輪整合成一套框架紀錄，之後對該框架進行全面逆向批判，找出錯誤和漏洞。

本輪執行方向：
- 建立新的獨立研究紀錄，不把候選框架直接覆寫成正式企劃或 P2 權威規格。
- 將外部工具吸收流程分為來源核驗、原理分析、能力規格、關係辨識、採用裁決、獨立測試、受控發布和生命週期管理。
- 將「不會有衝突」修正為「衝突可被發現、分類、隔離和裁決」。
- 以反例檢查自我驗證、錯誤蒸餾、能力關係組合爆炸、授權與來源風險、模組化假象、模型行為不等價、知識過期、安全攻擊、更新原子性、評估偏誤及治理過重。
- 為核心假說設計可執行的紅隊案例和量測指標，不將文件完成視為架構正確或能力已實作。

四輪共同形成的核心命題是：P2 不應只建立工具清單，而應建立一套能把外部技術轉化為可比較、可驗證、可替換且可追溯能力的治理與演化機制；能否做到，必須用可重複的端到端實驗證明。

## 1. 逆向批判：主要錯誤、漏洞與反例

以下將問題按風險區分。優先級是本次分析判斷，不是統計測量，也不是已在 P2 程式中全部重現的缺陷。

### CRIT-01｜「衝突會轉化成重疊」是錯誤假設

- **反例：** 兩套規則各自都有效，但一套要求 fail-open 以維持可用性，另一套要求 fail-closed 以保護資料；兩種方法對資料新鮮度或權限的定義也可能不同。
- **漏洞：** 若框架只以重疊／互補分類，會漏掉政策矛盾、狀態衝突、資源競爭、時序問題和副作用。
- **修正：** 關係模型必須明確表達 conflict、incompatible、dependency、unknown；「不相容」可作為合法的裁決結果，而不要求融合。
- **驗收：** 對同一輸入設計相互矛盾的規則，系統必須標出矛盾、拒絕隱式合併，並記錄裁決和適用範圍。

### CRIT-02｜AI 產生的錯誤抽象可能被放大成共用能力

- **反例：** AI 根據不完整的 README 抽取一套通用方法；其他任務重用此方法後，在不同環境中造成同類錯誤。
- **漏洞：** 蒸餾能把正確知識變成可重用能力，也能把錯誤假設變成系統級錯誤。
- **修正：** 每項抽象保留來源範圍、支持／反證、未知條件、信心依據和針對性實驗；重要能力先保留為 EXPERIMENTAL，不可自動提升為 STABLE。
- **驗收：** 故意提供缺少關鍵條件的來源，檢查系統會不會產生過度通用的原理，並將未驗證部分明確標記。

### CRIT-03｜由同一 AI 設計、實作、測試和批准會形成循環驗證

- **反例：** 模型寫出錯誤實作，再產生與該實作假設一致的測試，最後因測試通過而宣稱成功。
- **漏洞：** 程式與測試都可能忠實反映同一個錯誤理解。
- **修正：** 測試資料與接受條件應先固定；重要功能需有獨立驗收者、人工審核或不同機制的反例測試。模型不同不等於真正獨立，因為它們可能共享訓練資料、偏誤及提示內容。
- **驗收：** 建立已知錯誤但能通過弱測試的實作，檢查獨立驗收是否能揭露問題。

### CRIT-04｜原理抽取與合法／授權的界線未充分定義

- **反例：** 外部專案包含特殊授權條款、專利限制、機密內容、個人資料或不可再散布的實作；「逆向分析」不能自動授權複製程式碼或受限制內容。
- **漏洞：** 技術上能讀取不代表有權將其複製、再散布或商品化。
- **修正：** 來源登錄中必須包含授權和使用條件；依賴外部內容時記錄義務。對不明權利、受限資料或法律風險標示 BLOCKED／待專業審查，不將法律判斷交給模型單獨決定。
- **驗收：** 使用授權不明及限制不同的候選來源，確認系統不會自動將它們納入共用能力。

### CRIT-05｜標準化可能抹掉重要的操作語意

- **反例：** 兩工具表面上都有「分析依賴」輸入／輸出，但其中一個只解析靜態匯入，另一個會執行程式、讀取網路資料或改動檔案。
- **漏洞：** 抽象介面如果只保留功能名稱和資料格式，就掩蓋了環境依賴、可信度、成本、時效與副作用。
- **修正：** 契約須包含前置條件、環境、資料來源、執行權限、非功能需求、可觀測性和失效模式；不相容能力可以維持獨立介面。
- **驗收：** 用語意近似但副作用不同的工具，檢查標準化是否保留重要差異。

### HIGH-06｜能力關係圖可能出現組合爆炸

- **反例：** 若有 N 個能力，最壞情況下兩兩關係候選數可達 N(N-1)/2；一千個能力即有 499,500 組無向配對。
- **漏洞：** 若每新增能力都要求人工審查全域兩兩關係，更新成本會隨規模快速增加。
- **修正：** 不做無差別全配對。根據語意、依賴、共同介面、實際呼叫與已觀察衝突，採候選檢索和有界關係分析；對未知關係不當作相容，只在相關任務或變更影響範圍內加深檢查。
- **驗收：** 逐步擴大能力目錄，量測每次納入的關係分析成本、漏掉的已知衝突和不必要的關係數。

### HIGH-07｜「模組化」不保證變更半徑小

- **反例：** 多個模組都直接讀取同一份 Current、共用 Schema 或交叉引用實作細節；單一契約變更便迫使全域更新。
- **漏洞：** 檔案分開只是物理分割，不等於低耦合。
- **修正：** 明確依賴方向、介面契約、版本相容政策、影響分析及測試分層；共用權威變更要明確列為跨模組重大變更，而不是假裝可以局部處理。
- **驗收：** 追蹤代表性變更的實際影響範圍，測量受影響元件、修改檔案、測試成本與回歸錯誤率。

### HIGH-08｜模型可替換不代表模型行為等價

- **反例：** 新模型更快、成本更低，但更常輸出錯誤 JSON、略過工具呼叫前置檢查或更改錯誤處理方式。
- **漏洞：** API 介面相同不等於語意行為相同。
- **修正：** 為模型建立任務能力檔案與版本化適配器，使用共用任務集測量任務成功、工具選擇、契約遵循、失敗模式、成本和延遲；不達標時按任務路由回舊模型。
- **驗收：** 至少測試同一能力在兩種模型上的正向、負向和邊界案例，並保留可比較結果。

### HIGH-09｜外部知識會過期，來源指紋不足以證明語意仍正確

- **反例：** 外部服務 API 沒有改版本號，但權限政策、服務行為、文件內容或部署設定已改變。
- **漏洞：** Hash 只能確定被比較的位元組是否不同，不會保證資訊仍適用於現況。
- **修正：** 區分內容版本、觀察時間、環境版本和適用期限；以事件或風險觸發重新驗證，重要外部服務須設定過期／重新核實規則。
- **驗收：** 以 API 行為改變但本地舊規格未同步為反例，確認系統能阻擋舊假設被當作最新真值。

### HIGH-10｜外部工具與文件本身可能是攻擊入口

- **反例：** 工具描述、README、範例程式或外部內容含有 prompt injection，誘導系統洩漏上下文、擴大權限或執行未授權命令。
- **漏洞：** 逆向流程會大量讀取外部資料；若把外部指令當成治理規則，就把探索層連通了控制層。
- **修正：** 把外部內容當不可信資料；限制網路、檔案、憑證與副作用；工具呼叫前後設政策檢查；重要操作 default-deny，證據／政策未知時阻擋；發布與寫入須另有明確授權。
- **驗收：** 建立惡意工具說明、路徑穿越、憑證外洩誘導和未授權寫入測試。

### HIGH-11｜人氣和活動指標不能決定能力價值

- **反例：** 高 Star 專案可能不符合當前需求、停止相容、授權不適合或成本過高；小型專案可能解決關鍵特殊問題。
- **漏洞：** 把候選發現排名當成能力品質會形成流行度偏誤。
- **修正：** 外部工具雷達只用於發現候選；後續依功能適配、證據品質、維護活性、安全、授權、成本及任務基準獨立評分。允許低人氣候選進入分析，也允許熱門候選被拒絕。
- **驗收：** 準備「高人氣但不適用」和「低人氣但有效」的對照樣本，驗證排序與採用決策不混淆。

### HIGH-12｜AI 生成的基準測試可能錯誤、偏狹或被過擬合

- **反例：** 測試只驗證生成者預期的實作細節，拒絕其他合理解法；或被測系統針對已知測試輸出特例。
- **漏洞：** 測試通過的意義取決於測試本身有效，而非只看 PASS 旗標。
- **修正：** 接受條件先定義；重要測試由獨立來源審核；使用未知保留集、隨機化／變形測試、負向／邊界／回歸樣本，以及任務結果層級評估。
- **外部依據：** OpenAI 於 2026-02-23 公布的 SWE-bench Verified 審查，在 138 個被審查案例中至少 59.4% 被判定有足以影響公平性的測試或題目問題；同年 7 月對 SWE-bench Pro 的另一篇審查估計約 30% 任務有問題。這些是特定基準及其研究者的審查結果，不應外推為所有基準都有相同比例，但足以說明評估本身必須受驗證。
- **驗收：** 對評估套件本身進行人工抽查、反例挑戰和任務改寫，估計錯判比例。

### HIGH-13｜抽象、能力、工作流程、工具與角色可能再次混層

- **反例：** 把某個工具名稱當成能力，把工作流當成能力實作，再為每個能力都新增永久 Agent，造成多份規則與狀態。
- **漏洞：** 表面上建立很多層，實際上仍在重複管理相同職責。
- **修正：** 能力是可重用的職責／契約；方法是實現策略；適配器是外部介接；工作流是按條件組合能力；角色是一次工作中的責任分配。只有責任不可合併且有持續價值時，才新增常駐角色或服務。
- **驗收：** 對新增元件逐項檢查唯一責任、輸入輸出、狀態所有者、必要性和可被既有元件吸收的替代方案。

### HIGH-14｜自動更新可能產生非原子狀態或錯誤回退

- **反例：** 新能力先更新登錄表，適配器和測試尚未發布；另一個流程已按新版能力路由，造成短暫不一致。
- **漏洞：** 單檔插拔不保證整個能力及其依賴的更新具有原子性。
- **修正：** 發布交易須綁定整組版本與指紋；先驗證依賴和測試，再切換路由；切換失败則回到已知完整集合。明確區分資料庫／檔案原子性和外部副作用回復能力。
- **驗收：** 在發布中途故意中斷，確認不會留下部分啟用狀態，並能恢復至舊版。

### HIGH-15｜能力評級缺少一致的目的函數，容易以單一分數掩蓋取捨

- **反例：** 一項工具準確度最高但成本過高；另一項便宜但在高風險任務中漏錯；第三項只適用少量場景。
- **漏洞：** 一個總分可能掩蓋安全、正確性、可復原性等不能互相抵銷的硬性條件。
- **修正：** 先設不可交易的 Gate（安全、權限、資料完整性、最低正確性），再按任務類別比較成本、速度和維護；允許 Pareto 前沿或任務條件式選擇，不強求全域唯一冠軍。
- **驗收：** 使用成本與正確性互有優劣的候選，確認硬性限制優先，且依任務條件做選擇。

### HIGH-16｜自動化治理流程可能重於它所解決的問題

- **反例：** 微小、可逆且低風險的知識補充也需跑全套來源審查、關係掃描、回歸和批准，處理成本高於價值。
- **漏洞：** 框架因保護每一層而發展成多重控制面和過多狀態，降低吸收新能力的效率。
- **修正：** 依變更影響而非檔案數分級；普通知識更新走短路徑，能力介面變更走相容性測試，權限／安全／權威變更走嚴格 Gate。任何捷徑都不得跳過適用的安全和驗收條件。
- **驗收：** 比較各風險級別的處理時間、漏錯率和人工介入，不只統計規則數或步驟數。

### HIGH-17｜「自我演化」可能只是把 Markdown 改得越來越多

- **反例：** 系統反覆整理規則與文件，但實際任務成功率沒有上升，甚至每次啟動需要讀取更多內容。
- **漏洞：** 文件產生量被誤當成能力成長。
- **修正：** 演化必須有前後對照的行為指標；不再有用的候選規則應能退場，保留原始來源與可追溯歷史但不讓歷史全部進入每次 Context。
- **驗收：** 在相同、未公開給模型的任務集上比較版本，要求完成品質提升或維護成本下降，並報告錯誤與退化。

### HIGH-18｜「抽取原理」與「自動學會新能力」不是同一回事

- **反例：** 系統保存了能力規格，卻沒有可執行的實作、權限、資料或環境；只靠描述無法完成任務。
- **漏洞：** 把知識表徵誤認成可用執行能力。
- **修正：** 分開 Knowledge／Method／Capability Contract／Implementation／Runtime Evidence；只有在有執行機制且通過驗收後，才把能力標為可用。
- **驗收：** 將只有說明文件、沒有 caller 或實作的能力提交路由器，確認系統會拒絕將它當作可執行能力。

### HIGH-19｜權威狀態與派生視圖可能不同步

- **反例：** 唯一 Current 已進入新的批次，README 投影仍顯示舊工作切片；後續操作者可能照錯誤的摘要執行。
- **實際觀察：** 本次唯讀檢查 P2 README Current Projection 顯示 P2-B2.2；P1-CURRENT.json 則顯示 P2-B1-B8-CODE-FIRST。Current 是 P2 自己規定的權威來源，因此 README 應被視為過期派生視圖。
- **修正：** 派生視圖應由權威來源產生或有自動一致性檢查；每次啟動按明確規則讀取 Current，不依靠摘要文件推斷。來源有衝突時明確阻擋受影響工作。
- **驗收：** 注入互相矛盾的 Current 與 README，驗證啟動行為採用唯一權威並標記投影過期。

### HIGH-20｜「完整逆向分析」缺少停止條件，容易陷入無限研究

- **反例：** 不斷嘗試取得所有來源與所有內部細節，導致系統永遠不進入可驗證的最小整合。
- **漏洞：** 「完整」沒有可操作邊界；任何未讀內容都可能被視為阻塞。
- **修正：** 以任務相關性、風險、依賴範圍和證據缺口定義充分程度。明列未分析範圍；只要它不影響本次裁決，允許帶 UNKNOWN 前進到低風險隔離實驗。核心安全或權限未知時仍須阻擋。
- **驗收：** 提供大型來源庫，確認系統能只解析和本次能力有關的範圍，並保留其覆蓋限制。

## 2. 逆向測試集：必須讓框架在對抗情境下失敗一次，才能檢查是否能攔截

## 3. 量測指標與對照實驗

不能只驗證「框架有沒有步驟」，要驗證框架是否產生可量化的改善。

### 11.1 核心指標
- **能力抽取精確度：** 人工審核的關鍵條件、限制和副作用是否被正確保留。
- **關係判斷品質：** 已知重疊、互補、依賴、矛盾和不相容的 Precision／Recall。
- **衝突漏判率：** 已知不能安全並用的能力，有多少被錯誤判為相容。
- **整合成本：** 從新來源出現到取得合格能力所需的時間、模型呼叫、人工介入與執行資源。
- **回歸率：** 每次更新造成舊有合格任務退化的比例及嚴重度。
- **變更半徑：** 一項局部更新實際影響的模組、契約和測試範圍。
- **恢復能力：** 發布失敗後恢復到已知有效版本的成功率與時間。
- **模型替換穩定性：** 不同模型對同一能力契約的成功率、錯誤模式和成本。
- **有效淘汰率：** 被拒絕或退場的候選是否確實減少維護成本，且未遺失必要能力。
- **實際任務效益：** 使用框架後，代表性任務的正確率、完成時間、返工量與成本是否改善。

### 11.2 建議的最小比較實驗
- **A 組：** 人工直接把外部工具加入現有工具清單。
- **B 組：** AI 依候選框架逆向分析、建立能力規格和關係紀錄，再選擇整合方式。
- **C 組：** 同一流程，但增加獨立驗證、版本鎖定和受控發布。

使用同一組 3–5 項能力來源及同一批任務，以相同接受條件測量；加入一個衝突來源、一個外部依賴工具、一個來源不完整的案例。由不知道組別的審核者判斷抽取與整合結果，並保留失敗案例。若 B 比 A 更易維護但錯誤率增加，或 C 的治理成本超出節省，這些都必須如實計入結果。

首輪實驗應小而可區分，目標是發現最基本的失效機制，不是宣稱框架已經全面通用。

## 4. 初步裁決

### 可以暫時保留的方向
- 用能力而非工具名稱作為長期管理單位。
- 分開來源、能力規格、具體實作、工作流、證據和治理狀態。
- 對重疊和差異進行分析，不因重疊就直接刪除。
- 模型與工具透過適配層替換，重要更新先測試、再發布。
- 蒸餾可重用原則，同時保留來源、未知、證據和版本資訊。
- 讓能力能夠拒絕納入、隔離、降級、退場和回退。

### 必須修改或撤回的絕對化主張
- 「整合後不會有衝突」：撤回。目標應為衝突可發現、可分類、可隔離及可裁決。
- 「AI 擅長拆解，因此可完成逆向融合」：修改。AI 是候選分析引擎；品質須以外部證據、執行結果和獨立驗收判定。
- 「能力標準化後就能直接插拔」：撤回。只有契約相容、狀態相容、權限與副作用受控、且通過驗收後才可替換。
- 「持續蒸餾會令系統自然越來越好」：撤回。只有在測量任務效果且維護成本受控時，才能證明演化有益。
- 「模型更新只需更換插頭」：修改。介接可插拔，行為仍要重驗；核心契約應保持穩定，但能力品質可能改變。

### 目前仍未知
- P2 各功能在最新 HEAD 的真實測試結果。
- 外部工具雷達能否由候選發現延伸到來源核驗、原理分析、關係辨識和能力採用的完整端到端流程。
- 關係圖在規模擴大後的實際成本。
- 多模型／多工具環境下的實際更新半徑、回歸率與恢復成功率。
- 能力目錄長期累積後，是否能降低任務成本，而非製造更多管理開銷。

因此，本文只把框架重整到可討論、可反證、可實驗的程度，不宣告其正確性已被證明。

## 6. 後續順序與決策邊界

1. 先以本文作新的研究紀錄和逆向批判基線；不要立即修改 P2、P1 或把本文視為正式權威藍圖。
2. 若要繼續研究，優先把 CRIT-01 至 CRIT-05 與 RT-01 至 RT-05 轉成小型可執行試驗，因為它們直接測試核心假設與循環驗證問題。
3. 之後才用 3–5 種實際來源完成一條縱向閉環：來源核驗 → 能力抽取 → 關係判斷 → 採用裁決 → 隔離測試 → 發布／回退。
4. 收集真實結果後，再決定哪些候選原則值得融入現有架構；需明確標出保留、修正、替換、延後、拒絕和待驗證項。
5. 若要正式更新企劃或既有 v0.2 提案，需另行提出新舊差異與受影響文件，取得明確授權後再整合；本文建立本身不構成該授權。

**最終研究判斷：** P2 的方向值得實驗，但成立與否不取決於 AI 能否寫出一份完整框架，而取決於系統能否在來源不完整、方法互相矛盾、模型更換、工具出錯和更新中斷等反例下，仍維持可追溯、可驗證、可回退且具實際效益的能力演進。
