- 唯一責任：設計長期知識庫與短期研究工作區的資料分流、結案、退場及驗收方式。
- 既有規範：[文件生命週期與退場藍圖 v0.2](./forAVAr_文件生命週期中斷恢復與退場藍圖_v0.2.md)、[去重與蒸餾規範](../去重與蒸餾規範.md)、[版本治理與分流規範](../版本治理與分流規範.md)。
- 事件依據：[EVT-0056 刪除與退場流程紀錄](../追溯事件/EVT-0056_GitHub文件刪除失效分析與退場流程修正.md)。

## 摘要

根因不是刪除操作不夠多，而是短期原始資料與長期知識曾進入同一 Git 歷史。一般刪除只移除目前分支中的路徑，不會自動清除舊提交、Blob、外部複本或快取。

候選解法是「主儲存庫保存可長期重用的知識與治理文件；每個有明確結案邊界的研究批次，使用獨立、私人、可拋棄的暫存儲存庫」。結案時先蒸餾與驗收，再刪除整個暫存儲存庫。這降低主儲存庫歷史膨脹，不等同承諾資料立即永久抹除。

本文件是新提案紀錄，不修改既有正式企劃、不把候選方案標成已採納，也沒有在本輪向 forAVArb 寫入內容。

## 1. 現況證據與根因

1. forAVAr 目前有退場藍圖、去重蒸餾、版本治理、問題清單與 SOP；主要缺口不是缺少另一份刪除 SOP，而是長期儲存庫的資料准入邊界不足。
2. 56 個專題檔案已從 forAVAr 的目前分支移除，但刪除前的提交仍在目前分支歷史祖先鏈中，且舊 Blob 曾被直接讀取成功。狀態因此是目前分支移除已驗證、歷史清除未完成。
3. Git 的提交歷史是版本追蹤機制。刪除路徑會新增提交，而不是消除原先引入資料的提交；一般 Git 垃圾回收也會保留仍由分支、標籤、reflog 或其他引用到達的物件。
4. GitHub 官方說明：歷史改寫需以適當工具重寫並重新推送；舊 clone、fork、PR 及 SHA 快取可能仍持有資料。刪除儲存庫後，部分儲存庫可在 90 天內復原，因此「刪除專案」也不等於保證立即不可恢復。
5. 已查得 forAVArb 的 repository metadata 為 private、預設分支 main、回報 size=0。這支持將其規劃為首個暫存工作區；本提案未將任何研究原始材料上傳至該庫。

## 2. 目標與不承諾事項

### 目標

- 避免短期原始資料、解析副本、龐大中間檔及暫存輸出進入 forAVAr 長期 Git 歷史。
- 只把經過驗收、可跨題重用的根因屬性、控制方法、限制和必要參考寫入 forAVAr。
- 讓每批任務有明確的開始、結案條件、退場檢查及可查狀態。
- 不複製新的問題清單、SOP 登錄或平行索引；重用既有 PR／CF／SOP 與唯一權威文件。

### 不承諾

- 不宣稱刪除 GitHub 儲存庫會立刻回收所有伺服器空間。
- 不宣稱刪除儲存庫會抹除使用者曾建立的下載副本、外部複本或所有平台快取。
- 不把本文件視為已授權歷史改寫、正式企劃更新或自動化實作。
- 不在主儲存庫保留為了證明清除而必須保存的完整專題內容；驗收痕跡只保留必要、最小且已去識別的狀態資料。

## 3. 新舊方案比較

| 面向 | 舊方式：原始資料直接進 forAVAr 後刪除 | 候選方式：獨立暫存儲存庫 |
|---|---|---|
| 主儲存庫歷史 | 每輪新增與刪除都可能留下歷史 | 原始資料的提交歷史不進主儲存庫 |
| 結案刪除範圍 | 逐檔刪除，容易漏路徑；舊 Blob 仍可讀 | 以整個短期儲存庫為退場單位 |
| 操作成本 | 初期低，事後追查／歷史清除成本高 | 每批需管理儲存庫與結案步驟，範圍清楚 |
| 主庫風險 | 原始專題與通用知識易混合 | 知識要跨庫搬移，須防止誤拷原始材料 |
| 永久清除保證 | 不成立 | 仍不成立；刪庫有復原窗口及外部副本限制 |
| 適用性 | 正式規範、長期知識 | 有結案邊界的原始資料、解析副本、暫存研究 |

候選方案主要改善「主庫長期歷史不再持續接收暫存資料」，不應誤稱已解決所有資料永久清除問題。

## 4. 資料分層與唯一責任

### A. forAVAr：長期知識與治理主庫

允許保存：
- 通用根因屬性、可重用方法、跨題成立的控制及其適用限制。
- 正式文件、唯一權威規範、問題／流程／SOP 登錄與必要索引。
- 已去識別、最小化的退場狀態與方法驗收結果。
- 在必要且有授權下保留的來源索引或引用；不得因此複製整份原始專題資料。

預設禁止：
- 尚未蒸餾的整批原始研究材料與專題證據包。
- 可由來源重新產生的解析副本、暫存 JSON、重複全文、失敗後的多份中間輸出。
- 為了留「刪除證明」而保留大量已退出專題的原始細節。

### B. forAVArb：第一個暫存工作區

- 定位：一個有明確範圍與結案條件的暫存工作區；「備用」名稱不代表它是永久備份庫。
- 預設私人；只放當前批次實際需要的原始資料、解析副本、工作草稿及必要證據。
- 不把 forAVAr 主庫整庫複製過來，不把 P1／P2 唯讀參照內容複製成另一份副本。
- 每批只保留一份 canonical 原始來源與一份必要的工作輸出；版本差異留在暫存專案自身歷史，避免檔案多份重複。
- forAVArb 已存在，建議作為第一個批次工作區；它結案後刪除。之後的批次使用新的唯一專案名稱，不重新使用同一個持續累積歷史的暫存庫。可按「有結案邊界的批次」切分，不按每則對話切分。

### B.1 暫存儲存庫最小結構

不預先建立大量空資料夾或模板檔；只在實際需要時建立，避免工作區本身也變成管理負擔。建議根目錄以一份 README 為入口，其餘按需採用以下分類：

- 來源：使用者提供的原始檔與來源定位；原件不覆寫。
- 處理：解析副本、暫存中間結果；可重建內容不複製多份。
- 分析：主張、證據、反證、衝突與未知分開標記。
- 候選蒸餾：只放準備提交主庫的通用化候選，不放完整個案敘事。
- 驗收：資料數量對帳、主庫寫入後的讀回結果、未完成事項與退場狀態。

README 最低欄位：批次 ID、目標與範圍、允許來源、必交成果、禁止寫入主庫的內容、當前階段、結案條件、阻塞及下一步。若某類資料不存在，不必建立空目錄或空文件。不要把整個 forAVAr 主庫複製進暫存庫。

### C. 不保留／應於結案清除的資料

只有在確認未被重要結論、未解研究、驗收、恢復或法定保留要求依賴後，才可退場。禁止為了「看起來乾淨」刪除唯一來源、獨有證據、反例或必要的未解事項。

## 5. 研究批次生命週期

CREATED → INGESTING → ANALYZING → DISTILLING → ACCEPTANCE_PENDING → CLOSED → DELETED_FROM_GITHUB

- **CREATED**：批次 ID、任務目標、允許來源、預定輸出、禁止輸出及結案條件明確。
- **INGESTING**：原始材料只進暫存庫；記錄來源、格式、數量及必要的完整性指紋。
- **ANALYZING**：保留原始證據與分析推論分層；不得把假說寫成事實。
- **DISTILLING**：檢查 forAVAr 是否已有相同責任文件；優先補證據、修正、接線或融合，只有證明無法重用時才提出新候選。
- **ACCEPTANCE_PENDING**：核對必交輸出、證據邊界、反例、未知、索引、引用及未完事項；主庫寫入後必須回讀。
- **CLOSED**：結論已驗收、通用知識已歸位、所有未完成事項已決定保留位置或標示阻塞，且沒有依賴仍只存在於暫存庫。
- **DELETED_FROM_GITHUB**：確認儲存庫刪除操作成功。這只是 GitHub 專案層級退場狀態，不代表所有副本／快取已永久消失。

任一階段遇到權限、來源完整性、未完成工作或唯一證據問題，改為 RETIREMENT_BLOCKED；不可為了達成清除指標而跳過驗收。

## 6. 結案閘門

刪除前必須逐項核對：
1. 原始資料項目總數＝已分析＋明確未分析／阻塞；不得有不明差額。
2. 蒸餾結果已寫入指定 forAVAr 權威文件，並讀回確認內容正確。
3. 索引與必要引用可定位；沒有仍待執行的任務依賴暫存庫。
4. 唯一證據與不可重建資訊的保留決策已完成；使用者要求完全不留專題紀錄時，不另留可識別個案的細節。
5. 已區分三個結果：主庫沒有原始材料、暫存儲存庫已刪除、永久歷史／平台層清除是否驗證。前兩項不得冒充第三項。
6. 記錄最小驗收狀態即可：批次代碼、數量、結案日期、狀態、主庫回讀結果與未能保證的範圍。避免保存原始路徑、案件名稱或完整內容，除非稽核需要且得到授權。

## 7. 命名、批次與防膨脹

- 每個暫存儲存庫對應一個「有完整結案邊界的工作批次」，不是一則對話，也不是長期存放所有舊材料的總庫。
- 名稱使用不含個案敏感資訊的序號與日期，例如 forAVArb-20261023-001；現有 forAVArb 作為第一批，不改名、不刪除，直到結案閘門全部通過。
- 已刪除的儲存庫可能有復原窗口，因此不要假設刪除後立刻能重用同名。後續名稱用新序號。
- 以「主庫是否新增不必要原始資料」「每批是否按期結案」「結案殘留是否可說明」作為指標；不把儲存庫數量愈少當唯一目標。
- 不新增永久性的完整案件清冊或第二套資料庫來記錄所有已刪批次。若需要運行追蹤，沿用既有 SOP 執行台帳與退場事件唯一責任，且僅記最小必要資訊。

## 8. 遷移與驗收階段

### 第 0 階段：目前狀態
已建立 forAVArb；metadata 顯示 private、預設分支 main、size=0。尚未向此庫寫入任何材料；應先把它定位成單批暫存工作區，而非保留式備份。

### 第 1 階段：候選流程桌上推演
選一個低風險、有限批次演練正常路徑、資料項目差額、主庫回讀失敗、未解事項、刪庫遭拒與誤刪恢復。這只是模擬，不能標實際驗證通過。

### 第 2 階段：單批試行
在授權後，以一個具結案邊界的批次操作；逐項量測資料總數、主庫新增量、引用核對、操作步數、失敗／返工與結案後殘留。未完成的範圍標 PARTIAL。

### 第 3 階段：獨立批次回歸
在另一個不同輸入／批次再次執行。若只是同一案例重跑，不足以證明跨情境可用。

### 第 4 階段：裁定是否整合正式規範
只有試行證據顯示主庫原始材料增量下降、結案漏失沒有惡化、蒸餾與回讀可靠、操作成本可接受，才提出修改現有退場藍圖／SOP 的版本比較。不因提案寫完就提升為 CURRENT。

## 10. 未決問題與風險

- GitHub 刪庫與後端物件回收的確切完成時間不能由一般操作直接觀測。
- 刪除後的復原期限、快取、外部複本並非本提案可控制範圍；真正涉及敏感資訊時須採獨立風險處理。
- 暫存庫操作會增加批次命名和結案管理成本；須透過單批及另一個獨立批次試行，確認成本低於主庫持續累積與清理的總成本。
- forAVArb 的 metadata 並不證明所有平台端備份已經不存在；此提案也未進行平台儲存層驗證。
- 目前是候選設計，未修改正式退場藍圖、現行 SOP 或能力登錄；正式整合仍需明確的「更新企劃」授權與前後方案比較。

## 外部依據的設計解讀

1. GitHub 官方「Removing sensitive data from a repository」：一般刪除不等於歷史清除；歷史改寫會改變提交識別並有重新污染、分支與複本風險。  
   https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository
2. GitHub 官方「Deleting a repository」：部分刪除的 repository 可在 90 天內恢復；刪庫的後果與歷史內容的普遍永久抹除不是同一個承諾。  
   https://docs.github.com/en/repositories/creating-and-managing-repositories/deleting-a-repository
3. Git 官方「git-gc」：一般垃圾回收會保留仍由 refs、reflogs 等引用的物件，不應期待它替主動刪除的歷史資料提供完整清除保證。  
   https://git-scm.com/docs/git-gc
