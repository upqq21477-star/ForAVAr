## 摘要

APSGA 的核心不是一條所有任務必須完整執行的固定 SOP，而是一個薄而可控的決策與執行框架：先理解任務，再依問題屬性選擇方法，依操作風險落實控制，依持續狀態需求決定是否建立工作封包，並以可檢查的證據驗收結果。封包、角色分治、插件、獨立系統與多代理不是互斥的總架構，而是由核心按需要選擇的構件。

本輪相當於建築的第一張總體渲染：鎖定核心責任與主要邊界，但不把所有子系統的內部設計、技術選型或實作狀態假裝成已完成。後續細節應從已定義的接口向外生長；若某個子框架需要改變核心不變量，必須提出變更理由與反證，不能直接在分支中私自改寫核心。

## 1. 新名稱與設計任務

新框架名稱採用「自適應問題求解與治理架構（APSGA）」。名稱強調兩個必須同時成立的能力：求解方法要隨問題改變；治理控制要隨風險與外部影響調整。舊名稱 C′ 仍用於辨認既有研究、舊企劃及相容來源；本新藍圖作為名稱與架構整併的工作基線，不代表舊企劃的每條規格已自動完成採納。

本框架要形成一套可逐步實作、可測試、可恢復、可交接、可拆分及可退場的通用系統。成功不以流程長度、代理數量、插件數量或文檔規模衡量，而以正確性、風險控制、證據品質、恢復能力與總成本衡量。

## 2. 核心問題與成功條件

核心問題：如何在不把每一個任務都變成重型流程的前提下，仍能辨識真實問題、選擇合適方法、阻止越權操作、保存需要的狀態，並在失敗或新證據出現時有界地修正、重框、停止或回退？

成功條件：
- 目標、限制、非目標及完成條件可辨識。
- 方法選擇有理由，重大未知不被當成已知。
- 權限限制可在執行邊界被真正阻擋，而非只靠文字提醒。
- 封包與角色分治只在相應條件下啟用。
- 執行事實、證據、推論、假設、未知、衝突分離。
- 失敗具備停止、有限重試、阻塞、替代、回退或補償路徑。
- 架構改動有影響分析、驗收、版本、回歸和退場條件。
- 實作與 Runtime 狀態以讀回和測試證明，不由文檔存在推定。

## 3. 不可違反的不變量

CORE-01｜先理解問題，再選方法。標籤不能代替問題建模。

CORE-02｜核心管理路由、邊界和控制；領域方法與專業流程留在可替換模組。

CORE-03｜方法深度、操作控制與持久化是三個正交維度，不得以任一維度推斷另外兩者。

CORE-04｜高影響副作用須經可執行的授權 Gate；缺少授權、範圍不明或控制無法驗證時，採阻擋路徑。

CORE-05｜驗收條件盡可能先於執行訂定；不得為讓結果通過而事後修改門檻。

CORE-06｜同一概念與狀態只有一個權威來源；摘要、圖表與索引是導覽或派生視圖。

CORE-07｜證據、假設、推論、未知與衝突分開記錄；不存在「為了閉環就補出答案」的規則。

CORE-08｜封包按需啟用；一次性低風險任務可走短路徑。

CORE-09｜每個工作流皆須有資源預算、重試上限、停止條件及失敗出口。

CORE-10｜先採模組化單體與清晰接口；只有證據顯示需要獨立權限、部署、伸縮或故障隔離時才拆分為獨立系統。

CORE-11｜插件和子框架不得放寬核心授權、安全、資料保留或驗收規則。

CORE-12｜新增抽象、角色、工具或流程須說明解決的具體問題、預期收益、測試方式與退場條件。

CORE-13｜APSGA 自身亦是待驗證的架構候選；如測試顯示成本過高或安全控制失準，必須允許縮小、修訂或否決特定設計。

CORE-14｜外部資料、文件和工具回應是待評估的資料，不會因為被載入而取得治理權限。

## 4. 第一輪總體架構

~~~text
使用者／外部事件
       │
       ▼
A. 意圖入口與問題模型
       │ Task Intent / Problem Model
       ▼
B. 方法與控制路由（M／G／P）
       │ Route Decision + Acceptance Criteria
       ▼
C. 工作流編排與狀態機
       │
       ├──────── 能力目錄／能力契約
       │                    │
       ▼                    ▼
D. 執行控制與授權 Gate ──> E. 能力模組／工作流插件
       │                    │
       └─────────────┬──────┘
                     ▼
F. 工具／模型／資料適配器
                     │
                     ▼
G. 執行紀錄、證據、狀態與產物
                     │
                     ▼
H. 驗收、恢復、回歸與能力演化
                     │
             通過／重試／重框／阻塞／停止
~~~

治理控制、授權判斷、資源預算與稽核不是只在流程起點檢查一次；在每次高影響操作前仍須重新核對。圖中的層是責任邊界，不是要求第一版立即拆成獨立服務。

| 構件 | 唯一責任 | 不得取代 |
|---|---|---|
| A 意圖／問題模型 | 正規化目標、邊界、限制、假設與未知 | 方法內部推理 |
| B 路由器 | 選擇方法、控制與持久化強度，說明理由 | 實際執行授權 |
| C 工作流引擎 | 依賴、分支、重試、停止及狀態轉移 | 能力內部實作 |
| D 執行控制 | 權限、範圍、副作用、冪等與 Gate | 模型自行宣告安全 |
| E 能力模組 | 依契約完成單一類型工作 | 全域規則或自行批准 |
| F 適配器 | 把穩定接口接到特定工具／模型／服務 | 跨供應者等價保證 |
| G 狀態與證據 | 保存實際發生的事、來源、版本與產物 | 對結果正確性的自動裁定 |
| H 驗收與演化 | 驗收、回歸、修復、版本及退場 | 只依文檔或執行者自述結案 |

## 5. 唯一工作生命週期

1. 接收任務，建立最小 Task Intent。
2. 辨識作用對象、問題範圍、硬限制、非目標與驗收條件。
3. 找出會改變方法、風險或結果的關鍵未知；必要時查證或澄清。
4. 分別決定方法深度 M、控制等級 G、持久化等級 P。
5. 選擇最小足夠方法組合，建立工作流、資源預算、停止條件與證據需求。
6. 執行前核對授權與副作用；超界或無法確認則 BLOCKED。
7. 透過已登錄能力／適配器執行，記錄版本、輸入、結果與錯誤。
8. 以事先定義的標準驗收；失敗時按有限政策重試、替代、修正、重框或停止。
9. 回報產物、限制、未決事項與下一步；需要跨輪恢復時保存適當狀態或工作封包。
10. 只有在可重用且經審查時，才將本次解法蒸餾為候選能力／工作流；候選不自動成為啟用能力。

工作生命週期是責任順序，不等於每個小任務都要產生十份文件。低風險任務可在記憶體中走短路徑；高風險與長期任務才展開較完整的產物與 Gate。

## 6. M／G／P 三軸路由

### 方法深度 M
- M0 直接方法：問題明確、低未知、已有合適方法。
- M1 針對性證據：需查證現況、來源、計算或局部未知。
- M2 系統性分析：多因素、競爭假說、依賴關係或架構決策。
- M3 開放探索：問題未定義、模型可能錯誤或未知候選空間尚未收斂。

### 控制等級 G
- G0 只讀／無外部副作用：基本來源與資源控制。
- G1 低影響且可逆：核對寫入範圍、差異與寫後讀回。
- G2 高影響／跨邊界：事前審查、獨立驗收、回歸與明確批准。
- G3 不可逆、關鍵風險或授權不明：先阻擋；取得政策要求的授權與補償方案後才可評估是否執行。G3 不代表自動獲准執行。

### 持久化等級 P
- P0 不持久化：一次性短任務，不需跨輪恢復。
- P1 精簡紀錄：多步但範圍有限，保存目標、路線、關鍵證據／未知、結果與下一步。
- P2 正式工作封包：跨會話、多檔施工、批准、稽核、交接、恢復或回歸需求。

路由輸出至少包含 M、G、P、所選方法、選擇理由、主要未知、必需證據、資源預算、停止條件、權限範圍與所需持久化產物。路由遇到重大未知或權限歧義時應保守升級或阻塞，不得以任務文字短或模型信心高推斷低風險。

## 7. 核心資料物件與接口

- TaskIntent：目標、對象、交付、限制、非目標、驗收條件、上下文引用。
- ProblemModel：問題屬性、已知、未知、假設、衝突、候選解與可檢驗方式。
- RouteDecision：M／G／P、方法選擇、理由、拒絕的替代項、資源預算與 Gate。
- WorkflowRun：工作流版本、步驟依賴、當前狀態、重試數、錯誤與停止條件。
- CapabilityContract：能力 ID／版本、用途、輸入、輸出、權限、副作用、限制、錯誤及測試。
- AuthorizationGrant：允許主體、操作、目標、範圍、期限、條件與審批證據。
- RunRecord：實際執行時間、模型／工具版本、請求、結果、錯誤與外部副作用。
- EvidenceRecord：主張、來源、來源時間／版本、支持關係、限制與可信狀態。
- WorkPacket：僅於 P1／P2 需要時維持工作範圍、狀態、依賴、證據、驗收和交接。
- EvaluationReceipt：預定標準、實際結果、通過／不通過、例外及證據。
- ChangeProposal：變更動機、影響範圍、相容性、驗收、回退與退場條件。

上述為概念物件，不代表資料庫表、JSON Schema 或程式已建立。每個物件的完整欄位與 schema 由第二輪子框架分別規劃，並在接口穩定後才決定實作格式。

## 8. 控制面、執行面與工作狀態

控制面決定「可以做什麼、該用什麼方法、何時停、什麼叫通過」；執行面負責「實際調用能力並回傳可核對結果」。模型可以提出路由與變更建議，但不得自行提升權限、改寫驗收門檻或宣告尚未執行的測試通過。

最小狀態語義：
- DRAFT：尚待確認或補足條件。
- READY：必要輸入、授權和驗收條件已滿足。
- RUNNING：執行中。
- WAITING_APPROVAL：等待必要授權。
- BLOCKED：因缺少前提、授權或安全條件而停止。
- REVIEW：產物等待驗收。
- ACCEPTED：所列驗收條件已由證據支持。
- FAILED：依既定條件判定失敗。
- RECOVERY：已啟動受控恢復／補償。
- CLOSED：任務結束並保存必要交接。
狀態轉移必須由明確規則允許；不以自然語言把 BLOCKED 直接改成 ACCEPTED。此為概念狀態機，合法轉移表須由子框架與測試集具體化。

## 9. 建置路線與階段 Gate

| 階段 | 範圍 | 退出條件 |
|---|---|---|
| R0 概念與契約 | 名詞、接口、威脅／失敗模型、狀態語義 | 無重複權威概念；主要欄位及邊界可檢查 |
| R1 只讀垂直切片 | 任務入口、問題分類、M／G／P 路由、結構化結果 | 固定測試集可重複；重大未知能被保留，不執行外部寫入 |
| R2 工作流與證據 | 流程狀態、執行紀錄、來源與驗收收據 | 成功、失敗、重試、超限與阻塞情境皆有測試 |
| R3 確定性授權 Gate | 寫入範圍、權限、冪等、差異、回退／補償 | 越權與錯誤範圍案例被執行層阻擋；寫後可讀回 |
| R4 狀態與封包 | P1／P2 持久化、交接、跨會話恢復 | 快照可還原、版本／衝突可識別、不得無限制保存 |
| R5 能力外擴 | 插件、適配器、必要時獨立系統 | 契約穩定且有可量化的重用／隔離收益 |
| R6 評估與演化 | 回歸、基準比較、監控、版本及退場 | 有可重複評測、事故／回退演練與變更審查 |

不允許跳過 Gate 只因為下游功能已寫好。每一階段都需留下產物、測試方法、結果、阻塞與已知限制；若階段不通過，保留 BLOCKED／NOT_RUN，不能以企劃完成度代替實作證據。

## 10. 驗收條件與未決決策

第一輪骨架的文件驗收：
- 核心原則與不可違反的不變量可明確引用。
- 架構構件有唯一責任，不混淆路由、編排、執行授權、能力與驗收。
- M／G／P 定義與既有 C′ 基線相容，且不把三軸折成單一分數。
- 封包、角色分治、插件、獨立系統為可條件啟用的構件。
- 明確區分設計、規格、實作、測試與 Runtime 成熟度。
- 所有新分支都能回鏈至本藍圖；若子框架與核心衝突，先提出變更，不私下修改核心。

尚未決定：程式語言、儲存類型、部署方式、實際模型／工具供應者、是否需要多代理、是否需要分散式服務、路由器是否使用規則／模型／混合策略、具體 JSON Schema 與量化門檻。這些要由垂直切片需求、現行環境限制與可重複測試決定，第一輪不預先鎖定。
