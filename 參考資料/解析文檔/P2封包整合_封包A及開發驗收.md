## 6. 封包 A HANDOFF 的工程治理分支

以下只記錄 HANDOFF（2026-10-16）所述內容；由於原 ZIP 位元組不可讀取，除非有其他直接來源佐證，不得將其當成最新施工狀態。

### 6.1 當時宣稱的發現

HANDOFF 聲稱本次對 182 個模組做過靜態掃描，發現 15 個無引用／無測試模組、多套階段／閉環骨架、重疊工具與常設規則被手抄成本場條件；並描述 canonical_json、content_hash、原子寫入等共用工具的使用情況。這些數字與判讀只記為 HANDOFF_CLAIM，不當成已重做的掃描結果。

### 6.2 W0–W8 歷史工作批次

| 批次 | HANDOFF 所述主旨 | 在本整合文件中的定位 |
|---|---|---|
| W0 | 完成剩餘功能重疊組閱讀與判定 | 盤點／研究工作，不是常設生命週期 |
| W1 | 把固定規則轉成可防再發的檢查 | 工程治理與程式 Gate |
| W2 | F30 四階段通用化 | 工程成熟度軸 |
| W3 | 收斂 PLANNING 出口 | 規劃流程與出口契約 |
| W4 | 合併兩套八步閉環 | 消除重複流程的整併工作 |
| W5 | 接上進件與執行流程 | 系統接線工作 |
| W6 | 實際整體運行（HANDOFF 指向 R9） | 真實 Runtime 驗證，不可用模擬代替 |
| W7 | 常設規則改由單一來源產生 | 單一權威資料治理 |
| W8 | 合併小工具 | 工具重用；合併前需比對輸出、錯誤與呼叫契約 |

HANDOFF 另列退場機制補強、預算對齊、孤兒 Schema 登錄、progress/ 讀取者盤點、docs/plans 合併、S7 收口及 R9 等任務。它們是那場交接快照的工作清單；真正開發前應回到取得後的 ZIP、最新 Current 及源碼核實是否仍存在或已完成。

### 6.3 單場操作規則快照

- 當時建議的單場預算為讀取不超過 48 KB、寫入不超過 36 KB、呼叫不超過 30 次；任一達 70% 時停止開新工作，開始收尾。
- 工作單元應有界；先讀必要輸入和切片，不因文件很大就一次載入整份。
- 新建前記錄 REUSE / MODIFY / MERGE / NEW；NEW 必須說明現有候選為何不能重用。
- 只在有實跑時宣稱程式實際通過。模擬標 SIMULATED_PASS；假說標 HYPOTHESIS；沒有證據標 NOT_EXECUTED。
- HANDOFF 所列的權威路徑與保護規則屬來源專案的場次規則；不得自動套用到其他 repo 或視為本專案可修改清單。

## 7. 後續開發的融合路徑

本路徑是給後續開發者的建議順序，不表示已在 P2 執行。每階段都先核對權威來源與允許修改範圍。

### D0｜先解封包 A，建立完整來源基線

1. 取得原始 ZIP bytes，核對登錄大小、裸檔 SHA-256、ZIP／Zip64 中央目錄與 EOCD。
2. 建立逐成員 manifest：來源路徑、壓縮／解壓大小、方法、CRC32、格式、狀態、解析文件位置。
3. 按現有八個分類目錄歸檔，但一個成員只能有一個 canonical 位置；其他交叉用途用索引引用。
4. 把 HANDOFF 的每個數字／主張逐項對到實際源碼、呼叫鏈、測試和執行證據。若不可驗，保留 UNKNOWN。

### D1｜凍結概念契約，不直接改程式

1. 將 H0–H2 作為候選簡單主線，確認 H3 分支的必要性和分支記錄方式。
2. 把「流程步驟、封包類型、角色、封包狀態、證據標籤、F30 成熟度」分成獨立欄位或視圖，避免混軸。
3. 定義每個功能的最低條件契約：主要位置、觸發條件、必需輸入、禁止條件、授權／成本 Gate、輸出、接受條件、下一步／失敗回退。
4. 把現有 Task／Result／Execution／Current／Schema 的欄位對齊後才決定是否需要擴充；不直接建立第二份封包真相。

### D2｜建立能力／模組／測試的映射

以 F01–F30 作功能層索引，以實際模組／入口／呼叫鏈作實作層索引，以測試／執行輸出作驗證層索引。三者以穩定 ID 連接，但數量不要求一對一。對「無引用／無測試」模組先查動態呼叫、注入、CLI、配置、反射、外部入口與測試漏失，再裁定重用／接線／合併／退場，不得只依靜態 grep 結果刪除。

### D3｜用小範圍端到端案例驗證閉環

至少包含以下測試案例：

- 正常路徑：前置條件成立 → READY → RUNNING → 結果與證據 → PASS → 合法 next。
- 輸入缺失：不可直接 RUNNING；補資料或 BLOCKED。
- 權限／成本／安全不成立：硬性 Gate 阻止調用。
- 功能觸發不成立：不調用，不因能力存在而強制經過。
- 施工失敗：FAIL，保留錯誤結果與根因候選，不得改寫成 PASS。
- 中斷／重試：能辨識已完成與未完成部分，避免重複副作用。
- 驗收失敗：回到實際問題所在的上游節點，不放寬原接受條件。
- 獨立驗收：Executor 不可自行批准自己的結果。
- 資料退場：有依賴／證據保留需求者不得刪除；可安全清除的暫存才退出。
- Runtime：真實執行證據獨立記錄；模擬結果不得升級。

### D4｜用量測決定是否推廣

簡化前後至少比較：重複功能定義數、錯誤調用率、無效工具調用、上下文／讀取量、交接缺失、狀態漂移、失敗後返工次數、全案閉環成功率。沒有實測數據則標 UNMEASURED，不憑直覺宣稱新模型效率更高。

## 8. 開發驗收閘門

未來任何實作若要採用這份整合概念，應逐項通過以下檢查；此清單是建議驗收條件，不是既有 P2 測試已通過的宣告。

- [ ] 每個正式功能只有一個 canonical 定義與一個主要流程歸屬。
- [ ] 其他節點以 ID／封包引用使用該功能，不複製第二份真相。
- [ ] H0–H2 足夠簡單；只有真實選擇點才展開 H3+。
- [ ] 封包契約涵蓋目標、必要輸入與來源、條件／權限／資源、允許動作、輸出、接受條件、證據、狀態與 next／回退。
- [ ] 硬性條件由確定性檢查器優先驗證；語意判斷不能覆蓋權限／成本／安全限制。
- [ ] WAITING / READY / RUNNING / PASS / FAIL / BLOCKED 與證據標籤、工程成熟度分離；正式狀態需先與既有 Schema 對帳。
- [ ] FAIL 和 BLOCKED 可區分；不能跳過條件直接成功，不能無限重試。
- [ ] Executor／施工者不能自行驗收；Verifier／Assurance 使用預先定義的接受條件與獨立證據。
- [ ] 單封包 PASS 與全案結案分開；全案要有最終驗收、Current 更新和退場判定。
- [ ] Current／程式藍圖／功能矩陣的權威所有權清楚，視圖由來源派生。
- [ ] 測試覆蓋正常、負例、邊界、中斷、重試、權限／成本、驗收失敗與資料生命週期。
- [ ] 模擬、靜態、實際測試、整批驗收與 Runtime 證據標記不混用。
- [ ] 新增功能前有 REUSE／MODIFY／MERGE／NEW 比較；孤兒模組不因無引用／無測試而直接刪除。
- [ ] 結案只保留必要結果、證據與下一步上下文；暫存資料安全退場並可追溯。
