## 1. 核心目的

這份矩陣解決「不同文件談到相似概念，但用途、權威層級和可支持的結論不同」的重複問題。後續解析前先查本表；相同概念只補差異與新證據，不整份複製已知結論。

| 封包 A 解壓分類索引 | 定義封包 A 解壓後各類檔案的唯一歸檔位置 | 每類文件應放置的位置及歸檔規則 | 不證明分類骨架內已有 ZIP 成員 | 只保留分類規則；實際內容按成員清冊歸檔 |
| 封包 B 系統性重點整理 | 蒸餾封包 B 的核心提案、已通過結構驗收及殘留差異 | 核心設計主張、驗收狀態及待裁定問題 | 全文語意完全一致、企劃書已獲 P2 採納 | 只留結論與證據邊界；詳細差異回指專屬稽核 |

<a id="section-3"></a>
## 3. 明確的重疊群組與處理決策

### DUP-001／DUP-002：Markdown 與 DOCX 配對

- **重疊原因：** 同一標題／主題各有 Markdown 及 Word 格式。
- **驗收結果：** ZIP 成員與 OOXML 結構通過；標題、379 個表格儲存格和正文有序字元序列比對完成。發現的差異已分類；沒找到未解釋的實質內容缺失。
- **處理：** 原始 ZIP 不刪成員。搜尋／蒸餾以 Markdown 作文字首選，DOCX 保留作版面參照；不宣稱兩格式原始字元逐字完全相同。細節見「封包B雙格式完整性與差異稽核.md」§9.6。

### DUP-003：Claude Code Modernization 詳細報告與蒸餾摘要

- **重疊原因：** 同一外部專案研究有詳細版與濃縮版。
- **處理：** 完整研究為細節首選；蒸餾摘要只保留核心架構、值得借鑑的原則與完整報告的連結。若摘要中有完整研究沒有的唯一事實，先移回完整報告並記錄來源，之後才可精簡摘要。

### DUP-004：封包式流程企劃與 P1／P2 功能骨架映射

- **重疊原因：** 兩者都談 P2 功能及流程結構。
- **本質差異：** 企劃書提出「怎麼用封包跑通一次問題解決」；骨架樹回答「功能原子應歸在哪個位置及如何回查 ID」。
- **處理：** 不合併成一份權威規格；企劃書引用骨架映射，骨架映射只增加交叉連結，不複製整套流程敘述。

### DUP-005：Relay ZIP 與 HANDOFF

- **重疊原因：** 同一工作場次的封包與交接描述相關內容。
- **本質差異：** ZIP 是打包內容；HANDOFF 是人可讀的狀態摘要和下一步指示。
- **處理：** HANDOFF 作為導航和待核主張；封包內容、工具輸出及程式檔才是驗證內部事實的來源。ZIP A 本體尚未讀取，所以其內部內容保持未知。

### DUP-006：外部研究與 P2 設計建議

- **重疊原因：** Claude Code Modernization、WebToApp 可能都提到測試、模組分工、安全或交接。
- **處理：** 先保留外部專案的實際實作事實；可泛化原理集中到單一「可移植原則」索引。不要把兩個外部專案的機制當成 P2 已有功能，也不要因為術語相似就推論同一實作。

<a id="section-4"></a>
## 4. 後續文件新增門檻

在新增解析文件前，必須先回答：

1. 新文件的唯一責任是什麼，現有哪份文件不能承載？
2. 它會新增哪些可驗證事實，而非再次講述相同原理？
3. 它的來源檔案與版本是什麼？
4. 哪些現有段落只需要引用，哪些內容真的需要新增？
5. 哪些內容仍是 UNKNOWN／INFERRED／HANDOFF_CLAIM？

若只新增同一結論或同一套流程說明，不另建文件；補入既有分析並連回新證據。若確有新主題，先登記本矩陣與總索引，再開始解析。
