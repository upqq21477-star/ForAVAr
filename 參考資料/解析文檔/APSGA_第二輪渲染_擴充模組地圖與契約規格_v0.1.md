## 摘要

第二輪不追求立即完成所有細節，而是把第一輪總體圖轉成一組能分別研究、設計、實作、測試與替換的子框架。每個分支只擁有自己的專業細節，不得複製核心規則或產生第二個權威定義。後續以「選定一個擴充分支 → 建立詳細規格 → 反向檢查接口 → 測試 → 回填狀態」為基本循環。

「外部擴充」指從核心責任邊界向外長出的專門子框架，並不代表一定要部署成外部服務。預設先維持模組化單體；只有獨立部署、隔離、縮放或團隊所有權的收益經證明後，才討論分散式切分。

## 1. 第二輪設計規則

1. 每一分支只有一個唯一責任；共同原則連結核心藍圖，不在各分支複製全文。
2. 每一分支先定輸入、輸出、權限、副作用、錯誤、狀態與驗收，再決定內部演算法或技術。
3. 先做最小接口與垂直切片；不先把所有分支都寫成完整的大文件。
4. 子框架可提出核心變更建議，但不得在自己的分支直接改動核心契約。
5. 每個分支必須保留未知、假設、反例、依賴、測試狀態及退出條件。
6. 文件建立、語意模擬、靜態檢查、單元測試、整合測試、Runtime 測試是不同證據等級。
7. 功能尚未接線或未通過 Gate 前，不得對外宣稱已啟用。
8. 若兩個分支有重疊，先調整唯一責任與接口，不用複製資料解決。
9. 子框架只有在可重用、獨立替換、獨立權限、獨立驗收或維護成本下降其中至少一項成立時，才有必要獨立成檔／模組。
10. 子框架若在實測中沒有收益或造成更多不一致，允許合併、降級、停用或退場。

~~~text
APSGA 核心（薄核心／唯一治理面）
├─ X01 意圖入口與問題建模
├─ X02 方法路由器（M 軸）
├─ X03 風險、權限與執行 Gate（G 軸）
├─ X04 持久化、工作封包與恢復（P 軸）
├─ X05 工作流編排與狀態機
├─ X06 能力目錄、契約與插件組合
├─ X07 模型／工具／資料適配器
├─ X08 證據、來源追溯與狀態紀錄
├─ X09 驗收、回歸與基準比較
├─ X10 錯誤處理、冪等、補償與恢復
├─ X11 版本、文件、交接與能力生命週期治理
└─ X12 成本、觀測性與操作介面（後置候選）
~~~

上述為邏輯模組地圖，非強制的部署拓撲。X01–X05 是第一批核心路徑候選；X06–X11 依垂直切片需要分段建立；X12 在具備真實執行資料後再細化。不得為了讓樹完整而對所有分支同步開工。

## 3. 各子框架責任與接口

| ID／分支 | 唯一責任與必要產物 | 依賴／進入條件 |
|---|---|---|
| X01 意圖入口與問題建模 | TaskIntent、ProblemModel；描述目標、對象、限制、非目標、假設、未知、衝突與可檢驗方式 | 優先；依賴核心名詞 |
| X02 方法路由器 | RouteDecision；依問題屬性挑方法深度、方法組合、必需證據與預算 | X01；延續方法選擇框架，但須定義本系統接口 |
| X03 風險／授權 Gate | AuthorizationGrant、拒絕結果、操作範圍與審批紀錄；能在執行前阻擋越權 | 核心權限邊界先定；寫入能力啟用前必備 |
| X04 持久化／封包 | P0–P2 的保存規則、WorkPacket、快照、交接、保留與刪除 | 先定狀態權威、資料最小化與存取邊界 |
| X05 工作流與狀態機 | WorkflowRun、合法狀態轉移、分支、重試、停止與恢復 | X01–X03；先完成只讀垂直切片 |
| X06 能力目錄／插件 | CapabilityContract、版本、適用條件、依賴、啟用狀態與退場 | 核心接口穩定；每項能力有驗收 |
| X07 適配器 | 將統一接口連接特定模型、工具或服務；保存版本、錯誤及相容性 | X03 的執行限制、X06 的能力契約 |
| X08 證據與追溯 | EvidenceRecord、RunRecord、來源版本、支持關係、未知與衝突 | 與各路徑共用；先訂唯一權威來源 |
| X09 驗收與回歸 | EvaluationReceipt、測試集、基線、失敗分類及回歸決策 | 接受條件先定；連接各分支驗收結果 |
| X10 錯誤與恢復 | 錯誤分類、重試預算、冪等鍵、補償／回退、恢復演練 | 依副作用與狀態機要求選擇 |
| X11 文件與能力治理 | 唯一職責、版本、變更、交接、啟用／降級／棄用／退場流程 | 使用現有 forAVAr 文件治理規則；避免新造重複登錄表 |
| X12 觀測性與介面 | 成本、延遲、失敗率、人工介入、看板／操作介面 | 需有真實執行資料與明確操作需求；不在第一階段優先 |

### 每個分支共通輸入／輸出

共通輸入至少包含：task_id、核心規格版本、呼叫方、授權上下文、相關物件引用、資源預算及適用限制。

共通輸出至少包含：結果狀態、結構化產物引用、使用的版本、執行紀錄、證據／未知、錯誤代碼、是否產生副作用及下一步建議。

上述欄位是接口候選，不能在尚未建立 schema 與測試前當作已實作格式。

## 4. 依賴順序與展開路線

第一批——先穩定最小可用閉環：
1. X01 意圖入口與問題模型。
2. X02 方法路由器，只做路由建議與結構化輸出。
3. X09 的最小驗收標準與固定測試案例。
4. X08 的最低限度執行／證據紀錄。
5. X05 只讀工作流與狀態機。
6. X03 授權 Gate；在通過前不啟用正式寫入能力。

第二批——具備測試與風險控制後：
7. X06 能力目錄與首個端到端能力。
8. X07 一個受限適配器。
9. X10 錯誤、重試、冪等與恢復。
10. X04 P1／P2 持久化及封包恢復。
11. X11 版本與能力生命週期整合。

第三批——有證據才投入：
12. X12 觀測性與操作介面。
13. 多代理、平行工作、獨立系統或分散式部署等候選拓撲。

此排序可因實際障礙調整，但變更時必須記錄依賴原因與新的驗收方式。不得因為已列出模組，就認為各模組必須一口氣開發完成。

## 5. 子框架詳細規格模板

每個分支在進入詳細設計時，使用以下欄位：

1. 分支 ID、名稱、版本、成熟度與唯一責任。
2. 要解決的具體問題、非目標及使用情境。
3. 與核心不變量的關係及不得越過的邊界。
4. 輸入／輸出契約、資料 schema 候選及權威來源。
5. 正常路徑、分支條件、錯誤路徑、停止與恢復。
6. 權限需求、副作用、敏感資料及保留政策。
7. 上游／下游依賴與相容性規則。
8. 可觀測的接受條件、單元／整合／對抗／回歸測試。
9. 資源預算、失效模式、誤判代價及反例。
10. 實作方案與替代方案；尚未決定的技術須標候選。
11. 建置、測試、Runtime 與採用狀態，分開記錄。
12. 版本變更、回退、降級、合併與退場條件。
13. 開放問題、負責文件與雙向索引。

缺少的欄位可以標 UNKNOWN／NOT_DECIDED／NOT_RUN，不得用模糊文字填滿。

## 6. 跨分支契約與相容性

- 核心規則只有一處權威定義；子分支使用連結引用。
- 路由器只能提出 RouteDecision；執行 Gate 才能依實際權限核准或拒絕操作。
- 能力模組不得自行宣告授權，也不得直接把結果寫成 ACCEPTED。
- 執行紀錄描述實際發生的事；EvidenceRecord 描述證據支持哪些主張；EvaluationReceipt 描述是否達到標準，三者不得混為一種紀錄。
- 工作封包保存任務實例狀態，不是能力登錄表，也不是整個系統的永久知識庫。
- 不同模型或工具適配器即使使用相同接口，仍需獨立測試行為差異。
- 任何接口變更要檢查上游呼叫方、下游消費者、持久化資料、測試集及交接文件；不能只更新單一分支。
- 子分支發現核心錯誤時提出 ChangeProposal；核心變更經審查及回歸後才更新主藍圖。

## 7. 第三輪以後的渲染循環

第二輪完成擴充樹後，接下來按分支逐個做第三輪渲染，即把一個子框架展開為可實作規格。每輪固定採用：

選定分支 → 讀取權威基線及關聯問題 → 寫明責任與非目標 → 定義接口 → 展開成功／失敗流程 → 逆向尋找反例與繞過路徑 → 設計驗收 → 檢查依賴及文件引用 → 標示未決 → 寫入獨立分支文件 → 讀回與檢查 → 更新索引／追溯。

每輪輸出要明確分為：
- 已確立：由既有基線或驗收結果支持。
- 候選設計：邏輯完整但尚未測試。
- 待研究：缺少來源、決策或測試資料。
- 被否決／退場：保留原因和替代方案。
- 實作狀態：NOT_STARTED、IN_PROGRESS、BLOCKED、NOT_RUN、PASS 或 FAIL；不得互相代換。

## 8. 擴充驗收與退場

某分支可標為規格完成，需滿足：唯一責任清楚；接口欄位可驗證；主要成功與錯誤分支已列；權限／副作用已分析；接受條件與對應測試可追溯；依賴與回退方式明確；未決事項如實列出。

此狀態只代表「規格完成」，不代表「已實作」或「Runtime 通過」。能力若不再重用、契約無法維持、維護成本高於收益或安全要求無法滿足，應依影響分析合併、降級、停用或退場。退場時保留歷史證據並更新現行索引，避免舊文件仍被誤用為啟用能力。

## 9. 尚未決定的接口事項

仍待第一批垂直切片決定：TaskIntent／RouteDecision／CapabilityContract 的正式 schema；狀態持久化格式；錯誤代碼命名；工作封包的版本與遷移策略；證據的來源權重與衝突表示；驗收收據的簽署／獨立性機制；實際程式語言及部署拓撲。

這些問題不阻礙建立架構骨架，但在對外啟用對應功能前必須完成具體規格與驗收。
