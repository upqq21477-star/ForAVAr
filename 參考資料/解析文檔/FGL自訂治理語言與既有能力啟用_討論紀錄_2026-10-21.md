## 摘要

1. **核心結論：** 值得評估 forAVAr 專用的「治理語言」，但應先把既有 SOP、Brain 工作方法及治理能力轉成機器可驗證的規則契約，不應從零打造完整通用程式語言。
2. **候選定位：** FGL（forAVAr Governance Language）只是暫定名稱。其候選用途是描述任務、前置條件、權限、流程、驗收、失敗處理及退場規則；名稱、語法、實作與採用決策均未核准。
3. **候選技術分工：** 規則層先用 JSON／YAML 等成熟格式；Python 承擔解析、流程整合與驗證；只有在量測證明有收益時，才把特定安全／效能敏感模組評估為 Rust。C 保留給既有原生介面或明確需要的情境。
4. **既有能力可先行利用：** 已形成的對話 SOP、任務路由、問題建模、方案比較、來源核對、驗收與交接方法，不必等待正式程式化 Brain Runtime。
5. **必須分清證據：** 文件存在、對話方法可用、程式已寫、正式 caller 已接線、測試實際通過、Runtime 端到端通過是不同狀態。反覆討論或單次文件驗收，不能直接證明跨任務通用或 Runtime 正常。
6. **下一步：** 先建立能力清冊與唯一權威映射，再選低風險流程建立結構化規則、靜態驗證和模擬執行，最後才決定是否需要自訂語法及開放實際操作權限。

## 1. 問題與範圍

本紀錄處理兩個相連問題：
- 是否值得為 forAVAr 建立專用語言，讓治理規則可被解析、驗證、測試及受控執行？
- 現有 SOP、「大腦啟用」工作方法及 P1／P2 參考能力，能否在自訂語言與程式化 Runtime 完成前先行規劃並分階段採用？

範圍包括語言用途、與 C／Rust／Python 的差異、能力重用、啟用證據分級、施工階段、風險與驗收條件。本紀錄不授權改寫 C′ 企劃，不新增正式程式碼，不修改 P1／P2，也不表示任何自動化功能已啟動。

## 3. 核心模型與技術分工

### 3.1 三個不能混為一談的層次

1. **治理規格／專用語言：** 表達目標、輸入、前置條件、權限、允許操作、停止條件、驗收與失敗處理。
2. **執行引擎／通用程式語言：** 解析規格、驗證條件、呼叫能力、管理副作用及保存結果。近期可用 Python 實作。
3. **原生實作層：** 只有當低階控制、原生介面或有證據支持的效能提升確有需要時，才評估 Rust 或 C。

FGL 不等於執行引擎；規格本身不會自動產生安全性，權限限制必須由實際執行層強制落實。

### 3.2 FGL 候選定位

FGL 是「forAVAr Governance Language」的暫定名稱，尚未定案。候選目標不是取代 Python／Rust，而是讓可重用治理規則成為機器可驗證的契約。

一項規則至少要能表達：觸發條件、適用範圍、必需輸入、前置條件、唯一權威來源與版本、允許／禁止動作、授權、預期輸出、成功／失敗條件、停止／回復／退場方式、證據及相容性。

### 3.3 候選技術分工

- **Python：** 近期主控、規則驗證、流程編排、文件／JSON 處理與測試工具的首選，原因是現有參考程式主要採 Python。
- **Rust：** 未來個別原生模組的候選；需以效能基準或安全需求證明收益。採用 Rust 不等於邏輯自動正確。
- **C：** 保留給既有 C 函式庫、平台／硬體介面或明確 ABI 需求；目前沒有證據支持全系統改寫成 C。
- **FGL：** 候選治理規則表示層，應與執行語言解耦。

以上皆為候選建議，不是核准的技術決策。完整通用語言、獨立編譯器及套件生態不列為第一階段目標。

## 4. 既有能力啟用分級

| 分級 | 能力／證據情況 | 建議處置 |
|---|---|---|
| A｜可先行沿用 | 對話層任務理解、問題建模、方法選擇、來源核對、反例檢查、交接與收口 | 按風險自適應使用；不宣稱是正式程式 Runtime |
| B｜規格已形成，待擴大驗證 | SOP 選用、文件建檔／蒸餾、跨文件分流、版本治理與引用驗收 | 轉成機器可驗證契約並執行多情境試行 |
| C｜程式或測試已有部分產物 | Brain mode controller、Schema、Central 路由、生命週期／驗收模組 | 核對現行版本、正式 caller、實際測試及獨立驗收證據後再升級 |
| D｜未經驗收不得開啟 | 自動修改核心規則、無監督高影響寫入／刪除、自動權限提升或無回退證據的自我修改 | 預設封鎖；要求授權、最小範圍、測試、回退及獨立驗收 |

分類僅為候選治理模型。每個能力的實際狀態須從其唯一權威文件、當前程式、測試與執行證據判定，不能只依分類表升級狀態。

## 5. 分階段落地方案

### Phase 0｜能力盤點與權威對帳
對照現有 SOP、Brain 方法、模組、Schema、測試及唯一權威文件，標示重複責任、來源版本、真實狀態與缺少的 caller／Runtime 證據。P1／P2 保持唯讀。

**Gate：** 每項候選能力有唯一責任來源、適用條件、狀態及未證明事項；重複規則與衝突沒有被隱藏。

### Phase 1｜先結構化規則，不先造語法
挑選一條低風險、常重複的流程，以 JSON／YAML 或等價契約描述輸入、前置條件、權限、結果、停止及驗收。

**Gate：** 可解析和驗證；缺欄、錯誤型別、衝突版本或缺少授權會被拒絕。

### Phase 2｜建立靜態驗證與模擬執行
先以 Python 建立最小驗證器／dry-run，不執行外部寫入或刪除。候選流程包括 SOP 路由、文件生命週期前置檢查、Brain 決策交接。

**Gate：** 正常、負例、邊界案例有預定結果；模擬結果不冒稱真實操作或 Runtime 通過。

### Phase 3｜用同一基準比較收益
比較原流程與規則化流程在漏檢、錯誤操作、重複工作、人工核對成本、執行時間及維護成本上的差異。

**Gate：** 實際結果可讀回、可重跑；收益、退化與未測範圍清楚。沒有足夠收益時，保留結構化契約即可，不擴張語言工程。

### Phase 4｜有限度受控執行
只有前階段通過後才逐項接入實際能力。高影響操作須有明確授權、影響分析、回復計畫、執行層權限檢查及獨立驗收。

**Gate：** 越權與前置條件失敗會被阻擋；結果可讀回，失敗可停止／恢復，證據與執行版本相符。

### Phase 5｜裁定是否建立 FGL 語法或採用 Rust／C
只有當結構化契約有可重現的可讀性或表達瓶頸，才建立最小專用語法；只有個別模組有基準數據證明效能／安全收益時，才評估 Rust／C。

**Gate：** 語義相容測試通過；遷移成本、執行收益、維護負擔及回退方案均已評估。

## 6. 風險與禁止推論

1. **避免重複造輪子：** JSON／YAML、Python 與既有 SOP 已能解決的問題，不應為了自創語法重做。
2. **避免第二權威：** 正式規則、機器契約及 Runtime 狀態必須有清楚的唯一責任與同步方式。
3. **格式正確不等於政策正確：** 解析成功不代表授權正確；授權正確也不代表執行結果正確。
4. **反覆討論不等於完整驗證：** 每項驗證聲明須附適用範圍、案例、執行方式及實際證據；跨情境效力未知就維持未知。
5. **防止自我放寬權限：** 自動化不能自行修改核心權限、測試門檻、驗收器或回退政策，再以修改後的規則判定自己通過。
6. **不得宣稱語言會直接提高 AI 智力：** 可直接期待的是規則一致性、可驗證性與執行控制，不是模型推理能力自動升級。
7. **不得把檔案存在當成接線證據：** 設計、程式碼、正式 caller、實際程式執行與端到端 Runtime 是不同證據層。
8. **控制架構膨脹：** 新語言、資料庫、服務或 Agent 都必須由實際需求、失敗案例或量測結果證明必要性。

## 7. 決策狀態、待裁定與驗收

### 7.1 可作為後續討論基線

- 先重用現有 SOP 與 Brain 對話工作方法，不必等正式 Runtime 全部完成才開始規則化。
- 初期使用結構化契約及 Python 驗證器，不從通用語言或全系統重寫開始。
- 把規則表示、執行引擎、原生實作與證據控制分層。
- 能力分級啟用；未證明的範圍保留未驗證；高影響操作維持受控。
- P1／P2 僅參照；新增及後續實作只在 forAVAr 進行。

### 7.2 尚未決定

1. 是否正式採用 FGL 名稱，以及最後選擇專用語法還是結構化契約。
2. 哪份規格是治理規則的唯一權威，以及變更後如何同步契約和測試。
3. 第一條試行流程要選 SOP 路由、文件生命週期或 Brain 決策交接。
4. 「反覆驗證」的最低證據門檻、代表性案例與獨立驗收責任。
5. 哪些操作只可模擬、哪些在授權後可真實執行。
6. 何種量測結果會觸發 Rust／C 評估。
7. 是否需要正式 parser、語言版本相容性與遷移機制。

### 7.3 本輪不作出的決策

本紀錄不核准 FGL 正式建置、不指定最終語法、不選定全系統 Runtime 語言、不授權高風險自動化、不更新 C′ 主企劃，也不將 P1／P2 的未驗證程式標為可用。

### 7.4 後續規劃／試行的最低驗收條件

- [ ] 每項能力有唯一權威來源、版本、觸發、輸入、輸出、權限與未驗證事項。
- [ ] 重複規則和衝突有明確處置，沒有建立競爭的 Current 或治理控制面。
- [ ] 有正常、負例、邊界及必要的失敗／恢復測試。
- [ ] 授權不足、來源過期、證據缺失或前置條件不成立時，會阻擋或回報 BLOCKED／UNKNOWN。
- [ ] 靜態解析、模擬、真實執行、外部副作用及 Runtime 證據分開標記。
- [ ] 用相同基準比較原流程與規則化流程的品質、成本與維護負擔。
- [ ] 寫入僅發生在授權的 forAVAr 範圍；P1／P2 不寫入。
- [ ] 語言或執行模組升級具備相容性、回退及獨立驗收證據。
