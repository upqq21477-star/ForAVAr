## 0. 核心裁定

**暫不新建平行的問題管理引擎、第二套問題清單、第二份學習登錄或另一套變更追溯系統。** 目前已有大量相似職責：CF-004 對話成果持久化、CF-008 雙向引用及追溯、CF-009 SOP 生命週期、CF-010 對話蒸餾與 SOP 建檔、PR-053 前置規則未觸發、PR-054 資訊分類／唯一歸位／回寫閉環；另有 SOP-META-001、SOP-DOC-001、SOP 執行與演化台帳、問題清單、能力覆蓋登錄、變更追溯總表和文件責任矩陣。

因此優先方案是：**融合共同入口、疊代現有職責、把資料寫回既有權威位置；僅在實際責任缺口被證據確認後才新增。** 對外提供單一指令「整合對話問題」，但指令只負責協調既有流程，不成為新的資料權威。

本輪建立的是規劃與引用映射，不代表已完成全庫語意稽核、改寫既有文件或接通 Runtime。

## 2. 單一指令應是編排入口，不是新引擎

指令名稱：**整合對話問題**

支援範圍：
- 預設：目前對話與目前任務中實際可存取、直接相關的先前紀錄。
- 指定範圍：使用者指定的對話、日期、檔案或專案資料。
- 「本專案全部對話」不得被解讀為可無條件取得所有歷史聊天全文；每次執行必須回報來源覆蓋、可讀性、使用的是逐字內容還是摘要，以及未取得範圍。

### 2.1 整合流程

1. **範圍與來源回執**：鎖定讀取／寫入權限、任務主題、原始要求與可用來源；列出未讀取或不完整的來源。
2. **事件擷取**：擷取使用者校正、偏題、漏做、重複失敗、新漏洞、決策、修正、未解阻塞和實際驗收結果；保留原始來源定位。
3. **對帳既有問題**：先查 PR-001–054、相關 SOP／CF、追溯事件及開發紀錄。相同失效模式記為既有 PR 的新 occurrence；來源新增、根因假說更新和新問題候選分開標記。文字相似不能單獨作為合併依據。
4. **根因與重要性分析**：區分目標／路由、既有能力未調用、職責重疊、證據／來源、執行、驗收、回寫、權限及成本問題。單次低風險錯誤只需記錄；重複或高影響問題才做完整根因／反方檢查。
5. **選用處置**：REUSE（重用）、FIX（修正）、CONNECT（接線）、MERGE（融合重複責任）、EXTEND（擴充既有流程）、NEW（證明無既有責任可承載後才新增）、BLOCKED 或 NOT_APPLICABLE。
6. **按責任寫回**：CF-004 負責將結論歸入唯一權威文件；CF-008 管引用／追溯；CF-009 管流程採納與生命週期；只有形成可重複、可驗收方法時才由 CF-010 產生 SOP 候選。現況問題仍寫回既有 PR 清單，執行結果寫回 SOP 台帳／追溯事件，能力採納才更新能力覆蓋登錄。
7. **回讀與驗收**：讀回實際提交版本、核對來源引用、狀態、必要索引、受影響文件及授權邊界；分開回報已記錄、已寫入、已讀回、已執行測試和已驗證成效。

### 2.2 三層觸發

- **L0 常駐輕量偵測**：當前任務偵測使用者校正、同類失敗再現、未交付產物、資料衝突或驗收漏項；形成候選事件，不自動升格規則。
- **L1 明確深度整合**：收到「整合對話問題」後跑完整擷取、去重、PR 對帳、根因與引用同步流程。
- **L2 完整性閘門**：只有重大偏題、重複高影響失敗、宣稱完整、跨多檔案／架構變更、測試失敗或未知責任缺口時，才啟動 G0–G6。不可把完整流程施加於每個普通對話。

## 4. 分階段實作與驗收

| 階段 | 工作 | 通過條件 |
|---|---|---|
| Phase 0 | 裁定 CF-004／CF-010 職責狀態矛盾；確認 PR-053／054 唯一入口 | 一份現況說明無互相矛盾；責任、輸入、輸出與觸發條件清楚 |
| Phase 1 | 完成直接相關參考文件與引用矩陣 | 每份文件有權威類型、唯一責任、來源與去向；未覆蓋範圍清楚標示 |
| Phase 2 | 以現有 CF-004／010／008／009 編排指令的操作契約 | 同一問題只用既有 PR ID；SOP、追溯與能力登錄按既有責任寫回 |
| Phase 3 | 單一對話／單次任務試行 | 可提取事件、匹配既有問題、回報來源覆蓋，不假稱讀遍舊對話 |
| Phase 4 | 專案文件與指定對話來源試行 | 能發現同義重複、引用斷鏈、狀態衝突與讀回失敗；不建立第二套資料庫 |
| Phase 5 | 後續任務回歸與常駐觸發驗收 | 代表性任務的漏項、重複 PR、重複提醒、返工與整合成本有可比較基線；通過前維持 TRIAL |

必要案例包括：已有相同 PR 不重複新增、CF-004／010 分工衝突、摘要不等於逐字來源、多文件部分更新、未授權企劃修改、P1／P2 READ_ONLY、規則有文件但未觸發、根因修正後再次復發。未執行的案例標 NOT_RUN，不可當成 PASS。

## 5. 外部方法依據

- NASA 需求管理要求需求來源、下層分配、設計與驗證結果維持雙向追溯，並管理基線變更與重複需求。此原則支持本方案的「來源—問題—責任—修正—驗收」追溯，不支持另建平行索引。[NASA：Requirements Management](https://www.nasa.gov/reference/6-2-requirements-management/)
- Google SRE 的 postmortem 實務要求把事件、根因和影響轉成有優先級、責任歸屬與追蹤的行動，並以後續預防效果衡量成效；只有報告而沒有跟進不足以防復發。[Google SRE Workbook：Postmortem Culture](https://sre.google/workbook/postmortem-culture/)
- Atlassian 的問題管理將單一事件與造成多個事件的潛在根因區分，並強調偵測、分類、優先排序、診斷及追蹤；適合用來解釋為何同一 PR 應容納多次 occurrence，而不是每次都開新問題。[Atlassian：Problem Management](https://www.atlassian.com/itsm/problem-management/)
