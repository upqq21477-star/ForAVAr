## 摘要

本文件把「設計上的閉環」定義為：系統不只描述理想成功路徑，也對未知、衝突、拒絕、失敗、外部依賴、狀態漂移、資源耗盡、交接與架構變更提供明確且有界的處置；每條路徑均能產生可辨識的狀態、責任、證據與下一步，或有理由地停止。閉環不等於每件事都必須被解決，更不允許為了形式上的完整而虛構資訊或無限重試。

每次擴充必須通過同一套選型程序：定義要解決的問題、比較至少一個更簡單的替代方案、找出新增複雜度與失效模式、檢查核心相容性、定義可驗收結果，最後依證據採用、保留候選、拒絕或延後。所謂「最優解」只能相對於明確的目標、限制、成本與證據成立，不宣稱存在脫離情境的絕對最優架構。

## 1. 閉環的定義與邊界

APSGA 的閉環由五種閉合共同構成：

- 目標閉合：目標、限制、非目標與接受條件明確；若互相衝突，記錄衝突並進入決策或阻塞，不假裝同時滿足。
- 控制閉合：每個可能產生副作用的操作，都能追溯到權限、作用範圍、執行前 Gate 與結果核對。
- 狀態閉合：成功、失敗、等待、阻塞、重試、恢復、取消及結案都有明確狀態與合法轉移。
- 證據閉合：重要主張能追溯來源或測試；未知與未執行如實保留；不能用「沒有發現問題」推導「已證明安全」。
- 生命週期閉合：工作、能力、文件、版本和資料能建立、使用、驗收、更新、降級、回退或退場。

閉環允許以 BLOCKED、REJECTED、CANCELLED 或 NOT_PROVEN 結束。這些是有效的安全終點，不是系統失敗的遮掩。若沒有可接受解，應說明原因、剩餘風險與可選下一步，而非持續產生新模組直到看似完成。

          |                              |
          +<-----------------------------+

      | 通過             | 不通過
      v                  v
[7 有界執行]         [阻塞／拒絕／重新規劃]
      |
      v
[8 以獨立證據驗收]
  |通過  |可修正  |不可接受／超限
  v      v         v
[結案] [有限修正] [回退／補償／停止]
  |      |         |
  +------>----------+
          |
          v
[9 蒸餾經驗：候選規則／能力／測試]
          |
          v
[10 變更審查與回歸；通過才採納]
          |

任何循環都必須有重試上限、資源預算、停止條件及狀態紀錄。步驟 9 的經驗不自動升格為正式規則；必須先驗證重用價值、適用邊界與副作用。

## 3. 必須覆蓋的情境集合

| 情境 ID | 局面 | 必須具備的處置閉環 |
|---|---|---|
| S01 | 目標明確、低風險 | 使用最短足夠路徑；完成後驗收，不強制建立封包 |
| S02 | 目標模糊或缺資料 | 提問、查證或顯式標記未知；不得擅自補成事實 |
| S03 | 多目標互相衝突 | 呈現衝突與取捨，依優先級／授權決定；無權裁決時阻塞 |
| S04 | 高影響或不可逆操作 | 事前授權、作用範圍核對、獨立驗收及可行的回退／補償 |
| S05 | 執行失敗或部分成功 | 區分未執行、部分副作用與完整失敗；採有限重試、補償或停止 |
| S06 | 外部工具／來源失效 | 記錄依賴、版本與失效；可替代時驗證替代品，不可替代時阻塞 |
| S07 | 證據衝突或來源過期 | 保留競爭證據、時間與適用範圍；不能只選符合預期的來源 |
| S08 | 跨會話／交接／長期工作 | 保存最小必要狀態、權威來源、未決項與下一步；讀回核對後恢復 |
| S09 | 權限越界或提示注入 | 外部內容不具授權權力；由執行 Gate 阻擋超範圍操作並記錄原因 |
| S10 | 資源、時間或成本耗盡 | 觸發預算 Gate；保存可恢復狀態，回報已完成／未完成，不無限擴張 |
| S11 | 規格、依賴或資料漂移 | 重新驗證相容性與證據新鮮度；失配時阻塞、遷移或回退 |
| S12 | 新增能力／架構變更 | 先做影響分析與最簡替代比較，經測試與審查後才採納 |
| S13 | 驗收不通過 | 保留失敗證據，禁止自行降低門檻；修正後使用相同基線重驗 |
| S14 | 無法找到安全可行解 | 明確 REJECTED／BLOCKED／NOT_PROVEN，說明限制與替代方向 |
| S15 | 重複任務與重複副作用 | 使用冪等策略、重複執行偵測或事前查詢，避免重複寫入／扣款／通知 |
| S16 | 能力無用、過時或引入風險 | 停用、降級、合併或退場；更新索引並保留追溯記錄 |

本清單是首版情境基線，不宣稱涵蓋所有可能情況。新增情境時要說明它是新風險、既有情境的子類，還是可由現有規則覆蓋；避免無理由地擴增分類。

## 4. 每次擴充的比較與採納程序

每個新功能、角色、插件、流程、資料物件或服務都必須經過以下步驟：

1. 問題定義：具體描述目前哪個失敗、成本或能力缺口需要解決；沒有可指認的問題，不新增抽象。
2. 成功指標：定義預期改善，例如錯誤率、完成時間、可恢復性、權限違規攔截率、維護成本或證據可追溯性。
3. 最小替代：至少比較「不新增構件，只修正既有流程／契約」的方案；若不適用，解釋原因。
4. 候選比較：按相同任務、相同資料、相同驗收門檻比較候選方案，避免只讓新方案使用更有利條件。
5. 逆向分析：找出新構件會引入的狀態、接口、依賴、權限、同步、失敗與維護負擔。
6. 核心相容性：核對核心不變量、唯一權威來源、M／G／P 分離、有限循環與退出路徑。
7. 失敗演練：至少覆蓋正常、缺資料、衝突、超限、部分失敗、重複執行及回退／阻塞案例中與該變更相關者。
8. 決策記錄：採納、條件採納、保留候選、延後或拒絕；記錄理由、證據、未決風險與重審條件。
9. 驗收與回歸：以預先訂定的標準測試；未跑的測試標 NOT_RUN，不能寫 PASS。
10. 生命週期：定義版本、監測訊號、停用方式、遷移、回退與退場條件。

若證據不足，正確結論是「暫不採納／保留候選」，而不是因為方案看起來完整就直接納入核心。

## 5. 架構選型評估維度

每個候選方案都按相同維度評估，不以單一總分掩蓋致命缺陷：

- 問題適配：是否解決已定義的問題，是否存在更簡單的既有能力。
- 正確性與可驗收性：結果能否用明確證據檢查。
- 安全與授權：越權是否能被執行層阻擋，副作用是否可追溯。
- 失敗隔離與恢復：失敗範圍、部分成功、重試及補償是否可控。
- 狀態與證據完整性：來源、版本、未知、衝突及交接是否保存。
- 複雜度與維護成本：新增狀態、接口、依賴、角色、文件和測試的總負擔。
- 資源效率：延遲、成本、令牌、儲存與人工介入。
- 可逆性與可退場性：能否停用、回退、遷移或合併。
- 核心相容性：是否維持單一權威、M／G／P 正交、權限隔離與有限循環。
- 擴展收益：重用、隔離或獨立部署的實際收益是否由需求與測試支持。

採納規則：安全、權限或資料完整性等硬限制不通過，直接淘汰，不以其他優點抵銷。其餘方案依情境比較成本與效益；若沒有可信數據，不偽造精確分數。當方案在各指標間互有優劣時，記錄 Pareto 取捨與選擇理由，不宣稱絕對最優。

## 6. 反製造問題 Gate

新增構件前，逐一回答：

- 它修復的具體問題是什麼？是否有事件、測試失敗、可重現案例或明確需求支持？
- 既有核心／能力能否透過小幅修正解決？
- 它是否建立第二個權威來源、重複狀態、重複索引或重複職責？
- 它增加多少新狀態、接口、依賴、權限、測試與維護工作？
- 當構件失效、資料過期或版本不相容時，系統如何退回安全狀態？
- 它是否迫使低風險任務走更重流程，或讓高風險任務錯走短路徑？
- 它是否使問題更難診斷、交接、測試、回退或退場？
- 如何證明它比最簡替代方案更好？何種結果會推翻這個判斷？

任何硬限制失敗，或新增複雜度沒有可驗收收益，均不得直接採納。若尚無測試能力，先把它留在設計候選區，不能放入核心不變量。

## 7. 跨模組不變量與責任閉環

- 路由器提出方法選擇，不核發操作權限。
- 授權 Gate 核對主體、操作、目標、範圍、條件與有效性，不替方法品質背書。
- 工作流引擎負責狀態轉移、預算、分支、停止與恢復，不自行改寫接受條件。
- 能力模組只在契約授權範圍內執行，不自行批准自己的副作用或宣告最終驗收通過。
- RunRecord 說明實際發生什麼；EvidenceRecord 說明證據支持什麼；EvaluationReceipt 說明是否達標；三者不可互相取代。
- WorkPacket 是某個工作實例的狀態與交接載體，不是全域能力目錄或永久知識庫。
- 版本治理負責變更、相容性、回退和退場；不能由單一能力自行宣告其版本為全域現行版本。
- 若模組之間互相要求對方批准、產生循環依賴或無人負責最終狀態，視為責任設計缺陷，必須重切邊界。

## 8. 驗收、證據與成熟度

每項設計／能力的狀態至少區分：

- CONCEPT：只有概念。
- SPEC_DRAFT：有初稿規格，接口或失效條件仍可能改變。
- SPEC_REVIEWED：規格經逆向分析與接口審查。
- IMPLEMENTED_UNVERIFIED：程式存在，但尚無足夠測試證據。
- TESTED：指定測試已執行並符合門檻；需附測試範圍。
- RUNTIME_VERIFIED：在明確環境、版本與情境下有可讀回的 Runtime 證據。
- BLOCKED／NOT_RUN／FAILED：分別表示被阻塞、未執行或執行未通過。
- DEPRECATED／RETIRED：不再建議使用或已退場，仍保留必要追溯。

不能把文件完成度當成實作完成度；不能把一次通過推廣成所有局面均安全；不能把測試沒覆蓋到的情境標記為通過。

## 9. 下一輪建置順序

1. 以本文件情境集合逆向檢查第一、二輪藍圖，列出覆蓋、部分覆蓋及缺口。
2. 展開 X01 問題建模與 X02 路由契約，納入衝突、未知與安全拒絕。
3. 定義最小測試案例集，至少包含 S01–S16 中各主要失敗類別的代表案例。
4. 建立只讀垂直切片，驗證輸入、路由、證據與狀態輸出。
5. 再實作 X03 授權 Gate 與 X05 狀態機，測試阻擋、重試上限及狀態恢復。
6. 根據實際失敗與效能數據決定是否需要封包、插件、角色分治、獨立系統或多代理。
7. 每輪記錄被採納與被否決的替代方案；定期檢查新增複雜度是否仍有價值。
