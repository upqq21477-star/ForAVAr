### 候選執行鏈

INTAKE → INTENT → PREFLIGHT → ROUTE → AUTHORIZE → PLAN → EXECUTE → VERIFY → PERSIST → EVALUATE／REVIEW

- INTAKE：保存請求／來源，不先把內容升格為規則。
- INTENT：明確目標、輸出、限制、非目標與成功條件。
- PREFLIGHT：按風險檢索相關 MASTER／SOP／問題，核對權威、衝突、唯一責任和受影響文件。
- ROUTE：產生 M／G／P 候選、方法、未知、證據需求與預算。
- AUTHORIZE：由確定性程式核對讀寫範圍、外部副作用和必要批准；未通過則 BLOCKED。
- PLAN／EXECUTE：建立變更集與狀態；每步保存結果、錯誤和收據。
- VERIFY：檢查內容、契約、連結、權限、回歸和來源支持。
- PERSIST：只將採納的成果寫入唯一權威；同步派生索引。
- EVALUATE／REVIEW：量測品質、成本、失敗和復發，再更新問題／SOP 狀態。

這是責任流程，不代表每項任務都需新增十個檔案或十次模型呼叫。低風險工作可以合併步驟；高影響／多文件工作保留可觀測 Gate 和收據。

## 2. 防止新資訊漏進流程

先分類新內容為 SOURCE／EVIDENCE、FACT／CLAIM／INFERENCE、PROBLEM、DECISION／RULE、SOP_CANDIDATE、RUN／TEST_EVIDENCE 或 OPEN_QUESTION。這些是候選類別，不是已採用的最終 Schema。

最小路由契約回答：來源／版本、證據狀態、唯一權威目標、相關問題／決策 ID、需更新文件、持久化等級、寫入批准、驗收方式、下一步與退場條件。若無法判定唯一責任，保留 OPEN／CONFLICT，不硬塞進相似文件。

**不能只靠模型記住 SOP 自動執行。** 需要一個每項合格任務都會經過的程式入口，按確定性條件執行必要檢索、載入規則、核對版本與授權。模型只產生可驗證的語意候選。資料源讀不到、權威衝突或授權不足時，依風險停止或 BLOCKED。

## 3. 自然語言與程式語言

### 自然語言／術語治理

- 固定 ID、Schema 欄位、狀態值、工具參數和事件類型使用穩定英文識別碼，避免翻譯造成介面漂移。
- 概念定義、理由、用法、邊界和交接說明可用繁體中文；首次出現給予唯一中英對照，如「方法深度 Method Depth」。
- 每個概念只指定一份權威定義；別的文件以引用／摘要表示，不另立同義名稱。
- 將「事實、來源主張、推論、假說、未知、衝突、阻塞」當成不同狀態，不讓流暢語句把它們合併。
- 面向 AI 的提示和 SOP 需有精確欄位、觸發條件、輸入／輸出和失敗分支；面向人類的研究報告可用自然語言，但重要聲明需要回鏈到證據。
- 自動翻譯或蒸餾時，保留原始措辭、權威術語映射和未知；禁止「修辭優化」改變權限或語意。

### 程式語言候選

| 候選 | 適合條件 | 代價／限制 | 本研究建議 |
|---|---|---|---|
| Python | 研究、文件檢查、資料轉換、測試集與評測原型 | 若產品本體為 Web／Node，可能需另一套前端或 API | 暫作原型優先候選，不是正式定案 |
| TypeScript | Web／Node.js／Vercel 為主部署，需要前後端共享型別 | AI／資料處理生態及現有執行環境須實測；型別不替代執行期驗證 | 若目標平台以 Web 為主，與 Python 用同一垂直切片比較 |
| Go／Rust 等 | 有明確部署、資源、併發或可執行檔需求 | 原型迭代及 AI／資料生態的成本需另證 | 第一版沒有具體需求前不優先 |

Python 的 Protocols 可描述介面契約（https://typing.python.org/en/latest/spec/protocol.html）；TypeScript Handbook 提供型別與介面機制（https://www.typescriptlang.org/docs/handbook/index.html）。這些資料只支持可用性，不證明哪一種語言最符合 forAVAr。

先決定部署環境、權限、長任務持續性、排程、可觀測性和使用者操作方式，再決定語言。不要因範例用了 YAML 或 JSON 就將資料格式當成語言選型。可用 JSON Schema／JSON 作跨語言契約候選，但同一狀態不得在 Markdown、YAML、資料庫三處手動維護成三個權威。

## 4. 第一個端到端垂直切片

挑一項真實但可控的工作：將新研究發現寫入 forAVAr，並同步問題清單、研討紀錄、索引與追溯。最小實作必須：
1. 找到現有相關問題、SOP 和唯一責任文件。
2. 將來源、事實、推論、未知與候選決策分類。
3. 建立受影響文件清單和授權範圍。
4. 不重複建立問題 ID／SOP。
5. 寫入中途失敗時識別已完成／未完成項。
6. 讀回檢查內容、ID、連結、字元長度與狀態。
7. 記錄可重跑、可對帳且不重複副作用的收據。
8. 測試下一次任務是否透過程式入口載入相關規則，而不只是文件寫了「應該載入」。

## 5. A／B／C′ 對照

### 試驗組
- A：最簡單且可靠的基線，採已知方法和必要檢查。
- B：固定 SOP／完整封包流程。
- C′-candidate：確定性控制外殼、M／G／P 條件路由、只啟用需要的模組和持久化。

### 控制變項
相同任務、評分規準、模型版本、工具權限和資料來源；無法固定者要記錄。調整集用於修正，保留集用於未見案例驗證。

### 任務覆蓋
涵蓋簡單問答、外部查證、多步研究、多檔寫入、來源衝突、未知／工具失敗、部分提交、跨會話交接、未授權企劃修改、不可信來源指令、長任務與資源上限。早期可以用 30–50 類型探索，但不能據此宣告普遍最佳。

### 指標
- 品質：目標滿足率、必要內容漏失、來源支持、引用正確率。
- 安全：未授權動作攔截、提示注入成功、錯誤副作用。
- 路由：高風險漏判、低風險過度升級、方法不匹配。
- 恢復：部分失敗辨識、冪等、狀態恢復、交接重做率。
- 效率：端到端時間、工具／Token／費用、人工介入和返工。
- 維護：變更半徑、同步負擔、故障診斷時間及回歸成本。

任何未授權高影響操作都是硬性 NO-GO。若 C′ 沒有在品質／安全不退步時降低總成本或重要錯誤，就要縮小或否決；若 A 對某類任務已足夠，保留短路徑；若完整封包只對高風險工作有效，只在該情境使用。
