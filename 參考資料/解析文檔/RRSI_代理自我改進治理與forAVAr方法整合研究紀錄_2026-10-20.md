## 1. 本輪研究目標

本輪延續「通用問題屬性導向方法選擇框架 v0.2」的研究方向，檢查 RRSI（Regularized Recursive Self-Improvement of Agent Harnesses）能否提供可移植的演化治理原則，並分析應如何與 forAVAr 的通用方法選擇架構分工。

研究目標不是直接把 RRSI 的所有護欄加入 forAVAr，而是：
1. 還原反覆修改系統並依評測選擇版本時的主要失效模式。
2. 區分論文直接報告的結果、可移植的工程原則及仍待驗證的設計假說。
3. 判斷此類方法應在通用框架中位於什麼層級，以及何時才啟用。
4. 保存本輪討論提出的紀錄與企劃更新控制要求，避免研究結論未經裁定便直接變成權威規格。

## 2. RRSI 的研究定位

RRSI 針對的是 Agent Harness 的遞迴改進。Harness 包含提示詞、控制流程、工具、記憶與上下文管理；研究中的底層模型保持固定，主要調整的是模型周圍的系統配置。因此，不應把此研究直接等同於模型權重自主學習或無限制的 AI 自我進化。

核心問題是：代理系統可以反覆修改自身並提高特定評測集成績，但若它逐漸記住訓練任務的特例、評分線索或環境細節，改進就不一定能遷移到未見任務。

## 3. 原始研究公開的主要結果

依 RRSI 論文摘要，作者在涵蓋程式工程、代理工作任務及工程設計的八項基準上進行評估，並報告：
- 演化所針對的評測分割中，最高提升 14.1 個百分點。
- 五項分佈外（OOD）基準中，最高提升 4.7 個百分點。
- 相較未加正規化的演化方法，政策推理 Token 約減少 30%。

以上是特定論文實驗設定下的結果，不可解讀為所有任務都會有同樣增益，也不可直接推論為 forAVAr 已獲得相同改善。絕對百分點、相對百分比、演化集成績、保留測試及 OOD 結果必須分開報告。

## 4. RRSI 的治理機制與其抽象意義

論文的核心做法，是保留相當大的候選修改空間，同時約束候選生成路線與版本接受規則。

| 機制 | RRSI 中的用途 | 可移植的抽象問題 |
|---|---|---|
| 隨演化進度調整編輯預算 | 限制單一候選一次打包多少獨立修改 | 修改過多時，能否辨識真正有效的變更？ |
| 完整的修改歷史 | 追蹤已試過的改動與失敗假設，減少重複探索已證偽路線 | 是否保存負面證據與可追溯的變更脈絡？ |
| 停滯時轉向未探索組件 | 不讓搜尋長期只集中於熟悉的改動方向 | 如何平衡局部改良與新方向探索？ |
| 評測專屬改動批評者 | 檢查候選是否利用基準名稱、資料或特殊邏輯 | 評估機制是否可能被候選方案反向利用？ |
| 對噪聲、小幅變更與低價值改動的篩選 | 避免將測量波動或無意義改動當成進步 | 接受門檻是否把測量誤差納入考量？ |
| 成本與效能共同評估 | 排除無法以效能收益合理補償額外 Token 成本的改動 | 是否存在多目標代價，而非只看單一分數？ |
| 移除長期無效或不再有用的組件 | 控制冗餘與架構膨脹 | 系統是否能簡化、淘汰與回退，而非只會累加補丁？ |

這張表是本次討論對原研究機制的整理，不是宣稱原論文必然將上述七項以完全相同的方式分項命名。具體執行細節以原論文與公開程式庫為準。

## 5. 初步抽象：三種控制層

本輪分析將機制抽象成三類控制，而不是將七項護欄固定套在所有任務。

### 5.1 變更生成控制

決定候選一次能修改多少、如何使用過往經驗，以及停滯後何時探索新的路線。核心問題是讓搜尋保持可理解、可追溯和有邊界。

### 5.2 結果接受控制

候選不應只因一次評分較高便自動採用。接受決策需按任務檢查效能、評測洩漏風險、噪聲、成本及硬性限制。

### 5.3 長期狀態治理

保留版本、變更理由、已失敗的假設、測試範圍、回退資訊及組件價值判斷。此層負責避免每輪修改把系統逐漸變成無法追溯或難以維護的狀態。

以上三層屬本輪抽象模型，尚未經 forAVAr 本地實驗證明。

## 6. 外部研究交叉參照

### 6.1 AIDE²：遞迴改進 AI 研究代理

AIDE² 論文描述 AI 研究代理反覆修改自身程式、在任務集上評估改版，並依隱藏評估保留改進。作者報告一個自主執行八天的過程，找到七次連續改進；最強版本在四個保留基準上達到或超越指定的人工作業代理。該研究另報告，在未被直接最佳化的獨立任務族上，reward hacking 比率由 55% 降至 32%。

此結果提供另一個遞迴自我改進案例，但不能視為獨立重現 RRSI 的全部機制或數據。

### 6.2 自我改進研究分類

《From Existing Methods to New Research Ideas: Two Perspectives on Recursive Self-Improvement》提出九個設計維度，分為更新目標、更新組織、更新時機與範圍、回饋與選擇四組。這支持以可分離的設計維度比較方法，而不只用「使用哪個演算法」為唯一分類。

該文是分類與研究構想框架，不等於其分類已經證明能改善所有自我改進系統。

## 7. 反證、限制與需防範的錯誤外推

### 7.1 修改歷史不自動提供因果歸因

多項修改一起加入後得到的整體提升，不能證明每個修改都各自有效。若需確認單一組件效果，必須視問題使用消融試驗、單項對照、重複測試或其他合適設計。

### 7.2 未發現明顯洩漏不代表已證明泛化

靜態檢查可攔截部分基準專屬硬編碼，但不能排除候選因反覆接觸相同任務而學到的隱性偏差。應將「未發現明顯洩漏」「保留測試通過」「跨任務／跨環境泛化」視為不同證據強度。

### 7.3 Token 不是全部成本

在其他任務中，總成本還可能包含執行延遲、工具調用、失敗率、人工修復、維護負擔及錯誤造成的損失。成本模型須依任務決定，不可把 Token 量直接當成通用成本指標。

### 7.4 角色分工不保證獨立驗證

若提案者、分析者與批評者共享同一模型或共同前提，分工本身不保證能抓出相同的盲點。高影響結論仍需可靠測試、可追查的資料或其他能區分真假主張的獨立驗證方法。

### 7.5 不宜過度外推

RRSI 的研究範圍主要是固定底層模型的 Agent Harness 演化。它並未證明所有工作領域都需要演化治理，也未證明完整護欄組合在每一種代理架構中都是最優。

## 8. 與 forAVAr v0.2 的暫定關係

forAVAr 的「通用問題屬性導向方法選擇框架 v0.2」先描述任務的認知目的、結構成熟度、未知來源、可檢驗性、目標與限制、候選空間、動態性及風險，再選擇適合的方法模組。

依此分層，RRSI 不宜取代通用核心，而應作為可能被選用的專門演化治理方法。較合理的啟用條件是：任務確實反覆修改系統、利用評測回饋選擇版本、有多個可組合的候選修改，而且存在足夠可靠的評估方式。

單次量測、明確的簡單問題或沒有可用驗收信號的任務，不應無條件啟用完整的自我改進迴圈。

## 9. 本輪提出的通用化設計假說

建議 forAVAr 未來評估一項候選原則：

> 系統產生的改進候選，只有經過與任務相符的證據、風險、資源及泛化檢查後，才可被提升為新的持續狀態。

可供實驗的機制包括：
1. 保留原始基準，將調整資料與最終驗證資料分離。
2. 為每次修改保存假設、差異、結果、成本、接受／拒絕理由與版本。
3. 在探索與收斂之間採用條件式策略，並將停滯視為檢查新方向的觸發條件之一。
4. 先檢查硬性限制，再評估效能收益及多種成本。
5. 允許對低價值組件提出重新測試、替換或移除，但不能因短期無增益便無條件刪除。
6. 依任務風險進行獨立驗證、回退和必要的回歸測試。

這六點是本輪整合後的設計假說，不是已驗證的 forAVAr 正式能力，也不是 RRSI 原文逐字提出的六步流程。

## 10. 建議的本地驗證方式

若日後批准將該方向納入企劃，可用至少四種對照方案評估：
- A：單次修改，沒有持續演化迴圈。
- B：允許反覆修改，但沒有專門演化治理。
- C：只使用部分治理機制，例如歷史紀錄、保留測試和成本門檻。
- D：採用完整的條件式演化治理。

測量應依任務類型涵蓋：保留／OOD 表現、錯誤率、評測專屬行為、資源消耗、修改可歸因性、回歸風險、維護成本與總完成成本。測試案例、接受門檻及主要指標應事先定義，避免因反覆調整而讓測試集變成另一個演化目標。

在完成 forAVAr 本地對照前，不得宣稱該通用化假說已被證明更快、更便宜或更準確。

## 11. 本次討論新增的紀錄與企劃更新控制要求

使用者明確要求將以下工作方式作為 forAVAr 後續基本能力的候選內容，避免每次都由使用者重新提醒：

1. **沒有明確的企劃更新授權時，只進行討論、研究、分析與紀錄。** 不得因為討論得出結論，就直接修改企劃、方法規格或其他權威文件。
2. **新主題建立新紀錄文件。** 不同主題分開保存，避免將所有內容擠進同一份文件。
3. **同一輪持續討論可更新當輪紀錄。** 這是為保存正在發展的同一份討論記錄，不代表可以更新權威企劃。
4. **同一主題在後續新一輪重新開展時另建新文件。** 不覆寫舊紀錄；由新檔記錄本輪新增問題、證據和結論，再引用前次紀錄。
5. **收到明確企劃更新指令後，先做版本比較。** 必須列出舊版與新版差異，分為融合、取代、保留、淘汰及尚待驗證，逐項說明依據與影響。
6. **先提交差異及整合方案讓使用者確認。** 未確認前，不將變更整合成新的權威版本，也不讓新方案自動取代原權威文件。
7. **使用者確認後才建立新的權威紀錄。** 整合時更新必要的索引、文件責任與版本關係，保留必要歷史及可追溯的變更理由。
8. **寫入範圍限制不變。** 只允許在 forAVAr 新增或修改；P1 和 P2 始終唯讀。

### 11.1 與既有方法規格的關係

目前 v0.2 已表示持久紀錄應依任務需求啟用，簡單一次性任務不必強制建立長篇紀錄；但它沒有完整載明這次使用者提出的「新主題／新一輪紀錄分檔」以及「企劃更新前比較、經確認後才能整合」的具體工作控制規則。

這表示新要求不是要取代方法選擇框架，而是要補充一個上層的專案工作治理規則：何時允許寫入、何種文件可更新、如何管理討論紀錄，以及如何授權權威版本變更。

本節目前只保存使用者要求，不代表已將規則整合進 v0.2 或能力架構提案。
