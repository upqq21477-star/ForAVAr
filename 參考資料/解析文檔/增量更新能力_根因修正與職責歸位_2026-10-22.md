## 1. 摘要與裁定

本次要建置的不是「新增功能的流程」，而是可重複使用的**增量更新能力**：每次更新先辨識原本哪裡失效、根因是否有證據、該修哪個既有節點，再判定是否真有必要新增功能；接著為變更指定唯一主要功能責任、文件權威與批准權限，最後以最小差異、分級測試、回退和復發檢查完成閉環。

核對現有 SOP 後，結論是「有部分元件，未形成必然執行的整體契約」：
- SOP-META-001 v0.5 已有任務分級、根因未知時不得定版、重大語意變更配對模擬、權限限制與回歸原則。
- CF-004 已處理文件盤點、內容分責、去重、衝突、最小寫入及讀回驗收。
- CF-009 已處理 SOP 選擇、驗收和演化；CF-010 已處理從對談／操作蒸餾 SOP 候選。
- SOP-CAND-005、006、007 已分別記錄前置職責掃描、問題到回歸閉環、變更影響／完成閘門的待處理缺口。
- 缺少的是將上述能力接成每次更新都能按觸發條件走的流程，尤其沒有強制把「問題證據 → 根因可信度 → 原責任節點 → 最小修正 → 驗收 → 復發檢查」串起來，也沒有把功能責任、文件責任和批准權限拆開。

**裁定：**不另立平行 SOP；增量更新流程由 SOP-META-001 第 2 節唯一維護，CF-009 負責入口與路由。CF-004 負責成果持久化，問題清單管理問題狀態，能力登錄／功能骨架承載功能映射，文件責任矩陣承載文件權威。v0.7 再將「先盤點既有能力，證明修正／擴充不足後才可新增」提升為所有語意更新的前置閘門。這仍是文件治理規則，不代表 Runtime 自動攔截或跨任務已驗證。

## 2. 根因分析

### 2.1 可觀察的流程失效

前次架構分析把「分析藍圖、外部比對、尋找優化」過早收窄為工具比較，沒有先固定系統目的、核心問題、長期變化壓力及設計不變量。之後雖能回溯原因、把問題加入問題清單，仍不能單靠保存紀錄保證下次工作自動先做前置檢查。

這暴露的是更新流程的連接缺口，不宜只用另一條「先想清楚」的提醒修補。

### 2.2 根因裁定

1. **啟動缺口：** 任務主流程要求目標明確，但對「修正／擴充／取代既有系統」未強制重建最新基線及列出核心不變量。
2. **診斷連接缺口：** SOP 第 6 節說明失敗如何處理，卻未要求每次變更均追蹤到原責任節點；因此可能只記住失敗，沒有改到觸發失敗的流程。
3. **職責粒度不一致：** 文件責任矩陣能決定哪份文件維護內容，卻不能代替功能／架構層的功能歸屬裁定；批准者的權限又是第三件事。
4. **擴建偏差：** 沒有明確要求「先修既有節點，再考慮新增」，容易把局部缺陷包裝為新功能需求，導致平行功能、重複權限與維護成本上升。
5. **結案缺口：** 寫入、單次模擬、內容驗收與復發檢查可能被混為一談。文件更新成功不等於問題已解決。

### 2.3 應保留的既有控制

不重做既有 SOP 的任務分級、來源核對、版本治理、權限、部分提交修復、重大變更模擬閘門及 SOP 生命週期。此次只補上它們之間缺失的連接流程，並以變更影響程度決定檢查深度，避免每次新增功能都全域重查。

## 3. 更新任務的標準流程

更新類任務在授權和 SOP 選擇後，按下列流程執行：

`BASELINE → DIAGNOSE → CLASSIFY_CHANGE → MAP_OWNERSHIP → DEFINE_MINIMAL_DIFF → IMPACT_TEST → APPLY → VERIFY_REGRESSION → PERSIST_TRACE → RECURRENCE_CHECK`

### 3.1 流程步驟與產物

| 步驟 | 必須回答的問題 | 必要產物／通過條件 |
|---|---|---|
| BASELINE | 現行系統實際是什麼？原始目標與不變量是什麼？ | 以最新權威文件／來源重建基線；分清現況、提案、歷史與未驗證項，不只依賴上一輪對話記憶 |
| DIAGNOSE | 預期行為與實際行為差在哪？是症狀、直接原因還是根因？ | 問題 ID／證據／影響／根因可信度／反例；根因未知時標 HYPOTHESIS，不把猜測寫成固定規則 |
| CLASSIFY_CHANGE | 是修正、擴充、引入新能力類型、替換／退役，還是核心契約／權限變更？ | 明確變更類型；不能把所有差異都當成「新增功能」 |
| MAP_OWNERSHIP | 哪個功能節點負責行為？哪份文件維護權威？誰有權批准？ | 功能責任、文件責任、批准／權限責任三欄分開；每項行為有唯一主要責任節點，跨功能協調不等於重複擁有執行權 |
| DEFINE_MINIMAL_DIFF | 修正現有節點是否足夠？新功能存在的必要性是什麼？ | 只列必要變更、明確不改範圍、依賴與回退方式；新增類別須證明現有分類／契約不能承載 |
| IMPACT_TEST | 變更會影響哪些功能、契約、檔案、權限和使用情境？ | 依 `Δ0–Δ3` 分級，固定基線／候選方案及同一組驗收條件 |
| APPLY | 變更是否在授權範圍內，且依唯一責任寫入？ | 按變更集執行；多檔部分提交時標 PARTIAL，只修復不一致項 |
| VERIFY_REGRESSION | 新行為是否成立？舊有通過行為是否仍成立？ | 分開記錄內容、引用、功能行為、權限和回歸結果；沒有實際執行的項目為 NOT_VERIFIED |
| PERSIST_TRACE | 問題、變更、文件與證據能否互相回查？ | 更新唯一責任文件、問題狀態、必要索引／追溯及執行台帳，不複製整份分析 |
| RECURRENCE_CHECK | 相同類型任務再出現時，流程能否從存檔規則觸發正確步驟？ | 在後續代表性任務或無前文的受限重演中檢查；未做則保持 NOT_VERIFIED，不提前結案 |

### 3.2 功能歸屬決策規則

| 變更情況 | 歸位規則 | 不得採取的捷徑 |
|---|---|---|
| 原功能失效、根因位於既有節點 | 修正該節點的邏輯、契約、觸發條件或驗收，再測試原失敗案例 | 不先建立另一個功能繞過根因 |
| 既有能力的相容性擴充 | 由原功能責任節點維護；新實作經同一契約／局部測試接入 | 不因有新工具就建立平行權威 |
| 多能力共同完成任務 | 一個協調／路由節點負責組合流程；各底層能力仍擁有自己的執行責任與契約 | 不讓協調層複製底層功能，也不讓多個節點同時擁有最終裁定權 |
| 現有分類或契約確實無法表示的新能力 | 先提供不可歸入既有類別的證據、責任邊界、輸入／輸出、依賴、副作用及退場方式，再提出新類別候選 | 不以「新穎」「比較強」或單一工具存在作為新增理由 |
| 替換或退役既有能力 | 比較代表性任務，盤點使用者／依賴，定義遷移、回退及舊能力退場條件 | 不因新方案能運作就直接刪除舊路徑 |
| 權限、證據、驗收或安全控制 | 由明確的治理／政策責任維護；新功能不得自行授予自己權限或修改驗收門檻 | 不讓被更新的內容同時修改保護它的控制面 |
| 正式企劃或唯讀外部來源 | 按授權邊界處理；正式企劃需明確「更新企劃」授權，P1／P2 保持唯讀 | 不以模擬通過代替授權 |

### 3.3 變更影響分級

此分級與任務風險 L0–L3 不同；前者決定**影響面與回歸範圍**，後者決定**任務風險與必要授權**。兩者取較嚴格的必要檢查，不互相替代。

| 變更影響 | 範圍 | 最低檢查 |
|---|---|---|
| Δ0｜非語意 | 拼字、格式或不改含義的索引修正 | 讀回與路徑／格式檢查；不啟動重型配對模擬 |
| Δ1｜局部 | 一個已知責任節點的局部修正、同契約相容實作 | 重現原失敗案例、局部行為檢查及直接回歸 |
| Δ2｜跨節點 | 多文件、多能力、共享依賴或一般介面改動 | 依賴／契約檢查、受影響能力回歸、雙向引用及部分提交回復檢查 |
| Δ3｜核心／控制面 | 核心目的、不變量、共用契約、權限／安全控制、不可逆或正式架構裁定 | 同輸入現行／候選配對模擬、正常與失敗情境、回歸、回退及適用時的獨立／無前文檢查；需要的明確授權不可省略 |

**檢索範圍規則：** 不要求每一項新功能都全域比較。只在核心不變量、共享契約、跨節點依賴、責任重疊、新能力類型、影響範圍不明或品質／成本／風險可能顯著改變時擴大掃描。高風險權限檢查始終是獨立硬性控制。

## 4. 配對桌上推演

比較現行 SOP-META-001 v0.5（含 CF-004／CF-009 已有規則）與納入上述增量流程的候選版本。此為同一案例集的定性桌上推演，並非模型盲測、真實 Runtime 測試或耗時量測。

| 測試 | 情境 | 現行流程的能力／缺口 | 候選流程應有結果 | 桌上推演判斷 |
|---|---|---|---|---|
| T1 | 模糊要求「分析藍圖及工具」 | 目標／驗收要求存在，但未明定先建立目的、核心不變量與長期壓力模型 | 先固定原始問題與架構要求，再外部比對 | 改善順序偏移風險 |
| T2 | 新能力其實屬於既有類別 | 文件層有去重／職責掃描，功能層歸屬未成為必填產物 | 先映射既有功能責任，優先修正／擴充原節點 | 降低平行功能風險 |
| T3 | 根因仍未知 | 已規定未知根因不可成為永久規則 | 保留 HYPOTHESIS，先收集可區分證據，不宣稱修復 | 保留既有優點 |
| T4 | 同類缺陷再次出現 | 台帳有紀錄要求，但復發檢查未連成必備步驟 | 從問題 ID 回查舊控制與測試，檢查控制是否未觸發或不足 | 補上閉環缺口 |
| T5 | 共享契約或權限改動 | 重大語意變更已有配對模擬及授權閘門 | 加上責任／依賴映射，但不削弱既有 Gate | 改善影響追蹤，不替代既有控制 |
| T6 | 單一拼字修正 | 已有最小必要路徑 | Δ0 只讀回與做簡單檢查 | 不應增加重型流程 |
| T7 | 新工具連向 P2 唯讀來源或正式企劃 | 已有授權規則 | 保持唯讀邊界；正式企劃仍需明確授權 | 無權限放寬 |
| T8 | 替換舊能力 | 有 SOP 退役生命週期，但能力遷移依賴與功能回退未必逐項列出 | 比較代表性任務、遷移依賴、設定回退，通過後才退役 | 補上能力層的退場檢查 |

**模擬結果：** 候選流程對 T1–T8 均定義了對應控制點；現行規則並非全無涵蓋，主要缺口是步驟的必然連接、功能職責映射與復發檢查。候選流程也會增加更新任務的前置成本，因此以 Δ0–Δ3 分級避免對低風險變更使用完整檢查。

**決策：GO（僅進入 TRIAL）。** 這是對已知治理缺口的程序修正；可以先寫入 SOP 試行，但不能宣稱整體速度、漏失率或跨任務改善幅度已證實。若後續代表性案例顯示增量流程造成無效成本、錯誤阻擋或責任歧義，須按證據修訂或回退。

## 5. 驗收與結案門檻

一次更新不能只以「新文字已寫入」結案。應依下列狀態分層回報：

- **規範已寫入：** 唯一責任 SOP 已更新並讀回；只證明文件層完成。
- **映射已完成：** 問題 ID、根因證據／可信度、功能責任、文件權威及批准權限已逐項連結。
- **內容／結構已驗收：** 索引、相對路徑、狀態、變更追溯和必要欄位均檢查。
- **行為已驗證：** 已執行原失敗案例與相關回歸測試，保存測試輸入、預期、實際及結果。
- **復發控制已驗證：** 在後續代表性任務或受限無前文重演中，流程能從持久化規則觸發正確處理。
- **完整結案：** 前述適用條件通過、無未處理的高風險缺口，且必要的獨立檢查／使用者核准已完成。任何未執行項目維持 NOT_VERIFIED。

### 本次落地狀態

- SOP-META-001 v0.7：已加入語意更新前的既有能力盤點與禁止無證據新增規則；狀態 TRIAL。

- SOP-CAND-005／006／007：已映射至新流程，仍需代表性任務驗證。
- 問題 PR-053 等既有狀態：不因文件修訂自動關閉；是否解決仍取決於後續行為證據。
- 正式藍圖：未修改。
- P1／P2：未寫入或修改。
- 未完成事項：至少兩個不同情境／輸入的真實執行或涵蓋主要分支的回歸測試；成本、延遲、返工及復發率量測；無前文獨立評估。

## 6. 後續執行的代表性案例

1. **同類缺陷修正：** 問題清單已存在同一 ID，驗證是否優先修復原責任節點，不新增同義功能。
2. **相容的新能力：** 能力落在既有類別，驗證是否只更新登錄／契約與局部檢查，而不觸發不必要的全域工具比較。
3. **真正的新能力類型：** 現有分類無法表達，驗證是否先提出缺口證據、唯一責任、介面、依賴及退場規格。
4. **重複失敗／共享契約改動：** 驗證復發檢查、影響分級、回歸及回退能否正確觸發。
5. **低風險內容修正：** 驗證流程能走最小路徑，不因新增規則使所有任務成本一起膨脹。

在完成上述代表性案例之前，本報告與 SOP 更新都只能證明「已設計／已寫入」，不能證明「系統已可靠學會」。


## 7. 後續強制門檻校正｜2026-10-22

在使用者要求再次確認後，將規則由「優先修正既有節點」加強為明確的寫入前 Gate：凡改變功能、邏輯、能力、流程或架構的語意更新，必須先查能力登錄、forAVAr 內的 P1／P2 功能骨架映射、相關 SOP／PR 與責任矩陣；記錄已查能力 ID、重疊／衝突、證據缺口，以及既有能力為何不能修正／擴充。未完成盤點或沒有證據證明既有能力無法承載時，標記 BLOCKED，不得先新增後補理由。純讀取及不改語意的機械修正走最小路徑。此規則已同步到 SOP-META-001 v0.7、CF-009 啟動路由、README 的 AI 開工順序與能力登錄的機器可讀前置契約。

**校驗界線：** 已確認上述文件與機器 manifest 有一致的門檻描述；本次沒有執行 Runtime／CI 強制測試，也沒有獨立盲測後續對話是否必然遵循。因此狀態為「文件治理規則已更新，持續行為待驗證」，不能宣稱自動封鎖已實現。
