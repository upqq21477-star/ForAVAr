## 7. 證據模型、封包、持久化與記憶

### 7.1 分離三類狀態

1. **任務／執行狀態：** 任務目前階段、工具執行、重試、取消、checkpoint 與完成狀態。
2. **主張／來源證據狀態：** 哪個主張受哪些來源或觀察支持、範圍、日期、衝突及未知。
3. **跨任務長期記憶／規則：** 經重複案例與回歸證據證明可重用的規則或偏好。

三者可以透過 ID 相互連接，但不應以同一欄位或同一快照取代。任務狀態不能冒充證據，來源帳不能冒充工具收據，單次失敗不能自動變成長期規則。

### 7.2 M/G/P/T 中的 P 與工作封包

- **P0：** 不需要持久化；工作完成後只保留有明確要求的最小紀錄。
- **P1：** 保存精簡可追溯資訊，例如任務、狀態、關鍵結論、未決項與證據連結。
- **P2：** 對跨會話、多階段、高影響或可中斷任務使用正式工作封包／checkpoint。

封包不是任務真相的唯一權威，也不能覆蓋目前權威文件、實際檔案狀態或工具回執。

### 7.3 工作封包的條件性最小欄位

只有 P2 情境才按需啟用以下欄位：
- package_id、任務／目標、範圍、接受條件、版本與來源；
- 當前階段、已驗證完成項、未完成／阻塞項、決策與理由；
- 任務／依賴 ID、重要主張及來源／執行證據連結；
- 授權範圍、禁止操作、風險與未決的權限條件；
- checkpoint、冪等／不可重播操作標記、恢復點與回滾計畫；
- 交接者／接手條件、有效期限、敏感度及退場策略；
- manifest/hash 僅在完整性、批次同步或跨庫交付有需要時使用。

實際 schema 沿用 StateBundle 契約與現有文件生命週期規格；此處不建立第二套封包格式。StateBundle 仍是衍生／可攜狀態視圖；除非正式批准契約另有定義，不能把它當作覆蓋 Current 的權威資料。

### 7.4 Run Record／執行收據

對需要實際工具執行證明的工作，收據候選至少連結 task_id、run_id、目標版本、時間、命令／工具、exit status、環境、輸出指紋、引用 evidence IDs 及結果狀態。欄位是否必填依執行類型定義。缺少必要觀察證據時不得標記 EXECUTED/PASS；工具成功執行和任務品質驗收必須分開。

## 8. Runtime 最小責任鏈與明確限制

正式規劃的責任鏈為：

`FRAME → EVIDENCE → ROUTE → [AUTHORIZATION] → EXECUTION → EVALUATION → FEEDBACK`

與任務固定流程、F0–F7 相容，但不取代它們。

### 8.1 需要確保的行為

- task/frame 有非空目標及可判定的接受條件。
- 快速路徑只能在必要風險／未知／副作用欄位明確符合低風險條件時短路。
- 高風險或副作用操作遇 critical unknown、授權缺失或 policy gate 失敗時阻塞。
- Runtime／工具執行權限不能被模型路由或任務 profile 自行授予。
- execution 狀態與內容驗收分開；未執行、部分執行、阻塞、失敗和已通過不可混用。
- 真實收據綁定執行版本、工具、時間、輸出指紋和證據引用；未要求的欄位不可僅為整齊而強制所有任務使用。
- timeout、取消、重試、未知副作用和中斷恢復要有獨立狀態與處理契約。
- 寫入／刪除／權限變更等副作用需具明確允許範圍、執行身分、前後狀態檢查及需要時回滾。

### 8.2 Python vertical slice 的現況與靜態測試假說

目前 `runtime/foravar_vertical_slice.py` 已知狀態為 `ADAPTER_SEAM_NOT_INTEGRATED`；它提供可呼叫的流程外殼，但不提供完整模型、權限引擎、任務登錄、持久化、重試迴圈或 GitHub 操作。以下為待驗風險假說，未確證為 bug：
1. 缺少部分必要 observed evidence 欄位時，可能仍進入接受判定；
2. `risk_level=CRITICAL` 本身可能不在 adapter seam 強制授權，需由獨立 G／policy gate 保證；
3. `Evidence.status=CONFLICT` 可能在部分條件下流入路由，需測試是否必須阻塞。

優先用檔案 17 的 contract subcases 驗證：缺欄、重複 ID、task_id 不一致、證據狀態不一致、critical unknown、授權拒絕、執行 PARTIAL／BLOCKED／NOT_RUN、timeout／unknown side effect、收據不完整及恢復一致性。本次未執行 Python 測試或真實 Runtime 故障注入。

## 9. 安全、權限、資料保護與邊界

- 高影響、不可逆或授權不明的操作，預設先阻擋受影響行為；可以繼續不受影響且明確安全的工作時，必須分離範圍。
- G／policy gate 不能被 M 的分析深度、T 的協作拓撲、P 的持久化選擇或模型信心覆蓋。
- 任何「唯讀」規範需同時辨認 repo metadata、憑證權限和工具能力；若權限與政策不符，禁止寫入並記錄邊界落差，不自行改變權限。
- 個資、機密、未獲使用權之資料依資料准入、敏感度、保留期限和用途限制處理；私有 repo 不等於任何資料都能安全上傳。
- 需要刪除或退場的資料，先核對所有者、授權、引用、依賴、備份與回復能力；不得以資料夾移動假裝從 Git 歷史刪除，也不得無證據宣稱永久清除。
- 安全控制必須是硬門檻；即使效率／品質平均分很高，也不能抵銷未授權副作用。
- 當環境不支援真正的權限隔離、審核或持久化時，系統需如實標記能力限制，不能把文件規則說成已自動強制。

## 10. 失敗分類、修正傳播、中斷恢復與停止

### 10.1 失敗分類

用既有 SOP／PR／Runtime 錯誤契約進行歸因，至少區分：目標／語意錯誤、來源或證據錯誤、推論／模型錯誤、方法／路由錯誤、工具／adapter 錯誤、授權／policy 阻擋、持久化／狀態錯誤、整合／依賴更新錯誤、驗收／測量錯誤及成本／停止錯誤。分類新增前先對照既有問題 ID，不另開同義問題清單。

### 10.2 修正傳播

- 修正前定位根因是否有證據；未知根因保留 UNKNOWN。
- 確定影響範圍與直接依賴，建立本次變更集。
- 只更新受影響的主張、文件、輸出、引用、測試和狀態，不無故重建全庫。
- 下游驗收重新綁定新版本；上游變動令相關舊證據失效時，明確標記 INVALIDATED。
- 修正後做相應回歸及復發檢查；重複失敗先核對既有控制是否未觸發、設計不足或根因不同，不只新增規則。

### 10.3 狀態與重試

- **PASS：** 凍結接受條件均有足夠執行證據支持。
- **PARTIAL：** 有明確完成與未完成邊界，且已完成部分可獨立驗收。
- **BLOCKED：** 必要輸入、授權、環境或證據不足；受影響行為不可推進。
- **FAILED：** 有執行結果證明未達必要條件或操作失敗。
- **NOT_EXECUTED：** 沒有執行，不得推論結果。
- **NOT_VERIFIED／NOT_PROVEN：** 目前證據不能證明通過。
- **INCONCLUSIVE：** 執行或評估有做，但樣本、量測或對照不足以裁決。

重試需有上限和不同方法／新資訊條件；同一輸入和同一方法無新增證據時不可無限原樣重跑。部分寫入失敗時，先讀回實際狀態，再只修復不一致項。
