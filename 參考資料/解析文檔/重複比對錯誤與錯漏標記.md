## 1. 標記狀態定義

| 狀態 | 意義 |
|---|---|
| `CONFIRMED_ERROR` | 有直接證據可確認內容錯誤。 |
| `CONFIRMED_FORMAT_LOSS` | 文字或功能由一種格式轉到另一種格式時未保留。 |
| `KNOWN_GAP` | 原始來源已知缺失或必要資料確定取不到。 |
| `SCOPE_CLARIFICATION` | 語句可能使用不同統計範圍，不應誤判成內容毀損。 |
| `RESOLVED_WITH_LIMITATIONS` | 已完成明確範圍的驗收，但結論不能擴大到未檢查範圍。 |
| `FALSE_POSITIVE_CLOSED` | 初步比對疑似錯漏，經正規化／來源回讀後排除。 |
| `BLOCKED` | 關鍵來源證據尚未取得，不能對內容作判定。 |

## 2. 固定標記

### ERR-001｜對話訊息數的範圍措辭歧義

- **狀態：** `SCOPE_CLARIFICATION`
- **直接證據：** 對話紀錄 Markdown 與 DOCX 都可找到主訊息編號 1–15；完整性初核寫 15 則（8 則使用者、7 則助理），前段又將訊息 1–13 描述為核心設計討論及文件整理，14–15 描述為交付後保存／完整性檢查；另有一句「本輪主題對話共 13 則訊息」。
- **裁定：** 「13」可能指核心主題訊息 1–13，而「15」包含交付後續 14–15。現有證據不足以證明數字錯誤，因此不再標記為已確認來源錯誤。
- **處置：** 保留原文，不自行更正。若取得作者確認或更早平台匯出，再裁定原意。

### GAP-001｜訊息 1 之前的助理回覆不完整

- **狀態：** `KNOWN_GAP`
- **直接證據：** 兩種格式都說明訊息 1 前有較早的助理回覆片段，但只保存可見結尾，完整前文無法從目前可檢索來源恢復。
- **影響：** 對話紀錄不是已證明涵蓋該更早回覆的完整逐字原文。
- **處置：** 保留缺口。取得可驗證的原始聊天記錄前，不從摘要重建缺文，也不標示為零遺漏。

### FMT-001｜五個 sandbox URL 保留文字，但失去可點擊功能

- **狀態：** `CONFIRMED_FORMAT_LOSS`
- **直接證據：** Markdown 內有五個 sandbox URL。五個 URL 文字都可在對話紀錄 DOCX 主文件找到，但 DOCX 有 0 個 hyperlink 元素及 0 個外部 OOXML relationship。
- **影響：** 路徑文字保留，Word 的可點擊外部連結行為未保留；部分連結標籤的說明詞也被縮短。歷史 sandbox 目標不保證目前有效。
- **處置：** 不改原始文件。若發布新版本，須先驗證目標有效性，再決定是否轉成可用連結。

### GAP-002｜Markdown／DOCX 跨格式差異驗收

- **狀態：** `RESOLVED_WITH_LIMITATIONS`
- **已通過的結構證據：** 外層 ZIP 4/4 成員大小與 CRC32 通過；兩份 DOCX 各 17/17 OOXML 部件大小與 CRC32 通過；28 個內部 relationship targets 缺失 0；Content Types 缺少宣告 0、孤立 Override 0。
- **標題／表格證據：** 對話紀錄標題 75/75、企劃書標題 72/72；13 張表、137 列、379 個儲存格的正規化文字差異 0。
- **非表格正文有序序列比對：** 對話紀錄 Markdown／DOCX 分別 10,502／10,642 個正規化字元，最大共同有序序列 10,463 個字元；企劃書分別 9,887／9,923 個正規化字元，Markdown 全部 9,887 個字元都能按順序對齊，DOCX 另有 36 個字元。量化表、正規化規則及每類差異見「封包B雙格式完整性與差異稽核.md」§9.6。
- **差異裁定：** DOCX 額外數字屬 Word 標題／層級編號；交付段落差異屬 sandbox URL 的可點擊功能與短標籤；範圍句有少量措辭不同；企劃書 20 個內部 TOC anchor 全部對應存在的 bookmarks；頁首／頁尾屬版面識別文字，註腳／註解 XML 無文字。沒有未解釋的實質內容缺失。
- **限制：** 本標記代表已完成所述抽取、正規化、表格與有序字元序列檢查，不代表兩個原始格式逐字元完全相同，不保證未抽取的 UI 樣式／隱藏中繼資料相同。
- **處置：** 跨格式差異項已收口。GAP-001 來源缺口及 FMT-001 連結功能損失分別追蹤，不再留在 GAP-002 名下。

### FALSE-001｜企劃書 12.1 標題比對假陽性

- **狀態：** `FALSE_POSITIVE_CLOSED`
- **直接證據：** Markdown 標題含反引號，移除 Markdown 行內標記後，可在 DOCX 找到「12.1 FAIL 與 BLOCKED 的差異」。
- **處置：** 不改來源文件。標題比對須先正規化 Markdown 標記。

### BLOCKED-001｜封包 A 原始 ZIP 位元組讀取阻塞

- **狀態：** `BLOCKED`
- **來源：** `參考資料/原始檔案/壓縮檔/P2-relay-R3d130j.zip`
- **身分：** Git Blob SHA `0e58526bd35c30a25f3b27033a4952ec5f25bf10`，GitHub 登錄大小 1,885,519 bytes；P2 唯讀副本同 SHA／同大小。
- **已試途徑：** forAVAr 與 P2 的 Contents Base64 均回傳空內容；Blob fetch 以 UTF-8 解碼二進位失敗；raw／網頁檔案讀取未交付 bytes；未登入的外部抓取對私有 repository 路徑回 404。P2 main 與七個相關分支均沒有另一份已解壓工作樹或所需的舊封包工具／計畫檔；P2 路徑歷史只見 2026-10-17 的上傳提交。外部擷取服務目前沒有可用額度。
- **裁定：** 以上是取檔途徑失敗，不是 ZIP 損壞證據。成員清單、壓縮方法、內部 CRC、程式與測試內容全部仍未知。
- **解阻條件：** 取得可驗證的原始位元組後，先核對實際大小／SHA-256，再驗 ZIP 結構、建立完整成員清冊、分批解壓並記錄 CRC。解阻前不得猜測成員或宣告實際解析完成。
