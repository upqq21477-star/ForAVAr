## 1. 摘要與裁定

本次失效的根因不是「少比較了幾個工具」，而是**研究順序錯誤**：把「分析最新藍圖、外部比對、尋找優化方式」過早窄化成產品／工具選型，未先推導系統目的、核心問題、未來變化壓力、設計不變量與演進機制。

這導致上一輪雖列出 Agent Runtime、評測工具及工作流工具，卻沒有先回答核心架構問題：當模型、工具、能力與資料持續增加或改變時，如何避免每次新增能力都觸發全域比較、架構重建與重複返工。

**問題已登錄，不代表控制已修好。** 本次沒有新增同義 PR 編號；沿用 PR-001、PR-006、PR-011、PR-012、PR-013、PR-039、PR-053、PR-054，並關聯 PR-010、PR-031、PR-037、PR-048、PR-051。

## 2. 可觀察失效與根因

### 2.1 失效行為

1. 先列外部產品與工具，再反向解釋它們的價值。
2. 沒有先恢復原始設計目的：思考核心是目的，工具、流程、角色、文件和治理是支援手段。
3. 沒有先建模能力持續增加的長期情境，例如功能重疊、介面／模型更新、能力替換、資料規模成長、舊能力退場和未知問題。
4. 沒有將穩定的架構不變量與可替換的實作選項分開。
5. 把持續驗證滑向「每次都要重新比較」，未先設計依變更影響範圍決定驗證深度的機制。
6. 專案已有相近問題與前置規則，但規則沒有在分析開始時實際約束方法選擇。

### 2.2 根因裁定

- **直接根因：** 先選局部解法、後確認問題框架；研究方法與問題層級不匹配。
- **架構缺口：** 既有問題清單／SOP 尚未可靠轉化為工作開始時的前置檢查。
- **學習缺口：** 登錄失敗不等於下一次執行必然觸發修正。
- **非本次根因：** 並無證據顯示只要換用某個外部工具，就能解決這種分析順序錯誤。

對模型內部原因不作不可觀察的臆測；以上判定依據是上一輪可見的回答順序，以及 Repository 內已存在、卻沒有在該回答開始時發揮約束作用的相關規則。

## 3. 修正後的架構分析順序

架構級研究開始時，依序執行：

1. **恢復根本目的：** 讀取核心骨架主軸、最新藍圖和相關問題 ID；說明系統要長期達成什麼，不先列產品。
2. **拆解核心問題：** 分開認知目標、控制需求、執行能力、狀態／證據支援和文件生命週期。
3. **推導未來壓力：** 從能力數量增加、功能重疊、模型/API 變動、資料累積、未知問題和舊能力退場推導失效情境。
4. **定義不變量：** 核心目的、責任邊界、能力契約、權限／證據邊界、可回退性及狀態一致性。
5. **設計演進機制：** 使新能力能被分類、登錄、比較、接入、替換與退場，避免每次變更重新設計全系統。
6. **再做外部比對：** 依已定義的架構需求，按能力類別比較候選；只對可能改變架構裁定的差異做深入研究。
7. **最後評估證據與成本：** 區分設計推論、桌上模擬、實際測試和 Runtime 觀察；未量測不宣稱改善。

## 4. 能力持續增加時的條件式處理

這不是「完全不評估新工具」，而是**不讓每個新工具都觸發全域比較**。

| 變更類型 | 預設處理 | 升級到較大範圍的條件 |
|---|---|---|
| 既有能力類別中的相容實作 | 登錄用途、版本、輸入／輸出、依賴與權限；執行必要的局部相容檢查 | 相容性失敗、可觀察品質／成本差異或共享依賴改變 |
| 既有能力的候選替代品 | 只在實際選擇可能改變時，以代表性任務比較 | 基準結果顯示重要品質、風險、成本或維護差異 |
| 新能力類型 | 先檢查現有能力契約能否描述，不立即擴建整套架構 | 現有分類／契約確實無法表達其責任或副作用 |
| 核心不變量、共享契約或全域狀態改變 | 觸發架構級影響分析與回歸 | 必須檢查所有受影響的消費者與狀態轉移 |
| 高風險、越權或不可逆操作 | 執行層硬性 Gate，不可因變更局部而略過 | 任何授權、範圍或恢復條件不明時先阻擋 |
| 舊能力退場 | 檢查使用者、依賴、遷移、恢復及回退 | 有必要來源、依賴或驗收尚未處理時維持阻塞 |

此設計可降低全域重評的頻率，但不能保證完全不返工。其價值在於把返工限制在實際受影響的範圍，並讓必要的架構重整仍可被觸發。

## 5. 「失去記憶」受限重演

### 5.1 測試目的

檢查在假設前次對話內容不再可用時，能否透過 forAVAr 的最新藍圖和已更新問題清單，恢復原則與正確的分析順序；不能把「記得使用者剛剛糾正過什麼」當作通過條件。

### 5.2 重演輸入

**重演 A｜只有原始任務：**

> 啟用深度研究，分析最新藍圖，與外部相似工具、模型及產品比較，尋找更優化的方法。

**重演 B｜使用者指出偏離：**

> 未來工具、功能與能力只會增加。若每次都全面比較，能力膨脹後會嚴重影響效率。應先理解系統原理、核心問題與未來局面，再分析為何把核心丟失及如何避免。

**模擬記憶邊界：** 將先前對話視為不可用，只允許依原始任務和 Repository 當前文件重建；從問題清單中提取適用的已知失效模式。這是本回合中的受限桌上模擬，不是真正清除本模型上下文或啟動獨立的新模型實例。

### 5.3 預先設定的通過條件

| ID | 通過條件 |
|---|---|
| T1 | 先說清楚系統目的與核心問題，不先列工具 |
| T2 | 明確推導能力膨脹和長期演進壓力 |
| T3 | 分離穩定不變量與可替換的實作內容 |
| T4 | 提出能力分類、契約、依賴和退場等演進機制 |
| T5 | 不要求每新增一項能力都做全域比較 |
| T6 | 只在架構需求確定後才進行外部工具比對 |
| T7 | 保留必要的驗證、硬性控制及合法未知狀態 |
| T8 | 明確區分桌上模擬與真實 Runtime 證據 |

### 5.4 受限重演結果

依照已回讀的問題清單，在受限重演中生成的模擬輸出如下：

> **核心裁定：** forAVAr 的研究目標不是收集最佳工具清單，而是建立以思考核心為目的、能持續吸收和替換能力、且不因能力規模成長而反覆全域返工的架構。外部工具只能在架構要求定義後，作為可替換能力候選。
>
> 首先明確根本問題：思考核心不得被工具、工作流、治理或文件治理取代；系統還必須承受能力數量增加、功能重疊、模型／API 變動、狀態與資料累積、舊能力退場，以及現有分類無法描述新能力等壓力。
>
> 因此，先定義穩定的不變量與能力介面，再建立能力登錄、分類與去重、契約、Adapter、變更影響分級、按需驗收、版本管理和安全退場。新增能力若屬既有相容類型，只做登錄、契約與局部相容檢查；只有在共享契約、核心原則、新能力分類或重大效益差異被觸發時，才升級到架構級比較。高風險與授權檢查始終是獨立硬性控制。
>
> 外部比對應按架構責任分組：Agent Runtime、狀態工作流、評測與優化工具不可直接混成同一張排行榜。先找出候選工具能補足哪一項已定義需求，再決定是否做深入比較。工具的新穎度本身不是接入理由。
>
> 最後以具體反例檢查：能力數量增加十倍、主要模型更換、某個外部服務退場、共享契約改變或出現未分類能力時，系統能否限定影響範圍、維持核心責任並可回退。未經實際基準與回歸測試，只能稱為候選設計，不能宣稱最優。

- 思考核心是系統目的；工具和治理不是核心本身。
- 長期問題是能力規模持續成長後，如何維持可擴充、可替換、可定位影響且不必全域返工的架構。
- 應先設計穩定的能力分類／契約／適配邊界、變更影響分級、增量驗收、版本與退場機制。
- 外部產品只能用來驗證這些架構需求是否已有可重用的實作；不應反過來決定核心長什麼樣子。
- 相容的局部新增採用輕量檢查；共享契約、核心不變量或重大風險改變才升級到架構級審查。
- 不宣稱新方案已證實最優；若沒有實測基線，效益只能標記為待驗證。

**桌上檢查表：** T1–T8 的修正後目標輸出均有對應規則，按設計符合性可判 8/8 符合。原先回答則未滿足 T1、T2、T4、T5、T6，且 T3 只有口頭聲明、沒有形成演進機制。

這個 8/8 是本回合依預先列出的文字檢查表所做的人工桌上評估，不是獨立盲評，也不是實際的新會話行為成功率。因此只能裁定「改進方案在設計邏輯上可執行」，不能裁定「系統已確實避免復發」。
