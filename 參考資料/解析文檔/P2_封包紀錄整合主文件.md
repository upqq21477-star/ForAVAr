## 2. 可融合的共同核心

以下項目在封包 B 討論／企劃與封包 A 的交接規程中有交集，可整理成共同原則。共同原則不代表它們已在 P2 程式中實作。

### 2.1 最高目標：解決問題

最高層目標是把使用者目標轉成符合範圍、限制與接受條件的可檢查結果。架構簡化的重點不是刪掉功能、角色或保障，而是減少同一概念被多套文件、圖表和狀態機重複描述，再要求 AI 自己記住它們的對應。

### 2.2 一條簡單的因果流程

討論稿已將 H0–H2 的簡單骨架視為方向正確；企劃書將它明確寫成五個基本環節：

**理解問題 → 決定做法 → 執行做法 → 檢查結果 → 修正與結案**

- **H0：** 唯一最高目標——解決問題。
- **H1：** 五個穩定環節。
- **H2：** 各環節的基本功能與步驟。
- **H3+：** 只有遇到真實方法選擇、能力選擇、條件判斷、依賴排序或回退決策時才展開分支。

前兩層保持愚蠢、穩定、容易判斷；分歧放在需要選擇的更深層，不把每種角色、工具或環境都先製作成新的頂層流程。

**接受狀態：** 這是討論中獲得認同的概念基線；仍屬設計參考，正式成為 P2 權威架構前，須與 P2 唯一施工藍圖及 Current 對帳。

### 2.3 一份權威底圖，多種派生視圖

不同圖表回答不同問題，但不能各自成為一套內容重複、獨立維護的真相：

| 視圖 | 主要回答 | 權威來源要求 |
|---|---|---|
| 功能／能力歸位樹 | 此功能的唯一主要歸屬在哪裡？ | 每項功能只有一個正式定義；跨環節引用 ID |
| 因果／流程圖 | 哪些條件導致下一步，失敗回到哪裡？ | 使用節點、封包與條件 ID 引用 |
| 角色／責任視圖 | 誰有權負責、執行或驗收？ | 維持職權與資料所有權邊界 |
| 狀態／進度視圖 | 目前在哪一步、是否能推進？ | 由唯一權威狀態與事件證據派生 |
| 施工／驗收視圖 | 哪些變更已做、哪些證據成立？ | 引用實際差異、測試輸出與驗收結果 |

樹狀位置表達「歸屬」；前置條件、因果引用與封包連結表達「流程」；角色視圖表達「責任」；Current 與證據表達「現在確實發生了什麼」。不可把這些混成同一欄位，也不可為每種視圖再建一份自己的關係真相。

### 2.4 功能是可條件啟用的能力，不是另一條流程

一個功能只建立一份正式定義，可被多個環節引用；主歸屬不等於只能在一處被使用。功能啟用必須同時考慮：

1. **位置：** 流程確實到達該功能的適用節點。
2. **觸發：** 可觀察的觸發條件成立。
3. **輸入：** 必要資料、來源、版本與依賴齊備。
4. **權限：** 當前角色／工作單元有權執行。
5. **資源與安全：** 成本、時間、上下文、外部工具額度及安全限制允許。
6. **衝突：** 目標、來源、範圍及依賴不存在未解衝突。

必要硬性條件不成立就不調用；資料可補則先補資料；無法合法或可靠地繼續就 BLOCKED。AI 覺得功能「可能有幫助」不能取代這些 Gate。

### 2.5 狀態與證據分開

狀態回答封包走到哪裡；證據回答為什麼可以相信結果。以下層級不可互相冒充：

- 文件／設計已寫入。
- 靜態閱讀與契約檢查。
- 局部案例推演或模擬。
- 實際程式測試。
- 整批整合驗收。
- 真實 Runtime 觀測。

單一封包 PASS 不等於整體任務已結案；模擬、靜態檢查、程式檔存在或摘要內容均不能升格成真實執行證據。

### 2.6 封包傳遞必要上下文與因果

每次推進只須保存可追溯的最小因果鏈：由哪個封包／條件觸發、前置條件如何核對、選了哪個分支及其理由／證據、產生什麼結果、下一步被允許或為何停止。下一個封包引用上游 ID、位置、版本或指紋，只載入本步驟所需的內容，不反覆複製完整歷史。

### 2.7 結案時管理結果、證據、交接與暫存

封包閉環時分成四類處理：

1. 留存最終產出、已確認決策、必要限制與下一步所需事實。
2. 保留關鍵判定、執行狀態、驗收及復現失敗所需的證據。
3. 以引用交接下一步必需的輸出、來源和 Current 狀態。
4. 清除不再被引用、不再支撐驗收或診斷的暫存；必要歷史改封存而非直接刪除。

仍被開啟封包引用、仍用於復現失敗、仍支撐未完成驗收或有保留規則的資料，不得提早退場。

### 2.8 先比對既有，再決定重用或新增

新增能力／系統前先確認既有流程並寫明 REUSE / MODIFY / MERGE / NEW。NEW 必須列出已查的候選與它們為何不能修改或合併；不可因入口、名稱或視圖不同就重造一份功能。對 P2 Schema 與 Current 的變更須先做相容性核對，避免第二份權威資料。

## 3. 概念分支：保留而不強行合併

本章的「分支」是不同概念／觀察軸，不是要求建立多套競爭的主流程。它們可以互相引用，不能互相取代。

### BR-01｜H0–H3 問題解決流程（目標流程軸）

- **核心：** H0 解決問題；H1 五步；H2 為基本步驟；H3+ 才展開實際選擇與因果分支。
- **用途：** 決定一個問題在邏輯上需要經過哪些環節。
- **不代表：** 每個環節都必須形成獨立檔案，或每個微小動作都得產生封包。
- **來源：** 封包 B 對話紀錄、企劃書 v0.1。
- **狀態：** 討論概念已獲認同；正式權威化仍待 P2 藍圖對帳。

### BR-02｜封包類型（工作單元分類軸）

企劃書把工作單元分為規劃、藍圖、施工、驗收、修正五種。它們按「本次工作性質」區分，不是另一套 H1 流程，也不是每一種各自一套控制器。

| 封包類型 | 輸入要點 | 主要輸出／接受條件 |
|---|---|---|
| 規劃 | 原始目標、範圍、限制、未知 | 可執行方案、選擇理由、驗收標準 |
| 藍圖 | 已確認規劃、既有架構、依賴 | 變更位置、責任、依賴、驗收要求 |
| 施工 | 核准範圍、必需輸入、權限 | 實際差異、產物、執行與錯誤證據 |
| 驗收 | 原接受條件、輸出及證據 | 獨立判定通過／失敗／阻塞 |
| 修正 | 已定位的失敗或差異 | 最小修正、根因依據、回到正確驗收點 |

一個封包類型可能跨越 H1 的多個環節；一個 H1 環節也可能包含不同類型的封包。不要強行做一對一映射。

#### 四段主鏈與第五種修正封包的差別

對話階段曾用四段連續工作封包描述一般主鏈：**規劃 → 藍圖 → 施工 → 驗收**。企劃書 v0.1 隨後把「修正封包」加進封包類型清單，形成五種工作類型。

這兩個版本要一起保留，不把差別壓平：

- **四段主鏈：** 描述一般工作從規劃到驗收的主要交接順序。
- **五種工作類型：** 在四種常見類型外，加入「修正」作為失敗、驗收未通過或證據定位出缺口時的條件式工作類型。
- **融合解讀：** 修正不一定是每次任務的必經第五階段；它可作為由 FAIL／BLOCKED 或驗收結果觸發的分支封包，完成後返回受影響的施工／驗收步驟。
- **仍需決策：** 正式實作時要決定「修正」是封包類型、封包的回退路由，或兩者皆有；在與 P2 現有契約對帳前，不先增加第二套狀態機。


### BR-03｜角色／系統責任拓樸（責任軸）

封包 A 的 HANDOFF 引述 P2 系統主軸有主核心、Brain、Central、Role 與臨時工程工作群、Current／執行事實、能力與知識、System Factory、Assurance、F30 批次階段協調器。封包 B 企劃則主張不要把 Brain、Central、Role、Runtime、Knowledge、Assurance 當成互相獨立的平行流程。

**融合判定：兩者不必互相否定。** 保留責任邊界與角色權限；把它們映射到共同問題流程的節點與動作中。流程是「事情怎麼發生」，責任拓樸是「誰做什麼與誰擁有權威資料」。不能因流程共用就取消角色隔離、獨立驗收或資料所有權。

HANDOFF 所述連線順序是：使用者目標 → 讀 Current 與必要藍圖 → Brain 理解並選方案 → 定義交接契約與有界 Work Unit → 臨時工作群施工 → 獨立驗收 → 更新唯一 Current → 蒸餾可重用結論。此段仍屬 HANDOFF_CLAIM，須對照 ZIP 本體與 P2 權威來源。

**「現況重疊」與「目標單一流程」須保留為不同命題：** HANDOFF 聲稱既有程式中並存多套階段／閉環骨架；封包 B 企劃則提出把未來運作收斂成單一主流程。前者是尚待 ZIP 本體驗證的現況診斷主張，後者是未核准的目標設計，不能視為互相矛盾，也不能當成已完成合併的證據。

### BR-04｜F30 四階段工程生命週期（能力成熟度軸）

HANDOFF 的 F30 四階段規則為：

1. **藍圖：** 節點有重點、待辦有排序。
2. **能運行：** 每個功能有入口與退出，退出碼 0。
3. **閉環：** 有正確呼叫、結束、退場及可重用的程式化結果。
4. **實際運行：** 必須有真實執行證據；沒有證據標 NOT_EXECUTED。

這四階段不是 H1 的替代品，也不是封包狀態機。H1 說明處理問題的步驟；F30 說明新能力／工程成果達到哪個成熟度。每個 H1 環節可涉及不同成熟度的功能。

**證據限制：** F30 與工作狀態來自 HANDOFF 描述；封包 A 位元組尚未取得，尚不能重新核對其源碼與測試。

### BR-05｜封包狀態（單一工作單元的運行軸）

封包 B 企劃提出的六種最小狀態是 WAITING / READY / RUNNING / PASS / FAIL / BLOCKED。

| 狀態 | 含義 | 合法後續 |
|---|---|---|
| WAITING | 等待上游封包或必要條件 | 條件成立後重新評估 |
| READY | 必需輸入、前置條件與權限成立 | 可開始執行 |
| RUNNING | 工作開始但未定案 | 等待結果 |
| PASS | 預先定義的接受條件通過，證據足夠 | 依已確認的 next 引用推進 |
| FAIL | 有可評估結果，但未達接受條件 | 根因分析／修正，再驗收 |
| BLOCKED | 不能合法或可靠地開始／繼續 | 解阻後重新評估，或停止 |

這是提案中的初步最小模型，不是已核准 Schema。正式開發前，須對照 P2 既有狀態機及 Task／Result／Execution／Current 契約；可重用就重用。不得把證據等級、阻塞原因或生命週期成熟度塞進狀態枚舉。

### BR-06｜證據標籤（證據軸）

封包 A HANDOFF 使用的標籤包括 PROGRAM_EXECUTED_PASS、SIMULATED_PASS、PATCHED_UNVERIFIED、NOT_EXECUTED、HYPOTHESIS；封包 B 整理規範另使用 DIRECTLY_INSPECTED、HANDOFF_CLAIM、INFERRED、NOT_VERIFIED、BLOCKED。

這些標籤不是狀態。可用一個獨立證據欄記錄「結論為何可信」；不要用 PASS 代替真實測試證據，也不要用 SIMULATED_PASS 冒充 PROGRAM_EXECUTED_PASS。不同來源中的標籤應先做語意對帳，再決定是否建立統一枚舉。

### BR-07｜會話交接、資源預算與批次編排（操作治理軸）

R3d130j HANDOFF 是 2026-10-16 的一次交接指示，記錄的規則／數字需視為該場次快照，不可直接認定為當前全域標準。它提到：

- 單場限制：讀取不超過 48 KB、寫入不超過 36 KB、工具呼叫不超過 30 次；任一資源到 70% 就停止開新任務並收尾。
- 開工流程：先驗證 ZIP 與交接，再啟動會話；只讀「下一批輸入」，大文件按標題切片。
- 收尾流程：先更新交接資料，再走結案工具；改過程式、登記表或需要全批驗收時，使用對應加強模式。
- 施工前比較：REUSE / MODIFY / MERGE / NEW；不得直接堆疊新模組。
- 固定保護：不隨意修改鎖定權威檔案、不修改既有測試期望；測試必須標示模擬或實跑，不可混用。
- W0–W8 工作計畫和其他待辦為當時交接內容，不是最新 Current。

這些內容屬操作／會話治理，不能拿來取代 P2 的產品架構，也不得在不核對最新規則前當成永遠生效的硬規格。完整原文保留在 [R3d130j-HANDOFF](../原始檔案/交接/R3d130j-HANDOFF.md)。

### BR-08｜模組、功能與能力不是同一層級

- 封包 B 提案映射的是 P2 功能登錄中的 F01–F30，屬「功能／責任」層級。
- 封包 A HANDOFF 聲稱對 182 個模組做過掃描，並稱 15 個模組沒有引用／測試，屬源碼／模組層級的 HANDOFF_CLAIM。
- CAP、角色、工具、Schema、測試、執行封包亦是其他類型的資產。

這些數量不能互相相減或互相比對成矛盾。要確認 30 項功能是否覆蓋所有模組，必須在取得封包 A 真正內容後，建立「功能 ID ↔ 模組 ↔ 入口／呼叫鏈 ↔ 測試 ↔ 證據」映射；不得依名稱相似直接合併或刪除模組。

## 7. 後續開發的融合路徑

本路徑是給後續開發者的建議順序，不表示已在 P2 執行。每階段都先核對權威來源與允許修改範圍。

### D0｜先解封包 A，建立完整來源基線

1. 取得原始 ZIP bytes，核對登錄大小、裸檔 SHA-256、ZIP／Zip64 中央目錄與 EOCD。
2. 建立逐成員 manifest：來源路徑、壓縮／解壓大小、方法、CRC32、格式、狀態、解析文件位置。
3. 按現有八個分類目錄歸檔，但一個成員只能有一個 canonical 位置；其他交叉用途用索引引用。
4. 把 HANDOFF 的每個數字／主張逐項對到實際源碼、呼叫鏈、測試和執行證據。若不可驗，保留 UNKNOWN。

### D1｜凍結概念契約，不直接改程式

1. 將 H0–H2 作為候選簡單主線，確認 H3 分支的必要性和分支記錄方式。
2. 把「流程步驟、封包類型、角色、封包狀態、證據標籤、F30 成熟度」分成獨立欄位或視圖，避免混軸。
3. 定義每個功能的最低條件契約：主要位置、觸發條件、必需輸入、禁止條件、授權／成本 Gate、輸出、接受條件、下一步／失敗回退。
4. 把現有 Task／Result／Execution／Current／Schema 的欄位對齊後才決定是否需要擴充；不直接建立第二份封包真相。

### D2｜建立能力／模組／測試的映射

以 F01–F30 作功能層索引，以實際模組／入口／呼叫鏈作實作層索引，以測試／執行輸出作驗證層索引。三者以穩定 ID 連接，但數量不要求一對一。對「無引用／無測試」模組先查動態呼叫、注入、CLI、配置、反射、外部入口與測試漏失，再裁定重用／接線／合併／退場，不得只依靜態 grep 結果刪除。

### D3｜用小範圍端到端案例驗證閉環

至少包含以下測試案例：

- 正常路徑：前置條件成立 → READY → RUNNING → 結果與證據 → PASS → 合法 next。
- 輸入缺失：不可直接 RUNNING；補資料或 BLOCKED。
- 權限／成本／安全不成立：硬性 Gate 阻止調用。
- 功能觸發不成立：不調用，不因能力存在而強制經過。
- 施工失敗：FAIL，保留錯誤結果與根因候選，不得改寫成 PASS。
- 中斷／重試：能辨識已完成與未完成部分，避免重複副作用。
- 驗收失敗：回到實際問題所在的上游節點，不放寬原接受條件。
- 獨立驗收：Executor 不可自行批准自己的結果。
- 資料退場：有依賴／證據保留需求者不得刪除；可安全清除的暫存才退出。
- Runtime：真實執行證據獨立記錄；模擬結果不得升級。

### D4｜用量測決定是否推廣

簡化前後至少比較：重複功能定義數、錯誤調用率、無效工具調用、上下文／讀取量、交接缺失、狀態漂移、失敗後返工次數、全案閉環成功率。沒有實測數據則標 UNMEASURED，不憑直覺宣稱新模型效率更高。

- [ ] 單封包 PASS 與全案結案分開；全案要有最終驗收、Current 更新和退場判定。
- [ ] Current／程式藍圖／功能矩陣的權威所有權清楚，視圖由來源派生。
- [ ] 測試覆蓋正常、負例、邊界、中斷、重試、權限／成本、驗收失敗與資料生命週期。
- [ ] 模擬、靜態、實際測試、整批驗收與 Runtime 證據標記不混用。
- [ ] 新增功能前有 REUSE／MODIFY／MERGE／NEW 比較；孤兒模組不因無引用／無測試而直接刪除。
- [ ] 結案只保留必要結果、證據與下一步上下文；暫存資料安全退場並可追溯。
