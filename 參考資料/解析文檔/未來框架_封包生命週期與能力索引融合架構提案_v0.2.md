## 0. 結論先行

**維持混合架構，並將討論紀錄與企劃變更控制提升為基礎治理契約：封包負責「一個工作如何受控地完成」；能力系統負責「有哪些可重用的功能、何時可以呼叫、如何被替換」；流程圖負責「何時、依什麼條件，以什麼順序組合能力」；功能樹與索引負責「能力歸屬、查找和導航」；治理契約負責「哪些事可記錄、哪些變更需明確授權、如何比較並確認版本」。這些職責分開，但透過唯一 ID、狀態、版本及證據互相引用。**

不建議把每項功能都塞進單一封包流程樹，也不建議只建一棵龐大的功能樹，然後靠樹狀位置推斷執行順序。前者會讓能力重用困難；後者會混淆分類、因果、職權、狀態和驗收。

推薦的核心關係：

~~~text
基礎治理契約（專案邊界、工作模式、寫入權限、變更 Gate）
        │ 橫向約束所有專案型工作
        ▼
使用者目標／外部事件
        │
        ▼
意圖與範圍正規化
        │
        ▼
工作封包（本次工作實例、輸入、授權、驗收、退出）
        │
        ▼
工作流編排器（依條件建立有向流程／依賴圖）
        │
        ├── 能力索引與路由器 ──► 可替換能力／工具插件
        │                             │
        ◄──────── 結果、產物、證據 ───┘
        │
        ▼
獨立驗收與結案閘門
        │
        ├── 不通過：有界修復、重新路由、阻塞或回退
        └── 通過：保存證據、交接、封存／清理
~~~

基礎治理契約是跨流程的授權與限制，不是每一項任務都要額外跑完的獨立研究步驟。以上是建議的邏輯架構，不代表目前已有對應 Runtime。

## 2. 架構分層與唯一職責

| 層 | 名稱 | 唯一主要責任 | 不應負責 |
|---|---|---|---|
| L0 | 基礎治理與職權 | 定義討論／紀錄／企劃更新權限、變更風險分級、誰能決定／執行／驗收，以及批准與停止條件 | 不代替領域分析或執行細節 |
| L1 | 意圖／任務路由 | 把使用者要求正規化成目標、輸出、限制、深度、風險與候選路線 | 不直接承擔所有分析、搜尋或施工 |
| L2 | 工作流編排 | 建立步驟、條件、依賴、分支、重試、回退與停止路徑 | 不複製每個插件的內部演算法 |
| L3 | 工作封包 | 保存本次工作實例的範圍、狀態、輸入、決策、驗收和交接 | 不當作整個能力目錄或永久知識庫 |
| L4 | 能力登錄與插件契約 | 定義能力的 ID、輸入／輸出、前置條件、版本、權限、成本和替換狀態 | 不自行決定整條工作流順序 |
| L5 | 執行介面／工具適配器 | 把已授權的能力請求轉交模型、程式、外部工具或服務，正規化返回值 | 不繞過編排、權限和驗收 |
| L6 | 證據、產物與知識 | 保存來源、決策依據、執行輸出、測試和可重用結論 | 不把計畫或推論偽裝成已執行事實 |
| L7 | 版本、影響、退場與演進 | 管理相容性、回歸範圍、灰度／切換、棄用、回退和最終退場 | 不私自改變既有工作封包的驗收標準 |

此處的分層表示責任邊界，不要求一開始就拆成多個服務或專案。初期可採同一 Repository、同一執行環境中的模組化結構；只有當獨立部署、隔離或擴展需求有實證時，再拆出程序或服務。

## 3. 工作封包：將工作閉環做成可組合的基本積木

### 3.1 封包是工作實例，不是所有功能的容器

封包的單位應是「可明確界定輸入、輸出、權限和驗收的一段工作」。封包可以引用多個能力，也可以由父封包管理子封包；但不應為每個微小操作都建立完整封包。只在有獨立責任、狀態、驗收、交接或回退價值時，才拆成子封包。

應分開三個物件：

- **封包模板（Packet Template）：** 定義某類工作反覆需要的欄位、必備 Gate、預設流程和驗收方式。
- **封包實例（Work Packet）：** 本次工作的實際目標、輸入、狀態、決策、輸出和證據。
- **執行紀錄（Run Record）：** 每一次能力／工具實際呼叫的輸入摘要、版本、開始／結束狀態、輸出指紋、錯誤與重試資料。

模板更新不應追改已經執行完的實例；實例應固定記錄自己實際採用的模板與能力版本。

### 3.2 封包契約的建議欄位

| 欄位群 | 必要內容 | 用途 |
|---|---|---|
| 身分與版本 | packet_id、packet_type、template_id、template_version、parent_packet_id、schema_version | 可追溯且不因重新分類而失去身分 |
| 啟動條件 | trigger、preconditions、scope、explicit_authorization、resource_limits | 判斷何時能開始及何時必須阻擋 |
| 目的與原因 | goal、expected_outputs、success_criteria、rationale、priority | 區分「要達成什麼」和「為什麼做」 |
| 資料與認知狀態 | inputs、source_refs、assumptions、unknowns、conflicts、sensitivity | 不把來源主張、假設與已確認事實混在一起 |
| 方法與施工 | selected_workflow_ref、plan、dependency_refs、capability_refs、tool_refs、retry_budget | 記錄選定路線、前置依賴和允許的執行範圍 |
| 職權 | owner_role、executor_role、verifier_role、approval_gates、allowed_write_scope | 防止執行者越權或自己核准自己的結果 |
| 產物與證據 | artifact_refs、decision_log_refs、run_record_refs、evidence_refs | 對結果提供來源和執行證據 |
| 驗收與退出 | acceptance_criteria、exit_conditions、failure_policy、rollback_plan、handoff_requirements | 定義怎樣算完成、怎樣停止、失敗後怎樣處理 |
| 生命週期 | status、created_at、updated_at、closed_at、closure_reason、retention_policy | 支援進度追蹤、交接和資料保留／清理 |

不同封包類型可以透過 schema profile 增減欄位；不要強迫每個小型查詢都填滿所有欄位。但高風險、跨模組、長時間或不可逆操作必須要求更完整的權限、驗收、備份與回退資訊。

### 3.3 建議的封包生命週期

```text
DRAFT → ADMITTED → READY → RUNNING → VERIFYING → ACCEPTED → CLOSED
                     │          │           │
                     ├─ BLOCKED ├─ FAILED   └─ REJECTED
                     │          │                │
                     └─ CANCELLED               └─ 有界修復後重新驗收
```

以上狀態是提案，後續應以正式 Schema 固定允許轉移。額外規則：

- 只有前置條件、授權與必要輸入齊備，才能由 DRAFT／BLOCKED 進入 ADMITTED／READY。
- 執行失敗不等於封包自然結束；必須選擇有界重試、替代能力、退回規劃、阻塞、取消或回退。
- 驗收拒絕不能靠修改接受標準來「做成通過」。
- 結案必須記錄最終狀態、實際輸出、未解限制、必要證據、下一個負責者與保存政策。
- 任務封包的結案狀態，不等於能力模組已退場；兩者使用不同狀態機。

### 3.4 封包結束、退出與退場的差異

- **結束條件（exit condition）：** 本次工作是否已達到目標、遇到停止條件或無法繼續的狀態。
- **退場機制（rollback／recovery／retirement）：** 工作或能力停止後，要如何恢復狀態、切換替代路線、保全證據及處理剩餘資料。
- **封包結案（closeout）：** 對本次工作結果、證據、限制、交接和資料保存做最後核對。
- **能力退場（capability retirement）：** 一個可重用能力不再接受新工作、完成遷移、等待依賴清空後，才正式停用或移除。

不應把這四件事縮成一個 `done=true`。

## 4. 能力系統：唯一歸屬、跨流程重用、獨立替換

### 4.1 一個能力只定義一次，允許多個入口與用途

每個能力應有穩定的 canonical ID 和唯一正式定義。功能樹提供一個主要歸屬位置，方便管理與責任歸屬；標籤、同義詞、用途、入口、相關概念、父子關係和依賴另行登錄。樹狀位置不限制能力只能被一個流程呼叫。

不要為「分析文件」「逆向分析」「根因分析」「比較分析」直接複製四份共用核心。如果其輸入、輸出、判定規則和驗收標準實際不同，可以建立不同的任務模板或專用能力；若只是同一能力的不同上下文或深度，使用同一 canonical capability 加上設定檔／參數。

### 4.2 能力登錄欄位

| 欄位群 | 最低要求 |
|---|---|
| 身分 | capability_id、名稱、別名／同義詞、分類、主要歸屬、版本 |
| 意圖 | purpose、適用／不適用情境、典型使用案例、負面案例 |
| 契約 | input_schema、output_schema、side_effects、idempotency／重複呼叫規則 |
| 啟動 | preconditions、required_inputs、permissions、risk_level、resource_budget |
| 行為 | execution_adapter、選用方法／深度、錯誤碼、可重試錯誤、停止條件 |
| 關係 | dependency_refs、replacement_for、consumed_by／引用者、impact_scope |
| 驗收 | contract_tests、representative_cases、counterexamples、evidence_requirements |
| 演進 | lifecycle_state、deprecated_since、replacement_id、migration_guide、rollback_version |
| 觀測 | invocation_count、failure_rate、latency／cost、acceptance_rate、last_verified_revision |

欄位可分成必填核心和按風險啟用的擴充欄位。正式 Schema 應先定義哪些欄位是必填、哪些是選填，以及缺少欄位的預設與阻擋行為。

### 4.3 功能索引的三種入口，不是三套功能

1. **功能樹（歸屬入口）：** 回答「這項能力的主要責任和管理位置在哪裡？」
2. **語義索引／標籤（查找入口）：** 回答「使用者用不同詞語提出這類需求時，該找哪些候選能力？」
3. **流程／依賴圖（執行入口）：** 回答「完成這個目標需要呼叫哪些能力，順序和條件是什麼？」

三種入口只保留參照 ID，不複製能力完整定義。可在不同視圖中顯示同一能力，但不能因此生成第二份正式定義。

## 5. 重疊功能的處理：以「組合工作流」解決，不以複製能力解決

### 5.1 範例：「搜尋也需要分析」

將這類任務拆成三種不同責任：

- **搜尋能力：** 從指定來源取得資料，產生來源、時間、查詢條件和擷取結果；它的主要驗收是相關性、來源可追溯性和覆蓋範圍。
- **分析能力：** 依據輸入資料回答問題，產生比較、因果候選、限制、反例或結論；它的主要驗收是推理鏈、資料支持、反證處理和不確定性標記。
- **研究分析工作流：** 根據任務需要，先搜尋／擷取，再分析；若需要補證據，回到搜尋或證據補齊分支，最後整合與驗收。

因此，一個任務同時需要搜尋和分析時，封包引用兩項能力並由編排器設定先後關係。這不是功能重疊的錯誤，而是組合式工作流的正常情況。真正應避免的是同一段搜尋或推理邏輯被複製在多個能力內，導致版本和驗收不一致。

### 5.2 「分析」應先作為意圖入口，而不是無條件執行的萬能模組

使用者說「分析」時，路由器先確認分析對象、目標產物與必要深度，再選擇適用的流程：

- 已有完整資料，要求解釋或比較：直接分析現有輸入，必要時補上證據／反例能力。
- 需要外部資料才能回答：組合搜尋、來源驗證和分析。
- 要理解陌生專案結構：組合來源盤點、靜態檢查、架構映射、差異／依賴分析與驗收。
- 要找故障根因：組合狀態確認、假設生成、針對性診斷、反例或重現、根因驗證與修復驗收。

上述為路由設計範例，不代表這些能力目前已全部實作。真正路由應依能力登錄裡已存在且通過適用驗證的項目，不得因名稱相近而假定其可用。

### 5.3 路由判斷順序

1. **硬性 Gate 優先：** 權限、使用者明確限制、安全／隱私、寫入範圍、不可逆動作、必要資料缺失；不符即阻擋或要求補件。
2. **目標與輸出：** 這次最終要交付的結果是什麼。
3. **意圖與領域：** 搜尋、分析、施工、驗收、整理、研究等任務型態。
4. **契約匹配：** 候選能力的輸入／輸出 schema、前置條件與限制是否符合。
5. **依賴與重複消除：** 將候選能力組成有向無環依賴圖；同一 canonical ID／同一輸入版本的重複步驟應合併，除非需求明確要求獨立重跑。
6. **深度與資源：** 按使用者要求和任務風險選擇最低足夠深度，再評估時間、成本、上下文和工具額度。
7. **記錄選擇理由：** 記下選用能力、被拒候選、條件、能力版本和未解不確定性，便於後續診斷。

如果多個候選都符合，不應無條件全部執行。優先選擇契約匹配且滿足成功條件的最小組合；若差異會實質改變結果而無法裁定，則分支並行比較或要求最小必要澄清。能力不可用時，要明確標示缺口／阻塞，不能只因名字存在於索引就宣稱能執行。

## 6. 職權與責任切分

職權、功能分類和封包階段必須是三個不同欄位。不能因某能力被歸在「分析」樹下，就自動獲得規劃、寫入、批准或驗收權限。

| 角色 | 負責決策／操作 | 明確禁止或限制 |
|---|---|---|
| 治理／授權者 | 高風險與不可逆動作批准、全局範圍、權限和停止規則 | 不應繞過留存的變更記錄和驗收 Gate |
| 認知／研究決策者 | 理解目標、建立問題模型、比較方案、提出路線和範圍 | 不因提出方案就宣稱施工或驗收完成 |
| 協調器／工作流編排器 | 讀取契約、判斷狀態轉移、安排依賴、選能力、記錄結果和分支 | 不包辦所有領域推理、不讓插件互相任意直連 |
| 執行者／能力適配器 | 在核准範圍內呼叫工具、產生產物、回報實際執行結果 | 不擴大授權、不改驗收標準、不自授最終 PASS |
| 獨立驗收者 | 對預先定義的接受條件檢查產物、差異和證據，給出 PASS／FAIL／BLOCKED | 不暗中修改被驗收產物來讓結果通過 |
| 能力／登錄管理者 | 管理正式定義、版本、別名、依賴、替代關係、棄用和退場 | 不僅因新版本存在就立即刪除舊版 |
| 證據／知識保管者 | 保留來源、運行紀錄、結論、限制和歷史可追溯性 | 不把未執行、假設或推論升格為事實 |

這些是邏輯職責，不必一開始就由七個獨立代理或七個服務承擔。可先採角色契約和明確輸入／輸出邊界；高風險工作再加強執行／驗收隔離。

### 6.1 變更權限的最小規則

- 任務提出者／控制者可定義目標、核准範圍和接受條件。
- 「研究／討論」「研究紀錄」與「更新企劃／權威規格」是三種不同授權；前兩者不自動授權後者。
- 對企劃的確認只對已展示的目標文件、基準版本、差異分類與預定寫入範圍有效；實質變更後須重新確認。
- 執行者只能改授權範圍內的產物，不能偷偷改規格。
- 驗收者只對照契約與證據判定結果；失敗時退回修復流程，不直接接手修補後自我通過。
- 能力版本、工作流模板、schema 或共享規則的變更，必須有變更影響分析和適用回歸。
- 對權威狀態、索引或核心契約的更新，都要先確認唯一寫入位置，再做寫後讀回和連結／Schema 驗證。

### 6.2 基礎治理能力：討論紀錄與企劃變更控制

這項能力是所有 forAVAr 專案型工作的基礎治理契約，不是可由普通路由器任意跳過的分析插件。為避免只寫在文件裡卻無法執行，治理契約、紀錄能力、企劃變更能力與啟動載入機制分開定義；以下 ID 為本提案候選 ID，尚非已登錄或已實作能力。

| 候選能力／契約 ID | 唯一責任 | 啟動條件 | 主要輸出 | 明確禁止 |
|---|---|---|---|---|
| FORAVAR-GOV-BASELINE | 定義專案寫入邊界、工作模式、權限優先序及企劃更新 Gate | 每次開始或接手 forAVAr 專案工作 | 已載入的治理版本、權限／模式判定 | 不承擔領域研究，也不把提案自動升格為已核准規格 |
| FORAVAR-CAP-DISCUSSION-RECORD | 建立與維護研究紀錄的主題／輪次、證據及歷史連結 | 新主題、同輪持續研究、或同一主題開始新的研究輪次 | 獨立 Markdown 紀錄、record ID、相關紀錄引用、索引更新要求 | 不覆寫先前輪次，不藉由記錄結果修改權威企劃 |
| FORAVAR-CAP-PLAN-CHANGE-CONTROL | 管理企劃／權威規格的比較、分類、影響分析、使用者確認、整合及驗收 | 使用者明確授權更新企劃，且目標與範圍可識別 | 新舊差異表、變更分類、影響清單、授權狀態、新版本及驗收紀錄 | 確認前不得整合；不得擴張確認範圍；不得寫入 P1／P2 |
| FORAVAR-GOV-BOOTSTRAP-VERIFY | 驗證每個新會話／專案入口是否載入治理契約 | 新會話、交接或任務入口 | 載入狀態及啟動測試結果 | 不得因檔案存在就宣稱載入成功或行為已驗收 |

#### 基礎工作規則

- 沒有明確企劃更新授權時，只能進行研究、分析、討論與紀錄；不得修改權威企劃。
- 不同主題須建獨立紀錄；同一研究輪次可持續更新當輪紀錄；同主題在後續重新開展時另建新檔並連結舊檔。
- 接受研究結論、同意建立紀錄或一般性的「繼續／完善」不自動等於同意修改企劃。
- 收到企劃更新授權後，先比較舊版與新方案，逐項列出融合、取代、保留、淘汰及待驗證內容，並說明理由與影響；經使用者確認後才整合成新的權威版本。
- 確認綁定到所展示的差異、基準版本及明列範圍。確認後若差異實質改變，必須重新比較並重新確認。
- 在寫入前重新核對基準；寫入後回讀文件、核對索引／矩陣／連結及驗收結果。失敗時明確標記 FAIL／BLOCKED，不得宣稱完成。
- 使用者指定的專案邊界持續有效：forAVAr 是唯一可寫專案；P1、P2 僅作唯讀參考。

#### 啟動載入的實作限制

把這些要求列入架構，只能證明目標規格已文件化，不能保證所有後續對話或 Agent 會自動讀取。正式採用前須指定唯一啟動入口、載入順序和缺載入時的阻擋行為，並執行跨新會話測試。未完成上述工作前，能力狀態應標示為 PROPOSED／NOT_VERIFIED，而非 ACTIVE／VERIFIED。

本節定義的是目標能力與驗收要求，不表示目前 ChatGPT 執行環境已自動載入該文件或已具備可驗證的 Runtime。

## 7. 能力、封包、產物使用不同的生命週期

| 物件 | 建議狀態 | 狀態轉移原則 |
|---|---|---|
| 工作封包 | DRAFT、ADMITTED、READY、RUNNING、VERIFYING、ACCEPTED、CLOSED、BLOCKED、FAILED、CANCELLED、REJECTED | 由前置條件、施工結果和驗收證據推動，不以文字摘要自行改狀態 |
| 能力版本 | CANDIDATE、ACTIVE、DEPRECATED、QUARANTINED、RETIRED | 新版先驗證，再切流量；舊版先棄用，等依賴遷移後才能退場 |
| 工作流模板 | DRAFT、VALIDATED、ACTIVE、DEPRECATED、RETIRED | 變更模板時做契約和分支覆蓋測試；既有封包保留所使用的模板版本 |
| 產物／暫存 | ACTIVE、REFERENCED、ARCHIVED、ELIGIBLE_FOR_CLEANUP、DELETED | 被引用、支撐驗收、故障復現或保留政策要求時不能清除 |
| 證據紀錄 | RECORDED、VERIFIED、SUPERSEDED、RETAINED／ARCHIVED | 新證據可取代目前判斷，但不能抹除舊判斷形成的歷史軌跡 |

具體狀態字串與是否需要所有狀態，需由正式 schema 和真實案例裁定。上表是概念提案。

## 8. 更新疊代、替換和回退

### 8.1 快速更新的關鍵不是省略驗收，而是縮小改動面

1. 先確認變更授權與類型：研究紀錄、低風險文件整理、企劃／規格變更、破壞性／跨權威／權限變更；再辨識文件／索引、能力實作、能力契約、工作流、共享 Schema 或資料生命週期等受影響對象。
2. 由變更影響登錄反查受影響能力、封包模板、消費者、測試和資料。
3. 優先只替換能力的內部實作；只要對外輸入／輸出契約仍相容，就不要求所有呼叫者一起改。
4. 若契約不相容，建立新版本和遷移策略，不直接覆蓋正在被工作封包引用的版本。
5. 先核對實際差異仍與已確認方案一致；若範圍或語義已實質改變，返回差異比較並重新取得確認。再跑契約測試、代表性成功／失敗案例和受影響回歸；按風險決定是否需完整整合驗收。
6. 比較新舊版本的結果和指標；符合啟用 Gate 才更新路由。
7. 觀察新版本實際使用狀況；有回歸、成本惡化或驗收失敗時，切回最後已驗證版本。
8. 記錄變更、驗收證據、路由切換、回退結果和剩餘風險，再處理舊版退場。

### 8.2 相容性規則

- 能以向後相容的方式增加欄位時，應保留舊欄位語義並為新欄位訂定預設行為。
- 刪除、改名或改變欄位意義屬潛在破壞性變更；須升版、提供轉換／遷移並覆蓋舊版消費者。
- 執行中的封包要固定引用其實際採用的能力／工作流版本，避免中途改版導致同一任務重播出不同路徑。
- 回退不只切回程式，也須確認輸出資料、狀態、外部副作用和證據是否能被安全恢復。
- 任何能力升級、插件替換或外部工具更改，都不能單憑新版本號判定優於舊版；需依指定任務、驗收和維護成本比較。

## 9. 資料、證據與結案

每個能影響重要決策的步驟，最低保留一條可以回溯的因果鏈：

```text
來源／觸發
  → 前置條件核對
  → 選擇的能力／版本與理由
  → 執行紀錄
  → 輸出／產物
  → 驗收標準與結果
  → 後續分支／交接／結案
```

資料最少區分：原始來源、規範化輸入、假設／未知／衝突、執行中間產物、最終輸出、驗收證據、可重用知識。引用優先使用穩定 ID、版本或雜湊，不在每個封包重複貼入整份歷史。

關閉工作封包前需確認：

- 最終輸出符合原始目標，且沒有偷改成功標準。
- 所有必需接受條件均有實際證據；未執行的檢查標示 NOT_EXECUTED，不可標 PASS。
- 已記錄失敗、未知、限制、被排除的範圍和剩餘工作。
- 下游封包取得必要的引用、版本、狀態與輸入，而不是複製無關歷史。
- 暫存只有在沒有活躍引用、不再支撐診斷／驗收且符合保留政策時，才進入清理。
- 有損壞風險或不可逆變更時，已保存所需恢復資料並明確記錄退場／回退結果。

## 10. 防止架構隨功能增長而失控的規則

1. **一個概念、一份正式定義。** 摘要、流程、圖表和交接文件都引用 canonical ID，不複製完整規則。
2. **樹表達歸屬、圖表達關係、封包表達本次工作。** 三種結構不可混成單一樹。
3. **插件不直接任意互叫。** 由編排器統一控制依賴、權限、版本和資料流；如果未來要開放能力間直接呼叫，必須有契約、授權和循環依賴檢查。
4. **路由器只做路由。** 不把大段領域邏輯塞入中央控制器；每個能力擁有自己的領域定義、契約和測試。
5. **預設最小足夠流程。** 不把簡單問答強迫包成完整重流程；只在風險、複雜度、跨系統、不可逆或驗收要求達到門檻時擴大封包。
11. **明確分離紀錄授權與企劃更新授權。** 新主題／新研究輪次獨立建檔；研究紀錄可依紀錄規則更新，但權威企劃不得因討論結論、一般性的「繼續／完善」或研究紀錄獲得肯定就被修改。
12. **確認必須綁定具體差異。** 保存基準版本、目標路徑、變更分類、預定寫入範圍與方案識別；確認後如實質差異改變，需重新確認。
13. **規則載入需有實際入口與測試。** 文件寫好不代表能力生效；應在啟動契約指定唯一載入入口與讀取順序，並以跨新會話測試驗證。
14. **沒有合格候選時維持現狀。** 不為了達成「有更新」而硬做變更；可保留當前版、標記 BLOCKED 或要求缺失資訊。
6. **未知與衝突一級化。** 候選能力、版本、來源或必要資料不存在／衝突時要記錄並阻塞，不推斷出不存在的能力。
7. **深度漸進。** 基本任務走穩定淺層；遇到證據不足、重大分歧、依賴或反例時才展開更深分支。
8. **退場要有前置檢查。** 查無新呼叫者、遷移完成、證據保留、回退路徑與資料清理政策通過後，才能移除舊能力。
9. **高風險變更有完整回歸，低風險變更縮小驗收面。** 根據變更影響而不是一律全量或一律不測。
10. **不因抽象漂亮就預先實作所有模組。** 先建立最小契約、最小能力集和真實案例，根據使用頻率與失敗證據增補。

## 11. 建議實施順序

### Phase 0｜核對權威和凍結命名原則
- 對帳本提案與既有 P2 封包整合主文件、功能樹、重疊矩陣和去重規範。
- 明確區分目前已證實、提案、推論和待實作事項。
- 裁定穩定 ID、版本欄位和唯一權威登錄表的歸屬。
- 驗收：沒有第二份 Current、第二份功能定義或把提案誤標成已實作。

### Phase 1｜先定資料契約，不急著大規模施工
- 定義 Work Packet、Capability Definition、Workflow Template、Run Record、Evidence／Artifact Reference 的最小 Schema。
- 定義封包狀態、能力狀態和資料生命週期三組不同狀態機。
- 定義角色契約、可寫範圍與不可逆操作的批准 Gate。
- 驗收：有效案例可通過 Schema；缺必填資料、不合法狀態轉移和越權操作會被明確拒絕。

### Phase 2｜建立最小能力登錄和路由
- 先為目前真實需要的能力建唯一 ID、用途、輸入／輸出、前置條件、適用／不適用情境和版本。
- 將別名／同義詞、標籤與候選用途映射到 canonical ID；禁止複製模組作為搜尋捷徑。
- 建立「搜尋＋分析」等少量代表性組合流程。
- 驗收：不同詞語可導向同一 canonical 能力；複合任務可組合能力且無重複執行；沒有合適能力時回報缺口。

### Phase 3｜建立受控執行和獨立驗收
- 由編排器負責呼叫能力、處理回傳值、狀態轉移、重試預算和停止條件。
- 保存實際執行與驗收證據，分開設計／模擬／程式測試／真實 Runtime 等證據層級。
- 驗收：施工、失敗、回退和不通過路徑均有明確終點；執行者不能自行修改驗收結果。

### Phase 4｜加入版本、影響分析與退場
- 建立能力消費者／依賴關係、變更影響登錄、相容性檢查、回歸選擇和退場流程。
- 支援新舊版本並存、指定版本引用、切換和回退；完成遷移前不能移除仍被使用的版本。
- 驗收：模擬破壞性契約變更時會觸發升版、遷移和適用回歸；已退場能力不會被新封包選用。

### Phase 5｜依測量結果再擴充
- 用真實任務記錄路由正確性、重複能力呼叫、失敗返工、驗收率、版本替換耗時和單次任務資源成本。
- 先建立基準值，再訂改善目標；在沒有基準前不虛構 KPI 數字。
- 只擴充有明確使用情境、責任邊界和驗收方法的模組。

## 12. 量測指標與比較方法

| 指標 | 定義 | 用途 |
|---|---|---|
| 路由準確率 | 被選擇的流程／能力是否符合預先核定的預期路線 | 找出路由器錯選與漏選 |
| 重複呼叫率 | 同一任務中對相同輸入、相同目的的非必要重複執行次數 | 發現功能重疊或資料流設計不良 |
| 無法路由率 | 已有需求卻無合適候選，或資料不足／版本不可用而阻塞的比率 | 找出能力缺口，並區分必要阻塞和索引缺失 |
| 返工率 | 初次驗收失敗後需重新施工的比例 | 評估契約、規劃和執行品質 |
| 驗收證據完整率 | 必要驗收條件具有可核對證據的比例 | 防止只看產物存在就宣稱通過 |
| 替換週期 | 從候選版本建立到完成驗證、切換及回退觀察的時間 | 評估插件可替換性與更新速度 |
| 變更擴散面 | 一次局部能力變更影響到的文件、契約、能力與測試數量 | 評估模組邊界是否有效 |
| 結案可復現性 | 後續人員能否透過封包引用、版本和證據理解及重建重要決策 | 評估交接品質 |

量測應以固定的代表性任務集比較「只有功能樹」「只有封包流程」和「混合架構」三種方法；記錄完成時間、重複執行、返工和證據缺口。沒有實驗結果之前，結論只能是設計建議，不能宣稱已證明效率較高。

## 13. 主要風險與控制

| 風險 | 可能後果 | 控制方式 |
|---|---|---|
| 封包欄位過多 | 簡單任務也產生沉重流程 | 依風險和複雜度採欄位 profile；允許低風險短路 |
| 能力分類太細或太多別名 | 路由混亂、同義重複、索引難維護 | 穩定 canonical ID；別名只索引，不建立新定義 |
| 只有樹沒有依賴圖 | 不知道真正的執行順序、循環和條件 | 以獨立流程／依賴圖表示條件與資料流 |
| 中央路由器越做越大 | 形成單點瓶頸，修改影響全系統 | 路由只掌握通用規則，領域行為留在能力契約 |
| 插件間任意互相呼叫 | 隱藏依賴、循環、難以測試和替換 | 由編排器控制呼叫；依賴需登錄並檢查 |
| 新版覆蓋舊版 | 未結束工作中途改變行為，無法回退 | 封包固定版本；新版並存驗收，逐步切換 |
| 自動清理過早 | 失去驗收、診斷、審計或重建所需資料 | 依賴、保留和證據 Gate 通過後才清理 |
| 把模擬當實測 | 錯誤宣告完成、無法復現 | 明確標註證據層級和 NOT_EXECUTED |
| 一開始過度微服務化 | 部署、通訊、監控及版本成本超出收益 | 先以模組化單體／單一 Repository 實證，再按需求拆分 |

## 16. 討論紀錄與企劃變更治理：核心契約

本節將使用者明確提出的工作規則轉為可驗收的架構要求。它補充既有封包／能力／工作流架構，不取代通用問題屬性導向方法選擇框架 v0.2。

### 16.1 三種工作模式，分開授權

| 模式 | 允許的操作 | 不自動包含的權限 |
|---|---|---|
| DISCUSS / RESEARCH | 思考、外部研究、比較、反證、形成候選結論 | 修改企劃或權威規格 |
| RECORD | 建立或更新本輪研究紀錄、整理來源、更新必要索引與文件責任紀錄 | 將研究結論升格為正式企劃 |
| PLAN_UPDATE | 比較與整合企劃內容，依確認後範圍建立新版本 | 實作程式、修改 P1／P2 或擴張未核准範圍 |

使用者明確授權更新企劃後，可先進入差異準備階段；在差異與影響方案被確認前，不可整合成新的權威版本。若目標或範圍不清楚，應先釐清或保持在候選方案狀態，而不是自行選擇可能改變權威內容的寫入範圍。

### 16.2 討論輪次與文件管理

- 同一主題、同一研究輪次的連續討論，可補充該輪紀錄，以維持狀態更新。
- 新主題需建立獨立紀錄。
- 同主題在後續另開一輪進行二次研究、反證或深度延伸，也需建立新檔；引用舊紀錄，不直接覆寫。
- 每份紀錄最少保存：record_id、主題、日期、前置／相關紀錄、唯一責任、狀態、關鍵結果、證據與限制、未決問題及後續驗證。
- 逐字聊天備份與研究整理紀錄是不同的資料類型。除非實際保存了逐字匯出，不可把彙整文件宣稱為完整逐字紀錄。
- README 與職責矩陣各自維持唯一責任：README 負責導航和閱讀順序；職責矩陣負責文件權威、角色與引用方向；詳細研究證據留在專屬紀錄。

### 16.3 變更風險分級

| 分級 | 用途 | 最低程序 |
|---|---|---|
| R0｜研究紀錄 | 新增／補充本輪研究，不改權威企劃 | 記錄主題、證據邊界與狀態；更新必要索引；寫後讀回與連結檢查 |
| R1｜低風險整理 | 不改語義、權威狀態或對外契約的格式／連結整理 | 核對前後差異，確認沒有語義改變，執行相關文件檢查 |
| R2｜企劃／規格變更 | 改變方案、要求、方法規格、能力契約或權威內容 | 基準盤點、新舊比較、變更分類、影響分析、使用者確認、確認範圍重核、寫後驗收 |
| R3｜高影響／破壞性變更 | 改變寫入權限、權威來源、相容性、資料生命週期或多個下游系統 | R2 全部程序，加上明確風險／回退計畫、依賴與回歸評估；未核准不可執行 |

分級依實際語義、風險和影響面決定，不以行數或檔案大小判定。跨多個文件但不改權威語義的導航同步，可以走適當的低風險檢查；修改一行卻改變授權、成功標準或權威地位，仍需走 R2／R3。

## 17. 企劃更新的標準程序

### 17.1 比較前

1. 讀取當前權威文件與相關歷史版本。
2. 確認目標文件、基準版本、目的、使用者限制和可修改範圍。
3. 蒐集新研究紀錄及可支持變更的證據；把外部研究主張、工程推論和未驗證假說分開。
4. 若無法確認目標權威文件或版本，先列出已確認的範圍與未知點，不進入整合。

### 17.2 差異提案必備欄位

| 欄位 | 必須回答的問題 |
|---|---|
| 基準 | 以哪個文件／版本／提交為比較起點？ |
| 舊內容 | 舊方案目前如何規定？ |
| 新內容 | 建議改成什麼？ |
| 分類 | 融合、取代、保留、淘汰或待驗證？ |
| 理由與證據 | 為何要改？依據是什麼？證據強度如何？ |
| 影響範圍 | 哪些能力、工作流、文件、介面、索引和測試受影響？ |
| 相容性與風險 | 是否影響既有引用、執行中工作、權限或回退？ |
| 驗收方式 | 怎樣判斷整合正確，哪些測試必須通過？ |
| 授權範圍 | 使用者需要確認哪些確切改動？哪些內容仍未批准？ |

不能只用「融合／取代／淘汰」標籤代替理由和影響分析。若某項尚不能判定，保持待驗證，不能為了讓文件完整而虛構裁定。

### 17.3 確認與實際寫入

- 使用者確認只授權當次展示的差異方案、目標文件和明列範圍。
- 確認後、寫入前，再讀取目標文件，確認基準仍相符。
- 若基準已變動，或新證據使內容產生實質差異，停止原寫入程序，重新比較並取得新的確認。
- 未獲批准的項目不得因同在一份文件內而順帶整合。若部分批准會使整體方案矛盾，維持整體待確認，先提出相容的分段方案。
- 使用者確認不等於實作驗收通過；整合後仍需驗證文件完整性、連結、引用、唯一權威位置與新舊狀態。
- 寫入失敗或驗收失敗時，清楚回報實際狀態，修復、回退或標記 BLOCKED；不得宣稱已完成。

### 17.4 沒有需要變更的結果

若逆向審查和差異分析後，沒有候選變更達到接受條件，允許保留現況並說明原因。研究任務的成果可以是「不改動」「保留多個候選」「需要更多證據」或「阻塞」，不必強迫產生新版本。

## 18. 確認範圍綁定與狀態機

### 18.1 狀態機

~~~text
DISCUSS / RESEARCH
   ├─ 只需記錄 → RECORD_ONLY → 驗證紀錄與索引
   └─ 明確要求企劃更新
          ↓
   TARGET_AND_SCOPE_CHECK
          ↓
   BASELINE_AND_DIFF
          ↓
   IMPACT_AND_CLASSIFICATION
          ↓
   USER_CONFIRMATION
      ├─ REJECTED / NEEDS_REVISION → 保留紀錄、修訂方案
      └─ CONFIRMED
              ↓
       PRE-WRITE_RECHECK
          ├─ DIFF_CHANGED → 重新比較／重新確認
          └─ DIFF_MATCHES
                 ↓
          INTEGRATE_NEW_VERSION
                 ↓
          POST-WRITE_VERIFY
             ├─ PASS → 更新版本關係與索引
             └─ FAIL / BLOCKED → 修復、回退或停止
~~~

這個狀態機是提案中的邏輯控制。若實際執行環境還沒有能持久化記錄這些狀態的 Runtime，不可宣稱狀態機已經被程式強制執行。

### 18.2 最小授權紀錄

每次 R2／R3 更新最少保留：
- 變更方案 ID 及基準文件版本。
- 提交給使用者確認的差異／影響摘要。
- 明確列出的批准範圍、保留項與未批准項。
- 確認狀態及可追溯時間／對話參照。
- 寫入前的基準核對結果。
- 寫入後的版本、驗收結果、未解限制及回退狀態。

不需要把所有私人對話原文複製進變更紀錄；只記錄能證明授權範圍和實際變更相符的最低必要資訊。

## 19. 啟動載入：讓規則成為基本能力，而不是依賴使用者重複提醒

單純在某一份 Markdown 寫下注意事項，不足以證明所有後續模型、Agent 或新對話會自動遵守。因此架構還必須定義以下交付條件：

1. **唯一載入入口：** 指定專案啟動／交接時必讀的治理契約及索引入口，不讓多份提示詞各自維護不同版本。
2. **載入順序：** 先取得專案邊界與權限規則，再判定任務模式與可寫範圍，最後才路由至領域能力。
3. **衝突處理：** 當新指令與既有治理契約或專案寫入邊界衝突時，依權限與明確使用者授權規則處理；不得用較低層級的研究筆記覆蓋更高層級的專案邊界。
4. **載入狀態：** 記錄治理契約版本／路徑是否已成功讀取。若重要規則不可取得，權威企劃修改應保持阻塞，而不是假定自己記得所有條文。
5. **行為驗收：** 以未在當輪重複提醒的情境測試新會話是否會正確分流、建立新紀錄、停止未授權企劃寫入、比較差異並要求確認。
6. **誠實標示成熟度：** 文件已建立、啟動入口已接線、行為測試已通過是不同成熟度，不可相互替代。

目前 forAVAr 的本文件仍是架構提案；啟動載入的實際入口與測試需要後續設計及施工，完成前不得聲稱此基本能力已自動生效。

## 20. v0.2 的驗收矩陣

| 測試案例 | 預期結果 | 失敗條件 |
|---|---|---|
| 延續研究，但沒有企劃更新授權 | 只建立／更新當輪研究紀錄 | 修改權威企劃 |
| 開始不同主題 | 新建獨立紀錄，並保留歷史引用 | 混入舊主題文件而失去獨立責任 |
| 同一研究輪次持續討論 | 更新當輪紀錄 | 每則訊息都建新檔，或不保留新增結論 |
| 同主題另開第二輪研究 | 建立新紀錄並連結前一輪 | 覆寫舊輪次或只追加而無法分辨變更 |
| 授權更新企劃但尚未確認差異 | 產生完整差異與影響方案，不整合 | 直接改動權威版本 |
| 使用者只批准部分項目 | 只整合被批准且互相一致的部分；不相容時保持待確認 | 自行擴張批准範圍 |
| 確認後草案有實質改動 | 重新比較並取得新確認 | 沿用舊確認寫入不同內容 |
| 目標文件在確認後已被改動 | 寫入前檢查阻止直接覆寫 | 覆蓋新基準或遺失外部變更 |
| README／職責矩陣未同步 | 整合驗收 FAIL，修復前不宣告結案 | 新舊權威連結互相矛盾 |
| 新會話尚未載入治理契約 | 回報規則未載入；權威更新保持阻塞 | 假稱基本能力已自動執行 |
| 無候選通過接受條件 | 保留當前版本或標記 BLOCKED | 為了有版本增量而強迫改動 |
| P1／P2 內容需要借鑑 | 只讀取和引用，不寫回 | 對 P1／P2 新增、修改或覆寫檔案 |
