## 1. 來源與證據邊界

- 原始 ZIP：`參考資料/原始檔案/壓縮檔/P2_封包式問題解決架構_文件套件.zip`

- ZIP 含 4 個成員：對話紀錄 Markdown／DOCX、企劃書 v0.1 Markdown／DOCX。四個成員的解壓大小與 CRC32 均通過。
- 兩份 DOCX 各 17 個 OOXML 部件，內層大小／CRC 均通過；28 個內部 relationship targets 全部存在；Content Types 缺少宣告 0、孤立 Override 0。
- 企劃書標示 `v0.1 / PROPOSAL / 尚待確認，不代表已核准或實作`。這是設計提案，不是 P2 既有功能證明。

## 2. 核心設計主張

### 單一問題解決主線
**理解問題 → 決定做法 → 執行做法 → 檢查結果 → 修正與結案**

H0–H2 保持穩定；只有在能力選擇、條件判斷、策略分支或回退位置確實需要時才於 H3 展開。不同工作階段共用生命週期原則，不建立互相競爭的平行流程。

### 單一權威資料，多種派生視圖
- 功能樹表達功能歸屬。
- 因果／狀態關係表達觸發、前置條件、結果流向、失敗回退。
- 角色圖表達執行責任。
- 不同視圖從共同的權威資料衍生，避免各圖各自維護而漂移。

### 最小封包與中控契約
工作單位描述目標、必要輸入與前置條件、責任／允許動作、產物／證據、狀態與下一步／失敗回退。中控只定位合法下一步、檢查條件與權限、派送授權工作、接收結果／證據並推進或阻塞；不取代語意決策、施工或獨立驗收。

### 狀態與證據分離
狀態回答流程進度，證據回答為何可相信。靜態檢查、文件存在、模擬或推論不可冒充實際執行通過。

## 4. 必須保留的來源限制

- **ERR-001｜範圍措辭歧義：** 來源將訊息 1–13 描述為核心討論、14–15 描述為交付後續，同時又寫「共 13 則」。13 可能只指核心主題訊息，不能視為已證實的數字錯誤。
- **GAP-001｜已知來源缺口：** 訊息 1 前的助理回覆只保存結尾片段；完整原文未取得。
- **FMT-001｜格式功能損失：** 五個 sandbox URL 的文字在 DOCX 內可找到，但 DOCX 沒有對應的可點擊 hyperlink／外部關係；短標籤也有少量差異。
- **企劃書權威邊界：** 設計提案不自動成為 P2 已核准規格或實作證明。
