## 2. 核心設計主張

### 2.1 單一問題解決主線

核心流程：

**理解問題 → 決定做法 → 執行做法 → 檢查結果 → 修正與結案**

H0–H2 保持穩定；只有當能力選擇、條件判斷、策略分支或回退位置確實需要時，才在 H3 展開。不同工作階段應共用生命週期原則，不為規劃、施工、驗收各建立一套互相競爭的流程。

### 2.2 單一權威資料，多種派生視圖

- 功能樹表達「功能放在哪裡」。
- 因果／狀態關係表達「何時啟用、前置條件、結果交給誰、失敗回到哪裡」。
- 角色圖表達「誰負責執行」。
- 若同時需要多種圖，應從共同的權威資料衍生，避免各圖獨立維護後讓 AI 自行猜測它們的對應關係。

### 2.3 最小封包契約

一個需持久化或交接的工作單位至少描述：定位與目標、輸入與前置條件、責任／允許動作、產物及證據、狀態與下一步／失敗回退。缺少其中必要欄位時，無法可靠地由別的流程接手。

### 2.4 中控的最小職責

中控負責定位合法下一步、檢查前置條件／權限／資源、派送授權工作、接收結果與證據，並據結果推進、回退、阻塞或停止；不應取代語意決策、角色執行或獨立驗收。

### 2.5 狀態與證據分離

提案列出的 WAITING、READY、RUNNING、PASS、FAIL、BLOCKED 是待與既有 P2 狀態機對帳的候選，不可直接升格為權威狀態。狀態回答「進度到哪」，證據回答「為何可相信」。靜態檢查、文件存在、推論或模擬，均不能冒充實際執行通過。

### 2.6 能力條件與閉環

能力啟用至少要檢查觸發條件、輸入完整性、權限、資源、安全與衝突；程式可判定的硬條件交給驗證器，語意判斷須標示來源、假設與不確定性。結案應保留核心結果、決策、必要證據及下游需要的資料，並依規則封存／清理暫存。

## 4. 必須保留的來源差異與缺口

- **ERR-001｜計數範圍矛盾：** 對話紀錄同時出現「共 13 則訊息」與主訊息編號 1–15／共 15 則。13 可能是核心設計訊息數，但未獲原始聊天來源裁定，不改寫原文。
- **GAP-001｜前置回覆缺失：** 訊息 1 前的助理回覆只保留結尾片段；封包內兩種格式皆無法恢復完整前文。
- **FMT-001｜格式功能損失：** Markdown 的五個歷史 sandbox 連結未在 DOCX 主文件保留可點擊外部超連結。
- **GAP-002｜語意驗收未收口：** 第二輪非表格文字覆蓋篩查的 6-gram 覆蓋率為對話紀錄 98.88%／98.77%、企劃書 98.65%／98.55%；低覆蓋候選僅見交付連結／Word 標題編號表示，未發現高可信度實質缺章。逐段語意等價仍未被完全證明。
- **FALSE-001｜已排除的假陽性：** 企劃書 12.1 標題因 Markdown 標記造成字面差異，正規化後已找到對應，不是缺章。
