## 3. 直接確認的文件錯誤

### DOC-01｜架構提案 v0.2 的第 10 節清單編號次序錯亂

位置：`未來框架_封包生命週期與能力索引融合架構提案_v0.2.md`，第 10 節「防止架構隨功能增長而失控的規則」。

該清單先列 1–5，接著列 11–14，再回到 6–10。從內容看，這不是有意分組的編號，而是排序錯誤。

- 影響：引用特定規則時容易產生歧義；也削弱後續將規則轉成測試 ID 或唯一條款編號的可靠性。
- 嚴重度：中（文件品質／引用一致性）。
- 建議處理：在取得對架構提案的明確更新授權後，依原內容重排為連續 1–14，逐項比對文字，不改變規則語義，並重新檢查引用。
- 本輪處置：只記錄缺陷，不直接修改架構提案，以免把靜態驗收擴張成未授權的企劃更新。

### DOC-02｜跨文件職責矩陣的一列少一欄

位置：`跨文件重疊與唯一職責矩陣.md`，第 2 節文件責任表中「通用問題屬性導向方法選擇框架_v0.2.md」一列。

表頭有五欄，但該列只有四欄，因此「不可單獨用於證明」與「蒸餾策略」的內容錯位，無法正確表達唯一責任。

- 影響：文件職責、不可證明事項與蒸餾策略容易被誤讀；這直接破壞該矩陣原本要提供的導航與權威邊界。
- 嚴重度：中。
- 本輪處置：已在職責矩陣更新中補齊五欄，保留原本語意，並會在寫後重新讀回驗證。

## 4. 逆向思維：目前架構仍未封閉的漏洞

以下是文件證據能支持的架構缺口；除明確標為文件錯誤外，其餘均是尚待驗證的風險，不宣稱已在 Runtime 發生。

### ARCH-01｜「唯一權威來源」尚未完全落到具體資料契約

提案多處要求一個概念只維護一份正式定義、Current 不可由摘要取代、文件索引與職責矩陣不得衝突。但提案自己的裁定清單仍把「哪一份登錄表是能力、工作流、封包模板、狀態及職權的唯一權威來源」列為待決事項。

- 反例：能力目錄說版本 A 為 ACTIVE，封包模板仍引用版本 B，README 卻指向版本 C。
- 失效路徑：每份文件都符合自身格式，但系統整體沒有唯一真實狀態。
- 缺口：尚無 canonical path、Schema、ID 規則、衝突優先序與自動一致性檢查的已驗實作。
- 驗收條件：刻意製造兩個權威狀態衝突，系統必須在執行前阻擋並指向唯一裁決來源，不可自行挑一個較新的文字文件。

### ARCH-02｜R0–R3 風險分級仍偏定性

提案說分級依語義、風險與影響面決定，不依行數或檔案大小；但尚未把常見邊界情境轉成足夠明確的決策規則。

- 反例：只改一行卻改變寫入授權；或改動多個文件但純粹修正內部連結。不同操作者可能對同一工作判成不同風險級別。
- 失效路徑：簡單工作被過度治理，高風險工作反而走短路徑。
- 缺口：缺少風險判定表、典型案例與爭議處理規則。
- 驗收條件：準備一組固定邊界案例，由多次獨立判定比較一致性；所有涉及權限、權威、資料破壞及不可逆行為的案例，必須有明確的升級規則。

### ARCH-03｜確認範圍目前是流程設計，不是已被強制的授權機制

提案已描述 CONFIRMED、PRE-WRITE_RECHECK、DIFF_CHANGED、POST-WRITE_VERIFY 等狀態，但文件同時承認這只是邏輯狀態機，若沒有 Runtime 就不能聲稱程式會強制執行。

- 反例：使用者只批准差異 A；實際寫入時混入差異 B，或基準文件已被他人更新。
- 失效路徑：文字流程看似完整，實際工具仍能直接覆寫目標。
- 缺口：未見授權紀錄 Schema、確認內容指紋、寫入閘門與衝突時的強制阻擋證據。
- 驗收條件：在確認後修改草案或基準文件，寫入程序必須停止並要求重新比較／確認；未批准項不得寫入。

### ARCH-04｜啟動載入與跨會話遵守尚未驗收

提案正確指出，單獨把治理規則寫在 Markdown 中，不代表新的模型或會話一定會讀取並遵守。但目前文件尚未指向已執行的唯一載入器，也沒有跨會話行為測試收據。

- 反例：新會話只讀 README 或舊摘要，沒有載入治理契約，卻直接修改權威企劃。
- 失效路徑：架構依賴「應該被記得」的規則，而非可觀察的啟動前置條件。
- 缺口：無法由現存文件證明每次啟動載入了哪個版本、讀取失敗時如何阻塞、載入狀態如何保留。
- 驗收條件：在不重複提醒的全新會話，執行不同主題紀錄、未授權企劃更新、已確認範圍被改動三類測試；記錄載入版本和實際行為。

### ARCH-05｜測試矩陣尚未形成可重複的驗收套件

提案列出了多個預期案例，但測試案例清單不是測試本身，也不證明其結果已通過。

- 反例：文件宣稱「README／職責矩陣不同步時 FAIL」，但沒有自動檢查或固定人工核對表。
- 失效路徑：每輪都重新用自然語言判斷，標準隨操作者改變。
- 缺口：未見測試 ID、固定輸入、預期結果、執行方式、環境版本、實際結果與收據指紋。
- 驗收條件：把提案的關鍵案例轉成可重複的測試表；每筆都需要 PASS／FAIL／BLOCKED、證據位置、日期與被測版本。未執行者維持 NOT_EXECUTED。

### ARCH-06｜能力關係分析的範圍控制尚須落地

P2 候選架構指出能力關係可能組合爆炸，也反對把所有相似內容都歸為重疊。forAVAr 架構則要求依賴、路由、版本及變更影響分析。兩者的方向相容，但目前未見已驗證的關係資料模型或規模成本測量。

- 反例：新增一項能力後，要求與所有既有能力逐一比較，導致更新成本大幅增加；反過來，若只查名稱相似，則可能漏掉隱性依賴。
- 缺口：候選關係生成條件、關係邊的方向／版本／證據欄位、何時做局部檢查、如何標示 UNKNOWN，尚未形成可執行契約。
- 驗收條件：以逐步增長的能力集合量測分析時間、已知關係召回率與錯誤關係比例；在證據不足時必須保留 UNKNOWN，不自動判為相容。

### ARCH-07｜抽象層的命名有跨專案歧義

通用方法規格把問題屬性標成 P1、P2 等，而專案上下文也用 P1／P2 指不同的參考專案。

- 反例：交接摘要寫「P2 屬性不完整」，讀者無法第一時間確定是在談第二個問題屬性還是 P2 專案。
- 嚴重度：低至中；主要影響搜尋、交接與跨文件引用。
- 驗收條件：新建文件時以完整術語或具命名空間的 ID 交代首次出現的 P1／P2，並確認不影響既有含義。這項命名規則須在未來更新時再裁定，不在本輪直接改寫方法規格。

### ARCH-08｜記錄分流已改善，但來源證據與授權鏈仍不足

本輪已按主題拆出四份 P2 紀錄，並保留 RRSI 獨立紀錄。這解決了目前已識別的主題混放；但分流來源仍是先前整合稿，而不是完整可核對的原始對談匯出。

- 反例：研究摘要把某句要求標為使用者明確授權，但原始對談無法回溯，後續人員把摘要誤認為可寫入正式企劃的批准。
- 缺口：記錄本身已有主題與來源欄位概念，但沒有每個重大決策／授權都綁定原始訊息參照的實際資料紀錄。
- 驗收條件：對涉及企劃更新、權限、刪除、範圍擴大等重大裁定，沒有可核對的原文依據就標記 UNVERIFIED，不以整理稿推斷批准。

## 5. 架構中值得保留的部分

下列原則目前沒有發現直接矛盾，適合作為後續候選基線，但仍需行為驗收：

1. **以責任分層，而非過早微服務化。** L0–L7 表達不同責任，不要求每層都變成獨立服務。
2. **區分工作封包、能力、工作流、產物與證據。** 不把單一任務狀態與永久能力成熟度混在一起。
3. **明確分開研究紀錄權限與企劃更新權限。** 記錄成果不自動成為正式方案。
4. **確認需綁定具體差異，寫入前重核，寫入後驗收。** 能直接處理本輪主題偏移的部分原因。
5. **允許 UNKNOWN、BLOCKED 或維持現狀。** 不為了讓文件看似完整而捏造裁定或強迫更新。
6. **將索引同步列為驗收條件。** README 和職責矩陣各有唯一責任，不應各自複製整套規則。

## 6. 正式採納前必須補完的 Gate

| Gate | 必須具備的交付物 | 通過條件 |
|---|---|---|
| G1｜唯一權威 | 權威來源清單、canonical path、Schema／ID／版本規則 | 同一概念只有一個可裁決的權威狀態；衝突會阻塞 |
| G2｜治理載入 | 唯一啟動入口、載入順序、載入失敗行為及版本證據 | 新會話可在未重複提醒下遵守最低權限與分流規則 |
| G3｜變更授權 | 差異方案 ID、基準指紋、批准範圍、確認記錄及寫入前核對 | 任何未批准差異或基準改變都會停止寫入 |
| G4｜可執行測試 | 對應驗收矩陣的測試輸入、預期結果、執行器與收據格式 | 關鍵案例實際執行；未測項維持 NOT_EXECUTED |
