## 0. AI 使用規則

1. 先辨識任務目標、輸出、授權、風險及成功條件，再選流程；不得因本文件存在就強制每項任務跑完整流程。
2. 選用流程後，讀取其「權威文件」。本索引只存精簡摘要，不複製完整規格。
3. 同一任務可組合多個流程；依賴流程先執行，非必要模組可跳過並說明理由。
4. 來源不足、版本衝突、驗證未執行時，標記 UNKNOWN／CONFLICT／NOT_VERIFIED／BLOCKED；不得用推測補成確定事實。
5. 文件寫入、結構檢查、內容驗證、Runtime 驗收是不同狀態，不可互相代替。
6. forAVAr 是本專案唯一可寫入目標；P1、P2 僅供唯讀參照。正式企劃未獲明確「更新企劃」指令不得改寫。

## 2. CF-004｜對話成果轉成可追溯文件

### 名稱
對話成果轉成可追溯文件流程（Conversation-to-Canonical-Records, C2CR）。

### 簡述內容
把對話中新增的判斷、證據及待辦，整理成可搜尋、去重、可追溯且不互相矛盾的文件更新；不把推論升格成事實，也不把文件存在視為功能已驗證。

### 功能
- 維持單一權威入口與明確文件職責。
- 將詳細問題集中到問題清單；主分析只保留摘要、問題 ID 與連結。
- 保留來源、版本、證據等級、限制、未知和衝突。
- 同步索引與責任矩陣，讓後續 AI 能定位內容並接續工作。
- 控制寫入範圍，避免未授權修改正式企劃或唯讀參照專案。

### 觸發條件
當使用者要求將對話結果寫入專案文件、合併／蒸餾多份分析、整理問題清單、更新文件索引或準備交接時啟用。純一次性問答且無持久化需求時不啟用。

### 流程
1. **授權與範圍閘門**：確認唯一可寫入的 repository、允許路徑、是否涉及正式企劃、交付物及禁止事項。權限不明即停止寫入。
2. **既有上下文盤點**：讀取總索引、去重規範、唯一職責矩陣、相關主文件與最新來源；搜尋是否已有同職責文件。
3. **變更映射**：把每項新內容映射為「主張／證據／問題／決策／待辦」之一，指定唯一存放文件和預期更新位置。
4. **來源與證據核對**：核對原始檔、版本、路徑、雜湊、數量或相關輸出；區分直接觀察、已執行驗證、外部主張、推論、未知與阻塞。只對本任務需要且可取得的欄位執行。
5. **職責分流**：原始證據留在原件／清冊；完整分析放主分析；根因、案例、狀態與處理追蹤放問題清單；摘要只保留結論、ID 與連結；流程規則放專用流程文件；README 負責導航；責任矩陣界定文件分工。
6. **去重與衝突處理**：刪除重複敘述，不刪除獨有證據、限制或反例。相似概念但職責不同則分開並互相引用。權威來源衝突未解時，記錄衝突，不自行裁定。
7. **最小變更寫入**：只修改已授權文件；先寫入正文，再依實際路徑更新索引與責任矩陣。每次更新後重新讀取最新內容／版本，再進行同檔下一次更新，避免使用過期內容覆寫。
8. **獨立驗收**：檢查必要主張是否有來源或明確標記、數量／指紋是否一致、連結是否存在、索引是否指向正確文件、重複責任是否解除、未授權路徑是否未變更。只宣告實際執行過的檢查結果。
9. **結案與交接**：回報新增／修改文件、核心結果、驗收範圍、未完成檢查、剩餘衝突及下一步；提供可直接開啟的權威文件連結。

### 邏輯與不可違反的規則
- **權威優先**：原始來源及其明確版本優先於衍生摘要；摘要不得反向覆寫來源事實。
- **一項內容一個主責位置**：同一詳細內容只維護一份權威正文；其他文件用短摘要和連結引用。
- **問題與報告分離**：主報告回答「發現什麼、證據到哪裡」；問題清單回答「問題為何、影響什麼、如何追蹤」。兩者不得重複保存完整根因分析。
- **證據與推論分離**：每項重要結論必須可追溯，否則標為 INFERRED、NOT_VERIFIED、CONFLICT 或 BLOCKED。
- **不以缺席推導不存在**：未找到、無法讀取、未執行，不等於不存在、損壞或通過。
- **數量守恆**：若有明確預期總數，必須將項目分為已處理、明確阻塞或不支援；無法對帳不得宣告完整。
- **寫入與驗收分離**：提交成功只證明寫入成功；連結、內容、行為與 Runtime 須分別驗證。
- **最小必要變更**：不為了對齊索引而改動無關文件；不在授權範圍外修正「看起來相關」的問題。
- **條件式深度**：簡單低風險任務可縮短流程；高風險、跨文件、多來源或需交接任務才展開完整對帳與反證。
- **失敗即保留狀態**：任何檢查未執行、結果不明或發現衝突，必須保留未完成狀態，不得自動標記 PASS。

### 最低驗收條件
- 每項重要新增結論均有來源，或清楚標為推論／未知。
- 每份更新文件仍符合其唯一責任，沒有複製整段其他文件。
- 必要的目錄、相對連結和交叉引用已更新且實際檢查。
- 數量、版本、指紋和狀態沒有未說明的互相矛盾；無法確認的差異已登錄。
- 寫入僅發生於授權範圍。
- 回報清楚分開「已寫入」「已靜態檢查」「已執行測試」和「尚未驗證」。

## 3. 通用根源模型

將 CF-004 抽象成七個可組合的操作，不綁定 ZIP、P2 或任何特定領域：

**授權 → 盤點 → 證據化 → 分責 → 去重／處理衝突 → 變更 → 驗收／交接**

| 原始操作 | 要回答的唯一問題 | 產出 |
|---|---|---|
| 授權 | 哪些資料與路徑允許讀／寫？哪些行為禁止？ | 範圍與權限邊界 |
| 盤點 | 已有什麼、由誰負責、哪個來源較權威？ | 來源圖與文件職責映射 |
| 證據化 | 每項主張由什麼支持？哪些仍未知？ | 主張—來源—證據狀態映射 |
| 分責 | 每項內容應由哪份文件唯一維護？ | canonical path 與交叉引用方案 |
| 去重／處理衝突 | 哪些是真重複，哪些是獨有差異或權威衝突？ | 去重結果與未決問題 |
| 變更 | 為達成要求，最少需修改哪些授權文件？ | 可追溯的實際變更 |
| 驗收／交接 | 變更是否符合內容、連結、狀態、權限及完整性條件？ | 驗收證據、未完成項與交接入口 |

此模型的通用性來自共同的控制問題，不表示七個操作在每個任務都必須逐項執行。對單一簡單文件，可合併步驟；對高風險或多來源任務，應保留逐步證據。

## 4. 失效分支與處理規則

| 觸發情況 | 必須採取的處理 | 禁止的結論 |
|---|---|---|
| 找不到預期來源 | 核對權威索引、路徑、版本和替代來源；登錄缺口。 | 「檔案不存在」除非已充分驗證。 |
| 兩個權威來源互相衝突 | 保留兩端證據、來源時間／版本與影響，標記 CONFLICT。 | 未核實前自行選一端當真。 |
| 內容重複但文件職責不同 | 保留各文件，移除重複正文並建立引用。 | 只因用詞相似就合併／刪除。 |
| 文字相同但來源版本不同 | 保留來源鏈及版本身分，記錄等價範圍。 | 把內容相同等同來源可互換。 |
| 無法完成檢查 | 明示未檢查項、原因與影響。 | 將未檢查當作 PASS。 |
| 正文已更新但索引／引用未更新 | 維持未結案，補齊導航並重查。 | 宣告文件更新完整。 |
| 發現超出本輪授權的缺陷 | 登錄問題與建議位置，等待合適授權。 | 順手修改正式企劃或唯讀專案。 |

## 6. CF-006–CF-008｜版本治理、分流與雙向引用

### 觸發後的執行契約

1. 先讀取[版本治理與分流規範](./版本治理與分流規範.md)、[文件與分支索引](./文件與分支索引.md)和[變更追溯總表](./變更追溯總表.md)。
2. 依 DOC_ID／TOPIC_ID 判斷新內容是否屬既有 MASTER、既有分支、獨立子題或原始 SOURCE。不得只依檔名或語義相似度合併。
3. 先起草 MASTER 摘要、TOC、分支索引、incoming／outgoing 引用與變更事件，再寫入目標正文；不得先刪除舊檔再補回鏈。
4. 一般 AI 可讀文件不得超過 8,000 字元；MASTER 目標不超過 6,000 字元。超限依語義分流、逐項對帳，不得任意截斷。
5. 每個一般邏輯文件最多 3 份完整版本：CURRENT 一份、BACKUP 最多兩份。原始對話是分開的 SOURCE 事件，不算同一 MASTER 的版本，且不作日常索引入口。
6. 每條現行引用都有可反查的入鏈紀錄；更新後重新讀回實際檔案及連結。未完整掃描的引用圖標記 PARTIAL。
7. 只有完成內容守恆、索引／雙向引用核對及必要檢查後，才可輪替備份或把舊檔標為 BACKUP_ONLY。
8. 變更事件寫入[追溯總表](./變更追溯總表.md)。未執行檢查標為 NOT_VERIFIED／BLOCKED；不得以提交成功代替內容驗收。

### 禁止事項

- 不把多輪同題對話各自列為現行知識入口；它們必須歸入單一 MASTER，原文作來源備份。
- 不以語義相似為理由合併不同職責的分支。
- 不對舊版建立新的一般內容引用；歷史版本只從追溯表按需調閱。
- 不因摘要成功建立就宣稱原始來源及獨有證據已完整保留。


## 7. CF-009｜SOP 固定流程與演化管理

### 觸發後的執行契約

1. 判斷是否已有符合觸發條件的 CURRENT SOP；有則先讀標準流程，不重新設計整套方法。
2. 依 SOP 規範辨識任務等級、授權邊界、必要輸入、預期輸出及驗收門檻。
3. 依標準步驟執行，只在明確觸發條件成立時進入特定分支；缺前置條件或無回復方案時按停止規則處理。
4. 分別驗證內容、來源、引用、權限及實際執行結果；不得用單一「完成」標記取代分層驗收。
5. 對每次非瑣碎 SOP 執行，在[執行與演化台帳](./SOP執行與演化台帳.md)追加一列結果、偏差、驗收證據和改良候選。
6. 執行失敗不直接改寫 SOP。只有已證實且可重現的根因，才轉成簡短的前置檢查、分支條件或停止規則。
7. SOP 候選依[固定流程與演化管理規範](./SOP固定流程與演化管理.md)進行試行、回歸檢查和定版；沒有達到驗收門檻時維持 DRAFT／TRIAL。

### 不可違反的規則

- 流程目錄只做導航；唯一完整步驟放在 SOP 權威文件，不複製到多份索引。
- 歷史案例說明某次發生了什麼；SOP 只列目前有效且有證據支持的步驟。
- 常規成功只記一列；只有例外、根因及改良候選才保存詳細案例。
- SOP 內容被文件化不等於模型已自動執行或被 Runtime 強制；有效性必須由台帳中的實際案例驗證。
